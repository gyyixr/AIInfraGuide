MLA 要解决的问题可以直接用一句话表达：历史 token 已经计算过，下一步生成时还要为它们保存多少数据？

本节讨论 V2/V3 系列的经典 MLA。
V4 的共享 KV、压缩注意力和分组输出投影另见 2.4；不要把 V3 的缓存公式原封不动套到 V4.1。

核对日期：2026-11-07。
主要证据是 [V2 论文](https://arxiv.org/abs/2405.04434)、[V3 论文](https://arxiv.org/abs/2412.19437) 和 [V3 固定版本 model.py](https://github.com/deepseek-ai/DeepSeek-V3/blob/9b4e9788e4a3a731f7567338ed15d3ec549ce03b/inference/model.py)。
下文所有小矩阵均为教学构造，不是导出的模型权重。

## 1. 从缓存开始，而不是从缩写开始

自回归生成第 $t$ 个位置时，当前 query 要访问此前所有可见位置的 key/value。
如果使用 $H$ 个头、每头 $d_k$ 维 key、$d_v$ 维 value，普通 MHA 的每层每 token 缓存为：

$$
N_{\mathrm{MHA}}=H(d_k+d_v).
$$

若元素占 $b$ 字节、层数为 $L$、批内总缓存 token 数为 $T_\Sigma$：

$$
M_{\mathrm{MHA}}=L T_\Sigma H(d_k+d_v)b.
$$

这不包括权重、workspace、页表、碎片以及运行时元数据。
这里的 $T_\Sigma$ 是所有请求的 token 数之和，不一定是 batch size 乘同一个长度。

缓存有两个成本：存放它需要容量，decode 反复读取它需要带宽。
因此，即使模型权重已经装得下，长上下文仍可能因 KV 容量或读取时间失去吞吐。

## 2. 先约定矩阵方向

本文用列向量说明单 token，用批量行向量说明代码。
这两种记法相差转置，不能在一条推导中随意混用。

| 符号 | 列向量写法的 shape | 意义 |
|---|---|---|
| $h_t$ | $[D]$ | 本层输入 |
| $W^{DKV}$ | $[r,D]$ | KV 下投影 |
| $c_t$ | $[r]$ | 压缩 KV latent |
| $W_i^{UK}$ | $[d_c,r]$ | 第 $i$ 头内容 key 上投影 |
| $W_i^{UV}$ | $[d_v,r]$ | 第 $i$ 头 value 上投影 |
| $q^C_{t,i}$ | $[d_c]$ | 不含 RoPE 的 query 部分 |
| $q^R_{t,i}$ | $[d_r]$ | 含 RoPE 的 query 部分 |
| $k^R_t$ | $[d_r]$ | 各头共享的位置 key |

实际代码中会对下投影 latent 做 RMSNorm。
为了把吸收推导写清楚，下面直接把经过这一归一化的结果记为 $c_t$。

## 3. 低秩压缩：只保存共同的来源

普通 MHA 给每个头保存不同的 K/V。
MLA 先构造一个所有头共享的来源：

$$
c_t=\operatorname{RMSNorm}(W^{DKV}h_t).
$$

再由它生成不同头的内容 key/value：

$$
k^C_{t,i}=W_i^{UK}c_t,\qquad v_{t,i}=W_i^{UV}c_t.
$$

如果历史位置保留了 $c_t$，理论上便能重建这些 K/V。
这不意味着 inference 应在每一步真的把所有历史位置重建一次。
下一步的矩阵吸收正是为了避免这种开销。

这也不是“对已经训练好的任意 MHA 做无损压缩”。
MLA 本身就是带低秩约束的参数化，模型按该参数化训练。

## 4. 为什么普通 RoPE 妨碍吸收

不考虑位置编码时，点积可以改写为：

$$
(q^C_{t,i})^\top W_i^{UK}c_s
=\left((W_i^{UK})^\top q^C_{t,i}\right)^\top c_s.
$$

左边先把历史 latent 展开成 key。
右边先把当前 query 投影到 latent 空间。

加入普通 RoPE 后，表达式变成：

$$
q_t^\top R_t^\top R_s W^{UK}c_s.
$$

$R_t^\top R_s$ 随历史位置 $s$ 变化。
一般不能用一组与 $s$ 无关的固定矩阵，把这一整段吸收到当前 query 中。

不能随意交换矩阵顺序：通常 $RW\ne WR$。
“都是线性算子”只允许在维度匹配时结合，不允许任意交换。

## 5. 解耦 RoPE：分开内容和位置

MLA 使用两部分打分：

$$
\ell_{t,s,i}=
\frac{(q^C_{t,i})^\top k^C_{s,i}+
(q^R_{t,i})^\top k^R_s}{\sqrt{d_c+d_r}}.
$$

内容部分可以做矩阵吸收。
位置部分保留一个小的、跨头共享的 RoPE key。

$$
q^R_{t,i}=R_t\widetilde q^R_{t,i},\qquad
k^R_s=R_s\widetilde k^R_s.
$$

因此历史位置只需保存：

$$
[c_s;k^R_s]\in\mathbb R^{r+d_r}.
$$

Query 的位置分量仍然可以随头不同。
共享的是历史位置的 RoPE key，而不是要求所有头的 query 相同。

## 6. Query 侧也可以低秩，但用途不同

V3 的 query 路径也经过低秩瓶颈：

$$
c_t^Q=\operatorname{RMSNorm}(W^{DQ}h_t),
\quad [q^C_t;\widetilde q^R_t]=W^{UQ}c_t^Q.
$$

KV 低秩直接减少跨时间保存的缓存。
Query 低秩主要影响当前 token 的投影参数、计算和激活。
历史 query 通常不用留到后续 decode 步，所以两者的收益不能混为一谈。

## 7. 一组完整数例：先展开 key

取一个头、两个历史位置，忽略位置项和缩放，只比较内容部分。
令：

$$
c_1=\begin{bmatrix}1\\2\end{bmatrix},\quad
c_2=\begin{bmatrix}3\\1\end{bmatrix},\quad
W^{UK}=\begin{bmatrix}1&0\\0&2\\1&1\end{bmatrix}.
$$

当前 query 为：

$$
q=\begin{bmatrix}2\\1\\-1\end{bmatrix}.
$$

先展开两个 key：

$$
k_1=\begin{bmatrix}1\\4\\3\end{bmatrix},\qquad
k_2=\begin{bmatrix}3\\2\\4\end{bmatrix}.
$$

于是：

$$
q^\top k_1=2+4-3=3,
\quad q^\top k_2=6+2-4=4.
$$

所有历史位置都展开 key 的实现，在这里保存的是两个三维向量。

## 8. 同一组数例：吸收进 query

先计算：

$$
\bar q=(W^{UK})^\top q
=\begin{bmatrix}1\\1\end{bmatrix}.
$$

再与 latent 点积：

$$
\bar q^\top c_1=3,\qquad
\bar q^\top c_2=4.
$$

打分完全一致。
核心变化是先处理当前一个 query，历史位置仍保留二维 latent。

softmax 后：

$$
p_1=\frac{e^3}{e^3+e^4}=0.268941,\qquad
p_2=0.731059.
$$

这里用未缩放 logits 是为了手算清楚。
真实模型使用同一个正确 softmax scale，两条路径仍应一致。

## 9. Value 也能把展开推迟

令：

$$
W^{UV}=\begin{bmatrix}1&1\\2&0\end{bmatrix}.
$$

先展开再加权：

$$
v_1=[3,2]^\top,\quad v_2=[4,6]^\top,
\quad o=p_1v_1+p_2v_2.
$$

得到：

$$
o\approx[3.731059,4.924234]^\top.
$$

也可以先对 latent 加权：

$$
z=p_1c_1+p_2c_2
\approx[2.462117,1.268941]^\top.
$$

再计算 $W^{UV}z$，得到相同结果。
这把对很多历史位置的 value 上投影，移成对聚合结果的一次投影。

后续输出矩阵还可与 value 上投影进行数学上的组合。
实际实现是否物理合并权重，取决于量化、布局、张量并行和 GEMM 形状。
数学可结合不等于所有结合方式都更快。

## 10. V3 配置的缓存账本

V3 671B 配置使用 $H=128$、$d_c=128$、$d_r=64$、$d_v=128$、$r=512$。
参数依据 [config_671B.json](https://github.com/deepseek-ai/DeepSeek-V3/blob/9b4e9788e4a3a731f7567338ed15d3ec549ce03b/inference/configs/config_671B.json)。

若比较相同头数与展开维度的朴素 K/V 缓存：

$$
128(128+64+128)=40960\ \text{elements/token/layer}.
$$

MLA latent 缓存为：

$$
512+64=576\ \text{elements/token/layer}.
$$

以两者均为 BF16 的简化比较：

| 对象 | 每层每 token | 61 层每 token |
|---|---:|---:|
| 朴素展开 K/V | 81920 bytes | 4997120 bytes |
| MLA latent + RoPE key | 1152 bytes | 70272 bytes |

两者比值约 $71.11$。
这是指定参照下的元素数量比较，不是“MLA 对任意 GQA 都节省 71 倍”。
若参照是少量 KV heads 的 GQA，比值会明显不同。

## 11. 批量 shape 逐项走一遍

取 $B=2,S=3,T=5,H=4,r=8,d_c=4,d_r=2,d_v=4$。
这些维度仅用于理解。

| 步骤 | 输入 | 输出 |
|---|---|---|
| KV 下投影并拆分 | `[2,3,D]` | latent `[2,3,8]`，位置 `[2,3,2]` |
| Query 上投影 | `[2,3,rq]` | `[2,3,4,6]` |
| 拆分 query | `[2,3,4,6]` | 内容 `[2,3,4,4]`，位置 `[2,3,4,2]` |
| 内容 query 吸收 | `[2,3,4,4]` | `[2,3,4,8]` |
| 内容打分 | query 与 cache `[2,5,8]` | `[2,3,4,5]` |
| 位置打分 | query 与 cache `[2,5,2]` | `[2,3,4,5]` |
| softmax | `[2,3,4,5]` | `[2,3,4,5]` |
| latent 加权 | attention 与 cache | `[2,3,4,8]` |
| value 上投影 | `[2,3,4,8]` | `[2,3,4,4]` |
| 合头与输出投影 | `[2,3,16]` | `[2,3,D]` |

数学上写出了 scores 张量，并不要求高性能内核把整个 scores 写入 HBM。
FlashAttention/FlashMLA 类内核可以分块计算并维护在线 softmax 状态。

## 12. 源码定位：从变量名回到公式

固定版本的 `MLA` 同时包含 `naive` 与 `absorb` 路径。

| 代码对象 | 对应数学对象 | 观察重点 |
|---|---|---|
| `wkv_a` | 下投影与位置 key 投影 | 输出后按 rank/rope 维拆分 |
| `kv_norm` | latent RMSNorm | 不能跨过非线性归一化随意合并 |
| `wkv_b` | $W^{UK},W^{UV}$ | reshape 后按 key/value 维切片 |
| `q_nope` | 内容 query | absorb 后最后一维从内容维变为 rank |
| `kv_cache` | $c_s$ | 不含 head 维 |
| `pe_cache` | $k_s^R$ | 不含 head 维 |
| `einsum bshc,btc` | latent 内容打分 | `c` 是 rank |
| `einsum bsht,btc` | latent 加权 | `t` 为历史位置 |

顺序读 `__init__`、`forward`、两个分支，再读并行 Linear。
不要只看类名后便推断其 GPU 执行策略。

## 13. Prefill 和 decode 为什么可能选不同路径

Prefill 同时处理很多 query，矩阵形状大，展开后进行高吞吐 GEMM 可能划算。
Decode 的 query 很少，反复读历史缓存的成本更突出，压缩表示通常更重要。

两种路径的数学目标相同，但量化顺序、累计顺序和 dtype 可带来数值差异。
因此测试需分别核对：

1. FP64 小矩阵代数等价。
2. BF16/FP8 容差下的 logits 误差。
3. token mask 与位置偏移是否一致。
4. 真正目标设备上的端到端时延。

仅通过第一项不能宣布获得生产加速。

## 14. 自包含小实验

下面代码可以直接核对本节吸收等价；只依赖 NumPy。
它是数学参考，不是 FlashMLA benchmark。

```python
import numpy as np

C = np.array([[1., 2.], [3., 1.]])
UK = np.array([[1., 0.], [0., 2.], [1., 1.]])
UV = np.array([[1., 1.], [2., 0.]])
q = np.array([2., 1., -1.])

scores_expand = (C @ UK.T) @ q
scores_absorb = C @ (UK.T @ q)
np.testing.assert_allclose(scores_expand, scores_absorb)

p = np.exp(scores_expand - scores_expand.max())
p /= p.sum()
out_expand = p @ (C @ UV.T)
out_absorb = (p @ C) @ UV.T
np.testing.assert_allclose(out_expand, out_absorb)
print(scores_expand, p, out_absorb)
```

增加 RoPE 时，要在两条路径使用同一份位置项。
若把非线性 RMSNorm 移到矩阵之外，两条路径通常不再等价。

## 15. 反例与适用边界

**缓存少，不保证 attention FLOPs 一定更少。**
吸收后 query 的维度可能比原内容头维更大，计算量与访存量之间存在交换。

**量化不是矩阵吸收。**
前者减少每元素位宽，后者改变存储表示与计算顺序，两者可以组合但误差来源不同。

**低秩不是低参数 LoRA 微调。**
这里是基础架构的一部分，不能把 `q_lora_rank` 的命名误读成只训练小适配器。

**并行分片不能机械除以 TP。**
内容头投影可以分片，但共享 latent cache 可能复制；必须查看具体引擎的布局。

**KV Cache 不等于训练激活。**
训练反向还要保留或重算更多中间结果，本节缓存公式不能当训练显存总公式。

## 16. 自测与答案

**问题 1：为什么 query 的低秩不直接减少历史 KV？**

答案：历史 cache 保存 key/value 来源，query 通常在当前步用完即释放。

**问题 2：MLA 每 token 为什么还要存位置 key？**

答案：RoPE 的位置依赖阻碍把完整 key 投影吸收到一个与历史位置无关的 query 变换中。

**问题 3：$W^{UV}\sum_s p_sc_s$ 与 $\sum_s p_sW^{UV}c_s$ 为什么相等？**

答案：固定线性映射对加权和可分配；若中间插入逐 token 非线性则不能这样移。

**问题 4：把 `576` 再乘 128 个头对不对？**

答案：不对。这一 latent 与小位置 key 已在头间共享，乘头数会重复计数。

**问题 5：朴素路径与吸收路径 logits 不一致，先查什么？**

答案：矩阵方向、head reshape、RoPE布局、softmax scale、mask和量化位置。

**问题 6：为什么不能声称本节证明了 H800 上的吞吐？**

答案：代数等价与元素计数未测量设备、内核调度、带宽、batch及服务开销。

**问题 7：本节公式能直接算 V4.1 的890字节吗？**

答案：不能。V4.1还有序列压缩、跨层共享和FP4布局，需用2.9的账本。
