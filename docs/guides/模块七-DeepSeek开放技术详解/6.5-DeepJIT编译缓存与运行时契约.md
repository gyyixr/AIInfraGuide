## 1. JIT 不只是调用一次编译器

一个算子库要支持不同 GPU、shape、精度和 tile 参数，经常需要在运行时生成或选择专门的 kernel。真正难的部分包括：如何判断已有二进制仍然有效、如何安全共享缓存、怎样加载到设备、在哪条 stream 上执行、失败时如何退回。

DeepJIT 将这些重复的运行时工作集中起来，使 DeepGEMM、DeepEP 等消费者可以专注于各自的 device code。

本节核对官方快照：

```text
deepseek-ai/DeepJIT
6e4bba88ee9e73a0986714f7f6bb45590ebeb04d
核对日期：2026-11-07
```

它是面向 CUDA 与 Ascend 的 header-only C++20 JIT runtime，不是把任意 Python 函数自动变成最优 GPU kernel 的编译器，也不保证 CUDA 源码可以直接转换成 Ascend 源码。

## 2. 五层对象与责任

| 层次 | 输入输出 | 主要责任 |
|---|---|---|
| 算子库 | shape/dtype/布局 → kernel 配置 | 数学语义、tile选择、代码生成 |
| DeepJIT | source/options → 编译/缓存/加载对象 | 复用和生命周期 |
| 设备编译器 | CUDA/Ascend源码 → 设备二进制 | 指令选择、寄存器分配等 |
| Driver/ACL | 二进制 → 可执行kernel | 设备模块加载、启动 |
| 框架stream | tensor依赖与执行顺序 | 与前后算子协作 |

应用通常仍需要一个 host C++/Python 扩展。所谓“不在安装时编译所有 CUDA kernel”，并不等于没有 host 扩展构建、没有编译器依赖或完全没有冷启动。

## 3. 一次调用的完整状态流

```text
算子收到输入及配置
  → 确认当前设备与后端
  → 形成源码、tracked includes、编译选项
  → 计算cache digest
  → 查询已加载的内存缓存
      命中：直接取得kernel
      未命中：查询磁盘cache roots
        命中：检查/加载已发布的设备二进制
        未命中：临时目录编译 → 同步 → 原子发布
  → 设备模块加载
  → 在约定stream启动
  → 保持模块和参数对象活到消费结束
```

这里有三种常见“命中”：

1. 已经加载到本进程的 kernel 命中。
2. 本机磁盘上已有二进制，但本进程尚未加载。
3. 共享文件系统上命中，需要网络读取后再加载。

它们都避免完整编译，却具有不同延迟，benchmark 不能统一写成一个 warm 状态。

## 4. 一个正确缓存键至少要回答什么

缓存键要判断：本次请求是否可以安全复用某份二进制。仅使用函数名或输入 shape 显然不够。

本快照 CUDA digest 包含的关键类别：

- 应用提供的 `extra_signature`。
- 完整 `nvcc --version` 输出的摘要。
- 实际生效的编译选项。
- post hook 的路径和文件内容摘要。
- 源码及 tracked include tree 的解析摘要。

每部分带长度编码，避免不同字段的连接产生歧义。实际使用双状态 FNV-1a 形成 32 字符十六进制摘要；它是快速缓存校验值，不是加密安全散列。

### 4.1 为什么长度前缀必要

朴素拼接时：

```text
字段组A: ["ab", "c"] → "abc"
字段组B: ["a", "bc"] → "abc"
```

两个不同配置可能得到相同字节串。显式长度编码则分别是 `2:ab1:c` 与 `1:a2:bc`，边界不再依赖分隔符是否出现在内容里。

同理，二进制字符串可能包含零字节，不能用普通 C 字符串结束约定替代明确长度。

### 4.2 编译 flags 的顺序可能有语义

`-DVALUE=1 -DVALUE=2` 与相反顺序不能默认视为等价。构造规范化 JSON 时可以排序对象字段，但不应随意排序编译参数数组。

一个教学 key 例子如下。它使用 SHA-256 方便标准库复现，**不模拟 DeepJIT 的实际 FNV digest**：

```python
import hashlib
import json

def teaching_cache_key(source, flags, compiler, dependencies, extra):
    record = {
        "source": source,
        "flags": list(flags),  # 保持顺序
        "compiler": compiler,
        "dependencies": dependencies,
        "extra": extra,
    }
    data = json.dumps(record, sort_keys=True, separators=(",", ":")).encode()
    return hashlib.sha256(data).hexdigest()

base = teaching_cache_key("kernel", ["-DA=1", "-DA=2"], "nvcc-X", {}, "abi-1")
other = teaching_cache_key("kernel", ["-DA=2", "-DA=1"], "nvcc-X", {}, "abi-1")
assert base != other
assert base != teaching_cache_key("kernel", ["-DA=1", "-DA=2"], "nvcc-X", {}, "abi-2")
```

## 5. 未自动发现的环境也是输入

固定 README 明确列出一些不会被自动完整发现的隐式条件，例如：

- `NVCC_PREPEND_FLAGS` / `NVCC_APPEND_FLAGS`。
- `CPATH` 或 host 编译器选择。
- 未纳入 tracked tree 的第三方头文件变化。
- 应用特定的 ABI 或外部依赖变化。

因此有两种工程选择：限制隐式环境，让构建更可控；或者把这些影响编码进 `extra_signature` / 显式编译参数。

版本号一样的编译器也不必然代表全部工具链一样，完整可复现实验应记录环境来源和依赖锁定方式。

### 5.1 include 路径与 include 内容

该实现有意不把 `Config::include_dirs` 的路径本身直接计入相同一类 flags 摘要，而依靠 tracked include 内容。这样可允许相同内容在不同目录下复用。

但如果源码使用 `__FILE__` 等依赖路径的行为，移动相同内容可能改变编译结果。此时“内容相同所以等价”的假设需要重新检查。

显式写进编译 flags 的 `-I...` 仍属于实际 flags，规则也不一样。不要把“某类 include 路径被排除”泛化成所有路径都不影响 key。

### 5.2 内容摘要本身也有缓存生命周期

把内容哈希纳入 key，不等于每次调用都重新读取全部依赖文件。该固定实现会在线程内缓存 post-hook 的文件哈希，修改 hook 后需要按文档重启进程；tracked header 的摘要也可在 runtime 生命周期内缓存，修改头文件后需要重新建立相应 runtime。

因此，长活进程中直接热改一个文件，不保证下一次调用立刻生成新 digest。开发与部署时应记录 runtime 创建边界，使用明确的重启/重建和新 `extra_signature` 策略，并先等待旧执行结束；不能把缓存失效寄托在一次磁盘文件修改上。

## 6. 冷启动成本怎样计算

假设一次完整编译 1200 ms，查找/解析 2 ms，设备加载 15 ms，单次 kernel 0.05 ms。这些是教学假设：

| 状态 | 主要成本 |
|---|---|
| 完全冷启动 | 约 1217.05 ms |
| 磁盘命中但未加载 | 仍有读取/解析/设备加载 |
| 进程内已加载 | 主要为接口与kernel执行 |

如果一个任务只运行 100 次、每次其他计算 5 ms，1.2 秒编译会显著影响总 wall time；长时间运行后，它的摊销又不同。

应分别报告 cold、disk-warm、memory-warm，并说明是否提前覆盖了所有 shape specialization。只把第一次迭代丢掉，不能保证后面不会遇到新的 shape 再编译。

## 7. 动态 shape 与编译缓存的相互影响

算子库可以选择把某些维度纳入专门化，也可以保留为运行时参数：

| 选择 | 优点 | 代价 |
|---|---|---|
| 更多编译期常量 | 优化器可消除分支、专门化布局 | 变体数与冷启动增加 |
| 更多运行时维度 | 缓存复用范围大 | 可能有额外分支、边界处理与较弱优化 |
| 分桶/padding | 限制变体数量与graph形状 | 额外计算、内存与mask复杂度 |

DeepJIT 负责缓存和编译机制；具体哪些 shape 应专门化，仍由消费者决定。不能把 JIT runtime 存在当作已经解决动态 batching 的证明。

## 8. 并发编译与原子发布

多个进程甚至多个节点可能同时发现同一个缓存项不存在。若它们直接写同一个最终二进制，读者可能看到半写入文件。

本快照采用独立临时目录构建、同步文件/目录，再原子 rename 发布完整条目的方式。多个进程可以重复编译同一 key，再复用先发布的结果。

```text
不存在cache条目
  → worker A: tmp-A中编译
  → worker B: tmp-B中编译
  → A完成并同步，发布最终目录
  → B完成后发现已发布条目，复用或按实现处理
  → 消费者只读取标记为完整的条目
```

这避免读半成品，但不保证没有重复编译。全局分布式锁也会引入锁服务、失效检测和延迟，二者是不同设计取舍。

### 8.1 rename 原子性不等于掉电持久性

原子 rename 解决路径切换可见性；`fsync` 和底层文件系统语义解决持久化条件。跨文件系统移动、某些对象存储挂载、缺少目录同步的实现不能自动继承相同保证。

共享缓存文件系统至少要满足项目声明的原子目录 rename 与文件/目录 `fsync` 语义。部署前应在实际文件系统上验证并发发布和故障恢复。

## 9. Cache entry 里保存了什么

当前 CUDA entry 包含源码、CUBIN、元数据、提交标记，以及可选的 PTX/SASS 等产物。

| 文件或字段 | 可以帮助回答 | 不能单独证明 |
|---|---|---|
| `kernel.cu` | 当时生成了什么源码 | 所有外部依赖已完全记录 |
| `kernel.cubin` | 实际加载的设备二进制 | 对当前设备和ABI一定适用 |
| `meta.json` | 编译参数与部分环境信息 | 完整shell上下文和所有隐式变量 |
| `.committed` | 按协议认为条目发布完成 | 内容来自可信作者或未被篡改 |
| PTX/SASS | 指令、寄存器和生成代码检查 | 端到端性能及数值质量 |

`dump_ptx` / `dump_sass` 控制附加产物，不进入缓存 digest。若命中一个没有 dump 的旧条目，打开 dump 开关不必然重新编译来补文件；分析时应确认观察的是哪次编译。

编译 tag 不属于 digest 的内容，但目录名使用 `<tag>.<digest>`。它仍参与缓存命名空间，不应把“没有进摘要”理解成完全无影响。

## 10. 多 root 与失败回退

可以配置一串 cache roots，按顺序查找并将 miss 写入可用位置。个人可写缓存与共享 lookup 缓存可以共同使用。

这里要分清两个问题：

- **性能/可用性**：一个共享盘慢或不可写时，是否能回退。
- **可信性**：一个共享目录中的二进制是否允许被当前进程直接加载。

快照 README 明确要求 cache roots 可信。将 CUBIN 缓存当成普通可任意多人写入的临时文件目录，会把可执行产物的信任边界弄错。

多用户权限与 SGID 设置属于具体部署配置，不应在不了解共享组和目录用途时照抄管理员命令。学习实验可使用自己的专用缓存目录。

## 11. 超时不是统一的一只秒表

当前实现区分文件系统操作与编译进程：

- 文件系统操作经独立 I/O worker，默认每操作有约 10 秒超时。
- 编译器子进程有单独的默认 5 分钟期限。
- 排队时间与编译执行不一定包含在文件系统操作的期限内。
- 多次 I/O 超时后，某个 root 会在该 runtime 生命周期里被跳过。

这是固定源码的行为说明，应用仍需设更外层的请求/启动期限，不能简单把 `10秒×一次操作` 当成整个冷启动最大耗时。

超时 worker 可能仍在后台使用临时目录。因此立即递归删除所有临时目录未必安全；清理应尊重在途操作与运行时协议。

## 12. CUDA 与 Ascend 的共同抽象和不同部分

| 方面 | CUDA | Ascend |
|---|---|---|
| 设备编译 | NVCC生成CUBIN | Bisheng/链接器生成对应设备产物 |
| 加载与启动 | CUDA Driver API | ACL相关接口 |
| 框架stream | PyTorch CUDA stream | `torch_npu`相关stream |
| 共同机制 | 源码/依赖摘要、缓存、懒初始化、编译诊断 | 同左 |
| 不共享的语义 | kernel源码、指令与启动选项 | 必须按Ascend实现重新核对 |

这里的跨平台是共享 JIT 基础设施，并不表示一个 CUDA kernel 不经适配就能在另一加速器上运行。

同样，DeepJIT 支持某后端，不代表每一个依赖它的消费者都支持相同硬件、dtype 或算子。需要分别看 DeepGEMM、DeepEP、FlashMLA 等项目的版本矩阵。

## 13. 已公开能力与 WIP

本快照明确将以下内容列为开发中：

- 根据历史缓存自动预测并预热未来 kernel。
- 从 Python 直接提交源码的通用编译 API。

因此，不应写出未经证实的 `deep_jit.compile(python_source)` 使用教程，也不能声称 runtime 已自动消除未来新 shape 的编译延迟。

应用可以自己安排代表性工作负载做预热，但那是应用层实验策略，与项目尚未实现的自动历史预热功能不同。

## 14. 排障时保存哪份证据

| 症状 | 证据与定位顺序 |
|---|---|
| 一直重新编译 | 比较digest输入、flags顺序、extra signature与include内容 |
| cache命中却行为错误 | 检查隐式编译环境、ABI、设备架构和过期依赖 |
| 多节点启动同时很慢 | 检查并发miss、共享盘metadata和重复编译数量 |
| 打开dump却没有SASS | 检查是否cache hit而没有新编译 |
| 只在非默认stream出错 | 检查加载/启动stream与tensor依赖 |
| 编译失败后启动一直卡住 | 分别看compiler timeout、I/O worker和root fallback |

建议记录源码摘要、最终编译命令、版本、cache root选择、命中层级、编译/加载/执行耗时和正确性对照。只保留一句“JIT fail”不足以复现。

## 15. 自测与参考答案

**1. shape一样为什么可能不能复用二进制？** dtype、布局、架构、编译参数、依赖、ABI或生成源码可能不同。

**2. 为什么不能排序编译flags来稳定key？** 参数顺序可能改变宏覆盖、include搜索或编译行为；应保留有效语义。

**3. 原子rename是否保证发布后掉电也不会丢数据？** 不独立保证，还依赖文件/目录同步和底层持久化语义。

**4. 多进程重复编译同一kernel是错误吗？** 不一定。无锁发布可允许重复工作，只要消费者不会读取半成品且结果符合相同契约。

**5. 为什么命中磁盘缓存仍可能慢？** 网络/磁盘读取、元数据解析、设备模块加载和首次设备初始化仍有成本。

**6. `extra_signature` 有什么用？** 为运行时未自动发现的应用依赖、ABI或环境条件提供显式身份，前提是调用者持续维护它。

**7. CUDA/Ascend共用runtime是否等于共用kernel源码？** 不是，共享的是编译缓存与生命周期抽象，设备代码和工具链仍按后端区分。
