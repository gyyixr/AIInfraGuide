## 1. smallpond 在数据系统中的位置

模型训练前往往要读取、清洗、分区、聚合和重新组织大量数据。GPU 训练框架不适合承担所有这些操作；一个高效的数据处理层可以把训练输入变成更容易并行读取和恢复的文件集合。

smallpond 是 DeepSeek 公开的数据处理框架，结合 DuckDB 等执行能力与文件存储。3FS 可以承载大规模共享数据，但小型原理实验与所有数据变换并不天然需要真实 3FS 集群。

本节核对官方快照 `52ecc5e45535c7448f848bcb45b0da00d9484f81`，日期 2026-11-07。需要特别区分“DataFrame API”“逻辑计划”“执行器”和“底层存储”四层。

## 2. 从用户表达式到物理执行

```text
read_parquet / read_csv
  → DataFrame逻辑变换
  → repartition / partial_sql / map
  → logical nodes与依赖
  → planner生成可执行tasks
  → 调度器与executors运行DuckDB/Arrow/Python工作
  → 中间文件、manifest和最终输出
```

同一个高层表达式可能对应多个分区任务，不是一次函数调用就把全部数据装入一个 Python 进程。

当前 `smallpond.init()` 返回高层 Session，默认可建立本地 Ray 环境，也能按配置接入更多 worker。仓库还包含自己的执行计划、scheduler、work queue 和低层执行入口；应沿实际入口追踪，而不是看见一个 `Scheduler` 文件就推断所有任务都直接走同一条路径。

### 2.1 “无需长期服务”不等于“没有运行时进程”

项目强调容易运行、无需预先维护某些长期服务，不代表一个作业只存在用户脚本这一个进程。Session、Ray、executor、线程池和存储客户端仍可能占用 CPU、内存、端口和文件句柄。

容量与生命周期分析必须包含这些运行时资源。

## 3. 惰性变换与物化操作

固定源码中的 DataFrame 会记录逻辑 plan。常见变换先构建新的依赖节点；真正的输出或收集操作会触发执行。

| 操作 | 该快照中的关键含义 |
|---|---|
| `read_parquet` | 创建数据源与DataFrame |
| `repartition` | 创建新的分区/Shuffle逻辑 |
| `partial_sql` | 对所接收分区执行SQL逻辑 |
| `write_parquet_lazy` | 创建输出节点，返回新的DataFrame |
| `write_parquet` | 调用lazy输出后再`compute()`，是阻塞操作 |
| `to_pandas` | 触发计算，再把结果收集为本机Pandas对象 |

只测“构建 DataFrame 链”的耗时可能完全没测到数据处理。另一方面，`to_pandas()` 可能把大结果拉回单机，不能当成 PB 级流水线的通用输出方式。

Session 还维护节点到任务的映射，用于复用已计算依赖。是否重算与使用了什么输出缓存，需要结合实际执行日志，而非只看用户代码重复调用了哪个方法。

## 4. 三种分区不是同一种动作

| 分区方式 | 基本依据 | 典型风险 |
|---|---|---|
| 按文件 | 将输入文件分配到任务 | 文件大小差异带来负载倾斜 |
| 按行 | 按记录量重新分配 | 需要读取/重写，字节与行数仍可能不同 |
| 按key的Hash | 相同key进入同一目标分区 | 热点key造成单分区过载 |

源码当前参数为 `by_rows=True`，而部分入门文档出现 `by_row` 的旧拼写。编写可运行脚本时应以固定 `dataframe.py` 的签名为准。

按文件均匀分配 100 个文件，不代表字节数或执行时间均匀：一个 200 GB 文件与一个 20 MB 文件都只计作“一个文件”。

## 5. Hash 分区为什么影响正确性

考虑数据：

```text
(A,2), (B,1), (A,4), (A,100), (B,9)
```

目标是每个 key 的总和、条数、最小值、最大值与平均值。若先把相同 key Hash 到同一分区，每个分区内部就能算完整的 key 聚合。

对于 A：

$$
sum_A=2+4+100=106,\quad count_A=3,
\quad mean_A=106/3.
$$

对于 B：sum=10、count=2、mean=5。

如果只是按文件分区，一个 key 可能散在多个任务上，此时 `partial_sql` 的 group-by 只产生局部结果，还需要正确的合并阶段。

### 5.1 局部平均值不能直接再平均

设 A 的两个分区分别有 `[2,4]` 与 `[100]`：

$$
\frac{mean([2,4])+mean([100])}{2}=51.5,
$$

而全局平均值为 $106/3\approx35.333$。

正确可合并状态是 `(sum,count)`，再用总 sum 除总 count。min/max/sum/count 的合并规则各不相同；distinct count、分位数、去重与排序还需要更具体的状态设计。

这与分布式训练中“各 rank 局部均值的均值”是同一种权重错误。

## 6. 一个无依赖的分区正确性例子

下例用 SHA-256 构造教学分区器，只验证 key 一致性和聚合结果，不模拟 smallpond 的实际 hash 算法：

```python
import hashlib
from collections import defaultdict

rows = [("A",2), ("B",1), ("A",4), ("A",100), ("B",9)]
parts = [[] for _ in range(2)]
for key, value in rows:
    digest = hashlib.sha256(key.encode()).digest()
    bucket = int.from_bytes(digest[:8], "little") % len(parts)
    parts[bucket].append((key, value))

result = {}
for part in parts:
    grouped = defaultdict(list)
    for key, value in part:
        grouped[key].append(value)
    for key, values in grouped.items():
        assert key not in result  # 相同key只出现在一个目标分区
        result[key] = {"sum":sum(values), "count":len(values),
                       "min":min(values), "max":max(values)}

assert result["A"] == {"sum":106, "count":3, "min":2, "max":100}
assert result["B"] == {"sum":10, "count":2, "min":1, "max":9}
```

跨进程复现时，不应把默认 Python `hash()` 无条件当作稳定持久分区协议。实际系统应记录所用 hash、key 编码、分区数和实现版本。

## 7. smallpond API 的最小教学路径

以下示意脚本依赖 smallpond 与 PyArrow，需要在专用环境中运行；本次只静态核对该固定 API，没有部署并执行完整 smallpond 作业：

```python
from pathlib import Path
import pyarrow as pa
import pyarrow.parquet as pq
import smallpond

root = Path("smallpond-demo")
if root.exists():
    raise RuntimeError("请选择一个新的实验目录")
root.mkdir()
pq.write_table(pa.table({"key":["A","B","A","A","B"],
                         "value":[2,1,4,100,9]}), root / "input.parquet")

sp = smallpond.init(data_root=str(root / "runtime"), memory_allocator="system")
data = sp.read_parquet(str(root / "input.parquet"))
data = data.repartition(2, hash_by="key")
summary = sp.partial_sql(
    "SELECT key, sum(value) AS total, count(*) AS n, "
    "min(value) AS lo, max(value) AS hi FROM {0} GROUP BY key", data)
summary.write_parquet(str(root / "output"))
print(summary.to_pandas().sort_values("key"))  # 仅适合本例的小结果
```

这个顺序的关键是先按 key 分区，再做分区内聚合。若替换为不保持 key 局部性的分区方式，应重新设计最终聚合。

结果顺序不必与输入相同，业务需要确定顺序时应显式排序；不能把任务完成顺序当成稳定数据协议。

## 8. Shuffle 的 I/O 放大

假设原始输入为 D 字节。一个简单“读取→分区落盘→再读取分区→计算输出”的管线，至少可能包含：

$$
V_{IO}\approx D_{read}+D_{shuffle-write}+D_{shuffle-read}+D_{output-write}.
$$

若中间分区和最终输出都与原始数据同量级，就是约 4D 的逻辑存储流量，还未计算多副本、压缩比变化和重试。

因此 100 TiB 输入不等于只需在存储上搬运 100 TiB。优化投影、提前过滤、局部预聚合和压缩，可能比单纯增加 worker 更有效。

### 8.1 提前投影的数例

原记录 1000 字节，只需要 100 字节字段参与 shuffle。若能在读取后、shuffle 前丢掉无关字段，后续中间数据量可能缩小约十倍。

但若过滤条件或 UDF 还需要被丢掉的字段，这样做会改变结果。算子下推首先要满足语义，再计算收益。

## 9. 分区数是并行度与开销的交换

分区太少：单个任务大、倾斜难摊平、失败重做成本高。分区太多：metadata、文件打开、调度和小文件合并成本增加。

假设 1 TiB 数据：

| 分区数 | 平均每分区数据 | 可能问题 |
|---|---:|---|
| 16 | 64 GiB | 单任务内存/长尾压力大 |
| 1024 | 1 GiB | 仍需结合算子内存和机器资源 |
| 1048576 | 1 MiB | 小文件与调度数量非常大 |

这些是平均值，热点 key 可以让实际最大分区远高于平均。合理做法是先采样估计 key 和字节分布，再用最大分区和分位数指导资源配置。

## 10. 热点 key 怎样处理

一个 key 占全部数据 40% 时，普通 Hash 分区仍会把这 40% 放在同一个目标上。增加其他分区不会拆开它。

可以在语义允许的情况下：

- 先在源端做可合并的局部聚合。
- 对热点 key 加 salt 拆分，再做第二次聚合。
- 将大 key 单独分流到专门路径。
- 为不可合并操作设计不同算法或外部排序。

例如 sum/count 可以分盐聚合后合并；任意依赖全组顺序的 Python UDF 则未必能这样拆。不能把“热点加salt”当成对所有操作都保持等价的技巧。

## 11. 线程、任务与 NUMA 预算

一个 executor 并发运行多个 DuckDB 查询，每个查询又可能使用多个线程。总线程数近似是：

$$
N_{threads}\approx N_{tasks}\times threads_{per\ task}+N_{runtime}.
$$

若机器有 96 个物理核，16 个任务各用 16 线程，已经产生 256 个查询线程，还没算运行时。线程越多不一定越快，可能增加抢占、cache 竞争和跨 NUMA 访问。

同理，16 个任务每个允许 32 GiB 工作内存，理论预算已达 512 GiB。若主机只有 256 GiB，系统可能频繁 spill 或 OOM。

应按 CPU、内存、临时盘、网络和文件句柄同时限制并发，而非只看一个 `num_executors`。

## 12. Data root 中哪些是结果，哪些是运行状态

官方 internals 文档区分 config、log、queue、output、staging、temp 等目录，保存逻辑/执行计划、运行上下文和任务进度。

| 目录/状态 | 用途 | 管理注意点 |
|---|---|---|
| config | 计划与运行配置 | 与代码、依赖和输入版本绑定 |
| queue | 调度器与worker消息 | 不应误删仍在运行的队列 |
| staging | 中间产物与任务完成信息 | 恢复和重试可能依赖 |
| temp | 临时执行文件 | 仍在途任务可能使用 |
| output | 交付数据/manifest | 应有完整性与发布规则 |
| log | 图、时间线和事件 | 定位倾斜、重试和性能瓶颈 |

输出 manifest、链接与真实数据复制也可能是不同 sink 行为。一个很小的结果文件不代表全部数据已经复制到新的持久位置。

## 13. 任务级恢复的范围

公开文档说明 checkpoint 主要是 task-level，部分任务可以支持 batch-level。它不等于每条记录都恰好执行一次，更不自动让任意外部副作用具有 exactly-once 语义。

纯转换任务重跑通常可以通过确定输入和隔离输出保持结果一致；向外部服务发请求、更新数据库或修改共享对象的 UDF，则需要幂等键与提交协议。

```text
task开始
  → 读取固定输入
  → 写临时产物
  → 完成并记录结果
  → 下游消费已完成产物
```

故障注入应覆盖：输出写到一半、数据已写但完成标记未提交、完成标记已提交但 worker 未返回、重试时发现旧产物等窗口。

本节没有验证真实多节点故障恢复；这些是基于公开状态设计提出的验收路径。

## 14. GraySort 数字的适用范围

官方报告用 50 个计算节点和 25 个 3FS 存储节点，将 110.5 TiB 数据分为 8192 个分区，约 30 分 14 秒完成排序，平均约 3.66 TiB/min。

这个结果说明特定系统组合在该排序任务上的能力；它不能直接代表包含 Python UDF、复杂 join、LLM 标注或高度倾斜语料的吞吐。

复现报告时需要同时记录输入记录大小、分区策略、共享存储、复制与压缩、CPU/NUMA、内存、临时数据量和失败重试。

## 15. 如何接入 LLM 数据管线

一个可追溯的数据产物至少应绑定：

- 源数据版本与内容指纹。
- 清洗、去重和过滤规则。
- 语言/领域分桶与混合权重。
- tokenizer 及特殊 token 约定。
- 输出分区、顺序、schema 与统计摘要。
- 代码、依赖、参数与执行日志。

smallpond 可承担其中的并行数据处理，但“数据处理成功”不等于训练数据没有泄漏、重复或偏差。质量抽样、去污染与下游训练数据索引仍需独立验收。

训练框架的 sample/shuffle index 还要绑定这里产出的不可变数据版本；否则存储路径一样、内容却变了，会破坏恢复语义。

## 16. 自测与参考答案

**1. `repartition(100)` 是否保证每个key只在一个任务中？** 不自动保证，需要按相应key进行Hash分区或采用其他明确的同key归并策略。

**2. 为什么局部AVG不能直接平均？** 各分区有效条数不同会改变权重，应合并sum和count，或先把同key全部数据送到同一分区。

**3. `write_parquet_lazy`与`write_parquet`的区别是什么？** 前者构造输出DataFrame，后者在此基础上调用compute并等待；需按固定版本接口判断执行边界。

**4. 为什么大结果不适合`to_pandas()`？** 它触发计算并将结果收集成单机对象，最终仍受本机内存限制。

**5. “无长期服务”是否没有Ray/worker进程？** 不是，本快照的Session入口使用Ray和执行资源，强调的是部署使用方式而非不存在运行时。

**6. 任务可重试就有exactly-once副作用吗？** 没有，外部写入需要幂等与提交协议；任务级恢复只覆盖其明确管理的状态。

**7. 增加分区能解决一个超大热点key吗？** 普通Hash不能，需要预聚合、盐化或专门算法，并验证数学等价。
