## 本章定位

前八章从公开模型、论文和源码解释DeepSeek技术。本章把这些说明变成可以复查的实验与工程检查，回答“我能在手头环境中验证哪一层”。

它不要求先下载最大的模型，也不把CPU小例子当作真实集群结果。不同证据层次各有明确价值和边界。

## 快速运行

```bash
# 仓库根目录；无需GPU与第三方Python依赖
npm run test:deepseek
npm run lab:deepseek
```

在已经安装PyTorch的解释器环境中：

```bash
python labs/deepseek/mla_torch.py --device cpu
python labs/deepseek/mla_torch.py --device cuda
```

第二条需要当前进程能访问CUDA设备。环境隔离导致无法访问GPU，与硬件本身不支持某个专用kernel是不同问题，应分别诊断。

## 从数学例到完整系统

一个合理的递进顺序：

1. 固定输入，复算公式和shape。
2. 核对真实接口的dtype、stride、scale和索引。
3. 单算子与独立高精度oracle对照。
4. 固定模型的一层、多层和多步回归。
5. 加入Graph、异步、缓存与并行。
6. 加入实际请求分布、质量评估和故障注入。
7. 在相同硬件预算与SLO下比较完整服务。

每次提升证据层次，都要新增对应检查，不能只把旧测试重复运行更多次。

## 学习验收

**为什么14项测试通过还不能称DeepSeek模型已复现？** 因为它们使用合成小输入，未加载官方模型，也未执行目标硬件上的完整实现。

**为什么仍然值得先跑？** 公式、布局和状态错误在小例子里更容易定位；它们能为后续真实kernel建立独立oracle。

**为什么要保留失败反例？** 能识别错误归约、错误gate或选择偏差，证明测试不仅会给正确实现亮绿灯。

**什么时候可以报告性能提升？** 在同一数学/质量目标、同一工作负载与明确计时边界下完成对照，并记录资源和统计条件之后。

## 继续实践

根据硬件选择第9.2节的项目，不要把安装包名字、模型配置长度或一次API返回成功当作完整能力证明。每次实验保留输入、输出和版本，才能将学习内容继续扩展成可答辩的工程项目。
