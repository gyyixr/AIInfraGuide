这里的recipe不是训练超参数配方，也不是安装环境的脚本集合。
`deepseek-recipe`是Rust库和Python binding，负责API协议转换、DeepSeek prompt编码与模型输出解析。

核对日期：2026-11-07。
固定版本为 `935817c66f5d6e64838f419692545f06787e485f`，workspace版本0.2.0。
依据 [固定README](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/README.md) 与对应编码和stream文档。

## 1. 它在系统里的位置

```text
Messages / Chat Completions / Responses 请求
  -> protocol conversion
  -> Conversation
  -> V4/V4.1 prompt rendering
  -> tokenizer编码
  -> 调用方的推理后端
  -> backend chunks
  -> StreamProcessor
  -> 对应API响应
```

模型推理、工具执行和HTTP传输由调用方提供。
库不会因为收到tool call就自动执行shell命令。

## 2. 为什么需要中间Conversation

不同API的字段、角色和工具表示不完全相同。
如果每一种API都直接编写一套模型模板，容易出现重复逻辑和不一致。

中间Conversation把消息、图像、工具和生成设置统一为内部语义。
之后再按模型版本渲染。

这与把所有输入简单拼成一个字符串不同。

## 3. 各包职责

| 包 | 职责 |
|---|---|
| `deepseek-recipe-core` | conversation、消息、图像和tool类型 |
| `deepseek-recipe` | API转换与输出解析 |
| `deepseek-recipe-encoding` | V4/V4.1模板与token编码 |
| `deepseek-recipe-image` | 图像获取和预处理 |
| `deepseek-recipe-macros` | prompt构造辅助 |
| `deepseek-recipe-python` | Python绑定 |

`server-rs`与`server-py`是mock inference接入示例。
不能把示例HTTP响应当成真实DeepSeek模型推理结果。

## 4. 一个最小请求的生命周期

用户提交一条文字消息。
转换器先解析model名、messages和生成参数。

得到Conversation后，V4.1编码器加入该版本需要的角色与控制标记。
如果附加tokenizer，再转成token IDs。

调用方将这些IDs交给真实引擎；没有真实引擎时也可以用mock输出测试协议。

## 5. Model alias需要显式映射

库默认识别指定正式模型名。
API服务可能使用 `deepseek-flash`等别名。

调用方应通过ConversionOptions注册别名到正确模型版本。

别名字符串相同不保证不同日期指向相同权重。
协议版本、模型revision和线上路由应分别记录。

## 6. Render与encode不同

`render_conversation`生成prompt文本、特殊token范围和图像来源。
`encode`还需要匹配的tokenizer。

没有tokenizer时，render仍可用于检查模板。
但encode应报MissingTokenizer，而不是猜测每个词对应哪个ID。

字符串长度、UTF-8字节数和token数都不相同。

## 7. 为什么特殊token要保留显式范围

模型模板插入的控制标记需要作为特殊token编码。
用户正文里恰好出现相同拼写时，应作为普通内容处理。

库用 `special_ranges`区分这两类位置。
普通文本区间按不含added vocabulary的路径编码。

因此，调用方只拿最终字符串自行tokenize，可能丢失原来的安全与语义边界。

## 8. 一个控制标记反例

用户想讨论字符串 `</think>` 的用途。
如果编码器把用户正文里的该字符串当成真正的控制token，可能改变对话结构。

正确处理保留“用户在谈论这个字面量”的语义。
模板自己插入的控制位置才具有对应控制作用。

这不等于解决所有prompt injection问题，但能避免一种具体的控制token混淆。

## 9. UTF-8范围不能按字符下标猜

例如中文“你好”在UTF-8中通常占6字节，但只有2个Unicode字符。

如果特殊范围记录的是byte offsets，用字符索引切片会产生错位。

```text
文本字符数 ≠ UTF-8字节数 ≠ tokenizer token数
```

协议组件跨Rust/Python/JavaScript传递范围时，要明确单位。

## 10. V4.1 reasoning effort的映射

固定 `dsv41.rs`将类别映射为数字提示：

| 类别 | 本版本渲染值 |
|---|---:|
| Low | 50 |
| High / Xhigh / 未指定 | 75 |
| Max | 100 |

这属于该库版本的分类映射。
模型本身支持1—100连续强度，不表示这个特定枚举接口直接暴露每个整数。

## 11. Thinking内容与历史管理

编码器处理thinking mode、assistant reasoning content和prefix continuation。

是否保留历史reasoning、是否在未完成assistant前缀后闭合控制标记，会影响接续语义。

不能把所有历史思考块一律拼入或一律删除，然后宣称与官方编码相同。
应遵循对应Conversation字段和模型版本。

## 12. Tool schema与调用参数

模型需要看到工具名称与参数schema。
输出tool call又需要被解析成结构化名称、参数与调用ID。

DSML相关渲染会区分字符串参数与非字符串JSON值。
数字3和字符串“3”不能不加区分地序列化。

参数JSON键顺序、转义和特殊字符也应通过一致的序列化路径处理。

## 13. 工具执行由谁负责

Recipe产生或解析tool call。
应用程序或harness根据权限和环境执行它。

结果再作为对应tool message送回Conversation。

如果工具调用被解析两次并各执行一次，可能产生重复副作用。
因此API adapter与tool executor需要明确唯一的执行责任。

## 14. 结构化输出分两层

转换器可以验证JSON Schema并将约束写入prompt或InferenceOptions。

但真正限制模型只能生成符合schema的token，需要推理后端执行constrained decoding。

“schema已传入库”不等于“输出一定严格满足schema”。
调用方还应解析最终结果并处理不合规输出。

## 15. 图像路径与模型版本

库支持base64和外部URL图像，并提供V4.1预处理组件。
V4文本模型不接受图像，固定版本转换会用不支持图像的文字占位。

这不是自动调用OCR将图片转成文字。
也不是V4因此拥有与V4.1相同视觉能力。

## 16. 图像URL获取是应用边界

README说明默认fetcher可连接任意地址，服务接受不可信URL时应安装DestinationFilter。

原因是网络获取本身属于有外部影响的操作，可能访问不应暴露的内部地址。

本节不执行任何图像URL请求。
接入服务应按实际允许来源设置过滤和资源限制，而不是把协议解析当网络授权。

## 17. Context budget怎么计算

prompt预算包含编码后的文本IDs，以及图像占位展开成真实视觉tokens后的调整。

$$
N_{prompt}=N_{encoded}+N_{image\ adjustment}.
$$

然后检查：

$$
N_{prompt}+N_{max\ output}\le N_{context}.
$$

只按一个image placeholder算1token会低估真实模型输入长度。

## 18. 一个预算数例

设文本和占位编码得到1000token。
图片实际占256个视觉位置，而占位已算1个，因此调整为255。

$$
N_{prompt}=1255.
$$

若context limit4096，剩余输出空间2841。
请求max_tokens=3000应报告超出，而不是悄悄让后端运行到错误。

真实图像还可能有行标记，具体调整必须来自实际预处理结果。

## 19. 默认输出上限不是模型极限

固定库在未指定max_tokens时按模式给默认值：非thinking8192，thinking一般65536，max effort131072。

默认值会受剩余context空间限制。
显式请求则按总预算检查。

这些是协议库默认，不是模型最大上下文或权重训练长度的同义词。

## 20. 流式输出为什么需要状态机

后端可能把一个控制标记分成多个chunk。
UTF-8字符或token解码也可能跨chunk才完整。

如果每个chunk独立解析，可能误识别thinking结束、tool参数或stop sequence。

StreamProcessor维护跨chunk状态，直到获得足够信息再输出协议事件。

## 21. 一个拆分示例

后端分三次给出：

```text
chunk1: </th
chunk2: ink>答
chunk3: 案
```

解析器需要识别完整控制边界，而不是把第一段立即当普通正文发出。

Tokens模式还保留特殊token身份；Text模式没有token边界，只能按字符串规则识别。
两种输入路径的保证不同。

## 22. Logprob由后端提供

Recipe可以接收并转换logprobs字段。
它不计算模型概率。

如果后端没有返回真实logprob，协议层不能从输出文本推算。

对于RL数据，保存的概率还要注明temperature、top-p和mask是否已作用。
这与4.2中的采样一致性直接相关。

## 23. Usage也有计数条件

带tokenizer时，processor可编码reasoning内容统计reasoning_tokens。
没有tokenizer时，不能宣称得到相同精确计数。

cache-hit tokens等字段来自后端usage记录。
协议转换不会自己知道哪些KV命中。

计费字段与训练统计都不应使用字符数冒充token数。

## 24. 最小可复现接入步骤

1. 固定Recipe commit与依赖lockfile。
2. 固定模型revision及tokenizer文件。
3. 注册model alias与版本映射。
4. 保存规范化后的Conversation。
5. 检查rendered prompt和special ranges。
6. 编码后计算真实context预算。
7. 用mock backend验证完整/流式响应。
8. 最后连接真实模型引擎并做数值与行为检查。

先验证协议，再验证模型，有助于定位问题来源。

## 25. 官方mock实验怎么使用

固定仓库提供encoding-decoding demo和mock server示例。
可以观察同一Conversation如何渲染成prompt，再把预设输出解析回不同协议。

```bash
cargo run -p encoding-decoding-demo --locked
```

该命令需要已准备好匹配源码和Rust依赖的环境。
它用于模板和解析验证，不证明真实推理吞吐或模型能力。

## 26. 一个无需模型的预算检查

```python
encoded = 1000
visual_tokens = 256
placeholder_tokens = 1
context = 4096
prompt = encoded + visual_tokens - placeholder_tokens
remaining = context - prompt
assert prompt == 1255
assert remaining == 2841
assert prompt + 3000 > context
print(prompt, remaining)
```

这验证本节算术，不代替官方图像处理和tokenizer。

## 27. 接入失败的定位顺序

先检查model alias与模板版本。
再检查tokenizer特殊ID、显式范围和图像span。

然后检查流式chunk顺序、finish reason和tool call关联。
最后再判断是否是推理后端或模型质量问题。

同一条请求若只有某个API格式失败，通常应先比较转换后的Conversation。

## 28. 自测与答案

**问题1：Recipe是否是DeepSeek训练超参数配方？**

答案：不是，它是协议、prompt编码与输出解析库。

**问题2：render是否必须加载tokenizer？**

答案：可以只render；encode需要匹配tokenizer。

**问题3：为何用户输入的特殊token拼写不能直接当控制token？**

答案：否则正文会改变模板控制结构，需保留显式范围。

**问题4：JSON Schema传给Recipe是否保证严格输出？**

答案：不保证，后端是否执行约束解码由调用方决定。

**问题5：图片占位只算1token可以吗？**

答案：不够，需要加实际视觉token调整。

**问题6：Recipe能从文本生成logprob吗？**

答案：不能，概率必须由模型后端提供。

**问题7：mock server成功是否意味着真实模型可用？**

答案：不意味着，它只证明对应协议路径。
