截至2026-11-07，本专题核对到的官方后续版本包括DeepSeek-V4.1-Flash及2026-10-17发布的DeepSeek-V4.1-Flash-1017。
学习路线若止于V3/R1，会遗漏跨层KV共享、CED、原生视觉和Engram等重要变化。

本页先建立全景，CED、Engram、CSA2分别在2.7、2.8、2.9展开。
DSpark的投机生成与调度在后续推理章节展开。

核对日期：2026-11-07。
主要依据为 [官方V4.1报告](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/314113f8a7dadb388215396ba5fbee2c610a04d6/DeepSeek_V41_Tech_Report.pdf) 和 [1017发布说明](https://api-docs.deepseek.com/news/news261017/)。

## 1. 先把版本固定下来

| 对象 | 本次核对revision |
|---|---|
| V4-Flash | `60d8d70770c6776ff598c94bb586a859a38244f1` |
| V4.1-Flash | `314113f8a7dadb388215396ba5fbee2c610a04d6` |
| V4.1-Flash-1017 | `1bae0e1088993b9b82de08f59de5be5a34e42170` |

这些是Hugging Face模型仓库revision，不是GitHub仓库commit。
链接中的 `main` 可能继续变化，复现时应固定revision。

本次读取的两份V4.1 `inference/model.py` 和 `inference/config.json` 分别字节相同。
这一观察只证明参考代码和配置一致，不证明两份权重一致。

## 2. V4.1不是给V4增加一个视觉插件那么简单

| 方面 | V4-Flash | V4.1-Flash |
|---|---|---|
| 主干层数 | 43 | 40 |
| 主干hidden维 | 4096 | 5120 |
| 全局attention | CSA/HCA交替 | CSA2跨层共享 |
| 序列压缩比 | 4 / 128 | encoder 2，decoder 1 |
| 全局KV生成 | 各层自身路径 | decoder取最终encoder来源 |
| 残差 | mHC | Single-Pass mHC |
| 条件记忆 | 本配置无Engram模块 | 两层Engram |
| 视觉输入 | 初始文本V4主模型无原生视觉路径 | 从预训练开始联合图文 |
| 主KV精度 | 依对应布局的FP8混合 | FP4 main KV |
| speculative模块 | MTP路线 | DSpark |

2026-08的V4-Flash-Vision-Exp属于单独发布节点。
不能因同属V4系列就把V4-Flash、Vision-Exp与V4.1的架构描述合并。

## 3. 参数口径必须拆开

报告明确给出：

$$
P_{\mathrm{backbone}}=552\mathrm B,
\qquad P_{\mathrm{Engram}}=196\mathrm B.
$$

这两项算术相加约为748B。
因此把“552B”直接称为含Engram的全部参数不正确。

同时，视觉编码器、投机模块、词表头是否包含在某一表格的统计中，要跟随该表原文。
本节用“主干552B+Engram196B”保留报告的分类，避免把近似合计当精确checkpoint参数总数。

## 4. 8B与16B是不同阶段的活跃口径

官方报告给出prefill约8B、decode约16B活跃参数。
其核心原因是CED让长prompt的大部分位置只经过encoder一半主干。

这不是每个token从同一专家池中选择数量突然减半。
各MoE层仍使用对应的top-6 routed experts加1 shared expert。

短prompt、decoder窗口回放和额外视觉前向会改变实际计算占比。
因此“prefill严格只花decode的一半时间”不是从活跃参数统计能推出的结论。

## 5. 整体数据流

```text
文本 token ids ───────────────┐
                             ├→ 混合 embedding 序列
图像 → patch → ViT → projector┘
  → 20层 causal encoder
  → decoder共享全局KV来源
  → 20层 decoder
  → 输出文本logits
```

所有语言主干层保持因果生成语义。
图像内部ViT使用双向视觉attention，语言主干再把图像表示与文本位置共同处理。

“causal encoder”不等于传统机器翻译中能看完整未来文本的双向encoder。

## 6. 一张图像怎样变成patch

固定配置的patch大小为14。
以1344×1344的RGB图像为例：

$$
1344/14=96.
$$

得到96×96=9216个patch。
每个patch展开长度为：

$$
3\times14\times14=588.
$$

线性patch embedding把588维映射到1024维。

| 阶段 | shape，不写batch |
|---|---|
| RGB图像 | `[3,1344,1344]` |
| patch集合 | `[9216,3,14,14]` |
| patch flatten | `[9216,588]` |
| patch embedding | `[9216,1024]` |

真实预处理会根据尺寸约束调整图像。
这组尺寸是用于完整演算的可整除例子。

## 7. DeepSeek-ViT的结构

固定配置：32层，hidden维1024，16个attention头。
每个头维度为：

$$
1024/16=64.
$$

ViT使用2D-RoPE、RMSNorm和SwiGLU。
patch embedding使用线性投影，与报告的Muon矩阵优化设计相配合。

ViT处理一张图的所有patch时使用双向attention。
这不违背语言模型的自回归输出，因为整张输入图片本来就是已给定条件。

## 8. 为什么位置编码要分二维

同样相邻的序列索引可能代表横向相邻，也可能跨到下一行。
2D位置编码分别保留行、列坐标关系。

例如patch `(row=2,col=3)` 与 `(2,4)`是横向相邻。
`(2,3)` 与 `(3,3)`是纵向相邻。

仅把96×96展成9216的一维序列，会把几何关系埋进固定展平约定。
二维旋转明确区分这两种位移。

但2D-RoPE本身不保证模型能正确读出所有小字。
视觉分辨率、压缩、训练分布与任务都决定最终能力。

## 9. Pixel-unshuffle把空间信息搬到通道

ViT输出为96×96×1024。
将每个3×3邻域的9个向量拼接：

$$
[96,96,1024]\to[32,32,9216].
$$

视觉token数从9216变成1024，恰好减少9倍。
每个输出token暂时有9倍通道数。

这不是对9个位置求均值，而是重排和拼接。
信息压缩主要发生在后续可学习投影中。

## 10. MLP projector映射到语言隐藏空间

固定参考 `Aligner` 使用两层线性变换，中间GELU：

$$
z=\operatorname{Linear}_2\left(
\operatorname{GELU}(\operatorname{Linear}_1(v))\right).
$$

例子中的维度是：

$$
9216\to5120\to5120.
$$

最终得到1024个5120维视觉embedding，与语言模型hidden维匹配。

| 阶段 | shape |
|---|---|
| ViT特征 | `[9216,1024]` |
| 3×3空间重排 | `[1024,9216]` |
| 第一投影 | `[1024,5120]` |
| GELU | `[1024,5120]` |
| 第二投影 | `[1024,5120]` |

## 11. 不能把1024当整张图片的完整prompt长度

图像span还可能包括image start、end与行分隔标记。
这些位置也会进入语言序列。

参考实现有 `image_start`、`image_end`、`image_newline` 可学习embedding。
因此“视觉特征数1024”与“编码后的prompt token数”不完全相同。

图像缩放、长宽比与padding也会影响最终网格。
评估上下文预算时应使用实际编码后的序列长度。

## 12. 不是所有图像都恰好整除3

若patch网格是 $h\times w$，参考 `Aligner` 会把空间维补到3的倍数。
输出网格为：

$$
\lceil h/3\rceil\times\lceil w/3\rceil.
$$

比如patch网格5×7，补到6×9，输出2×3=6个视觉token。
不能直接用35/9得到非整数长度。

padding并不表示原图真的多出新内容。
它是投影输入的布局处理，需与预处理和训练约定一致。

## 13. 视觉embedding如何并入文字

Tokenizer与消息编码器先构造混合序列及图像span标记。
普通文本位置走词嵌入。
图像位置由ViT/projector的输出覆盖对应embedding。

然后所有位置进入同一语言主干。
这与先用OCR提取文字、再把文字作为用户消息是不同的信息路径。

模型原生接收图像表示，才可能直接利用布局、颜色、对象关系等非文字信息。
但是否正确理解仍需任务评估。

## 14. 图像与Engram如何相处

Engram依赖离散文本token的n-gram查表。
图像span没有与普通词片一致的n-gram语义。

参考代码将图像位置从Engram处理里排除。
哈希历史遇到图像边界时使用阻断/填充规则，避免把跨图像的两段文本错误地当作连续n-gram。

因此对多模态模型，token mask不仅影响loss，也影响架构中的条件记忆与路由。

## 15. 图文MoE使用不同校正bias

文本与图片的hidden分布不同。
若只统计混合总负载，可能掩盖模态内部的不均衡。

V4.1分别维护文本与视觉校正bias，用它们选择专家。
被选专家的输出仍由原始路由score加权。

这给共享专家池提供模态相关负载反馈。
不是将整个网络拆成一个文本模型和一个图像模型。

## 16. 视觉成本不能只算语言token

将9216个patch压成1024个语言视觉token，减少的是语言主干的序列负担。
前面的ViT仍处理9216个patch。

如果大量图片导致视觉编码成为瓶颈，仅优化LLM KV cache可能收益有限。
训练或服务可以分别调度视觉编码阶段与语言阶段，但调度实现不是一段 `encode_image` 函数就全部具备。

多模态吞吐报告应列出图片数、分辨率、预处理策略、文字长度与batch。
只写tokens/s可能掩盖视觉前处理成本。

## 17. 1017的证据该怎么读

官方将1017称为minor update，并报告推理、代码、agent和视觉能力提升。
发布说明强调自反馈强化学习带来的完整项目开发能力改进。

这一层证据不等于公开了全部后训练样本、环境和更新过程。
也没有理由据此虚构一个与V4.1完全不同的新attention架构。

本次固定源码与配置一致，适合沿用本章的参考结构解释。
权重、采样建议、评估harness与分数仍要分别记录。

## 18. 采样和harness也是版本差异

1017模型卡推荐temperature=1.0、top-p=1.0。
此前V4.1模型卡给出top-p=0.95或1.0的建议区间。

对外比较还要记录reasoning effort、输出上限、工具权限、上下文预算与agent scaffold。
这些设置影响任务成功率、输出长度和总运行时间。

同一个模型在不同harness里得到不同结果，不代表权重或架构变化。

## 19. 参考源码已经开放到哪一层

固定 `inference/` 包含：

| 文件 | 可直接核对的内容 |
|---|---|
| `model.py` | 主干、CSA2、MoE、mHC、Engram调用、DSpark前向 |
| `vision.py` | ViT、2D-RoPE、patch投影、Aligner |
| `image_processor.py` | 图像预处理和span组织 |
| `engram.py` | tokenizer压缩与n-gram哈希状态 |
| `kernel.py` | 参考量化和attention相关操作 |
| `generate.py` | 示例生成流程 |
| `convert.py` | 权重转换 |

官方README明确把这套实现定位为可读参考。
它的普通自回归生成不是完整DSpark生产验证调度器。

## 20. 一次源码阅读任务

选一个“文字—图像—文字”输入，按以下顺序画shape：

1. 编码器输出哪些token id和span类型。
2. 图片实际切出多少patch。
3. ViT输出多少1024维特征。
4. Aligner输出多少5120维特征。
5. 哪些embedding被覆盖。
6. 哪些位置使用视觉router bias。
7. 哪些位置跳过Engram。
8. 语言主干最终输出多少词表logits。

完成这个任务，比只背“原生多模态”更接近真正理解。

## 21. 自测与答案

**问题1：552B是否包含报告单列的196B Engram？**

答案：报告将二者单列；应写552B主干加196B Engram，避免口径混淆。

**问题2：8B/16B为什么不是两种top-k？**

答案：主要来自prefill跳过大量decoder位置与decode经过完整主干的差异。

**问题3：1344图片为何得到1024个视觉特征？**

答案：1344/14=96，96×96 patch经3×3重排变成32×32。

**问题4：Pixel-unshuffle是否就是平均池化？**

答案：不是，它把空间邻域重排到通道，再由MLP投影。

**问题5：视觉ViT双向attention是否泄漏未来输出？**

答案：图片是已给定输入；语言生成仍按因果mask处理。

**问题6：源码一致是否说明1017没有更新？**

答案：不能，权重与后训练可以更新而架构代码保持一致。

**问题7：1024视觉特征是否意味着图片恰好占1024个prompt位置？**

答案：不一定，还要计入图像边界/行标记等编码开销。
