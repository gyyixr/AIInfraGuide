## 1. 公开引擎与完整在线服务要分清

DeepInfer 来源于 DeepSeek 的推理系统，当前公开版本提供 V4.1-Flash 的离线推理核心。它包含模型执行、并行、调度、DSpark、结构化输出和若干缓存状态机制。

README 同时明确列出完整服务仍需要的部分：生产 KV cache system、VE/Prefill/Decode 解耦的服务组织，以及跨 Attention-DP 副本的负载均衡。

这并不意味着代码里没有 KV tensor 或 BlockManager。区别在于，单引擎内部的缓存分配与算子接口，不等于已经开放完整的外部缓存存储、服务路由和运营控制面。

本节核对官方 commit：

```text
a679bb86ce36e883a98a97733492b686e5b9a08e
日期：2026-11-07
```

本机另一个 DeepInfer checkout 的 HEAD 与此不同，本文的代码结论来自官方固定内容，而不是混用本地目录行号。

## 2. 先建立三层地图

| 层次 | 主要对象 | 负责的问题 |
|---|---|---|
| 入口与编排 | `LLM`、`EngineArgs`、`LLMEngine` | 请求、配置、worker与结果 |
| 调度与状态 | C++ `Scheduler`、Sequence/Block/Output pools | 本轮算谁、地址与状态什么时候有效 |
| 设备执行 | `Worker`、`ModelRunner`、模型与算子库 | 输入组织、图/模型前向、采样 |

底层继续调用 FlashMLA、DeepGEMM、DeepEP、DeepSelect、TileKernels 及专用算子，但不能据此省略中间的 metadata、stream 和对象所有权。

## 3. 入口的真实调用链

```text
deepinfer.entrypoints.llm.LLM(...)
  → EngineArgs(..., offline_inference=True)
  → LLMEngine.from_engine_args
  → 配置、tokenizer、worker、cache、scheduler初始化

LLM.generate(...)
  → _add_request
  → LLMEngine.add_request
  → _run_engine循环
      has_unfinished_requests
      step 或 flush_inflight_reqs
      clone输出并按request_id收集
  → token解码/返回
```

这条路径是离线 batch 接口，不应写成公开仓库已经提供完整、可直接替代生产 gateway 的在线服务链。

### 3.1 同名参数的最终值来自多层

`LLM.__init__` 会给部分参数设置入口默认值，再构造 `EngineArgs`。`EngineArgs.__post_init__` 还会根据 engine type 设置环境变量默认值，并对懒解析的环境项重新初始化。

因此只看 `environ.py` 中某字段的初始 factory 值，可能得不到实际入口的有效配置。

## 4. 一个具体例子：ZOS 默认值如何生效

环境描述器的 bool factory 默认值可以是 False，但 `EngineArgs.__post_init__` 对 `DEEPINFER_ZERO_OVERHEAD_SCHEDULING` 使用 `setdefault`：NORMAL 与 COMPLETION 引擎默认开启，PROMPT 引擎按其类型默认关闭。

它随后调用 `environ.rearm(...)`，避免某字段在配置确定前被访问并缓存了旧值。

| 情况 | 最终行为的来源 |
|---|---|
| 用户已设置环境变量 | `setdefault`不会覆盖 |
| 用户未设置，NORMAL/COMPLETION | engine type提供默认开启 |
| 用户未设置，PROMPT | engine type提供相应关闭默认 |
| 描述器此前已被读取 | rearm使之后按新环境重新解析 |

这个例子说明“文档说默认开”与“底层声明默认False”可以同时出现，必须沿实际构造链解决，而不是任选一处当真。

## 5. 并行度不是 EP×DP×CP 无条件相乘

固定 `ParallelConfig` 中，CP 作为 model-parallel size，Attention-DP 与 Engram 的范围共同影响 world size。

若 DP 未指定而为 0，配置先用 EP 与 CP 推导一个至少为 1 的 DP；Engram 度为 0 时也按其他维度推导。随后：

$$
W=\max(CP\times DP,\ EngramParallel).
$$

同时检查整除与 rank 范围约束。EP 必须与相应物理网格兼容，但不是再无条件乘一次。

### 5.1 两个例子

| 输入配置 | 推导 | world size |
|---|---|---:|
| CP=1、DP=8、EP=2、Engram=0 | Engram默认8，EP整除8 | 8 |
| CP=8、DP=0、EP=2、Engram=0 | DP推导为1，Engram为8 | 8 |

把第一行误算成 `1×8×2=16`，会错误理解设备数和请求复制关系。

这里的 DP 是 Attention 相关的执行视图，不能直接套用“每个 DP rank 都是完整独立 MoE 模型”的传统推理复制概念。具体 group 成员还要继续读 parallel state，而不是只看整数乘积。

## 6. 外层 DP 启动与内层 CP worker

公开 examples 的 `_launch.py` 根据节点 `RANK/WORLD_SIZE` 分配全局 DP rank，使用 spawn 创建进程；随后每个引擎再按 CP 创建 follower worker，并在本进程构建 driver worker。

这至少涉及两层编号：

- launcher 用来划分节点和 DP 工作的编号。
- 引擎内部的 CP rank、device local rank 和通信组成员。

示例中的环境变量语义应以该 launcher 代码为准，不能把某个脚本的 `WORLD_SIZE=节点数` 惯例误当成所有 `torchrun` 场景的统一含义。

GPU 可见设备列表、CP worker 绑定与并行配置必须一起核对；日志应同时保存逻辑组和物理设备映射。

## 7. Scheduler 返回的不只是一个 token batch

`LLMEngine.step()` 调用 C++ Scheduler，得到序列 metadata 和 scheduler outputs。后者还可能包含：

- 本轮是 prompt 还是 decode。
- 新排入、完成或需要处理的序列。
- 需要 clone/zero 的状态或块。
- 本轮 token 数、索引、采样与结构化输出状态。

若只把 scheduler 理解成“从队列里取几个请求”，就无法解释后续为何需要 clone、延迟释放和状态回填。

### 7.1 状态复制先于消费者

发生抢占、共享或特定缓存策略时，调度结果可能要求复制/清零状态。相关操作完成与何时解除 pin，要和本轮模型、采样及后处理共同组织。

不能在 CPU 队列里删除了序列，就立即认为其所有 KV/state slot 都已无人使用。

## 8. Worker 的 Forward—Post-process—Sample 循环

固定源码将每一步统一为以下顺序：

1. 执行当前 step 的主模型 forward。
2. 后处理上一个待完成 step。
3. 准备并执行当前 step 的采样。
4. 对 prompt 或非 ZOS step 立即后处理；ZOS decode 则把当前状态保存到下一步。

```text
step t:
  forward(t) → post_process(t-1) → sample(t) → 保存state(t)

step t+1:
  forward(t+1) → post_process(t) → sample(t+1) → 保存state(t+1)
```

目标是将部分 CPU 后处理与下一步设备执行重叠。它不意味着完全没有 CPU 开销，也不保证所有同步都消失。

例如某些序列长度修正需要等待 D2H 事件后更新 CPU metadata；这属于明确的数据依赖，不应简单删除以追求“零同步”。

## 9. ModelRunner 中禁止随意同步的区域

`execute_main_model` 先准备输入，再选择 CUDA Graph replay 或普通模型前向。`execute_sample` 则准备 sampler inputs 并调用模型采样。

两条核心路径都使用防止意外 CUDA 同步的约束，避免一次 `.item()` 或 host 读取把重叠窗口打断。

| 动作 | 所处阶段 | 必须核对 |
|---|---|---|
| 输入metadata准备 | 前向之前 | 有效数、padding、实际索引 |
| Graph replay | 主模型执行 | 地址、容量、shape桶 |
| eager forward | 主模型执行 | 与graph的数值及布局一致性 |
| sample/verify | 模型输出之后 | proposal、target、stop和grammar |
| D2H结果处理 | 同步点之后 | 读的是哪一step、对象仍否有效 |

“函数返回”与“device已经执行完”不能混为一谈；当前 stream 的依赖、结果事件和 host 消费点需要分别画出来。

## 10. 最后一轮为什么还要 flush

在 ZOS 下，最后一步 decode 的结果可能仍保存在 `prev_step_state`，等待下一步后处理。如果引擎发现没有未完成请求就直接退出，会漏交付最后一批结果或未完成资源释放。

公开 `_run_engine` 因此在没有普通 unfinished 请求时仍调用 `flush_inflight_reqs()`，再结束循环。

一个教学状态机：

| 调用 | 当前forward | 返回的已后处理结果 |
|---|---|---|
| step 0 | batch 0 | 可能尚无decode结果 |
| step 1 | batch 1 | batch 0 |
| step 2 | batch 2 | batch 1 |
| flush | 不再启动普通新batch | batch 2 |

实际 prompt、placeholder 和非 ZOS 分支会改变细节，不能把这个简图当成所有 step 的固定输出数量。

## 11. 输出池的所有权是可见的 API 契约

`step()` 返回的数据中包含受 output pool 管理的对象/指针表达。文档说明这些对象可能在下一步释放；若调用者需要长期保留，必须 clone。

入口 `_run_engine` 会对 raw output 做 `RequestOutput.clone(...)` 后再放进结果集合。这不是无意义的数据复制，而是跨越生命周期边界。

`DeferredRelease` 收集本轮需保留的 metadata、output 和 pin 信息，在后续安全阶段再释放。省掉这一步可能引入 use-after-free 或“对象仍存在但字段已经属于新请求”的错误。

### 11.1 不能只验证返回数量

最小回归应检查：

- request ID 是否正确。
- token ID、位置和 finished 状态是否属于同一请求。
- flush 后是否仍有遗留结果。
- clone 后的结果能否跨下一步保持不变。
- 中止/超时/grammar失败是否恰好释放一次资源。

这些与最终文本是否可读是不同层次的正确性。

## 12. 扩展钩子不等于功能已经实现

固定 `LLMEngine` 中可看到 `init_pd_split`、`do_save_kvcache`、`pe_do_save_kvcache`、`send_processed_prompts` 等扩展方法，其中若干只有说明或默认空实现。

这些钩子说明引擎预留了集成边界，但不能据此写成“仓库已经提供完整 PD 部署与外部 KV 服务”。

| 公开核心中可见 | 完整服务仍需补充 |
|---|---|
| 内部KV/state buffer和调度 | 跨请求/跨副本的持久缓存系统 |
| PROMPT/COMPLETION类型与钩子 | 服务发现、路由、传输协议与重试 |
| 单引擎结果组织 | 在线协议、配额、鉴权、流式背压 |
| Attention-DP执行支持 | 跨完整服务副本的负载与cache-aware routing |

这是论文、开源引擎与生产系统之间最重要的复现边界之一。

## 13. Bounded Replay 与缓存精确性

V4.1 的 decoder SWA 可用 bounded replay 减少部分 prefill 工作。代码提供 `off`、`mask`、`compact` 等模式，并检查保留后缀覆盖 SWA 窗口与最大回退范围。

例如假设窗口为 128，nextn=5，最低回退预算至少为 6，则保留后缀不能短于 $128+6=134$。README 的示例保留 140 个 token，满足这个示意约束。

但满足 buffer/回退范围不等于数学上与完整 prefill 严格相同。模型报告说明 bounded replay 是近似，边界 hidden state 与命中位置可能影响结果；代码也对相关抢占场景作了提醒。

因此质量与可复现测试必须固定缓存命中与 replay 模式，不能把缓存命中差异统统归为随机采样噪声。

## 14. “确定性采样”需要一组配置

公开说明将 batch-invariant inference 与 deterministic sampling 分开。要获得特定确定性模式，需要设置 batch-invariant、关闭相应 variable-length MTP 调度，并给每请求固定 `seq_seed`；该保证还有平台范围。

仅设置一个全局 seed，不能自动推出不同 batch 组合、不同 cache hit、不同图桶、不同后端都逐 token 相同。

阅读或复现时至少记录：

```text
model revision / tokenizer revision
平台及kernel版本
batch-invariant开关
MTP/varlen/nextn参数
seq_seed与采样参数
bounded replay模式与cache命中状态
```

## 15. 结构化输出也是独立生命周期

Grammar/JSON schema 的编译、matcher 构建、mask 生成和请求结束状态会与调度交互。

一个结构化输出请求不能因为 matcher 尚未就绪就被当成普通无约束采样，也不能在 matcher 构建失败后永久占据 KV。当前 step 中存在对异常 SO bookkeeping 的检查和请求级终止处理。

验收除了 JSON 能否解析，还需检查取消、EOS、空输出、编译超时和资源回收；这与 Agent 工具协议的可靠性直接相关。

## 16. 依赖锁定：主仓库 SHA 不是全部

DeepInfer 的 vendor gitlink 固定了依赖版本。本节快照中，例如：

| 依赖 | vendor固定SHA |
|---|---|
| DeepEP | `f6aa38fe06cd4a0489e7730365d4e0114970a2f3` |
| DeepGEMM | `1fc9c66975ee322d628b3288534ca0e9ce12a64d` |
| FlashMLA | `2e5429fc5653bab6e081f09477126f731882a6a9` |
| DeepSelect | `bfa4507d935f17ebfc3d0f00ff7d3c9a4d0e5c18` |

它们不全等于本专题第 5/6 章单独研究的各项目最新快照。分别解释某个库的最新公开能力，不代表这些 main HEAD 已作为一整套组合验证。

复现引擎时应优先保留其依赖锁定关系，再在需要时做有对照的升级，而不是把所有子项目一起更新到最新。

## 17. Benchmark 的边界

README 的公开性能图报告了特定 SM100 prefill/decode 集群规模，属于团队报告。examples 还将 prefill 与 decode 的 profiling 窗口、请求数量和长度分开组织，并复用相应 prefix KV。

因此应说明：

- prefill测的是非缓存后缀还是完整输入。
- decode有多少有效请求，哪些短请求已退出。
- warm-up和稳态采样是否被数据量填满。
- 启用了哪些DSpark、replay、EPLB与图选项。
- 计时是单引擎离线吞吐还是在线SLO下goodput。

不能把这组图直接解释成任意用户在线请求的 TTFT、TPOT 或单位成本。

## 18. 一条可审查的阅读与实验路线

1. `entrypoints/llm.py`：请求创建、结果clone和最终flush。
2. `engine/arg_utils.py`、`config.py`：有效默认值与并行约束。
3. `engine/llm_engine.py`：调度、状态复制、扩展钩子与延迟释放。
4. `worker/worker.py`：Forward—Post-process—Sample循环。
5. `worker/model_runner.py`：输入、Graph与禁止意外同步的区域。
6. `model_executor/layers/sampler.py`：采样、验证、stop和grammar。
7. `examples/README.md` 与测试：benchmark/PPL/多模态基线的真实输入和边界。

在匹配硬件前，可以先做并行度算例、输出生命周期模拟和小张量数学 oracle。本次未加载 V4.1 全量权重，也未运行 SM100/Ascend950 的真实引擎。

## 19. 自测与深入追问

**1. 为什么env字段默认False，正常入口却默认启用ZOS？** EngineArgs按engine type设置缺省环境值并rearm懒解析字段；有效配置来自完整构造链。

**2. EP=2、DP=8、CP=1是否需要16张卡？** 按本快照默认Engram配置，world为8；EP是兼容网格中的专家通信视图，不能重复相乘。

**3. ZOS decode的结果为什么可能晚一轮返回？** 上一步后处理与当前forward重叠，当前状态保留到下一步；退出前需flush。

**4. 为什么入口要clone raw output？** output pool的对象可能在下一step释放或复用，clone跨越了临时生命周期。

**5. 找到`do_save_kvcache`就能声称外部KV服务开源吗？** 不能，默认扩展钩子与完整存储/路由/故障协议有明确差别。

**6. 保留SWA窗口加回退长度是否证明replay精确？** 只满足必要资源范围；bounded replay本身仍是近似，需单独测质量与可复现性。

**7. 为什么不直接把所有vendor库升级为最新？** 缓存格式、ABI、布局与API可能变化，主仓库锁定了一组组合；升级需逐项对照验证。

**8. “zero-overhead”是否不再需要CPU同步？** 不是；它组织关键路径的重叠，真实的数据依赖、D2H与结果交付仍有同步点。
