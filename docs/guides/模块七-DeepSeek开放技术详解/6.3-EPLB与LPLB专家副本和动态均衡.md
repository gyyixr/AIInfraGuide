## 1. 四种“负载均衡”不能合成一个开关

MoE 系统中可以在不同层做均衡：

| 层次 | 决策对象 | 是否直接改变模型路由 |
|---|---|---|
| 模型训练 | router 分数、偏置、辅助损失 | 可能改变逻辑专家选择 |
| 物理放置 | 哪张卡存哪些专家或副本 | 不应改变逻辑专家函数 |
| 当前 batch 分发 | 同一逻辑专家用哪个物理副本 | 保持等价副本时不改变逻辑选择 |
| 服务路由 | 请求送到哪组完整模型副本 | 改变请求调度与缓存局部性 |

DeepSeek 的 EPLB 与 LPLB 主要处于第二、三层。它们并不替代训练时的负载均衡机制，也不直接解决 HTTP 层的多租户排队。

本节核对日期为 2026-11-07：

- EPLB：`d52c72d5b2f2fb4c41afbf8eb21366820239913d`。
- LPLB：`0490f79452f7ef277e814449600b1b1dd4c663b3`。

EPLB 官方仓库公开了其放置规划算法；LPLB 明确标注早期研究阶段，不能将其性能优势写成普遍成立的生产结论。

## 2. 为什么平均计算量不决定一层耗时

假设四张 GPU 分别处理 120、60、30、30 个等成本专家 token。总工作量为 240，平均每卡 60，但同步执行时间由最忙的 120 决定。

若每个 token 的计算时间简化为 $c$，只考虑计算：

$$
T_{layer}\approx c\max_i L_i.
$$

一个直观的不均衡指标是：

$$
\eta_{balance}=\frac{\operatorname{mean}(L_i)}{\max_iL_i}.
$$

上述值为 $60/120=0.5$。它不是完整 GPU 利用率，只是在等成本、同步等待模型下刻画负载分布。

真实成本还随 GEMM shape、padding、量化、通信距离和设备状态变化。因此负载统计用 token 数，还是用预测时间，需要明确。

## 3. 逻辑专家与物理副本

设模型有 $E$ 个逻辑专家，逻辑专家 $e$ 的预计负载为 $w_e$，分配 $r_e\ge1$ 个副本。若请求能均匀分给相同专家的副本，则每副本预计负载：

$$
\widetilde w_e=\frac{w_e}{r_e},\qquad \sum_e r_e=R.
$$

$R$ 是总物理槽位数，通常需要满足每 GPU 相同槽位容量等约束。增加副本减少单副本负载，却增加权重驻留、加载和一致性维护成本。

物理副本不是新专家：它们应提供相同的参数函数。推理中还需确保量化 scale、adapter 和参数版本一致；训练中必须把副本梯度合回正确优化器状态。

## 4. EPLB 的两个规划层次

固定源码的核心函数包括：

- `replicate_experts`：决定哪些逻辑专家增加副本。
- `balanced_packing`：在每包元素数量受限的前提下，尽量均匀放置带权对象。
- `rebalance_experts_hierarchical`：把组、节点、GPU 的层次连接起来。
- `rebalance_experts`：选择层级或全局策略并生成映射。

### 4.1 贪心复制

初始每个逻辑专家一个副本。每增加一个物理槽位，选择当前 $w_e/r_e$ 最大的专家，再给它增加一份副本。

直觉是先拆最重的单副本工作。它解决的是这个规划模型中的负载拆分；最终 GPU 的负载还取决于 pack 约束和布局，不是直接得到端到端全局最优。

### 4.2 容量受限的 packing

`balanced_packing` 按对象重量降序处理，把下一个对象放到仍有空槽位且当前负载最小的包。

如果每 GPU 只能放两份专家，不能为了追求负载相等而让一张卡放五份。权重内存容量与专家槽位数是这类规划的硬约束之一。

## 5. 逐步复算一个官方算法输入

取逻辑负载：

$$
w=[120,60,30,30],\qquad E=4,\quad R=8.
$$

从副本数 `[1,1,1,1]` 出发，四次增配为：

| 步骤 | 当前每副本负载 | 本轮增配 | 新副本数 |
|---|---|---|---|
| 1 | `[120,60,30,30]` | 专家 0 | `[2,1,1,1]` |
| 2 | `[60,60,30,30]` | 并列时本例选专家 0 | `[3,1,1,1]` |
| 3 | `[40,60,30,30]` | 专家 1 | `[3,2,1,1]` |
| 4 | `[40,30,30,30]` | 专家 0 | `[4,2,1,1]` |

最后八个物理副本的预测负载都为 30。四 GPU、每 GPU 两个槽位，理想 pack 后每卡为 60。

相对于初始最大值 120，等成本计算模型里的慢卡负载降为 60。但副本数量从 4 增至 8，权重驻留容量翻倍；规划、迁移和路由也并非零成本。

### 5.1 本次 CPU 实际执行结果

本项目在 CPU 上执行了上述固定版本的官方 `eplb.py`：

```text
logical loads        = [[120,60,30,30]]
num_replicas         = 8
num_groups           = 1
num_nodes            = 1
num_gpus             = 4

replica counts       = [[4,2,1,1]]
physical_to_logical  = [[0,0,1,0,2,1,3,0]]
estimated GPU loads = [[60,60,60,60]]
```

`physical_to_logical` 连续两个槽位分给同一 GPU。本次结果在一张 GPU 上放了同一逻辑专家的两份物理槽位，这反映了算法的槽位/负载模型，不能据此声称它已经优化所有去重、内存与执行细节。

记录在 `labs/deepseek/results/eplb-reference.json`。该实验验证 Python 规划输出，没有执行 GPU 专家计算、权重迁移、分布式训练或性能测试。

## 6. 三张映射表怎样一起使用

输出不是只有一份“专家排列”：

| 映射 | 方向 | 用途 |
|---|---|---|
| `phy2log` | 物理槽位 → 逻辑专家 | 加载正确权重、解释本地槽位 |
| `log2phy` | 逻辑专家 → 多个物理槽位 | 路由时选择副本 |
| `logcnt` | 逻辑专家 → 副本数 | 有效范围与分流 |

`log2phy` 为了保持矩形 shape 可以包含 `-1` padding，不能把它当成一个有效物理目标。消费时应结合 `logcnt`，并确保物理槽位到 rank/本地偏移的映射一致。

一个稳妥的验证是对每个逻辑专家枚举所有有效物理槽位，再检查反向映射都回到该专家；还要检查每个物理槽位恰好被解释一次。

## 7. 层级策略与全局策略

模型的 group-limited routing 会让专家组具有通信局部性。若规划条件允许，可以先把专家组分到节点，再在节点内部复制和放到 GPU，减少跨节点流量。

固定实现按 `num_groups % num_nodes == 0` 选择层级路径；否则使用把专家作为全局集合的路径。这个条件是该代码的组织约束，不是“所有网络都以它判断性能最优”的定律。

层级选择涉及三种目标：

1. 节点间的负载均衡。
2. 节点内部各 GPU 的负载均衡。
3. 模型路由造成的跨节点通信。

仅看最后一项或仅看 token 数都可能得出错误方案。相同负载放置在不同 RDMA/NVLink 拓扑上，实际关键路径可能不同。

## 8. 负载预测不是仓库自动完成的功能

EPLB 的输入是预计负载。官方 README 明确把如何预测负载留给集成者，可以基于历史统计的移动平均等方法。

例如：

$$
\widehat w_{t}=\alpha w_t+(1-\alpha)\widehat w_{t-1}.
$$

$\alpha$ 太大，规划频繁追逐单个 batch 的噪声；太小，热点变化后反应慢。真正系统还需要最小重排间隔、收益阈值和迁移预算。

### 8.1 用一个阈值计算是否值得迁移

假设重排需要 200 ms，预计之后每批节省 2 ms，热点预计持续 200 批。忽略其他成本：

$$
\text{净收益}\approx200\times2-200=200\text{ ms}.
$$

若热点只持续 50 批，净收益为 -100 ms。这些是教学数字，说明需要预测持续时间，而不是每看到一点不均衡就搬权重。

还需考虑迁移期间双份权重的显存峰值、量化 scale、在途 batch 与策略版本。

## 9. LPLB：固定副本拓扑上的动态流量分配

EPLB 更适合根据估计统计规划放置。即使长期负载平衡，单个小 batch 仍可能随机产生严重偏斜；LPLB 尝试用线性规划在已经准备好的副本连边上动态转移可转移的 token。

简化为一个有向图。GPU 为节点，存在某个逻辑专家的冗余副本就允许在相应边上转移该专家的任务。

设初始负载 $l_i$，边流量 $f_{ij}$，边容量 $c_{ij}$：

$$
0\le f_{ij}\le c_{ij},
\qquad
l'_i=l_i-\sum_jf_{ij}+\sum_jf_{ji}.
$$

一个教学目标是：

$$
\min z\quad\text{s.t.}\quad l'_i\le z\quad\forall i.
$$

不是所有 token 都能流向所有 GPU；只有该目标有对应逻辑专家副本，且满足当前 batch 可转移数，才有有效边容量。

### 9.1 两 GPU 的手算

初始负载 `[10,2]`，GPU 0 有最多 4 个任务可以转到 GPU 1：

$$
l'_0=10-f,\qquad l'_1=2+f,\qquad0\le f\le4.
$$

令二者相等得 $f=4$，最终 `[6,6]`，最大值从 10 变成 6。

若容量只有 2，最优只能到 `[8,4]`。增加更多 LP 求解迭代不能突破没有副本或没有可转移 token 的结构限制。

## 10. LP 最优不等于端到端最优

官方 LPLB 明确指出若只平衡总 token 数，没有考虑 grouped GEMM 的非线性时间，可能得到实际次优方案。

例如某 GPU 的专家任务从 1+63 行变成 32+32 行，token 总数都是 64，但 tile、padding、kernel 并行性可能完全不同。跨节点搬运也可能抵消计算侧节省。

官方说明求解本身可能达到约百微秒量级，并将其列为小 batch 的成本风险；这属于项目自报特定实现量级，不是本文本机测量。

评估应同时记录：

- 规划前后每 GPU、每专家的真实有效数。
- solver 时间与通信同步时间。
- grouped GEMM 的实际 shape 和执行时间。
- 新增 dispatch/combine 距离与网络拥塞。
- 整层或整 token 的 p50/p95/p99 延迟。

## 11. 接口年代要单独核对

本节固定 LPLB README 仍描述与旧 DeepEP/NVSHMEM 路径的集成；当前 DeepEP V2.5 已更换接口和后端。

因此不能把两个项目各自最新的 commit 简单安装在一起，就认为官方已经验证兼容。应固定一个受支持组合，或者明确编写适配并完成前向、反向与生命周期测试。

EPLB 的纯 Python 放置规划与 GPU 通信解耦较多，但“能运行规划”不证明模型运行时已消费了新映射。

## 12. 训练中的副本一致性

推理副本主要关心权重版本，训练副本还增加梯度和 optimizer ownership。

```text
原专家参数版本k
  → 副本权重/scale同步完成
  → 使用版本k进行专家前向和反向
  → 副本梯度归回原专家
  → 原专家optimizer更新到k+1
  → 下一轮发布或预取
```

如果物理放置在前向后、反向前改变，却没有保留旧映射，梯度可能归给错误专家。checkpoint 也需要知道逻辑参数归属，不能把临时物理槽位编号当作永久模型参数名。

## 13. 实验设计与验收

建议按三层推进：

1. **规划层**：CPU 上检查映射、容量、负载守恒和极端输入；本次已执行这一层的官方 EPLB 例子。
2. **数值层**：小模型比较固定映射与副本重定向后的前向、输入梯度和专家梯度。
3. **系统层**：真实 GPU 拓扑下测 planner、迁移、dispatch、GEMM、combine 和端到端收益。

有价值的极端输入包括全零负载、单专家热点、热点突然迁移、组数不能整除节点数、物理槽位不足、某个副本失效和多个在途版本并存。

## 14. 自测与参考答案

**1. 给热点专家复制两份，为什么不等于模型多了两个专家？** 它们仍代表同一逻辑函数，参数相同；只是运行位置和任务分流改变。

**2. `[120,60,30,30]` 增配到八份，副本计数是什么？** 本例固定算法为 `[4,2,1,1]`，每副本预计负载为 30。

**3. 平均负载已经均衡，还可能有长尾吗？** 会。每批随机性、不同 GEMM shape、通信与设备 fail-slow 都可能产生尾部延迟。

**4. 为什么负载预测必须版本化记录？** 规划根据历史估计作出；不保存统计窗口和预测参数，就无法解释某次映射为何有效或失效。

**5. LP 能否把任意 token 调到空闲 GPU？** 不能，目标 GPU 必须有对应逻辑专家副本，边容量也受可转移任务限制。

**6. 最忙卡 token 数下降就应上线吗？** 不够，需要把求解、同步、迁移和新通信成本计入完整层或请求的关键路径。

**7. 用 CPU 跑通官方 EPLB 证明了什么？** 证明该输入下规划程序和映射结果可执行；不证明专家执行、动态迁移或 GPU 加速。
