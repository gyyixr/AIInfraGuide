## 1. “同一 API”需要拆成多层检查

一个项目可以在两种加速器上提供相同 Python 函数名，但这不意味着设备二进制、scale 格式、stream 行为和全部子功能都完全相同。

应分别检查：

1. 导入路径与函数签名。
2. 数学语义与支持 dtype。
3. 输入/输出的实际 layout、stride 和打包格式。
4. buffer、异步和 Graph 生命周期。
5. 单机/多机的通信拓扑与参与者约束。
6. 编译器、运行时、驱动与固件组合。
7. 正确性、性能和生产路径实际验证范围。

本节按 2026-11-07 的官方固定资料建立矩阵，不把“支持 Ascend”或“支持 NVIDIA”当成一个无条件布尔值。

## 3. NVIDIA 路径也不是一个统一支持范围

| 库 | 当前README所列主要目标 | 关键边界 |
|---|---|---|
| DeepGEMM | SM90/SM100 | 各GEMM/融合路径、scale和布局分别检查 |
| DeepEP | Hopper或更新架构的指定环境 | CUDA/NCCL/互联及buffer模式约束 |
| FlashMLA当前版本 | SM100/SM103 | 已改变旧模型和KV格式兼容性 |
| TileKernels | SM90/SM100 | Python/PyTorch/TileLang和具体kernel限制 |
| DeepInfer当前公开核心 | SM100 | 全模型、并行、内存与依赖组合 |

表中的硬件范围来自项目声明；没有写入的未来架构不能自动视为已验证。

FlashMLA还需要按kernel细分：当前Ascend支持指定的稀疏prefill/decode，dense MHA forward/backward和fused norm-RoPE-attn-RoPE-cast仍仅有CUDA路径。仓库支持两种后端不等于每个导出算子都具备相同覆盖。

尤其，RTX 3090 的 SM86 不会因为软件能表示 FP8/FP4 dtype，就自动获得这些新架构 kernel 的执行能力。数据格式、编译目标和硬件指令支持是不同层。

## 4. DeepGEMM-Ascend 的实现思路

该项目保持 `deep_gemm` 包与相关矩阵接口，使用 Ascend 的矩阵乘加原语构建对应内核，并处理分形布局、地址计算、对齐与设备侧流水。

矩阵数学仍是同一组 GEMM；实际优化利用的是 Ascend 的计算和数据搬运机制，不能将 WGMMA/TMA 等 NVIDIA 术语直接改名后当作完整实现解释。

固定 README 的开发验证目标是 Ascend 950 系列，工具链列出 CANN 9.20、Bisheng、`torch_npu`、C++20 等。CANN 的具体版本与包名应以实际可安装环境记录为准，不凭近似版本号推断兼容。

### 4.1 共同矩阵接口下的不同 scale 容器

当前文档指出，Ascend 路径将 K 方向每两个 UE8M0 scale 打包进一个 int16，并采用适合硬件的 MN-major 排列；NVIDIA 对应路径可能使用四个 scale 的 int32 打包。

| 逻辑scale | NVIDIA示意容器 | Ascend示意容器 |
|---|---|---|
| `s0,s1,s2,s3` | 一个32-bit word | 两个16-bit word |
| 索引到scale | 按该内核的packed layout | 按Ascend对应layout |
| 转换入口 | 对应layout utility | Ascend对应layout utility |

即使小端字节序列碰巧相同，tensor 的 dtype、shape、stride 和行列排列仍可能不同。一次 `.view()` 不能自动完成任意布局适配。

### 4.2 可手算的打包例子

UE8M0 编码 `[127,128,129,130]` 分别表示指数尺度 `[1,2,4,8]`：

```python
codes = [127,128,129,130]
word32 = sum(v << (8*i) for i,v in enumerate(codes))
words16 = [codes[0] | (codes[1] << 8),
           codes[2] | (codes[3] << 8)]
assert [(word32 >> (8*i)) & 255 for i in range(4)] == codes
assert [words16[0] & 255, words16[0] >> 8,
        words16[1] & 255, words16[1] >> 8] == codes
```

该代码只验证打包关系，不验证真实 MN-major stride、设备转换函数或特定 tensor 的合法性。

## 5. Dtype 组合与 epilogue 要单独核对

同样叫低精度 GEMM，输入可能是 FP8×FP8、FP8×FP4、FP4×FP4 或 BF16×BF16。是否支持某个混合组合，以对应接口和测试为准。

Ascend 文档还区分完整 C tensor 与 `[1,N]` bias 的 epilogue 路径。它们在存储、原子累加和cast前后顺序上可能不同。

将 `D=C+AB` 的数学等式写对，只是第一步。需要继续核对：

- C/D 是否具有相同 dtype。
- C 是完整矩阵还是广播 bias。
- 是否累加到已有输出。
- scale 是否只接受指数形式，而非任意 FP32 实数。
- 输出 cast、饱和和舍入发生在何处。

误把“FP32容器”理解成“任意FP32 scale数值都合法”，是格式迁移中的典型错误。

## 6. DeepEP-Ascend 的通信栈

Ascend 版本对齐 DeepEP 的 buffer 风格 API，但底层使用 HCCL/HCOMM、UBMEM、URMA 和 Ascend C kernel，并通过 DeepJIT 编译。

| 层次 | NVIDIA路径中的典型对象 | Ascend对应路径 |
|---|---|---|
| 框架tensor/stream | PyTorch CUDA | PyTorch + torch_npu |
| 通信运行时 | NCCL Gin等 | HCCL/HCOMM等 |
| 机内/机间传输 | NVLink、RDMA | 对应UBMEM/URMA连接 |
| 计算资源参数 | SM数量 | 同名兼容参数可能解释为AI core数量 |
| 设备编译 | CUDA工具链 | CANN/Bisheng |

参数名 `num_sms` 在兼容接口中可能保留，但不能据此声称 NPU 内部就是 CUDA SM。

## 7. 当前能力矩阵中的未实现项

固定 DeepEP-Ascend README 给出具体限制：

| 功能 | 当前公开边界 |
|---|---|
| EPBuffer | expanded BF16/FP8 dispatch、BF16 combine等指定模式 |
| Bucket | 已有batched all-gather；RS/AR设备kernel仍在开发 |
| 专家副本预取/梯度归还 | 对齐了API，但Ascend通信kernel尚未实现 |
| PP/Engram | 实验功能，继续验证中 |
| Hybrid通信 | 不支持 |
| CPU-backed Engram | 不支持 |
| Graph capture | 不支持 |

因此“存在同名方法”和“功能可执行”必须分开。不能因为 NVIDIA 分支某方法已有成熟实现，就把相同结论直接写到 Ascend 分支。

### 7.1 参与者和模式约束

文档要求支持的 Ascend 主机与互联、匹配 CANN/torch_npu，并对多 rank 数量及 EP 参数给出限制。比如该版本多 rank 通信要求偶数 rank；EP 要求指定 expanded/reduction 模式。

这些条件应在启动前检查，不能等到 collective hang 才猜测哪个 rank 的协议不同。

## 8. PoC 测量与公开部署基线

DeepEP-Ascend README 对性能环境作了特别说明：报告使用特定 Ascend 950DT、CANN、PoC HDK 与手动配置，并同时提到供应商商业版本的发布计划。

不能把计划日期当成已经公开可下载的事实，也不能把 PoC 测量写成在任意公开驱动上可直接复现的结果。实际部署要记录拿到的准确版本及厂商支持条件。

本教程没有修改任何驱动或固件，也没有在 NPU 上复现这些结果。这里的重点是读懂报告与复现环境之间的证据边界。

## 9. TileKernels 与 TileLang 的归属

TileKernels 是 DeepSeek 组织下公开的算子集合；TileLang 是独立的 `tile-ai` 项目。前者使用后者，但不能把整个 TileLang 生态都归为 DeepSeek 独有技术。

当前 TileKernels 包含路由、量化、Engram、mHC、随机数和变换等算子，并提供相应 PyTorch reference 与测试组织。

| 层次 | 典型职责 |
|---|---|
| TileLang | DSL、编译和后端生成机制 |
| TileKernels | 针对模型操作的具体高性能实现 |
| DeepInfer/训练系统 | 选择算子、准备布局与维护状态 |

看到有多个后端，并不保证每个算子在每个后端上具有完全相同的支持范围或误差表现；应按实际测试矩阵验收。

## 10. 如何做跨后端正确性对照

第一步不要比较最终自然语言答案，而是固定输入，在相同数学目标下对照：

1. 参数和 scale 的逻辑值。
2. shape、轴含义、padding与mask。
3. 单算子FP32/BF16参考输出。
4. 中间激活、梯度或缓存反量化结果。
5. 多层/多步误差增长。
6. 最终PPL、任务质量与采样协议。

假设两个后端输出差异为 $\Delta$，要同时观察绝对误差、相对误差和输入尺度；接近零的参考值可能让相对误差非常大，因此单一指标不足够。

同 seed 不自动代表同随机序列或同舍入，跨平台逐 bit 一致是比数学近似一致更强的要求。

## 11. 相同软件包名的环境风险

DeepGEMM 与 DeepGEMM-Ascend 都可提供 `deep_gemm`，DeepEP 的两个平台也可使用相同包名。安装后实际 import 到哪份代码，应通过包来源与文件路径确认。

推荐将不同后端的依赖环境分别锁定，再记录：

```text
Python / PyTorch / torch_npu
device architecture
CUDA或CANN及编译器
各仓库commit和submodule commit
实际import文件路径
配置与测试结果
```

不是通过堆叠更多包就能获得一个同时支持全部设备的环境。当前公开接口相容，也不等于已支持异构设备共同组成同一个 collective group。

## 12. 性能数字的口径校验

DeepGEMM-Ascend 报告了一组 BF16 GEMM：M=4096、N=7168、K=16384，耗时约2229.9微秒，报告约431 TFLOPS。

按一次乘和一次加计：

$$
F=2MNK\approx9.62\times10^{11},
\qquad F/T\approx431\times10^{12}\ \mathrm{FLOP/s}.
$$

这只能核对数值计算口径。它仍绑定官方的设备、CANN、cold-L2测量方式和shape，不能推出整个模型达到相同比例的硬件峰值。

跨平台比较还要统一精度、实际工作量、batch、通信、预处理和质量；把FP4峰值除以BF16实际吞吐没有公平意义。

## 13. 多后端迁移的验收表

| 阶段 | 必要证据 |
|---|---|
| API接入 | 参数、返回值、异常与未实现路径确认 |
| Tensor布局 | scale、packing、stride与索引空间对齐 |
| 算子正确性 | 小确定例、随机例、边界形状与误差 |
| 异步执行 | stream依赖、buffer生命周期与取消 |
| 分布式路径 | rank/容量一致、collective顺序与故障处理 |
| 性能 | 同负载、同精度、同质量的端到端测量 |
| 发布 | 回归阈值、环境锁定、回退与已知限制 |

这个表描述工程流程，不声称所有公开库已替集成者完成上述全部证明。

## 14. 如何在只有一张 RTX 3090 时学习

可以执行与设备无关的矩阵、scale、路由、TopK、softmax与状态机 oracle；也可以用普通 PyTorch 对模型机制做小规模参考计算。

但不能把这些结果标为 FlashMLA SM100、DeepEP RDMA、Ascend MegaMoE 或完整 V4.1 的性能验证。

本模块第 9 章把可本地运行的数学实验和需目标硬件的复现项目分开列出。硬件不足时仍能验证很多语义，但证据等级必须保持清楚。

## 15. 自测与参考答案

**1. API兼容是否意味着可以直接复用序列化的scale tensor？** 不一定，容器dtype、打包粒度和物理布局可能不同。

**2. 同名`num_sms`在Ascend路径意味着什么？** 它可能是兼容接口，实际选择AI core资源；应看该后端说明。

**3. 公开`lb_prefetch_weights`方法是否证明设备kernel实现了？** 不证明，当前Ascend文档明确存在API已对齐、kernel未实现的情况。

**4. 支持多种后端是否支持混合GPU/NPU通信组？** 不能推断，需要独立的异构collective和执行支持证据。

**5. PoC HDK上的报告为什么不能当成公开环境复现？** 固件与配置不同，且报告本身说明其测量基线，公开商业版本计划不是实际结果。

**6. 为什么要检查import文件路径？** 相同Python包名可能来自不同平台包，安装成功不代表选到了预期实现。

**7. 单算子达到99%峰值说明整模型也如此吗？** 不能，模型还有小算子、通信、路由、缓存与调度等不同瓶颈。
