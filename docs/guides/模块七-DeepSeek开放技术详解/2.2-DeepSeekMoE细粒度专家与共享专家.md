MoE 的关键是把“总共拥有多少参数”和“这个 token 使用多少参数”分开。
DeepSeekMoE 进一步把专家切得更细，并让一部分专家承担共享计算。

核对日期：2026-11-07。
本节以 [DeepSeekMoE 论文](https://arxiv.org/abs/2401.06066)、[V3 固定版本路由代码](https://github.com/deepseek-ai/DeepSeek-V3/blob/9b4e9788e4a3a731f7567338ed15d3ec549ce03b/inference/model.py#L551) 为主，再对照 V4/V4.1 配置。
数值例子是自行构造的教学模型。

## 1. 先从一个普通 FFN 算参数

SwiGLU 专家可写为：

$$
E_i(x)=W_{2,i}\left[\operatorname{SiLU}(W_{1,i}x)\odot W_{3,i}x\right].
$$

令隐藏维为 $D$，专家中间维为 $d_e$。
忽略 bias，每个专家包含：

$$
P_e=Dd_e+d_eD+Dd_e=3Dd_e.
$$

三个矩阵不是三倍的深度，而是两个并行上投影和一个下投影。

| 张量 | 单 token shape | 一批 $N$ 个 token |
|---|---|---|
| 输入 | `[D]` | `[N,D]` |
| gate 分支 | `[de]` | `[N,de]` |
| up 分支 | `[de]` | `[N,de]` |
| 逐元素相乘 | `[de]` | `[N,de]` |
| 输出 | `[D]` | `[N,D]` |

## 2. 把一个 FFN 换成专家池

设共有 $N_r$ 个 routed experts，每个 token 选择 $K$ 个：

$$
y_t=\sum_{i\in S_t}g_{t,i}E_i(x_t),\qquad |S_t|=K.
$$

如果每个专家形状相同：

$$
P_{\mathrm{total,experts}}=N_rP_e,
\quad P_{\mathrm{active,experts}}=KP_e.
$$

但模型总参数还包括 attention、embedding、router、norm 等。
因此“总专家数除以 top-k”通常不等于总模型参数除以激活参数。

## 3. 细粒度切分的直觉

原本有 $N$ 个大专家，每个中间维为 $d_e$，每次激活 $K$ 个。
把每个专家的宽度缩小 $m$ 倍、专家数量增加 $m$ 倍：

$$
N\longrightarrow mN,\quad d_e\longrightarrow d_e/m,
\quad K\longrightarrow mK.
$$

忽略路由与通信开销，参数量保持：

$$
(mN)\cdot3D(d_e/m)=N\cdot3Dd_e.
$$

每 token 激活的专家矩阵参数量也保持：

$$
(mK)\cdot3D(d_e/m)=K\cdot3Dd_e.
$$

变化在于模型可以拼出更多专家组合。

## 4. 一组组合数例子

取原始 $N=4,K=1,m=2$。
原模型每个 token 从4个大专家中选择1个，有4种选择。
切分后从8个小专家中选择2个，有：

$$
\binom82=28
$$

种无序组合。

每个小专家中间维只有原来一半，因此激活的专家 FFN 计算近似相同。
模型不再必须把一整块能力绑在一个大专家上。

但“28种组合”不保证训练后28种都被使用，更不保证专家自动按人类学科分类。
专家分工是训练结果，需要路由统计、激活分析与干预实验才能判断。

## 5. 为什么还需要共享专家

一些计算对很多 token 都有用。
如果每个 routed expert 都学一份，参数可能重复消耗。
共享专家让这部分计算始终执行：

$$
y_t=\sum_{j=1}^{N_s}E^{\mathrm{shared}}_j(x_t)
+\sum_{i\in S_t}g_{t,i}E^{\mathrm{routed}}_i(x_t).
$$

共享专家的结果通常直接相加；不要默认它也由同一个 top-k gate 加权。
具体合并方式必须跟随模型实现。

在 V3 参考实现中，共享路径写成一个更宽的 `MLP`。
`n_shared_experts * moe_inter_dim` 是其合并后的中间维。
这与把等宽共享专家的输出相加具有对应关系，但物理模块组织可以不同。

## 6. 一个小模型的参数账本

设 $D=8,d_e=4,N_r=8,K=2,N_s=1$。
单专家参数量：

$$
P_e=3\times8\times4=96.
$$

| 项目 | 计算 | 参数数 |
|---|---|---:|
| routed 专家池 | $8\times96$ | 768 |
| shared 专家 | $1\times96$ | 96 |
| 本 token 激活 routed | $2\times96$ | 192 |
| 本 token 激活全部专家 | $(2+1)\times96$ | 288 |
| router，无 bias | $8\times8$ | 64 |

总专家参数为864，每 token 使用288个专家矩阵参数。
再加router后，总量与活跃量的比例已经改变。

这只是参数参与计算的计数。
一次矩阵乘法的 FLOPs、权重读取量和实际延迟还需根据 batch 与复用计算。

## 7. Gate 先产生亲和度

以 V3 的 sigmoid gate 为例：

$$
s_{t,i}=\sigma(x_t^\top e_i).
$$

$s_{t,i}$ 表示 token 与专家的亲和度。
训练时要同时处理两个目标：

1. 选择有助于任务的专家。
2. 避免很多 token 都挤到少数专家。

这两个目标有关联，但不是同一个变量。

## 8. 校正偏置用于选人，不直接用于发工资

V3 auxiliary-loss-free balancing 的关键写法是：

$$
S_t=\operatorname{TopK}_i(s_{t,i}+b_i).
$$

选择完集合后，用原始分数计算输出权重：

$$
g_{t,i}=\alpha\frac{s_{t,i}}{\sum_{j\in S_t}s_{t,j}},\quad i\in S_t.
$$

这里 $\alpha$ 是 routing scale。
偏置 $b_i$ 改变被选中的机会，而不直接进入加权值的分子。

`auxiliary-loss-free` 指这一负载校正机制不依赖向主任务损失添加传统的专家均衡辅助项。
V3 仍披露了很小的序列级辅助均衡项，不能把模型整体说成完全没有任何辅助损失。

## 9. 手算一次路由

四个专家的原始分数为：

$$
s=[0.8,0.6,0.3,0.2].
$$

校正偏置为：

$$
b=[-0.5,0,0.4,0].
$$

调整后的选人分数：

$$
s+b=[0.3,0.6,0.7,0.2].
$$

选择 top-2，得到专家3和专家2（这里用从1开始的编号）。
注意，原始分数最高的专家1没有被选中。

取 $\alpha=1$，专家2与3的权重是：

$$
g_2=0.6/(0.6+0.3)=2/3,
\quad g_3=1/3.
$$

不能写成 $0.6/(0.6+0.7)$ 与 $0.7/(0.6+0.7)$。
后者错误地把负载调节偏置当成了语义混合权重。

## 10. 把专家输出也算完

设：

$$
E_2(x)=[3,0],\quad E_3(x)=[0,6],
\quad E_s(x)=[1,1].
$$

路由部分：

$$
(2/3)[3,0]+(1/3)[0,6]=[2,2].
$$

加入共享专家：

$$
y=[1,1]+[2,2]=[3,3].
$$

若 $\alpha=1.5$，路由部分变为 $[3,3]$，最终为 $[4,4]$。
共享专家并没有因此乘1.5。

## 11. 负载均衡反馈长什么样

假设一批有100个 token，每 token 选择2个专家，共200次分配。
四个专家均匀负载目标为50。
观察到实际负载：

$$
[80,60,40,20].
$$

直觉上应降低前两个专家的偏置，提高后两个的偏置。
一种示意更新是：

$$
b_i\leftarrow b_i+\gamma\operatorname{sign}(\bar n-n_i).
$$

这是为了说明反馈方向。
实际训练的更新粒度、统计范围、步长和通信实现必须看对应版本，不能由推理 `Gate` 代码推断完整训练算法。

推理源码里保留训练得到的 bias，不等于服务端每步都按同一训练规则更新 bias。

## 12. 从路由结果到 GPU 工作量

取三个 token，分别选择：

| token | 专家集合 | 原 token 行 |
|---|---|---:|
| A | 0、2 | 0 |
| B | 2、3 | 1 |
| C | 0、3 | 2 |

重排后：

| expert | token batch |
|---|---|
| 0 | A、C |
| 1 | 空 |
| 2 | A、B |
| 3 | B、C |

每个专家看到自己的小批次，计算完成后再按原 token 行和 gate 权重汇总。
一个 token 激活多个专家，意味着它的表示可能被复制到多个计算位置。

如果专家位于不同 GPU，dispatch 与 combine 通信进入关键路径。
DeepEP、EPLB 和计算通信融合正是在这一层发挥作用。

## 13. 专家细不一定就更快

专家越多，每个专家分到的 token 越少。
较小 GEMM 可能更难利用 Tensor Core。

跨设备选择数增加，dispatch 的目标数和元数据也可能增加。
因此细粒度专家的模型质量收益，需要 grouped GEMM、路由重排和通信实现配合。

理论激活参数相同，不代表硬件时延相同。
这也是架构论文与系统论文必须联合阅读的原因。

## 14. Device-limited routing 与负载均衡不是一回事

限制 token 最多访问几个节点或专家组，主要控制通信范围。
均衡专家收到的 token 数，主要控制设备工作量。

可以先选组，再在选中的组里选专家。
但分组分数的定义可能随版本改变。
V3固定源码在存在校正bias时，用组内最高的两个调整后分数之和作组分数。

这不是任意MoE都采用的通用定义。
同时也不能把逻辑专家组直接等同于实际机器，部署映射可能变化。

## 15. V2、V3、V4、V4.1如何对照

| 版本 | routed / active / shared | 额外关注点 |
|---|---|---|
| V2 主模型 | 160 / 6 / 2 | 细粒度专家与通信约束 |
| V3 主模型 | 256 / 8 / 1 | sigmoid、校正bias、负载均衡 |
| V4-Flash | 256 / 6 / 1 | sqrt-softplus；前3层token-id hash routing |
| V4.1-Flash | 384 / 6 / 1 | 图像/文本分别维护校正bias |

这些是对应官方模型配置的读取结果，不是整个家族所有大小模型的共同常量。
V4-Pro 的专家数量和维度必须另查其配置。

V4 的 hash routing 以 token id 查专家选择表，减轻早期路由的不稳定。
V4.1 参考实现中没有沿用该 `n_hash_layers` 参数，不能默认继承所有 V4 细节。

## 16. V4.1 的模态分别均衡

假设文本token的专家负载为 $[90,10]$，图像token为 $[10,90]$。
相加为 $[100,100]$，整体看似完全均衡。
但两个模态分别有严重偏好。

V4.1 为文本和图像维护各自的校正bias。
每个token使用所属模态的bias选专家，再用原始score加权。

这样能观察并调节模态内部负载。
它不是给图片和文字各建一套完全隔离的专家池。

## 17. 代码阅读路线

先读 `ModelArgs`，再读实际大模型 `config.json`。
然后沿以下顺序跟踪一个token：

```text
输入 hidden
  -> Gate 计算原始 scores
  -> 保存 original_scores
  -> 添加 correction bias
  -> 可选的 group 筛选
  -> top-k 选 expert ids
  -> 从 original_scores gather weights
  -> 归一化与 routing scale
  -> token 按 expert 重排
  -> Expert / grouped GEMM
  -> 加权 combine
  -> 加 shared expert
```

[V3固定源码](https://github.com/deepseek-ai/DeepSeek-V3/blob/9b4e9788e4a3a731f7567338ed15d3ec549ce03b/inference/model.py) 使用易读的专家循环与分布式归约。
这一参考实现不能代表生产DeepEP全部通信路径。

## 18. 一个可验证的路由小实验

```python
import numpy as np

score = np.array([.8, .6, .3, .2])
bias = np.array([-.5, 0., .4, 0.])
chosen = np.argsort(score + bias)[-2:]
weight = score[chosen]
weight /= weight.sum()
experts = np.array([[9., 9.], [3., 0.], [0., 6.], [8., 8.]])
shared = np.array([1., 1.])
y = shared + (weight[:, None] * experts[chosen]).sum(0)
np.testing.assert_allclose(y, [3., 3.])
print(chosen, weight, y)
```

把输出权重误改为 `score + bias` 再运行，会看到不同结果。
这是一个路由语义检查，未模拟跨节点通信。

## 19. 自测与答案

**问题1：总参数很大但激活参数很少，权重就都不用放内存吗？**

答案：没有被当前token激活的专家可能被下一个token或别的请求激活；需要存储、分片或卸载策略。

**问题2：共享专家是否减少路由专家数量？**

答案：设计时可以重新分配参数预算，但一旦配置确定，两者分别计数。

**问题3：top-k的bias为什么不能直接进输出权重？**

答案：它承担负载调节角色；原始亲和度保留任务混合语义。

**问题4：细分专家为什么保持理论FFN计算却可能变慢？**

答案：小矩阵效率、token重排、更多目标通信与同步开销都可能恶化。

**问题5：负载均衡能否保证语义专家专业化？**

答案：不能。均衡是分配统计，专业化是表征与功能性质。

**问题6：V4.1的文本/图像bias是否代表两套MoE模型？**

答案：不是。专家池可共享，只是选择校正按模态区分。

**问题7：为什么推理源码不足以复现负载均衡训练？**

答案：还缺训练统计、更新周期、全局聚合、调度以及训练checkpoint状态。
