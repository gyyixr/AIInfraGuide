## 1. “复现成功”必须先指定对象

复现可以指公式、一个函数、一个kernel、某个模型输出、论文指标或完整服务。它们需要不同证据。

| 层次 | 一个成功例子 | 不能自动推出 |
|---|---|---|
| 数学关系 | MLA两条计算路径输出/梯度一致 | 官方GPU kernel正确 |
| 接口/布局 | packed KV解析与索引符合契约 | 模型质量复现 |
| 单算子 | 固定shape下与oracle相符 | 任意shape、dtype和平台都相符 |
| 模型级 | 固定checkpoint上PPL/任务结果达标 | 线上SLO与故障恢复 |
| 系统级 | 指定负载下吞吐、尾延迟与恢复达标 | 其他集群或业务同样成立 |

本项目的已执行实验集中在数学、状态、CPU规划和小型普通PyTorch GPU计算。下面给出向更高层推进的方法，不把尚未执行的项目写成已完成。

## 2. 实验合同：先冻结六类输入

一个可审查的合同可以写为：

```yaml
# 教学记录格式，不是DeepInfer/DeepEP的启动配置
source:
  repository_commit: "固定SHA"
  submodules: "逐项固定"
model:
  weights_revision: "固定revision"
  tokenizer_revision: "固定revision"
  chat_template: "指纹或版本"
workload:
  request_ids: "固定集合"
  input_output_lengths: "明确分布"
  sampling: "temperature/top-p/top-k/seed"
  cache_policy: "命中、replay与格式"
execution:
  hardware: "型号与数量"
  parallel_groups: "逻辑组和物理映射"
  precision: "参数/计算/KV/scale"
measurement:
  warmup: "明确次数"
  boundary: "CPU/GPU事件或端到端"
acceptance:
  numerics: "误差与失败条件"
  quality: "独立任务与指标"
  performance: "延迟/吞吐/SLO"
```

缺少这些字段时，一次速度差异可能来自模型、输入或缓存，而不是声称的优化机制。

## 3. 硬件选择的第一张表

| 环境 | 合理的起点 | 需要额外条件的方向 |
|---|---|---|
| 普通CPU | 标准库oracle、官方EPLB规划、协议与数据状态 | GPU/NPU kernel不可据此验证 |
| RTX3090/SM86 | 普通PyTorch合成模型、能装下的小模型 | 当前SM90/SM100专用DeepSeek kernel不适配 |
| Hopper/SM90 | 相容版本的DeepGEMM/DeepEP、旧FlashMLA部分路径 | 当前FlashMLA已改变旧架构范围 |
| SM100/SM103 | 按各库矩阵选择当前kernel | 库级支持不等于完整引擎所有组合 |
| Ascend950 | 相应Ascend实现和匹配CANN/torch_npu | 未实现的buffer模式、Graph和公开驱动条件 |

每行都还需要内存、工具链与依赖检查。硬件名称只通过第一道门，不是完整复现许可。

## 4. 先算容量，别只看激活参数

MoE的激活参数控制一部分每token计算量，总参数决定需要存储或访问的权重。Engram等条件记忆又有自己的表容量与放置策略。

假设某组件有196B个一字节权重，仅原始数据就是约196 GB，尚未计scale、索引、元数据与其他层。这不能被“每token只访问少量条目”变成几GB的完整驻留需求。

如果允许远程或CPU存储，还要分析访问量与重叠窗口：

$$
T_{memory}\gtrsim\frac{bytes_{accessed}}{B_{effective}}+T_{fixed}.
$$

省GPU显存可能把瓶颈转移到主机、网络和随机访问，而不意味着总成本消失。

## 5. 项目 P0：把公式变成可证伪的 oracle

**目标**：在不依赖大模型的环境中确认数学和状态契约。

输入是确定的小矩阵、路由表、概率向量、页表与版本状态。输出必须包含可手算数值及错误实现的反例。

验收包括：

- 完整反量化与分块scale计算一致。
- 原始/展开/合并token顺序正确。
- TopK不同块顺序结果一致。
- prefix概率、拒绝残差和错误选择偏差可复算。
- 对齐gap与无效容量不会进入有效数据。

对应本仓库14项检查。这一层已执行，但不包含真实分布式资源竞争。

## 6. 项目 P1：官方 EPLB 规划与极端负载

固定 `eplb.py`，先复现第6.3节结果，再构造：

| 负载 | 要观察什么 |
|---|---|
| 完全均匀 | 是否无意义增加不均衡 |
| 单专家热点 | 副本数与每GPU槽位约束 |
| 多层不同热点 | 层间映射是否独立解释 |
| 组/节点不整除 | 是否进入正确全局策略 |
| 热点迁移 | 旧统计导致的规划滞后 |

容量、映射互逆和负载守恒是第一步。性能项目还需把实际GEMM、路由和权重搬迁纳入，不把规划输出的均匀程度直接当GPU加速比。

## 7. 项目 P2：MLA数值与梯度

从本仓库 `mla_torch.py` 开始，固定输入，先比较float64完整投影与吸收路径。

再分别改变一个条件：latent维度、query长度、head数、位置、mask、dtype。每次都记录输出与梯度误差，不同时改所有条件。

**负对照**可以包括：漏掉RoPE分支、转置错轴、把不同head混到一起、把价值投影提前或延后时误改矩阵方向。

RTX3090上的本次实验只验证普通PyTorch数学链路，不能用其耗时比较FlashMLA或官方V4.1引擎。

## 8. 项目 P3：目标硬件上的单 kernel

在相容硬件上，按固定官方测试提取最小case，而不是先跑默认最大形状。

| kernel | 独立oracle应覆盖 |
|---|---|
| FlashMLA | sparse集合、物理索引、空行、sink、KV格式 |
| DeepGEMM | shape、scale粒度、layout、padding、累加语义 |
| DeepSelect | TopK集合、排序、变长、tie与异常值 |
| DeepEP | dispatch/combine、gate、梯度与异步事件 |
| TileKernels | 对应PyTorch reference、前向/反向与支持后端 |

先验证接口合法性与结果，再测时间。错误输出即使更快也不能进入性能对照。

### 8.1 误差不能只有一个全局相对值

建议同时保留最大绝对误差、均方误差、分位数和与输入尺度有关的相对误差。近零参考值需要特殊处理，不能让分母太小产生没有意义的百分比。

对量化还需看饱和比例、scale分布、长尾值和误差随层数/步数增长；一次矩阵通过不代表长上下文模型稳定。

## 9. 项目 P4：DeepInfer离线模型回归

这一步需要符合官方公开核心的硬件、足够权重/KV/主机内存和固定依赖。

建议按以下阶段收集证据：

1. 配置、tokenizer与权重revision核对。
2. 固定短prompt的token ID、单步logits/PPL。
3. 多步生成和EOS/stop处理。
4. 图/非图、ZOS开/关的明确对照。
5. 多模态输入、结构化输出及失败清理。
6. 长prompt与bounded replay/cache-hit分桶。
7. DP/CP/EP/Engram组与vendor依赖检查。

官方短/长PPL基线属于指定样本与平台，不应在看到误差后直接覆盖旧golden。先解释数值变化，确认预期后再更新。

### 9.1 为什么不只看最终文本

两个实现可能因采样不同生成不同但合理的回答，也可能因错误而碰巧生成相同短句。固定token回放的logits/logprob与状态统计，可以把数值问题和随机性分开。

对近似replay，比较对象应明确为相同replay策略，或将它作为独立近似机制做质量实验。

## 10. 项目 P5：DSpark分布与吞吐双验收

算法验收与系统验收不能混在一起：

| 算法侧 | 系统侧 |
|---|---|
| proposal与target条件一致 | draft/verify/调度各阶段时间 |
| 接受概率与residual正确 | Graph桶与验证容量 |
| 非预见性/历史容量信息边界 | 不同并发和到达模式 |
| EOS、grammar与回退一致 | per-user速度和总goodput |
| 统计分布或固定模式回归 | 缓存、重排、资源与尾延迟 |

一个算法可以数学正确却没有速度收益；一个测起来更快的实现也可能悄悄改变输出分布。两边都需要通过。

### 10.1 两动作统计检验的量级

若目标动作A概率0.6，独立采样N=100000次，其频率标准误量级：

$$
\sqrt{0.6\times0.4/100000}\approx0.00155.
$$

错误选择规则给出0.8，与0.6的差远大于该量级，容易识别。但统计检验只能排除已测试条件下的大偏差，不代替正确性证明。

## 11. 项目 P6：缓存/PD控制面的补齐

公开DeepInfer预留的外部缓存与PD集成钩子，需要上层协议。可先做小型状态模型，不急于接真实大模型。

一条传输记录至少应说明：

```text
request/transfer ID
model/tokenizer/adapter revision
RoPE位置与KV量化格式
源/目标shard layout
有效token范围与checksum
接收、确认、取消、释放状态
资源引用或lease
```

这些是自建协议的教学字段，不是声称存在某个统一官方API。

需要演练：重复确认、迟到消息、部分接收、超时、取消后完成、源端重启、目标端内存不足。任何一条都可能造成重复计数、错误命中或提前释放。

## 12. 项目 P7：3FS/smallpond数据与恢复

先从小的不可变输入版本和专用实验目录开始，固定schema、分区与输出检查。

对数据处理验证：行数/字节数、key分布、聚合等价、重复与丢失、任务重试和manifest指向。

对存储验证：严格/relaxed读取、活跃文件长度、fsync/close、复制状态、版本不一致和恢复中的读写。

将它接到训练checkpoint时，还需验证模型/optimizer/RNG/数据进度的一致提交。文件系统能读到字节，不自动证明训练可精确续跑。

## 13. 冷启动、热缓存与稳态要分开

JIT编译、权重加载、KV预热、图捕获和请求冷启动可以占据完全不同的时间尺度。

| 状态 | 可能仍在发生的工作 |
|---|---|
| 进程冷启动 | 库加载、设备上下文、模型初始化 |
| kernel冷启动 | 编译、磁盘发布、设备模块加载 |
| 模型热但prefix冷 | 完整prefill与新KV分配 |
| prefix热 | 查找、恢复或回放及剩余后缀 |
| 长时间稳态 | 连续batch、迁移、GC、背景负载 |

一个优化若仅改善其中一种状态，应按状态报告。不能把热prefix结果与另一个冷prefix基线直接归因于kernel性能。

## 14. 容量不等于吞吐，吞吐不等于 Goodput

能装入模型只是容量可行；每秒生成很多token也可能伴随不可接受的排队与尾延迟。

对交互服务，至少考虑：

$$
Goodput=\frac{\text{满足质量与SLO的有效完成请求或token}}{\text{墙钟时间}}.
$$

SLO必须给具体阈值和分位数，不能只写“低延迟”。到达模型、输入长度、输出长度、失败和取消也需要记录。

成本比较则需固定质量与服务预算；报告团队历史成本不能当成今天相同模型在任意机器上的报价。

## 15. 故障与回退条件

| 失败 | 首先保留 | 可能回退方向 |
|---|---|---|
| 数值不一致 | 最小输入、dtype、layout、版本 | 高精度oracle、非融合路径 |
| 异步才失败 | stream/event和buffer时间线 | 同步诊断模式，定位后恢复优化 |
| Graph才失败 | 地址、容量、padding桶 | eager路径与固定shape |
| 多rank挂起 | 所有rank首错与collective顺序 | 最小通信例与同一组配置 |
| KV命中后质量变差 | 命中key、位置、replay模式 | 禁用相应近似/缓存路径对照 |
| 数据恢复错位 | manifest、数据游标、随机状态 | 从一致提交点重放 |

回退是为了隔离因果关系，不是永久跳过正确性要求。修复之后应重新跑最小失败case，再做相关整链路验证。

## 16. 一份合格的实验结论

不够具体的结论是“开了某库快一倍”。可复查的结论应包含：

> 在固定模型与权重、指定硬件/版本、长度与到达分布下，改变一个机制；独立数值和质量检查达到给定条件；指定计时范围内某指标由A变为B，代价是C；其余路径尚未验证。

这个结构同样适用于失败实验。若新方法没有收益，记录是哪一阶段抵消了理论节省，也是一份有效工程结果。

## 17. 本项目当前验收范围

已保留：标准库14项数学/状态检查、固定官方EPLB的CPU规划结果、CPU与RTX3090上的合成MLA前向/反向结果，以及各章独立算例和固定源码核对。

没有保留为已完成结果的包括：全量V4.1权重推理、官方SM100/NPU kernel吞吐、真实RDMA/3FS集群、全规模DSpark训练及生产SLO复现。

这不是删去相关技术内容：前面章节已经详解其机制、接口与验收方法；运行证据需要匹配硬件和工作负载后另行建立。

## 18. 自测与参考答案

**1. 库安装成功，为什么还不能宣称支持某模型？** 还需核对模型结构、权重转换、KV格式、kernel、并行和运行时组合。

**2. 为什么总参数与激活参数要分开算？** 前者影响存储与加载，后者只描述部分每token计算；远程/CPU放置也有带宽代价。

**3. 为什么不能无理由刷新PPL golden？** 可能把错误固化成新基线，必须先说明差异来源并通过独立检查。

**4. 只提高accepted length是否说明DSpark更快？** 不说明，验证容量、draft和调度成本可能增加，需看整体负载曲线。

**5. 文件rename成功是否等于训练checkpoint事务完成？** 不等于，还需数据持久化、全部shard、manifest、optimizer/RNG/游标一致性。

**6. 同seed为何可能不逐token相同？** batch、后端、图、近似replay、随机数分配或采样语义可能不同，应按实际确定性保证检查。

**7. 什么情况下可以把结果推广到别的硬件？** 需要新的版本/架构支持证据与实测，理论模型只能给待验证的预测。
