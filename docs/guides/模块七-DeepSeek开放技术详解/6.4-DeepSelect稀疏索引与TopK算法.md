## 1. 为什么稀疏 Attention 还需要一个专用 TopK

把完整 Attention 改成只看少量 token，通常要先选择这些 token。若选择阶段本身昂贵，后面的稀疏算子即使很快，整个系统也未必获益。

DeepSelect 面向两个明确场景：

- 稀疏注意力索引器从大量上下文候选中选位置。
- 采样器从大词表中选少量候选 token。

它不计算 Attention，也不产生索引打分；输入分数来自模型或其他算子。它也不是所有输入规模、dtype 和 k 下通用最优的排序库。

本节基于官方固定快照 `bfa4507d935f17ebfc3d0f00ff7d3c9a4d0e5c18`，核对日期 2026-11-07。原理推导依据同快照的官方 deep-dive，CPU 例子使用独立参考实现。

## 2. TopK 与完整排序有什么不同

给定一行 $N$ 个数，TopK 只需找出最大的 $k$ 个元素及其索引。若不要求结果按值排序，就不必为其余 $N-k$ 个元素建立全序。

$$
\mathcal S=\operatorname{argTopK}_{j\in[0,N)}x_j.
$$

当 $N$ 很大、$k\ll N$ 时，避免在全体数据上反复排序和搬运可以节省大量工作。但一般精确 TopK 仍需检查全部输入，不能跳过未见元素就保证没有漏掉最大值。

### 2.1 三种不同的结果要求

| 要求 | 输出示例 | 额外工作 |
|---|---|---|
| 只需 TopK 集合 | 合法集合，顺序无关 | 最少的排序约束 |
| 按值降序 | 最大值先输出 | 对选中元素再排序 |
| 按原索引升序 | 原序列位置递增 | 对选中索引排序 |

后两者不能混淆。稀疏 attention 可能更关心位置顺序和后端访存，采样算法则可能需要按概率大小排序；应由实际消费者决定。

## 3. Scan—Filter—Compact 的核心思想

维护一个候选集合 $C$ 和阈值 $T$。当已经至少保留了 k 个元素，$T$ 表示当前候选中第 k 大的值。

每次读取一个大小至多为 $B$ 的连续输入块：

1. **Scan**：读取该块全部元素。
2. **Filter**：只把可能进入当前 TopK 的元素加入候选。
3. **Compact**：当候选达到一定容量时，将它压回 k 个，并更新阈值。

阈值只能增大：后续看到更多输入，已经确认的第 k 大值不会变小。一个比当前阈值还小的元素，未来也不可能重新进入全局 TopK。

这个不变量让后续块的候选比例逐步降低，但不会免去读取这些块的成本。

## 4. 一次完整手算

输入长度 12，分为三个连续块，取 $k=3,B=4$。候选达到 `k+B₂=6` 时压缩，$B_2=3$：

```text
块0: [3,1,8,2]    原索引0..3
块1: [7,5,6,4]    原索引4..7
块2: [9,0,12,10]  原索引8..11
```

选择处理顺序 `[块1,块0,块2]`。

### 4.1 第一块

初始没有 k 个已确认候选，先读入块 1 的四个数：`[7,5,6,4]`。候选数 4，未达到触发阈值 6，尚不做压缩。

### 4.2 第二块

读入块 0 后，候选为 `[7,5,6,4,3,1,8,2]`，共八个元素。压缩后保留 `[8,7,6]`，阈值更新为 6。

此时已经扫描的八个元素中，任何小于 6 的值都不可能在最终前三中胜过这三个候选。

### 4.3 第三块

块 2 的 `[9,0,12,10]` 只有 9、12、10 高于当前阈值。加入后候选为 `[8,7,6,9,12,10]`，再次压缩，得到 `[12,10,9]`，阈值为 9。

最终按值降序的索引是 `[10,11,8]`。如果要求索引升序，输出索引变成 `[8,10,11]`，对应值应一起重排为 `[9,12,10]`。

### 4.4 块顺序影响工作量，但不改变正确集合

若先处理块 2 再处理块 0，第一次压缩就能建立阈值 9；之后块 1 的数都被过滤，压缩工作量更少。

这个例子说明好的早期阈值很重要。算法用与输入独立的随机块排列，降低总是按不利数值顺序扫描导致的性能退化。

随机性不是“用近似 TopK 换速度”。在数学前提满足时，无论块顺序如何，都应得到同一个 TopK 值集合；重复值的索引顺序则要看 API 对 tie 的约定。

## 5. 为什么额外候选空间可以很小

若压缩触发阈值是 $k+B_2$，每次最多新增 B 个元素，则候选峰值受以下量级约束：

$$
|C|\lesssim k+B_2+B.
$$

定义 $L=k+B+B_2$。除了块排列，候选空间为 $O(L)$，可尽量放在 shared memory 等片上存储里，而不是反复操作一个长度 N 的全局缓冲。

用 `k=512,B=B₂=1024` 的例子，候选容量量级约为 2560 个元素。具体占用还要乘 value、index、辅助 radix 状态的字节数，并计入其他 shared memory 需求。

不能只根据“候选不到 3000 个”就断言共享内存一定足够；GPU 资源约束还包括线程块、寄存器、对齐和并发 block 数。

## 6. 随机块顺序下的期望工作量

设共有 $m=\lceil N/B\rceil$ 个块，以与输入独立的均匀随机排列处理。为了简化证明，先假设元素互不相同。

令第 i 个已处理块新增候选数为 $A_i$。开始处理该块时，候选尚未达到再次压缩的阈值；能新加入的元素必定位于前 i 个块的前 L 大范围内。

在给定前 i 个块的集合时，当前块是其中均匀选择的一个，因此：

$$
\mathbb E[A_i]\le\frac Li.
$$

对全部块求和：

$$
\mathbb E[A]\le L\sum_{i=1}^{m}\frac1i=LH_m.
$$

其中 $H_m$ 为调和数，约为 $\log m$ 加一个常数量级。

### 6.1 将候选数换成压缩工作量

每次内部压缩至少移除 $B_2$ 个候选，因此压缩次数 R 满足 $RB_2\le A$。除每次新加入的元素外，保留的 k 个元素会在后续压缩再次参与：

$$
W=A+kR\le\left(1+\frac{k}{B_2}\right)A.
$$

于是：

$$
\mathbb E[W]\le\left(1+\frac{k}{B_2}\right)LH_m.
$$

当 $B,B_2=\Theta(k)$，额外 TopK 压缩工作量可表达为 $O(k\log(N/k))$。

**这不是总算法只需亚线性访问输入。** 读取 N 个元素的 $O(N)$ 扫描仍然存在；上述界描述额外候选选择工作的期望量。

## 7. 可运行的 CPU 参考算法

下面用 Python 排序替代 GPU radix-select，只验证阈值逻辑和结果，不模拟性能。为避免隐含 NaN/无穷语义，显式要求有限数：

```python
import math

def scan_filter_topk(values, k, block_size, extra, order):
    assert 1 <= k <= len(values)
    assert all(math.isfinite(x) for x in values)
    blocks = [list(enumerate(values))[i:i+block_size]
              for i in range(0, len(values), block_size)]
    assert sorted(order) == list(range(len(blocks)))
    candidate = []
    threshold = -math.inf
    work = 0
    for block_id in order:
        for index, value in blocks[block_id]:
            if value > threshold:
                candidate.append((value, index))
        if len(candidate) >= k + extra:
            work += len(candidate)
            candidate = sorted(candidate, reverse=True)[:k]
            threshold = candidate[-1][0]
    work += len(candidate)
    result = sorted(candidate, reverse=True)[:k]
    return result, work

x = [3,1,8,2,7,5,6,4,9,0,12,10]
a, work_a = scan_filter_topk(x, 3, 4, 3, [1,0,2])
b, work_b = scan_filter_topk(x, 3, 4, 3, [2,0,1])
assert a == b == [(12,10),(10,11),(9,8)]
assert work_a == 17 and work_b == 11
```

这里 result 的 tie 行为由 Python tuple 排序决定，不能当作官方 CUDA/Ascend kernel 的稳定排序保证。

## 8. GPU 实现为什么还需要专门优化

算法缩小了候选集合，但 Filter 阶段仍需要把不同线程选中的元素紧凑地写到共同缓冲区。

朴素方法可能扫描两遍：第一遍计数决定偏移，第二遍重新判断并写入。官方实现的思路包括在第一次判断时保留 bit mask，再枚举置位位置，减少重复判断和 CUDA Core 工作。

一个 32-bit mask 可以表示 32 个候选是否超过阈值：

```python
mask = 0b10110
positions = []
while mask:
    low = mask & -mask
    positions.append(low.bit_length() - 1)
    mask &= mask - 1
assert positions == [1, 2, 4]
```

实际 GPU 还需要 warp/block 内的计数与前缀定位、shared memory 写入和同步。不能仅把 `__ffs` 换成循环，就得到完整 DeepSelect 实现。

BF16 成对比较、字节排列和整型指令可以减少常数，但依赖具体架构和数据布局；其意义是更高效地搬运与筛选，而非提高浮点乘加率。

## 9. 接口约束与排序选项

当前 README 聚焦 $k\le4096$，并主要针对 DSA 常见的较小 k 优化。大 k 或非常不同的 shape 必须重新测量。

| 场景 | 常见输入 | 本快照边界 |
|---|---|---|
| 索引器 | BF16，多种 batch/上下文长度 | CUDA 与 Ascend 路径 |
| 采样器 | FP32，约 128K 词表 | 当前 FP32 输入只在 CUDA 路径支持 |
| 按值排序 | `sorted=True` | 需核查 dtype/backend；README 标明 CUDA FP32 变体支持 |
| 按索引排序 | `sorted_index=True` | 与按值排序不同，会增加工作 |
| 只需位置 | `return_value=False` | 可以省去不需要的 value 输出 |

输入最后一维要求连续，row stride 还必须满足接口查询返回的字节对齐要求。输出也可能为了对齐而不是普通 contiguous tensor；下游不能默认 `.view()` 总是合法。

## 10. 变长行、空余项和异常值

`end` 给每行一个不包含终点的有效范围。行长度小于 k 时，接口用配置的 OOB fill value/index 补齐。

例如逻辑长度 3、k=4，第四个槽位不是被模型选中的真实 token；必须保持 fill 语义传给下游，不能将默认占位误当成词表第 0 项。

### 10.1 NaN 行为不是普通异常返回

该快照默认在检测到 NaN 时触发 kernel `trap()`。CUDA 中长度不超过 k 的短行有不执行 NaN 检查的特殊路径，README 已注明。

因此“打开默认 NaN 检查”不能替代上游输入验证，也不能把所有失败都当作可以捕获后继续复用同一设备状态的普通 Python 错误。教学实验不需要故意执行 trap，数值检测可以先在独立小数据上完成。

## 11. 如何比较性能

TopK 主要是读取、比较和选择，不适合用 TFLOPS 表达其性能。可用有效输入带宽：

$$
B_{eff}=\frac{\text{batch}\times N\times b_{element}}{T}.
$$

但要注明是否包含输出写回、padding、随机块顺序准备、后处理排序和 stream 同步。

对照 `torch.topk` 时必须统一：

- dtype、shape、k 和有效长度。
- 返回值是否需要排序、是否需要 values。
- 重复值、NaN、无效范围与 fill 规则。
- warm-up、图捕获、计时方式及设备。

官方“相对某基线的加速范围”只对应其 benchmark，不能套用到所有 k 和 GPU。当前项目没有执行 DeepSelect GPU 性能测试。

## 12. 接到 DSA 时的五个不变量

1. 分数列的含义必须与输出索引含义一致：逻辑 token、压缩块、候选集局部索引不可混用。
2. 若在候选子集内 TopK，输出位置还需映射回全局缓存地址。
3. 因果和 padding 屏蔽必须在选择或消费者中保持一致。
4. 输出按索引排序不能丢失与 value、权重或其他 metadata 的对应关系。
5. 量化分数会改变排序边界，特别是相近值；kernel exact TopK 不代表模型相对于高精度原始分数完全相同。

V4.1 分层索引和 CSA2 的候选定义见第 2.9 节。DeepSelect 只解决给定分数上的选择，不能证明索引器没有遗漏对任务重要的上下文。

## 13. 自测与参考答案

**1. 阈值为何只升不降？** 每次保留已扫描数据中的 k 个最大值，再加入新数据不会使第 k 大值变小。

**2. 为什么不能宣称总复杂度是 $O(k\log N)$？** 全部 N 个输入仍需扫描；该式描述额外候选选择工作，不包括必要读取。

**3. 随机块顺序会让 TopK 近似吗？** 对有限、明确比较语义的输入，它改变中间工作量，不改变正确值集合。tie 的索引约定另行处理。

**4. `sorted_index=True` 是否保证最大值在第一位？** 不是，它按输入位置排序；按值降序是另一种要求。

**5. 输出 shape 相同，为何下游 kernel 仍可能不接受？** stride、对齐、dtype、OOB fill 和索引空间都属于接口契约。

**6. FlashMLA 看到一个合法整数索引，是否说明该索引正确？** 不一定，它可能来自错误的候选集坐标或陈旧缓存页映射，必须核对语义地址。

**7. 只看微基准提速是否值得接入？** 还需测整个索引器和 Attention 关键路径；转换布局、额外排序或同步可能抵消收益。
