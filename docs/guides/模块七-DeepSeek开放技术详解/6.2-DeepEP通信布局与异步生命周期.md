## 1. 先选版本，再解释通信

许多教程介绍的 DeepEP 是 2025 年的 V1：分别讨论吞吐路径、低延迟路径和 NVSHMEM。但本节核对的官方主干已经是 V2.5：

```text
deepseek-ai/DeepEP
f6aa38fe06cd4a0489e7730365d4e0114970a2f3
核对日期：2026-11-07
```

该版本使用 NCCL Gin 后端与 DeepJIT，将 EP、Engram、PP 和 bucket 通信拆成不同 buffer 类；README 明确移除 V1 API、旧文档和 NVSHMEM 依赖。

因此，“DeepEP 使用 NVSHMEM”“低延迟 EP 不占 SM”等说法都必须附版本与操作路径。当前快照明确说明 EP dispatch/combine 使用 GPU SM，不支持零 SM 的 RDMA EP。

本文同时解释跨版本仍成立的数学语义，以及只属于本快照的 API 和内存契约。它不是一份在本机运行过的多 GPU 性能报告。

## 2. MoE 层为什么需要两次数据重排

Attention 后的 token 通常按请求或序列顺序存放；专家 GEMM 希望按 expert 收到连续输入；下一层又需要恢复原 token 顺序。

```text
原始 token 顺序
  → router 选逻辑专家与权重
  → dispatch 到专家所在设备，并展开为专家行
  → 专家计算
  → 应用路由权重
  → combine 求和并回到原 token
```

dispatch 与 combine 解决的是**数据归属和布局变化**，不是让模型重新选择更好的专家。路由决策由模型给出；底层可将同一逻辑专家映射到等价物理副本，但不能随意换成另一个专家函数。

## 3. 两 token、三专家的完整数例

输入只有一个标量维度，以便每一步都能手算：

| token | 输入 $x$ | 路由及权重 |
|---|---:|---|
| $t_0$ | 2 | $e_0:0.25$，$e_2:0.75$ |
| $t_1$ | 3 | $e_1:0.6$，$e_2:0.4$ |

定义专家函数：$f_0(x)=x$，$f_1(x)=2x$，$f_2(x)=3x$。rank 0 放专家 0、1，rank 1 放专家 2。

### 3.1 Dispatch 后的专家行

| 目标 rank | 专家 | 源 token | 输入 | 对应 gate |
|---|---|---|---:|---:|
| 0 | 0 | 0 | 2 | 0.25 |
| 0 | 1 | 1 | 3 | 0.6 |
| 1 | 2 | 0 | 2 | 0.75 |
| 1 | 2 | 1 | 3 | 0.4 |

两个 token 变成四个专家任务。路由元数据必须足以把每个输出送回正确的 token；仅保留一个拼接后的输入矩阵不够。

### 3.2 计算与 Combine

先算专家结果并乘 gate：

$$
y_0=0.25\times2+0.75\times6=5,
$$

$$
y_1=0.6\times6+0.4\times9=7.2.
$$

当前 expanded 示例的契约是：专家计算侧应用接收的 gate，combine 对给定的专家输出求和。不能既在专家侧乘一次，又在 combine 前重复乘一次。

对于 $t_0$：

- 完全不乘 gate：$2+6=8$。
- 正确乘一次：$0.25\times2+0.75\times6=5$。
- 乘两次：$0.25^2\times2+0.75^2\times6=3.5$。

三个结果都有限、都可能让训练继续，但只有中间一个对应模型定义。

### 3.3 反向方向为什么互换

保持 gate 不变，输入梯度是专家路径贡献的和：

$$
\frac{\partial y_0}{\partial x_0}=0.25+3\times0.75=2.5,
\qquad
\frac{\partial y_1}{\partial x_1}=2\times0.6+3\times0.4=2.4.
$$

前向 dispatch 把一个 token 分发给多个专家，反向自然要把各专家的输入梯度合回源 token；前向 combine 把多份贡献求和，反向则把同一个输出梯度分发到相应路径。

这解释了官方 helper 中“dispatch backward 使用 combine、combine backward 使用 dispatch”的结构。router logits 的梯度还需经过 gate 计算图，不能把本例的固定 gate 简化套到全部反向。

## 4. 网络 token 数与展开行数不是同一口径

一个 token 的两个专家可能位于同一目标 rank。网络层可以按目标 rank 去重，只传一份输入，收到后再展开成两个专家行。

于是至少要区分：

| 数量 | 描述 |
|---|---|
| 原始 token 数 | 模型输入行数 |
| token–expert 对数 | top-k 路由后专家任务数 |
| 每目标 rank 的去重 token 数 | 同一 token 发往该 rank 只计一次 |
| 专家对齐后的行数 | grouped GEMM 布局含 padding |
| 预分配容量 | buffer 为最大负载留出的空间 |

`top-k=8` 不意味着每个 token 都跨网络发送八份。它可能命中本 rank、多名专家共享目标 rank，或经过拓扑相关的转发路径。

### 4.1 Payload 的量级估算

假设 4096 个 token、hidden=7168、BF16，按八个专家完全展开的数据量为：

$$
4096\times7168\times8\times2=448\ \mathrm{MiB}.
$$

如果示意条件下每 token 只需发送到两个不同远端 rank，按去重输入计的净数据量为 112 MiB。实际网络量还需加入 gate、索引、scale、协议、转发和结果回传；这两个数字均不是实测带宽。

判断一个优化减少了多少通信，要先问减少的是专家行、远端副本还是网络 hop，不能混用分母。

## 5. Expanded layout 的对齐计数

当前 `EPHandle` 保存多个不同意义的计数。特别容易误读的是 `psum_num_recv_tokens_per_expert`：在 expanded 模式下，它不是简单的“真实 token 数累积和”。

对专家 $i$，它保存“之前专家按 alignment 对齐后的总行数，加上当前专家真实行数”。当前专家起点由前一项向上对齐得到。

设四个专家真实 token 数 `[3,5,0,2]`，alignment=4：

| 专家 | 起点 | 真实数 | `psum[i]` | 下一段起点 |
|---|---:|---:|---:|---:|
| 0 | 0 | 3 | 3 | 4 |
| 1 | 4 | 5 | 9 | 12 |
| 2 | 12 | 0 | 12 | 12 |
| 3 | 12 | 2 | 14 | 16 |

有效行分别为 `[0,3)`、`[4,9)`、空区间、`[12,14)`。直接算 `psum[1]-psum[0]=6` 会把一个 padding 行当成专家 1 的输入；正确值为 `9-align(3,4)=5`。

### 5.1 计数解码的最小代码

```python
def align(x, multiple):
    return ((x + multiple - 1) // multiple) * multiple

def expanded_ranges(psum, alignment):
    ranges = []
    start = 0
    for end in psum:
        assert end >= start
        ranges.append((start, end))
        start = align(end, alignment)
    return ranges

ranges = expanded_ranges([3, 9, 12, 14], 4)
assert [end-start for start, end in ranges] == [3, 5, 0, 2]
```

这段验证布局公式；GPU 上应读取相应设备计数，避免为了得到 Python 列表而引入不必要的 host 同步。

## 6. `do_cpu_sync` 改变什么

`do_cpu_sync=True` 可以获得精确输出大小与 CPU 侧专家计数，常用于训练和 prefill 集成。

`False` 则按配置容量分配输出，让下游使用 GPU 侧计数解释有效范围。这有利于 decode 的异步执行与图捕获，但下游 kernel 必须理解容量与有效数的差别。

`do_zero_padding=True` 会清理专家段之间的对齐 gap；它不等于把整个未使用容量变成合法数据。不能把一个 capacity-shaped tensor 的全部行都送进 loss、激活统计或 combine。

## 7. Handle 是一次路由的状态契约

`EPHandle` 关联 top-k 索引、来源映射、目标 buffer、计数、expanded 选项与通信配置。

复用 handle 的前提是需要重放同一布局，例如同一前向对应的反向。新一轮 decode 即使 shape 相同，也可能产生不同专家路由；“都是 decode”不是复用旧 handle 的理由。

### 7.1 必须保持不变的对象

- 原始 `topk_idx` 在 handle 所有使用结束前不能被改写。
- 所有参与 rank 必须使用同一轮配置和容量约定。
- 输入/输出 buffer 的生命周期要覆盖相关 stream 上的消费者。
- 对应的专家物理映射必须与权重版本一致。

代码中的 PyTorch version counter 可以捕获部分普通原位修改，却不能完整捕获 `.data`、裸指针写入或无 version counter 的 inference tensor。正确性不能仅依赖“框架会帮我检测”。

## 8. Deferred epilogue：返回值可能在等待时才生成

本快照支持 `defer_epilogue=True` 与 `async_with_compute_stream=True`。调用先返回 `EventOverlap`，等待时在当前 stream 运行 epilogue 并产生最终返回值。

```text
准备输入
  → dispatch 返回 EventOverlap
  → 排入不依赖 dispatch 结果的独立计算
  → event.wait() 建立当前stream依赖并运行epilogue
  → 得到 recv tensors 与 handle
  → 专家计算
```

这里的 `wait()` 不应被解释成“整个 GPU 变为 idle、CPU 已能任意读取所有内存”。它的关键语义是当前 stream 的依赖和 epilogue 执行；CPU 观测与跨 stream 消费需按各自同步规则处理。

### 8.1 第一次 wait 的结果要保存

`EventOverlap` 的 post-wait hook 在首次执行后会清除。不要写成先随手 `event.wait()`，稍后再 `recv=event.wait()` 并期待第二次仍返回第一次结果。

示意集成：

```python
# 教学控制流：具体dispatch参数见本节固定源码。
pending = launch_dispatch_with_deferred_epilogue()
run_independent_work()
recv_x, recv_indices, recv_weights, handle = pending.wait()
expert_output = run_experts_and_apply_gate(recv_x, recv_weights)
pending_combine = launch_combine_with_deferred_epilogue(expert_output, handle)
run_other_independent_work()
combined_x, combined_topk_weights = pending_combine.wait()
```

上面是生命周期示意，不是可直接运行的官方 API 包装；它刻意把异步通信、独立计算与结果消费分开。

### 8.2 输入事件必须在正确位置捕获

若独立计算先被排入当前 stream，再让通信等待当前 stream，通信仍可能被这段独立计算挡住，失去重叠机会。

官方建议在输入准备好时先捕获 input-ready event，把该 event 作为通信的 `previous_event`，再排独立计算。相关分配需要使用与该路径匹配的 comm-stream 约定。

优化目标是缩短关键路径，同时保证消费顺序；不能为了减少一个 event 就忽略 buffer 仍被异步使用的事实。

## 9. NCCL Gin、NVLink 与 RDMA 的层次

NCCL Gin 是当前实现采用的设备侧通信后端。使用它不等于所有数据都通过 Python 的 `torch.distributed.all_to_all` 调用搬运。

| 层次 | 作用 |
|---|---|
| Python/框架 | 创建组、配置 buffer、组织算子与事件 |
| DeepEP kernel | 处理路由、数据搬运、转发和布局 |
| NCCL Gin/通信运行时 | 提供设备侧网络能力与 communicator 关联 |
| NVLink/RDMA 网络 | 承载机内、机间传输 |

Hybrid 与 direct 模式如何选择，要结合 scale-up 域、scale-out 连接和实际 kernel 路径。传输带宽、QP 数、通信 SM 数与 GEMM 资源互相影响；“通信库更快”不能脱离计算资源占用比较。

当前 README 提供解析估算 SM/QP 的路径，也允许按操作覆盖。它不意味着所有拓扑都无需测量，尤其在拥塞、异构链路或与其他作业共享资源时。

## 10. 从 EP 扩展到其他 buffer

| 类/功能 | 职责 | 本快照状态 |
|---|---|---|
| `EPBuffer` | 专家 dispatch/combine 与副本交换 | 核心 EP 路径 |
| `BucketBuffer` | 批量 AG/RS/AR，适配 CP/DP | 实验功能 |
| `EngramBuffer` | 跨 GPU/CPU 远程记忆访问 | 实验功能；额外依赖特定 Gin 能力 |
| `PPBuffer` | 流水线 P2P 数据交换 | 实验功能 |
| `BufferAllocator` | 构造前规划对称 tensor 分配 | 统一 buffer 生命周期的一部分 |

不能把一个版本新增某类 primitive，直接描述成完整训练框架已支持所有 CP/DP/PP 组合。上层仍需要数值归约、状态管理、错误处理和相同 collective 顺序。

### 10.1 冗余专家的权重与梯度

训练时，专家副本不只是多复制一个前向权重。前向之前需要将正确版本的权重和 scale 送到副本；反向之后，副本产生的梯度要归回原专家的优化器所有者。

当前 `lb_prefetch_weights` 和 `lb_reduce_grads` 提供相关通信原语。复制方案由调用者提供，不能认为 DeepEP 自动预测热点并决定全局最优专家分配。

模型权重、量化 scale、逻辑专家 ID 和优化器状态之间的映射必须共同维护，EPLB/LPLB 的职责见下一节。

## 11. 硬件要求与迁移清单

该固定快照的 README 要求 Linux、Python 3.10+、NVIDIA Hopper 或更新架构、CUDA 13.1+、PyTorch 2.10+、NCCL 2.32.3+、C++20 编译环境，并按操作使用 NVLink/RDMA。

它还要求 PyTorch 和 DeepEP 在进程中加载一致的 NCCL 共享库。安装成功与能正确执行某个通信拓扑，是两件需要分别验证的事。

从旧版集成迁移时：

1. 固定双方 commit，列出旧 `Buffer`/低延迟接口的实际调用。
2. 核对新 `EPBuffer`、计数与 expanded 布局。
3. 重做 gate 应用位置与 combine 输入 dtype 检查。
4. 重做 event、缓存 handle、buffer 释放与 graph capture 检查。
5. 对相同路由输入比较前向和反向的独立 oracle。
6. 再比较同硬件、相同有效 token 的端到端时间。

这不要求读者立即升级。旧框架可能固定旧 API；“安装最新 DeepEP”不自动成为兼容方案。

## 12. 故障定位表

| 现象 | 优先检查 |
|---|---|
| 输出值稳定偏小/偏大 | gate 是否重复或遗漏，combine 是否重复加法 |
| 某些专家尾部出现随机值 | 对齐计数、容量与有效范围是否混用 |
| 第二次 wait 得不到 tensor | deferred hook 是否已被消费 |
| 只有开启异步才错 | 输入事件、跨stream依赖、buffer生命周期 |
| 新decode步结果异常 | 是否复用了旧路由 handle |
| 性能提高但训练不收敛 | 逻辑专家映射、scale版本、梯度归还 |
| 初始化或退出hang | rank配置、容量、未完成操作与communicator顺序 |

## 13. 自测与参考答案

**1. top-k=8，通信一定发送八份输入吗？** 不一定。同目标 rank 可去重，还要区分本地专家、远端目的和内部展开行。

**2. `[3,9,12,14]` 的 expanded psum、alignment=4，真实计数是多少？** `[3,5,0,2]`，每段起点需要先对齐前一项。

**3. `do_cpu_sync=False` 是否不需要专家计数？** 仍需要设备侧有效计数，只是不把每轮结果同步为 CPU 精确 shape。

**4. 为什么 deferred wait 的结果只能依赖第一次返回？** post-wait hook 执行后被清除；后续等待不自动重新生成和返回相同对象。

**5. router 选择不变，仅改物理副本会改变数学吗？** 若副本权重、scale、精度和输入完全等价，目标函数应保持；执行顺序和低精度仍需验证数值容差。

**6. 当前 DeepEP 是否仍以 NVSHMEM 为必要依赖？** 本节 V2.5 快照已移除 V1/NVSHMEM，使用 NCCL Gin；依赖旧接口的生态项目可能仍需旧版本。

**7. 训练专家副本只同步权重够吗？** 不够，反向梯度还需归回正确优化器所有者，并维护更新与发布版本。
