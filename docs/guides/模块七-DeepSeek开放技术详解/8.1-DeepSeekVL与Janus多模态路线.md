DeepSeek-VL、VL2、Janus与V4.1都处理多模态，但它们的视觉路径和输出目标不同。
本节按“图像进入哪里、输出是什么”建立可比较的结构图。

核对日期：2026-11-07。
主要依据 [VL2论文](https://arxiv.org/abs/2412.10302)、[Janus论文](https://arxiv.org/abs/2410.13848) 与固定官方源码。

## 1. 先区分理解与生成

图像理解输入图片与文字，输出描述、答案、定位或其他文字结构。
图像生成输入文字或其他条件，输出图像。

理解需要提取语义、布局和对象关系。
生成还要保留或重建纹理、颜色、空间细节。

同一种视觉编码未必同时适合两个目标。

## 2. 路线对照

| 模型路线 | 视觉输入路径 | 典型输出 |
|---|---|---|
| DeepSeek-VL | 混合视觉编码 | 文字与视觉理解结果 |
| DeepSeek-VL2 | 动态切图、共享视觉encoder、MoE语言模型 | 文字、文档理解、grounding |
| Janus/Janus-Pro | 理解编码与生成编码分开 | 文字与图像 |
| JanusFlow | 自回归语言与rectified flow结合 | 文字与图像 |
| V4.1 | 原生图文预训练、DeepSeek-ViT | 自回归文字 |

同一组织有图像生成研究，不意味着每个聊天模型都能生成图片。

## 3. DeepSeek-VL的双视觉尺度

VL2论文回顾VL使用SigLIP语义路径与SAM细节路径，分别处理不同输入分辨率。

较低分辨率路径帮助提取全局语义。
高分辨率路径保留更细的视觉信息。

但固定分辨率限制了极端长宽比或高密度文档场景。
VL2因此转向动态tiling。

## 4. 为什么不能直接把长图缩成正方形

一张768×2304长文档，如果压成384×384，会丢失大量小字细节并改变几何比例。

按长宽比调整后切成多个局部tile，可以保留局部信息。
再加一张全局thumbnail，帮助模型理解整体布局。

代价是视觉token数量、encoder计算和LLM上下文开销增加。

## 5. VL2动态切图

论文以384×384作为基础tile。
从候选网格中选择合适宽高比例，调整图片并补边，再划分局部tile。

训练描述的候选网格满足一定tile数上限；评估设置可能使用不同上限。
应读取对应processor配置，而不是永久写死“最多9块”。

多图场景还可能限制或关闭动态切图，以控制上下文长度。

## 6. 一个2×3局部网格例子

设图片划分为2行、3列，共6个局部tile。
再加1个全局thumbnail，总共7次视觉tile编码。

每个tile经过视觉encoder生成27×27=729个特征。
总原始视觉特征数：

$$
7\times729=5103.
$$

这已经比“每图只当一个token”复杂得多。

## 7. 从27×27压缩到14×14

VL2通过2×2空间重排/压缩和projector，把每tile视觉token降至14×14=196。

27不是2的倍数，所以需要padding或等价边界处理。
不能用729/4=182.25当实际输出长度。

空间维减少，通道信息先重组，再投影到语言hidden维。

## 8. 行分隔符也是token

全局thumbnail有14行，每行14个视觉特征加一个newline。
因此全局部分为：

$$
14(14+1)=210.
$$

局部2×3网格拼成28×42的视觉网格，每行加一个newline：

$$
28(42+1)=1204.
$$

再加1个view separator，总数：

$$
210+1+1204=1415.
$$

## 9. 为什么不是7×196

7×196=1372只计视觉特征。
其余43个位置是全局14行换行、局部28行换行和1个视图分隔。

$$
1372+14+28+1=1415.
$$

这类格式位置影响上下文长度和image mask，不能在processor与模型之间漏掉。

## 10. VL2输入shape账本

| 对象 | 教学例子的shape |
|---|---|
| 一张图的tiles | `[7,3,384,384]` |
| encoder特征 | `[7,729,1152]` |
| projector后 | `[7,196,D]` |
| 全局加newline | `[210,D]` |
| 局部重排加newline | `[1204,D]` |
| 合并图像span | `[1415,D]` |
| 混合文本后 | `[T_text+1415,D]`加其他协议位置 |

D取决于VL2型号。
Tiny、Small与主模型不是同一个hidden维。

## 11. VL2也不是所有型号都相同attention

官方论文表格中Tiny使用MHA，Small与主模型采用MLA配置。
MoE专家数、激活参数和词表也随型号变化。

因此“VL2用了MLA”作为家族概括需要补充型号条件。
部署一个Tiny模型不能用主模型的cache公式直接估算。

## 12. Grounding是协议能力

VL2的特殊标记支持引用对象与定位等输出。
普通问图不一定需要grounding标记。

坐标范围、框格式与文本指代必须按模型约定解析。
一段看似坐标的文字不自动构成可靠定位结果。

评估还需核对图片resize后的坐标与原图坐标转换。

## 13. 源码中的图像融合

固定 `prepare_inputs_embeds`先计算各样本tile数。
然后批量运行vision和projector，再按global/local布局重组。

最终图像embedding填入文本embedding序列里由mask指定的位置。

如果mask位置数量与视觉span长度不同，应在预处理边界报错，而不是静默截断。

## 14. Janus为何拆开视觉编码

用于理解的语义encoder可以忽略某些像素细节。
用于生成的编码则需要支持图像重建。

Janus使用两个不同视觉路径，同时共享统一Transformer主干。

理解输入走语义视觉encoder与aligner。
生成训练图像先变成离散code IDs，再由生成embedding、head与图像decoder处理。

## 15. Janus理解路径

```text
图片
  -> 语义vision encoder
  -> aligner
  -> 替换image mask位置的embedding
文字
  -> 词embedding
两者
  -> 共享language model
  -> 文字答案
```

源码中对应 `vision_model`、`aligner` 和 `prepare_inputs_embeds`。

## 16. Janus生成路径

```text
文字条件
  -> 共享Transformer
  -> generation head
  -> 图像code id
  -> generation embedding反馈下一步
  -> 完整code网格
  -> VQ图像decoder
```

代码中的 `gen_head` 与普通文字词表head不同。
生成的code ID不是Unicode字符或普通语言token。

## 17. 384图像为什么需要576个code

官方示例image size384，生成空间步幅16。

$$
384/16=24,\qquad24\times24=576.
$$

模型逐步生成576个图像code，再恢复成24×24的latent网格并解码。

这只是对应公开示例的设定，不代表所有视觉生成模型都用576个token。

## 18. Codebook与语言词表分开

Janus原始论文的生成codebook大小为16384。
语言模型仍有自己的文字词表。

| 对象 | 意义 |
|---|---|
| text token id | 语言片段 |
| image code id | VQ空间的离散码 |
| vision embedding | 连续语义特征 |

这三者可以映射到相同主干hidden维，但原始语义不同。

## 19. 为什么使用classifier-free guidance

图像生成时，分别计算带条件与弱/无条件logits。
按权重组合：

$$
z_{cfg}=z_{uncond}+w(z_{cond}-z_{uncond}).
$$

它增强条件对生成分布的影响。
使用logits组合后再softmax，不是直接把两组概率线性相加。

## 20. CFG手算

取两个候选code的logits：

$$
z_{cond}=[2,0],\quad z_{uncond}=[1,1],\quad w=2.
$$

则：

$$
z_{cfg}=[3,-1].
$$

softmax后第一个code概率约0.982。
如果w=1，则回到条件logits；w=0则只有无条件分布。

过大的w不保证质量单调提高，可能影响多样性和细节。

## 21. CFG为何增加batch

官方示例为每个待生成图像保留cond/uncond两条分支。
要生成B张图，模型批量维可能变成2B。

输出head后再取偶数/奇数分支组合。
如果只按B估算KV与激活，会低估该示例的实际容量。

## 22. Janus训练阶段

原始论文分为适配器与image head训练、统一预训练、SFT三个阶段。
阶段间参数冻结范围与数据混合不同。

统一预训练同时考虑文字、视觉理解和视觉生成任务。
Janus-Pro进一步调整训练策略、数据与模型规模。

不能把“统一主干”解释为所有阶段、所有模块都从第一步一起更新。

## 23. JanusFlow是另一种生成路线

JanusFlow把自回归语言与rectified flow结合。
图像生成不应再按Janus离散VQ逐token循环原样解释。

一种教学插值为：

$$
x_t=(1-t)x_{noise}+t x_{data}.
$$

模型学习相应连续状态的流动方向，再通过数值积分生成图像。
具体时间方向和网络条件以JanusFlow论文为准。

## 24. 与V4.1的关系

V4.1原生处理图文，但公开定义的输出是自回归文字。
其DeepSeek-ViT、3×3重排和CED/CSA2主干见2.6—2.9。

它不是把Janus生成head直接接到V4上。
两条研究线能共享经验，仍需分别看模型结构证据。

## 25. 一个多模态验证清单

同一图片至少检查：

- resize与crop数量。
- image span与文本mask长度。
- global/local顺序和newline数量。
- 图像与文字位置是否正确对应。
- 生成head使用哪个词表。
- 输出坐标或code是否按正确格式还原。

shape相同也可能顺序错误，尤其是tile拼接和cond/uncond交错。

## 26. 公开源码与实验边界

VL2和Janus都提供官方推理代码与权重入口。
代码许可证与模型协议需按artifact分别读取，不能只看一个badge。

本节没有下载完整模型权重，也未执行图像理解或图像生成benchmark。
token数量与CFG数例为可复核的数学和源码级说明。

## 27. 自测与答案

**问题1：VL2的2×3网格为什么是1415而不是1372token？**

答案：还包括全局与局部行分隔及view separator。

**问题2：VL2-Tiny一定用MLA吗？**

答案：不是，论文表格中Tiny使用MHA。

**问题3：Janus为何分开理解与生成编码？**

答案：语义理解和像素重建对视觉表示的需求不同。

**问题4：图像code ID是文字token吗？**

答案：不是，它属于图像生成codebook。

**问题5：CFG能否直接线性相加概率？**

答案：该实现组合logits后softmax，不能随意换成概率加法。

**问题6：2B分支对显存有什么影响？**

答案：cond/uncond都执行，KV与激活需按实际批量计算。

**问题7：V4.1能看图是否证明它能生成Janus式图像？**

答案：不能，公开输出模态与生成模块不同。
