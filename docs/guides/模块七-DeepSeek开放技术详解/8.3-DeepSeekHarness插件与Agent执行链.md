DeepSeek Harness简称dsh，是组织模型调用、工具和会话的agent运行框架。
它不负责更新LLM权重，也不是一个下载后就能复现DeepSeek RL训练的trainer。

核对日期：2026-11-07。
固定版本为 `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159`。
依据 [官方架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/docs/architecture.md) 与对应源码。

官方将当前项目标为developer preview，接口迭代较快。
本节所有具体路径均绑定上述版本。

## 1. Harness夹在哪两层之间

```text
用户/评估任务
  -> Harness
       -> 模型API或推理后端
       -> 工具与执行环境
       -> 会话事件日志
  -> 最终回答与任务结果
```

模型负责产生下一步文本或动作。
工具执行器负责操作文件、运行命令等。
Harness负责把这些动作串成有状态任务。

## 2. 为什么不是训练框架

一个RL系统可以让harness执行rollout，然后收集轨迹和reward训练模型。
但harness自身不因此拥有optimizer、梯度聚合和策略更新。

| 层 | 主要职责 |
|---|---|
| 模型 | 条件分布 |
| 推理引擎 | 高效执行模型 |
| Harness | 对话、工具、上下文和状态 |
| Sandbox | 执行隔离与资源 |
| RL trainer | 优势、loss、梯度和checkpoint |

DSec与harness也不同：前者提供环境基础设施，后者运行agent循环。

## 3. Everything-is-a-plugin的含义

项目基于Cordis，将模型adapter、工具registry、session log和agent loop等都组织为插件。

插件向共享context注册服务、事件监听和可撤销effect。
卸载插件时，对应注册应被清理。

这不是只有UI插件可以替换，而是核心能力本身也通过可组合接口提供。

## 4. 定义、provider与consumer

一个能力可以拆成：

1. Service definition：声明接口。
2. Provider：实现本地或远程行为。
3. Consumer：通过接口使用能力，例如模型可调用tool。

更换文件系统或subprocess provider，可以改变实际执行位置。
但调用方仍应遵守同一接口语义与权限约束。

## 5. Profile与bundle

profile是一个命名的运行组合。
bundle是配置行与其挂载代码的分发单位。

本版本包含web、headless、sdk、sdk-minimal和acp等profile模板。
不同profile可使用不同界面、传输和插件集合。

启动同一个 `dsh` 命令，通过profile选择运行形态。

## 6. 配置层的顺序

架构文档给出的组合顺序为：

```text
profile中的有序bundles
  -> profile自身patch
  -> home patch
  -> 命令行--patch overlays
```

后层可以覆盖前层指定的行。
patch按row id替换整份config或插入新行，并非任意字段自动深合并。

## 7. 一个配置覆盖反例

假设某示意插件初始config为：

```json
{"enabled": true, "timeout": 10}
```

后层对该row提供：

```json
{"timeout": 20}
```

若语义是整份config替换，不能假定enabled仍继承true。
最终行为还要看插件的默认值与schema。

这解释了为什么调试时要检查最终展开配置，而不只阅读某一层YAML。

## 8. 核心服务的分工

| 包 | context或职责 |
|---|---|
| `core/session` | append-only事件与session store |
| `core/system-prompt` | prompt段落与工具schema组装 |
| `core/tools` | scoped工具定义和执行分派 |
| `core/agent` | Agent接口、registry与事件 |
| `core/agent-loop` | 默认循环驱动 |
| `core/scope` | 每agent作用域注册 |
| `llm/llm` | 消息、stream与adapter接口 |

这些边界决定一个扩展应放在哪里。
不是所有新行为都要直接修改agent loop。

## 9. Turn与step不同

一个step是一次模型请求及其产生的工具调用。
一个turn可以包含零个或多个step。

用户提出一个任务后，模型可能先读文件、再编辑、再运行测试、最后回答。
这可以是同一个turn中的多个step。

把turn等同一次HTTP调用，会误读取消、重试和工具续接语义。

## 10. 一个四step例子

| step | 模型动作 | 工具结果 |
|---|---|---|
| 1 | 请求读取文件 | 返回源码 |
| 2 | 请求修改代码 | 返回修改结果 |
| 3 | 请求运行测试 | 返回退出码与日志 |
| 4 | 生成最终回答 | 无工具调用 |

共4次模型请求、3次工具操作，但属于一个任务turn。

工具执行之后仍有工作欠账时，loop继续下一请求。

## 11. 请求开始前发生什么

loop领取待处理输入，快照session中的模型选择。
组装系统prompt、上下文与本step允许的工具schema。

`agent/pre-step`等扩展点可以接受、改写或拒绝输入。
如果第一次输入被拒绝或改写为空，可能关闭turn而不产生step。

这与请求已经发出去后再取消是不同阶段。

## 12. PrepareCall绑定模型adapter

源码在正式请求前调用 `llm.prepareCall`。
这一步确定可用adapter及其实际能力与配置。

系统消息与用户消息的提交应与这个准备边界协调。
取消发生在准备阶段时，不应把未正式接纳的输入误记成已经发送给模型。

## 13. 模型看到的历史来自事件日志

`deriveMessages()`从session事件派生模型历史。
请求边界会冻结对应历史与配置，避免流式执行过程中插件悄悄修改已发出的请求。

这使“某一步模型到底看到了什么”具有可重建依据。

日志不只是UI聊天气泡的副本，而是上下文的来源。

## 14. Durable事件与live事件

| 类型 | 作用 |
|---|---|
| session事件 | 持久记录turn、step、消息和工具事实 |
| agent事件 | 当前进程内的运行状态与扩展点 |
| capability事件 | 文件、工具、遥测等接口挂钩 |

实时stream chunk用于UI增量展示。
完整assistant message或attempt在settlement时提交。

不能假设每个已显示的临时chunk都已成为持久模型历史。

## 15. Assistant message与attempt

成功完成的assistant message进入模型历史。
失败、取消或重试中的attempt可以作为日志证据保留，但不一定加入后续模型可见消息。

这避免把失败请求的半段输出无意当成已承诺答案。

硬进程崩溃发生在settlement前时，未提交临时stream还可能丢失。
因此持久化保证要按具体提交边界描述。

## 16. 工具执行链

```text
模型输出tool calls
  -> scoped定义与可用性检查
  -> tools/pre-execute
  -> executor执行
  -> tools/post-execute
  -> tool/result进入session
  -> 继续模型请求
```

工具schema只告诉模型如何调用。
真正执行还需executor、权限、取消和结果序列化。

## 17. Scoped工具注册

全局工具可以被某个agent作用域中的定义遮蔽。
同一作用域重复注册会报错。

限制规则还要与继承关系组合。
子agent不应仅因拥有同名tool就绕过上层约束。

源码中的 `ScopedLayers` 和 `ToolLayer` 是理解这一行为的入口。

## 18. 工具定义与执行器分开

`ToolsService`登记定义并把调用交给选中的executor。
本版本不再通过一个旧mode字段同时选择所有执行方式。

模型看到的工具呈现可以是native调用，也可以由PTC等执行方式组织。

不要把旧版本配置字段照抄到当前版本后，再把失败归咎于模型能力。

## 19. 工具输出也有契约

固定源码要求工具定义声明输出schema与render等接口。
结果需要同时满足程序消费和模型展示需求。

若实际工具返回内容与schema不符，可能在解析或后续上下文中失败。

一个shell命令退出0也不意味着应用语义成功；必要时还应检查产物和结构化字段。

## 20. 并发只适合独立操作

读取两个互不依赖的文件可以并行。
先编辑再测试则有依赖，测试必须看到编辑结果。

教学估算：两个独立读取分别1s和2s，串行3s，理想并行约2s。

但共享磁盘、API限速和执行器并发限制可能降低收益。
并发不能改变用户要求的操作顺序语义。

## 21. 取消需要跨层传播

取消信号可能发生在模型请求、stream读取或工具执行阶段。

loop需要结束当前工作、记录合理状态，并处理尚欠的tool result。
工具后端也必须决定如何停止进程、回收资源和保留部分输出。

仅停止UI显示，不等于远程命令已经停止。

## 22. Resume不应重复外部副作用

重启后根据日志恢复上下文时，已完成的文件写入或工具动作不应默认重做。

同一tool call id应关联明确的结果与执行状态。
未完成操作则需要错误或恢复策略。

这与DSec中的命令恢复有共同系统问题，但两者不是同一实现。

## 23. 模型选择与重试

当前turn或step可以固定模型选择快照。
重试应保留该请求身份的必要设置，避免同一逻辑请求悄悄换模型或推理强度。

若确实更换provider或上下文格式，应产生新的请求系列边界。
这样日志才能准确解释结果来源。

## 24. 性能评估应覆盖整个任务

只测模型tokens/s，会漏掉：

- 工具等待。
- prompt组装与上下文扩展。
- 网络传输与stream解析。
- 文件系统和测试时间。
- 重试与错误恢复。

因此应记录任务成功率、总时长、模型token、工具次数与失败类型。

## 25. 一个事件数量账本

假设一个turn有4个step，每步各记录start/end。
有3个tool call和3个tool result。

仅这几类事件至少有：

$$
2+4\times2+3\times2=16.
$$

还未计入消息、请求header、context和stream settlement。
这说明append-only事件log规模不能简单等同聊天消息条数。

## 26. 开发阅读路线

先看固定 `docs/architecture.md`的turn flow。
再跟 `packages/core/agent-loop/src/agent.ts`中的step开始、prepareCall、history冻结与tools.execute。

最后才看具体模型adapter、shell或UI插件。

## 27. 开放与运行边界

harness代码开放，允许学习完整agent执行与插件结构。
它不包含模型权重训练过程，也不代表DSec的完整生产控制面。

本节没有安装插件、配置用户凭据或发起真实模型API请求。
示例事件与时间数字均为教学构造。

## 28. 自测与答案

**问题1：一次turn一定只有一次模型请求吗？**

答案：不是，turn可包含多个模型与工具step。

**问题2：模型看到的历史应从哪里重建？**

答案：从持久session事件及明确投影规则，而不只是UI临时状态。

**问题3：实时chunk显示了是否一定已持久提交？**

答案：不一定，要看settlement边界。

**问题4：patch一定逐字段深合并吗？**

答案：该架构按row替换整份config，不能默认深合并。

**问题5：tool schema是否等于执行授权？**

答案：不是，还需执行器、guard与环境权限约束。

**问题6：读取文件与修改后测试是否都能随意并行？**

答案：前者可能独立，后者有先后依赖。

**问题7：harness是否自动成为RL trainer？**

答案：不是，它可供rollout使用，但不负责梯度和optimizer。
