Agent训练不仅消耗GPU。
代码编译、浏览器、测试、文件操作和长时间等待，会产生大量CPU、内存、存储和环境管理需求。

DSec研究如何在大规模并发下提供这些执行环境。
它与LLM推理引擎、agent harness和RL算法属于不同层。

核对日期：2026-11-07。
主要来源为 [DSec官方作者论文v1](https://arxiv.org/html/2609.22978v1)。
本次没有定位到独立公开的完整DSec服务端仓库，因此具体生产机制按论文披露标注。

## 1. 为什么CPU低利用率仍会资源不足

Agent生成下一步动作时，sandbox可能暂时不运行CPU任务。
但进程内存、文件cache、工作目录和VM状态仍占资源。

大量sandbox同时等待模型，就可能出现CPU很闲而内存耗尽。

因此高密度部署不能只看平均CPU利用率。
还要管理环境的存活时间和驻留状态。

## 2. 四类执行后端

| 后端 | 适合场景 | 主要边界 |
|---|---|---|
| FnCall | 短小、近似无状态任务 | 复用预创建环境 |
| Container | 代码仓库与一般工具工作 | 共享所在系统内核 |
| MicroVM | 需要更强隔离的Linux任务 | 启动和内存成本更高 |
| Full VM | 完整OS、GUI、移动系统等 | 功能完整但成本更大 |

统一SDK不是抹平所有后端语义。
调用方仍需选择与任务相符的后端。

## 3. 注意论文中的容器隔离层

DSec描述FnCall和container运行在QEMU/libvirt VM内，而不是直接运行在裸机宿主上。
这为不受信任工具执行增加一个内核与网络边界。

MicroVM使用Firecracker路线。
Full VM用于完整系统与图形功能需求。

不能只写“container共享host kernel”而漏掉论文部署中的外层VM。

## 4. 用户可见生命周期

```text
选择后端和环境版本
  -> 请求资源与网络策略
  -> 调度到节点
  -> 创建sandbox
  -> 执行多轮工具操作
  -> 可能暂停和恢复
  -> 完成或TTL过期
  -> 回收资源
```

状态机必须区分创建中、运行、暂停、失败与销毁。
否则重试可能创建重复环境或丢失已有任务。

## 5. 控制服务与节点运行时

| 组件 | 论文中的职责 |
|---|---|
| IAM | 身份、授权、project与配额 |
| apiserver | 请求入口与转发 |
| placement engine | 过滤候选节点并选放置 |
| watcher | 健康和负载视图 |
| edge | 单节点创建、准入、状态与资源 |
| aether | sandbox内代理通道 |
| chronus | 独立shell session与操作接口 |

组件名称来自论文，不表示读者已能下载同名完整开源服务。

## 6. 为什么还要节点本地准入

placement使用周期性刷新负载，视图可能滞后。
多个请求可能同时被分配到同一节点。

edge在实际创建前重新检查当前容量。
这样全局选择与本地准入共同减少过量承诺。

这是分布式调度常见的两层约束，不是“最少负载节点”一次决定就永远正确。

## 7. 可组合环境解决什么问题

一个任务环境可能包含：

- base OS与运行时。
- 任务workspace。
- 编译器或浏览器toolkit。
- 验证脚本和依赖。

若每种组合都制作单体镜像，更新一个工具可能要求重建大量任务镜像。
DSec把这些拆成独立版本层，再在创建时组合。

## 8. 一个镜像组合数例

假设有N=10000个workspace、m=3种base、k=4种toolkit版本。
若每个组合都构造单体镜像，组合空间可能达到：

$$
Nmk=120000.
$$

分层后需要维护workspace、base和toolkit各自版本，以及组合描述。
更新4个toolkit不必重新复制10000份workspace内容。

实际组合数量由任务配置决定；这个例子说明依赖解耦收益。

## 9. Overlayfs的读写分工

只读lower层组合成统一目录树。
运行时修改进入可写upper层。

删除还需要正确表达whiteout语义，不能简单把不存在文件视为“从所有lower层删除”。

层优先级决定同路径文件来自哪个版本。
因此环境可复现记录需要保留有序层列表，而不只是无序镜像集合。

## 10. EROFS为什么适合只读层

EROFS是面向只读数据的文件系统，支持压缩与随机访问。
读取某个文件时可以只获取相关块。

这与先下载整个tar.gz再解压不同。
大量环境只使用少量依赖时，按需读取可以同时减少启动等待与总I/O量。

## 11. 3FS不是直接承接所有小写入

DSec论文指出其共享存储更适合大块高吞吐访问，小随机I/O需要规避。

因此采用：

| I/O类型 | 主要位置 |
|---|---|
| 运行时小写入与日志 | 节点本地可写层 |
| 镜像只读数据 | 3FS按需、大块读取 |
| 可分离的文件系统metadata | 提前放本地 |

这是针对访问模式的分工，不是“远程文件系统足够快就全部放远程”。

## 12. 冷启动I/O数例

假设镜像20GB，某任务实际只读取其中1GB。
全量pull至少传20GB，按需读取理想只传约1GB加metadata。

如果1000个不同任务同时启动，这一差异会放大。

但按需读取可能把等待转移到首次触碰文件时。
需要prefetch、readahead与块合并来降低首次缺页延迟。

## 13. MicroVM的可写磁盘路径

论文使用OverlayBD等块级路径支持部分microVM磁盘需求。
通过ublk提供用户态块设备，并把远程读取按256KiB块组织到本地cache。

这与container的EROFS多设备metadata/data分离路径不同。
不能强行用同一文件系统方案覆盖所有后端。

Docker-in-VM等场景还会带来特殊文件系统兼容性要求。

## 14. 内存为什么会重复缓存

普通VM文件读取可能同时占宿主page cache和guest page cache。
多个VM使用相同只读数据时，这些副本可能重复。

virtio-pmem配合DAX直接映射host-backed页面，减少guest再复制一份cache。
共用只读层的microVM可以共享host cache。

这是文件页共享，不代表任意进程私有堆内存都自动共享。

## 15. DAX也有成本

论文说明guest仍需为映射地址范围维护 `struct page` 等metadata。
4KiB页、每页64B metadata时：

$$
64/4096=1/64.
$$

128GB设备对应约2GB guest metadata。

因此“零拷贝共享”不等于零内存开销。
冷数据缺页与buffered I/O预读能力也存在权衡。

## 16. DAMON与balloon分别做什么

DAMON抽样识别长时间未访问的冷文件页，并通过内核回收路径释放。
virtio-balloon free-page reporting把guest空闲页报告给host，使host可释放对应物理内存。

前者帮助guest产生可回收空闲页。
后者把guest空闲转化为host实际可用容量。

只在guest里标记free，不一定意味着host RSS立刻下降。

## 17. 一个内存账本例子

一个VM分配4GiB，其中1GiB是活跃私有内存、2GiB冷文件cache、1GiB空闲。

如果没有host可见的回收机制，宿主可能仍承担大部分驻留页。
回收冷cache再报告空闲页，可以减少实际host占用。

具体回收量取决于脏页、共享页、巨大页和内核策略。
不能把逻辑分类直接当成确定释放量。

## 18. CPU QoS不止设置优先级

DSec区分latency-sensitive和best-effort任务。
BE使用SCHED_IDLE，在LS可运行时让出CPU。

但同一物理核的SMT sibling仍可能竞争执行资源。
因此论文结合core scheduling避免无关BE与LS占同一物理核的兄弟线程。

调度优先级与物理核资源隔离是两层问题。

## 19. 一个SMT干扰直觉

两个逻辑CPU不意味着两套完全独立执行单元。
若LS任务与高吞吐BE任务共用同一物理核，LS延迟可能增加。

把BE移到真正空闲的核或禁止该共跑组合，可能改善尾延迟。
代价是部分吞吐与调度自由度。

应同时报告LS延迟与集群整体利用率。

## 20. 环境由agent构造也需要清理

论文允许agent交互式搭建环境，再通过增量快照形成可复用任务。

构造账户与训练执行账户分开。
打包前删除答案、参考实现和构造过程残留，避免训练agent从意外渠道取答案。

环境构造成功不等于训练评估有效，还需要检查可解性和信息泄漏。

## 21. 为什么agent loop移出GPU训练pod

训练GPU作业可能被抢占。
如果agent loop随pod消失，而sandbox仍在运行，恢复时就需要重建两者一致状态。

V4.1路线把agent sandbox与worker container放在可抢占GPU池之外。
worker与sandbox保存rollout执行状态，训练作业恢复后重新连接。

这解耦了训练作业生命周期与长任务生命周期。

## 22. 旧方案的命令重放边界

论文描述早期方案用命令日志协调恢复。
已完成操作应复用记录结果，而不是再次执行。

比如“创建文件并追加一行”执行两次，结果可能不同。
因此重放必须区分重建观察与重新施加外部副作用。

新架构减少这类跨组件重建复杂度，但仍要处理节点失败等情况。

## 23. Container暂停与恢复

论文路径先暂停进程树，再启用必要swap和主动内存回收。
恢复前对映射发起异步预取，然后unpause。

仅 `docker pause` 会停止执行，却未必释放大量内存。
主动回收是另一个必要步骤。

这里是机制解释，不建议在任意运行环境中不加检查执行这些系统级操作。

## 24. MicroVM暂停与恢复

microVM保存内存与执行状态快照，再终止运行中的Firecracker进程以释放内存。
恢复时启动新进程并载入快照。

磁盘快照与内存/CPU状态必须对应。
只保存文件系统不能恢复进程的执行位置、栈和打开句柄语义。

## 25. 故障与安全为何影响训练质量

如果agent读到构造阶段残留答案，reward变高但能力未必提高。
如果日志无限增长，环境可能拖垮存储。
如果工具命令在错误边界执行，可能破坏其他任务或自身环境。

论文通过文件/socket访问控制、网络策略和观测持续加固。
这些机制不能保证防住所有内核漏洞或所有破坏行为。

## 26. 一个最小可审计任务记录

| 字段 | 内容 |
|---|---|
| 环境版本 | 有序base/workspace/toolkit层 |
| 后端 | FnCall/container/microVM/full VM |
| 资源 | CPU、内存、磁盘、TTL |
| 网络策略 | 允许的目的服务与范围 |

基础设施异常不应无条件计作模型任务失败。

## 27. 自测与答案

**问题1：CPU利用率低为何仍可能无法增加sandbox？**

答案：内存、cache和长期状态仍驻留，可能先耗尽容量。

**问题2：可组合层与单体镜像最大差别是什么？**

答案：base、workspace、toolkit可独立版本和更新，减少组合重建。

**问题3：为什么小写入放本地？**

答案：避免共享存储的小随机I/O成本，并把远程访问组织为大块只读。

**问题4：DAX是否零内存开销？**

答案：不是，还包括映射metadata与缺页处理等成本。

**问题5：为何CPU低优先级仍需core scheduling？**

答案：SMT sibling共享物理执行资源，优先级本身不能消除全部干扰。

**问题6：暂停container是否自动释放内存？**

答案：不一定，论文另加主动回收与恢复预取。

**问题7：公开DSec论文是否等于完整server源码已开放？**

答案：不能这样推断，本次未找到独立完整服务端仓库。

### 如何评估环境服务本身

至少分别测量创建延迟、首次命令延迟、稳态执行延迟和暂停恢复延迟。
平均值之外，还要看高分位数与失败率。

镜像是否冷缓存、访问多少文件、后端类型和资源超售比例都应写入测试条件。
一次热缓存创建很快，不能证明大批冷镜像并发启动同样快。

任务失败还应区分模型动作错误、验证器错误、环境构造错误与平台故障。
只有正确分类，才能判断应该优化训练数据还是基础设施。
