## 1. 先明确 DeepGEMM 的职责

DeepGEMM 的起点是高效的低精度矩阵乘法；当前公开版本已扩展到 BF16/FP8/FP4 GEMM、MoE 融合、稀疏索引打分与 Hyper-Connection 相关计算。它提供的是可以嵌入训练和推理运行时的底层计算原语。

完整请求如何排队、KV 如何分配、专家权重如何从 checkpoint 加载、采样结果如何流式返回，仍由上层系统组织。一个 GEMM 测试达到高吞吐，也不能单独证明端到端服务更快。

本节核对 **2026-11-07** 的官方快照：

```text
deepseek-ai/DeepGEMM
5081f8513af57e61696de4f4f04b0e707ffb503e
```

所有接口与硬件表都绑定该快照。2025 年初的代码和教程可以帮助理解设计演进，但不能代替当前 API。

## 2. 从一个 Linear 的三个维度开始

设输入为 $A\in\mathbb R^{M\times K}$，权重按 $B\in\mathbb R^{N\times K}$ 存储：

$$
D=AB^T,\qquad D\in\mathbb R^{M\times N}.
$$

| 维度 | 在 LLM 中常见的含义 | 性能影响 |
|---|---|---|
| $M$ | token 数，或某专家收到的有效 token 数 | 小 $M$ 可能无法充分利用 Tensor Core |
| $K$ | 输入隐藏维或 FFN 中间维 | 归约长度、缩放块数和访存量 |
| $N$ | 输出隐藏维或 FFN 中间维 | 输出 tile 数、权重读取量 |

在稠密层中，$M$ 可以由多个请求的 token 合并得到；在 MoE 中，每个专家的 $M_e$ 不同。Prefill 常有较多 token，Decode 常是每请求少量 token，两者即使模型相同也不是同一个 GEMM 工作负载。

基础计算量按一次乘和一次加计：

$$
F\approx2MNK.
$$

这个式子不包含量化、转置、路由、激活函数、通信或 padding。后面比较整个 MoE 时必须把这些补回来。

## 3. 低精度乘法的真正对象是“数据＋缩放”

量化后的 tensor 不能脱离 scale 使用。对归约维按块 $g$ 划分的低精度矩阵：

$$
A_{mk}\approx s^A_{m,g(k)}\widehat A_{mk},\qquad
B_{nk}\approx s^B_{b(n),g(k)}\widehat B_{nk}.
$$

$b(n)$ 表示权重的输出维分组。将它代入矩阵乘法：

$$
D_{mn}\approx\sum_g
s^A_{m,g}s^B_{b(n),g}
\left(\sum_{k\in g}\widehat A_{mk}\widehat B_{nk}\right).
$$

scale 依赖归约块，因此一般不能把所有低精度乘积先加成一个总和，再在最后乘任意一个 scale。分块缩放的位置决定了计算结果。

### 3.1 一组可手算的完整例子

为了只观察缩放，不模拟 FP8 编码，把以下小整数视为可表示的量化值。实际内核常见块长为 128 等，本例将 $K$ 块长缩成 2：

$$
\widehat A=\begin{bmatrix}1&2&3&4\\2&0&1&3\end{bmatrix},\quad
\widehat B=\begin{bmatrix}2&1&0&1\\1&3&2&0\end{bmatrix}.
$$

输入两个行的块 scale 分别为 `[0.5,1]`、`[2,0.25]`；两个权重行共享块 scale `[1,2]`。

| 输出 | 第一个 K 块贡献 | 第二个 K 块贡献 | 合计 |
|---|---|---|---:|
| $D_{00}$ | $0.5\times1\times(1\times2+2\times1)=2$ | $1\times2\times(3\times0+4\times1)=8$ | 10 |
| $D_{01}$ | $0.5\times1\times(1\times1+2\times3)=3.5$ | $1\times2\times(3\times2+4\times0)=12$ | 15.5 |
| $D_{10}$ | $2\times1\times(2\times2+0\times1)=8$ | $0.25\times2\times(1\times0+3\times1)=1.5$ | 9.5 |
| $D_{11}$ | $2\times1\times(2\times1+0\times3)=4$ | $0.25\times2\times(1\times2+3\times0)=1$ | 5 |

如果对 $D_{00}$ 错用第一个块的 scale 乘整个 dot product，会得到 $0.5\times8=4$，而正确分块结果是 10。

### 3.2 一个独立于 GPU 的 oracle

```python
def block_scaled_gemm(a, b, sa, sb, block_k):
    # a:[M,K], b:[N,K], sa:[M,G], sb:[G]；示例让B所有行共享scale。
    m, k, n = len(a), len(a[0]), len(b)
    assert k % block_k == 0
    out = [[0.0 for _ in range(n)] for _ in range(m)]
    for i in range(m):
        for j in range(n):
            for g in range(k // block_k):
                partial = sum(a[i][t] * b[j][t]
                              for t in range(g*block_k, (g+1)*block_k))
                out[i][j] += partial * sa[i][g] * sb[g]
    return out

a = [[1, 2, 3, 4], [2, 0, 1, 3]]
b = [[2, 1, 0, 1], [1, 3, 2, 0]]
answer = block_scaled_gemm(a, b, [[0.5, 1], [2, 0.25]], [1, 2], 2)
assert answer == [[10.0, 15.5], [9.5, 5.0]]
```

这是分块反量化的数学检查，没有验证 FP8/FP4 的编码舍入、Tensor Core 内部精度或 DeepGEMM 内核。

## 4. 缩放的逻辑 shape 与物理布局

两份 scale tensor 数值相同、逻辑 shape 相同，不代表它们满足同一个 GPU kernel 的加载约定。

核对快照的 README 要求 LHS scale 使用适合 TMA 的对齐及转置存储布局。这里的“转置布局”首先指 stride 和内存排列，不能简单把逻辑矩阵转置后把 shape 也交换。

例如逻辑 shape `[M,G]`：

- 普通连续存储的 stride 通常为 `[G,1]`。
- 按另一轴连续、并带 padding 的布局可能是 `[1,M_pad]`。
- 两者按 `[m,g]` 访问应得到相同 scale，但物理加载方式不同。

| 架构路径 | 快照中的 scale 格式 | 需要额外注意 |
|---|---|---|
| SM90 | FP32 scale | 实际 stride、对齐、所选 1D/2D 缩放变体 |
| SM100 | 打包 UE8M0 scale | 4 个 8-bit scale 打包到一个整型容器，逻辑 scale 数不等于容器元素数 |

UE8M0 的指数缩放和任意 FP32 实数 scale 也不是相同数值模型。转换格式时要检查量化误差，而非只把四个字节拼成一个整数。

## 5. Tensor Core 流水线的四个阶段

一份输入 tile 的典型生命周期：

```text
HBM中的量化数据与scale
  → 异步搬运到片上缓冲
  → 等待该tile的数据与barrier就绪
  → Tensor Core做块乘法并应用对应缩放/累积逻辑
  → epilogue转换与写回D
```

现代 GPU 可以让不同 warp/warp-group 分工：有的负责搬运，有的负责矩阵计算，有的负责输出。多个 tile 缓冲让加载下一块与计算当前块重叠。

但重叠成立需要同时满足依赖与资源条件：

1. 生产者不能覆写消费者仍在使用的共享内存阶段。
2. 消费者不能读取 TMA 尚未完成的 tile。
3. scale 与量化数据必须属于同一逻辑 tile。
4. barrier phase/计数需要随循环轮次一致推进。
5. 增加 stage 数可能降低 occupancy，不能只看流水更深。

SM90 与 SM100 的矩阵、Tensor Memory、异步执行机制不同，代码路径也分开。将 Hopper 的 WGMMA 教程逐行套到 Blackwell，不是可靠的移植方式。

## 6. Contiguous Grouped GEMM：把每个专家的 token 连起来

同一层 MoE 的专家通常具有相同 $N,K$，但 token 数 $M_e$ 不同。可以把专家输入按专家编号排列为一个大矩阵，并记录每段属于哪个专家。

假设三个专家收到 `[5,2,7]` 行，kernel 要求每段对齐到 4 行：

| 专家 | 有效行 | 对齐后行数 | padding |
|---|---:|---:|---:|
| 0 | 5 | 8 | 3 |
| 1 | 2 | 4 | 2 |
| 2 | 7 | 8 | 1 |
| 总计 | 14 | 20 | 6 |

计算效率不能只按 14 行估计。若实际执行所有对齐行，padding 占执行行数的 30%；若只统计有用 FLOPs，报告方式还要明确。

DeepGEMM 当前有 M-axis grouped 路径，其核心约束是各专家的 $N,K$ 一致。一般的“每个 group 都是任意 shape 的矩阵乘”并不是同一个接口。

### 6.1 前向与权重反向的归约轴不同

前向：

$$
Y_e=X_eW_e^T.
$$

权重梯度：

$$
\nabla W_e=(\nabla Y_e)^TX_e.
$$

在权重梯度里，token 数 $M_e$ 成为归约轴。因此用于权重 backward 的 K-axis grouped GEMM，与前向按 M 组织的 grouped GEMM 不是换个函数名就能互用。

必须沿实际 shape 推导转置、输出与归约维，并核对 accumulation dtype、是否累加已有梯度和多 microbatch 生命周期。

## 7. Masked Grouped GEMM：容量与有效数分开

Decode 中每个专家收到多少 token 取决于路由。若为了拿到精确数量每层都同步回 CPU，会破坏异步调度和 CUDA Graph 的收益。

一种方法是预分配固定容量，GPU 侧提供有效计数，kernel 只处理相应范围。必须区分：

- 预分配 shape 与真实有效 shape。
- 用于对齐的零 padding 与未使用容量。
- 一份静态 graph 的地址稳定性与动态有效计数。

容量为 128、有效数为 13，不代表剩余 115 行都是可被消费的零样本；即使内存碰巧为零，语义上也仍无效。上游 DeepEP 的接收计数和 grouped GEMM 的 mask/范围必须对齐。

## 8. Mega MoE：融合的边界扩大到了通信

当前 SM100 Mega MoE 把专家 dispatch、两次 linear、SwiGLU 和 combine 放入一个协作执行的路径，并在 NVLink 域内重叠通信与 Tensor Core 计算。

它减少的不仅是 Python 调用次数，还包括独立 kernel 间的中间张量写回、启动间隙和某些等待。代价则是更强的 buffer、布局和拓扑约束。

```text
量化输入与top-k路由
  → 对称内存中准备输入/scale/专家索引/权重
  → dispatch与本地专家tile调度
  → GEMM1 → SwiGLU → GEMM2
  → combine → BF16输出
```

### 8.1 对称内存不等于自动复制全部 tensor

对称 buffer 的分配、通信组与所有 rank 的容量约定必须一致。使用接口前应检查：

| 检查 | 原因 |
|---|---|
| 所有 rank 的容量一致 | 避免远程地址偏移解释不一致 |
| 权重经过指定转换 | kernel 不一定接受原始 checkpoint 存储布局 |
| 输入和路由数据写入完成 | 防止消费上一次请求残留 |
| expert top-k 索引范围 | 逻辑专家、物理副本与局部专家编号不能混用 |
| 生命周期覆盖全部在途计算 | buffer 不能提前销毁或重用 |

README 的示例要求相应 PyTorch 对称内存支持；普通单进程 CPU 内存不能替代这些执行语义。

### 8.2 融合也有不划算的情形

若通信域跨低带宽网络、各专家 shape 差异太大、路由长尾严重或需要频繁变更布局，一个高度融合的路径不一定比可组合算子更容易调度。

比较时应固定模型、有效 token、路由分布、精度和通信组，测完整 MoE 层延迟。不能拿 fused kernel 的 TFLOPS 直接除以另一路径包含 CPU 调度的 wall time。

## 9. Roofline 和端到端账本

粗略算术强度：

$$
AI\approx\frac{2MNK}{b_A MK+b_B NK+b_D MN+\text{scale bytes}}.
$$

这是按所列输入各读取一次、输出写回一次得到的理想算术强度估计：在冷数据的这一口径下，字节量是乐观下界，算术强度相应是乐观上界。重复加载和额外搬运会降低实际强度；若输入已经驻留片上缓存，则需重新定义 HBM 计数边界。真实工作还可能包括：

- 输入的 dtype 转换和动态 scale 计算。
- TMA scale 布局转换与 padding。
- MoE 路由、排序、dispatch/combine。
- JIT 首次编译、模块加载与缓存查找。
- kernel 内部的局部存储、寄存器 spill 与同步等待。

因此应分别测 `cast/layout`、`gemm`、`route/comm` 和整层时间。如果 GEMM 提速 30%，但 GEMM 只占端到端时间 20%，总收益上限远小于 30%。

## 10. 源码阅读顺序

固定快照的建议路径：

1. `deep_gemm/__init__.py`：确认实际导出接口，而非沿用旧博客的函数签名。
2. `tests/test_fp8_fp4.py`、`tests/generators.py`：查看输入 dtype、scale、形状和 reference。
3. `deep_gemm/utils/layout.py`：理解逻辑 shape 与物理 stride 的转换。
4. `deep_gemm/include/deep_gemm/layout/`、`scheduler/`：看 tile 如何分配与排列。
5. `impls/sm90_*` 与 `impls/sm100_*`：分清架构路径。
6. `tests/test_mega_moe.py`：看多进程初始化、对称 buffer 与完整测量边界。
7. `deep_gemm/testing/bench.py`：确认 warm-up、图捕获、计时和指标公式。

公开目录中同时有 legacy 和新路径。出现同名概念时应由实际 import/call 证明走了哪条路径，而不能只凭目录存在推断已启用。

## 11. 硬件与可复现边界

该快照 README 的基本要求是 NVIDIA SM90/SM100、CUDA 12.9+、PyTorch 2.3+ 和具备 C++20 `std::format` 的编译环境；各子路径还有额外条件。

RTX 3090 的 SM86 不能因为“也支持 Tensor Core”就运行这些 SM90/SM100 kernel。可以在 CPU/普通 PyTorch 上验证数学和误差模型，再在匹配硬件上执行官方测试。

这里没有安装或运行完整 DeepGEMM GPU benchmark，官方吞吐数字属于其报告条件。任何自己的测试报告都至少保留 commit、GPU、CUDA、shape、dtype、scale、alignment、warm-up、计时方式和正确性误差。

## 12. 自测与深入追问

**1. 为什么 scale 不能总在最后乘？** 因为各 K 块的 $s_A s_B$ 可能不同；先累加会丢失块级系数。本节 $D_{00}$ 的错误值 4 与正确值 10 是反例。

**2. shape 相同的 scale tensor 为什么可能被拒绝？** kernel 对 stride、对齐、打包格式和物理访问方向也有要求。shape 只描述逻辑索引域。

**3. 前向的 grouped M 与权重反向的 grouped K 有什么关系？** 前向 token 数是输出行数，权重梯度里 token 成了归约轴，矩阵排列和累积策略因此不同。

**4. 无 CPU 同步如何知道专家 token 数？** 有效计数仍存在，只是由 GPU tensor/handle 保存并被 kernel 读取。它不是“不需要计数”。

**5. Mega MoE 是否替代整个推理引擎？** 它优化一段专家层的数据流，上层仍需请求调度、KV、模型版本、采样、容错与服务协议。

**6. FP8 GEMM 比 BF16 快，整层一定更快吗？** 不一定，cast、scale、布局、padding、通信和小 shape 效率可能抵消收益。

**7. 为什么要把 first-run 和 steady-state 分开？** DeepJIT 编译、加载及缓存初始化属于冷启动；将它混入稳定态会产生不同结论，也不能完全忽略线上冷启动成本。
