## 1. 从模型数学走到可执行的 Attention

第 2 章解释 MLA、DSA 与 CSA2 的模型结构。本节进入实际算子接口：query 怎样组织，稀疏索引如何定位缓存，量化 scale 放在哪里，返回的统计量如何被后续逻辑使用。

FlashMLA 是 Attention kernel 库，不负责完整请求服务、权重下载、跨进程调度或外部 KV 存储。它的正确性依赖上层提供满足契约的输入。

本节主要核对 2026-11-07 的快照：

```text
当前：395cb3afbb331fef7b1b21e9340861b9436b42d8
官方指向的旧版本：ba89a3466e9470ad08ab39738d4e7bb66989e1e7
```

## 2. 2026-09-30 的兼容性分界

当前 README 明确说明：该次发布移除了 Hopper 与早期模型（V3/V3.2/V4.0）的对应支持，并改变 FP8/FP4 KV 格式。旧硬件、旧模型或旧格式需要使用相应旧快照。

| 项目 | 旧快照 | 本节当前快照 |
|---|---|---|
| NVIDIA路径 | 按算子支持SM90/SM100 | SM100/SM103 |
| 主要模型范围 | 不同kernel覆盖V3到V4.1的部分组合 | 聚焦V4.1 |
| KV格式 | 必须按旧版文档 | 新的528/288字节形式 |
| CUDA要求 | 基础12.8+，部分路径更高 | 13.1+，推荐13.2+ |
| PyTorch要求 | 2.0+基线 | 2.10+ |
| Ascend | 按旧版实际实现核对 | Ascend950、相应CANN/torch_npu路径 |

这张表不是说旧版任意 kernel 都支持所有旧模型，而是强调必须把“模型×硬件×kernel×cache格式×版本”作为一组条件。

## 3. 为什么 Prefill 与 Decode 需要不同组织方式

Prefill 一次处理较多 query token，计算量大；Decode 往往每请求只有一或少量 query，却要读取较长历史 KV，容易受内存带宽和并行粒度限制。

对稀疏 Attention，令每个 query 选择 k 个历史位置：

$$
O_i=\sum_{j\in\mathcal S_i}
\operatorname{softmax}_j(q_i^Tk_j/\sqrt d)\,v_j.
$$

这里的稀疏集合 $\mathcal S_i$ 已经由上游索引器决定。kernel 高效计算这个集合上的 Attention，不证明该集合相对于完整 Attention 没有模型近似误差。

精确性需要说明参照对象：对给定稀疏集合的数学结果，和对所有历史 token 的完整注意力，是两种不同目标。

## 4. Prefill 接口的 Shape 账本

固定 README 给出的稀疏前向接口使用：

| 输入 | 形状或含义 |
|---|---|
| `q` | `[s_q,h_q,d_qk]` |
| `kv` | `[s_kv,h_kv,d_qk]` |
| `indices` | `[s_q,h_kv,topk]` |
| `sm_scale` | 分数缩放标量 |
| `attn_sink` | 可选每query head的额外sink分数 |
| `topk_length` | 可选每query的有效选择数 |

当前这条 prefill API 没有独立 batch 维。多请求需要由上层组织 packed 输入和相应索引偏移，不能只给 tensor 多加一维就期待自动隔离请求。

返回包括输出、`max_logits` 与 `lse`。三者属于不同数学对象，尤其不能把最大分数当成 log-sum-exp 使用。

### 4.1 Packed 请求的索引必须隔离

两个请求分别占 KV 行 `[0,5)` 与 `[5,9)`。第二个请求的局部位置 2，在拼接后的全局 tensor 中是位置 7。

若漏加偏移，kernel 可能仍然读到有效内存，却读取第一个请求的数据。这类错误未必触发越界检查，因此要用带请求身份的确定值例子验证。

## 5. Decode 索引包含物理页地址

Decode 的 `indices` 使用形如 `[batch_size,seq_len_q,topk]` 的组织，元素已经编码为 KV cache 中的物理位置：

$$
index=physical\_block\times page\_size+offset.
$$

这与逻辑 token 编号不同。

### 5.1 一次页映射手算

假设 page size=4，一个请求的逻辑页映射为 `[2,5]`。逻辑 token `[1,4,5]` 对应：

| 逻辑token | 逻辑页 | 页内偏移 | 物理页 | 最终索引 |
|---:|---:|---:|---:|---:|
| 1 | 0 | 1 | 2 | 9 |
| 4 | 1 | 0 | 5 | 20 |
| 5 | 1 | 1 | 5 | 21 |

把 `[1,4,5]` 直接传给要求物理索引的 kernel，会得到错误结果，即便这些整数没有越界。

该稀疏路径已经在 indices 中编码物理页，所以不再通过 `block_table` 重新做同一映射；README 说明该参数仍保留为位置参数，允许按接口传 `None`。不能据此推断所有 FlashMLA 路径都不需要 block table。

## 6. FP8 与 FP4 每条缓存记录有多少字节

当前 V4.1 的 `head_dim=512`，README 描述两种记录：

### 6.1 FP8：528 字节

512 个 E4M3 数据值每个占一字节，共 512 字节；每连续 32 个值有一个 E8M0 scale，共 16 字节：

$$
512+512/32=528\text{ bytes}.
$$

RoPE 对应维度也被量化，不再因为是位置部分就自动保留 BF16。这与某些旧 MLA 缓存形式不同。

### 6.2 FP4：288 字节

512 个 E2M1 值每个四 bit，共 256 字节；每 16 个值有一个 E4M3 scale，共 32 字节：

$$
512/2+512/16=288\text{ bytes}.
$$

两个四 bit 数据放在一个字节中，偶数索引在低 nibble。存储顺序是量化原始数据在前、scale 紧接其后。

### 6.3 不能把两种记录随意互换

当前 README 对解码中的 FP4 记录还有位置约束：它用于对应 FP8 主 cache 配置下的 `extra_k_cache`。仅从末维看见 288，不能推出所有参数位置都接受纯 FP4 缓存。

上层模型可能同时管理 SWA 和压缩缓存。模型论文中的全模型平均 bytes/token，和某个 kernel 的单条缓存记录字节数，也不是同一口径。

例如第 2.9 节的 890 bytes/token 还涉及跨层共享和压缩比例，不能用 `890×层数` 或把它直接填进 `k_cache` 最后一维。

## 7. 量化值与 scale 的独立解析

E2M1 正数可表示集合为：

$$
\{0,0.5,1,1.5,2,3,4,6\}.
$$

给定一个示意字节 `0x62`，低 nibble=2，对应 1；高 nibble=6，对应 4。若该组 scale=0.5，解码的两个实数为 `[0.5,2.0]`。

```python
levels = [0.0,0.5,1.0,1.5,2.0,3.0,4.0,6.0]

def decode_e2m1(code):
    sign = -1.0 if code & 8 else 1.0
    return sign * levels[code & 7]

packed = 0x62
decoded = [decode_e2m1(packed & 15)*0.5,
           decode_e2m1(packed >> 4)*0.5]
assert decoded == [0.5,2.0]
```

这里只验证 nibble 顺序与给定 scale 的反量化。它不实现官方量化舍入、scale 编码或全部 cache layout，也不等于已执行 FlashMLA kernel。

## 8. LSE 为什么是合并分块的关键

对某个 query，令分数为 $z_j$：

$$
lse=\log\sum_j e^{z_j}.
$$

若两个分块分别返回归一化输出 $O_1,O_2$ 与 $lse_1,lse_2$，可以先计算：

$$
lse=\operatorname{logaddexp}(lse_1,lse_2),
$$

再合并：

$$
O=e^{lse_1-lse}O_1+e^{lse_2-lse}O_2.
$$

不能简单平均两块输出，因为块的概率质量可能不同。多 CTA/Split-KV 的实现可利用类似统计量，但具体调度、缓冲和归约方式要看所选 kernel。

### 8.1 返回 Shape 的转置陷阱

Decode 返回的 `out` 为 `[batch,seq_len_q,h_q,d_v]`，`lse` 为 `[batch,h_q,seq_len_q]`。后两维次序不同。

广播时只凭 shape 能凑上，可能把 query 与 head 混淆。应对每个轴建立明确标签，再做转置和扩维。

## 9. Attention sink 的数值例子

一个 sink 可以只增加 softmax 分母而不贡献普通 value。假设普通候选的未归一化权重为 1 和 3，value 为 2 和 6：

$$
O=(1\times2+3\times6)/4=5,\qquad lse=\log4.
$$

若 sink 权重为 2，结果缩放为：

$$
O'=5\times\frac4{4+2}=\frac{10}{3}.
$$

当前 prefill 接口的 sink 会改变输出缩放，但 README 明确说明不改变返回的 `lse` 与 `max_logits`。因此消费者不能假定所有返回统计量都已经包含 sink。

## 10. 空索引行是特殊契约

给无效索引填 `-1` 是常见做法；prefill 文档还允许超出 `s_kv` 的值表示无效。不要把无效位置 gather 到任意真实 token 后忘记 mask。

尤其要注意全无效行：普通 PyTorch 的全负无穷 softmax 可能产生 NaN；当前稀疏 prefill kernel 约定返回零输出、`max_logits=-inf` 和特殊的 `lse=+inf`。

这个 `+inf` 是实现的 sentinel，不是数学上空集合的标准 log-sum-exp。若后续要合并分块，必须按有效计数和该 API 的协议处理，不能把它直接当作无限概率质量。

一个正确 oracle 应分别测试正常行、部分无效行和全无效行，而不是仅用随机满长 indices。

## 11. 调度元数据的生命周期

当前 `get_mla_metadata()` 可以先返回占位对象，实际调度信息在后续 kernel 调用中生成。其作用是帮助组织 tile/split 等执行，而不是替代 token 的真实缓存索引。

复用元数据时需要保持与当前 batch、query 数、cache 几何及调用约定相容。跨请求、跨 shape 或跨版本复用的前提必须被验证，不能把一次成功调用得到的 tuple 永久当成全局常量。

CUDA Graph 等静态执行方式还要求相关地址与容量稳定。元数据内容可以变化，不代表 tensor 地址和有效范围可以任意改变。

## 12. 融合小算子的收益与代价

公开融合路径把 norm/RoPE/attention/输出逆旋转及 cast 等操作放在一条高效路径中。实际是否有 Q-norm、使用何种位置变换，应由模型版本和配置决定。

当前快照的这条融合kernel以及dense MHA forward/backward仅支持CUDA；Ascend提供的是指定稀疏prefill/decode路径。不能把仓库整体的双后端介绍理解成每一个kernel都有两个后端实现。

这种融合可以减少：

- 独立 kernel launch。
- 中间 tensor 的 HBM 写回与再读取。
- 某些格式转换和同步开销。

代价包括更严格的输入布局、预先转换的权重和更复杂的正确性验证。不能因为把操作放在一个 kernel 里，就忽略旋转方向、scale 和输出 dtype。

对照测试最好先将每一步拆开做高精度 reference，再逐步对齐融合后的结果；不应只比较最终采样文本是否“看起来合理”。

## 13. 带宽、稀疏度与性能上限

若每个 query 只访问 k 条记录，裸 KV 读取量可粗估为：

$$
V\approx B\,S_q\,k\,b_{record}.
$$

但真实访存还受多个 head 复用、物理索引局部性、缓存命中、页布局、额外 scale 和重复候选影响。

例如 k 减半不保证延迟减半：索引生成、固定启动开销和输出处理可能保持不变，稀疏访存也可能降低连续访问效率。

因此测量应分别报告索引器、TopK、KV读取与Attention核心，以及完整层的时间。DeepSelect 快了或FlashMLA快了，都不能自动代替端到端证据。

## 14. 硬件、ABI 与安装边界

当前 CUDA wheel 使用 PyTorch Stable C++ ABI 和 CPython Limited API 的约定，但仍受实际编译进二进制的 GPU 架构约束。

Ascend 路径通过 `torch_npu` 获取原生 stream，还需要相容的 PyTorch/torch_npu/CANN 组合。CUDA wheel 的复用条件不能直接套到 Ascend wheel。

RTX 3090/SM86 不属于本节当前 kernel 的目标架构；旧快照中的 SM90 也不等于 SM86。合理的本机学习范围是数学、布局与缓存地址 oracle，真实性能需在符合矩阵的硬件上测试。

官方安装过程包含寄存器 spill 检查等机制。若为了编译通过关闭检查，应记录该改动并重新测量，不能把跳过验证的产物当成与原报告同条件。

## 15. 集成验收顺序

1. 固定模型、FlashMLA及依赖版本，核对硬件。
2. 用小确定数组验证逻辑/物理索引、request边界和无效项。
3. 分别验证FP8/FP4记录的packing与scale解析。
4. 对照高精度稀疏Attention，测试sink与空行。
5. 核对out/lse轴顺序和多块合并。
6. 再启用fusion、Graph、异步和多batch布局。
7. 最后测端到端PPL、质量与延迟，不通过随意刷新golden掩盖数值变化。

## 16. 自测与参考答案

**1. 为什么当前FlashMLA不能按旧Hopper教程直接安装使用？** 2026-09-30之后的支持矩阵与KV格式有破坏性变化，应选择匹配版本。

**2. 528字节怎样得到？** 512个FP8数据字节，加每32维一个E8M0 scale的16字节。

**3. 288字节怎样得到？** 512个FP4值占256字节，加每16维一个E4M3 scale的32字节；还须满足具体cache参数位置约束。

**4. 为什么传了block_table仍可能读错页？** 稀疏路径可能要求indices已经包含物理地址，不能期待该参数替你再次映射逻辑位置。

**5. 两块输出何时可以简单平均？** 只有其softmax质量恰好相同等特殊条件；一般应使用LSE权重。

**6. 全无效行的`lse=+inf`如何理解？** 它是当前实现的特殊返回约定，不是可直接代入普通分块合并公式的概率质量。

**7. 启用attention sink后返回LSE包含sink吗？** 该prefill接口明确不包含，输出缩放和统计量要分别解释。

**8. kernel误差小是否证明整模型复现成功？** 仍需验证索引选择、量化校准、权重布局、缓存生命周期及模型质量。
