从collective布局和RDMA生命周期，延伸到NUMA、pinned memory、IO流水和checkpoint争用。

## 1. 通信先定义布局与口径

AllReduce、ReduceScatter、AllGather与AllToAll输出不同ownership。
每rank、全group、单方向与send+receive不能混算。
经典ring的α-β模型用于分辨固定延迟和字节项。
真实NCCL算法、拓扑与并发仍需测量。

## 2. 重叠与最慢路径

大bucket摊薄launch却可能晚ready。
小bucket提前通信，却增加开销和资源争用。
MoE不均匀A2A需要完整流量矩阵与最热rank。
PD/KV传输则需要请求级reservation、completion与取消。

```text
logical tensor layout
  → process group
  → rank / GPU / NIC mapping
  → transport
  → completion and visibility
  → safe buffer reuse
```

## 3. RDMA 仍然有 ownership

直接设备访问减少CPU数据搬运，不消除注册、权限和同步。
旧writer持有地址时不能立即复用目标内存。
Timeout需要配合实际数据面失效或drain条件。
网络优化同时增加inflight buffer和故障恢复复杂度。

## 4. 主机与 IO 流水

数据从存储经过读取、解压、transform、packing、pinned buffer和H2D。
线程所在CPU与页面所在NUMA node是两项事实。
更改CPU绑定不自动迁移已有页面。
多个worker和深prefetch可以增加争用与内存，而非总能提速。

Host buffer在copy完成后回收，device buffer需等最后consumer。
异步checkpoint还会占用CPU、PCIe、NIC与磁盘。
数据读取、消费与optimizer提交游标需要分开。
恢复时不能把预取游标当作已训练进度。

## 5. 动手任务

- 手算大/小Ring AllReduce的固定与带宽项。
- 比较总字节相同但接收热点不同的A2A矩阵。
- 按实际TP shard计算CP通信字节。
- 计算串行与三阶段流水的完成时间。
- 模拟H2D source buffer禁止提前复用。
- 估算workers×prefetch×batch bytes的内存峰值。

## 9. 阅读后的下一步

先画数据从源到consumer经过的完整物理路径。
为每段标记node、CPU、内存、GPU、NIC或存储。
再为每个buffer写明最后读写事件与回收者。
选择小消息、较大payload和并发干扰三种负载。
同时保存latency、bandwidth、inflight bytes和最慢rank。
这比只抄一条通信或NUMA命令更容易定位问题。

选择一个真实瓶颈，写出可证伪假设与最小实验。
先确认有效工作和正确性，再衡量关键路径变化。
出现与预测不同的结果时，保留失败并修正模型。
完成时交付可复跑数据、条件与回退，而不是孤立的最佳数字。
