## 时间线告诉你哪段重要，微架构解释它为何如此

先从系统trace选出热点，再研究它的实际地址和指令。
本节不重复推理指标，而是把kernel从源码表达式拆到内存事务、线程协作和资源约束。
训练的norm/optimizer和推理的norm/sampling可以使用同一套分析方法。
它们的shape与调用频率仍需分别测量。

所有地址和资源数字为教学模型。
真实bank宽度、sector、寄存器分配粒度和指令支持需按目标架构确认。
CPU算例不代表已经采集过GPU counters。

## 1. Grid、block、warp 与 SM

Kernel启动一个grid，其中包含多个thread blocks。
一个block在其执行期间驻留于一个SM，threads以warp为基本调度单位组织。
多个blocks/warps是否能同时驻留，受线程数、寄存器、shared memory和架构上限限制。
普通block内barrier不能同步整个grid。

| 层 | 典型资源/作用 |
|---|---|
| thread | registers、局部执行状态 |
| warp | 指令发射、active mask |
| block | shared memory、block barrier |
| SM | 多个驻留block/warp与执行单元 |
| GPU | L2、显存、copy与互联资源 |

编程模型的local memory是线程私有地址空间。
它不是保证位于低延迟片上存储。
寄存器spill往往通过device memory/cache层次访问。

## 2. Coalescing 要画每个 lane 的地址

设32个lane各读取一个FP32，即4字节。
连续访问：

$$
addr(lane)=base+4\cdot lane.
$$

若base对齐到32字节sector，这128字节落在4个sector。
Stride=8个元素时：

$$
addr(lane)=base+32\cdot lane.
$$

每lane落在不同sector，需要32个sector覆盖同样128字节有效数据。
简化事务效率从100%降到12.5%。
实际cache line、指令合并和重放还会改变观测，模型只用于定位地址问题。

### 2.1 向量类型不是充分条件

`float4`只有在对齐、连续布局和编译器生成相应指令时才有预期效果。
AoS字段访问、错位base或大stride仍可能产生大量事务。
改变lane映射常比单纯改类型更重要。
最后用实际load/store sectors与字节验证。

## 3. Shared memory bank 的教学模型

假设32个bank，每bank按4字节word映射：

$$
bank(addr)=(addr/4)\bmod32.
$$

一个32×32 FP32 tile按行存储。
同一列的第lane行地址word为 $32\cdot lane+col$。
所有lane映射到同一个bank。
如果读取不同地址，就会形成冲突；broadcast等特殊情况需另辨。

将行stride改为33，bank变为：

$$
(33\cdot lane+col)\bmod32=(lane+col)\bmod32.
$$

每lane落入不同bank。
这解释了经典padding思路。
但padding增加shared占用，可能降低驻留block数量，不能保证全局更快。

## 4. 可运行的地址与 bank 检查

```python
from collections import Counter

def sectors(stride_elements, base=0, sector_bytes=32):
    return { (base+4*lane*stride_elements)//sector_bytes
             for lane in range(32) }

assert len(sectors(1)) == 4
assert len(sectors(8)) == 32
assert len(sectors(1,base=4)) == 5
print("sectors",len(sectors(1)),len(sectors(8)),len(sectors(1,4)))

def bank_hist(row_stride_words, column=0):
    return Counter((lane*row_stride_words+column)%32 for lane in range(32))

bad = bank_hist(32)
good = bank_hist(33)
assert max(bad.values()) == 32
assert max(good.values()) == 1
print("max lanes per bank",max(bad.values()),max(good.values()))

useful = 32*4
for stride in [1,8]:
    actual_model = len(sectors(stride))*32
    print("stride",stride,"modeled efficiency",useful/actual_model)
```

代码没有模拟实际GPU指令分解、多周期宽访问或broadcast。
它用于手算第一层地址证据。
真实结论必须回到目标架构profiler。

## 5. 寄存器、shared 与 occupancy 的约束

假设某教学SM可提供65536个32-bit寄存器。
每block 256线程，每线程64寄存器：

$$
R_{block}=256\times64=16384.
$$

仅按寄存器上限，最多可放4个block。
若每线程增加到96寄存器，每block24576，最多2个block。
真实分配存在粒度和其他上限，所以这只是资源筛选近似。

同时还需检查shared bytes、线程数、block数和架构限制。
降低寄存器不一定更快，因为可能增加spill或降低ILP/reuse。
目标不是最大occupancy，而是最短正确执行时间。

## 6. GEMM 的三层 tile

```text
CTA/block tile
  global → shared，跨多个warp复用

warp tile
  warps分工消费局部矩阵片段

instruction tile
  MMA/Tensor Core实际操作形状
```

大CTA tile提高复用，但占用更多shared/register。
小tile提高可调度粒度，但可能重复加载和增加边缘浪费。
Skinny-M的MoE专家或decode不应直接套大训练GEMM的tile。
Tile选择必须随shape分布而不是单一方阵峰值决定。

### 6.1 Epilogue 的成本

GEMM后还可能有bias、activation、cast、quant和residual。
融合epilogue可省中间写回与launch。
但也会改变寄存器存活区间、layout和可用vendor kernel。
需要比较完整算子路径，而不是只看mainloop TFLOPS。

## 7. 异步搬运的双缓冲

最简单的流水：

```text
load tile 0
compute tile 0 + load tile 1
compute tile 1 + load tile 2
...
compute final tile
```

生产者不能覆盖消费者仍在读的buffer。
消费者不能在数据ready前开始计算。
需要明确每stage的empty、filling、ready、consuming状态和同步事件。

`cp.async`、TMA、WGMMA和其他原语有架构范围。
一般生产者/消费者思想可以迁移，具体指令不能跨架构照搬。
SM86实验不等于Hopper/Blackwell路径验证。

## 8. 同步原语不能互相替代

| 原语 | 主要保证 | 不自动保证 |
|---|---|---|
| block barrier | 参与线程在block边界同步 | 全grid同步 |
| warp sync | 指定参与lane同步 | 任意其他warp完成 |
| memory fence | 指定内存顺序/可见性语义 | 其他线程已到达 |
| atomic | 单位置RMW原子性 | 整个数据结构事务 |
| stream event | 设备执行依赖 | CPU已等待完成 |

存在分支时，参与barrier的线程集合必须合法。
错误地让部分线程提前return、其他线程等待，会造成hang或未定义行为。
跨block规约通常需要多kernel、cooperative机制或其他受支持方案。
不能用普通`__syncthreads()`完成全grid同步。

## 9. NCU 计数器如何形成假设

| 证据组合 | 候选解释 | 进一步验证 |
|---|---|---|
| sectors多、useful bytes少 | 未合并或错位访问 | 画lane地址 |
| local load/store多 | spill或局部数组 | 编译报告、live range |
| bank冲突高 | shared布局不合适 | stride/padding/swizzle |
| tensor pipe低 | shape、fallback、依赖 | 实际指令与tile |
| eligible warps少 | 长依赖或资源不足 | stall与occupancy |
| DRAM低且kernel慢 | 不一定带宽受限 | compute、指令、同步 |

一个counter不能单独确诊。
例如DRAM低可能因为cache好，也可能因为计算瓶颈，或根本没有足够并行。
应同时查看实际时间、指令和内存层次。
Profiler版本与GPU会改变可用metric名称，不宜永久固定一组名字。

## 10. 五种实现路线如何选择

| 路线 | 适合 | 主要成本 |
|---|---|---|
| Vendor/framework kernel | 语义与shape已覆盖 | 定制空间有限 |
| Triton | 快速表达tile、reduction、fusion | JIT、shape与架构特化 |
| CUDA/C++ | 细粒度同步、底层与新硬件 | 开发和维护复杂度 |
| CUTLASS/CuTe | GEMM布局、MMA、pipeline | 抽象学习与版本依赖 |
| TileLang | tile级算法与调度表达 | 编译器/target支持核验 |

选择不应按“越底层越快”排序。
先看现成实现能否满足语义，再评估热点是否值得定制。
不同语言都需要实际生成代码和counter验证。

### 10.1 TileLang 与 CuTe 不能只看语法对比

二者的tile、layout、pipeline表达服务于不同抽象层与编译路径。
学习时用同一GEMM/RMSNorm语义、相同shape与硬件对比。
记录是否自动推导layout、采用何种MMA与共享内存安排。
不要从代码更短推断kernel更快。

动态文档中出现某target，也不代表当前安装环境能编译或运行全部路径。
实际版本、依赖与架构矩阵需随产物保存。
本节不安装或变更任何工具链。

## 11. 一个训练/推理共用的融合反例

Residual加RMSNorm可合并中间读写。
训练还要保存反向所需状态，推理通常没有同样的backward保存需求。
同一forward融合在训练中可能增加activation或改变backward效率。
因此不能只用推理forward测量推导训练step收益。

若fusion让register从64升到96，驻留block可能下降。
如果同时出现spill，额外流量可能抵消省掉的中间tensor。
验收应测forward、backward、峰值内存和完整step。

## 12. 实验应交付什么

```text
semantic contract
  shape/stride/dtype/mask/aliasing
reference
  random + boundary + adversarial
compiler artifact
  register/shared/spill + generated code
microbenchmark
  warmup/repeats + representative distribution
system integration
  actual dispatch + critical path + regression
```

PTX展示虚拟ISA意图，SASS展示目标设备机器指令。
两者都要和实际执行路径关联。
某文件里出现MMA字符串，不证明运行时热点使用它。
测量还需防止输入被理想cache条件过度复用。

## 13. 六道追问与答案

### Q1：为什么连续FP32访问通常比stride大访问高效？

同一warp的有效字节落入更少sector/事务。
大stride会放大实际搬运字节。
仍需考虑对齐、cache与具体指令。

### Q2：shared padding解决冲突后是否一定更快？

不一定。
它增加shared容量与地址计算，可能减少驻留block。
要看减少的冲突是否超过新增代价。

### Q3：为什么限制寄存器可能变慢？

编译器可能把值spill到device memory，或增加重算。
ILP与数据复用也可能下降。
应比较编译报告、counter和时间。

### Q4：Tensor输入是FP16，是否必然使用Tensor Core？

还需硬件、kernel、shape、layout和对齐支持。
实际选择可能fallback。
看launched kernel和机器指令，不只看dtype。

### Q5：训练kernel与推理kernel能共用验证吗？

可共用部分forward reference，但训练还需backward、保存状态和数值稳定性。
完整step的内存和通信也不同。
应按目标路径分别验收。

### Q6：选择Triton还是CUDA的首要依据？

语义、硬件覆盖、可表达的同步/布局、维护与性能证据。
先用低成本方式验证收益，再决定是否投入更底层实现。
语言名字本身不构成速度证据。

## 14. 来源与边界

### 用一个融合字节账检查优化动机

设长度N的FP32向量需要先做residual加法，再做norm。
不融合的第一步读x和residual，写中间z，共12N字节。
第二步至少读z和weight、写y，共12N字节。
忽略reduction额外读取和cache后，总逻辑流量约24N字节。

理想融合路径读x、residual、weight，写y，约16N字节。
因此可消除的逻辑流量是8N字节，约原模型的三分之一。
取N=2^20，对应从24MiB降到16MiB。
如果实际HBM流量没有相应下降，可能中间z本来就在cache，或融合引入spill。
这个字节账是预测，计数器用于证伪它。

训练还需考虑保存z或r供backward使用。
若必须写回其中一个状态，实际节省会变小。
这也是为什么forward与完整训练step需分开测。

### 从源码到指令的核验顺序

1. 确认调用的实际kernel，不只看registry。
2. 查看编译器报告的register/shared/spill。
3. 查看PTX或中间IR的访存和计算意图。
4. 必要时查看SASS确认目标设备指令。
5. 用NCU确认该路径实际执行和主要瓶颈。
6. 回到无profiler计时与端到端结果。

任何一层不一致都可能解释“代码看起来优化了却没收益”。
生成代码只能证明实现方式，不能单独证明性能。

对应推理宝典KERN-001—026、CODE-013—017。
训练综述第8.2、8.3节；Megatron报告的TE/算子与性能证据边界。
