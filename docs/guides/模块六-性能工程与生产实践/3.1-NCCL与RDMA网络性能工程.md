## 通信优化从“谁需要什么数据”开始

训练梯度同步、TP输出、CP上下文、MoE路由和PD交接都涉及网络。
但它们的语义、粒度和生命周期不同。
先确定张量布局与consumer，再选择collective或transfer。
不能因为某库更快，就用错误的通信语义替代原操作。

本节公式采用明确的每rank单方向逻辑payload口径。
算法模型用于估计和反证，不替代实际NCCL选择与拓扑测量。
CPU代码不启动通信组或修改网络配置。

## 1. 四个常见 collective

| 操作 | 输入 | 输出 | 典型用途 |
|---|---|---|---|
| AllReduce | 各rank完整局部贡献 | 所有rank得完整规约结果 | 梯度、row-TP |
| ReduceScatter | 各rank完整贡献 | 各rank得不同规约分片 | 分片optimizer |
| AllGather | 各rank不同分片 | 所有rank得完整拼接 | 参数/activation |
| AllToAll | 每rank给各目标不同块 | 收到各来源给自己的块 | EP、sequence-head交换 |

如果后继算子只需shard，RS比AR后再切更符合ownership。
AG的输出顺序由rank顺序决定，改变rank mapping可能改变数据布局。
所有参与者的调用顺序、count与dtype必须符合接口契约。
其中一个rank进入不同操作，会造成hang或数据错误。

## 2. 统一字节口径

报告一个“通信量”之前先写：

```text
per rank or whole group
sent or received or send+receive
logical payload or physical hop-bytes
one layer or one step
input size or final gathered size
```

例如Ring AllReduce的每rank发送与接收可同时发生。
时间式不能因为同时有send与receive就机械再乘2。
跨交换机的hop-bytes还取决于实际路由，不等于逻辑payload。

## 3. Ring 的 α-β 模型

设group大小为 $q$，完整逻辑tensor为 $n$ bytes。
$\alpha$ 是每phase固定延迟，$\beta$ 是seconds/byte。
经典ring模型为：

$$
T_{AG}\approx(q-1)\alpha+\frac{q-1}{q}n\beta,
$$

$$
T_{RS}\approx(q-1)\alpha+\frac{q-1}{q}n\beta,
$$

$$
T_{AR}\approx2(q-1)\alpha+2\frac{q-1}{q}n\beta.
$$

AG的$n$是最终完整输出，不是每rank初始shard。
RS的$n$是每rank完整输入。
AR的输入输出均为$n$。
若混淆这些定义，会得到相差group size的错误结果。

## 4. 大小消息的完整数例

取 $q=8$、每phase $\alpha=5\ \mu s$、有效带宽50GB/s。
对$n=1GB$的AR：

$$
V_{sent}=2\frac78\times1GB=1.75GB.
$$

带宽项为35ms，固定项70μs，总计约35.07ms。
对$n=4KiB$：

$$
V_{sent}=7168bytes,
\quad T\approx70\mu s+0.14336\mu s.
$$

小消息主要由固定延迟主导。
这解释了为什么TP decode频繁小collective可能对延迟特别敏感。
真实NCCL可能选tree、NVLS或其他算法，不能把ring式写成通用实测预测。

## 5. 算法带宽与总线带宽

某些通信benchmark同时报告algorithm bandwidth与bus bandwidth。
前者常以逻辑tensor大小除时间，后者按collective流量模型调整。
具体定义要读工具版本，不能把busBW直接与网卡payload速率等同。

同一AR在不同group size下，校正因子不同。
训练报告若混用两种带宽，会让扩展效率看起来异常。
最终服务时间还包括rank ready偏差，而独立benchmark可能没有这种等待。

## 6. Bucket 大小的双重效应

训练梯度bucket大，可以摊薄固定开销并提高大消息效率。
但要等更多梯度ready后才能发，减少可重叠窗口。
小bucket更早启动，却增加launch、metadata和通信计算争用。

```text
large bucket:
  late ready → one large collective → exposed tail

small buckets:
  early ready → several collectives overlapped with later backward
```

应测bucket ready→start、collective持续时间和最后不可隐藏尾部。
还要测GEMM是否因NCCL占SM/HBM而变慢。
只看通信时间下降不足以证明step缩短。

## 7. DistOpt 的 RS→update→AG

Megatron固定参考的普通Distributed Optimizer先RS梯度，再本地更新拥有的参数片段，再AG计算参数。
RS+AG的经典ring字节量与AR同阶。
核心收益是状态分片与时序可重叠，不是通信自动减半。

`overlap_param_gather`要求consumer在使用权重前等待相应bucket。
提前调用模块或不同rank顺序不一致，会破坏这一契约。
训练的optimizer state ownership与推理常驻权重复制不能混算。
这里按参考报告冻结snapshot解释，不倒灌stable0.19的新路径。

## 8. RDMA 省掉什么，没有省掉什么

RDMA允许网络设备对已注册区域进行直接访问，减少远端CPU参与数据搬运。
GPUDirect RDMA可让支持的NIC路径访问GPU内存。
仍需要地址注册、权限、连接/队列、完成事件和内存生命周期。
硬件、PCIe拓扑、IOMMU/ACS与驱动配置影响是否可用和实际路径。

```text
register / expose memory
  → exchange address and access metadata
  → submit operation
  → transport completion
  → consumer visibility / synchronization
  → retire registration and buffer
```

“one-sided”不等于没有同步。
远端不执行CPU拷贝，也不代表可以随时释放目标页面。
取消需要保证旧writer无法继续写入复用地址。

## 9. 物理拓扑与 rank 放置

```text
GPU SM/HBM
  → NVLink/NVSwitch or PCIe
  → NIC local path
  → leaf/spine/rail
  → peer NIC
  → peer GPU
```

TP通常偏好低延迟高带宽域。
PP较少发送较规则activation，但受stage平衡影响。
EP是稀疏不均匀路由矩阵，最热rank和最慢link很重要。
CP还需考虑ring/AllToAll的布局与mask负载。

这些是设计起点，不是固定部署规则。
每个rank应记录GPU UUID、node、NIC与NUMA。
仅设置一个网络接口变量不能证明实际数据路径正确。

## 10. 不规则 A2A 的矩阵视角

设 $M_{ij}$ 是rank i发送到j的字节。
总流量是 $\sum_{ij}M_{ij}$。
但每rank发送、接收峰值分别为行和、列和的最大值。
跨节点流量还需按物理mapping筛选。

两组矩阵即使总字节相同，也可能一组均衡、一组全部汇到单rank。
因此MoE不能只报平均带宽。
需要route histogram、recv tokens、dispatch/GEMM/combine逐阶段时间。
专家迁移也会暂时占用同一网络。

## 11. 可运行的通信模型

```python
def ring_ar(nbytes, ranks, bandwidth, alpha):
    sent = 2*(ranks-1)/ranks*nbytes
    seconds = 2*(ranks-1)*alpha + sent/bandwidth
    return sent, seconds

large = ring_ar(1e9,8,50e9,5e-6)
small = ring_ar(4096,8,50e9,5e-6)
assert large[0] == 1.75e9
assert abs(large[1]*1000-35.07) < 1e-9
assert abs(small[1]*1e6-70.14336) < 1e-9
print("large_ms",large[1]*1000,"small_us",small[1]*1e6)

uniform = [[0,10,10,10],[10,0,10,10],[10,10,0,10],[10,10,10,0]]
hot = [[0,0,0,30],[0,0,0,30],[0,0,0,30],[10,10,10,0]]
def summary(matrix):
    sends = [sum(row) for row in matrix]
    receives = [sum(row[j] for row in matrix) for j in range(len(matrix))]
    return sum(sends),max(sends),max(receives)
assert summary(uniform) == (120,30,30)
assert summary(hot) == (120,30,90)
print("uniform",summary(uniform),"hot",summary(hot))
```

矩阵单位可理解为MiB，示例只比较分布。
它没有模拟switch拥塞、协议、并发或GPU计算。
真实带宽需要实际拓扑和目标message分布测量。

## 12. 四层基准矩阵

| 层 | 目的 |
|---|---|
| 单链路 | 验证基本GPU/NIC/PCIe路径 |
| 单节点collective | 检查机内拓扑与rank mapping |
| 全域collective | 观察跨节点规模与算法 |
| 应用pattern replay | 复现小/大消息、依赖与并发 |

最后一层尤其重要。
独立大AR带宽很好，不保证TP小消息或EP不均匀A2A好。
训练的bucket ready偏差、推理的burst也不会出现在单一microbenchmark里。
保存所有rank的开始与结束时间。

## 13. 排错先于调参

1. 核对group、rank、device与调用序号。
2. 查更早的OOM、kernel fault或CPU阻塞。
3. 固定小tensor与小world复现。
4. 确认NIC、NUMA、shared memory与实际transport。
5. 检查网络错误、拥塞和链路速率。
6. 最后单变量比较算法/通道/环境设置。

不要把一组未经解释的NCCL环境变量当万能修复。
某版本有效的参数可能在另一版本改变语义或已不适用。
应保存默认基线、变更理由、前后结果与回退。

## 14. 传输生命周期的性能代价

更深的inflight队列可以提高带宽利用。
它也增加注册内存、buffer占用和取消drain时间。
训练prefetch太深可能放大activation/parameter峰值。
PD预分配太早可能让D等待期间占住KV。

因此通信优化同时是内存与生命周期优化。
为每个buffer写清producer、consumer、最后访问事件和回收点。
不满足安全契约的“更快释放”不是有效优化。

## 15. 六道追问与答案

### Q1：为什么RS+AG不等于通信减半？

在经典ring同口径下，两者合计与AR同阶。
收益是中间shard ownership和可重叠时序。
不同dtype、拓扑与算法会改变实际时间。

### Q2：大消息带宽高，为什么decode仍慢？

Decode可能频繁发送小collective，固定延迟占主导。
还可能被最慢rank与CPU调度限制。
应使用目标message分布。

### Q3：RDMA是否不需要远端协调？

仍需注册、权限、地址与完成/可见性协议。
远端CPU不参与数据拷贝，不等于没有ownership。
取消与重启尤其需要fencing。

### Q4：同样总A2A字节为何尾部不同？

目标分布、rank负载和瓶颈链路不同。
最大列和可能远高于均值。
需要完整流量矩阵与逐rank阶段时间。

### Q5：overlap开关为什么可能降低性能？

通信与计算共享SM/HBM或缺少独立窗口。
额外buffer/event与调度也有开销。
应测关键路径而不是仅看两条stream重叠。

### Q6：collective timeout首先查什么？

先查全rank调用与更早错误。
有人未到场就会让其他人等待。
网络检查重要，但不能跳过控制流一致性。

## 16. 来源与版本

### CP 通信再算一遍实际 shard

CP group通常固定TP坐标，因此不能直接使用模型全局KV宽度。
设本TP rank实际持有的K或V宽度为 $H_{KV,r}$，CP大小为C。
每rank本地K+V字节为：

$$
n_{local}=2B\frac{S}{C}H_{KV,r}b.
$$

均匀ring forward需要接收其他C-1份shard：

$$
n_{remote-recv}=n_{local}(C-1).
$$

取B=1、S=32768、C=4、$H_{KV,r}=256$、b=2。
本地K+V为8MiB，远端单方向接收约24MiB。
发送同阶；如果报告send+receive才再加另一方向。
这个例子不直接适用于AllGather或sequence-to-head A2A。

若GQA heads少于TP并出现复制，$H_{KV,r}$必须包含实际复制。
Backward的dK/dV通信也需按具体协议展开，不能直接宣称与forward完全相等。
这能避免把训练/推理或不同CP实现的通信量混算。
