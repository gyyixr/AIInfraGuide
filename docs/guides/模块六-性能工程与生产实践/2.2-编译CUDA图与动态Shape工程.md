## 编译快不快，取决于捕获范围与实际请求分布

训练常有重复step，但也可能存在变长packing、MoE动态shape和条件分支。
推理每轮batch、context和请求组成变化更频繁。
编译器和CUDA Graph可以减少开销，也可能增加specialization、padding和内存。
本节将这些成本放进同一生命周期模型。

官方资料核验于2026-11-07。
PyTorch动态文档/API会变化，示例配置必须按实际安装版本重查。
本节CPU模型不调用torch，也不声称已经运行compile或graph。

## 1. 三种“图”不是同一个对象

| 层 | 表示什么 | 主要作用 |
|---|---|---|
| PyTorch计算图/IR | Tensor操作与依赖 | 分析、变换、融合 |
| 编译后执行代码 | kernel与调用代码 | 执行优化后的计算 |
| CUDA Graph | GPU操作与执行依赖 | 低开销重复提交 |

torch.compile可以生成或组合多个kernel。
CUDA Graph通常复用已确定的执行结构，并不自动把多个kernel融合成一个。
两者可以一起使用，也可以独立启用。
“图捕获成功”需说明捕获的是哪一层。

## 2. Graph break 的含义

编译前端遇到无法纳入当前图的代码时，可能结束当前图、回到Python处理，再继续捕获后续部分。
常见触发涉及数据依赖控制流、某些Python副作用、不支持操作与直接读取tensor数据。
具体行为受版本、设置和fullgraph策略影响。
不能把某个函数永远列为“必然graph break”，也不能假设所有Python都能捕获。

```text
captured segment A
  → Python / unsupported boundary
  → captured segment B
```

Break本身不一定是bug。
一个低频日志或复杂控制分支留在Python可能更合理。
但热路径频繁break会增加调用、同步和优化边界。

### 2.1 数据依赖与shape依赖不同

`if x.shape[0] > 128`根据形状选择路径。
`if x.sum() > 0`根据tensor内容选择路径。
前者可能通过shape guards/specialization处理，后者通常需要受支持的控制流表达或离开当前图。
具体能否捕获应看版本日志和实际IR。

## 3. Guard 保护编译假设

编译结果可能依赖shape、stride、dtype、device、Python常量或对象状态。
Guard在后续调用检查这些假设是否仍成立。
失败时可能选择已有其他specialization、重新编译或fallback。

```text
input
  → evaluate guards
  → matching compiled variant?
       yes: execute
       no: specialize/compile/fallback
```

Guard不是多余检查。
删除不成立的guard会让错误的编译代码处理不兼容输入。
优化应减少不必要specialization，而不是绕过正确性条件。

## 4. 动态 shape 不是“以后永不编译”

Symbolic dimensions可以让多个形状共享一份图。
但分支、内存布局、backend条件或优化仍可能引入范围约束。
有些维度动态，有些维度仍需specialize。
动态rank、数据依赖输出大小和普通尺寸变化也不是同一类问题。

使用`dynamic=True/False/None`等配置前，应查本机API。
先记录recompile原因，再决定哪些维度值得动态化。
盲目把所有维度都动态化，可能让优化机会减少或增加复杂度。

### 4.1 调试入口

PyTorch官方提供guards、recompiles、graph_breaks、dynamic等日志方向。
常见命令形状是：

```bash
TORCH_LOGS="graph_breaks,recompiles" python your_reproducer.py
```

这条命令需先用当前PyTorch的日志帮助核对可用名称。
日志收集应面向短复现，不长期对生产全流量打开高量输出。
保存真正导致break/guard失败的代码位置与输入。

## 5. Shape bucket 的收益与浪费

将不同请求形状映射到有限bucket，可降低编译和capture变体数。
代价是padding、mask、额外显存和可能不理想的kernel形状。

```text
actual tokens: 17, 24, 31, 33
buckets:      32, 32, 32, 64
```

有效token总数105，执行桶总数160。
按token计的padding放大为160/105≈1.524。
这不直接等于时间放大，因为tile效率与launch开销同时变化。
但它是必须报告的工作量差异。

### 5.1 不能只优化最常见shape

低频长shape可能决定p99或显存峰值。
大量长尾shape又可能造成编译cache churn。
可以为高频shape预编译，长尾走受支持的动态或eager路径。
具体边界需用真实分布与冷启动成本选择。

## 6. 编译成本的回本次数

设额外编译/capture成本为 $C$，每次节省 $\Delta t$：

$$
n_{break-even}=C/\Delta t.
$$

如果额外花120秒，每次只省0.2ms，需要60万次调用才摊平。
训练长作业可能足够，短评测或低流量模型可能不够。
升级、重启或shape变化导致cache失效，还会重新支付这笔成本。

最好分别报告cold total、steady-state与预计生命周期总成本。
不能只展示warm benchmark。

## 7. CUDA Graph 的地址契约

普通PyTorch capture/replay路径依赖捕获时的虚拟地址。
新数据通常copy进长期持有的static input，再replay，再读取static output。
如果把Python变量重新绑定到新tensor，graph不一定改用新地址。
这与“更新同一buffer内容”不同。

```text
safe conceptual pattern:
  static_input contents ← new data
  replay captured operations
  consume static_output

unsafe assumption:
  static_input = another allocation
  assume captured graph automatically follows Python name
```

CUDA底层有graph更新等机制，但它们有各自约束。
不能以存在更新API为理由，忽略所用框架capture路径的固定地址契约。

## 8. Graph-private pool 与峰值内存

PyTorch为capture分配的内存具有graph相关生命周期。
图对象和相关tensor仍存活时，地址不能被任意复用。
多个capture默认可能保留各自pool，增加显存占用。

共享pool只在受支持的执行顺序与非并发条件下安全。
不能因为两图“看起来不会同时用”就手工释放它们依赖的buffer。
需要通过明确的调用顺序和资源owner证明。

训练中的activation与optimizer workspace、推理中的KV都会与graph pools争显存。
Graph减少host时间，却可能因挤压KV导致更多抢占。
应评估整个系统，而不只测replay launch。

## 9. 多 stream capture 的依赖

跨stream工作仍需event建立正确顺序。
Capture不自动发现数据依赖并替你同步。
写入新输入前，应确保上一轮读者已经完成。
读取或覆盖output前，同样需要确认replay完成。

```text
copy stream writes input
  → event
compute stream replays graph
  → event
consumer reads output
```

异步host返回不表示device完成。
取消和模型卸载时，要等待依赖graph的所有工作退出。
这与KV传输的retirement思想一致。

## 10. 可运行的 bucket 与地址生命周期模型

```python
shapes = [17,24,31,33]
buckets = [16,32,64]
chosen = [next(b for b in buckets if b >= n) for n in shapes]
assert chosen == [32,32,32,64]
assert sum(shapes) == 105 and sum(chosen) == 160
print("padding_factor",sum(chosen)/sum(shapes))

compile_seconds = 120
saved_seconds = 0.0002
assert compile_seconds/saved_seconds == 600000
print("break_even_calls",int(compile_seconds/saved_seconds))

class Buffer:
    def __init__(self, value):
        self.value = value
        self.alive = True

class Captured:
    def __init__(self, buffer):
        self.buffer = buffer
    def replay(self):
        assert self.buffer.alive
        return self.buffer.value*2

static = Buffer(3)
graph = Captured(static)
assert graph.replay() == 6
new = Buffer(8)
static = new  # 仅改变变量绑定，不改变graph持有对象。
assert graph.replay() == 6
graph.buffer.value = 8
assert graph.replay() == 16
print("captured resource identity preserved")
```

Python对象模拟地址owner，不模拟CUDA Graph底层功能。
它只说明名称绑定与被捕获资源身份不同。
真实安全还需要stream/event和allocator契约。

## 11. 训练与推理的不同动态性

| 动态来源 | 训练关注 | 推理关注 |
|---|---|---|
| sequence length | packing、loss mask、CP | context、chunk、KV |
| batch变化 | microbatch/GBS schedule | continuous batching |
| MoE路由 | forward/backward、A2A | 小decode、专家长尾 |
| 控制流 | optimizer skip、checkpoint | cancel、stop、spec accept |
| 状态更新 | grad/param ownership | accepted/computed progress |

训练step的完整capture需要处理optimizer和collective的支持条件。
推理graph通常围绕有限形状的执行片段。
不能把一个模式的capture成功推广到另一个模式。
所有rank的collective顺序仍需一致。

## 12. 优化前后应记录

- 首次编译和capture时间。
- 编译变体数与cache大小。
- guard失败、recompile与graph break原因。
- actual/ padded token或元素数。
- graph hit与eager fallback比例。
- CPU提交时间和GPU实际计算时间。
- graph pool、workspace与KV/activation峰值。
- correctness、质量、故障与生命周期结果。

收益归因要区分codegen优化、launch减少和shape重排。
同时开启多个变化时，需要消融。
复现问题时保留最小输入、版本、日志和生成代码。

## 13. 性能反例

长GEMM本来占满关键路径，host launch只占1%，graph几乎没有可消除空间。
高离散shape不断产生新specialization，编译时间主导短任务。
Graph bucket padding使小请求计算膨胀，抵消提交收益。
Graph pools挤压KV，引擎更多preempt/recompute。

这些现象不说明编译或graph“无用”。
它们说明适用域应由工作负载和资源约束定义。
可以调整bucket、缩小capture范围或为长尾保留eager。

## 14. 六道追问与答案

### Q1：torch.compile是否等于CUDA Graph？

不等于。
前者捕获与优化计算，后者复用GPU执行提交。
两者可组合，但收益来源与约束不同。

### Q2：Graph break一定需要消除吗？

不一定。
低频或不适合捕获的控制逻辑保留在Python可能更稳。
重点是热路径的开销与优化边界。

### Q3：dynamic shape为什么还会recompile？

某些guard、分支和backend要求仍需specialization。
动态维度不等于所有输入性质都动态。
应查看真实guard失败原因。

### Q4：换一个同shape tensor为何不等于更新graph输入？

普通capture记录的是资源地址与操作。
Python变量重绑定不自动修改捕获地址。
通常应copy到长期持有的static buffer。

### Q5：共享graph pool为什么有并发风险？

不同图可能复用同一地址作为临时或输出存储。
并发replay或错误顺序可能互相覆盖。
需要遵守框架支持的顺序与生命周期。

### Q6：如何判断编译值得？

比较额外编译成本、每次收益、调用次数和cache失效周期。
同时检查padding、内存和tail。
不能只看steady-state最优一轮。

## 15. 来源与版本范围

### Graph pools 与 KV 的容量数例

假设GPU可分配预算为24GiB，权重和基础runtime占14GiB。
原来留给KV与其他动态状态10GiB。
若新增四个graph bucket各保留0.75GiB独立空间，额外占3GiB。
在不共享且其他条件不变的模型中，动态余量降到7GiB。

若标准GQA每token为128KiB，少掉的3GiB相当于24576个token槽。
这可能降低可接受并发，或增加抢占。
即使每次replay节省host时间，整个服务goodput仍可能下降。
实际bucket pool未必线性相加，应测allocator和graph实际存活对象。

这类容量变化应进入编译方案的发布门禁。
释放graph时也不能只删除一个Python名称，仍需确认相关tensor、工作和对象生命周期。

### 兼容性矩阵需要包含动态路径

| 条件 | 至少检查 |
|---|---|
| 新shape | guard/recompile/fallback |
| 新dtype | kernel与scale配置 |
| 不同stride | 编译假设与地址访问 |
| 模型更新 | captured权重/metadata身份 |
| 并发replay | pool共享与buffer覆盖 |
| 异常/取消 | 最后访问事件与清理 |
| 多rank | collective捕获与顺序 |

静态示例成功，只覆盖矩阵中的一个点。
部署应根据真实工作负载扩大验证，而不是默认全部兼容。

对应推理宝典KERN-017/018/027/028、训练综述8.3/8.5。
Megatron报告模块A/C强调overlap与buffer生命周期，不能仅复制布尔开关。

- [PyTorch Common Graph Breaks](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/compile/programming_model.common_graph_breaks.html)：移动主线文档，具体支持随版本变化。
- [PyTorch Dynamic Shapes](https://docs.pytorch.org/docs/main/user_guide/torch_compiler/torch.compiler_dynamic_shapes.html)：symbolic shape与guard边界。
- [PyTorch CUDA semantics 2.15](https://docs.pytorch.org/docs/2.15/notes/cuda.html)：capture、static buffers和graph pool语义。
