## GPU 等待数据时，瓶颈可能在主机链路的任何一段

训练读取样本、解压、tokenize、packing，再把数据送到GPU。
推理处理模板、多模态输入、权重加载和KV恢复，也有相似主机路径。
远端存储带宽足够，不代表CPU解析、NUMA或H2D能跟上。
因此要沿数据的实际存放位置和owner分析。

本节只读介绍拓扑检查，不修改用户CPU绑定或GPU状态。
CPU模拟验证流水时间与buffer所有权，不执行真实异步磁盘或CUDA操作。

## 1. 完整输入流水

```text
remote store / local NVMe
  → read buffer
  → decompress / parse
  → tokenize / transform
  → pack / collate
  → pinned host buffer
  → H2D copy
  → GPU consume
```

每个阶段都有吞吐、固定延迟、CPU/内存需求和失败路径。
只加DataLoader workers可能让磁盘seek、CPU争用和内存复制更严重。
应先分阶段计时，再决定并行哪个阶段。

## 2. NUMA 的两个位置

线程在哪个CPU运行，与内存页实际分配在哪个NUMA node，是不同问题。
GPU/NIC/NVMe还通过特定PCIe路径连接主机。
远端内存访问可能经过socket互联，增加延迟和共享带宽消耗。

```text
CPU node 0 memory ─ CPU0 ─ GPU0/NIC0
        │            │
        └─ inter-socket fabric ─ CPU1 ─ GPU1/NIC1
```

把线程后来绑到CPU1，不必然把已经分配的页迁到node1。
Linux memory policy通常影响后续分配，已有页需要另查实际驻留与迁移策略。
容器cpuset还可能限制可用节点，优先级与程序策略相互作用。

### 2.1 Read-only 拓扑检查

常见工具形状：

```bash
lscpu
numactl --hardware
nvidia-smi topo -m
```

是否可用取决于系统、权限与是否在WSL/容器中。
WSL暴露的拓扑不能无条件等同于裸机PCIe/NUMA全貌。
检查结果应作为当前环境证据保存，不从另一台机器复制绑定方案。

## 3. Pinned memory 解决什么

Pinned host memory使页面不会被普通分页机制移动，便于设备DMA访问。
它通常是实现高效异步H2D路径的重要条件之一。
但pinning本身有成本，过量使用会占用不可分页主机内存。
不能对每个小对象临时pin再期待零开销。

可采用长期存在的有限buffer pool。
数据填好后提交H2D，直到copy完成前producer不能重写源buffer。
目标GPU buffer也要在consumer完成前保持有效。
`non_blocking=True`是提交语义的一部分，不单独保证真正overlap。

## 4. 三阶段流水的时间模型

设读取、CPU处理、GPU执行分别为 $t_R,t_C,t_G$。
完全串行处理N批：

$$
T_{serial}=N(t_R+t_C+t_G).
$$

理想流水、独立资源且足够buffer时：

$$
T_{pipeline}\approx t_R+t_C+t_G+(N-1)\max(t_R,t_C,t_G).
$$

这包括填充与排空。
共享CPU、磁盘、PCIe或内存带宽会破坏独立假设。
有界buffer太小也会阻塞阶段，太大则增加内存与恢复复杂度。

### 4.1 完整数例

读取8ms，CPU处理12ms，GPU执行20ms，N=10。
串行时间400ms。
理想流水为40+9×20=220ms，约1.818倍。
若NUMA/CPU争用使处理涨到28ms，则流水为56+9×28=308ms。

此时GPU只有20ms工作，却要等28ms节拍。
继续优化GPU到15ms，只把填充尾部略微缩短，稳态仍由CPU主导。
应先修CPU/内存路径或减少transform工作。

## 5. 数据带宽的下界与实际差距

若训练每秒消费200万token，每token记录4字节：

$$
BW_{minimal}=2\times10^6\times4=8MB/s.
$$

这个数可能远小于存储标称带宽。
实际瓶颈可能是小文件metadata、随机seek、解压、在线图像变换或packing。
多模态样本的原始字节也远大于最终token IDs。

因此要测：

- bytes read与有效tokens。
- files/objects per batch。
- metadata请求与seek。
- 解压/parse CPU时间。
- page faults与复制量。
- GPU data-wait分布。

只拿8MB/s与“磁盘3GB/s”比较不能证明数据管线没有问题。

## 6. Buffer 的状态机

```text
FREE
  → READING
  → CPU_READY
  → H2D_INFLIGHT
  → GPU_READY
  → GPU_CONSUMING
  → RETIRING
  → FREE
```

如果host buffer与device buffer分开池，二者有不同回收事件。
Host在H2D完成后可归还，device需等GPU最后consumer完成。
取消不代表可以立刻重写两个buffer。
错误路径也需释放已取得但尚未提交的资源。

### 6.1 双缓冲不是无限队列

两个buffer可以覆盖简单producer/consumer重叠。
实际pipeline还可能需要更多槽以吸收抖动。
但预取应设上限，并传播backpressure。
不能通过无限累积样本把吞吐问题隐藏成内存增长。

## 7. 可运行的流水与所有权模型

```python
def pipeline_finish(stage_times, batches):
    free_at = [0]*len(stage_times)
    finished = []
    for _ in range(batches):
        ready = 0
        for i,duration in enumerate(stage_times):
            ready = max(ready,free_at[i])+duration
            free_at[i] = ready
        finished.append(ready)
    return finished[-1]

assert pipeline_finish([8,12,20],10) == 220
assert pipeline_finish([8,28,20],10) == 308
print("serial",10*(8+12+20),"pipeline",pipeline_finish([8,12,20],10))

class Slot:
    def __init__(self):
        self.state = "FREE"
    def fill(self):
        assert self.state == "FREE"
        self.state = "CPU_READY"
    def submit(self):
        assert self.state == "CPU_READY"
        self.state = "H2D_INFLIGHT"
    def copy_done(self):
        assert self.state == "H2D_INFLIGHT"
        self.state = "FREE"

s = Slot()
s.fill()
s.submit()
try:
    s.fill()
except AssertionError:
    pass
else:
    raise AssertionError("source overwritten before copy completion")
s.copy_done()
s.fill()
print("host slot reuse waits for copy completion")
```

流水函数假设各阶段独立且队列容量无限，用于计算乐观时间。
Slot模型则强调真实实现必须补上有限容量与完成事件。
两部分不能被误解为完整IO系统模拟。

## 8. Checkpoint 写出与输入争用

训练checkpoint可能D2H、序列化并写入本地或远端存储。
这些工作会和输入读取争用CPU、内存、PCIe、NIC和磁盘。
异步写出只消除部分阻塞，并不让资源成本消失。
需要观察checkpoint窗口内data-wait p99与step尾部。

写出流程应先形成一致快照或staging副本，再后台写入。
如果后台writer直接读正在更新的参数，可能混合不同step状态。
只有全部必要shard与metadata提交后，checkpoint才具备恢复意义。
函数返回不一定等于耐久完成。

## 9. 数据恢复游标必须与模型状态一致

只保存global step不足以恢复相同训练数据流。
还需dataset manifest、RNG、样本置换、packing buffer和全局已消费游标。
如果DP变化，rank局部游标还需映射回全局逻辑顺序。
预取但未提交的样本不能被误认为已经用于optimizer update。

```text
read/prefetch cursor
  may be ahead of
consumed batch cursor
  may be ahead of
committed optimizer-step cursor
```

恢复目标不同，可以允许不同等级的重复读取。
但必须明确哪些样本会重复或跳过。
“训练继续跑了”不等于bitwise continuation或相同数据语义。

## 10. 推理中的同类主机瓶颈

Tokenizer和chat template是输入CPU阶段。
多模态decode/resize/encoder准备可能占大量CPU与内存。
权重冷启动和KV offload使用存储、主机buffer与H2D。
Stream序列化又可能在输出端阻塞event loop。

可以复用有界队列、buffer owner和NUMA观测方法。
但推理目标是每请求SLO，不是只追稳态batch吞吐。
为提高总吞吐扩大batch等待，可能恶化TTFT。
应分别报告吞吐和用户可见延迟。

## 11. NUMA 优化的实验矩阵

| 变量 | 对照 |
|---|---|
| CPU affinity | 默认 / 与GPU邻近 |
| 内存分配 | 默认 / 明确policy后的新分配 |
| workers | 少、中、多 |
| prefetch | 1、2、4批等有限档位 |
| host buffer | 临时 / 长期pool |
| IO路径 | remote / local verified cache |
| checkpoint | 无 / 同路径并发 / 隔离路径 |

每轮记录CPU利用、RSS/pinned bytes、page faults、IO延迟、H2D和GPU空隙。
绑定策略必须基于实际拓扑。
测试结束应清楚记录是否修改了系统状态；本教程仅给设计，不自动执行绑定。

## 12. 性能反例

增加workers让CPU上下文切换和磁盘seek激增，吞吐下降。
过量pinned memory压迫系统可分页内存，其他服务受影响。
更深prefetch耗尽RAM，恢复时还需要丢弃大量未提交样本。
把线程绑到邻近CPU，但旧页仍在远端NUMA，收益不明显。
异步checkpoint挤占NIC，使训练collective尾部更长。

这些都说明“异步”“预取”“绑定”只是机制。
是否有收益取决于依赖、共享资源和生命周期。
优化必须有前后trace。

## 13. 六道追问与答案

### Q1：为什么CPU绑核后内存仍可能远端？

已有页的物理驻留通常不会因线程迁移自动按期望改变。
需要检查分配时policy、first-touch和实际页面位置。
容器cpuset还可能限制可选节点。

### Q2：non_blocking copy是否保证重叠？

不保证。
还要满足host内存、stream依赖、copy engine和独立工作等条件。
源/目标buffer直到相应完成前必须有效。

### Q3：为什么token记录带宽很小，数据仍拖慢训练？

小文件metadata、解压、parse、transform和随机IO可能主导。
多模态原始字节也不等于token ID大小。
需逐阶段测量。

### Q4：为什么异步checkpoint仍影响step？

它占用CPU、PCIe、内存、NIC或磁盘，并有staging/finalize关键路径。
后台工作可能拖慢输入或collective。
要测完整时间线。

### Q5：预取游标为什么不能当恢复游标？

预取数据可能尚未参与已提交optimizer step。
直接恢复到它会跳过样本。
需要区分读取、消费和提交边界。

### Q6：流水最慢阶段优化后会发生什么？

瓶颈可能转移到下一慢阶段。
总时间由填充、稳态节拍和排空共同决定。
应重新测量，而不是假设原speedup可无限叠加。

## 14. 来源与版本范围

### 有界预取容量数例

假设一批处理后数据为256MiB，有8个worker，每worker允许预取2批。
只算这些待消费batch就可能占：

$$
256MiB\times8\times2=4GiB.
$$

如果collate、pinned staging与GPU copy期间同时保留另一份，还会继续增长。
原始压缩buffer、多模态中间图像和Python对象也未计入。
因此prefetch参数不能只看队列项数量，要乘每项真实存活字节。

当GPU暂时慢于producer时，有界队列让producer等待。
这是一种正常背压，不一定是需要消除的“CPU空闲”。
若无限增加队列，只会延迟暴露瓶颈并扩大内存峰值。

推荐分别监控：

- raw read bytes。
- transformed batch bytes。
- pinned pool reserved/active bytes。
- H2D inflight bytes。
- queued batch age与count。
- committed与prefetched cursor距离。

这些字段连接吞吐、容量和恢复语义。

训练综述9.7/9.8、10.3与8.6；推理宝典PROD-002/010、KERN-018。
Megatron报告模块C的checkpoint、data/RNG ownership与异步finalization。
相关Megatron源码证据仍属于48a887f参考snapshot，非当前checkout断言。

- [Linux NUMA Memory Policy](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)：policy作用域与已有页面边界。
- [PyTorch CUDA semantics 2.15](https://docs.pytorch.org/docs/2.15/notes/cuda.html)：stream、pinned memory与异步访问。
- [PyTorch DataLoader](https://docs.pytorch.org/docs/stable/data.html)：worker、prefetch与pinning配置需按安装版本核验。
- [PyTorch async checkpoint recipe](https://docs.pytorch.org/tutorials/recipes/distributed_async_checkpoint_recipe.html)：staging与异步保存成本。

文中不把CPU流水模型写成实际存储吞吐。
NUMA、H2D和集群IO性能需在目标环境测量。
