## 性能结论首先是一个实验结论

“修改后快了5%”至少隐含比较对象、工作量、时间边界和随机误差。
如果A运行在低温设备、B运行在热设备，差异可能来自顺序。
如果B处理更短样本，差异可能来自workload。
本节重点是怎样让证据支持因果解释，不重复在线TTFT指标定义。

训练、推理和kernel都可以使用相同的实验骨架。
但采样单位和依赖结构不同，不能机械套同一统计脚本。
下面所有数据均为合成教学样本。

## 1. 先写可证伪假设

不够具体的假设：开启融合会更快。
可检验的假设：在指定shape与dtype下，融合消除两次中间HBM往返，使kernel时间至少下降10%，且端到端不回归。

一份假设包含：

```text
对象: 哪个模型/算子/配置
机制: 减少哪项资源或等待
预测: 哪些中间指标和最终指标改变
约束: correctness/quality/memory/SLO
反证: 什么结果说明机制判断错误
```

先写预测，再看结果，能减少事后解释。
没有中间观测的最终speedup仍可作为结果，但不足以证明具体机制。

## 2. 明确实验单位

| 任务 | 常见独立单位 | 容易误用的单位 |
|---|---|---|
| Kernel | 独立运行/受控重复组 | 同一热cache内每次launch |
| 训练 | seed/run或成对trace窗口 | 强相关的相邻step |
| 推理 | 独立压测轮次或请求cohort | 同batch内强耦合token gap |
| 集群 | 独立节点/拓扑实验 | 同一次collective的各rank |

同一batch的请求共享GPU与队列，通常不是完全独立样本。
相邻训练step可能共享温度、缓存和数据长度趋势。
把相关样本当作独立，会让置信区间过窄。
可按run或时间block做配对与重采样。

## 3. 固定与随机化分别负责什么

固定硬件、artifact、版本、dtype、并行和测量口径。
随机化运行顺序，减少温度、背景负载与时间趋势偏差。
同一对A/B使用相同trace、seed或shape集合。
环境不能完全固定时，记录其变化用于分层分析。

```text
pair 1: A then B
pair 2: B then A
pair 3: A then B
pair 4: B then A
```

随机化不是允许随意变化工作量。
固定输入也不是永远复用同一小buffer，让cache条件脱离业务。
需要显式设计cold、warm与steady-state三种条件。

## 4. 编译与warm-up单独报告

第一次调用可能包括JIT、autotune、graph capture、allocator扩容和频率变化。
稳态kernel计时应排除这些一次性成本，但产品冷启动评估不能把它们消失掉。
因此至少分：

- first-use latency。
- warm-up到稳定所需时间和工作量。
- steady-state时间分布。
- cache失效/新shape后的重新进入成本。

训练短作业可能无法摊薄长编译。
推理低流量模型也可能长期停留在冷启动主导状态。
只有稳态快，未必整体更经济。

## 5. 平均speedup有多个定义

给每个case的基线时间 $a_i$、候选时间 $b_i$：

$$
s_i=a_i/b_i.
$$

简单平均 $s_i$、几何平均、总时间比值具有不同含义。
若case代表不同出现频率，应按业务频率与工作量加权。
总工作时间比值为：

$$
S_{total}=\frac{\sum_i w_i a_i}{\sum_i w_i b_i}.
$$

不要先按喜好选择能得到最大收益的聚合方法。
应在实验契约中预先指定。

### 5.1 完整数例

两种shape各执行一次：

```text
shape 1: A=1 ms,   B=0.5 ms, speedup=2
shape 2: A=100 ms, B=100 ms, speedup=1
```

平均speedup=1.5，看似快50%。
实际总时间从101降到100.5 ms，速度比仅约1.00498。
如果shape2占绝大部分业务，微小shape1的巨大speedup没有相同权重。
这说明报告必须保留shape分布和聚合口径。

## 6. 配对差值减少公共波动

对第 $i$ 对实验，差值为：

$$
d_i=a_i-b_i.
$$

如果两次经历接近的公共环境，配对可以减少环境差异。
但A先运行可能改变B的cache或温度，因此还需顺序随机化与初始化。
可用相对差或log ratio，但其解释应清楚。

例如A和B每次都受到+10ms背景波动，配对差值仍能稳定反映1ms改进。
把两组数据拆开随机配对，则可能丢掉这种设计优势。
保存pair ID至关重要。

## 7. 置信区间不是“结果有95%概率正确”

常见频率学解释是：按相同程序重复抽样，构造的区间在长期中具有所声明覆盖率。
具体一次区间的含义仍依赖采样和模型假设。
区间不覆盖零可以支持某种差异，但不自动证明业务价值。
0.1%的显著改进可能远小于部署复杂度。

也不要把“不显著”说成“两者完全相同”。
它可能是样本量不足或噪声太大。
实用等价范围应预先定义，例如绝对延迟差小于某业务容忍值。

### 7.1 Bootstrap 的适用边界

Bootstrap从现有样本重采样，估计统计量的不确定性。
配对实验应整对采样，相关时间序列可考虑按block采样。
它无法创造原数据没有覆盖的故障、shape或流量。
样本太少或极端尾部太稀疏时，区间仍可能不可靠。

## 8. 可运行的配对 bootstrap

```python
import random
from statistics import mean

baseline = [100,102,98,105,101,99,103,100]
candidate = [96,98,95,100,97,95,99,96]
diffs = [a-b for a,b in zip(baseline,candidate)]
assert mean(diffs) == 4

rng = random.Random(7)
boot = []
for _ in range(4000):
    sampled = [diffs[rng.randrange(len(diffs))] for _ in diffs]
    boot.append(mean(sampled))
boot.sort()
lo = boot[int(0.025*len(boot))]
hi = boot[int(0.975*len(boot))-1]
assert lo <= mean(diffs) <= hi
assert lo > 0
print("paired improvement ms",mean(diffs),"interval",lo,hi)

simple_speedup = mean([1/0.5,100/100])
total_speedup = (1+100)/(0.5+100)
assert simple_speedup == 1.5
assert total_speedup < 1.01
print("mean ratios",simple_speedup,"total ratio",total_speedup)
```

这里只有8对合成样本，不作为真实上线统计模板的充分性证明。
真实实验需更多独立轮次，并按环境/shape结构设计采样。
Percentile取法也应随报告固定，不同工具可能略有差异。

## 9. 尾部统计与cohort

训练p99 step time可能来自checkpoint、长样本或fail-slow。
推理p99可能来自burst、长prompt或慢客户端。
先按已知机制分群，再解释总体尾部。
只把所有样本混在一起，会掩盖哪个子群发生退化。

记录样本数、窗口、异常与未完成请求。
中途超时而没有完成时间的请求不是可以删除的“坏数据”。
它们是删失或失败结果，需要单独统计。
否则候选可以通过不完成慢请求得到更好的p99。

## 10. 消融实验连接机制与结果

假设改动同时包含fusion、graph和batch调整。
先测完整方案可以判断是否值得继续，但归因需要拆开。

| 版本 | Fusion | Graph | Batch变化 | 目的 |
|---|---|---|---|---|
| A | 否 | 否 | 否 | 原始基线 |
| B | 是 | 否 | 否 | 融合独立作用 |
| C | 否 | 是 | 否 | 提交开销作用 |
| D | 是 | 是 | 否 | 二者交互 |
| E | 是 | 是 | 是 | 完整系统效果 |

如果B和C单独都有收益，D不一定等于两项相加。
Fusion减少launch后，graph可消除的开销也减少。
Batch变化还会改变cache、KV和矩阵形状。
这类交互需要实际测量，而不是简单乘speedup。

## 11. 训练实验还要控制数学工作

Global batch、有效loss token、学习率和数据顺序变化会影响收敛。
比较step time时应说明是否处理相同有效工作。
比较time-to-quality时需要相同质量门槛与可比训练计划。
如果新方案跳过异常batch，吞吐和质量都应记录。

不同rank的样本长度可能改变同步尾部。
需要保存长度分布、packing和loss mask口径。
MFU分子不能在A使用useful FLOPs、B使用executed FLOPs。
详见本章1.1的工作定义。

## 12. 自动调参容易过拟合

扫描上百配置后挑最快者，再用同一小样本报告收益，会受到选择偏差。
应将调参集与最终验证集分开。
候选在真实shape桶、冷启动和资源上限下复核。
保存失败与不支持配置，避免只展示幸存者。

Autotune成本也进入预算。
一个配置省0.1ms但编译多花10分钟，短作业可能无法回本。
按调用次数 $n$ 计算：

$$
n\Delta t>T_{compile-extra}.
$$

上述例子需要超过600万次调用才摊平10分钟。
若部署经常失效重编译，还要考虑实际缓存命中周期。

## 14. 六道追问与答案

### Q1：为什么不直接平均每个shape的speedup？

它隐含各shape等权，可能让微小任务主导结论。
应按实际频率和耗时计算总工作时间比，或明确其他聚合目的。
同时保留分shape结果。

### Q2：重复1000次launch是否等于1000个独立样本？

未必。
它们可能共享cache、频率和同一环境趋势。
需要独立运行组或按相关结构重采样。

### Q3：置信区间不含零就应该上线吗？

不一定。
还需实际业务收益、正确性、质量、成本和复杂度评估。
统计差异与工程价值不同。

### Q4：为什么要记录超时请求？

删除它们会让慢请求消失，低估尾部和失败率。
超时是系统结果的一部分。
需要明确cohort与删失口径。

### Q5：如何证明fusion减少HBM是提速原因？

固定其他配置，用消融比较，并观察实际流量、launch与时间。
若HBM没下降或spill增加，应修正假设。
最终端到端收益仍需复测。

### Q6：训练step更快，是否表示time-to-quality更短？

只有有效工作与收敛行为可比时才可推断。
batch、精度、数据顺序或跳步可能改变优化过程。
应另测质量门槛和恢复开销。

## 15. 来源与边界

### 多重比较与提前停止

扫描100个候选配置时，某个配置恰好因噪声胜出的机会会增加。
先用调参集筛选，再在独立验证集复核，可以降低这种选择偏差。
若同时检验大量shape，应预先区分主要指标与探索指标。
不能每跑一轮看一次结果，看到“显著”就立即停止，再使用固定样本量的解释。
停止规则本身会改变统计性质。

对工程项目，一个实用做法是：

```text
预先确定独立重复轮次
预先确定主要workload与聚合方法
预先确定复测触发条件
记录全部候选与失败结果
最终候选使用新的验证样本
```

这不要求每次开发都做昂贵完整统计。
快速探索可以少量测量，但结论应标为探索性。
上线证据再按固定合同收集。

### 长度桶的 Simpson 类误导

假设A测试时90%短请求，B测试时90%长请求。
B即使在每个长度桶都更快，总平均也可能更慢。
反过来，候选只接更多短请求，会在总体平均中显得更快。
因此需先比较相同bucket内的表现，再按同一目标分布加权。
训练中packing或数据mixture变化也会产生类似混淆。

报告至少保留输入/输出长度、任务、硬件和版本分群。
若分群样本太少，明确标为证据不足。
不要把分布变化误写为kernel回归。

推理宝典PERF-015—020、KERN-025/026、PROJECT-001—010。
训练综述第2.5、8.7、11.4节。
Megatron报告公式第10节、项目答辩与性能证据规则。
