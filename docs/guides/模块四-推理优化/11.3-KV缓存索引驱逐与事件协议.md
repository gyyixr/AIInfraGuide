## Scheduler 问能否分配，缓存层回答哪些页面可用

上一节的页预算背后，有一套比 free list 更丰富的状态。
某块页面可能没人主动引用，却仍保存有效 prefix，可供后续请求复用。
它同时是“可驱逐候选”和“语义上仍有缓存内容”的页面。
不能把 free queue 简单理解为所有页面已经清零。

本文固定使用 SGLang `46d9427b913b20ce0d72b95a9209717448b37368` 与 vLLM `9c8e90eb2637a863ca14e47fd436b10ed7ba6536`。
以下内容来自列出的源码片段，而非当前主分支的泛化说明。
混合模型的 cache groups/components 只讨论读到的接口边界。

## 1. 三个互相关联的结构

```text
semantic index
  prefix identity → reusable blocks

request block table
  logical position → physical block

physical pool
  block → refs, residency, eviction metadata
```

语义索引决定“能不能共享”。
block table 决定“本请求怎样访问”。
physical pool 决定“能不能分配或回收”。
三者更新顺序错误，会造成 stale index、重复分配或跨请求写入。

## 2. 前缀 key 为什么需要父链

同一 token block 在不同上文下会产生不同 KV。
所以 block hash 通常不只哈希当前 block tokens，还包含前序 prefix identity。
可抽象为：

$$
h_i=Hash(h_{i-1},tokens_i,extra_i).
$$

`extra` 表示影响语义的附加身份。
固定 vLLM hash 工具涉及 LoRA 名、多模态标识、cache salt 和 embedding hash 等。
具体字段随模型和版本变化，应读 `generate_block_hash_extra_keys`。
不能凭“用了 SHA”就推断完整语义身份已经覆盖。

### 2.1 教学数例

```text
A: [1,2] [3,4] [5,6]
B: [1,2] [9,4] [5,6]
```

第三个 block 虽然 tokens 相同，父 prefix 不同，因此 hash 应不同。
否则 B 会错误复用依赖 A 上文的 KV。
安全域或 adapter 不同，也应导致适当的 namespace 分离。

## 3. SGLang 的 Radix 视角

Radix tree 将公共 token 序列压缩成共享边或节点。
查询最长前缀时沿 token 路径下行。
新请求在某条边中间分叉时，需要 split，保持两个后缀的父前缀一致。

```text
root
  └─ [1,2]
       ├─ [3,4,5,6]  A
       └─ [9,4,5,6]  B
```

SGLang 还保留 `RadixKey` 这样的 token 与额外 namespace 表示。
不能把它简化成仅比较文本字符串。
页粒度、bigram 或特殊模型的逻辑单位需按所用实现确认。

固定 `RadixKey` 注释还明确一个重要范围：`cache_salt` 隔离进程内 radix tree 与外部 KV events，L3/remote storage key 不在这个契约内。
因此不能仅设置这一字段，就宣称所有外部缓存层已经完成租户隔离。
部署需要另查实际 storage backend 的 key、ACL 和 namespace。
这属于明确的接口边界，不应被“统一缓存”名称掩盖。

### 3.1 UnifiedRadixCache 的职责拆分

固定版本的 `UnifiedRadixCache.match_prefix`：

1. 先尝试 session 相关处理。
2. 缓存禁用时返回空匹配。
3. 调 tree core 完成匹配。
4. 应用匹配产生的 cache actions。
5. 由各 component 完成结果整理。

这说明统一 cache 是协调层，不把所有模型的存储细节都揉进单个树 walk。
FULL、SWA、MAMBA 等组件有不同驻留/可复用约束。
阅读时需要从 coordinator 追到具体 component，不能只读类名。

### 3.2 Insert 不是无条件写 map

固定 `insert` 使用 begin/resume 的可恢复步骤，并在每个屏障应用 actions。
`finally` 中还会结束插入并处理剩余 action。
这样异常路径也有机会把应该归还的资源送回 allocator。

若只在成功时处理 free action，失败插入会泄漏页面。
若重复应用 action，又可能 double free。
因此“树结构正确”和“资源动作恰好完成”要同时验证。

## 4. 锁定前缀影响可驱逐容量

请求命中 prefix 后，应持有相应锁或引用。
`inc_lock_ref`/`dec_lock_ref` 连接活跃请求与树节点。
固定实现还携带各组件跳过锁定的记录，释放时不能减掉从未增加的锁。

```text
match
  → pin prefix
  → allocate new suffix
  → execute
  → cache reusable suffix
  → release request pins
```

一个节点被多个活跃请求共享，只有最后引用释放后才成为可驱逐候选。
层次缓存中的异步写回也可能持有额外保护。
LRU 只决定安全候选的优先级，不能驱逐仍在使用的数据。

## 5. 请求完成不等于删除全部 KV

SGLang `cache_finished_req` 从输入与输出历史中确定有效 KV 长度。
组件可以限制实际可缓存长度。
可复用部分插入索引，未对齐尾部和不可缓存部分按契约归还。
如果禁用缓存，则走直接释放相应存储的路径。

这里要区分：

- 已采样的 token 数。
- 已真正计算并写入 KV 的 token 数。
- 因页或组件约束可缓存的 token 数。

自回归最后一个采样 token 可能尚未执行下一轮 forward。
不能拿 `len(input)+len(output)` 无条件当作全部 KV 都已存在。
必须使用运行时传入的有效 KV 边界。

## 6. vLLM 的 `KVCacheManager`

`get_computed_blocks` 查找可复用的完整 block。
固定代码把最大命中长度限制到 `request.num_tokens - 1`，因为还需要重新获得末尾 logits。
由于 block 对齐，可能重算不止一个 token。

例如 block size=16，prompt 长度=32。
即使之前 32 token 全部缓存，若命中上限是 31 且要求完整 block，只能命中 16。
剩余 16 token 再计算。
这是该固定路径的实现约束，不是 prefix caching 的数学必然要求。

### 6.1 `allocate_slots` 的布局

固定接口显式区分：

```text
already computed
new local cache hit
external computed KV
new compute tokens
lookahead/spec slots
```

此外有 encoder tokens、reserved blocks 和 full-sequence feasibility 等参数。
`delay_cache_blocks` 用于尚未完成的异步 KV 传输，避免提前发布为可复用缓存。
这正是“分配了地址”和“数据已经提交”必须分开的原因。

## 7. vLLM BlockPool：free queue 可以包含缓存

`get_new_blocks` 从 free block queue 取候选。
若候选仍有 cache hash，先从语义索引中移除并发出相应事件，再复用物理块。
然后将引用计数从零增加。

```text
ref=0, valid hash
  → evict hash metadata
  → notify removal
  → ref=1
  → new owner writes
```

`touch` 在命中共享 block 时增加引用。
如果原来 ref=0，会先把该 block 从 free queue 移除。
否则 allocator 可能在请求使用期间把它分配给别人。

### 7.1 `free_blocks` 的两类顺序

固定版本将无 hash 与有 hash 的零引用块分别处理。
无 cache 内容的块更早复用，以改善局部性。
有缓存内容的块排到较后位置，形成对应的 LRU 候选行为。
“free”在这里是可以回收的 ownership 状态，不等于缓存立即失效。

## 8. Cache events 的真实字段

固定 vLLM `kv_events.py` 定义：

```text
BlockStored
BlockRemoved
AllBlocksCleared
KVEventBatch
```

Stored 包含 block hash、父 hash、token IDs、block size、medium、LoRA/extra keys 和 group 信息等。
Removed 不需要重发全部 token 内容，但需能确定移除哪个 group/medium 的 block。
这些事件供外部消费者理解 worker 状态。
它们不是 allocator ownership 的转移凭证。

## 9. 外部路由协议需要额外可靠性

源码里的事件类不自动提供全部生产控制面能力。
部署还应定义 publisher identity、worker epoch、事件序号、gap detection 和 snapshot。
不要把这些建议字段误写成上述所有 dataclass 已经具备的属性。

事件丢失时，router 可能预测命中但 worker 已驱逐。
正确行为是 worker 实际 lookup miss，再重算或选其他合法恢复路径。
路由视图错误只能影响性能，不能使错误 KV 被消费。

Cache events 还可能暴露 token IDs 或关联信息。
外部消费者、日志与传输通道需要与缓存安全域一致的访问控制。
不能因为接口名叫 metrics/events 就忽略数据敏感性。

## 10. 可运行的父链与引用模型

```python
import hashlib
import json

def chain_hashes(tokens, block_size, namespace):
    parent = "root"
    result = []
    for start in range(0, len(tokens), block_size):
        block = tokens[start:start+block_size]
        if len(block) < block_size:
            break
        payload = json.dumps([parent, block, namespace]).encode()
        parent = hashlib.sha256(payload).hexdigest()
        result.append(parent)
    return result

a = chain_hashes([1,2,3,4,5,6], 2, "tenant-A")
b = chain_hashes([1,2,9,4,5,6], 2, "tenant-A")
c = chain_hashes([1,2,3,4,5,6], 2, "tenant-B")
assert a[0] == b[0]
assert a[1] != b[1]
assert a[2] != b[2]
assert a[0] != c[0]

class Block:
    def __init__(self):
        self.refs = 0
        self.hash = "cached-prefix"
        self.free_candidate = True

    def touch(self):
        assert self.refs >= 0
        self.free_candidate = False
        self.refs += 1

    def release(self):
        assert self.refs > 0
        self.refs -= 1
        self.free_candidate = self.refs == 0

block = Block()
block.touch()
block.touch()
block.release()
assert block.refs == 1 and not block.free_candidate
block.release()
assert block.free_candidate and block.hash is not None
print("parent chain, namespace and zero-ref cache semantics passed")
```

真实 hash 算法、extra key 和 free queue 并不由此 toy class 复刻。
模型只展示语义与 ownership 必须共同满足。
若加入异步读写，还要在 refs 之外增加 inflight/completion 约束。

## 11. 性能与正确性反例

### 11.1 高命中却更慢

命中的是很短 prefix，saved compute 小。
热点路由又让该副本 queue 变长。
因此应记录 saved tokens/time，而不只记录 hit count。

### 11.2 小 page 未必更好

小 page 减少尾部浪费，也增加页表、hash 和 kernel 地址处理。
大 page 减少 metadata，却使复用与驱逐粒度更粗。
应同时比较显存、查找时间和实际 attention kernel。

### 11.3 删除索引不等于释放数据

页面可能仍被请求或异步传输持有。
反过来，页面被复用前必须移除旧 hash。
否则后续 prefix lookup 会返回新 owner 的地址。

## 12. 六道追问与答案

### Q1：为什么 block hash 要包含父前缀？

相同 token block 在不同上文下的隐藏状态不同。
父链把此前语义包含进 key。
只哈希本块 tokens 会错误共享。

### Q2：零引用块是否一定没有缓存价值？

不是。
它可以仍保存可复用 prefix，只是允许被驱逐。
命中时需从 free candidate 集合移出并增加引用。

### Q3：为什么完整 prompt 命中仍可能重算一整页？

固定 vLLM 路径需要末尾 logits，并限制命中到 prompt-1。
完整 block 对齐进一步降低可用命中长度。
这是实现边界，应按版本核对。

### Q4：Radix 与 block hash 谁更先进？

它们优化不同的数据结构操作和传播方式。
Radix 擅长最长前缀与共享结构，block hash 便于块级身份和分布式事件。
选择需要看 mutation、锁、模型结构和 workload，而非单一排名。

### Q5：为什么 cache events 需要安全控制？

事件可能带 token IDs、LoRA 和语义标识。
外部消费者能观察请求内容或访问模式。
应按安全域授权，并最小化不必要字段传播。

### Q6：缓存插入失败最该测什么？

索引仍一致、页面不泄漏、不重复 free、锁计数正确。
必须覆盖 split/action 已部分执行后抛异常的情况。
只测正常 insert/match 不足以证明资源安全。
