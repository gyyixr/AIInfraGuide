## 使用方式与证据规则

本节从参考宝典 235 题的十三类能力中选取 40 个综合问题。
目的不是把每个编号缩写成一句口诀，而是展示可以继续追问的完整答案。
每题保留反例或边界；源码题沿第 11 章固定 snapshot 核对。

固定源码为 SGLang `46d9427b913b20ce0d72b95a9209717448b37368` 与 vLLM `9c8e90eb2637a863ca14e47fd436b10ed7ba6536`。

## 01｜从 HTTP 到首 token，哪些阶段可能是瓶颈？

**答案：**请求先经过认证、能力与长度校验，再做模板/tokenizer 或多模态处理。
执行请求经 IPC 进入 scheduler，等待 token/sequence/KV 预算，随后进行 prefill、logits 和采样。
输出 token 还需 detokenize、stop 判断、序列化和网络写出。
客户端 TTFT 包含这条关键路径，CUDA event 通常只覆盖其中设备部分。

SGLang 可从 `TokenizerManager.generate_request` 追到 scheduler 和 detokenizer 回传。
vLLM V1 则区分 AsyncLLM、EngineCore、OutputProcessor 和每请求 collector。
应关联 request/attempt ID、batch、rank 和模型版本，而不只看一个 GPU utilization。

**追问：**GPU 只花 10 ms、TTFT 却有 500 ms，优先查 queue、CPU 和 stream 边界。
**反例：**只把 GEMM 快一倍不能消除 450 ms 的排队。
**映射：**FND-001、PROD-002、PERF-001。

## 02｜为什么 prefill 与 decode 不能仅按“算力/带宽”二分？

**答案：**Prefill 一次处理多个输入 token，线性层通常形成较大 GEMM。
Decode 的每请求新 query 少，但要读取历史 KV，batch=1 Dense 模型还常受权重流量限制。
这些只是常见起点，batch、context、量化、MoE 和通信会改变实际瓶颈。
长 context decode 可能由 attention KV 流量主导；大 batch 又能更充分复用权重。

应根据实际 shape、FLOPs、HBM/L2 bytes 和 timeline 判断。
PD 的动机是阶段隔离和独立调参，不能从这个二分直接推导一定提速。

**追问：**固定 GPU 预算比较 aggregated、chunked 和 PD 的 SLO-goodput。
**反例：**短 prompt 低并发时，额外 KV handoff 可能只增加延迟。
**映射：**FND-002、PERF-007—011、DIST-016。

## 03｜GQA 的 KV 为什么按 KV heads 计算？

**答案：**多个 Q heads 可以共享一组 K/V heads。
标准 GQA 每 token KV 字节为 $2Lh_{kv}db$，系数 2 表示 K 与 V。
取 32 层、8 KV heads、128 维、BF16，得到 131072 bytes，即 128 KiB/token。
8192 token 的单序列 KV 是 1 GiB，尚未计页尾、scale 和其他状态。

TP 下需再看实际 KV shard 或复制，不能无条件除以 TP。
MLA、窗口层和 recurrent state 使用不同结构，应重新建模。

**追问：**TP=16 而 KV heads=8 时，检查 backend 是否复制 heads。
**反例：**用 32 个 Q heads 代替 8 个 KV heads，会高估四倍。
**映射：**FND-008、KV-001/002、PERF-004。

## 04｜TTFT、ITL 与 TPOT 如何从原始时间戳计算？

**答案：**设发送为 $s$，token 时间为 $t_1\ldots t_N$，最终完成为 $f$。
TTFT=$t_1-s$，ITL 为相邻 token 时间差。
以末 token 为边界，TPOT=$(t_N-t_1)/(N-1)$，仅在 $N>1$ 时定义。
E2E=$f-s$；若工具用 finish 替代 last-token 计算 TPOT，需要明确差别。

请求内平均 TPOT 会平滑单次长 gap。
SSE chunk 可能包含多个 token，所以 inter-chunk latency 不必等于 ITL。

**追问：**时间 `[0.5,0.54,0.58,0.9]` 的最大 ITL 为 320 ms，TPOT 约 133 ms。
**反例：**单 token 请求填 TPOT=0 会人为拉低均值。
**映射：**PERF-001/003、CODE-018。

## 05｜Little's Law 在什么情况下不能机械套用？

**答案：**$L=\lambda W$ 连接稳定、守恒、同一边界上的长期平均值。
有效进入引擎的速率与外部请求速率可能不同，因为 admission 会拒绝请求。
外部 100 req/s、准入 80 req/s、平均逗留 2.5 s，应算出 200 个平均驻留请求。
不能使用外部 100 得到 250。

持续增长的队列不具备稳态；短窗口又可能存在未完成请求的截断偏差。
公式也不提供 p99，更不能把请求 wall time 当 continuous batch 下的独占副本秒。

**追问：**配比用服务需求，驻留量用逗留时间，两者分别测。
**反例：**100 个请求共享一个 decode step，不能重复计算 100 份独占 GPU 时间。
**映射：**PERF-012—014、DIST-017。

## 06｜Open-loop 与 closed-loop 压测各回答什么？

**答案：**Open-loop 按独立时钟发请求，服务变慢也不自动降低计划到达率。
它能揭示容量不足时队列增长、拒绝和超时。
Closed-loop 固定并发客户端，完成后才继续发，适合衡量固定用户并发体验。
若 100 客户端的平均响应从 1 s 变成 5 s，零 think time 下 offered rate 约从 100 降到 20 req/s。

需要记录计划到达与实际发送，防止客户端自身成为瓶颈。
两种模式都应保留长度分布、EOS 与错误率。

**追问：**生产 burst 不能仅用稳态 Poisson 覆盖。
**反例：**闭环队列不爆炸，不足以证明开放流量不会过载。
**映射：**PERF-013/014/016。

## 07｜Paged KV 省了哪些内存，没省哪些？

**答案：**分页把逻辑序列和物理页面分离，减少连续大块预留和外部碎片。
它支持按增长分配、非连续存储、共享前缀和回收。
同 dtype、同有效 token 数下，理论 K/V 元素总量不因分页减少。
还存在尾页内部碎片、页表和索引开销。

page=16，长度为 17、31、33 的三序列需 32+32+48=112 槽。
有效 token 81，尾部浪费 31 槽。

**追问：**小 page 降碎片但可能增加 metadata 和 kernel 地址开销。
**反例：**“PagedAttention 把 KV 从 O(T) 降到 O(1)”是错误说法。
**映射：**KV-003—007、CODE-005。

## 08｜Prefix cache 为什么不能按相同文本子串复用？

**答案：**Causal 模型的 KV 依赖此前所有相关上下文。
普通跨请求复用要求从 token 0 开始的连续兼容前缀。
中间一个 token 不同后，后面再次相同的文字通常也不能直接复用旧 KV。
Key 还需包含模型、adapter、position、模板、多模态和安全域等语义身份。

Block hash 需要父前缀链；radix 需要正确的分叉结构。
缓存字段覆盖应按实际实现核验，不能用“hash 很安全”替代语义分析。

**追问：**仓库快照改变后，coding agent 的 prefix 从首个不同 token 起失效。
**反例：**同一 system prompt 配不同 LoRA，隐藏状态可能不同。
**映射：**KV-008—012、DESIGN-003/011。

## 09｜引用计数归零为什么还不能立刻 free？

**答案：**逻辑引用计数可能没有包含异步 GPU kernel、DMA 或 connector 保存。
它们仍可能持有物理地址。
需要同时满足逻辑引用、cache lock、异步访问都结束，或数据面已经可靠失效。
取消可将页面放入 RETIRING，而不是直接进入 FREE。

Generation 能拒绝旧控制消息，但不自动阻止已经发出的远端 write。
多 rank 要收齐实际 writer 的 drain 证明，重复 ack 不能重复计数。

**追问：**Timeout 是活性策略，必须解释旧写者为何不能再访问地址。
**反例：**旧 RDMA 写入已复用页面，可能没有越界却污染另一个请求。
**映射：**KV-019、CODE-019、DIST-020。

## 10｜Scheduler 为什么需要三种以上预算？

**答案：**token budget 限制本轮计算，sequence budget 限制请求槽，KV budget 限制持久存储。
它们不等价：新增一个 token 是否多占页，取决于尾页边界。
Spec 还需 lookahead，LoRA 需要 adapter residency，多模态可能有 encoder budget。
Admission 必须同时满足这些物理和语义约束。

Allocator 提供精确可行性，scheduler 负责等待、抢占、拒绝与公平策略。
把两者混在一起，会使租户优先级与页面状态难以解释。

**追问：**按 max_new_tokens 全预留与按步分配分别牺牲什么？
**反例：**只限制 `max_num_seqs` 仍可能在长 prefill 时 OOM。
**映射：**SCH-003/011、CODE-008。

## 11｜Chunked prefill 是否改变模型看到的上下文？

**答案：**正确实现只改变执行分块，不改变逻辑 prompt 与 causal 语义。
每个 chunk 写入 KV 并推进已计算位置，中间 chunk 不应提交伪生成 token。
SGLang 固定结果处理路径以 `inflight_middle_chunks` 区分这一情况。
vLLM 统一 token progress 通过预算限制每轮推进量。

小 chunk 保护 decode cadence，但增加调度/launch；大 chunk 利用 GEMM 更充分但干扰更长。
应扫描真实混合 trace 的 Pareto，不能给通用最佳大小。

**追问：**prompt=10、chunk=4，应推进 4、8、10，仅最后产生首个生成 token。
**反例：**把 chunk 当独立 prompt 会破坏上下文。
**映射：**SCH-004/005、CODE-008。

## 12｜抢占之后应删除哪些状态、保留哪些状态？

**答案：**可以释放受影响 KV，并重置依赖这些 KV 的 computed progress。
已经接受和对用户提交的 output tokens 必须保留。
恢复时用已有 token 历史重建 KV，而不是再次采样过去的 token。
在途结果还要按代际/状态区分交付与计数更新。

固定 vLLM 有条件保留某些 stale token 输出但禁止修改重置计数，也有需要 drop 的路径。
因此不能用一句“旧结果全部丢掉”概括所有异步实现。

**追问：**取消、抢占、prefix reset 三者的输出语义可能不同。
**反例：**重算时重新采样会让用户已看到的文本与后续历史分叉。
**映射：**SCH-006/012/013、CODE-019。

## 13｜FlashAttention 为什么 exact，又为什么不是线性 Attention？

**答案：**它通过分块和在线 softmax 避免把完整 score/probability 矩阵反复写入 HBM。
数学上仍计算 dense attention 所需的相互作用，忽略浮点顺序差异时保持相同语义。
Prefill 的核心 dense attention FLOPs 仍随序列长度近似二次增长。
减少的是中间存储与 IO，不是把全连接注意力变成线性工作量。

在线合并维护最大值、指数和以及未归一化输出，并用新最大值重标旧状态。
它也是 CP 分块精确合并的基础。

**追问：**不能直接平均两个分区各自 softmax 后的输出，因为分母不同。
**反例：**Sliding-window 改变可见历史，是另一类语义改变。
**映射：**ATTN-001/002、CODE-011。

## 14｜CP 的容量收益为什么伴随通信？

**答案：**每 rank 只保存部分序列相关状态，但精确 attention 仍需全局可见上下文的信息。
实现可以交换 KV、移动 Q，或合并局部 softmax 统计。
因此每卡内存下降并不等于全局工作量消失。
位置、mask、分区与浮点合并都必须一致。

连续 causal 切分可能让后部 query 计算更多，需考虑 zigzag 等均衡方式。
head 数、KV heads、网络与 backend 限制具体方案。

**追问：**Prefill CP 支持不自动意味着 decode KV 使用相同分片。
**反例：**把 TP 内复用的 CP 再乘一次会重复计算 GPU 数。
**映射：**ATTN-006/012、DIST-006。

## 15｜长上下文支持为什么至少有四个含义？

**答案：**模型配置允许某长度、位置编码可表示该长度、系统内存能运行、任务质量有效，是不同条件。
只修改 max length 或 RoPE 参数不能证明有效能力。
还需覆盖检索、跨段组合、位置分布、生成稳定性与成本。
系统方面要测 prefill、KV、decode 随长度增长和取消恢复。

长 prompt 和长输出相关时，驻留压力更大。
应保留 ISL/OSL 联合分布而非各自均值。

**追问：**1M coding agent 应用真实多轮与工具插入 trace 验证。
**反例：**短 needle 测试通过不等于复杂跨文档推理有效。
**映射：**ATTN-007—012、DESIGN-003。

## 16｜W4A16 省显存为什么不一定更快？

**答案：**4-bit 权重降低存储和读取字节，但计算仍可能是 FP16/BF16，并有反量化和重排。
低 batch、权重带宽主导时可能获益，大 batch 或不适配 shape 时反量化成本可能占优。
部分层保持高精度，metadata/padding 也会降低理想压缩比。
最终要查实际 per-layer method 和 launched kernel。

同时测加载峰值、KV 可用量、TTFT/TPOT、goodput 与质量。
“文件体积变小”不是性能验证。

**追问：**按硬件、shape、group size 与 backend 建能力矩阵。
**反例：**量化路径 fallback 到低效 kernel 可能比 BF16 更慢。
**映射：**QUANT-001/009/012—015。

## 17｜低精度问题应分哪六项回答？

**答案：**存储格式、输入计算格式、乘法指令、累加精度、scale 粒度与 kernel/fallback。
例如权重是 4-bit 编码，运行时可能反量化到 BF16，再以 FP32 累加部分操作。
相同“FP8”名字也可能对应不同格式与 scale 策略。
不能从 tensor dtype 单独推断实际 Tensor Core 指令。

能力还受 GPU 架构、库版本、对齐与 graph 支持影响。
RTX 3090 的 SM86 结论应与 Hopper/Blackwell 专有原语分开。

**追问：**检查 kernel 名、PTX/SASS 和 profiler，而不是只看配置。
**反例：**支持加载某格式，不等于本机原生执行该格式矩阵乘。
**映射：**QUANT-010/011、KERN-019/020。

## 18｜KV quant 和 weight quant 的质量验证能共用结论吗？

**答案：**不能直接共用。
权重量化影响模型线性变换，KV 量化影响缓存历史及每轮 attention 读取。
误差可能随位置、context、outlier 和生成长度变化。
需要独立覆盖长上下文、语言、任务、reasoning 与结构化输出。

还需计 scale/metadata、量化反量化 kernel 和实际容量收益。
存储节省不能自动转化为合格 goodput 提升。

**追问：**用分群质量下限与联合 SLO 门禁，不能只看平均分。
**反例：**短任务平均分不变，长上下文检索却可能明显退化。
**映射：**KV-013、QUANT-012—015、DESIGN-013。

## 19｜随机投机采样为何不能简化成 greedy token 匹配？

**答案：**目标分布为 $p$，草稿分布为 $q$，草稿采样 $y\sim q$。
接受概率是 $\min(1,p(y)/q(y))$；拒绝后从正部残差 $(p-q)_+$ 归一化采样。
接受质量来自 $\min(p,q)$，拒绝残差补足剩余目标概率，因此保持目标边缘分布。
Greedy matching 只对应特定确定性语义，不能代表随机分布校正。

必须使用采样处理器、temperature、grammar 后相应的目标与草稿概率。
候选拒绝还涉及 KV、grammar 与 RNG/状态回滚。

**追问：**通过离散分布枚举或 Monte Carlo 验证最终输出频率。
**反例：**直接接受所有草稿 token 会把分布变成草稿模型。
**映射：**SPEC-001—003/009、CODE-010。

## 20｜投机加速应比较什么成本？

**答案：**每轮成本包括 draft、verify、接受判定、额外 metadata/KV 和同步。
用每轮期望提交 token 数 $E[C]$ 除这些总成本，得到有效 token 速度。
接受率只是影响 $E[C]$ 的一个因素，不描述草稿成本和 target batch 效率。
大 batch、短输出、低接受或昂贵 draft 都可能让投机变慢。

候选长度增加也会增加 verify 工作和预留页。
应按 workload 扫描并保留“不启用更好”的区域。

**追问：**同样接受率下，长度分布和连续接受长度仍会影响收益。
**反例：**90% 接受率若 draft 比 target 还慢，仍未必有价值。
**映射：**SPEC-004—009、实践项目P5。

## 21｜投机拒绝后，为什么不能只改输出列表？

**答案：**候选已经可能写入 KV、推进 grammar、占用 lookahead slot，并关联随机状态。
只从 Python output list 删除 token，不会撤销这些执行副作用。
需要把 accepted prefix 提交，把 rejected suffix 的计算进度和资源按协议回滚。
已提交结果与尚未验证候选必须有不同状态。

异步 verify 返回时，还要确认请求未被取消或重新安排。
回滚应等待相关 kernel 完成，不能覆盖仍被访问的候选页。

**追问：**把 rejection 与 cancel 同时注入，检查页面守恒和输出去重。
**反例：**文本看似正确但 grammar 状态多走一步，会在后续结构化输出中出错。
**映射：**SPEC-009/010、SCH-014、CODE-019。

## 22｜TP、PP、DP、CP、EP 能否直接相乘？

**答案：**只有独立笛卡尔维度可以直接相乘。
普通 TP 切层内矩阵，PP 切层，DP 复制请求副本，CP 切上下文，EP 切专家。
某些 Attention DP/CP/TP 在已有物理 world 内分解，MoE 使用另一套分组视图。
需要先列实际 rank→GPU→node→NIC 和每个 group 的成员。

例如物理 world=8，attention DP=2、CP=2、TP=2，仍只有 8 个进程。
不能再把外层 8 与这三个维度相乘。

**追问：**权重、KV、dense replication 与 expert shards 分别记账。
**反例：**逻辑组数量多，不代表增加了同等数量的物理 GPU。
**映射：**DIST-001—006/011。

## 23｜MoE 四层均衡分别解决什么？

**答案：**训练均衡塑造 router 分布，专家复制增加等价物理副本，EPLB 调整专家位置，dispatch-time 为本批选择副本。
它们具有不同时间尺度和成本。
线上突发热点不会因为训练曾经均衡就消失。
迁移需要先准备并校验新权重，再提交 logical→physical map，最后等待旧读者退休。

每层延迟受最热专家、最慢 rank 与链路决定。
平均 token/expert 无法解释 tail，应拆 dispatch、GEMM、combine。

**追问：**重排能降低 rank 总负载，但不能拆开单个极热专家。
**反例：**把 token 发给另一不同专家是改模型语义，不是等价均衡。
**映射：**DIST-007—011、DESIGN-012。

## 24｜怎样算 PD 的网络下界与副本比？

**答案：**先算 KV 字节，再除以有效带宽并加控制、排队和 layout 成本。
标准例中 8K prompt、128 KiB/token 得 1 GiB；20 GiB/s payload 下界 50 ms。
若固定开销 3 ms，则至少约 53 ms，实际拥塞会更高。
副本比用平均 P/D 服务需求除目标利用率，不用请求 wall time 冒充独占需求。

假设 λ=12、P=0.08 副本秒、D=0.30、副本目标利用率0.7，得到 P=2、D=6。
若两类副本 GPU 数不同，还需另外换算总 GPU。

**追问：**先比较同 GPU 预算的 aggregated/chunked/PD。
**反例：**PD 并不自动提高 raw throughput。
**映射：**DIST-016—019、DESIGN-005。

## 25｜Occupancy 更高为什么还可能更慢？

**答案：**Occupancy 表示可驻留执行资源，不等于有效指令吞吐。
为提高 occupancy 缩小 tile，可能降低数据复用、增加同步和地址计算。
限制寄存器又可能产生 spill，增加 device memory 流量。
需要同时观察寄存器、shared memory、eligible warps、stall、实际 bytes 和时间。

Kernel 的目标是完成给定正确工作更快，而不是最大化某个比例。
一个资源用得更多但复用更好的 kernel，可能在较低 occupancy 下胜出。

**追问：**报告修改前后 spill 和 instruction count，解释机制。
**反例：**只看到 occupancy 从50%到100%不能宣布优化成功。
**映射：**KERN-005/006/016/017、CODE-017。

## 26｜为什么先 Nsight Systems 再 Nsight Compute？

**答案：**Nsys 先定位请求与 CPU/GPU/通信的时间线，判断瓶颈是否在 kernel。
NCU 再对代表性热点收集实际流量、执行单元、寄存器和 stall。
直接 profile 所有 kernel 会产生大量数据，重放还可能改变并发和缓存行为。
先缩小假设，再做重计数器采样更容易解释。

优化后仍需回到无 profiler 的端到端 A/B。
Profiler 中的 replay 时间不是正常服务延迟。

**追问：**使用 Amdahl 判断热点改善能否影响用户 SLO。
**反例：**一个占4%的kernel快2倍，总收益理论约2%。
**映射：**KERN-023—030、PERF-020。

## 27｜torch.compile、CUDA Graph 与手写 kernel 区别是什么？

**答案：**编译器捕获并变换计算，可能做分解、融合和代码生成。
CUDA Graph 复用既定 GPU 执行流程，主要减少 host launch 等开销。
手写 kernel 控制算子内部算法、布局、tile 和同步。
三者可以组合，但约束和收益来源不同。

动态 shape 可能触发 specialization/recompile，graph 还涉及地址、buffer 和 capture 约束。
不能把编译成功等同于所有请求都使用单一高效 graph。

**追问：**记录 graph hit、shape bucket、padding、编译时间和 fallback。
**反例：**17 token padding到32可能抵消部分launch收益。
**映射：**KERN-017/027/028。

## 28｜多租户为什么要四层背压？

**答案：**Gateway 保护连接、请求大小和基础速率；router/admission 保护队列、SLO 和副本资源。
Engine 保护 token/sequence/KV 等执行预算；writer 保护慢客户端输出 buffer。
只在最外层限 RPM，无法限制超长请求；只在 engine 限并发，又可能让 CPU/连接先爆。
取消和错误应沿层次传播，避免请求已离开但资源仍无限占用。

外部计费可按 token，内部应记录 GPU time、KV 和无效工作。
身份、模型授权与配额应分开校验。

**追问：**共享配额需要跨 gateway 原子性，不能每台各给完整额度。
**反例：**客户端自报 tenant_id 不构成可信认证。
**映射：**PROD-004—006/020、CODE-009。

## 29｜Startup、readiness、liveness 分别表示什么？

**答案：**Startup 允许较慢的初始化，readiness 决定现在是否接新流量，liveness 判断是否需要重启恢复。
模型加载包含 artifact、反序列化、H2D、组建立、JIT、graph 和 warm-up。
HTTP 端口可连不等于模型可服务。
错误 liveness 会反复杀掉还在正常加载的大模型。

缩容也应先摘流和 drain，再释放 GPU/传输资源。
探针路径和语义需核对实际服务实现，不能只复制 YAML。

**追问：**readiness 失败时不一定应重启，可能只是暂时不可接新请求。
**反例：**只配置短 liveness timeout 会造成永远启动不成功。
**映射：**PROD-009—011。

## 30｜部分流式输出后能否透明重试？

**答案：**从头重试可能产生重复文本、不同采样结果、重复工具调用和计费。
未输出前可在幂等和兼容约束下重试；输出后应明确中断或使用显式 resume。
Resume 至少需要事件序号、accepted tokens、模型/上下文身份和采样状态。
SSE 重连或 Last-Event-ID 不自动提供模型执行 checkpoint。

逻辑 request ID 与 attempt ID 应分开，便于审计和去重。
工具副作用还需要独立的操作幂等性。

**追问：**用户断开后，GPU/DMA 仍可能需要 drain 才能 free。
**反例：**把新回答直接拼在旧回答后面不能保证语义连续。
**映射：**PROD-001/003/014、DESIGN-006/008。

## 31｜有限显存部署 70B，第一张白板写什么？

**答案：**先写权重下界、KV、workspace/graph、通信和加载峰值。
70B BF16 权重约140GB，即130.39GiB；4-bit编码约35GB，但还需metadata与未量化层。
再根据模型KV结构、上下文与并发计算活动缓存。
最后筛选TP/PP/量化/模型变体等可行候选。

能加载只是容量约束，还需验证实际kernel、质量与SLO。
固定GPU预算下比较更多TP与更多副本，而不预设某并行度最佳。

**追问：**最满rank决定是否OOM，平均显存不能替代逐rank高水位。
**反例：**“35GB权重小于48GB，所以一定能服务”漏算KV与工作区。
**映射：**DESIGN-002、PERF-004—006。

## 32｜Prefix-aware router 如何避免热点？

**答案：**先过滤能力、健康、KV与队列硬限制，再比较预计完成时间。
评分应包含命中节省、queue、网络、恢复和hint过期风险。
Cache hint只是预测，worker lookup权威；过期应退化为安全miss。
可加负载上限、随机化和two-choice，避免多个来源追逐同一副本。

高命中长队列可能比低命中短队列更慢。
应记录predicted/actual reusable tokens和ETA误差。

**追问：**worker重启需要epoch失效与snapshot重建。
**反例：**最大化hit count不等于最小化TTFT。
**映射：**DESIGN-003/011、PROD-007/008、KV-020。

## 33｜p99 TPOT 突增但平均 TPS 不变，怎么查？

**答案：**先按时间、长度、租户、worker切分，找到具体长ITL。
关联长prefill、batch composition、KV pressure、抢占、graph miss与CPU阻塞。
再查逐rank/expert时间、通信链路、温度和频率。
平均TPS可能被其他请求补偿，不能排除局部starvation。

用正常/异常trace对照提出单一可验证假设。
必要时先限流、分池或回滚保护用户，再保留证据定位。

**追问：**客户端chunk合并也可能制造可见停顿。
**反例：**只看GPU平均util无法确定根因。
**映射：**DESIGN-010、PROD-012、KERN-024。

## 34｜手写 stable softmax 要处理什么边界？

**答案：**先减每行最大值，再计算指数和并归一化，通常使用FP32累加。
减最大值避免大正数导致exp溢出，但全mask、NaN和Inf仍要定义行为。
Log-softmax宜直接用$x-\operatorname{logsumexp}(x)$，避免先softmax下溢再取log。
如果分块，合并时需要按新的最大值重标旧指数和与输出。

测试随机、极值、空/最小shape、非连续stride与mask。
误差阈值应根据dtype和任务确定。

**追问：**全为负无穷时，直接减最大值会产生NaN，需要显式策略。
**反例：**“减最大值后永远稳定”忽略异常输入。
**映射：**CODE-001/002/011、FND-005/013。

## 35｜一个教学 allocator 怎样证明没有泄漏？

**答案：**建立固定物理pool，区分唯一allocated页与free页，检查总量守恒。
每请求block table与引用计数对应，fork共享完整页，写共享partial tail时COW。
分配失败必须事务回滚，不能留下半个请求的页面。
释放需要幂等，并等待异步读写完成。

用随机事件序列组合allocate/fork/append/cancel/free，比只测一条成功路径更有价值。
每一步都检查ref非负、owner一致和free/active互斥。

**追问：**ref=0的cached block可仍保留hash，复用前要移除旧索引。
**反例：**进程最终退出不等于运行期间没有资源泄漏。
**映射：**CODE-005—007/019。

## 36｜Collective hang 的检查顺序是什么？

**答案：**先收集全部rank最后进度和collective序号/type/count/dtype/group/stream。
核对是否有人更早OOM、异常或控制流分叉，导致没进入相同操作。
再做小world、单节点和固定tensor复现。
最后核对NIC/GPU/NUMA、RDMA、共享内存和网络，而不是先乱改一组环境变量。

失效组需要协调abort/restart。
单rank偷偷重建可能让其他rank永远等待旧序号。

**追问：**fail-slow与crash不同，最慢rank可能仍持续返回结果。
**反例：**NCCL timeout不直接证明网络坏了。
**映射：**CODE-020、DIST-020、PROD-014。

## 37｜如何用三分钟讲清一个优化项目？

**答案：**先给业务目标、模型/硬件/版本/workload和基线指标。
用trace说明瓶颈占比，提出可证伪假设和收益上限。
解释自己的具体改动、correctness/质量验证，再给受控A/B原始结果。
最后交代无收益区域、回归门禁、发布与回滚。

数字必须能从保存的样本重算。
“负责优化推理”不说明贡献，“某shape更快”也不能推广全服务。

**追问：**能否解释一个失败尝试及为什么预测错了？
**反例：**只展示最优shape与最好一轮，证据不完整。
**映射：**PROJECT-001—010。

## 38｜没有多机GPU，怎样做分布式项目仍然可信？

**答案：**先实现显存/通信字节、rank布局、P/D队列与生命周期模拟。
用CPU小算例验证协议不变量与break-even，明确参数是假设或来自指定来源。
有单GPU时补模型正确性与局部性能，不能把模拟延迟写成RDMA实测。
项目价值来自模型可解释、能被真实实验推翻和有失败边界。

若未来得到集群，直接用同一trace替换服务时间/带宽参数并比较预测误差。
这样形成可渐进验证的证据链。

**追问：**展示aggregated和PD各自胜出区域，而非预设PD更好。
**反例：**CPU事件循环每秒处理数百万事件不代表GPU生成吞吐。
**映射：**实践项目P6、DESIGN-005/007。

## 39｜读陌生推理仓库，如何避免只背类名？

**答案：**固定commit与dirty状态，选一个请求沿入口→token→queue→KV→forward→output→free追踪。
每个边界记录数据表示、owner、异步完成、异常路径和版本条件。
用符号定位后读取实际函数，列出已读范围，不把grep命中当完整覆盖。
跨框架比较按职责和不变量，而不是相似类名。

保留源码证据与教学模型的区别。
当前checkout静态成立，也不代表所有配置或硬件已运行验证。

**追问：**当旧资料路径变化，重新定位符号并记录实际路径。
**反例：**本文发现result processor位于`scheduler_components`，不能盲抄旧简写路径。
**映射：**PROJECT-006、SCH源码映射、KV源码映射。

## 40｜成本降低 40% 且质量不降，怎样答才严谨？

**答案：**先定义成本单位、质量阈值、SLO与统计置信度。
成本包含GPU、warm pool、CPU、网络、存储、失败与运维，按合格交付归一。
依次检查无效工作、排队/路由、缓存、并行、量化/spec与热点kernel，每项有A/B和反例。
如果证据只支持20%，就报告可实现范围与剩余瓶颈。

候选raw TPS下降也可能因达标率提高而降低单位合格成本。
不能通过删除失败请求或改变质量口径凑出收益。

**追问：**同时设置绝对SLO和相对回归门禁，artifact/runtime一起回滚。
**反例：**更多GPU带来更高TPS，但每百万合格token成本可能更高。
**映射：**DESIGN-015、PERF-019、PROD-015/016/020。

## 计算题复核脚本

```python
from math import ceil, exp, log

kv_per_token = 2*32*8*128*2
assert kv_per_token == 128*1024
assert kv_per_token*8192 == 2**30
assert sum(ceil(n/16)*16 for n in [17,31,33]) == 112
assert ceil(12*0.08/0.7) == 2
assert ceil(12*0.30/0.7) == 6
times = [0.5,0.54,0.58,0.9]
assert abs((times[-1]-times[0])/3 - 0.1333333333333333) < 1e-12

x = [1000.0, 1001.0, 999.0]
m = max(x)
z = sum(exp(v-m) for v in x)
p = [exp(v-m)/z for v in x]
logp = [v-(m+log(z)) for v in x]
assert abs(sum(p)-1) < 1e-12
assert all(abs(exp(lp)-pi) < 1e-12 for lp,pi in zip(logp,p))
print("capacity, page budget, PD ratio, timestamps and softmax passed")
```

该脚本不覆盖全mask、NaN/Inf、真实分页并发或GPU数值差异。
这些是题目要求继续补充的边界，而不是被基础断言证明的性质。
