## 多节点上线首先是身份一致性问题

两台机器都显示“模型加载成功”，不意味着它们加载了同一个模型。
权重目录名相同，也不能证明文件内容、tokenizer、chat template 和量化配置一致。
推理服务需要一份能够被各 rank 独立核验的部署身份。
然后才能讨论通信和性能。

本节采用一个 2 节点、每节点 4 GPU 的教学部署。
逻辑配置为 TP=4、PP=2，单副本共 8 rank。
具体框架是否支持目标模型的该组合，要以固定版本能力检查为准。
下文加载协议是工程设计，不是声称所有引擎已经实现同一套接口。

## 1. 四类身份不能混为一谈

| 身份 | 内容 | 解决的问题 |
|---|---|---|
| artifact | 权重和配置的内容哈希 | 是否同一模型 |
| runtime | 镜像、框架、CUDA、kernel | 是否同一执行契约 |
| topology | world、rank、TP/PP/EP groups | 如何分片和通信 |
| deployment epoch | 本次发布与进程世代 | 旧消息是否仍有效 |

模型目录里的文件时间戳不能替代内容哈希。
镜像标签 `latest` 不能替代镜像 digest。
同一个 global rank 在重启后仍需新的 process epoch。
否则旧进程的完成消息可能被误认为新进程已经 ready。

### 1.1 建议冻结的 manifest

```json
{
  "schema": 1,
  "model_id": "teaching-70b",
  "artifact_revision": "immutable-snapshot-id",
  "weights_digest": "sha256:...",
  "tokenizer_digest": "sha256:...",
  "template_digest": "sha256:...",
  "config_digest": "sha256:...",
  "quantization": "bf16",
  "kv_dtype": "bf16",
  "runtime_image": "registry/engine@sha256:...",
  "framework_commit": "fixed-commit",
  "world_size": 8,
  "tensor_parallel_size": 4,
  "pipeline_parallel_size": 2,
  "deployment_epoch": 17
}
```

省略号必须在真实发布前替换成真实摘要。
此 manifest 是示例格式，不是 vLLM 或 SGLang 的原生配置文件。
需要由发布控制面和 readiness wrapper 消费。

## 2. 先画 rank，再启动进程

教学映射如下：

| node | local GPU | global rank | PP stage | TP group |
|---|---:|---:|---:|---|
| A | 0 | 0 | 0 | 0、1、2、3 |
| A | 1 | 1 | 0 | 0、1、2、3 |
| A | 2 | 2 | 0 | 0、1、2、3 |
| A | 3 | 3 | 0 | 0、1、2、3 |
| B | 0 | 4 | 1 | 4、5、6、7 |
| B | 1 | 5 | 1 | 4、5、6、7 |
| B | 2 | 6 | 1 | 4、5、6、7 |
| B | 3 | 7 | 1 | 4、5、6、7 |

PP 通信连接两个 stage 的对应参与者。
真实 backend 可能对 activation 做 gather/scatter，不能仅凭这个表推断通信 payload。
表格还应补上 GPU UUID、PCIe bus、NUMA node、NIC 和可达 IP。

容器内 `CUDA_VISIBLE_DEVICES=0` 的 0 是逻辑序号。
它不一定对应宿主机编号 0。
设备身份应使用可追踪的 UUID，而不只保存可见序号。

## 3. 权重如何到达所有 rank

### 3.1 每节点独立读远端

优点是流程简单，节点可独立重试。
缺点是对象存储和网络可能承受重复下载。
同节点多个 rank 各读完整 checkpoint，又会放大本地文件系统压力。

### 3.2 节点缓存再由 rank 读取

先按 artifact digest 下载到临时目录。
校验成功后原子发布完成标记或重命名到只读路径。
各 rank 只读取已发布路径。
不可让 rank 在下载过程中读取同名未完成文件。

### 3.3 单读者加载后分发

可以减少重复远端读取。
但会引入单读者 CPU 内存、反序列化、网络广播和故障恢复成本。
某个阶段更快，并不证明整体启动更快。
还要处理量化重排、PP 分层、tensor shard 和不同节点的可用内存。

## 4. 启动时间模型与完整数例

若下载、解析、H2D、repack、warm-up 完全串行：

$$
T_{start}=T_{download}+T_{parse}+T_{H2D}
+T_{repack}+T_{group}+T_{warmup}.
$$

如果有 pipeline，关键路径更接近最长阶段与填充尾部。
必须以 timeline 验证重叠，而不是把每段时间直接相减。

假设一个 artifact 为 140 GB，远端有效读速率 2 GB/s。
单次完整下载至少需要 70 s。
两节点同时读，如果共享出口总计仍只有 2 GB/s，则总计 280 GB 至少需要 140 s。
“两台机器同时下载”不会自动让共享链路总吞吐翻倍。

若节点已有可信本地缓存，免去这部分下载，但仍有：

| 阶段 | 教学假设 |
|---|---:|
| 校验和读取 | 12 s |
| 解析与分片 | 18 s |
| H2D 与重排 | 15 s |
| 通信组建立 | 3 s |
| graph/JIT/warm-up | 25 s |

完全串行总计 73 s。
这些数值是教学输入，不是某 GPU 或框架的性能结论。
warm pool 的价值在于提前支付其中大量成本，代价是持续占用显存与设备。

## 5. 一次一致发布的状态机

```text
DISCOVER
  → FETCH_TEMP
  → VERIFY_ARTIFACT
  → PUBLISH_LOCAL_SNAPSHOT
  → CREATE_GROUPS
  → LOAD_SHARDS
  → VERIFY_RANK_IDENTITY
  → WARMUP
  → GROUP_READY
  → ROUTABLE
```

每一步都需说明 owner、超时、重试与失败清理。
`GROUP_READY` 需要所有必要 rank 满足相同 deployment epoch。
某个 rank 的端口可连接，只能证明进程在监听。
它不能证明其他 rank、模型和通信组已经可用。

### 5.1 为什么 ready 需要全组约束

若 stage 0 已 ready、stage 1 仍在加载，入口开始接流量会占住 stage 0 的 KV 和队列。
等后段启动完成时，队列可能早已超过 SLO。
若 stage 1 最后失败，还需要清理所有未完成请求。
因此路由单位通常应是可共同执行请求的完整副本。

### 5.2 模型切换需要双版本隔离

发布新 artifact 时，旧请求继续使用旧模型和旧 KV identity。
新请求在新副本完成 warm-up 后渐进路由过去。
不要在仍有活跃请求时把原权重目录替换成另一模型。
更不能让一个请求的前半段使用旧权重、后半段使用新权重。

## 6. 可运行的身份一致性检查

以下代码构建纯内存 manifest 和 rank records。
它演示启动屏障如何拒绝混合版本，不执行集群操作。

```python
import hashlib
import json

def digest(value):
    raw = json.dumps(
        value,
        sort_keys=True,
        separators=(",", ":"),
        ensure_ascii=False,
    ).encode()
    return hashlib.sha256(raw).hexdigest()

manifest = {
    "artifact": "snapshot-a",
    "tokenizer": "tokenizer-a",
    "runtime": "image-digest-a",
    "tp": 4,
    "pp": 2,
    "epoch": 17,
}
expected = digest(manifest)

def group_ready(records):
    if len(records) != 8:
        return False
    ranks = {r["rank"] for r in records}
    if ranks != set(range(8)):
        return False
    return all(
        r["digest"] == expected
        and r["epoch"] == 17
        and r["warmup_ok"]
        for r in records
    )

records = [
    {
        "rank": rank,
        "digest": expected,
        "epoch": 17,
        "warmup_ok": True,
    }
    for rank in range(8)
]
assert group_ready(records)

records[7]["digest"] = digest({**manifest, "artifact": "snapshot-b"})
assert not group_ready(records)
records[7]["digest"] = expected
records[7]["epoch"] = 16
assert not group_ready(records)
records[7]["epoch"] = 17
records[7]["warmup_ok"] = False
assert not group_ready(records)
print("mixed artifact, stale epoch, incomplete warmup rejected")
```

真实控制面还需验证报告者身份，不能信任任意客户端提交的 digest。
哈希保证内容一致性，不单独提供来源认证。
模型来源、镜像签名和访问权限属于另一层信任边界。

## 7. Ray、进程管理与通信的职责

Ray 可参与跨节点进程编排、资源分配和 placement。
NCCL 负责相应 GPU collective/P2P 通信。
框架负责模型分片、调度和请求执行。
这些组件的“运行成功”是不同层的信号。

```text
编排层: 节点可用、资源满足、worker 已启动
模型层: shard 身份正确、加载和 backend 校验通过
通信层: group 成员与调用序列一致
服务层: 请求可执行、流式输出和取消正确
```

先验证 placement 是否满足 TP 高速域要求。
再确认框架日志中的实际 distributed backend。
不能仅因机器安装 Ray 就认定当前引擎使用 Ray 执行。
同样，进程互相 ping 通不能证明 GPU Direct/RDMA 路径生效。

## 8. Collective hang 的证据顺序

先收集所有 rank 的最后成功步骤。
每个 collective 记录 group、序号、类型、count、dtype、stream 和张量 shape。
然后比较是否有 rank 根本没有进入该操作。

常见故障链是：

```text
rank 3 earlier OOM
  → rank 3 未进入下一次 AllReduce
  → 其他 rank 等待
  → 表面呈现 NCCL timeout
```

这时首先修复的是更早的 OOM。
直接调整 NCCL timeout 只会让等待更久。

| 检查顺序 | 证据 |
|---|---|
| 1 | rank/world/device/group 是否一致 |
| 2 | collective 序号和类型是否一致 |
| 3 | 是否有早先 Python/kernel/OOM 错误 |
| 4 | 单节点小 world 是否复现 |
| 5 | GPU/NIC/NUMA 与网络配置 |
| 6 | 通信算法和环境变量的单变量实验 |

一旦通信组失效，应按框架支持的方式整体隔离或重建。
不能让单个 rank 偷偷重启并加入仍执行旧操作的其他 ranks。

## 9. 失败、回滚与流式语义

启动阶段失败可以重试同一 immutable artifact。
但重试应保留已验证缓存，清理未发布临时文件。
运行阶段失败则需要先从 router 摘除整个受影响副本。

未输出 token 的请求可按幂等策略尝试其他兼容副本。
已经输出 token 的请求需要向用户报告中断或使用显式恢复协议。
把请求从头重跑并直接拼接新 stream 会产生重复或分叉。

回滚至少包含：

- 模型 artifact。
- tokenizer 与 chat template。
- runtime image 和框架 commit。
- backend、量化和 KV layout。
- 路由与配额配置。
- 对应的 cache namespace/epoch。

旧版本 KV 不一定能被回滚后的进程直接使用。
缓存失效成本应计入回滚容量预案。

## 10. 六道追问与答案

### Q1：同名模型目录是否足够保证一致？

不足够。
应核对文件内容、配置、tokenizer、template 和运行时身份。
下载未完成的目录还必须与已发布快照隔离。

### Q2：为什么 readiness 不能只检查 HTTP 200？

HTTP 监听可能早于权重加载和通信组初始化。
应由明确的模型/组/warm-up 状态决定是否可接流量。
一个健康端口无法替代全副本 readiness。

### Q3：加载峰值为什么高于稳态？

源权重、目标 shard、repack 输出和临时 buffer 可能同时存活。
需要按阶段测量 CPU 与 GPU 高水位。
只看服务稳定后的显存会漏掉启动 OOM。

### Q4：NCCL timeout 就说明网络坏了吗？

不说明。
某 rank 更早报错、控制流分叉、count 不一致都可能造成等待。
应先对齐所有 rank 的时间线和 collective 序号。

### Q5：一个副本需要 8 GPU，缺一张能否先接请求？

常规固定 TP/PP group 不可以。
要么按受支持的弹性协议重新分片建立新组，要么保持副本不可路由。
不能临时跳过缺失 shard。

### Q6：并行下载为何可能让启动更慢？

多个节点争用同一出口、对象存储限流或本地磁盘。
并行反序列化还可能耗尽 CPU 内存。
应测关键路径和共享资源，而不是最大化线程数。
