## 先拆开五个名字相似的问题

“KV cache”可以指一块 GPU 内存，也可以指跨请求索引或远端缓存系统。
如果不区分层次，设计容易让 router 管物理页面，让传输完成消息替代语义校验。
本节按 owner 和生命周期拆开这些概念。

| 层 | 回答的问题 | 权威状态 |
|---|---|---|
| Allocator | token 对应哪些本地物理页 | page pool、block table |
| Prefix index | 哪段连续前缀可复用 | radix/hash、语义 key |
| Hierarchical cache | 数据驻留在哪一层 | cache controller、异步操作 |
| P→D handoff | 此请求如何交接给 D | 请求事务、两端 reservation |
| KV-aware router | 请求发到哪个副本 | hint、负载和健康视图 |

五层可以组合，不能彼此替代。
特别是 router 的预测命中不能作为 KV 实际存在的证明。
真正的 lookup、版本匹配和可读检查必须由 worker 完成。

## 1. 同一前缀的语义身份

两个字符串看起来相同，不一定能复用 KV。
需要比较实际 token IDs 和影响隐藏状态的上下文。
至少考虑：

- 权重 artifact。
- tokenizer 与 special tokens。
- chat template。
- LoRA/adapter。
- position IDs 和 RoPE 配置。
- attention mask 与窗口规则。
- 多模态 encoder/输入身份。
- KV dtype 与布局兼容性。
- tenant 或安全域。

生成 temperature 通常不改变已给定 prompt 的前向隐藏状态。
但如果输入包含之前采样出的不同 token，前缀自然已经不同。
cache key 应围绕计算语义，而不是把所有 HTTP 参数盲目拼在一起。

### 1.1 只能复用连续前缀

假设请求 A 的 token 为：

```text
[10, 20, 30, 40, 50, 60]
```

请求 B 为：

```text
[10, 20, 99, 40, 50, 60]
```

普通 causal Transformer 最长可复用前缀只有前两个 token。
后面虽然再次出现 `40,50,60`，其隐藏状态依赖已经不同的上文。
不能按文本子串相同就复用这些 KV。

## 2. 分页与跨请求索引的关系

Allocator 保存物理页，prefix index 保存语义前缀到页的映射。
某个页可以被多个请求引用。
完整共享页只读，部分尾页继续写时可能需要 COW。

```text
prefix index
  └─ tokens [10,20,30,40]
       └─ physical blocks [7,12]

request A block table: [7,12,18]
request B block table: [7,12,25]
```

请求 A 结束后，不能直接释放 7、12，因为请求 B 或 prefix cache 仍持有引用。
反过来，prefix index 删除节点，也不代表正在执行的 GPU kernel 已停止读取页面。
逻辑引用和异步访问引用必须同时归零。

## 3. HiCache 的数据层次

可将驻留位置抽象为：

```text
L1: GPU KV pages
       ↕ device-host transfer
L2: host memory
       ↕ storage backend
L3: local SSD / remote storage
```

这只是层次模型；具体实现可能把 host memory 用作 staging 而非完整 L2。
SGLang 固定源码中的 `UnifiedRadixCache.init_hicache()` 负责初始化相关能力。
不能仅看到该函数存在，就认定所有 storage backend、模型或 attention 路径都已启用。
真实配置必须核对 backend、内存布局、缓存策略和启动日志。

### 3.1 命中不等于立即可读

Prefix index 可能知道某段 KV 在 CPU 或远端。
它的语义是“可尝试恢复”，不是 GPU attention 此刻就能读取。
需要先在目标 GPU 保留页，启动加载，并在消费前等待完成。

```text
INDEX_HIT
  → TARGET_RESERVED
  → LOAD_QUEUED
  → LOADING
  → READY
  → ATTENTION_READ
```

加载失败必须转为受控重算或请求失败。
不能把尚未填满的页面当成有效缓存继续 decode。

## 4. vLLM Connector 的两个角色

固定基线的 `KVConnectorBase_V1` 是 scheduler/worker 生命周期契约。
它可以承接请求 handoff、外部缓存或 offload 等不同用途。
Connector 名称相同，不代表所有实现具备相同错误恢复和数据一致性能力。

| 角色 | 主要责任 |
|---|---|
| Scheduler | 判断外部可用数据、安排页面、生成操作 metadata |
| Worker | 执行传输、等待可读、报告完成与加载错误 |

metadata 是控制信息，不应偷偷拥有不受跟踪的页面生命周期。
实际物理 buffer 的 owner 和释放回调必须明确。

### 4.1 按执行顺序理解接口

固定源码中的关键接口包括：

```text
start_load_kv(forward_context)
wait_for_layer_load(layer_name)
save_kv_layer(layer_name, kv_layer, attention_metadata)
wait_for_save()
get_finished(finished_request_ids)
request_finished(request, block_ids)
```

`start_load_kv` 发起加载。
`wait_for_layer_load` 在某层读 KV 之前确保该层可用。
`save_kv_layer` 可以在层执行过程中启动保存。
`wait_for_save` 表达保存相关的同步边界。

`request_finished` 返回异步接管标志时，不能立即归还请求页面。
需要等待 connector 通过 `get_finished` 报告对应传输完成。
具体 connector 可能采用不同粒度的同步，但必须满足这个 ownership contract。

### 4.2 请求结束与传输结束不是同一事件

```text
generation complete
  → request_finished says async ownership retained
  → response may complete
  → transport still reads source KV
  → get_finished reports completion
  → allocator can reclaim pages
```

客户端已经收完答案，不表示 GPU 页面可以重用。
异步保存仍可能读取它们。
同理，best-effort cache save 失败与必须成功的 P→D handoff 失败具有不同语义。

固定基线还区分 `requires_kv_delivery`。
请求交接必须保证数据可靠送达；可丢弃的缓存保存失败通常只是未来 cache miss。
将两者统一成“失败就忽略”会破坏 PD correctness。

## 5. Offload 与重算的 break-even

设需要恢复 $B$ 字节 KV，有效带宽为 $\beta$：

$$
T_{load}=T_{fixed}+\frac{B}{\beta}
+T_{queue}+T_{layout}+T_{dequant}.
$$

重算成本使用同 workload 下测量的 prefill 时间：

$$
T_{recompute}=f(T_{miss},batch,context,backend).
$$

只有当加载更快且不显著挤占其他关键资源时，恢复才值得。
不能把固定的“每 token prefill 时间”推广到所有长度和 batch。
attention 的非线性成本和 GEMM 利用率都会改变这个函数。

### 5.1 完整数例

8K prefix 的 KV 为 1 GiB。
假设 CPU→GPU 有效带宽 24 GiB/s，固定与 layout 合计 4 ms：

$$
T_{load}=1000/24+4\approx45.67\ \mathrm{ms}.
$$

若重算需 180 ms，恢复约节省 134.33 ms。
若远端路径有效带宽降到 4 GiB/s，且固定排队为 30 ms：

$$
T_{remote}=250+30=280\ \mathrm{ms}.
$$

此时重算 180 ms 更快。
但如果 GPU 当时拥堵而网络空闲，考虑排队后的结论可能再次变化。
应比较当前关键路径上的预计完成时间，而不只比较孤立设备时间。

## 6. 复用概率与缓存价值

设一段 KV 大小为 $B_i$，未来命中概率为 $p_i$，单次节省时间为 $s_i$。
一个简单价值密度是：

$$
v_i=\frac{p_i s_i}{B_i}.
$$

还可加入写入成本、租户配额、过期概率和 SLO 权重。
这说明“最长前缀一定最值得缓存”并不成立。
很长但几乎不会复用的前缀，可能挤掉大量稳定热点。

驱逐只能从安全集合选择：

$$
refcount=0\land locks=0\land inflight=0.
$$

LRU/LFU/cost-aware 只决定安全候选之间的顺序。
它们不能推翻正在读写的页面不可回收这一约束。

## 7. Router events 是提示而非所有权

缓存事件可以包含：

```text
worker_id
worker_epoch
model_identity
event_sequence
stored / removed / all_cleared
prefix_or_block_hash
residency_tier
```

Router 可能丢事件、延迟处理或在 worker 重启后保留旧视图。
因此需要 epoch、序号缺口检测、TTL 和周期 snapshot。
即使预测过期，也应只损失性能。
worker authoritative lookup 负责阻止错误复用。

### 一个反例

Router 认为 A 有 8K prefix，B 没有。
A 的排队预计 400 ms，命中能省 180 ms；B 的排队只有 20 ms。
即使 A 的 cache hint 完全正确，选 A 仍可能慢 200 ms。
路由应综合 queue、命中节省和 miss 风险，而不是最大化 hit count。

## 8. 可运行的缓存选择小算例

```python
GiB = 2**30
payload = GiB
local_ms = (payload / (24 * GiB)) * 1000 + 4
remote_ms = (payload / (4 * GiB)) * 1000 + 30
recompute_ms = 180
assert local_ms < recompute_ms < remote_ms
print(round(local_ms, 3), remote_ms, recompute_ms)

def expected_ttft(queue_ms, hit_probability, load_ms, recompute_ms):
    return queue_ms + (
        hit_probability * load_ms
        + (1 - hit_probability) * recompute_ms
    )

# A 的缓存更热，但排队更长。
a = expected_ttft(400, 0.95, local_ms, recompute_ms)
b = expected_ttft(20, 0.0, local_ms, recompute_ms)
assert b < a
print("A", round(a, 3), "B", round(b, 3))

def reusable_prefix(a, b, block_size):
    matched = 0
    for x, y in zip(a, b):
        if x != y:
            break
        matched += 1
    return matched // block_size * block_size

assert reusable_prefix([10,20,30,40], [10,20,99,40], 2) == 2
assert reusable_prefix([10,20,30], [10,20,30], 2) == 2
print("only complete, continuous prefix blocks reused")
```

示例省略了首 token logits 的特殊处理。
真实引擎即使命中整个 prompt，也可能需要重新执行末尾 token 以生成 logits。
不能把完整前缀命中等同于零 GPU 工作。

## 9. 配置核验与观测

分层缓存配置至少保存：

| 项目 | 必须确认 |
|---|---|
| backend | 安装版本、支持的内存类型 |
| layout | page size、KV dtype、模型结构 |
| capacity | GPU/CPU/远端配额和 staging |
| policy | write-through/write-back、预取阈值 |
| lifecycle | cancel、timeout、drain、重启 |
| isolation | tenant namespace、ACL、身份哈希 |

观测应同时记录 predicted hit 与 actual reusable tokens。
还要记录恢复字节、等待时间、传输失败、重算回退和 p99。
高 hit rate 但高 TTFT 可能由热点排队、远端慢恢复或 decode 主导造成。
只看命中次数很容易忽略命中的长度和成本。

## 10. 六道追问与答案

### Q1：Connector 就是 prefix cache 吗？

不是。
Connector 是引擎与外部 KV 操作的生命周期接口；prefix cache 是语义前缀索引。
一个 connector 可以传输请求 KV，也可以对接远端缓存。

### Q2：Router 能否直接确认某个 prefix 已经 ready？

它只能预测。
最终 worker 必须检查语义 key、驻留和异步完成状态。
最终一致的路由视图不能承担 correctness 权威。

### Q3：GPU 页引用计数为零是否可驱逐？

还不够。
异步 kernel、DMA、connector save 可能仍访问该页。
必须同时满足所有相关事件完成或数据面已经被可靠隔离。

### Q4：为什么相同文本不能保证 cache hit？

tokenizer、template、adapter、position 或多模态上下文可能不同。
即使 token IDs 相同，模型 artifact 与语义配置也必须兼容。

### Q5：Offload 扩大容量是否必然提高吞吐？

不必然。
传输、排队和重复驻留可能大于重算或直接拒绝的成本。
需要按负载比较 saved compute、bytes moved 和 goodput。

### Q6：全 prompt 命中为什么还可能计算最后一个 token？

缓存通常保存 K/V，并不一定保存所需 logits。
为了采样下一个 token，框架可能需要末尾 hidden/logits 计算。
应读实际命中长度处理，不能凭“100% hit”推断零计算。
