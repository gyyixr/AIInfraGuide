## 优化应交付可复核的收益

一次 kernel 提速、量化或调度改动，最终要回答四个问题：

1. 输出和协议是否仍正确？
2. 模型质量是否在业务允许范围内？
3. 实际 workload 的 SLO-goodput 是否改善？
4. 为此付出的总成本是否值得？

这四个问题必须联合评估。
单独追求 output TPS，可能通过拒绝难请求、缩短输出或降低模型质量获得表面收益。
本节用可审阅的实验契约避免这些混淆。

## 1. Correctness 与模型质量分层

| 层 | 典型问题 | 检查方法 |
|---|---|---|
| 算子数值 | mask、越界、精度、stride | reference + 边界 shape |
| 引擎语义 | stop、sampling、KV、cancel | golden 请求 + 状态不变量 |
| 协议 | chunk、finish、usage、重试 | 客户端契约检查 |
| 模型能力 | 推理、语言、长上下文、工具 | 业务分群评测 |

浮点输出不必始终逐 bit 相同。
但“有浮点误差”不能用来解释 shape 错误、KV 污染或 mask 语义变化。
误差阈值应由 dtype、算子和业务决定，而不是通用写死 `1e-3`。

量化可能在平均任务上几乎不变，却损伤长 context 或特定语言。
因此质量必须分群，不只报告一个总分。

## 2. 固定实验身份

一份比较至少冻结：

```text
GPU model/count/topology
driver + CUDA + framework commit
model artifact + tokenizer + template
weight/KV dtype + quantization metadata
actual attention/GEMM/MoE backend
TP/PP/DP/EP/CP groups
workload trace + sampling + EOS policy
queue/admission/token/KV budgets
warmup + cache policy + measurement window
```

如果同时更换模型、硬件和调度参数，结果仍可用于产品选择。
但不能把全部差异归因于一个 kernel patch。
工程报告应区分“系统方案比较”和“单变量因果实验”。

## 3. 交错 A/B 比先跑 A 再跑 B 更稳健

设备温度、频率、背景负载和缓存会随时间变化。
全部 A 在冷机器上跑、全部 B 在热机器上跑，容易制造趋势偏差。
可以使用随机化或交错顺序：

```text
A B B A | B A A B | A B B A
```

每对实验使用相同 trace seed、长度与缓存初始化策略。
冷缓存和热缓存分别比较。
不要让 B 无意中继承 A 预热好的 prefix cache，而 A 每次从空缓存开始。

对于生产 trace，可以配对计算每轮 goodput 和 p99 差异。
当变化小于噪声时，应报告“不确定”，而不是保留更好看的那一轮。

## 4. 相对回归与绝对 SLO 同时检查

设基线 p99 TPOT 为 $p_A$，候选为 $p_B$：

$$
Regression=\frac{p_B-p_A}{p_A}.
$$

如果允许相对退化不超过 5%，还必须满足业务绝对上限。

例如：

```text
baseline p99 TPOT = 49 ms
candidate p99 TPOT = 51 ms
relative regression ≈ 4.08%
absolute SLO = 50 ms
```

候选虽然低于 5% 相对阈值，却已经违背绝对 SLO。
反过来，10→10.6 ms 的 6% 退化可能远低于 SLO，但仍应解释原因。
门禁可以按严重程度区分阻断、复测与观察，不能只有一个百分比。

## 5. 完整成本数例

以每百万合格输出 token 成本为例：

$$
C_{million}=\frac{C_{hour}}{GoodTokens_{hour}}\times10^6.
$$

方案 A：每小时总成本 40 个成本单位，原始输出 120 万 token，80% 满足联合要求。
则合格输出 96 万，单位成本约：

$$
40/0.96\approx41.67.
$$

方案 B：每小时总成本 34，原始输出 110 万，95% 合格。
合格输出 104.5 万，单位成本约：

$$
34/1.045\approx32.54.
$$

单位合格 token 成本下降约：

$$
1-32.54/41.67\approx21.91\%.
$$

B 的 raw token 吞吐更低，但合格交付更多且成本更低。
这是一个教学账本，货币单位与硬件价格均为假设。
不能把该百分比写成某优化技术的普遍收益。

### 5.1 成本不能只数运行中的 GPU

总成本至少包括：

- GPU 使用与空闲容量。
- warm pool 和故障余量。
- CPU、内存和网络。
- artifact 与 KV storage。
- PD 复制和传输。
- 量化校准、编译与运维成本。
- 失败、重试和取消产生的无效工作。

如果 warm pool 让冷启动 SLO 达标，它的空闲时间仍然是服务成本。
如果部署更复杂导致恢复更慢，也应评估其可用性和运维代价。

## 6. 质量约束下的优化顺序

先修复无效工作和系统配置，再考虑改变模型行为的方案。
一条常见顺序是：

```text
修负载与测量口径
  → admission / routing / idle capacity
  → continuous batching / chunk / prefix
  → CPU / graph / layout
  → 并行拓扑与分池
  → quant / speculative / model routing
  → 热点 kernel
```

这不是固定排名。
若 trace 已证明热点 kernel 占 70%，可以优先处理它。
关键是每一步有假设、收益上限、验证和回退。

“成本必须降 40%”不意味着工程上一定存在满足质量约束的方案。
若证据只支持 22%，应报告可达到的范围与剩余瓶颈。
不能通过改变质量口径凑出目标。

## 7. 性能 CI 分成三个层次

| 层次 | 目的 | 合适的内容 |
|---|---|---|
| PR | 快速挡明显回归 | 核心正确性、小 shape、协议 |
| Nightly | 覆盖真实引擎行为 | trace、长短混合、取消、cache churn |
| Release | 上线风险评估 | 多硬件、长稳、故障、质量全矩阵 |

每个层次保存原始样本和环境。
PR microbenchmark 不能替代 release 的端到端质量评估。
长稳验证应关注内存增长、retiring bytes、错误、温度与缓存 churn。
只在服务启动后测 30 秒可能错过资源泄漏。

### 7.1 推荐的门禁结果

```text
PASS
  correctness, quality, stability, SLO, cost all within contract

RETEST
  small difference overlapping known noise band

BLOCK
  semantic error, quality breach, hard SLO breach, memory leak
```

RETEST 要有预算与结束条件。
不能无限重复直到出现一轮通过。
复测规则应在看到候选结果前定义。

## 8. 可运行的联合门禁

```python
def gate(candidate, baseline):
    reasons = []
    if not candidate["correct"]:
        reasons.append("correctness")
    if candidate["quality_drop_pp"] > 0.5:
        reasons.append("quality")
    if candidate["p99_tpot_ms"] > 50:
        reasons.append("absolute_slo")
    rel = candidate["p99_tpot_ms"] / baseline["p99_tpot_ms"] - 1
    if rel > 0.05:
        reasons.append("relative_regression")
    if candidate["error_rate"] > 0.01:
        reasons.append("errors")
    return reasons

baseline = {"p99_tpot_ms": 49}
candidate = {
    "correct": True,
    "quality_drop_pp": 0.2,
    "p99_tpot_ms": 51,
    "error_rate": 0.001,
}
assert gate(candidate, baseline) == ["absolute_slo"]

def cost_per_million(hourly_cost, raw_tokens, qualified_fraction):
    return hourly_cost / (raw_tokens * qualified_fraction) * 1_000_000

a = cost_per_million(40, 1_200_000, 0.80)
b = cost_per_million(34, 1_100_000, 0.95)
print("A", round(a, 3), "B", round(b, 3))
print("saving_percent", round((1-b/a)*100, 3))
assert b < a
```

质量阈值 0.5 个百分点只是示例。
真实质量指标要考虑样本量、置信区间、业务严重程度和分群下限。
不同任务不能共用一个未经讨论的阈值。

## 9. 质量评测的常见误判

### 9.1 只比较 greedy 文本完全一致

这能发现部分明显回归，但不足以评估随机采样和任务质量。
微小 logits 变化可能在长生成中放大为不同文本，而质量仍等价。
也可能短 golden 全通过，长上下文能力已经下降。

### 9.2 只看平均分

总分可能被高频简单任务主导。
应单独报告长 context、工具调用、结构化输出、语言和关键业务。
重要分群退化不能被其他分群提升抵消。

### 9.3 把长度变化当速度提升

候选因为 stop bug 提前终止，会显得 E2E 更短。
若量化使模型更早结束，工作量和质量也发生改变。
需要同时记录 OSL、finish reason、任务完成度与吞吐。

## 10. Shadow、Canary 和逐级放量

Shadow 将真实请求复制到候选，但不把候选输出交给用户。
它会增加资源消耗，并可能改变原服务负载，容量需预留。
涉及用户数据时沿用已有权限、隔离与保留策略。

Canary 将小比例真实流量交给新版本。
路由应尽量保留请求分布，避免只把简单短请求送给候选。
监控应按模型版本、租户、长度和硬件分组。

```text
offline gate
  → shadow
  → small canary
  → larger canary
  → full rollout
  → long-run observation
```

每个阶段都有观察窗口、晋级条件与自动回退条件。
观察窗口至少应覆盖相关缓存周期和代表性 burst。
不能在几分钟平稳低峰后就宣布长稳完成。

## 11. 回滚需要完整版本集合

回滚不只是把 Python 文件改回去。
应同步恢复：

```text
model artifact
tokenizer / template
runtime image / framework commit
kernel / backend / quant config
KV layout / cache namespace
router policy / quota / admission
```

旧 cache 与新版本不兼容时要安全失效。
清缓存会产生额外 prefill，回滚时可能出现短期容量压力。
应准备 warm pool、限流或渐进流量切换。

已流式输出的请求也需要确定归属。
通常让健康旧请求 drain，新请求按回滚配置进入。
若旧版本已经不安全，则按明确协议中断，不能静默拼接另一版本输出。

## 12. 优化项目的证据包

| 文件/记录 | 内容 |
|---|---|
| hypothesis | 瓶颈、预测收益和失败条件 |
| environment | 硬件、版本、artifact |
| workload | trace、seed、长度和缓存策略 |
| correctness | reference、边界和状态检查 |
| quality | 任务分群与阈值 |
| raw metrics | 每请求时间戳和结果 |
| profile | 关键 timeline、实际 kernel |
| rollout | canary、告警、回滚步骤 |

报告还应包含无收益区域和未覆盖硬件。
失败优化也有价值，只要能解释哪个预测被数据证伪。
不要删除失败样本后只保留最佳 speedup。

## 13. 六道追问与答案

### Q1：吞吐增加 20%，为什么成本可能上升？

可能使用了更多 GPU、网络、warm pool 或重试。
也可能 SLO 达标率下降，合格输出反而减少。
应按相同质量和服务目标归一总成本。

### Q2：p99 回归 4%，为何仍阻断？

候选可能跨过业务绝对 SLO。
相对阈值用于发现变化，绝对阈值用于保护体验。
两者需要同时检查。

### Q3：为什么量化要测长上下文？

KV 误差、outlier 和位置分布可能在长序列中放大。
短任务通过不能证明长 context 的质量保持。
weight quant 与 KV quant 还应分别评估。

### Q4：一轮 A/B 提升 2% 可以宣布成功吗？

如果噪声也在同一量级，证据不足。
应按预先规则重复、交错、保存原始结果，并报告不确定性。
不能只挑最优轮次。

### Q5：Canary 只放短请求是否更安全？

可以作为最早阶段，但不能代表全部业务。
晋级前仍需覆盖长请求、低频关键任务和 burst。
应明确它验证的是哪个子域。

### Q6：如何回答“成本降 40%，质量不能降”？

先固定成本单位、质量阈值与 SLO，再列证据支持的候选和收益上限。
逐项实验，保留反例和剩余瓶颈。
若做不到，应给可证明范围，不能承诺不存在的收益。
