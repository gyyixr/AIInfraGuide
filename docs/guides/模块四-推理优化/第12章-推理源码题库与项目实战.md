## 从知道概念到能够答辩

能定义TP、KV和continuous batching，只是第一层能力。
进一步需要手算容量、画请求状态、定位源码、解释反例，并运行可检查的小实验。
项目则把这些知识连接成完整的正确性与性能证据。
本章围绕这两个目标组织。

参考宝典有235题与十三类能力。
本章选择40个综合问题深答，不声称40题逐一替代全部235题。
每题附追问、反例和参考编号映射，便于回查原能力索引。
12.3另为全部235个原ID提供独立答案要点和本站文章入口，并逐类校验无遗漏。

## 1. 十三类能力地图

| 类别 | 要证明的能力 |
|---|---|
| FND | token、shape、Decoder数据流 |
| PERF | 指标、容量、负载、成本 |
| KV | 页、prefix、refs、异步生命周期 |
| SCH | 预算、chunk、抢占、公平 |
| ATTN | exact/IO、online softmax、长上下文 |
| QUANT | 格式、kernel、质量与硬件 |
| SPEC | 概率校正、成本与回滚 |
| DIST | rank groups、通信、MoE、PD |
| KERN | 地址、同步、profiling、编译 |
| PROD | 认证、配额、stream、恢复 |
| DESIGN | 约束、容量、架构取舍 |
| CODE | 可运行算法与状态不变量 |
| PROJECT | 原始证据、贡献与失败复盘 |

类别之间必须连接。
例如KV量化同时影响容量、kernel、质量和服务成本。
只在单一类别中背答案，容易在追问时失去边界。

## 2. 每题的四层回答

```text
定义
  → 公式/状态/数据流
  → 源码或实验依据
  → 条件、反例与验证方法
```

定义要短，推演要具体。
性能数字必须绑定模型、硬件、版本和workload。
没有实测时，明确说这是公式或教学假设。
源码固定commit与动态API也要分开。

## 3. 八类项目阶梯

1. 容量与时间戳实验室。
2. Mini Serving Engine。
3. SGLang/vLLM固定版本A/B。
4. 单GPU算子优化。
5. 量化与投机联合回归。
6. PD/Wide EP容量与故障模拟。
7. 三租户生产平台与故障演练。
8. 一个窄而完整的上游改进。

每个项目都按约束、成本、机制、验收、回退展开。
没有集群可以先做CPU模型，但不能冒充RDMA或多GPU实测。
单GPU证据也不能外推其他架构的专有原语。

## 4. 系统设计先写哪些数字

先区分日活、连接、RPS、GPU活跃序列。
再写ISL/OSL、prefix、burst、SLO、质量和成本。
根据单副本画像估容量，并加入per-rank显存和故障域。
之后才讨论router、PD、EP或多Region。

一个方案至少给两个候选和break-even。
每个故障都回答detect、contain、recover、correctness和user语义。
不承诺流式生成天然exactly-once。

## 5. 十二周路线的节奏

第1—2周建立数据流、容量和指标。
第3—4周实现KV与scheduler不变量。
第5—6周处理attention、spec与量化。
第7—8周完成一个真实算子与profile证据。
第9—10周学习分布式与生产故障。
第11—12周收口项目、模拟面试并查漏。

每周保留原理、源码、项目、口述四类活动。
最后阶段优先补齐已有项目证据，不无限增加新名词。

## 6. 项目报告必须包含

| 内容 | 目的 |
|---|---|
| baseline与环境 | 明确比较对象 |
| reference与边界 | 防止少算伪提速 |
| trace/profile | 证明瓶颈 |
| 单一假设与ablation | 解释因果 |
| 原始A/B与重复 | 识别噪声 |
| 质量/故障回归 | 保护语义与稳定性 |
| 失败尝试与限制 | 明确适用域 |
| rollout/rollback | 连接真实交付 |

README写“提升2倍”必须能追到原始样本。
没有数字也可以交付清晰机制和通过的正确性验证。
不要编造性能以填满简历。

## 7. 学习验收与来源

能在十分钟内画一条请求生命周期并算对KV单位。
能解释一个性能反例和一个异步资源错误。
能从固定源码找出支撑结论的函数与条件。
能重跑自己的实验，并承认尚未覆盖的边界。
