## 故障处理是正常数据流的一部分

推理系统不只需要回答请求成功时经过哪些组件。
还要回答其中一个 rank、网络连接或 KV 传输失败时，谁停止写入、谁释放页面、用户看到什么。
“失败重试”不是完整方案。
不同阶段的请求具有不同的可重试性和资源风险。

本节采用一个多租户、流式、长短请求混合的平台作为主线。
所有规模与成本数字均为教学假设。
故障注入代码为 CPU 状态模型，不执行真实设备重启或网络破坏。

## 1. 从需求开始，不从组件名开始

假设产品给出：

```text
日活用户：100000
峰值生成请求：80 requests/s
交互请求比例：80%
批处理请求比例：20%
交互 SLO：p99 TTFT ≤ 2 s，p99 TPOT ≤ 60 ms
模型：两个固定版本，工具能力不同
最长上下文：64K，普通请求中位 4K
```

日活、在线连接、GPU 活跃序列和 RPS 是不同指标。
10 万日活不能直接转换成 10 万 GPU 并发。
还需要 ISL/OSL 联合分布、burst、prefix、多轮和取消率。

质量、数据域与工具能力同样是硬要求。
备用模型不兼容工具 schema 时，不能静默 fallback。

## 2. 最小可解释架构

```text
Client
  → Gateway: auth, validation, quota, streaming
  → Capability Router: model/version/security filter
  → Admission: queue, token, KV, deadline
  → Model Pools: request DP + per-replica TP/PP/EP
  → GPU Workers
```

旁路控制面包括：

- artifact registry 与内容校验。
- deployment/health 状态。
- metrics、trace 与审计。
- 配额和计费策略。
- 缓存事件与路由提示。

Gateway 不拥有 GPU KV 页面。
Router 不以 hint 替代 worker lookup。
控制面短暂故障时，已有健康副本应按明确策略继续执行已接受请求。

## 3. 先做容量白板

假设某完整副本使用 4 GPU，在代表性 workload 下达到 10 req/s 的 SLO-goodput。
峰值目标 80 req/s，需要至少 8 个可服务副本。
如果要求任意一个副本失效后仍有 80 req/s，则至少 9 个。

$$
(n-1)\times10\ge80\Rightarrow n\ge9.
$$

总计 36 GPU。
这还是单副本故障模型。
若一台节点上放两个副本，并要求整节点故障后仍满足目标，则需：

$$
(n-2)\times10\ge80\Rightarrow n\ge10.
$$

总计 40 GPU。
因此副本分布与故障域决定真实冗余，不能只说“多留 10%”。

### 3.1 显存还要单独核验

服务率可行不代表每个长请求都可执行。
还需 per-rank 权重、KV、graph、workspace 和 retiring bytes。
64K 请求可能需要专门限额或长上下文池。
不能在平均请求容量里隐藏最坏合法请求的 OOM 风险。

## 4. 五步故障处理模板

每种故障都回答：

```text
Detect      依据什么发现
Contain     如何阻止扩大
Recover     如何恢复服务
Correctness 如何保证状态与内存正确
User        用户输出和计费如何解释
```

只写“重启 worker”缺少前后四步。
重启前还应保留必要证据，但不能为收集日志无限延迟隔离。
证据优先保存 rank timeline、版本、资源高水位和最后错误。

## 5. OOM：别让重试放大故障

OOM 可以发生在权重加载、graph capture、prefill workspace 或 KV 增长阶段。
不同阶段的修复方向不同。

| 阶段 | 可能原因 | 方向 |
|---|---|---|
| load | 双份权重/repack | 加载顺序、分片、峰值 |
| warm-up | graph pools | shape buckets、预算 |
| prefill | activation/workspace | chunk、长度、backend |
| decode | KV 增长/碎片/retiring | admission、回收、配额 |

处理流程：

1. 停止向受影响副本准入。
2. 保存 per-rank 高水位和请求 shape。
3. 按框架支持的恢复方式清理或重启。
4. 对相同请求应用可行配置或明确拒绝。
5. 防止无限重试同一必然 OOM 的 shape。

OOM 后是否可继续执行依赖错误类型和运行时状态。
不要假设 `empty_cache()` 能修复任意上下文或通信故障。

## 6. Collective hang：先找没到场的 rank

Collective 要求同组参与者按兼容顺序进入。
一个 rank 更早 OOM、异常或卡住，其他 rank 会在 collective 里等待。
因此 timeout 往往是后果。

```text
collective record:
  group_id
  sequence_number
  op_type
  count/dtype
  rank/device
  stream
  last_completed_step
```

先比较全部 rank 的最后记录。
再核对 shape、调用顺序与 earlier error。
最后才进入 NIC、RDMA、NUMA 和网络排查。
任何环境变量修改都应单变量验证并保存结果。

通信组失效后应整体隔离或按支持协议重建。
不能让某 rank 重启后直接加入旧组当前序号。

## 7. Fail-slow：没有崩溃也会拖垮服务

某个 rank 的 GPU 降频、NIC 拥塞或 CPU 被抢占，可能一直能返回结果，却显著拖慢全组。
平均 GPU 利用率与总体错误率可能仍正常。
需要监控逐 rank step time 和 collective 到达偏差。

```text
rank times: 18, 19, 18, 45 ms
mean: 25 ms
critical step: at least 45 ms
```

平均值不能解释单请求 45 ms 的关键路径。
应先验证是否 workload/专家分布不同，再检查硬件和链路。
无证据地驱逐最慢 rank 也可能掩盖真正的路由倾斜。

## 8. KV transfer failure

可能发生在目标 reservation、地址交换、部分层写入或完成 ack 阶段。
需要 request generation、worker epoch 和完整 writer 集合。
失败后将页面进入 retiring，直到异步访问结束或数据面已可靠隔离。

不能把“请求报错”与“页面可以复用”写在同一个无条件分支。
不能把 timeout 作为旧远端写入必然停止的证明。
具体状态机与 CPU 不变量模型见 7.3。

数据恢复要区分：

- 可重算的外部 cache miss。
- 必须送达的 P→D handoff。
- 已部分消费的 decode KV。

三者具有不同的回退条件，不能统一忽略错误。

## 9. Stream 中断与工具调用

未输出 token 前，可在幂等契约下重试兼容副本。
输出部分 token 后，需要显式中断或恢复协议。
如果已产生工具调用，重试还可能造成外部副作用重复。

```text
attempt 1: emits tool_call(id=K)
network breaks before client ack
attempt 2: emits same logical tool request again
```

执行工具的一方需要逻辑操作幂等 ID 和结果去重。
推理服务只重试文本生成，无法自动保证外部操作 exactly-once。
协议应明确工具调用何时视为 accepted/committed。

## 10. 演练矩阵

| 注入 | 预期隔离范围 | 验收 |
|---|---|---|
| 入口 burst | admission | 有界队列、可解释拒绝 |
| 长 prompt OOM | 副本/请求 | 无重试风暴、保留证据 |
| 单 worker crash | 完整计算组 | router 摘流、无全局 hang |
| 单 rank slow | 组/节点 | 能定位最慢者与原因 |
| KV ack 丢失 | transfer/request | 不提前 free、不 double free |
| router cache 过期 | 性能域 | safe miss、输出正确 |
| 客户端慢读 | 连接/请求 | buffer 有界、取消传播 |
| 控制面不可用 | 发布/配额策略 | 既有流量行为明确 |

演练先在隔离环境进行，并定义停止条件。
本节不提供会破坏真实服务的自动故障命令。
可先用状态模型验证不变量，再用受控集成环境验证实际 transport。

## 11. 可运行的重试与故障域模型

```python
from math import ceil

def replicas_needed(target_rps, capacity, lost_replicas):
    return ceil(target_rps/capacity) + lost_replicas

assert replicas_needed(80, 10, 1) == 9
assert replicas_needed(80, 10, 2) == 10

def retry_decision(visible_tokens, compatible, attempt, max_attempts=2):
    if not compatible:
        return "fail_incompatible"
    if visible_tokens > 0:
        return "explicit_stream_interruption"
    if attempt >= max_attempts:
        return "fail_retry_budget"
    return "retry_with_new_attempt_id"

assert retry_decision(0, True, 1) == "retry_with_new_attempt_id"
assert retry_decision(3, True, 1) == "explicit_stream_interruption"
assert retry_decision(0, True, 2) == "fail_retry_budget"

states = {rank: "RUNNING" for rank in range(4)}
def fail_group(failed_rank):
    states[failed_rank] = "FAILED"
    for rank in states:
        if rank != failed_rank:
            states[rank] = "ABORT_REQUESTED"

fail_group(2)
assert states == {
    0: "ABORT_REQUESTED",
    1: "ABORT_REQUESTED",
    2: "FAILED",
    3: "ABORT_REQUESTED",
}
print("capacity", replicas_needed(80, 10, 2))
print("group", states)
```

`ABORT_REQUESTED` 仍不是“数据面已经停止”。
真实系统还需等待框架与通信库完成终止，才能释放相关地址。
这个区别是教学模型保留的关键边界。

## 12. 三个完整系统设计题

### 12.1 为 32K—1M coding agent 设计缓存

先区分稳定 repository prefix、工具输出插入、多轮 append 和 branch。
cache identity 包括仓库快照、模型、tokenizer、template、adapter 和位置语义。
改变中间工具结果后，从首个不同 token 开始失效。

GPU 放热数据，CPU/远端放有恢复价值的旧前缀。
比较 load 与 recompute，再决定预取。
Router 在负载约束内利用 prefix hint，worker lookup 权威。
不能默认把所有 1M context 常驻 GPU。

验证覆盖 fork/COW、cancel、cache churn 和长 token gap。
模型“支持长度”与有效长上下文质量分别评测。

### 12.2 多模型统一 Gateway

首先建立模型能力与版本 registry。
按 context、工具、结构化输出、语言、质量和数据域过滤。
然后比较队列、成本与缓存价值。

Fallback 必须经过产品允许的兼容性规则。
不兼容模型不能静默替换。
usage、审计、canary 与回滚都保留实际 artifact。
Gateway 保持无 GPU ownership，方便独立扩展与恢复。

### 12.3 多 Region 高可用

先满足数据驻留与模型可用性，再考虑 RTT、队列和会话 locality。
跨 Region 复制全部 KV 可能花费很高，还会引入隐私与一致性问题。
很多场景以 prefix 重算作为 failover 基线更容易解释。

需要为 Region 故障准备容量，而不是只为单副本失败留余量。
已输出的 stream 跨 Region 也不能自动透明续接。
控制面可共享，但运行时请求与数据面应有明确故障边界。

## 13. 十二步答题顺序

1. 明确业务、用户与请求量口径。
2. 写出分位数 SLO、可用性、质量和成本目标。
3. 描述 ISL/OSL、burst、prefix 与取消。
4. 固定模型结构、dtype 与能力。
5. 算权重、KV、临时空间和网络。
6. 建立最小 aggregated + DP 基线。
7. 用 trace 找瓶颈。
8. 提出两种候选及 break-even。
9. 设计 admission、公平和背压。
10. 逐故障回答隔离、恢复、correctness、用户语义。
11. 定义压测、质量与故障演练证据。
12. 给出扩展触发条件和回滚方式。

好的系统设计不是组件数量多。
它应能解释每条请求、每块 KV 和每次失败的 owner。
不确定的性能结论要转成实验，而不是包装成事实。

## 14. 六道追问与答案

### Q1：10 万用户需要多少 GPU？

仅凭用户数无法计算。
需要峰值 RPS、并发、长度、模型、SLO 与单副本实测画像。
再按故障域、冷启动和显存上限计算。

### Q2：为什么单 rank 故障常要隔离整个副本？

TP/PP/EP 请求依赖完整计算组。
其他 rank 可能还在等待该成员或持有相关状态。
局部重启若没有受支持的协议会造成 hang 或错序。

### Q3：错误率为零，是否说明系统健康？

不说明。
fail-slow、队列增长、starvation 和缓存抖动都可能只影响 tail。
需要 SLO、逐 rank 时间与资源债务观测。

### Q4：Prefix hint 错误应该造成什么后果？

最多造成性能损失或受控重算。
worker 必须重新校验实际缓存身份和可用状态。
如果会返回错误结果，说明控制面与数据面职责越界。

### Q5：为什么重试要有全局预算？

过载或网络故障时，多个层同时重试会乘法放大工作量。
应协调 attempt 次数、deadline、退避和幂等。
已输出 stream 还需单独语义。

### Q6：故障演练成功的标准是什么？

不仅是服务最终恢复。
还要验证无错误输出、无 UAF/double free、无重复计费、队列有界和恢复时间达标。
证据应包含所有相关 rank 与请求状态。
