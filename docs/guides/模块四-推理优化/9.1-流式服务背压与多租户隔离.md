## 一个 HTTP 请求会占用多种资源

用户发送一条生成请求，不只是占用一个 API 连接。
它还可能占用 tokenizer CPU、排队槽、KV 页面、GPU 时间和输出缓冲。
如果只限制每秒请求数，长上下文请求仍可以占满显存。
如果只限制 GPU 并发，CPU 和连接层可能先过载。

本节把 admission、流式输出和取消连接起来。
目标是让每个请求的资源占用可解释、可限制、可回收。

## 1. 协议层与生成层分开

| 协议 | 特征 | 需要处理 |
|---|---|---|
| SSE | HTTP 上服务端单向事件流 | 事件边界、重连、代理缓冲 |
| WebSocket | 双向长连接 | 连接状态、控制消息、背压 |
| gRPC streaming | 类型化流和 HTTP/2 | 内部契约、deadline、流控 |

协议提供数据运输方式，不自动提供“生成过程恢复”。
SSE 的 `Last-Event-ID` 表达客户端最后见到的事件标识。
服务器仍需要保存事件或生成状态，才能实现有定义的重放。
不能因为使用 SSE，就声称断线后可以无缝续写模型。

### 1.1 最小流式事件

```text
event: token
id: req-123:17
data: {"request_id":"req-123","seq":17,"text":"..."}

event: finished
id: req-123:18
data: {"finish_reason":"stop","usage":{"output_tokens":42}}
```

这是教学协议，不是所有 OpenAI 兼容 API 的实际帧格式。
生产协议需要定义错误帧、最终 usage、序号与版本。
一个文本 chunk 可以包含多个 token，也可能包含空文本控制字段。

## 2. 认证、授权与配额是不同检查

认证回答“调用者是谁”。
授权回答“可以访问哪些模型、工具、adapter 和数据域”。
配额回答“在这段时间内可以消耗多少资源”。

推荐入口顺序：

```text
TLS/edge
  → authenticate principal
  → authorize model/capability/security domain
  → validate request size/context/options
  → reserve tenant quota
  → route and admit
```

不要把客户端传来的 `tenant_id` 直接当成可信身份。
它必须与经过验证的 principal 绑定。
也不要把 API key 原文写入 trace、错误日志或缓存 key。

### 2.1 引擎配置边界

某些引擎支持配置 API key，但未配置时可能不启用对应检查。
生产入口应由部署契约明确认证、TLS、模型授权和内网可达范围。
不能把“兼容某 API 协议”理解为已经具备完整多租户安全控制。
具体选项需按安装版本和入口路由核验。

## 3. 资源向量比单一 RPM 更接近真实成本

为请求定义估计资源向量：

$$
r=(1,T_{in},\hat T_{out},\hat M_{KV},\hat S_{GPU},connections).
$$

可以组合以下限制：

| 限制 | 主要保护 |
|---|---|
| RPM | 请求风暴和入口开销 |
| input/output TPM | 输入与生成工作量 |
| concurrency | 长驻留请求 |
| max context/KV bytes | 显存容量 |
| GPU-seconds | 内部成本归因 |
| stream buffer bytes | 慢客户端内存 |

输出长度未知，可以先按上限或预测预留，再按实际用量结算。
如果预测过低，继续生成前需要补充额度或按协议停止。
若平台故障与用户取消的计费规则不同，也应明确记录 outcome。

## 4. 四层背压

### 4.1 Gateway

限制连接数、请求体大小、认证失败和速率。
无效或超额请求尽早拒绝，避免占用 tokenizer 和 GPU。
返回可解释的状态和重试提示，客户端采用退避与 jitter。

### 4.2 Router/admission

结合健康、队列、KV、预计 token 和 SLO slack 选择副本。
不能把所有请求都排进无限队列。
预估已不可能满足 deadline 时，可以明确降级或拒绝。

### 4.3 Engine scheduler

同时限制 waiting/running、scheduled tokens、KV blocks 和特殊工作空间。
Speculative 候选、LoRA、多模态 encoder 也可能消耗预算。
单个 `max_num_seqs` 无法表达全部资源约束。

### 4.4 Stream writer

慢客户端可能让生成速度大于写出速度。
需要有界 buffer、写超时、取消传播和明确的清理状态。
否则一个失联连接可能长期占据 KV 与内存。

## 5. 慢客户端的完整数例

假设引擎输出 50 token/s，每 token 平均编码成 8 字节文本。
只计算文本 payload，生产速率约 400 B/s。
客户端只能消费 100 B/s，积压增长 300 B/s。

若输出 buffer 限制为 30 KiB：

$$
T_{fill}=\frac{30\times1024}{400-100}=102.4\ s.
$$

JSON、SSE 事件和日志会增加真实字节。
如果断线后还持续生成长回答，资源浪费会持续扩大。
因此 buffer 限制不应只按 token 数，还要按实际 bytes 和最长阻塞时间。

### 5.1 Pause 不一定可用

有些引擎无法以低成本冻结一个序列并释放其 GPU 状态。
暂停仍可能保留 KV，swap 还涉及传输。
可用策略是短时缓冲、限速、明确取消或受支持的挂起机制。
不能在 gateway 停止读取后假设 engine 自动安全暂停。

## 6. 流式重试的分界线

### 6.1 尚未输出用户可见 token

可以在幂等 key、模型身份和请求语义一致的前提下重试。
需要避免两个 attempt 同时生成并重复计费。
重试仍要受全局预算限制，不能让过载触发重试风暴。

### 6.2 已经输出部分 token

自动从头重跑会带来：

- 重复输出。
- 不同采样路径。
- 工具调用重复。
- 重复计费。
- 用户看到前后不一致的回答。

如果需要 resume，必须设计显式协议。
至少考虑 accepted tokens、模型版本、上下文、RNG/采样状态、事件序号与工具幂等。
传输层重连不能自动实现这些语义。

## 7. 请求、attempt 与计费记录

```text
logical request_id
  ├─ attempt 1: failed before visible token
  └─ attempt 2: completed
```

计费关联 logical request，执行跟踪关联 attempt。
usage 最终记录应按明确规则生成一次。
“响应发不出去”不代表 GPU 没有做工作，但平台可以按产品政策退款。
内部成本和对用户计费是两套口径，不能混为一谈。

```text
usage record:
  request_id
  final_attempt_id
  model_artifact
  input_tokens
  generated_tokens
  delivered_tokens_or_events
  outcome
  billing_policy_version
```

审计应能解释用户取消、平台错误和正常完成。
避免默认保留完整 prompt 和生成文本。

## 8. 可运行的双桶准入模型

下面例子在同一事务中检查请求桶与 token 桶。
所有检查通过后才一起扣减，避免一个桶已扣费而另一个失败。

```python
from dataclasses import dataclass

@dataclass
class Bucket:
    capacity: float
    refill_per_second: float
    tokens: float
    last: float = 0

    def refill(self, now):
        assert now >= self.last
        self.tokens = min(
            self.capacity,
            self.tokens + (now-self.last)*self.refill_per_second,
        )
        self.last = now

def admit(request_bucket, token_bucket, token_cost, now):
    request_bucket.refill(now)
    token_bucket.refill(now)
    if request_bucket.tokens < 1:
        return False
    if token_bucket.tokens < token_cost:
        return False
    request_bucket.tokens -= 1
    token_bucket.tokens -= token_cost
    return True

rpm = Bucket(2, 1, 2)
tpm = Bucket(100, 10, 100)
assert admit(rpm, tpm, 80, 0)
before = (rpm.tokens, tpm.tokens)
assert not admit(rpm, tpm, 30, 0)
assert (rpm.tokens, tpm.tokens) == before
assert admit(rpm, tpm, 30, 1)
print("atomic quota check passed")

produce_bytes_s, consume_bytes_s = 400, 100
buffer_bytes = 30 * 1024
fill_seconds = buffer_bytes / (produce_bytes_s-consume_bytes_s)
assert fill_seconds == 102.4
print("buffer_fill_s", fill_seconds)
```

代码是单线程教学模型。
真实 gateway 的共享配额需要锁、事务或原子脚本，且必须处理进程失败与预留过期。
多个 gateway 各自独立维护完整租户额度，会把全局配额放大。

## 9. 公平调度与 noisy neighbor

严格优先级可以保护高档服务，却可能让低优先级长期饥饿。
简单 FCFS 可解释，但长请求可能造成队首阻塞。
Prefix-aware 调度提高复用，也可能反复偏爱有缓存的大租户。

可组合：

```text
tenant quota
  + service-tier reservation
  + token deficit accounting
  + aging
  + hard KV limit
```

评价需按租户与长度 bucket 报告 queue age、SLO 和拒绝率。
总 TPS 正常不意味着公平。
应单独检查最长等待时间和低优先级是否持续获得服务。

### 9.1 缓存隔离

跨租户共享 prefix 可能提高命中率，也可能暴露访问时序或错误复用敏感 KV。
安全域应进入 cache namespace。
共享策略需要明确授权与威胁模型。
不能因为 KV 不是原始文本就认为它无需保护。

## 10. 取消传播与资源回收

背压还需要跨层关联观测。
例如 gateway 的 pending requests 下降、engine retiring bytes 却持续增长，说明用户已离开但物理资源仍未回收。
这时继续提高外层 RPM 上限只会加速显存耗尽。
应查看最老 cancel age、缺失的 transport ack 和仍存活的 stream writer。
同一逻辑请求的 quota reservation、attempt 与页面 owner 应能相互追踪。
所有超时路径都应保留最终 outcome，避免把请求从统计中直接删除。
这样才能把可解释计费与安全回收连接到同一生命周期。

```text
client disconnect
  → gateway cancel intent
  → router marks attempt terminal
  → scheduler stops new work
  → GPU/transport drain
  → pages retire
  → quota reservation reconciled
  → usage finalized once
```

HTTP close 与最后两步之间可能相隔较长时间。
需要监控 cancel-to-stop、cancel-to-free 与 retiring bytes。
使用 request generation 防止迟到结果写入新的 attempt。
KV 物理安全细节见 7.3。

## 11. 六道追问与答案

### Q1：只限 RPM 为什么不公平？

一个 100-token 请求与一个 100K-token 请求的 CPU、KV 和 GPU 工作量差异很大。
RPM 只能控制请求数量，应结合 token、并发和内存预算。

### Q2：SSE 自动重连是否保证回答续传？

不保证。
还需要服务端事件日志或生成 checkpoint，以及明确的序号和采样恢复语义。
协议重连与模型恢复是两层能力。

### Q3：已经输出 token 后能否透明重试？

通常不能安全地从头重试并继续拼接。
需要显式 resume 或向用户报告中断。
工具调用与计费还需额外幂等约束。

### Q4：慢客户端只影响自己的连接吗？

可能占用共享内存、event loop、KV 和 GPU 槽，拖慢其他租户。
有界 writer buffer 与取消传播属于系统容量控制的一部分。

### Q5：用户取消后立刻返还全部配额是否正确？

要区分预留额度、已发生用量和仍在 drain 的资源。
可以按产品规则结算 token，但物理容量只能在安全回收后返还 admission。

### Q6：高优先级是否可以绕过 KV 上限？

不可以。
优先级影响可行请求之间的顺序，不改变物理内存约束。
可使用预留容量或专池，但不能突破硬限制。
