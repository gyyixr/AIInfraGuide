## 调度计划还不是可执行 GPU 输入

Scheduler 决定哪些请求计算多少 token。
ModelRunner 还要把计划变成输入 IDs、positions、slot mapping、attention metadata 和实际执行路径。
它是请求状态到模型张量的关键转换边界。
很多 correctness 和性能问题就发生在这里。

固定基线：SGLang `46d9427b913b20ce0d72b95a9209717448b37368`，vLLM `9c8e90eb2637a863ca14e47fd436b10ed7ba6536`。
本文核对的是所列函数片段，不把它们当最新 API 或完整硬件支持清单。
代码示例是 CPU 数据布局模型，未执行实际模型前向。

## 1. 一个混合 batch 的表示转换

请求 A 是 decode，当前输入一个 token。
请求 B 是 prefill chunk，本轮输入三个 token。
展平输入可能是：

```text
request A: ids=[91],       positions=[31]
request B: ids=[10,20,30], positions=[0,1,2]

flattened ids:       [91,10,20,30]
flattened positions: [31, 0, 1, 2]
query boundaries:   [0,1,4]
sequence lengths:   [32,3]
```

这里总 token 数是 4，请求数是 2。
不能把两者混作 batch size。
Attention 还需要各请求的历史 block table、有效长度、mask 和 KV 写入位置。

### 1.1 为什么 positions 不能直接用全局 arange

展平后的第二个 token 属于另一个请求，其 position 是 0。
若直接赋 `[0,1,2,3]`，A 和 B 的 RoPE/因果语义都会错。
Prefix hit、chunked prefill 和 speculative branches 又会改变起点。
每个字段必须从请求语义推导，而不是从 tensor 行号猜测。

## 2. SGLang 的执行边界

固定主链可以沿以下符号阅读：

```text
Scheduler.run_batch
  → TpModelWorker.forward_batch_generation
  → ForwardBatch.init_new
  → ModelRunner.forward
  → _forward_raw / selected execution path
  → model forward
  → logits / sampling
  → GenerationBatchResult
```

`ScheduleBatch` 包含调度侧状态。
`ForwardBatch` 为执行侧准备张量与 metadata。
把二者分开有利于组织 CPU 调度与 GPU 执行，但也带来快照一致性要求。
已经提交的 batch 不能被后续队列修改悄悄改变。

### 2.1 PP 最后 stage 的职责

`TpModelWorker.forward_batch_generation` 对 PP 最后 rank 的行为与中间 stage 不同。
最后 stage 才产生最终 logits，并根据执行模式采样或延迟采样。
Spec verify 路径可能跳过普通采样，由对应 worker 继续处理。
因此“每个 worker 都独立 sample 一个 token”是错误心智模型。

### 2.2 ModelRunner 的外围工作

固定 `forward` 包含 profiling、专家分布记录等上下文，然后调用实际 forward 路径。
输出还携带 graph 可用性、专家路由等可选信息。
这些信息有助于观察实际 backend 和负载，而非只拿 logits 返回。
开启额外观测也可能改变性能，应标注配置。

## 3. SGLang attention backend 的阶段选择

`init_attention_backends` 先配置需要的辅助 hidden state 捕获，再解析 backend 字符串。
固定实现保存 prefill 与 decode 各自的选择，并构建相应 backend。
它明确要求发生在 decode graph capture 前。

这个顺序有实际原因：

- Graph capture 必须捕获正确的执行与辅助输出。
- Prefill 与 decode shape 和 metadata 不同。
- Spec/draft 可能有额外 hidden state 需求。
- CP/MLA 等配置可能改变合法后端集合。

所以“整个模型只用一个 attention kernel”通常过于粗糙。
应区分阶段、结构、硬件和实际调用。

## 4. vLLM V1 的执行侧状态

`GPUModelRunner.execute_model` 接收 `SchedulerOutput`。
固定代码先处理 connector preemption，再更新持久 batch 状态。
随后整理 token 数、准备输入、决定 padding 与 graph 执行方式。

```text
SchedulerOutput
  → handle connector preemptions
  → _update_states
  → _prepare_inputs
  → determine execution/padding
  → forward
  → logits/sample or deferred state
  → ModelRunnerOutput
```

`input_batch` 是持久执行缓存，不能假定每轮从零重建所有 tensor。
这种设计减少 CPU 开销，但要求删除、插入和重排请求时保持所有数组一致。
因此 `_update_states` 与 `_prepare_inputs` 是关键阅读点。

### 4.1 零 token 计划不一定完全无工作

固定路径在 `num_scheduled_tokens=0` 时，可能仍需执行 connector 相关进度。
特定 external launcher + DP 组合还需参与协调，避免各 rank 失步。
不能在自定义改动中简单 `if tokens == 0: return`，跳过全部协议。
空计算批次也可能承载控制面工作。

### 4.2 执行与采样可能分开

`execute_model` 的某些路径返回 `None`，要求后续调用 `sample_tokens`。
固定代码检查上一轮 deferred execute 状态未清理时禁止再次执行。
这是一项顺序契约，不是无关防御代码。
绕过它可能让 logits、grammar 或 RNG 对错请求。

## 5. vLLM CUDA backend 选择的真实条件

`platforms/cuda.py` 中的 `get_valid_backends` 遍历候选并调用 `validate_configuration`。
配置检查包括设备能力与 attention selector 的具体结构条件。
导入失败或动态库不可用也会使候选不合法。

### 5.1 用户强制与自动选择的区别

固定 `get_attn_backend_cls` 对用户明确选择的 backend 先单独校验。
如果不合法，会报出原因。
未指定时，才从合法候选中按优先顺序选择。

不能把这段代码描述成“用户强制无效也静默 fallback”。
自动选择与显式选择的可观测语义不同。
错误地吞掉配置错误可能掩盖实际性能路径。

### 5.2 六道关卡

```text
在 registry 中存在
  ≠ 依赖已安装
  ≠ 当前配置合法
  ≠ 能被 graph 捕获
  ≠ 数值质量合格
  ≠ 在当前 workload 最快
```

能力矩阵应逐项保存证据。
例如“支持 FP8 文件”不能直接推出“在 SM86 上执行原生 FP8 Tensor Core”。
实际可能解码到其他格式、走 fallback，或直接不支持。

## 6. 新模型 Day-0 的接入顺序

### 6.1 冻结 artifact 与 reference

保存权重、config、tokenizer、template、量化元数据和许可证信息。
先用可信 reference 对极小输入得到 logits/greedy 输出。
如果自定义模型代码改变 attention 或 norm，先逐层理解语义。
不要第一步就 autotune。

### 6.2 模型映射与权重加载

检查 architecture 名如何映射模型实现。
逐项核对 QKV packing、gate/up/down、tied embedding 和 TP shard 规则。
量化还需确认 scale、zero、group size、repack 与未量化层。
权重 shape 相同不保证拼接顺序相同。

### 6.3 KV 结构与 position

确认 MHA/GQA/MLA、窗口层、recurrent state 或混合层。
检查写入 slot、block layout、position IDs 与 RoPE 参数。
Prefix sharing、chunk 和 CP 都依赖这些契约。
单 token 测试通过不能证明长上下文正确。

### 6.4 从小到大的验证矩阵

```text
single token / tiny prompt
  → batch of different lengths
  → prefill + decode
  → long context / non-aligned tail
  → chunk / prefix / cancel
  → quant / spec / graph
  → distributed groups
```

每一步先输出正确，再检查性能和容量。
unsupported 应明确报错，不能用未验证近似静默替代。

## 7. 可运行的展平输入与 dispatch 模型

```python
requests = [
    {"id":"A", "tokens":[91], "start":31},
    {"id":"B", "tokens":[10,20,30], "start":0},
]
ids, positions, offsets = [], [], [0]
for req in requests:
    ids.extend(req["tokens"])
    positions.extend(range(req["start"], req["start"]+len(req["tokens"])))
    offsets.append(len(ids))
assert ids == [91,10,20,30]
assert positions == [31,0,1,2]
assert offsets == [0,1,4]

backends = {
    "special": {"min_cc":90, "dtypes":{"bf16"}},
    "portable": {"min_cc":80, "dtypes":{"bf16","fp16"}},
}

def select(cc, dtype, forced=None):
    def valid(name):
        item = backends[name]
        return cc >= item["min_cc"] and dtype in item["dtypes"]
    if forced is not None:
        if not valid(forced):
            raise ValueError("forced backend is invalid")
        return forced
    for name in backends:
        if valid(name):
            return name
    raise ValueError("no compatible backend")

assert select(86, "bf16") == "portable"
try:
    select(86, "bf16", forced="special")
except ValueError:
    pass
else:
    raise AssertionError("invalid explicit backend silently accepted")
print(ids, positions, offsets, select(86,"bf16"))
```

`special` 和 `portable` 是教学占位名，不是框架 backend。
模型验证显式配置报错和自动候选选择的区别。
实际支持条件远多于 compute capability 和 dtype 两项。

## 8. Graph、padding 与延迟的数例

假设一个 batch 实际有 17 个 token，graph bucket 支持 32。
如果必须 padding 到 32，表面工作量放大为：

$$
32/17\approx1.882.
$$

但这不直接表示耗时也放大 1.882 倍。
较大 tile 可能更有效率，graph 还能减少 CPU launch。
另一方面，如果多余 token 触发昂贵 attention 或内存访问，padding 成本可能明显。

假设 eager 计算 4 ms、launch/host 2 ms，总计 6 ms。
graph padding 后计算 4.8 ms、host 0.3 ms，总计 5.1 ms。
有收益但不是“去掉 2 ms 后只剩 4 ms”。
应测实际 bucket 分布与端到端关键路径。

## 9. 新模型常见错误定位

| 现象 | 优先核对 |
|---|---|
| 第一层开始 logits 不同 | 权重映射、dtype、norm |
| 短输入对，长输入错 | RoPE、mask、position、KV |
| batch=1 对，混合 batch 错 | offsets、slot、长度、padding |
| eager 对，graph 错 | 地址、静态 buffer、capture 状态 |
| 单卡对，TP 错 | shard 维度、head 复制、collective |
| 普通对，prefix hit 错 | cache identity 与有效 KV 长度 |

先固定输入与随机性，再找第一个偏离 reference 的张量。
不要只在最终文本层观察差异。
量化误差也应与结构性错误分开：错 head 映射不能用更大 atol 掩盖。

## 10. 六道追问与答案

回答源码追问时，可以先用下面的最小审计表组织证据。
每一行都应有可复现输入和期望结果，而不是只打勾“支持”。

| 用例 | 要证明的契约 |
|---|---|
| 两条不同起始position | 展平不混淆请求位置 |
| batch filter后再执行 | slot与request同序 |
| 非整除head/hidden | 合法校验或明确拒绝 |
| 显式不合法backend | 不静默选择另一实现 |
| 零token但有connector操作 | 协议仍可推进 |
| execute后延迟sample | 状态顺序不被跨轮覆盖 |
| graph bucket边界 | padding与有效token正确区分 |
| prefix命中后首token | logits与KV有效长度一致 |

这张表应随模型和backend扩大，而不替代真实代码阅读。
单卡通过后，再增加TP/PP和异步取消的组合。

### Q1：请求数与本轮 token 数为什么不同？

Decode 请求可能只贡献一个 token，prefill chunk 可以贡献数百。
ModelRunner 展平后按总 token 执行，同时保留请求边界和历史长度。

### Q2：为什么 zero-token batch 仍可能不能直接跳过？

它可能需要推进 connector 或参与分布式协调。
计算为空不意味着协议为空。
应读执行器对该分支的契约。

### Q3：用户强制 backend 不支持，应静默切换吗？

固定 vLLM 路径会报出不合法原因。
自动选择才遍历合法候选。
这样能避免用户误以为启用某路径而实际运行另一种。

### Q4：为什么 Day-0 不先做性能优化？

没有可信 reference，提速可能来自少算、错 mask 或错权重。
先建立逐层与端到端正确性，再优化热点。

### Q5：模型能加载，是否代表支持该量化格式？

还需核对各层 method、repack、实际 kernel、shape 和质量。
存储格式、计算格式和累加精度是不同维度。

### Q6：Graph 为什么需要关心生命周期？

捕获执行可能依赖稳定地址、buffer 与状态。
若重放期间 allocator 复用或释放这些资源，会产生错误。
支持 capture 不等于所有动态请求都可直接重放。
