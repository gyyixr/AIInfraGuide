## 首先确定慢发生在哪条路径

用户说“模型慢”，可能是在等 admission、tokenizer、prefill、KV handoff、decode 或流式网络。
直接优化一个 GEMM，可能与用户等待完全无关。
正确顺序是先确定请求关键路径，再寻找占主导的执行阶段。

本节区分三类证据：

1. 请求 trace：用户时间花在哪里。
2. 系统 timeline：CPU、GPU、通信如何交错。
3. kernel counters：一个热点 kernel 为什么慢。

三者相互补充。
一个 kernel 的峰值指标不能替代整个服务的 p99。

## 1. 最小 Trace 合约

```text
request
  gateway/auth
  tokenize/template
  admission wait
  engine queue
  prefill chunks
  KV restore / P-D transfer
  decode steps
  detokenize
  stream write
```

每个 span 至少包含：

| 字段 | 用途 |
|---|---|
| request/attempt ID | 关联重试和流式输出 |
| model artifact | 识别发布差异 |
| worker/rank | 找到局部 straggler |
| phase/batch ID | 关联共享 batch |
| token/context count | 解释 shape |
| backend/graph status | 识别实际路径 |
| status/cancel | 区分工作完成与被丢弃 |

日志默认不需要记录完整 prompt。
token 数、哈希、语义版本和抽样脱敏足以支持大部分性能分析。
高基数 request ID 适合 trace/log，不适合直接作为 Prometheus label。

## 2. 总时间不能把重叠 span 全部相加

假设 CPU 准备 batch B 的同时，GPU 正在执行 batch A。
两个 span 的持续时间都是真实的，但它们并行发生。
求和得到的是工作量，不是 wall-clock 延迟。

```text
time  0      5      10     15 ms
GPU   [ batch A ][ batch B ]
CPU       [prepare B]
```

若 CPU span 为 5 ms、GPU 两段共 15 ms，整段 wall time 可能仍只有 15 ms。
关键路径应根据依赖边和时间区间判断。
对 overlapping collective、KV transfer 和 compute 也一样。

### 2.1 一条 TTFT 数例

教学 trace 的串行关键路径：

| 阶段 | 时间 |
|---|---:|
| gateway/tokenizer | 20 ms |
| queue | 180 ms |
| prefill | 80 ms |
| stream flush | 10 ms |

TTFT=290 ms。
即使把 prefill 加速到 40 ms，TTFT 也仅降到 250 ms，约 1.16 倍。
若减少排队到 40 ms，则 TTFT 变成 150 ms，约 1.93 倍。
这说明优化优先级应由关键路径决定。

## 3. 先核实实际执行路径

配置写了某 backend，不代表所有请求都走它。
shape、dtype、硬件、graph 兼容、可用依赖和 kernel registry 都可能触发其他路径。

需要逐层核实：

```text
registry entry
  → installed library
  → configuration supported
  → selected backend
  → graph-compatible execution
  → actual launched kernel
  → numerical/quality acceptance
```

量化 checkpoint 名称也不是最终 kernel 名称。
加载时可能 repack，部分层保留高精度，部分 shape 走 fallback。
应保存启动选择日志和 timeline 中的实际 kernel。
否则 A/B 可能比较的是意料之外的不同实现。

## 4. Nsight Systems 先回答五个问题

1. GPU 是否有长空白区间？
2. CPU 是否及时提交下一批工作？
3. 是否有频繁同步与小 kernel launch？
4. collective 或 memcpy 是否位于关键路径？
5. 不同 rank 是否在同一位置等待？

典型模式：

| Timeline 现象 | 第一批假设 |
|---|---|
| GPU 空隙，单 CPU 核满 | tokenizer/scheduler/JSON |
| 很多短 kernel | launch overhead、未融合 |
| memcpy 后 GPU 等待 | 数据搬运或同步 |
| 某 rank 晚到 collective | earlier compute/CPU/硬件 straggler |
| graph miss 后变慢 | shape、编译、capture fallback |

这些是待验证假设，不是仅凭图形就成立的结论。
例如 GPU 空隙也可能因为系统没有足够请求。
需要同时查看 offered load 和 queue。

### 4.1 受控采集命令

下面展示常见 CLI 形状，执行前用本机版本确认选项：

```bash
nsys --version
nsys profile --help
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=none \
  --output=/tmp/inference-window \
  python your_bounded_reproducer.py
```

`your_bounded_reproducer.py` 是读者准备的有限时长复现程序。
不要直接让完整线上服务持续采集数小时。
先 warm-up，再采集能覆盖问题的短窗口。
采集开销本身也要与无 profiler 的基线比较。

## 5. Nsight Compute 再解释热点 kernel

只有确认某个 kernel 重要后，才值得采集更重的硬件计数器。
重点查看：

- 实际 DRAM/L2 流量。
- SM 和 tensor pipe 活跃度。
- 寄存器与 shared memory 占用。
- spill/local load/store。
- warp stalls 与 eligible warps。
- load/store 合并与事务放大。
- tile padding 和 shape 利用率。

不要一开始对整个服务的全部 kernel 采集 full metrics。
重放和序列化可能改变并发、缓存和时间行为。
先对一个代表性 shape 的热点做独立复现。

```bash
ncu --version
ncu --help
ncu --set basic \
  --launch-count 1 \
  --export /tmp/kernel-window \
  python your_kernel_reproducer.py
```

该命令只是入口示例。
目标 kernel 的过滤方法、权限和计数器集合需按当前安装版本确认。
不能用 profiler 引入的 replay 时间直接当正常服务延迟。

## 6. Roofline 要说明内存层次

算术强度：

$$
AI=\frac{FLOPs}{Bytes}.
$$

性能上界：

$$
P\le\min(P_{peak},BW\times AI).
$$

时间下界：

$$
t\ge\max\left(\frac{F}{P_{peak}},\frac{B}{BW}\right).
$$

$B$ 必须指明是哪一级的实际流量。
HBM bytes、L2 bytes 和逻辑 tensor 大小不能互换。
重复读取、cache hit、对齐和合并访问都会改变实际字节。

### 6.1 数例：为什么低于带宽顶不一定说明该换 tile

假设 kernel 做 4 TFLOP，实际读取 8 GB，算术强度 500 FLOP/byte。
设备给定有效计算顶为 100 TFLOP/s，带宽顶为 1 TB/s。
计算下界 40 ms，带宽下界 8 ms。
此时简单模型判断计算侧更可能限制性能。

如果实际 kernel 用了 70 ms，应继续看 tensor instruction、padding、依赖和 occupancy。
不能因为只用了 114 GB/s 就断言“访存优化一定最有效”。
低带宽可能只是计算限制的结果。

## 7. Occupancy 不是目标函数

较高 occupancy 有时帮助隐藏延迟。
但增加并发 block 可能要求缩小 tile，降低复用或增加指令。
限制寄存器可能产生 spill，反而增加 device memory 流量。

需要同时比较：

```text
tile shape
registers per thread
shared memory per block
active blocks/warps
spilled bytes
instruction count
kernel time
```

一个 occupancy=50% 的高复用 kernel 可能比 occupancy=100% 的版本更快。
性能指标应回到实际时间、正确性与端到端收益。

## 8. Amdahl 给出收益上限

若可优化部分占原始关键路径比例为 $f$，内部加速 $s$：

$$
Speedup=\frac{1}{(1-f)+f/s}.
$$

当某 kernel 只占 4%，内部加速 2 倍：

$$
Speedup=\frac{1}{0.96+0.04/2}\approx1.0204.
$$

理论上总收益仅约 2%。
如果新增 layout conversion 占 3%，最终还可能更慢。
如果优化减少排队、改变 batch 组成，端到端变化可不符合固定 $f$ 的简化模型。
此时应说明是系统效应，并用实际 A/B 验证。

## 9. 可运行的关键路径与 Amdahl 计算

```python
def amdahl(fraction, local_speedup):
    assert 0 <= fraction <= 1
    assert local_speedup > 0
    return 1 / (1-fraction + fraction/local_speedup)

baseline = {"host": 20, "queue": 180, "prefill": 80, "stream": 10}
old = sum(baseline.values())
kernel_change = old - baseline["prefill"] + 40
queue_change = old - baseline["queue"] + 40
assert old == 290
assert kernel_change == 250
assert queue_change == 150
print("prefill_2x_total", old/kernel_change)
print("queue_change_total", old/queue_change)
print("4_percent_kernel_2x", amdahl(0.04, 2))

flops = 4e12
actual_bytes = 8e9
compute_rate = 100e12
memory_rate = 1e12
compute_ms = flops/compute_rate*1000
memory_ms = actual_bytes/memory_rate*1000
assert compute_ms == 40
assert memory_ms == 8
print("AI", flops/actual_bytes)
print("time_lower_bound_ms", max(compute_ms, memory_ms))
```

它验证公式与单位，不预测特定 RTX/Hopper 设备的性能。
真实 $P_{peak}$ 和 $BW$ 应选择对应 dtype、指令路径和有效测量值。

## 10. 一次 p99 TPOT 回归的调查顺序

先按长度、租户、worker 和时间段切分受影响请求。
找出具体长 gap，关联当时的 batch composition。
比较发布前后实际 backend、graph hit 和 prefill chunk。

如果平均 TPS 不变，仍可能存在：

- 长 prefill 只影响少数 decode 请求。
- 某 rank/专家持续拖尾。
- 慢客户端导致单请求写出拥塞。
- CPU event loop 周期性阻塞。
- KV pressure 触发重算或迁移。
- 频率下降与其他请求补偿吞吐。

平均 TPS 不能排除局部 starvation。
必要时先限制问题流量或回滚，保留短 trace 后继续分析。

## 11. 验证优化没有偷偷少做工作

性能比较前检查：

| 边界 | 验证内容 |
|---|---|
| 语义 | mask、position、stop、sampling |
| Shape | batch、context、stride、尾块 |
| 数值 | dtype、累加、误差、NaN/Inf |
| 工作量 | 输入/输出 token、drop、取消 |
| 并发 | stream、event、buffer lifetime |
| 路径 | actual kernel、fallback、graph |

“少输出 token”“跳过长请求”“缓存了不兼容结果”都可能产生虚假的提速。
先 correctness，再 microbenchmark，最后回到端到端 trace。
优化报告必须保留无收益或退化 shape。

## 12. 六道追问与答案

### Q1：GPU utilization 100% 就没有 CPU 瓶颈吗？

不能这样推断。
采样粒度可能掩盖短空隙，GPU 也可能在低效等待或执行无关工作。
需要 timeline 和请求关键路径联合判断。

### Q2：为什么先 Nsys 再 NCU？

Nsys 找到系统阶段与热点，NCU 解释特定 kernel。
先对所有 kernel 收集重计数器容易改变行为并产生大量无关数据。

### Q3：CUDA event 计时是否等于客户端延迟？

不是。
它通常测设备 stream 上的目标区间，客户端延迟还包含排队、CPU 和网络。
多 stream 计时也需要正确的依赖与同步边界。

### Q4：更少 kernel 一定更快吗？

不一定。
融合可能增加寄存器、spill、shared memory 或同步，降低并发。
应比较真实 shape 的时间与端到端占比。

### Q5：新卡支持某 dtype，是否就使用对应 Tensor Core？

不一定。
还要核对库、backend、shape、alignment、实际指令和 fallback。
输入 tensor dtype 不能单独证明执行路径。

### Q6：RTX 3090 上能验证哪些结论？

可以验证其支持的 SM86 路径、访存、tiling、FP16/BF16 等实际算例。
不能把 Hopper 的 TMA/WGMMA 或 Blackwell 专有原语当成本机实测。
架构无关的公式可复用，硬件性能必须分开标注。
