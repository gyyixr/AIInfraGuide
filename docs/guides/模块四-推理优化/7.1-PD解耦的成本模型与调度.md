## 先定义要解决的干扰

Prefill 一次处理较长输入，decode 每步为活跃请求生成少量 token。
二者放在同一引擎中可以共享权重和空闲资源。
但长 prefill 也可能延长某些 decode step，造成用户可见 token 停顿。
是否需要分池，要从实际 timeline 和 SLO 违约开始判断。

“Prefill 一定计算受限、decode 一定带宽受限”过于绝对。
batch、context、量化、attention backend 和通信都会改变瓶颈。
P/D 解耦的主要工程收益是分别优化阶段并隔离干扰。
它增加传输和调度成本，不能预先保证总吞吐提高。

## 1. 三种候选架构

| 方案 | 优点 | 代价 |
|---|---|---|
| Aggregated | 共享池、无需跨引擎 KV handoff | phase 干扰 |
| Chunked prefill | 限制每轮长 prefill 工作量 | 更多轮次与调度 |
| Disaggregated | P/D 独立硬件、并行和容量 | KV 传输、双池、协调 |

Chunked prefill 通常是重要基线。
如果把超长 prefill 切成可控 chunk 已能达到 TPOT SLO，PD 的额外复杂度未必值得。
反之，如果强 tail SLO 与长 prompt 突发始终冲突，分池才有明确证据。

## 2. 一个请求在两个池之间流动

```text
gateway
  → validate/tokenize
  → choose P-D pair
  → reserve D capacity
  → P queue
  → P prefill
  → KV transfer
  → D verifies readiness
  → D decode
  → stream writer
```

有些实现先执行 P 再选择 D。
这种选择会改变何时预分配、是否需要中间 store，以及 D 满载时谁持有 KV。
应把流程写成具体协议，不能只画两个 GPU 方框。

| 状态 | 主要 owner | 占用的资源 |
|---|---|---|
| waiting P | 路由/调度器 | 队列、请求元数据 |
| prefill | P worker | 权重执行、P KV、workspace |
| transfer | transport + 两端 allocator | 源/目标 KV、注册 buffer |
| waiting D | D scheduler | D 预留 KV、队列 |
| decoding | D worker | 持续增长的 KV、decode 槽 |
| retiring | 生命周期控制器 | 未完成异步访问的页面 |

注意 transfer 时源与目标可能同时占据完整 KV。
这段重复容量不能从集群显存账上省略。

## 3. TTFT 的分解

客户端的首 token 延迟可写成：

$$
TTFT=T_{gateway}+T_{tokenize}+W_P+S_P
+T_{handoff}+W_D+T_{first-step}+T_{stream}.
$$

具体实现可能由 P 产生首 token，再由 D 继续。
这时客户端首 token 的边界不同，handoff 可能体现在第一个后续 ITL 中。
比较架构时必须统一用户可见的时间口径。

把 first token 提前到 P 并不消除后续等待。
若首 token 后停顿 800 ms，再恢复正常 cadence，平均 TPOT 可能掩盖这次卡顿。
因此需要保存逐 token ITL，而不只记录 TTFT 和一个平均 TPOT。

## 4. KV 传输字节模型

对标准 GQA：

$$
B_{KV}=T\times2Lh_{kv}db_{kv}.
$$

以 $L=32,h_{kv}=8,d=128,b_{kv}=2$ 为例：

$$
B_{token}=128\ \mathrm{KiB}.
$$

8K prompt 的 KV 是 1 GiB，32K prompt 是 4 GiB。
若有效传输带宽为 20 GiB/s，仅 payload 就至少需要 50 ms 和 200 ms。
再加 3 ms 的固定协调与 layout 成本，得到 53 ms 和 203 ms。

```text
8K:  8192 × 128 KiB = 1 GiB → 50 ms + 3 ms
32K: 32768 × 128 KiB = 4 GiB → 200 ms + 3 ms
```

这不是网卡峰值推测，而是显式假设有效带宽后的算例。
实际还可能涉及 KV shard 重分布、跨 dtype 转换、页表和 cache 命中。
P 的 TP 与 D 的 TP 不同，传输协议必须支持对应 layout。

### 4.1 平均流量也要满足网络容量

若每秒 10 个 8K 请求，每个传输 1 GiB：

$$
\lambda E[B_{KV}]=10\ \mathrm{GiB/s}.
$$

若可用总带宽为 20 GiB/s，平均利用率为 50%。
但 burst、多个传输共用 NIC、机架上行和长 prompt 会造成尾延迟。
不能因为平均小于上限就忽略排队。

## 5. P:D 配比必须使用服务需求

先区分两个概念：

- 请求逗留时间：用户从进入到完成的 wall time。
- 服务需求：该请求消耗的“副本秒”或 GPU 秒。

连续 batching 中，100 个请求可以共同经过一个 20 ms decode step。
不能把每个请求都按独占 20 ms 计入容量，否则把共享计算重复计算 100 次。
配比模型应从固定配置的测量中获得平均服务需求或有效容量。

设每请求平均 P 服务需求为 $d_P$ 副本秒，D 为 $d_D$ 副本秒。
有效进入率为 $\lambda$，目标利用率为 $u_P,u_D$：

$$
n_P\ge\left\lceil\frac{\lambda d_P}{u_P}\right\rceil,
\qquad
n_D\ge\left\lceil\frac{\lambda d_D}{u_D}\right\rceil.
$$

这些需求取决于 batch、context、并行和 OSL。
因此公式只用于初筛，最后仍需 trace replay 或在线压测。

### 5.1 完整数例

设在目标 workload 下测得：

```text
arrival rate λ = 12 requests/s
P service demand = 0.08 replica-s/request
D service demand = 0.30 replica-s/request
target utilization = 0.70
```

则：

$$
n_P=\lceil12\times0.08/0.7\rceil=2,
$$

$$
n_D=\lceil12\times0.30/0.7\rceil=6.
$$

若每个 P 副本使用 4 GPU、D 副本使用 2 GPU：

$$
GPU_{total}=2\times4+6\times2=20.
$$

P:D 副本数 1:3，不等于 GPU 数 1:3。
本例 GPU 分配为 8:12，即 2:3。
跨阶段不同 TP/PP 时尤其容易记错这个账。

## 6. Little's Law 用来算驻留请求

在稳定、守恒的边界内：

$$
L=\lambda W.
$$

若 D 池有效进入率 12 requests/s，平均在 D 停留 4 s，则平均驻留 48 请求。
这个 4 s 是逗留时间，可以包含排队和与其他请求共享的 decode。
它与上一节的 0.30 副本秒服务需求不是同一个量。

如果每请求平均驻留 KV 为 0.8 GiB，则平均 D KV 约 38.4 GiB。
真正容量还应考虑长度分布、峰值、增长、页尾和预分配。
Little's Law 不提供 p99，也不能直接替代显存峰值估计。

## 7. 一个双池 admission 判定

只看 P 空闲会把工作快速生产到满载的 D。
只看 D 空闲又可能因为 P 排队而达不到 TTFT。
需要同时检查 P、D 和传输资源。

```text
admit(request):
    validate capability and context limit
    estimate P work, D work, KV bytes
    choose healthy compatible P-D candidates
    reject candidates exceeding hard KV/network budget
    estimate queue and SLO slack
    reserve D token/KV credit with expiry
    enqueue P work using reservation generation
    on P failure: release reservation after async drain
    on transfer ready: commit D ownership
```

reservation 过期不等于目标页可立即复用。
如果源端已经获得地址并开始写入，就要遵循 transfer drain 协议。
相关取消与 UAF 问题见 7.3。

## 8. Layer-wise overlap 的上下界

如果每一层 KV 生成后立即传输，可与后续层 prefill 重叠。
完全串行时：

$$
T_{serial}=T_P+T_X.
$$

理想流水的下界接近：

$$
T_{pipe}\ge\max(T_P,T_X)+T_{fill/drain}.
$$

因此最大可能隐藏的传输时间不超过 $\min(T_P,T_X)$。
实际受层间依赖、NIC 争用、每层固定开销和 D readiness 限制。
不能仅因为传输在另一个 CUDA stream 上就断言已经重叠。

分层协议需要逐层 ready、epoch、目的 layout 和 completion。
某层失败时，不允许 D 读取“前几层完成、后几层缺失”的半成品 KV。
若支持逐层等待，消费位置必须在 attention 读之前建立同步。

## 9. 可运行的配比和传输计算

```python
from math import ceil

rate = 12
p_demand, d_demand = 0.08, 0.30
target = 0.70
p = ceil(rate * p_demand / target)
d = ceil(rate * d_demand / target)
assert (p, d) == (2, 6)
assert p * 4 + d * 2 == 20
print("replicas", p, d, "gpus", p * 4 + d * 2)

bytes_per_token = 2 * 32 * 8 * 128 * 2
bandwidth = 20 * 2**30
fixed_s = 0.003
for tokens in (8192, 32768):
    payload = tokens * bytes_per_token
    transfer_ms = (fixed_s + payload / bandwidth) * 1000
    print(tokens, payload / 2**30, round(transfer_ms, 3))

assert bytes_per_token == 128 * 1024
assert abs((fixed_s + 2**30 / bandwidth) * 1000 - 53) < 1e-9

# 两个阶段的简化串行/理想重叠下界。
prefill_ms, transfer_ms = 160, 53
print("serial_ms", prefill_ms + transfer_ms)
print("ideal_overlap_lower_bound_ms", max(prefill_ms, transfer_ms))
```

最后一行 160 ms 没有包含流水填充尾部和同步，只是乐观下界。
代码没有模拟真实 continuous batching，不能据此生成上线容量承诺。

## 10. 固定 GPU 总预算的实验矩阵

实验前先明确两个池的计费与故障边界。
P 使用 4 GPU、D 使用 2 GPU 时，应保存每阶段实际占用的 GPU-hours。
如果额外保留两个空闲 D 副本等待 burst，它们仍进入成本分母。
如果传输失败在 D 触发重新 prefill，应单独记录回退次数与无效 P 工作。
否则看似提高的 D decode 利用率可能隐藏了更多集群计算。
同样，P 输出首 token 的实现应额外统计 handoff 后首个 ITL。
这些字段让“phase isolation 改善体验”成为可证伪的结论。

| 变量 | 至少覆盖 |
|---|---|
| 输入长度 | 1K、8K、32K 与混合分布 |
| 输出长度 | 短回答、长 reasoning、真实 EOS |
| 到达过程 | 固定速率、Poisson、突发 trace |
| prefix | 冷缓存、热缓存、热点变化 |
| 架构 | aggregated、chunked、分池、PD |
| 网络 | 正常、拥塞、传输失败 |
| 目标 | TTFT/ITL/TPOT 联合 SLO |

每轮保存完成率、错误率、goodput、P/D queue、handoff 时间与 KV 高水位。
若 PD 使用更多 GPU，至少另报单位 GPU 的 goodput 与总成本。
避免把资源增加造成的收益归因于架构本身。

### 明确的反例

短 prompt、低并发、几乎没有 phase 干扰时，PD 仍需交接 KV。
这种情况下 aggregated 往往有更短关键路径。
慢网络下，长 prompt 产生的 KV 传输可能吞掉隔离收益。
双池负载比例变化时，一个池满载、另一个空闲也会降低利用率。

## 11. 六道追问与答案

### Q1：PD 一定提高 throughput 吗？

不一定。
它首先提供阶段隔离和独立调参能力；额外传输和双池空闲会降低 raw throughput。
特定 workload 下可能改善 SLO-goodput，必须测量。

### Q2：为什么不按 GPU utilization 决定 P:D？

相同 utilization 可以对应有效计算、内存等待或通信等待。
应结合 queue、服务需求、KV pressure、SLO 与到达预测。
GPU utilization 只是一条辅助信号。

### Q3：PD handoff 应与重算时间比较吗？

主要应与 phase isolation 带来的排队和干扰收益比较。
PD 的 P 已经需要执行 prefill。
只有 remote prefix reuse/offload 场景才直接比较“恢复 KV”与“重算 miss”。

### Q4：首 token 从 P 发出，是否就隐藏了全部 handoff？

没有。
handoff 可能出现在首个后续 token gap 中。
需要报告逐 token ITL 和连续停顿，不能仅看 TTFT。

### Q5：为何 D 预分配太早也有代价？

等待 P 的期间占用目标 KV 和 admission credit。
过早预留会降低 D 池有效并发，过晚预留则可能阻塞 handoff。
应结合超时、排队估计和生命周期协议设计。

### Q6：P 与 D 可以用不同 TP 吗？

仅当 connector 和模型 layout 支持相应重分布时。
需要核对 KV heads、page layout、dtype、层映射与实际传输路径。
不能仅凭两端模型名相同就认定互通。
