## 输入已经 token 化，下一步决定本轮做多少工作

入口把文本变成 token IDs 后，请求并不会立即独占 GPU。
Scheduler 在离散 iteration 边界选择工作、分配页面、提交执行并处理结果。
Continuous batching 的变化发生在这些安全边界，不是在 CUDA kernel 中途插入请求。

本节使用 SGLang `46d9427b913b20ce0d72b95a9209717448b37368` 与 vLLM `9c8e90eb2637a863ca14e47fd436b10ed7ba6536`。
所列源码为固定快照的片段阅读，未声称全文件或最新主线覆盖。
普通文本生成是主线，特殊模型路径以明确条件标注。

## 1. 三类预算必须同时满足

设本轮调度请求集合为 $R$，对请求 $i$ 分配 $n_i$ 个计算 token。
至少需要：

$$
\sum_{i\in R}n_i\le B_{token},
$$

$$
|R|\le B_{seq},
$$

$$
\sum_i\Delta blocks_i\le FreeBlocks.
$$

token budget 控制本轮计算。
sequence budget 控制请求槽和部分 per-request 元数据。
KV budget 控制持续驻留的物理存储。
多模态、LoRA、spec、graph 还可能增加独立限制。

### 1.1 为什么 token 与 KV 不等价

前缀命中 token 可以减少计算，但仍需要合法物理页与引用。
刚好落在已有尾页内的一个新 token，可能不需要新增页。
越过页边界的一个 token，则可能新增整页。
Speculative 候选还可能预留尚未提交的 lookahead 空间。

## 2. 一个完整的页预算数例

页大小为 16 token。
两个请求已占用有效长度分别为 31 与 16。
本轮分别新增 1 与 1 token。

```text
request A: 31 → 32，页数 2 → 2，新增 0 页
request B: 16 → 17，页数 1 → 2，新增 1 页
```

虽然两个请求各计算一个 token，新增 KV 页不同。
若第三个请求需要 prefill 20 token，则至少新增两页。
剩余只有两页时，三个请求不能全部按这个计划入场。
Scheduler 应缩小工作、等待或按策略抢占，allocator 则提供精确可行性。

## 3. SGLang：围绕 batch 的演进

普通 loop 的固定主链是：

```text
request_receiver.recv_requests
  → process_input_requests
  → get_next_batch_to_run
  → run_batch
  → process_batch_result
  → update last_batch
```

`get_next_batch_to_run` 返回计划，调用者更新 `running_batch`。
该函数处理 pending chunk abort、超时与此前 prefill batch 的合并。
对仍在 chunk 中的请求，需要从普通完成 prefill 的集合中排除。
否则它会被错误地当作可正常 decode 的序列。

### 3.1 waiting、running 与 chunked

| 状态载体 | 主要含义 |
|---|---|
| waiting queue | 尚未被准入或等待恢复 |
| running batch | 可以继续执行的稳定批 |
| last batch | 上轮提交/结果关联 |
| chunked request | 尚未完成的长 prefill |

这里的 `Req` 是富状态对象，包含 token、缓存匹配、输出和完成等信息。
Batch 则组织本轮张量与请求的对齐关系。
改变请求列表后，对应 tensor 行、长度、slot 等必须一起更新。

### 3.2 `filter_batch` 不只是删 Python 列表

固定实现先构造保留索引。
然后对 requests、sequence lengths、request pool indices 和其他状态同步筛选。
若所有请求被过滤，batch 会被视为空，旧 tensor 不应再进入 forward。
如果只删请求列表却保留原 slot mapping，输出就可能对错请求。

### 3.3 `merge_batch` 的必要条件

两个 batch 合并时，需要拼接相应请求与设备元数据。
forward mode、采样、LoRA、多模态和 graph 约束可能限制是否可混合。
“把两个 list 相加”不是完整 continuous batching。
读源码时应追踪每个与 batch 维同长的字段。

## 4. `PrefillAdder` 连接策略与资源

`PrefillAdder.add_one_req` 对待准入请求计算尚需执行的输入、剩余输出预算和页对齐开销。
固定实现还区分 host-hit、SWA 与 Mamba 等资源。
它会在获得缓存节点 lock 后重新检查预算，因为 lock 改变可驱逐集合。

这说明 feasibility 不是简单读取一个全局 free token 数。
一个被请求锁定的前缀可能从 evictable 变为 pinned。
预算必须与引用变化保持一致。

### 4.1 输出长度估计的两难

按最大输出全额预留，延迟更稳但利用率低。
只按当前需求准入，利用率高但长生成可能引发频繁抢占。
SGLang 的相关预算使用 `new_token_ratio` 等估计信息。
估计不是承诺，必须监控 preemption/retraction 与 SLO。

## 5. 中间 chunk 不能产生伪输出

长 prompt 被切成多个 chunk 后，中间阶段只是推进已计算 prompt。
它不是每个 chunk 都完成一次新的生成 token。
固定 SGLang `scheduler_components/batch_result_processor.py` 使用 `inflight_middle_chunks` 区分该状态。
中间 chunk 更新计数并跳过普通 streaming。

```text
prompt length=10, chunk=4
step 1: compute prompt positions 0..3，no generated output
step 2: compute prompt positions 4..7，no generated output
step 3: compute prompt positions 8..9，sample first output
```

如果每次 chunk 都 append 一个 token，会污染历史和用户输出。
这种错误可能仍产生流畅文本，因此需要明确 reference 对照。

## 6. vLLM V1：统一 token progress

固定 `Scheduler.schedule` 的注释解释了其统一表达：

```text
num_tokens_with_spec
  = prompt tokens + output tokens + speculative tokens

scheduled work
  = target progress - num_computed_tokens
```

实际公式还涉及异步 output placeholders、长度上限和 lookahead。
不要把简化公式当完整代码。
它的思想是让 computed progress 追赶请求当前需要处理的 token 位置。

### 6.1 为什么这种表达可容纳 chunk 与 spec

长 prefill 的 gap 大，token budget 只允许推进一部分。
普通 decode 的 gap 小，通常每轮推进一个新 token。
Speculative 模式增加候选位置与预留空间，结果返回后再修正接受进度。
Prefix hit 则先增加已经可复用的 computed 部分。

同一个数值抽象能覆盖多种 phase，但不意味着执行 kernel 没有 prefill/decode 区别。
Scheduler 的统一视图与 attention backend 的专用执行可以同时成立。

## 7. EngineCore 的提交边界

固定 `EngineCore.step` 执行：

```text
scheduler.schedule
  → executor.execute_model(non_block=True)
  → grammar preparation
  → wait/get model output
  → process aborts received during execution
  → scheduler.update_from_output
```

执行期间到达的 abort 会在结果提交前处理。
这是避免取消请求继续按正常路径提交输出的重要边界。
异步版本还有 batch queue 和更多重叠，不能只用这条同步图解释全部路径。

## 8. 抢占：保留输出，重建计算状态

普通 recompute 抢占释放 KV，并将请求放回 waiting。
已对用户提交的 output token 不能凭空删除。
恢复时使用已有 token 历史重新构造 KV，而不是重新抽样这些已接受 token。

固定 vLLM `_preempt_request` 重置 computed progress 和 speculative 状态，并登记 stale output 信息。
其 `drop_stale_output` 有条件分支：某些在途输出仍交付，但不能修改已经重置的 counters；其他场景需要丢弃。
因此不能把所有 stale output 一概写成“永远丢弃”。
是否交付与是否允许修改执行状态是两个问题。

### 8.1 为什么需要代际与结果快照

旧 batch 的结果可能在请求已经抢占、恢复或取消后到达。
结果处理必须知道它属于哪次执行状态。
否则旧完成可能推进新计数、重复输出或错误释放页面。
SGLang 的 overlap loop 同样需要保留 batch/result 对应关系。

## 9. 可运行的多预算与 chunk 推演

```python
from math import ceil

def extra_pages(old_tokens, new_tokens, page=16):
    return ceil((old_tokens+new_tokens)/page)-ceil(old_tokens/page)

assert extra_pages(31, 1) == 0
assert extra_pages(16, 1) == 1
assert extra_pages(0, 20) == 2

def admit(candidates, token_budget, page_budget, sequence_budget):
    plan = []
    for rid, old, new in candidates:
        pages = extra_pages(old, new)
        if len(plan) >= sequence_budget:
            break
        if new > token_budget or pages > page_budget:
            continue
        plan.append((rid, new))
        token_budget -= new
        page_budget -= pages
    return plan, token_budget, page_budget

plan, tokens_left, pages_left = admit(
    [("A",31,1),("B",16,1),("C",0,20)],
    token_budget=32,
    page_budget=2,
    sequence_budget=3,
)
assert plan == [("A",1),("B",1)]
assert (tokens_left,pages_left) == (30,1)

prompt, computed, chunk = 10, 0, 4
emissions = []
progress = []
while computed < prompt:
    computed += min(chunk, prompt-computed)
    progress.append(computed)
    if computed == prompt:
        emissions.append(99)
assert progress == [4,8,10]
assert emissions == [99]
print(plan, progress, emissions)
```

这个策略会跳过暂时不合适的候选，并非两个框架的完整策略复刻。
它只验证 token、sequence、page 三个预算彼此独立。
真实系统还要处理公平、优先级、deadline 与缓存锁。

## 10. 状态不变量比队列名字更稳定

阅读不同版本时，优先检查：

| 不变量 | 错误后果 |
|---|---|
| 每请求只处于合法调度集合 | 重复执行或永远不执行 |
| scheduled tokens 不超过预算 | 峰值超限 |
| block table 只引用有效 owner | KV 污染 |
| 中间 chunk 不提交生成 token | 输出语义错误 |
| 已提交 token 不因抢占重采样 | 前后分叉 |
| 旧结果不修改新代状态 | 计数错乱、重复释放 |
| GPU/DMA 完成前不回收 | UAF |
| 每 terminal outcome 只结算一次 | 重复 usage/计费 |

字段名和类名会变化，这些行为约束仍然存在。
当一个优化修改了异步顺序，就应明确说明它如何保持这些约束。

## 11. 公平与性能反例

优先长 prefix 命中请求，可能提高 TPS，却让无缓存租户长期等待。
优先短请求，可能降低平均 TTFT，却饿死长 reasoning。
更小 chunk 可以改善 decode cadence，却增加调度与 launch 开销。
更多并发可以提高吞吐，却增加 KV 压力与抢占重算。

因此回归指标至少包括：

- 总 goodput 与各租户达标率。
- p99 TTFT/ITL/TPOT。
- 最老 queue age。
- preemption 次数和重算 token。
- allocator 失败与 KV 高水位。
- CPU schedule time。

只报告平均 TPS，不足以判断调度器优化是否正确。

## 12. 六道追问与答案

### Q1：Continuous batching 是否能在 kernel 中途插入请求？

通常不是。
它在 iteration 或受支持的安全边界重组后续 batch。
已经提交的 kernel 使用既定输入和地址。

### Q2：同样新增一个 token，为什么页预算不同？

它可能落在已有尾页，也可能跨越页边界。
物理分配按页面粒度，计算按 token 粒度。
还需考虑 prefix sharing 和 lookahead。

### Q3：为什么中间 prefill chunk 不能 stream token？

它尚未处理完整输入，不应把中间 logits 当正式生成结果。
只推进 prompt KV 与 computed progress。
最后 chunk 完成后才按生成语义提交。

### Q4：抢占后为何不能从头重新采样？

用户可能已经看到部分输出。
重算 KV 应 teacher-force 已接受 token 历史，保持已提交语义。
重新采样可能产生不同回答。

### Q5：所有 stale output 都应该丢掉吗？

不是通用结论。
固定 vLLM 有条件保留在途 token 但禁止修改重置计数的路径，也有 drop 模式。
必须区分输出交付与执行状态更新的契约。

### Q6：Allocator 应该自行选择抢占谁吗？

普通分层设计中应由 scheduler 决定牺牲者和公平策略。
allocator 提供物理可行性与原子分配/回滚。
混在一起会让优先级和资源状态难以解释。
