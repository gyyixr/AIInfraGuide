## 本章要解决的问题

模型权重放得下，不代表能在目标并发和上下文下稳定服务。
分布式推理需要同时规划权重、KV、临时工作区和通信。
还必须保证所有 rank 对模型身份、请求顺序和故障恢复达成一致。
本章按容量、执行和部署三个层面展开。

原导读路径保留，详细内容进入以下三篇。

## 1. 先建容量模型

每个 rank 的显存账至少包含：

```text
weights
+ active KV
+ activations/workspace
+ CUDA Graph pools
+ communication buffers
+ runtime/allocator
+ reserve
```

标准 GQA 的 KV 字节是：

$$
M_{KV}=T_{active}\times2Lh_{kv}db_{kv}.
$$

使用 KV head 数，不使用 Q head 数。
TP 下还要确认 KV 是否真正分片，或者存在复制。
MLA、混合 recurrent state、滑动窗口层应按真实结构另算。

## 2. 并行维度与真实 GPU 数

TP 切单层矩阵，通常需要频繁 collective。
PP 切模型层，跨 stage 传 activation，并承担 bubble。
请求 DP 复制完整服务副本，推理时通常没有梯度同步。
CP 切上下文，仍需交换全局 attention 所需的信息。
EP 切专家，通过 token dispatch/combine 完成路由。

只有独立维度才能直接相乘。
某些 Attention DP/CP/TP 在同一个物理 world 内分解。
MoE 又可能对同一批 rank 建立另一套专家组。
因此先画 rank→GPU→node→NIC，再算逻辑组。

## 3. 通信量与通信时间

字节模型是起点，不是性能结论。
实际延迟还受固定启动成本、拓扑、协议、消息形状和最慢 rank 影响。
TP 增加到跨节点后，计算减少可能小于 collective 增加。
PP 更少的通信次数也可能被 stage 不均衡抵消。

同样 GPU 总预算下，应比较更大 TP 与更多 DP 副本。
所有候选必须先通过容量和正确性检查。
再用相同 trace、SLO 和缓存状态比较 goodput。

## 4. MoE 的四层均衡

| 层 | 作用 |
|---|---|
| 训练均衡 | 影响 router 学到的分布 |
| 专家复制 | 用额外权重显存增加物理副本 |
| EPLB | 根据统计迁移或重排专家 |
| Dispatch-time | 本批选择具体副本 |

它们互补，不能相互冒充。
把 token 发给另一个不同 logical expert 会改变模型语义。
专家映射更新还需要先准备权重、再提交 map、最后等待旧读者退出。

## 5. 多节点部署的一致性

每个副本应冻结 artifact、tokenizer、template、runtime 和 group 配置。
同名目录与相同镜像标签不足以证明内容一致。
加载需经过校验、分片、通信组初始化和代表性 warm-up。
完整副本 ready 后才进入路由。

一个 rank 的 HTTP 端口存活，不等于整个 TP/PP group 可执行。
Collective timeout 也不直接证明网络故障。
先查所有 rank 的最后进度、调用序号和更早 OOM/异常。

## 6. 本章动手任务

1. 计算 70B BF16 + GQA 在 TP=4 下的每卡权重和 KV。
2. 把 context、并发和 KV 复制因子分别翻倍，观察不同影响。
3. 画 8 个 rank 的 Attention DP/CP/TP 分解。
4. 对固定专家直方图比较两种物理布局。
5. 用 manifest 模型拒绝混合 artifact 和旧 epoch。

不要把这些 CPU 结果写成 GPU 性能测试。
若有多机环境，再补实际 collective、加载峰值和端到端压测。
