## 先固定“快”的含义

一个配置可以每秒生成更多 token，却让每个用户等待更久。
另一个配置可能平均延迟更低，却拒绝大量长请求。
因此 benchmark 必须同时描述工作量、时间边界、完成结果和服务目标。
单个 TPS 数字无法回答系统是否适合某项业务。

本节用纯 CPU 时间戳算例建立指标口径。
这些结果是计算验证，不是某推理引擎的性能报告。

## 1. 一条请求保存哪些时间戳

```text
a: client scheduled arrival
s: client actual send
g: gateway receive
q: engine queue enter
p: prefill start
t1: first visible token
t2 ... tN: later visible tokens
l: last visible token
f: final response/stream completion
```

`a` 与 `s` 分开，可以发现压测客户端来不及按计划发请求。
`l` 与 `f` 分开，可以发现最终 usage、finish 帧或网络 flush 的额外延迟。
客户端时钟与服务端时钟不能在未校准时直接相减。
跨机器 trace 应优先使用各自持续时间或有时钟误差标注的关联。

## 2. TTFT、ITL、TPOT 和 E2E

若从实际发送时刻开始测量：

$$
TTFT=t_1-s.
$$

逐 token 间隔：

$$
ITL_i=t_i-t_{i-1},\qquad i=2,\ldots,N.
$$

以最后一个 token 为边界的平均每输出 token 时间：

$$
TPOT=\frac{t_N-t_1}{N-1},\qquad N>1.
$$

有的工具使用 $(f-t_1)/(N-1)$。
只有当最终完成时间接近最后 token 时间时，两个值才接近。
报告中要明确采用哪个定义，不能将不同工具的字段直接混比。

$$
E2E=f-s.
$$

当 $N\le1$ 时，TPOT 未定义。
应记录缺失值与样本数，而不是填 0 拉低平均值。
失败且没有首 token 的请求也不能悄悄从分母中消失。

### 2.1 完整数例

实际发送为 0 s，token 时间为：

```text
[0.50, 0.54, 0.58, 0.90]
```

最终流结束为 0.93 s，则：

```text
TTFT = 0.50 s
ITL  = [0.04, 0.04, 0.32] s
TPOT_token = (0.90 - 0.50) / 3 = 0.1333 s
TPOT_finish = (0.93 - 0.50) / 3 = 0.1433 s
E2E = 0.93 s
```

平均 TPOT 已经比典型 40 ms 慢，但仍不能直接表达那次 320 ms 停顿。
用户感受到的是 token cadence，需要看逐 token gap 和连续抖动。

## 3. 分位数的聚合层次

“p99 TPOT”和“p99 ITL”通常不是同一个指标。

- p99 TPOT：先对每请求求平均 TPOT，再对请求取 p99。
- p99 ITL：收集所有 token gap，直接取 p99。
- 每请求最大 ITL 的 p99：先保留每请求最差停顿，再取 p99。

第二种统计会让长输出贡献更多样本。
第一种统计每个请求权重相同，但会平滑请求内部的尖峰。
三者各有用途，命名必须清楚。

### 3.1 p99 的样本量

100 个请求的 p99 只靠最末少数样本决定。
它通常不够稳定，尤其在混合长度和 burst 负载下。
报告需要给出请求数、token gap 数、重复轮次以及分位数计算方法。
bootstrap 也不能弥补完全没有覆盖真实故障模式的采样。

## 4. 吞吐的三个分母

$$
RPS=\frac{N_{completed}}{T_{wall}},
$$

$$
OutputTPS=\frac{\sum_r N_{out,r}}{T_{wall}},
$$

$$
TotalTPS=\frac{\sum_r(N_{in,r}+N_{out,r})}{T_{wall}}.
$$

Input TPS、output TPS 和 total TPS 必须分开命名。
把大量输入 token 加入分子会提高 total TPS，却不意味着生成更快。
wall time 应说明是否含 ramp-up、排空、冷启动与最后请求的尾部。

固定测量窗口中，跨边界请求还涉及 completion cohort 与 arrival cohort。
前者统计窗口内完成者，后者跟踪窗口内到达者直到结果明确。
二者可以都报告，但不可混用分子分母。

## 5. Goodput 的联合条件

定义一个教学 SLO：

```text
成功完成
且 TTFT ≤ 1 s
且 TPOT ≤ 50 ms
```

则：

$$
Goodput=\frac{\#\{r:success_r\land SLO_r\}}{T_{wall}}.
$$

如果业务还要求最大 token gap、E2E、质量或工具调用正确率，也应加入条件。
Goodput 的单位可以是请求/s或合格 token/s，必须明确。
不能把两种单位直接比较。

### 5.1 两个配置的反例

测量时间均为 100 s：

| 配置 | 到达 | 成功完成 | 满足联合 SLO | 输出 token |
|---|---:|---:|---:|---:|
| A | 1000 | 980 | 700 | 98000 |
| B | 1000 | 950 | 900 | 95000 |

A 的 output TPS 是 980，B 是 950。
但 A 的 goodput 只有 7 req/s，B 是 9 req/s。
若目标是交互 SLO，B 更合适。
还要报告 A 的 20 次失败与 B 的 50 次失败，不能只展示合格完成者。

SLO attainment 若以全部有效请求为分母，A=70%、B=90%。
如果以成功完成者为分母，应另外命名为“成功请求内 SLO 达标率”。
拒绝率和超时率必须保留。

## 6. Little's Law 的正确使用

在稳定、守恒且统计边界一致的系统：

$$
L=\lambda W.
$$

$L$ 是平均在系统内请求数。
$\lambda$ 是真正进入该边界的有效到达率。
$W$ 是这些请求在同一边界中的平均逗留时间。

例如外部到达 100 req/s，准入后只进入 80 req/s。
系统内平均停留 2.5 s，则：

$$
L=80\times2.5=200.
$$

使用外部 100 req/s 会得到错误的 250。
如果队列持续增长，不能用一个短窗口的平均值假装系统已经稳态。
Little's Law 不告诉你 p99，也不证明排队延迟满足 SLO。

## 7. Open-loop 与 closed-loop

### 7.1 Open-loop

按照独立时钟安排请求，不等待上一请求完成。
到达过程可以是固定间隔、Poisson 或生产 trace。
即使服务变慢，计划请求仍继续到达。
这样可以暴露系统容量不足时的排队和拒绝。

```text
scheduled arrivals: 0.0  0.1  0.2  0.3  0.4 ...
request duration:  0.2 → 0.5 → 1.0 → 2.0 ...
```

必须记录客户端实际发出时间。
如果客户端自身拥塞，只记录成功发出的请求，会低估 offered load。

### 7.2 Closed-loop

固定并发客户端，每个客户端收到完成后才发送下一请求。
若有 $C$ 个客户端、平均响应 $W$、think time 为 $Z$：

$$
X\approx\frac{C}{W+Z}.
$$

当 $C=100,Z=0,W=1s$，吞吐约 100 req/s。
服务慢到 $W=5s$ 时，客户端自动只发约 20 req/s。
看起来队列没有继续爆炸，其实 offered load 已经下降。

Closed-loop 适合回答固定用户并发的体验。
Open-loop 更适合回答某到达率下是否会过载。
二者应配合使用，不能将其中一个当万能容量证明。

## 8. 长度分布不能只给均值

两个 workload 平均 ISL 相同，却可能具有完全不同的 tail。
例如全部 4K prompt，与 90% 1K + 10% 31K，平均都是 4K。
后者的长 prefill 干扰、KV 峰值和 TTFT 分布可能更差。

还要保留 ISL 与 OSL 的相关性。
若长 prompt 往往也有长输出，KV 驻留和服务需求会同时放大。
独立随机抽 ISL/OSL 可能破坏这种相关结构。

推荐负载清单：

- ISL/OSL 联合分布。
- prefix 共享与失效模式。
- 多轮 append、branch、工具调用。
- sampling、EOS、stop、logprobs。
- tenant、priority、语言和模型。
- burst、取消、慢客户端。
- 冷启动、热缓存与长期 churn。

`ignore_eos` 可以控制输出工作量，适合部分 A/B。
但它改变真实终止分布，不能冒充业务吞吐与计费成本。

## 9. 可运行的指标计算

```python
from statistics import mean

def metrics(send, token_times, finish):
    if not token_times:
        return {"ttft": None, "tpot": None, "itl": [], "e2e": finish-send}
    gaps = [b-a for a, b in zip(token_times, token_times[1:])]
    return {
        "ttft": token_times[0] - send,
        "tpot": mean(gaps) if gaps else None,
        "itl": gaps,
        "e2e": finish - send,
    }

m = metrics(0, [0.50, 0.54, 0.58, 0.90], 0.93)
assert abs(m["tpot"] - 0.4/3) < 1e-9
assert abs(max(m["itl"]) - 0.32) < 1e-9
assert metrics(0, [0.2], 0.21)["tpot"] is None
print(m)

def report(arrivals, completed, good, tokens, seconds):
    return {
        "rps": completed/seconds,
        "output_tps": tokens/seconds,
        "goodput": good/seconds,
        "attainment": good/arrivals,
        "failure_rate": (arrivals-completed)/arrivals,
    }

a = report(1000, 980, 700, 98000, 100)
b = report(1000, 950, 900, 95000, 100)
assert a["output_tps"] > b["output_tps"]
assert a["goodput"] < b["goodput"]
print("A", a)
print("B", b)
assert 80 * 2.5 == 200
```

真实 trace 还应验证时间单调、重复事件、负 token gap 和缺失 finish。
异常数据不能直接带入分位数计算。
先报告 trace 完整性，再报告性能。

使用 vLLM bench、GenAI-Perf 或自定义客户端时，先保存版本与 `--help`。
不同工具对 tokenization、TTFT、TPOT、并发和 request rate 的定义可能不同。
不要只复制命令名而忽略统计实现。

  framework_commit: fixed-commit

输出报告必须能够从原始数据重新计算。

## 11. 六道追问与答案

### Q1：为什么 TPOT p99 很好，用户仍感到卡顿？

请求内平均把单次长 ITL 平滑了。
需要看逐 token gap、每请求最大 gap 和连续抖动。
网络分块也可能让用户一次看到多个 token。

### Q2：SSE chunk 是否等于一个 token？

不一定。
一个 chunk 可以包含多个 token 或控制信息。
如果无法恢复 token 边界，应明确指标是 inter-chunk latency。

### Q3：单 token 请求 TPOT 应填 0 吗？

不应。
没有首 token 之后的间隔，TPOT 未定义。
记录缺失并报告样本量，避免低估平均值。

### Q4：为什么 open-loop 更容易出现超时？

它不会因为服务变慢而自动减少到达率。
当 offered load 超过能力时，排队和拒绝会暴露出来。
这通常是有价值的容量证据，而非压测器错误。

### Q5：Little's Law 能推出 p99 吗？

不能。
它连接长期平均值，不描述尾部形状。
尾部需真实 trace、队列模型或实测分布。

### Q6：不同模型输出 token 数不同，如何比成本？

先统一任务和质量约束，再同时报请求、字符/任务完成与模型 token 口径。
不同 tokenizer 的 token 不天然等价。
按合格任务或合格输出归一通常更贴近产品价值。
