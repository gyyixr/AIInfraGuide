## 1. 结构化输出是逐 token 执行协议

要求“只输出JSON”可以写进prompt，但它不等于运行时语法约束。
Constrained decoding在每一步根据已接受历史计算合法token集合，再限制采样。
Grammar状态、tokenizer、模型logits、停止条件和stream必须对同一历史达成一致。
投机解码进一步引入尚未提交的候选历史。

本节固定vLLM `9c8e90eb2637a863ca14e47fd436b10ed7ba6536`。
已只读核对相关本地文件与HEAD一致；未安装或运行该引擎。
XGrammar设计背景参考[原论文](https://arxiv.org/abs/2411.15100)，接口事实以固定vLLM适配器为准。
CPU oracle是有限教学grammar，不是完整JSON Schema实现。

## 2. 五类状态不能合成一个对象

| 状态 | 生命周期 | 是否可直接跨请求共享 |
|---|---|---|
| Schema/grammar文本 | 请求或模板配置 | 身份相同且权限允许时可复用 |
| Compiled grammar | 编译缓存 | 编译上下文兼容时可复用 |
| Matcher/parser状态 | 已接受token历史 | 不可把可变状态随意共享 |
| Mask rows | 某批某位置 | 受request/position与设备事件保护 |
| Stream/stop状态 | 客户端可见输出 | 请求级独立 |

同一schema的两个请求可能已生成不同前缀。
共享compiled grammar通常合理，共享同一个可变matcher会把历史串在一起。
Reasoning parser还可能依赖每请求template kwargs，固定代码明确按请求保存。

## 3. 从 API 参数到编译结果

`StructuredOutputRequest.from_sampling_params`建立约束请求。
其key区分JSON、JSON object、regex、grammar、choice或结构标签等形式。
支持形式最终由选定backend与输入验证共同决定，不能由key枚举推断全部backend都兼容。

固定主链是：

```text
structured output parameters
  → request-local StructuredOutputRequest
  → StructuredOutputManager.grammar_init
  → backend.compile_grammar
  → compiled context + new matcher
  → grammar ready
  → scheduler admission
```

编译可能昂贵，尤其是首次schema/tokenizer组合。
它与GPU prefill不同，应有独立等待与错误指标。

### 3.1 异步编译的真实边界

普通路径将编译提交给线程池，request暂时等待Future。
`StructuredOutputRequest`轮询完成，并保留异常给scheduler处理。
编译错误应只失败对应请求，而不把异常吞掉后继续无约束生成。

固定manager还对`external_launcher`关闭异步编译。
原因是该模式每个TP rank都有scheduler，若各rank在不同时刻从grammar waiting进入waiting，会破坏一致调度。
这是明确的配置条件，不能泛化“编译永远异步且无代价”。

## 4. XGrammar 适配器做了什么

固定`backend_xgrammar.py`先从tokenizer建立TokenizerInfo。
编译器可缓存相应grammar，但每请求仍构造自己的GrammarMatcher。
Matcher配置stop token覆盖和投机所需rollback容量。

它暴露的核心操作是：

```text
fill_bitmask     根据当前状态生成下一token合法集合
accept_tokens    正式推进状态
validate_tokens  临时试走并回滚
rollback         撤销尚不应持久的推进
is_terminated    查询语法终止状态
```

Tokenizer token可能包含多个字符、空格或byte fallback。
不能用“下一个字符合法”直接替代“整个token解码后合法”。
编译上下文必须匹配tokenizer、词表及相应特殊token规则。

## 5. Mask 如何改变目标分布

设状态为g，合法token集合为A(g)，模型logit为z。
约束后的logit：

$$
\tilde z_v=\begin{cases}z_v,&v\in A(g)\\-\infty,&v\notin A(g).\end{cases}
$$

然后按实际temperature/truncation顺序得到目标分布。
在最简单softmax情形：

$$
p_G(v)=\frac{e^{z_v}\mathbf1[v\in A(g)]}{\sum_{u\in A(g)}e^{z_u}}.
$$

这改变了无约束模型的采样分布。
“保持target distribution”的投机正确性，必须说明target是约束后的哪条实际采样路径。
格式合法不保证字段事实正确、业务范围正确或工具调用安全。

### 5.1 All-masked 不是正常概率分布

若合法集合为空，softmax分母为0。
不能随便选一个token继续，也不能让NaN流入采样。
应区分语法已经终止、合法stop是否开放、schema不可满足和内部状态错误。
实际失败应有明确finish/error语义。

## 6. 数例：mask 存储不等于零开销

固定worker用int32压缩bitmask，每32个词表token占一个整数。
词表V=128000时，一行需要4000个int32，即16000 bytes。
Batch=16、每请求4个draft加1个bonus位置，需要80行，约1.22MiB。

$$
M_{mask}=B(\gamma+1)\lceil V/32\rceil\times4.
$$

如果改用逐logit FP32加法mask，仅这一表示就会放大32倍。
但bitmask仍需CPU构造、IPC/拷贝、位置映射和GPU应用。
高batch/长draft时，grammar可能进入关键路径。

## 7. Worker 必须对齐 request 与 position

固定模块化GPU路径`StructuredOutputsWorker.apply_grammar_bitmask`先复制mask与mapping。
它以`(request, position)`映射到实际logit rows，避免把调度位置和压缩后的logit绝对下标混淆。
当前stream等待copy stream后应用mask；copy stream又等待consumer，保护buffer复用。

```text
CPU matcher states
  → mask rows ordered by request / candidate position
  → async mask + mapping copy
  → GPU wait
  → mask matching logits
  → sampling / verification
  → buffer last-use completion
```

另一`GPUModelRunner`路径使用其对应structured-output工具函数。
本节不把两个worker实现名称拼成一条必经调用链。
跨路径共同需要的是位置、批次快照和异步生命周期一致。

## 8. 投机验证需要未来各位置的 mask

已接受历史h对应正式状态g。
草稿给出候选`y1,y2,...`，验证每一位置需要该候选前缀对应的合法集合。
生成mask时可以暂时推进matcher，但必须恢复到g，等待验证结果再正式提交。

```text
g --draft y1--> g1 --draft y2--> g2
│              │               │
mask at pos0   mask at pos1     bonus mask
└──────── temporary traversal ──┘
          rollback to g
          commit verified accepted path only
```

固定`grammar_bitmask`记录`state_advancements`，填完候选与bonus的mask后调用rollback。
这一步是“构造未来约束”，不是“已经接受草稿”。
普通scheduler随后用实际`new_token_ids`推进正式grammar状态。

### 8.1 随机投机的分布条件

设实际draft proposal为q，约束target为pG。
接受仍需使用实际proposal概率：$\min(1,p_G(y)/q(y))$。
拒绝残差对应正部`pG-q`。
Draft是否自身使用grammar约束，要按真实路径定义q，不能事后偷偷替换成另一分布。

如果draft提出非法token，target对它概率为0，需要正确拒绝/处理该候选后缀。
仅因为候选文本看起来像JSON，就跳过概率或grammar验证是不成立的。

## 9. Tree draft 的分支隔离

树的兄弟节点具有不同历史，不能复用同一个已推进到兄弟分支的matcher。
可以使用独立状态副本、持久状态结构或沿DFS推进/回滚。
选择哪种表示是实现问题，不改变“每条路径只见自己祖先”的不变量。

每个候选节点至少关联parent、token、position、grammar checkpoint与KV候选范围。
最终只有一条通过验证的路径提交。
其他分支的grammar、KV和输出候选都应退出正式历史。
Grammar rollback成功不等于GPU候选页面已经安全回收。

## 10. Reasoning、grammar终止与 stop string 是三条边界

某些请求先生成reasoning，再开始受约束答案。
固定manager的reasoner是request-local，并跟踪结束标记所在位置。
如果标记出现在一轮spec窗口中间，窗口后面的mask与正式推进必须使用正确分界。
不能把reasoning文本或结束标记作为JSON内容喂给grammar。

Grammar终止表示语法状态完成。
EOS/stop token由token级停止语义处理；stop string还需detokenize才能检查。
`max_tokens`可能在合法前缀尚未完整时终止，因此结构化输出仍可能因长度或取消返回不完整对象。
应用要检查finish reason和完整解析，而不能只看配置启用了JSON约束。

### 10.1 Spec 多 token 输出的 stop 一致性

固定`detokenizer.check_stop_strings`在一批新增文本内选择最早完成的stop string，同完成位置按列表顺序处理。
这使一轮spec产生多个token时，结果尽量与逐token追加的停止语义一致。
如果只按stop列表找到第一个匹配，可能跳过文本中更早完成的停止项。
Stream还需暂缓可能构成跨token stop的尾部，避免先发出后才想撤回。

## 11. CPU oracle：暂存候选与正式提交

语言只包含`{"x":0}`或`{"x":1}`及EOS。
这里每个符号当成教学token，不模拟真实BPE、byte fallback或任意JSON。

```python
class Grammar:
    edges = {
        0:{"{":1}, 1:{'"x"':2}, 2:{":":3},
        3:{"0":4,"1":4}, 4:{"}":5}, 5:{"EOS":6}, 6:{}
    }
    def __init__(self):
        self.states = [0]
    def allowed(self):
        return set(self.edges[self.states[-1]])
    def accept(self, token):
        assert token in self.allowed()
        self.states.append(self.edges[self.states[-1]][token])
    def rollback(self, count):
        assert 0 <= count < len(self.states)
        if count:
            del self.states[-count:]

g = Grammar()
for token in ["{",'"x"',":"]:
    g.accept(token)
saved = g.states.copy()
mask_rows = []
for token in ["0","}"]:
    mask_rows.append(g.allowed())
    g.accept(token)
mask_rows.append(g.allowed())
g.rollback(2)
assert g.states == saved
assert mask_rows == [{"0","1"},{"}"},{"EOS"}]

# 假设验证拒绝第一个draft，校正采样为1，只提交实际输出。
for token in ["1","}","EOS"]:
    g.accept(token)
assert g.states[-1] == 6
assert g.allowed() == set()

vocab,batch,draft = 128000,16,4
mask_bytes = batch*(draft+1)*((vocab+31)//32)*4
assert mask_bytes == 1280000
text = "A<END>B<STOP>"
stops = ["<STOP>","<END>"]
matches = [(text.index(s)+len(s),i,s) for i,s in enumerate(stops) if s in text]
assert min(matches)[2] == "<END>"
print("temporary masks rolled back; committed state complete; mask_bytes",mask_bytes)
```

Oracle验证状态顺序、rollback与stop优先级，不证明随机投机分布或XGrammar性能。
概率验证仍需独立的离散分布/Monte Carlo测试。

## 12. 取消与故障协议

| 事件 | 正确处理方向 |
|---|---|
| 编译失败 | 对应请求报错，不静默无约束运行 |
| 编译期间取消 | 标记终态；迟到Future不能重新入队 |
| mask构造期间取消 | 不提交旧状态，保留必要任务/资源到安全点 |
| GPU mask应用尚未完成 | buffer等待最后consumer，不提前覆写 |
| verifier返回旧attempt结果 | request/step generation校验 |
| grammar拒绝已验证输出 | 明确内部错误并停止，不盲目跳过 |
| 达到max_tokens | 返回长度终止，不能宣称完整schema结果 |

固定scheduler在正式`accept_tokens`失败时将请求置为错误完成。
本节没有声称线程池Future能被强制立即终止。
取消是停止提交与隔离迟到结果，再完成安全清理；其底层GPU/KV部分参见7.3。

## 13. 性能与质量反例

### 13.1 一个分布重归一化数例

假设模型在三个token上的原概率为`[0.40,0.35,0.25]`。
当前grammar只允许第0与第2个token。
去掉非法项后，正确分布是：

$$
p_G=[0.40/0.65,0,0.25/0.65]=[8/13,0,5/13].
$$

不能简单把中间概率清零后仍把原总和1作为分母。
也不能先按原分布采样，遇到非法项就默认替换成第0个token：那会得到另一种分布。
如果draft提议第1个token且q概率非零，约束target对它为0，必须按验证算法处理拒绝。
这说明格式约束同时影响概率校正，不只是给最终文本做格式检查。

### 13.2 系统成本仍需实际测量

编译缓存命中可以省schema准备，但每请求matcher仍需独立推进。
大词表、大batch、长draft增加mask行数和CPU工作。
GPU forward变快后，grammar与IPC更可能暴露在关键路径。
调大线程池也可能与tokenizer争CPU，不能无限并行。

格式合法的JSON仍可能值不正确、遗漏业务必需关系或返回无意义内容。
不同backend支持的schema/regex范围也可能不同。
用schema通过率、任务正确率、TTFT/ITL和错误率一起评估。
不要把论文“低开销”当每种schema和负载的保证。

## 14. 六道追问与答案

### Q1：Compiled grammar能共享，matcher也能共享吗？

Matcher包含每请求已接受历史，通常不能共享可变实例。
编译上下文和请求状态有不同生命周期。
Reasoning parser还可能依赖每请求参数。

### Q2：为什么生成spec mask之后要rollback？

那只是临时试走候选，以获得未来位置约束。
验证尚未决定提交哪些token。
不回滚会把尚未接受的draft写入正式历史。

### Q3：Grammar要求target与draft分布相同吗？

不要求模型分布相同。
接受校正必须使用真实proposal q和真实约束target pG。
后处理时擅自重定义q会破坏概率论证。

### Q4：JSON约束能保证任何终止时都返回完整JSON吗？

不能。
长度上限、取消、错误或不兼容stop可能截断合法前缀。
需要检查finish reason与完整解析结果。

### Q5：为什么异步grammar编译在某配置被关闭？

固定external_launcher模式每TP rank独立scheduler。
不同编译完成时刻可能让调度状态分叉。
性能机制必须服从分布式一致性。

### Q6：格式正确是否足以验收structured output？

还需任务语义、字段关系、长度/错误、stream与取消测试。
对工具调用还要验证授权与幂等。
语法约束不能替代这些应用契约。
