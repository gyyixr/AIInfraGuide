## 先过滤可服务副本，再优化路由

最快的副本如果不支持请求的模型、工具或 context，就不是可选目标。
拥有 prefix 的副本如果已经过载，也未必能更快返回首 token。
因此路由应先检查能力与硬约束，再比较预计完成时间。

扩缩容则回答“未来一段时间需要多少可服务副本”。
模型加载有延迟，所以它不能只对眼前队列做即时反应。
路由、admission 和 autoscaling 应共享一致的资源口径。

## 1. 路由决策分成三步

```text
1. capability filter
   model/artifact, context, tools, quant, security domain

2. hard guardrails
   readiness, health, queue cap, KV budget, tenant limit

3. ranking
   predicted queue + compute + transfer + network
```

Prefix locality 是第三步的优化信息。
它不应越过前两步的正确性与容量边界。
Router 的缓存视图最终一致，worker 的实际 lookup 才是权威。

## 2. 三类路由策略

| 策略 | 优点 | 常见失败 |
|---|---|---|
| Round-robin | 简单、低状态开销 | 忽略长度和异构能力 |
| Least-load | 适应负载变化 | 度量滞后、惊群 |
| Prefix-aware | 节省重复 prefill | 热点聚集、cache hint 过期 |

“load”应该说明具体单位。
队列请求数相同，可能一个队列全是短请求，另一个全是长上下文。
可以用 waiting tokens、预计服务需求、KV pressure 和 oldest queue age 组合估计。
估计误差需要通过 observed completion 回馈校准。

## 3. 一个可解释的评分模型

对副本 $r$：

$$
\hat T_r=T_{network,r}+\hat W_{queue,r}
+p_{hit,r}T_{hit,r}+(1-p_{hit,r})T_{miss,r}.
$$

也可以加入成本、风险与业务等级。
但不同量必须统一单位，否则任意加权的分数无法解释。
将成本换成策略权重时应记录权重来源。

### 3.1 完整数例

两个副本的网络时间相同，忽略不计：

| 副本 | queue | 命中概率 | hit compute | miss compute |
|---|---:|---:|---:|---:|
| A | 300 ms | 90% | 20 ms | 200 ms |
| B | 20 ms | 10% | 20 ms | 200 ms |

则：

$$
\hat T_A=300+0.9\times20+0.1\times200=338\ ms,
$$

$$
\hat T_B=20+0.1\times20+0.9\times200=202\ ms.
$$

B 命中率更低，但预计首 token 更快。
如果系统总是把热门 prefix 发到 A，会不断强化热点。
可以设置硬负载上限、随机化或 two-choice 选择，降低集体追逐同一副本。

## 4. 路由状态如何失效

缓存事件应带 worker epoch 与序号。
worker 重启后旧 cache hint 失效。
事件丢失、乱序和延迟需要 snapshot、TTL 与缺口检测。

```text
cache event epoch=7, seq=101
cache event epoch=7, seq=103
  → detected gap 102
  → mark hint uncertain
  → reconcile snapshot
```

不确定时应允许正常 miss/recompute。
不能用路由 hint 为错误 KV identity 背书。
同时将 predicted reusable tokens 与 actual reusable tokens 分开记录。
这样才能区分缓存失效、路由失误和输入变化。

## 5. Autoscaling 使用有效服务率

先在固定配置与 workload 下测量每副本满足 SLO 的服务能力。
设该能力为 $\mu_{SLO}$ requests/s。
预测到达率为 $\hat\lambda$，容量余量系数为 $h>1$：

$$
n_{desired}=\left\lceil\frac{h\hat\lambda}{\mu_{SLO}}\right\rceil.
$$

如果 $\mu_{SLO}$ 已经包含目标利用率的安全余量，就不要再重复乘另一套等价余量。
若用的是饱和 service rate，则需显式加入目标利用率。
两种口径都可以，但不能混算。

### 5.1 容量数例

每副本在既定长度混合下能稳定交付 8 req/s，且满足 SLO。
预测峰值是 50 req/s，额外故障/误差余量取 20%：

$$
n=\lceil1.2\times50/8\rceil=8.
$$

如果每副本需要 4 GPU，总量为 32 GPU。
这只适用于测量时的模型、长度、prefix、硬件和并行配置。
OSL 翻倍后不能继续使用原来的 8 req/s。

## 6. 冷启动带来的控制滞后

设现有容量为 $C$ req/s，突发到达率为 $\lambda>C$。
新副本启动需要 $T_{start}$ 秒。
若期间不拒绝，新增排队量近似为：

$$
\Delta Q=(\lambda-C)T_{start}.
$$

若现有容量 40 req/s，突发 60 req/s，冷启动 90 s：

$$
\Delta Q=20\times90=1800\ requests.
$$

即使 90 秒后扩到 80 req/s，清空新增队列也需约：

$$
1800/(80-60)=90\ s.
$$

这说明响应式扩容可能无法挽救已经错过的 TTFT SLO。
需要预测、warm pool、提前加载与有界 admission。
无限排队不能替代冷启动治理。

## 7. 冷启动分解

```text
schedule GPU resources
  → pull image
  → fetch/verify artifact
  → deserialize/shard
  → copy/repack weights
  → initialize groups
  → JIT/autotune
  → CUDA Graph capture
  → representative warm-up
  → readiness
```

其中一些阶段可以重叠，但最终应测关键路径。
本地 artifact cache 减少下载，不能消除 GPU copy 和 graph capture。
预置镜像减少 image pull，也不能证明模型权重已经可用。

### 7.1 Warm pool 的两类成本

一种是仅准备好节点、镜像和本地权重。
另一种是模型已经在 GPU 中且完成 warm-up。
前者便宜但仍有加载时间，后者响应快但持续占显存与 GPU。
应按冷启动 SLO 和流量可预测性选择，而不是统称“已预热”。

## 8. 三类探针的准确语义

| 探针 | 回答的问题 | 失败后的典型效果 |
|---|---|---|
| startup | 是否完成允许较慢的启动 | 按阈值重启 |
| readiness | 现在是否可以接新流量 | 从服务目标摘除 |
| liveness | 进程是否需要重启恢复 | 重启容器 |

配置 startup probe 后，Kubernetes 会先等待其成功，再开始对应的 liveness/readiness 检查。
readiness 失败不等于进程必须被杀死。
长模型加载期间反复触发 liveness，会形成永远启动不完的循环。
健康端点是否真的检查模型与组状态，需要阅读服务实现。

### 8.1 探针示例

下面配置假设你已经实现这三个不同语义的端点。
它不是声称所有推理引擎原生提供这些路径。

```yaml
startupProbe:
  httpGet:
    path: /startupz
    port: 8080
  periodSeconds: 5
  failureThreshold: 60
readinessProbe:
  httpGet:
    path: /readyz
    port: 8080
  periodSeconds: 2
  failureThreshold: 2
livenessProbe:
  httpGet:
    path: /livez
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
```

这里 startup 大致允许 300 秒启动窗口。
具体重启时间还受 timeout、调度和探针执行时间影响。
阈值应从真实启动分布与故障恢复目标确定。

## 9. 缩容比停进程多一步

```text
mark replica DRAINING
  → stop assigning new requests
  → drain existing streams / explicit deadline
  → finish or abort transfers safely
  → release cache and GPU resources
  → terminate worker group
```

普通 autoscaler 不理解一个 stream 是否已输出一半答案。
应用需要自己的 graceful drain 契约。
缩容时保留大量 hot prefix 的副本会影响下一轮 TTFT，也应计入选择。
但不能因此永久不缩容，应比较缓存价值与空闲成本。

### 9.1 Hysteresis 防止抖动

扩容可以相对积极，缩容则使用更长观察窗口和最小驻留时间。
同时限制每轮调整幅度。
若每次负载稍降就释放热副本，下一次突发又要重新冷启动。
反复变化会形成缓存与容量的正反馈抖动。

## 10. 可运行的路由与扩容计算

```python
from math import ceil

def eta(queue_ms, hit_probability):
    return queue_ms + hit_probability*20 + (1-hit_probability)*200

assert eta(300, 0.9) == 338
assert eta(20, 0.1) == 202
assert eta(20, 0.1) < eta(300, 0.9)

forecast, slo_capacity, headroom = 50, 8, 1.2
replicas = ceil(forecast * headroom / slo_capacity)
assert replicas == 8
print("replicas", replicas, "gpus", replicas * 4)

arrival, old_capacity, start_s = 60, 40, 90
backlog = max(0, arrival-old_capacity)*start_s
new_capacity = 80
drain_s = backlog/(new_capacity-arrival)
assert backlog == 1800
assert drain_s == 90
print("startup_backlog", backlog, "drain_seconds", drain_s)

# 一个保守缩容示意：负载连续低于阈值才缩一份。
loads = [0.7, 0.4, 0.3, 0.35, 0.6]
low_run = 0
events = []
for tick, load in enumerate(loads):
    low_run = low_run+1 if load < 0.4 else 0
    if low_run >= 2:
        events.append((tick, "consider drain one replica"))
        low_run = 0
assert events == [(3, "consider drain one replica")]
print(events)
```

缩容示例仅说明 hysteresis。
真实实现还需可用性下限、故障域、warm pool、queue 和 stream drain 条件。

## 11. 观测最小集合

| 类别 | 关键观测 |
|---|---|
| Router | predicted/actual hit、chosen replica、ETA error |
| Queue | depth、oldest age、waiting tokens |
| KV | free/active/retiring bytes、eviction |
| SLO | 每模型/租户/长度桶达标率 |
| Scale | desired/ready/draining replicas |
| Startup | 各阶段时间、失败原因、cache 状态 |
| Cost | warm/idle GPU、重试和无效工作 |

如果 desired=8、ready=4，问题可能是启动或资源调度，不是扩容公式。
如果 ready=8 但 queue 仍涨，要核对 workload 漂移与实际 service rate。
如果 GPU 利用率低但 queue 很长，先查 CPU、路由和故障副本。

## 12. 六道追问与答案

### Q1：为什么最少连接数不等于最少负载？

连接可能空闲，也可能包含长时间生成。
请求长度、KV 和阶段决定实际资源需求。
需要 workload-aware 的度量。

### Q2：为什么缓存最热的副本不一定最好？

命中节省可能小于排队代价。
还要考虑 hint 过期、网络和租户隔离。
先通过硬约束，再比较预计完成时间。

### Q3：扩容能否立即修好过载？

不能，模型加载和 warm-up 有明显滞后。
启动期间队列仍增长，可能已经超过 deadline。
需要提前量与有界准入。

### Q4：readiness 失败应立即重启吗？

不应自动等同。
它可以表示暂时不接新流量，进程可能仍在 drain 或恢复。
liveness 才表达需要通过重启处理的存活问题。

### Q5：缩容为什么可能让下一轮延迟恶化？

释放了热权重、graph 和 prefix cache，下一轮需重新启动和计算。
应加入 hysteresis、warm pool 和缓存价值估计。

### Q6：一个 service rate 能否长期使用？

不能无条件使用。
模型、长度、OSL、缓存、backend 和硬件变化都可能改变它。
需要按配置画像并持续校准。
