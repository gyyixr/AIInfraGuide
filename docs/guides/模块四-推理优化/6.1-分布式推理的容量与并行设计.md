## 先把部署问题写成资源约束

“模型能加载”只回答了部署的一部分问题。
在线系统还需要让一定数量的请求同时保留 KV，完成 prefill，并持续生成 token。
因此，选并行度之前应先给出以下输入。

| 输入 | 必须记录的内容 |
|---|---|
| 模型 | 参数量、层数、Q/KV heads、head dimension |
| 存储 | 权重格式、KV dtype、量化 scale 和 padding |
| 请求 | ISL/OSL 联合分布、并发、前缀复用 |
| 目标 | TTFT、ITL、TPOT 的分位数与 goodput |
| 设备 | 单卡可用显存、节点内互联、节点间网络 |
| 运行时 | 框架 commit、实际 backend、graph/workspace |

本节采用 GQA 的 Dense 模型作为算例。
MLA、滑动窗口层、混合 recurrent state 必须按真实缓存结构重新计算。
本文算例是容量模型和 CPU 算术，不代表任何 GPU 的实测服务能力。

## 1. 权重、KV 与临时空间分开算

### 1.1 权重只是下界

设参数量为 $P$，每参数编码使用 $b_w$ 字节，则：

$$
M_W \ge P b_w.
$$

这里使用大于等于，是因为量化还需要 scale、zero point、对齐、重排以及未量化层。
加载时可能同时存在 CPU 原始权重、GPU 重排前后权重和临时 staging buffer。
稳态显存和启动峰值应分别测量。

一个 70B 模型的 BF16 编码下界是：

$$
70\times10^9\times2=140\times10^9\ \mathrm{bytes}
\approx130.39\ \mathrm{GiB}.
$$

这里的 B 是十进制十亿，GiB 是 $2^{30}$ 字节。
不能直接把 140 GB 写成 140 GiB。

### 1.2 标准 GQA 的 KV 公式

设活跃缓存 token 总数为 $T$，层数为 $L$，KV heads 为 $h_{kv}$，每 head 维度为 $d$。
每个元素使用 $b_{kv}$ 字节，则：

$$
M_{KV}=T\times2Lh_{kv}db_{kv}.
$$

系数 2 表示 K 与 V。
使用的是 KV head 数，不能误用 Q head 数。
$T$ 是所有活跃序列实际驻留 token 的总和，不只是 batch size。

取 $L=80,h_{kv}=8,d=128,b_{kv}=2$：

$$
m_{token}=2\times80\times8\times128\times2
=327680\ \mathrm{bytes}=320\ \mathrm{KiB}.
$$

一个缓存长度为 8192 的序列需要：

$$
8192\times320\ \mathrm{KiB}=2.5\ \mathrm{GiB}.
$$

16 个这样的序列合计 40 GiB。
若生成继续增长到 12K，总量也继续增长，除非模型和实现允许安全窗口淘汰。

### 1.3 每个 rank 的总账

对 rank $r$：

$$
M_r=M_{W,r}+M_{KV,r}+M_{act,r}+M_{workspace,r}
+M_{graph,r}+M_{comm,r}+M_{runtime,r}+M_{reserve,r}.
$$

只要最满的一个 rank 超出容量，整个副本就不可服务。
因此约束是：

$$
\max_r M_r\le M_{usable,r}.
$$

模型总显存除以卡数只在分片均衡且没有额外复制时才成立。
Embedding、LM head、专家热点、PP 层数不整除都会打破均衡。

## 2. 五种并行切分不同对象

| 方式 | 切分对象 | 请求是否跨 rank | 主要通信 |
|---|---|---|---|
| TP | 单层矩阵或 heads | 是 | AR、RS、AG |
| PP | 模型层 | 是 | 相邻 stage activation |
| 请求 DP | 完整服务副本 | 单请求通常不跨副本 | 路由与控制面 |
| CP | 上下文序列 | 是 | KV/Q/softmax 统计交换 |
| EP | 路由专家 | 是 | dispatch 与 combine |

推理 DP 不执行训练中的梯度 AllReduce。
训练 ZeRO/FSDP 的模型状态公式也不能直接套给常驻推理引擎。
普通请求 DP 会复制整模型和各副本 KV；Attention DP 与 Wide EP 则可能共享专家池。

### 2.1 TP 的矩阵推导

设 $X\in\mathbb R^{B\times H}$，$W\in\mathbb R^{H\times F}$。
列并行沿输出维切分：

$$
W=[W_0,W_1],\qquad Y_i=XW_i.
$$

每个 rank 拿到 $[B,F/2]$ 的输出。
若下一个激活函数逐元素执行，可以保持这个分片布局。
下一个 down projection 使用行并行：

$$
Z=Y_0V_0+Y_1V_1.
$$

两份局部结果形状均为 $[B,H]$，需要求和。
根据后继算子的布局，可以选择 AllReduce 或 ReduceScatter。
“每个线性层都 AllGather”会制造不必要的通信。

### 2.2 TP 的延迟模型

对单次 decode step，可近似写成：

$$
t_{step}(p)\approx t_{compute}(p)+N_{coll}\alpha
+\frac{V_{coll}(p)}{\beta_{eff}}+t_{other}.
$$

$\alpha$ 是每次 collective 的固定延迟。
$\beta_{eff}$ 是实际链路有效带宽，不是网卡标称速率。
TP 增大虽然缩小计算，却不一定减少 collective 次数。
decode 的小消息尤其容易由 $N_{coll}\alpha$ 主导。

假设 TP=2 时计算 12 ms、通信 3 ms、其他 1 ms，总计 16 ms。
TP=4 后计算降到 7 ms，但跨节点通信增到 10 ms，则总计 18 ms。
更多 GPU 的单请求速度反而下降。
是否增加 DP 副本应在相同 GPU 总预算下另做比较。

## 3. PP 的吞吐与单请求依赖

PP 把不同层放到不同 stage。
一个 token 必须顺序穿过所有 stage 才能得到 logits。
下一 token 又依赖本次采样结果，因此不能把同一请求的未来 token 提前塞满流水线。
填充流水通常依赖多个独立请求或 microbatch。

对均衡 stage、每 stage 时间 $t$、$m$ 个独立 microbatch、$p$ 个 stage：

$$
T_{flush}\approx(m+p-1)t,
\qquad U\approx\frac{m}{m+p-1}.
$$

这是理想化 forward flush 模型，不是在线服务的精确吞吐公式。
当 $p=4,m=1$，利用率仅为 25%。
当 $p=4,m=12$，利用率为 80%。
但单个 microbatch 穿过四个 stage 仍需要约 $4t$。

如果 stage 时间为 4、4、9、3 ms，稳态节拍至少受 9 ms 的最慢 stage 限制。
按层数平均切分不能保证计算均衡。
需要考虑 attention、MoE、embedding、LM head 和网络发送成本。

## 4. CP 节省什么，又增加什么

CP 将一个长上下文分给多个 rank。
单 rank 只持部分 Q 或部分 KV，但精确 dense attention 仍然需要完整可见上下文的信息。
实现可以交换 KV、移动 Q，或计算局部 attention 后合并统计量。

对两个分区，设各自产生最大值 $m_i$、指数和 $l_i$、未归一化输出 $u_i$。
合并公式是：

$$
m=\max(m_0,m_1),
$$

$$
l=e^{m_0-m}l_0+e^{m_1-m}l_1,
$$

$$
o=\frac{e^{m_0-m}u_0+e^{m_1-m}u_1}{l}.
$$

不能直接平均两个分区各自归一化后的 attention 输出。
因为两边的 softmax 分母通常不同。
CP 的位置编码、causal mask、分区边界和全局长度必须一致。

训练中的 CP 与推理 prefill/decode CP 的具体缓存布局可能不同。
某个框架支持 prefill CP，并不自动说明 decode KV 也按同一方式分片。
容量规划必须追到实际 KV allocation 和 attention backend。

## 5. 进程数不能把所有参数机械相乘

只有独立笛卡尔维度才可以写成：

$$
W=DP\times PP\times TP\times CP.
$$

SGLang 固定源码基线中的 `compute_dp_attention_world_info` 在已有 TP world 内计算：

```text
attn_dp_size = dp_size if enable_dp_attention else 1
attn_tp_size = tp_size // attn_dp_size // attn_cp_size
tp_rank = (attn_dp_rank * attn_cp_size + attn_cp_rank)
          * attn_tp_size + attn_tp_rank
```

例如物理 world 为 8，attention DP=2、CP=2、attention TP=2。
实际只有 8 个进程，不能再乘成 $8\times2\times2=32$。
MoE 还可以用同一批进程建立另一套 EP/TP 分组。

| 物理 rank | Attention DP | CP | Attention TP |
|---|---:|---:|---:|
| 0 | 0 | 0 | 0 |
| 1 | 0 | 0 | 1 |
| 2 | 0 | 1 | 0 |
| 3 | 0 | 1 | 1 |
| 4 | 1 | 0 | 0 |
| 5 | 1 | 0 | 1 |
| 6 | 1 | 1 | 0 |
| 7 | 1 | 1 | 1 |

资源清单必须列物理 GPU UUID、global rank、node、NIC 和每个 group 的成员。
这样才能识别两个逻辑维度是否复用了同一组 GPU。

## 6. 完整容量算例与可运行代码

仍使用 70B BF16、80 层、8 个 KV heads、8192 缓存长度。
假设一副本 TP=4、PP=1，KV heads 可以均匀切分且没有复制。
每卡权重下界约 32.60 GiB。
16 个活跃序列的每卡 KV 约 10 GiB。
再预留 8 GiB 给 runtime、graph、workspace 与余量，总计约 50.60 GiB。

这意味着 80 GiB 卡在这个简化模型中有空间，但并不证明 TTFT/TPOT 达标。
如果每序列 context 翻倍到 16384，每卡 KV 增到 20 GiB。
如果模型只有一个 KV head 且实现复制 KV，不能继续除以 4。

下面代码只依赖 Python 标准库。

```python
from math import ceil

GiB = 2**30
params = 70_000_000_000
layers, kv_heads, head_dim = 80, 8, 128
tp = 4
weight_bytes = params * 2
per_token = 2 * layers * kv_heads * head_dim * 2

def estimate(context, sequences, kv_shards):
    weights = weight_bytes / tp / GiB
    kv = context * sequences * per_token / kv_shards / GiB
    return weights, kv, weights + kv + 8

for context in (8192, 16384):
    w, kv, total = estimate(context, 16, tp)
    print(context, round(w, 2), round(kv, 2), round(total, 2))

assert per_token == 327680
assert estimate(8192, 16, 4)[1] == 10

# 页尾的内部碎片必须另外计入。
block_size = 16
lengths = [17, 31, 33]
allocated = sum(ceil(n / block_size) * block_size for n in lengths)
assert allocated == 112
assert allocated - sum(lengths) == 31
print("tail_waste_tokens", 31)
```

预期两行容量分别约为 `8192 32.6 10.0 50.6` 和 `16384 32.6 20.0 60.6`。
页尾例子用 81 个有效 token，却占 112 个 token 槽。
分页降低外部碎片，但不消除内部尾页浪费。

## 7. 配置实验怎样落到真实运行时

先冻结模型 artifact 与框架 commit，再记录 `--help` 输出。
下面是 vLLM 常见启动形状，需用安装版本检查参数和模型支持。

```bash
vllm serve /models/model-snapshot \
  --tensor-parallel-size 4 \
  --pipeline-parallel-size 1 \
  --max-model-len 8192 \
  --max-num-seqs 16
```

这条命令没有配置跨节点地址、设备选择、认证或生产入口。
它用于表达单副本参数组合，不是完整集群部署脚本。
`max-num-seqs` 是调度上限，不是“每条序列始终占满最大长度”的承诺。
`max-model-len` 也不能代替真实负载分布。

推荐按固定 GPU 总预算比较：

| 候选 | 单副本 GPU | 副本数 | 需要验证 |
|---|---:|---:|---|
| TP=8 | 8 | 1 | 单请求延迟、通信比例 |
| TP=4 | 4 | 2 | 聚合 goodput、每副本 KV |
| TP=2、PP=2 | 4 | 2 | 跨节点 P2P、PP bubble |
| 更低位权重 + TP=2 | 2 | 4 | 质量、实际 kernel、KV 空间 |

所有候选都必须先通过输出正确性和加载容量检查。
不能以某个配置 OOM 后少完成请求的结果作为“低延迟”胜利。

## 8. 五道追问与答案

### Q1：TP=16、KV heads=8，KV 显存是否一定除以 16？

不是。
如果 backend 复制 KV heads，每个 KV head 可能由两个 rank 持有。
应检查 attention head partition 与 KV allocation 的实际 shape。
理论 head 数和物理存储的复制因子都必须进入公式。

### Q2：PP 为什么能扩吞吐却未必降低 TPOT？

多请求能同时占据不同 stage，提升流水吞吐。
但单请求每个 token 仍要顺序经过所有 stage，并等待最后采样。
stage 间网络和同步还可能增加单 token 延迟。

### Q3：DP=4 是否可以装下原来装不下的单个模型？

普通请求 DP 不可以，因为它复制整个副本。
需要 TP/PP/EP、受支持的量化或其他容量方案。
Attention DP 加共享 EP 的特殊实现要按实际 rank groups 另算。

### Q4：容量模型剩余 20 GiB，为什么运行时仍 OOM？

可能漏了 graph pools、prefill activation 峰值、量化 repack、通信 buffer 或临时 workspace。
也可能某个 PP stage 偏大，或者 KV 实际存在复制。
应分启动、warm-up、prefill 峰值、稳态 decode 测量每 rank 高水位。

### Q5：CP 能把 dense attention 的计算复杂度变成线性吗？

不能。
精确 dense attention 的全局工作量仍随上下文近似二次增长。
CP 分摊计算和内存；通信、mask 和 softmax 合并决定实际收益。
