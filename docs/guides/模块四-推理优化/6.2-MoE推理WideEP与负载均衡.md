## 先理解一个 token 为什么会访问多张卡

Dense MLP 对每个 token 执行同一组矩阵。
MoE 则先让 router 选择少量专家，再把 token 发到保存这些专家的设备。
参数总量决定权重容量，每 token 激活参数量决定主要线性计算。
二者不能替换。

例如教学模型有 64 个专家，每个专家 1 GiB，top-k=2。
虽然每 token 只访问两个专家，部署时仍要容纳全部 64 GiB 专家权重。
这里尚未计入 attention、router、共享专家、KV 和 workspace。
若按每 token 只激活两专家来估算总显存，会少算 32 倍。

本文只做数学与状态机推演，不声明运行过 Wide EP 集群。

## 1. 从张量到通信事务

### 1.1 Router 的输入和输出

设本 rank 有 $T$ 个 token，hidden dimension 为 $H$：

$$
X\in\mathbb R^{T\times H},\qquad
W_r\in\mathbb R^{H\times E}.
$$

Router 产生专家分数：

$$
S=XW_r,\qquad P=\operatorname{softmax}(S).
$$

对每个 token 选择 $k$ 个专家索引，并保存对应 gate weight。
有些模型使用其他 scoring、归一化或分组选专家规则。
必须保持模型定义，不能为了通信方便改成另一种路由。

### 1.2 Dispatch 不是一条 All-to-All 调用

实际事务通常包括：

1. 计算 token→logical expert。
2. 查 logical expert→physical replica 映射。
3. 选择目标 rank 和本地专家槽。
4. 统计每目标的 token 数。
5. 生成 prefix offsets 与 permutation。
6. 搬运 hidden states 和路由元数据。
7. 等待目标 buffer 就绪。
8. 执行专家 MLP。
9. Combine 回原 token 所在 rank。
10. 逆排列，并按 gate weight 求和。

```text
X[T,H]
  → ids[T,k], gates[T,k]
  → packed[sum_routes,H]
  → recv[local_routes,H]
  → grouped expert MLP
  → returned[sum_routes,H]
  → weighted_reduce[T,H]
```

`sum_routes` 通常是 $Tk$，但本地去重、同 rank 多专家复用和传输协议会改变网络字节。
必须区分“专家计算路由条数”和“跨节点发送次数”。

## 2. 完整流量数例

设全组共有 4096 个 token、$H=7168$、BF16、top-k=2。
若每条 route 单独发送一份 hidden payload：

$$
V_{dispatch}=4096\times2\times7168\times2
=117440512\ \mathrm{bytes}=112\ \mathrm{MiB}.
$$

Combine 返回相同维度的专家结果，数据量也约 112 MiB。
二者相加约 224 MiB，尚未包含 metadata、对齐和协议。

若 75% 的 route 真正跨节点，跨节点 payload 约为：

$$
224\times0.75=168\ \mathrm{MiB}.
$$

若简化成一条有效带宽 25 GiB/s 的共享瓶颈链路：

$$
t_{net}\ge\frac{168\ \mathrm{MiB}}{25\ \mathrm{GiB/s}}
=6.5625\ \mathrm{ms}.
$$

真实集群有多 NIC 并行、局部路由和不同链路拥塞。
因此这个结果只是“单共享瓶颈”假设下的字节下界。
不能直接把全组总字节除以单 NIC 带宽，当成每 rank 实际时间。
应同时保存每 rank、每节点、每 NIC 的发送与接收字节。

## 3. 真正的延迟由最慢 rank 决定

一层 MoE 的时间可写成：

$$
t_{MoE}\approx t_{route}+t_{dispatch}
+\max_r t_{experts,r}+t_{combine}+t_{sync}.
$$

如果通信与计算发生重叠，应使用实际关键路径，不能直接把重叠部分再相加。
“平均每专家 token 数”无法描述这个最大值。

例如 8 个专家收到以下 route 数：

```text
expert:  0    1    2    3    4   5   6   7
routes: 400  200  120  100   80  60  40  24
```

总数是 1024，平均每专家 128。
最大值是均值的 3.125 倍。
若每 rank 放两个专家，初始布局为：

| rank | 专家 | 接收 route |
|---|---|---:|
| 0 | 0、1 | 600 |
| 1 | 2、3 | 220 |
| 2 | 4、5 | 140 |
| 3 | 6、7 | 64 |

平均每 rank 256，但最慢 rank 承担 600。
重新排列为 `(0,7)、(1,6)、(2,5)、(3,4)` 后变成 424、240、180、180。
最热 rank 负载降低，但专家 0 自身仍有 400 条 route。
只重排不能把单个超热专家拆开；需要专家内部 TP 或物理副本等其他机制。

## 4. 四层均衡的职责不同

| 层次 | 改变什么 | 时间尺度 | 主要代价 |
|---|---|---|---|
| 训练均衡 | router 学到的分布 | 训练 step | 质量与目标耦合 |
| 专家复制 | physical copies 数量 | 部署/调整 | 权重显存 |
| EPLB | 专家放到哪些 rank | 统计窗口 | 权重迁移、抖动 |
| dispatch 均衡 | 本批选哪个副本 | 每批 | 元数据与选择成本 |

### 4.1 训练均衡不是线上调度器

训练中的辅助损失或 bias 更新影响 router 长期分布。
线上 prompt 分布变化，仍可能让少数专家突然变热。
不能声称模型训练得均衡，部署时就无需监控专家负载。
也不能在线任意修改 top-k 结果而继续宣称模型输出语义不变。

### 4.2 专家复制消耗真实显存

若给 1 GiB 的专家增加三个副本，集群多消耗 3 GiB 权重容量。
还需要检查 repack、量化 scales 和加载 workspace。
路由到不同物理副本必须执行相同 logical expert 的权重和实现。
“把 token 发给不忙的另一个专家”不是等价的负载均衡。

### 4.3 EPLB 的双重目标

EPLB 应优化 rank 的总工作量和通信布局。
只均衡 token 数，可能把高频通信专家迁到跨节点位置。
一个简单目标可以写成：

$$
J=\max_r \hat t_r
+\lambda_1 V_{cross-node}
+\lambda_2 V_{migration}.
$$

系数需要用真实时间或成本归一化。
窗口过短会追逐噪声，窗口过长又跟不上持续热点。
可使用最小驻留时间、收益阈值和迁移预算来抑制来回搬运。

### 4.4 Dispatch-time 选择

如果专家 0 有两份等价副本，可以把 400 条 route 分给不同 rank。
分配应考虑排队、目标 buffer 容量、跨节点成本和当前批的计数。
过期负载信息会造成多个来源同时选中同一副本。
随机化、two-choice 或分布式配额可以降低惊群，但不能替代容量上限。

## 5. 映射切换必须像一个小型发布协议

下面是推荐的不变量，而非某框架通用 API：

```text
OBSERVE
  → PLAN(epoch+1)
  → STAGE_WEIGHTS
  → VERIFY_CHECKSUM
  → ALL_TARGETS_READY
  → COMMIT_MAPPING(epoch+1)
  → RETIRE_OLD_READERS
  → FREE_OLD_COPY
```

每个 dispatch transaction 应固定使用一个 mapping epoch。
同一 token 的 dispatch 和 combine 必须共享对应 handle 与排列信息。
不能在 dispatch 之后重新查最新映射来解释 combine。

若 map 已切到新位置但权重尚未 ready，读到的是未初始化或旧专家。
若旧 copy 在最后一个 kernel 完成前释放，就会发生异步读后释放问题。
“控制面已经更新成功”不等于 GPU 上所有旧读者已经结束。

## 6. Wide EP 与 Attention DP 的资源记账

Wide EP 将专家池跨更大物理 world 分布。
Dense attention 可以用较小 TP，甚至让各组独立处理请求。
随后 MoE 部分把 token 汇入更大的 EP 通信域。

```text
物理 world: rank 0 1 2 3 4 5 6 7

Attention:
  组 A: 0 1    组 B: 2 3
  组 C: 4 5    组 D: 6 7

MoE:
  一个跨 8 rank 的专家通信域
```

这里仍然只有 8 张 GPU。
Attention 的四个请求组不是再额外增加四套专家权重。
准确容量需要分别计算 dense 权重复制、expert 分片、KV 分片和通信 buffer。

Wide EP 的收益来自减少专家重复存储、扩大专家计算容量。
其代价包括更广的故障域、跨节点 All-to-All、decode 小消息固定延迟。
它不是所有 MoE 的默认最优配置。

## 7. DeepEP 的路径、状态与版本边界

DeepEP 提供 MoE dispatch/combine 相关通信能力。
参考宝典和本地 SGLang 固定集成中的 normal/low-latency 命名，应作为该版本的路径理解。
这些路径的 buffer 和执行约束不同。
大 token 数 prefill 容易摊薄 layout 与通信成本。
小 decode batch 更关注固定延迟和 graph 兼容。

选择路径前应记录：

- 每 rank 输入 token 数分布。
- 每专家接收 token 数的最大值。
- hidden、top-k、dtype 与专家数量。
- 节点内外拓扑。
- backend 版本和支持的 GPU。
- CUDA Graph 是否捕获了实际路径。
- handle、event、hook 的持有与释放时刻。

低延迟路径的有界 buffer 可能按最坏情况预留。
不能只看平均 route 数就证明不会 overflow。
某路径名称中有“low latency”，也不能证明所有 shape 下都更快。

### 7.1 不把旧集成接口写成新版本 API

核验到的 DeepEP V2.5 固定 commit 为 `f6aa38fe06cd4a0489e7730365d4e0114970a2f3`。
该版以 `EPBuffer` 统一高吞吐/低延迟 EP 接口，并拆出 `EngramBuffer`、`PPBuffer`、`BucketBuffer`。
它使用 NCCL Gin，已移除 V1 API 和 NVSHMEM 依赖。
其 EP dispatch/combine 需要 GPU SM，不支持 zero-SM RDMA EP。
README 要求 Hopper 或更新 NVIDIA GPU、CUDA 13.1+、PyTorch 2.10+ 和 NCCL 2.32.3+。
因此旧教程的安装命令、buffer 构造与硬件声明不能直接套到这一版。
上述变化来自[固定 V2.5 README](https://github.com/deepseek-ai/DeepEP/blob/f6aa38fe06cd4a0489e7730365d4e0114970a2f3/README.md)，不代表本机执行过该库。
阅读框架集成时应分别保存框架 commit 与 DeepEP commit，核对接口兼容层。

## 8. 可运行的布局与流量小算例

```python
loads = [400, 200, 120, 100, 80, 60, 40, 24]
before = [[0, 1], [2, 3], [4, 5], [6, 7]]
after = [[0, 7], [1, 6], [2, 5], [3, 4]]

def rank_loads(layout):
    return [sum(loads[e] for e in rank) for rank in layout]

assert sum(loads) == 1024
assert rank_loads(before) == [600, 220, 140, 64]
assert rank_loads(after) == [424, 240, 180, 180]
print("before", rank_loads(before))
print("after ", rank_loads(after))
print("max_load_ratio", 600 / 424)

tokens, hidden, top_k, item_bytes = 4096, 7168, 2, 2
dispatch = tokens * hidden * top_k * item_bytes
round_trip = dispatch * 2
cross_node = round_trip * 0.75
seconds = cross_node / (25 * 2**30)
assert dispatch == 112 * 2**20
assert abs(seconds * 1000 - 6.5625) < 1e-10
print("cross_node_MiB", cross_node / 2**20)
print("shared_link_lower_bound_ms", seconds * 1000)
```

`600/424≈1.415` 是最大 token 计数的改善比例。
它不是可直接报告的系统加速比。
若通信占主导，专家计数改善可能几乎不改变总时间。

## 9. 性能反例与验收表

| 现象 | 可能原因 | 下一步证据 |
|---|---|---|
| EPLB 后更慢 | 迁移占网络、破坏 locality | 迁移字节与跨节点比例 |
| GPU 平均利用率高但尾慢 | 单专家/单 rank straggler | 最大接收数、逐 rank timeline |
| EP 越大越慢 | 小 GEMM、A2A 固定成本 | tokens/expert、dispatch 时间 |
| 复制后显存不足 | 专家权重挤占 KV | 权重、KV、buffer 分项 |
| 开启 overlap 无收益 | 带宽争用、依赖未解开 | 同时间轴上的重叠区间 |

实验必须保持模型输出语义和请求分布一致。
不能通过丢弃超容量 token 伪造吞吐提升。
若模型确实采用 capacity/drop 机制，需报告 drop 比例和质量变化。

## 10. 六道追问与答案

### Q1：MoE 激活参数小，为何仍需要很多 GPU？

全部专家权重需要常驻或按受支持策略加载。
此外还有 dense 层、KV、dispatch buffer 和专家副本。
激活参数量主要描述单 token 计算，不描述完整部署容量。

### Q2：All-to-All 字节相同，为何延迟不同？

来源和目标的分布可能不同，瓶颈链路和最慢 rank 也不同。
小消息固定延迟、拓扑、NUMA、NIC 绑定、buffer 等待都会改变时间。
需要看通信矩阵，而不只是一个总字节数。

### Q3：训练 auxiliary loss 可以替代 EPLB 吗？

不可以。
训练改变长期语义分布，EPLB 改变部署位置。
线上输入漂移与局部突发仍需要运行时观测。

### Q4：给热点专家复制权重，会改变输出吗？

理想情况下不会，因为副本表示同一个 logical expert。
前提是权重、精度、模型版本和执行语义兼容。
物理执行顺序不同仍可能产生浮点误差，需以质量和数值门禁验证。

### Q5：为什么 dispatch handle 不能提前释放？

Combine 仍可能需要它恢复 token 顺序和来源。
异步 kernel 或通信也可能仍引用其 buffer。
必须等最后一个依赖事件完成，不能按 Python 调用返回时刻回收。

### Q6：没有多机设备怎样做有价值的项目？

可以实现通信矩阵、专家布局、mapping epoch 和取消状态机模拟。
保存不同负载分布下的预测与不变量检查。
将结果标为 CPU 模拟，不能把模型时间写成实际 RDMA 性能。
