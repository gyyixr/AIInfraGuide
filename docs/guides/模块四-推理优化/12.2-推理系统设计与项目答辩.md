## 项目要证明你能解释系统，而不只是调用 API

一个推理项目的价值来自正确性、资源模型、性能证据和失败处理。
仅仅包一层 HTTP API，难以证明理解 scheduler、KV 和 GPU。
反过来，没有大集群也能通过可运行模拟与单卡实验建立可信证据。
关键是明确哪些是数学、CPU 模型、单 GPU 实测和多机实测。

本节整理参考宝典 P0—P8、DESIGN 与十二周路线，并与本仓库扩展章节对应。
八个项目均按照约束→成本→机制→验收→回退描述。
它们是可执行的项目设计，没有把尚未完成的项目冒充已验证成果。

## 1. 所有项目共用的证据包

```text
problem.md       业务目标、假设、SLO
environment.json 硬件、版本、artifact、配置
reference        可信输出或数学基线
workload         trace/shape/seed/长度分布
raw_results      每请求或每轮原始样本
profiles         关键路径与热点证据
regression       正确性/质量/故障不变量
limitations.md   失败尝试、无收益域、未覆盖条件
```

文件名只是建议，内容比目录形式重要。
所有图表应能由原始样本重算。
收益必须绑定相同工作量与质量条件。
没有测量时，简历中删除 speedup 数字，描述实现和验证即可。

## 2. 项目一：容量与时间戳实验室

### 约束

不依赖 GPU，只用 Python 标准库。
输入模型结构、dtype、context、并发和分页参数。
同时输入逐请求发送、token 和结束时间戳。

### 成本模型

权重=$P\times bytes$，标准KV=$2Lh_{kv}dbT$。
分页容量按每序列 `ceil(tokens/page_size)`，加上runtime/graph余量。
时间戳计算TTFT、ITL、TPOT、E2E、throughput与goodput。

### 机制

将单位显式存为bytes和seconds，输出时再转GiB/ms。
单token请求的TPOT为缺失值，失败与拒绝单独统计。
参数支持KV分片与复制因子，避免无条件除以TP。

### 验收

手算128KiB/token与8K=1GiB案例，与代码一致。
构造raw TPS更高但goodput更低的反例。
用open/closed-loop小模型解释负载反馈。

### 回退与答辩

遇到MLA或混合recurrent模型，拒绝套用GQA公式，返回“需实际layout”。
答辩重点：哪些项目是下界，哪些需要实测，为什么均值不足以配置显存。
对应本仓库6.1、8.1与参考P0。

## 3. 项目二：Mini Serving Engine

### 约束

先单模型、单进程CPU离散事件模拟，再接一个小模型执行器。
控制范围在可以完整解释的教学代码，不复制整个框架。
首版不加入多模态、MoE和复杂分布式。

### 成本模型

每tick记录scheduled tokens、sequence slots、active/cache/retiring blocks。
Prefill与decode服务时间使用可替换函数，明确是否来自实测。
输出queue、TTFT、ITL、preemption和goodput。

### 机制

实现static baseline→continuous batching→chunk→paged KV→prefix/COW。
再加入cancel、timeout、有界stream buffer和租户配额。
分离策略选择与allocator原子分配。

### 验收

每步检查free+unique allocated=total，引用计数非负。
fork后写共享tail触发COW，OOM分配失败原子回滚。
中间chunk不输出，已提交token不会因抢占重新采样。
随机注入取消与迟到完成，验证无double free和KV污染。

### 回退与答辩

一项功能出错时可禁用prefix、overlap或spec，回到可比较reference。
答辩不要只说“支持连续批处理”，要画一个请求被抢占再恢复的状态。
对应11.1—11.3、7.3与参考P1。

## 4. 项目三：SGLang/vLLM 固定版本 A/B

### 约束

同GPU、artifact、tokenizer、prompt token IDs、EOS与采样配置。
分别记录框架commit、backend、并行、显存比例和默认值差异。
两边可能没有完全同构参数，应按行为约束对齐。

### 成本模型

保存每请求trace、GPU-hours、KV峰值、重算token与失败率。
比较goodput—p99 TTFT—p99 TPOT的非支配点。
不能只比较各自最漂亮的峰值TPS。

### 机制

覆盖short-short、long-short、long-long及真实联合分布。
组合冷/热prefix、open-loop burst与closed-loop并发。
扫描chunk/token budget与并发上限，保存实际dispatch日志。

### 验收

先通过输出/协议正确性，再比较相同目标下容量。
交错A/B和多轮重复，保留噪声区间。
至少展示一个“吞吐增但交互SLO坏”的配置。

### 回退与答辩

新版本回归时回到固定artifact/runtime组合。
结论应是“在此workload和约束下某配置合适”，不宣布通用框架排名。
对应8.1—8.3、11章与参考P2。

## 5. 项目四：单 GPU 算子优化

### 约束

按实际GPU架构选择RMSNorm/residual、RoPE或online softmax等算子。
RTX3090只验证支持的SM86路径，不把TMA/WGMMA等当本机能力。
从可信FP32/reference开始，不先追速度。

### 成本模型

计算FLOPs、逻辑与实际流量、tile复用和launch占比。
用Amdahl估计端到端收益上限。
例如热点仅占4%，内部2倍只有约2%整体收益。

### 机制

选择Triton、CUDA或CUTLASS/CuTe中适合当前算法和硬件的实现。
优化一次只改主要因素：coalescing、tile、fusion或pipeline。
先Nsys确定热点，再NCU看bytes、register、spill和stall。

### 验收

覆盖非整除、stride、最小shape、极值与dtype。
使用warm-up、CUDA events、同步与重复测量，保存wall/device两种边界。
至少保留一个“occupancy更高却更慢”或“融合导致spill”的失败尝试。

### 回退与答辩

不支持shape/hardware时走明确fallback。
答辩要说明地址如何映射到事务、为什么当前tile减少了瓶颈。
对应8.2、后续性能工程模块与参考P3。

## 6. 项目五：量化与投机的联合回归

### 约束

选择足够小、能完整跑评测的模型。
量化与投机先分别验证，再组合，避免一次改变多个未知量。
保存tokenizer、quant config、draft与target身份。

### 成本模型

量化记录编码、scale、repack、workspace与KV容量。
投机记录draft+verify+accept时间除以期望提交token。
再把额外KV、graph、质量与SLO纳入总成本。

### 机制

先做离散分布接受/残差采样验证，再测试真实引擎可用路径。
量化核对actual kernel与未量化层。
按batch、context、输出长度与接受长度扫描。

### 验收

模型质量分语言、任务、长context和structured output。
包含低接受率、高batch、短输出等退化区域。
验证拒绝后KV/grammar回滚，以及cancel during verify。

### 回退与答辩

保留BF16 target-only基线，可独立关闭量化或spec。
不把高接受率直接当作加速证据。
对应12.1第16—21题与参考P4/P5。

## 7. 项目六：PD/Wide EP 的容量与故障模拟

### 约束

没有集群先CPU模拟；有集群再替换成实测服务时间和链路数据。
使用相同GPU总预算比较方案。
明确框架与DeepEP版本，不能混用V1集成和V2.5 API。

### 成本模型

PD记录P/D需求、KV字节、带宽、预分配等待、双份驻留和idle。
EP记录route矩阵、每expert/rank负载、dispatch/GEMM/combine。
最慢rank与共享瓶颈链路决定关键路径，不能只看平均。

### 机制

模拟aggregated、chunked、PD与不同P:D配比。
MoE模拟训练分布、专家复制、EPLB映射与dispatch选择四层机制。
加入generation、重复ack、丢ack和mapping epoch。

### 验收

展示PD胜出和aggregated胜出区域。
展示专家重排改善rank负载却未必提升整体时间的反例。
取消时不得提前free，map切换前权重必须ready。

### 回退与答辩

实测不支持预测时保留误差并修正模型。
声明CPU模拟不能验证RDMA性能或真实GPU memory ordering。
对应6.2、7.1—7.3与参考P6。

## 8. 项目七：三租户生产平台与故障演练

### 约束

设置交互、离线batch、long reasoning三个租户。
分别定义TTFT/TPOT、优先级、上下文、质量与计费规则。
实现模型能力过滤，不静默切换不兼容模型。

### 成本模型

用token、concurrency、KV、GPU-seconds组合资源账。
估算冷启动期间backlog，按副本/节点故障域计算冗余。
将warm pool、取消后retiring资源和重试工作计入成本。

### 机制

Gateway认证配额→router/admission→pool→有界stream writer。
加入startup/readiness/liveness、渐进发布和graceful drain。
按detect→contain→recover→correctness→user语义编写runbook。

### 验收

注入burst、超长prompt、慢客户端、CPU阻塞、worker crash和KV timeout。
验证队列有界、低优先级不无限饥饿、usage只结算一次。
部分stream不透明重试，缺失ack不被重复ack伪装为完成。

### 回退与答辩

提供限流、分池、禁用特性和artifact/runtime回滚。
回答“控制面不可用时已有请求怎么办”，不能只画正常路径。
对应9.1—9.3与参考P7。

## 9. 项目八：一个窄而完整的上游改进

### 约束

选择能在现有设备复现的问题，如指标口径、错误消息、边界shape或取消状态测试。
固定issue对应版本，不顺手重构无关模块。
提交行为需遵循仓库流程；本教程不代表已提交PR。

### 成本模型

评估修复新增的CPU、内存、同步或复杂度。
即使是correctness修复，也应说明是否影响热路径。
性能修复则先证明热点占比与最小可复现条件。

### 机制

先创建失败复现，再定位root cause，再做最小变更。
验证相关边界，整理环境、日志和前后结果。
用源码contract解释为什么修复有效。

### 验收

回归能在旧版本稳定失败、新版本通过。
说明未覆盖硬件和配置。
Reviewer能独立运行复现，不需要依赖口头解释。

### 回退与答辩

变更可单独回滚，说明兼容与迁移。
答辩重点是怎样收敛问题与回应review，而不只是“PR merged”。
对应参考P8与PROJECT-001—010。

## 10. 三个综合设计题的答题骨架

### 场景 A：10 万用户多模型平台

先区分DAU、连接、峰值RPS与GPU活跃序列。
固定ISL/OSL、工具能力、质量和SLO。
先用aggregated+request DP建立基线，再依据trace选择TP/PP/分池。
配额、stream和故障语义贯穿全部组件。

### 场景 B：长上下文 coding agent

识别稳定仓库prefix、工具插入、append和branch。
Key绑定仓库snapshot与模型身份，共享页写入用COW。
比较恢复与重算，GPU/CPU/remote按价值分层。
用真实多轮、cache churn和cancel验证，不只测一次长prompt。

### 场景 C：成本目标与质量约束

定义每合格请求或token的总成本。
列出低风险调度优化与会影响质量的模型/量化候选。
逐项A/B，给收益上限、无收益区域与回滚。
无法达到目标时，给证据支持的可行范围。

## 11. 十二周学习路线

每周参考分配：原理30%、源码20%、项目35%、口述复盘15%。
比例可调整，但每周都要有可检查产物。
不要等全部理论读完才开始项目。

| 周 | 学习与阅读 | 验收产物 |
|---|---|---|
| 1 | 请求数据流、Decoder shapes | 端到端图、三组shape |
| 2 | 权重/KV、TTFT/ITL、负载 | 容量与trace计算器 |
| 3 | paging、prefix、COW | allocator守恒与fork |
| 4 | scheduler、chunk、cancel | 事件模拟与竞态用例 |
| 5 | online softmax、CP、spec | 数值reference与拒绝校正 |
| 6 | 量化、格式、实际kernel | 质量/容量/支持矩阵 |
| 7 | CUDA/Triton基础、地址与tile | 一个正确的热点kernel |
| 8 | Nsys→NCU、Amdahl | profile、A/B与失败尝试 |
| 9 | TP/PP/EP/PD、网络 | rank图、流量与故障模型 |
| 10 | gateway、配额、探针、故障 | 三租户runbook与演练 |
| 11 | 系统设计、项目收口 | 可重现README与答辩材料 |
| 12 | 全真模拟、查漏 | 岗位能力—项目证据矩阵 |

### 每周四个固定动作

1. 用30秒给定义。
2. 用3分钟推公式、数据流或状态机。
3. 给一个性能/正确性反例。
4. 运行或复核一个能证伪结论的实验。

第12周不再广泛开新项目。
从参考235题随机抽题，记录条件遗漏、定义错误与无证据结论。
优先修复阻碍现有项目答辩的薄弱点。

## 12. 项目证据的简单评分模型

```python
dimensions = {
    "requirements": 3,
    "capacity": 3,
    "correctness": 4,
    "performance_evidence": 2,
    "failure_semantics": 3,
    "reproducibility": 4,
}
assert all(0 <= x <= 4 for x in dimensions.values())
average = sum(dimensions.values()) / len(dimensions)
weakest = min(dimensions, key=dimensions.get)
assert weakest == "performance_evidence"
print("average", round(average, 3), "next_focus", weakest)

hours = 10
allocation = {
    "theory": hours*0.30,
    "source": hours*0.20,
    "project": hours*0.35,
    "review": hours*0.15,
}
assert sum(allocation.values()) == hours
print(allocation)
```

评分是学习工具，不是招聘标准。
平均分高也不能抵消关键correctness缺口。
若存在无边界性能承诺、UAF或错误概率推导，应先修复再继续包装项目。

## 13. 六道答辩追问与答案

### Q1：你做的优化究竟属于哪一层？

说明改动发生在模型算法、调度、缓存、通信、kernel或测量口径。
然后给它影响其他层的路径。
例如chunk改调度，但影响GEMM shape、KV驻留与ITL。

### Q2：为什么你的基线是公平的？

给出相同artifact、输入token、质量、硬件预算与时间边界。
解释无法完全对齐的参数，并给敏感性分析。
不能仅说“都用默认参数”。

### Q3：如果去掉你的改动，哪条证据会变化？

用ablation回答具体机制，例如减少同步、降低实际bytes或缩短queue。
如果只能看到最终TPS变化，归因仍不充分。
应增加中间观测验证因果链。

### Q4：你最大的失败尝试是什么？

先讲预测，再讲测量如何反驳，最后讲保留的结论或工具。
例如fusion省launch但spill增加，结果端到端更慢。
不要把失败改写成没有原始数据的成功故事。

### Q5：没有集群是否意味着项目没价值？

不意味着。
明确CPU模拟与单卡证据边界，可以证明资源建模、协议和验证能力。
不能把尚未运行的多机性能写成已完成成果。

### Q6：怎样把项目写成简历一条？

使用“问题—自己的机制—验证证据—适用边界”。
有真实数据才写收益，并带核心条件。
示例：实现教学调度器，含分页/COW/chunk/cancel，用随机事件验证资源守恒；性能数字在真实测量后再补。
