## 用户取消请求，不等于 GPU 停止访问内存

一个请求可能同时存在于 HTTP stream、scheduler、GPU kernel 和网络传输队列中。
关闭连接只结束其中一条控制路径。
源端 NIC 可能仍在读 KV，目标端 DMA 也可能仍在写预分配页面。
因此取消必须被建模为一个协议，而不是一个布尔变量。

最危险的错误不是“取消后多算了一点”。
它是旧请求的异步操作写进新请求复用的页面，导致跨请求 KV 污染。
这种错误可能不触发越界，也可能产生看似正常但错误的输出。

## 1. 四种完成事件

| 事件 | 表示什么 | 不能推导什么 |
|---|---|---|
| HTTP close | 客户端不再接收 | GPU/DMA 已结束 |
| generation done | 不再生成 token | 异步保存已结束 |
| control ack | 对端收到控制消息 | 数据面已 drain |
| transfer completion | 特定传输完成 | 所有 writer 都结束 |

需要明确 completion 的作用域：单层、单 rank、单请求还是整个 transport。
“收到了一个 ack”不等于“所有 rank 都不能再写”。
多 rank 请求尤其需要完整的参与者集合。

## 2. 一个具体的 UAF 时间线

设目标页物理地址为 `0xA000`，当前属于请求 A。

```text
t0 D 为 A 分配 page 7，地址 0xA000
t1 P 获得远端地址并发出异步 write
t2 用户取消 A
t3 D 立即 free page 7
t4 D 把 page 7 分给请求 B
t5 旧 P write 到达 0xA000
t6 B attention 读取被覆盖的 KV
```

page ID 没有越界，地址也合法。
问题是这个合法地址已经属于另一个 owner。
内存 sanitizer 未必能把这种逻辑越权识别为普通越界。
必须通过 ownership 和 completion 来阻止地址过早复用。

## 3. 页面状态机

推荐的抽象状态是：

```text
FREE
  → RESERVED
  → FILLING
  → COMMITTED
  → RETIRING
  → FREE
```

各状态含义：

| 状态 | 是否可被 attention 读 | 是否可分配给别人 |
|---|---|---|
| FREE | 否 | 是 |
| RESERVED | 否 | 否 |
| FILLING | 否，除非逐层协议已证明对应层 ready | 否 |
| COMMITTED | 是 | 否 |
| RETIRING | 不再安排新读者 | 否 |

取消 `FILLING` 时应进入 `RETIRING`。
不能直接跳到 `FREE`。
已有读者结束前，`COMMITTED` 页面同样不能直接释放。

## 4. 请求状态与页面状态是两套状态机

请求可以已处于 `CANCELLED`，页面却仍是 `RETIRING`。
客户端结果完成和资源回收完成不能共用一个 `done` 标志。

```text
request outcome: CANCELLED
stream outcome:  CLOSED
transport:       DRAINING
pages:           RETIRING
usage record:    FINALIZED
```

这样的中间状态是正常的。
若强制所有组件同一时刻变成 done，通常会掩盖异步生命周期。
调度器可以停止把请求计入可运行集合，但保留资源债务记录。

## 5. Generation/epoch 能解决什么

控制消息应包含：

```text
request_id
request_generation
worker_epoch
transfer_id
source_rank
destination_rank
layout_identity
```

当请求 ID 或 page ID 复用时，generation 可以拒绝迟到的旧完成消息。
例如 A 的 generation=3 已退出，重试 generation=4。
旧 `ready(gen=3)` 不能把 gen=4 的请求标记为可 decode。

但是 generation 不会自动拦截裸 RDMA write。
如果旧 writer 已持有地址和有效远端访问权限，数据面可能不检查你的 JSON epoch。
因此还需要 drain、撤销可写能力、销毁相应 transport，或隔离旧内存区域。

这是控制面 fencing 与数据面 fencing 的区别。
只加一个 request UUID 不能证明 UAF 已消失。

## 6. 正确取消的顺序

一个保守协议可以写成：

1. 原子记录 cancel intent。
2. 从正常调度集合摘除请求。
3. 冻结该请求的 source/target 页面 owner。
4. 向所有可能 writer 发出 stop/drain。
5. 收集与本次 generation 匹配的完成证明。
6. 等待本地 GPU 最后读写事件。
7. 清理 metadata、room 和引用。
8. 将页面归还 allocator。
9. 对重复 cancel/ack 保持幂等。

发出 stop 不等于 stop 已执行。
收到远端 control ack 也必须确认其语义包含已排队数据操作的 drain。
若只确认“收到了取消请求”，仍然不能复用目标页。

## 7. 多 rank 的 ack 集合

若请求由 4 个 P rank 向 D 写入，需要知道实际可能写入的参与者集合。
例如：

```text
required = {P0, P1, P2, P3}
received = {P0, P1, P2}
```

此时不能因为 75% 完成就回收全部页面。
P3 可能正是卡住或网络最慢的 writer。
如果每 rank 使用独立且可分别归还的页面，也必须逐页证明对应写者全部结束。

重复 `P1 ack` 不应让计数从 3 变成 4。
使用 rank/transfer ID 集合，或等价的去重状态。
未知 rank、旧 epoch、旧 generation 的 ack 必须拒绝。

## 8. Timeout 是活性策略，不是安全证明

无限等待会泄漏容量，超时直接 free 又可能发生迟到写入。
安全恢复需要把“让系统继续”与“证明旧写者失效”同时处理。

可考虑的策略包括：

- 隔离该传输对应的地址区域，暂不复用。
- 销毁并确认停止相关 transport。
- 撤销远端写权限，并确认设备侧完成。
- 整体重启受影响 worker/pool，由更强故障边界阻断旧访问。
- 在有可信最坏时间边界的系统中证明等待条件。

这些策略的可用性取决于 backend。
不能写成通用的 `sleep(5); free()`。
时间过去了，不等于旧 NIC 或远端进程无法继续写。

### 8.1 固定源码的真实边界

SGLang 固定 commit 的 decode 路径有 deferred release。
decode 主动 abort 后，会等待 drain ack 或超时，再释放页面。
源码还记录超时未收齐 ack 时继续释放的 warning。

这证明该版本实现了延迟释放机制。
它不证明任意故障模型下都能排除迟到 DMA。
评估时应进一步核对具体 transport 的停止、超时和地址失效契约。
不能把“有 timeout 分支”写成严格 UAF 安全证明。

## 9. 可运行的保守生命周期模型

下面代码只模拟 ack 与页面复用约束。
它不模拟真实 RDMA，也不声称验证硬件 memory ordering。

```python
from dataclasses import dataclass, field

@dataclass
class Page:
    generation: int = 0
    state: str = "FREE"
    required: set = field(default_factory=set)
    acked: set = field(default_factory=set)
    local_complete: bool = False
    frees: int = 0

    def reserve(self, writers):
        assert self.state == "FREE"
        self.generation += 1
        self.state = "FILLING"
        self.required = set(writers)
        self.acked = set()
        self.local_complete = False
        return self.generation

    def cancel(self, generation):
        if generation != self.generation:
            return False
        if self.state in {"FILLING", "COMMITTED"}:
            self.state = "RETIRING"
        return True

    def ack(self, generation, writer):
        if generation != self.generation:
            return False
        if writer not in self.required:
            return False
        self.acked.add(writer)
        return True

    def try_free(self):
        safe = (
            self.state == "RETIRING"
            and self.acked == self.required
            and self.local_complete
        )
        if safe:
            self.state = "FREE"
            self.frees += 1
        return safe

page = Page()
g1 = page.reserve({0, 1})
page.cancel(g1)
page.ack(g1, 0)
page.ack(g1, 0)  # 重复 ack 不增加覆盖范围。
page.local_complete = True
assert not page.try_free()
page.ack(g1, 1)
assert page.try_free()
assert not page.try_free()  # 幂等，不 double free。
assert page.frees == 1

g2 = page.reserve({0, 1})
assert g2 == g1 + 1
assert not page.ack(g1, 1)  # 旧 generation 的完成被拒绝。
assert not page.cancel(g1)
assert page.state == "FILLING"
print("drain, dedup, local completion and generation checks passed")
```

该模型刻意不在 timeout 后自动 free。
真实系统可以增加 escalation 状态，但必须给出新的安全依据。

## 10. 容量债务数例

假设每个取消请求持有 1 GiB 目标 KV。
每秒有 4 个请求在传输中取消，平均 drain 需要 0.5 s。
稳定条件下，平均 retiring 请求数为：

$$
L_{retiring}=\lambda_{cancel}W_{drain}=4\times0.5=2.
$$

平均被延迟回收的目标 KV 为 2 GiB。
如果故障让 drain 增到 10 s，平均就变为 40 GiB。
源端还可能同时持有相应 KV，集群占用更高。

这解释了为什么取消率上升会造成 KV pressure，即使 running 请求数下降。
应单独监控 retiring bytes、最老未完成 age、missing ack 和隔离区域容量。
只监控 active sequence 会漏掉这笔资源债务。

## 11. 重试必须区分生成与传输

重复传输同一不可变 KV，可以设计成幂等操作。
但必须验证目标 generation、范围、layout 和提交状态。
重复生成则可能产生不同采样结果，尤其在已经输出 token 后。

```text
transport retry:
  same KV identity + same request generation
  + validated target reservation
  + duplicate-safe commit

generation retry:
  new execution attempt
  + explicit stream/billing semantics
  + possibly different RNG outcome
```

请求 retry 应使用新的 attempt ID。
逻辑 request ID 可用于计费去重和审计关联。
不要让新 attempt 继承旧 attempt 尚未 drain 的可写地址。

## 12. 故障注入矩阵

| 注入点 | 必须验证 |
|---|---|
| P 尚未执行 | 取消不泄漏 reservation |
| P kernel 中 | 最后 GPU 读写后才回收 |
| 一半 KV 到达 | D 不读取半成品 |
| 单 rank ack 丢失 | 不误判全组完成 |
| ack 重复/乱序 | 不 double free、不越代提交 |
| D 重启 | 旧 worker epoch 无法提交 |
| stream 断开 | usage 和资源清理各完成一次 |
| 快速复用 page ID | 旧数据不能污染新请求 |

仅在正常完成路径测 1000 次，并不能覆盖这些状态交错。
应在每个异步边界注入取消、超时和重启。
随机化事件顺序后仍需检查页面总量守恒与 ownership。

## 13. 六道追问与答案

### Q1：为什么 refcount=0 仍可能发生 UAF？

refcount 可能只跟踪逻辑请求引用。
异步 kernel、DMA 或 connector save 仍持有物理地址。
必须把异步读写纳入引用或 completion fence。

### Q2：加 generation 是否足以保护 RDMA？

不一定。
generation 可以拒绝旧控制消息，但旧远端 write 可能不经过该检查。
数据面还需 drain 或可靠地址权限隔离。

### Q3：为什么一个完成 ack 不够？

请求可能有多个 rank、多个层或多段传输。
必须覆盖所有实际 writer，并去重与校验 epoch。
ack 的语义也必须是数据操作完成，而非仅收到请求。

### Q4：超时后永不回收是否更安全？

它避免直接复用，但会耗尽容量，仍不是完整可用系统。
应升级到可证明停止旧访问的隔离或重启方案。
安全与活性需要分别设计。

### Q5：HTTP 流已经关闭，为什么还保留请求对象？

生命周期控制器仍需追踪传输、页面和 usage 的完成状态。
可以缩减用户数据，但不能丢掉清理所需 ownership 信息。

### Q6：怎样发现没有崩溃的 KV 污染？

用固定输入对照、generation 标记、页填充哨兵和故障注入检查。
在取消后快速复用同一 page ID，验证新请求结果与独立运行一致。
日志必须能关联 request、attempt、page 和 transfer。
