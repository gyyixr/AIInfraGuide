Activation checkpointing 的核心并不是“少做一次 forward”，而是先不长期保存某些反向所需的中间值，等反向真正需要时重新算出来。它把存储时间换成额外计算，收益取决于张量的大小、生命周期和重算位置。

本节 API 以 [PyTorch 2.9 checkpoint 文档](https://docs.pytorch.org/docs/2.9/checkpoint.html) 为参照。提供的 CPU 一致性实验验证计算语义；显存与耗时表均为标注假设的教学算例，不代表某个 GPU 的实测加速。

## 1. 为什么反向要留住前向激活

考虑两层线性网络：

$$
H=\phi(XW_1),\qquad Y=HW_2.
$$

反向已知 $dY$ 后：

$$
dW_2=H^T dY,\qquad dH=dY W_2^T.
$$

所以需要 $H$ 或足以重建 $H$ 的信息。继续计算 $dW_1$，还需要 $X$ 和激活函数的导数所需信息。

自动微分会让反向需要的张量活得更久。Python 局部变量离开作用域，不表示底层 tensor storage 已无人引用；autograd 的 saved tensors 可能仍然持有它。

### 1.1 先按生命周期分组

| 对象 | 通常何时创建 | 何时可以释放 |
|---|---|---|
| 参数与 optimizer states | 初始化或首次 step | 训练结束、卸载或重分片 |
| 梯度 buffer | backward 或预分配 | 清零/置空、更新后按实现释放 |
| 保存的激活 | forward | 对应 backward 完成后 |
| 当前 kernel workspace | 算子启动 | 算子与依赖完成后可复用 |
| 参数预取/通信 buffer | 异步通信前 | 通信与所有消费者完成后 |
| checkpoint 边界输入 | forward | 该段重算与 backward 完成后 |

这张表的重点是“最后一个消费者”。仅仅让 Python 引用计数下降，不足以解释 CUDA stream 上何时能安全复用内存。

## 2. 峰值是时间轴上的重叠

设时刻 $t$ 的 live tensor 显存为：

$$
M(t)=M_{state}(t)+M_{saved}(t)+M_{work}(t)+M_{comm}(t).
$$

需要关心的是：

$$
M_{peak}=\max_t M(t),
$$

而不是把四类内存各自的最大值无条件相加。它们的高峰不一定发生在同一时刻。

### 2.1 一个阶段账本

假设持久状态为 12 GiB，其他占用如下：

| 时刻 | 保存激活 | 工作区 | 通信/预取 | 总量 |
|---|---:|---:|---:|---:|
| forward 中段 | 4 GiB | 1 GiB | 2 GiB | 19 GiB |
| forward 末尾 | 8 GiB | 1 GiB | 0 GiB | 21 GiB |
| backward 初段 | 7 GiB | 2 GiB | 3 GiB | 24 GiB |
| optimizer step | 0 GiB | 4 GiB | 0 GiB | 16 GiB |

峰值为 24 GiB。若 checkpoint 把 saved activation 减半，但重算与预取重叠后该时刻工作区变成 3 GiB，则新峰值估算是：

$$
12+3.5+3+3=21.5\text{ GiB}.
$$

激活减少 50%，总峰值只减少约 10.4%。这不意味着 checkpoint 失效，而是其他项仍占主要空间。

## 3. 从链式网络推导分段 checkpoint

假设网络有 $L$ 层，每层保存中间量大小近似为 $a$，各层成本一致，暂不计持久状态。

### 3.1 不重算

若所有层的中间量都留到反向，保存量量级为：

$$
M_{saved}\sim La.
$$

### 3.2 每 $k$ 层组成一段

只长期保存段边界；反向处理某段时，重算该段内部的中间量。简化峰值近似：

$$
M_{act}(k)\sim\left(\frac{L}{k}+k\right)a.
$$

第一项是所有段边界，第二项是当前重算段内部的临时保存量。忽略首尾偏差、不同层大小和调度细节，可求：

$$
\frac{d}{dk}\left(\frac Lk+k\right)=-\frac{L}{k^2}+1=0,
\qquad k\approx\sqrt L.
$$

因此最优量级约为 $2\sqrt L a$。这是**这个分段模型**中的平方根规律，不是所有 checkpoint 配置的通用显存公式。

### 3.3 手算 64 层

取 $L=64,a=64$ MiB，未重算保存量约为 4096 MiB。

| 段长 $k$ | 边界与临时量近似 | 显存 |
|---:|---:|---:|
| 1 | $(64+1)a$ | 4160 MiB |
| 4 | $(16+4)a$ | 1280 MiB |
| 8 | $(8+8)a$ | 1024 MiB |
| 16 | $(4+16)a$ | 1280 MiB |
| 64 | $(1+64)a$ | 4160 MiB |

表里的 $k=1$ 并不说明真实“逐 block checkpoint”完全没用：真实 Transformer block 内有多份大激活，而边界输入可能小得多。本表假设每层内部保存量和边界都是 $a$，所以只能说明分段权衡。

实际模型应将边界大小 $a_b$ 与段内保存大小 $a_i$ 分开，近似写成 $La_b/k+ka_i$，最优段长随二者比例变化。

## 4. 完整重算到底多了多少计算

设原始前向 FLOPs 为 $F$、反向为 $B$，重算增加 $F_r$：

$$
\text{计算开销比例}=\frac{F_r}{F+B}.
$$

若粗略取 $B=2F$，且重算几乎完整一次前向 $F_r=F$，则原来 $3F$，现在 $4F$，总计算增加约 33%。

它的含义是**增加约一个完整前向**，不是“前向只增加 33%”。

实际 wall time 不必也增加 33%：

- 非重算时可能被显存带宽或通信等待限制。
- 重算能允许更大 microbatch，改善 GEMM 效率。
- selective checkpoint 只重算部分算子，$F_r<F$。
- 非重入 checkpoint 可以提前停止重算。
- FSDP 参数已释放时，重算可能引入新的参数取回或改变预取重叠。

必须比较同一训练目标、全局 batch、序列分布和硬件预算下的 tokens/s，不能只比较一次局部 forward。

## 5. PyTorch 的两个 checkpoint 路径

新代码应显式写 `use_reentrant=False`，避免依赖隐含默认值。两种机制不能只按“是否省显存”区分：

| 方面 | `use_reentrant=False` | `use_reentrant=True` |
|---|---|---|
| 首次前向 | 记录 autograd 图 | checkpoint 区域前向在 no-grad 下执行 |
| 重算范围 | 可在所需中间值齐全后提前停止 | 重算整个函数 |
| 输入要求 | 不要求输入本身必须 requires-grad | 至少一个输入、输出需满足梯度条件 |
| 复杂结构/调用方式 | 支持范围更广 | 对嵌套结构、detached tensor 等有限制 |

这里概括接口差异；具体限制以文末固定版本文档为准，不把未来版本新增能力倒推到旧环境。

### 5.1 函数需要可以重放

以下写法的数学函数依赖可变外部状态，不适合直接重算：

```python
# 错误示意：counter 在前向和重算时不同，改变实际计算。
def stateful_block(x):
    global counter
    counter += 1
    return x * counter
```

还应注意更新缓存、向列表追加张量、原地修改共享输入，以及 BatchNorm running statistics 等有副作用的操作。重算可能再次触发副作用，导致结果与原训练不同。

## 6. Dropout 与随机状态

Dropout 的前向 mask 是计算的一部分。若首次前向使用 mask A，反向重算使用 mask B，求出的梯度可能不对应原来的函数。

默认 checkpoint 会处理相应 RNG 状态，但有设备范围与设备迁移边界。不要在 checkpoint 函数里临时把张量移到一个之前不可见的新设备，再假定所有 RNG 都被正确保存。

`preserve_rng_state=False` 允许省略相关保存开销，但如果函数含随机操作，通常就不再与未 checkpoint 路径严格等价。除非明确接受并验证这个变化，否则不能仅为快一点就关掉。

### 6.1 CPU 输出与梯度一致性实验

下面是完整小实验，只依赖 PyTorch，CPU 即可执行：

```python
import copy
import torch
from torch import nn
from torch.utils.checkpoint import checkpoint

torch.manual_seed(11)
base = nn.ModuleList([
    nn.Sequential(nn.Linear(8, 8), nn.GELU(), nn.Dropout(0.25)),
    nn.Sequential(nn.Linear(8, 8), nn.GELU(), nn.Dropout(0.25)),
]).double()
x0 = torch.randn(3, 8, dtype=torch.float64)

def run(model, recompute):
    model.zero_grad(set_to_none=True)
    x = x0.clone().requires_grad_(True)
    torch.manual_seed(23)
    y = x
    for block in model:
        y = (checkpoint(block, y, use_reentrant=False,
                        preserve_rng_state=True) if recompute else block(y))
    loss = y.square().mean()
    loss.backward()
    gradients = [p.grad.detach().clone() for p in model.parameters()]
    return y.detach(), x.grad.detach(), gradients, torch.get_rng_state()

plain = run(copy.deepcopy(base), False)
saved = run(copy.deepcopy(base), True)
torch.testing.assert_close(plain[0], saved[0], rtol=1e-10, atol=1e-10)
torch.testing.assert_close(plain[1], saved[1], rtol=1e-10, atol=1e-10)
for a, b in zip(plain[2], saved[2]):
    torch.testing.assert_close(a, b, rtol=1e-10, atol=1e-10)
assert torch.equal(plain[3], saved[3])
print("checkpoint output, gradients and RNG state match")
```

这里验证前向、输入梯度、参数梯度和 RNG 进度。它没有测 CUDA 显存，也没有模拟分布式参数取回；不要把通过的断言当成多卡性能证据。

## 7. Selective checkpoint：按保存收益与重算成本选择

对某个候选张量 $i$，可以先估计一个粗略比值：

$$
\rho_i=\frac{\text{可减少的峰值字节}}{\text{新增重算时间}}.
$$

这个比值不是独立可加的最终优化目标，因为张量生命周期有重叠，但能帮助选初始候选。

| 候选 | 可能的考虑 |
|---|---|
| 大激活、便宜 elementwise | 重算可能划算 |
| 大 GEMM 输出 | 保存可避免昂贵 GEMM，但是否值得取决于其大小 |
| fused attention 内部中间值 | kernel 可能已采用自己的重计算，不能重复按朴素图估算 |
| 相同 storage 的多个 view | 不是多个独立分配，简单 numel 求和会重复计账 |

Selective API 可以表达优先保存或重算哪些算子结果；策略应按实际算子图检查。一个“保存每个 op 输出”的规则甚至可能比自动微分原本需要保存的内容更多。

## 8. 梯度累积与重计算怎样配合

设大 batch 有 32 条等权样本，改成 8 个 microbatch，每个 4 条：

- 同时保留的激活按 microbatch 大小缩小。
- 梯度需要跨 8 次 backward 累积，通常不会缩小为原来的八分之一。
- optimizer 每 8 个微批才 step 一次。
- 每次 backward 中，被 checkpoint 的部分各自重算。

DDP 中使用 `no_sync()` 时，前向也应处于对应上下文内。最后一个微批触发同步，之后才能执行依赖全局梯度的裁剪和更新。

对于不等长样本，若目标是全局 token mean，不能把每个微批的局部 token mean 再简单平均。这个归约问题与是否 checkpoint 独立，必须先把数学目标固定。

## 9. 怎样正确测显存收益

GPU 上的测量顺序可以是：

```python
# 诊断片段；model、optimizer、batch 由具体实验准备。
torch.cuda.synchronize()
torch.cuda.reset_peak_memory_stats()
loss = training_forward(batch)
loss.backward()
optimizer.step()
torch.cuda.synchronize()
print(torch.cuda.max_memory_allocated())
print(torch.cuda.max_memory_reserved())
```

应先做独立 warmup，再在一致的起始状态下测量。optimizer 状态可能在第一次 step 才创建，CUDA Graph、编译与内核缓存也会改变首次运行，因此要分别记录初始化峰值和稳定迭代峰值。

`max_memory_allocated` 描述 PyTorch allocator 管理的 live 分配峰值；`reserved` 还包含缓存池。进程显存还可能包含 NCCL、其他库和图相关分配。

比较两个方案时应释放旧模型与优化器，或者使用独立进程。不要在同一进程中保留两套模型，再把第二次测量的峰值归因于 checkpoint。

## 10. OOM 与性能倒退的诊断表

| 现象 | 优先假设 | 最小检查 |
|---|---|---|
| forward 更省，backward 仍 OOM | 重算工作区、梯度或预取重叠 | 按阶段查看 peak/trace |
| checkpoint 后梯度不同 | RNG、可变全局状态、in-place | 固定输入做输出/grad 对照 |
| 已删除 tensor 仍未释放 | autograd/list 间接引用或异步使用 | 检查生命周期与保存容器 |
| 更省显存却更慢很多 | 大 GEMM 重算、参数通信重复 | 对比算子与collective次数 |
| 减 microbatch 后吞吐降 | GEMM 过小、调度/同步频率 | 在相同global batch下扫描microbatch |
| reserved 很大、allocated 不大 | allocator 缓存或碎片 | 不先把所有 reserved 都称作泄漏 |

## 11. 自测与参考答案

**1. 逐 block checkpoint 为什么不自动是平方根显存？** 每个 block 输入仍长期保存；平方根推导要求把连续多层组成适当长度的段，并包含段内临时保存项。

**2. $F=10,B=20,F_r=10$ 时重算开销是多少？** 原总量 30，新总量 40，总计算增加 $1/3$；前向相关工作从 10 增加到 20。

**3. 梯度累积能把 Adam states 降为 $1/K$ 吗？** 通常不能。它改变同时处理的样本数，Adam 状态仍对应全部可训练参数，除非另有分片/卸载机制。

**4. 两个分段方案各节省 2 GiB，组合一定节省 4 GiB 峰值吗？** 不一定。原张量的高峰和重算临时量可能不在同一时刻，必须回到时间线。

**5. 为什么输出一致还要检查梯度？** RNG、detach 或错误重算可能保留前向数值却改变反向路径；训练正确性至少需要参数梯度对照。
