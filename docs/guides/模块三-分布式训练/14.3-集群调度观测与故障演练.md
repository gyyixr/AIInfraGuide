## 1. 训练作业需要的不只是N张GPU

同样64张GPU，可能集中在一个高速互联域，也可能分散在多个机架。

数量相同不代表TP、EP、DP通信路径相同。

节点还需要CPU、主机内存、本地存储、网络和镜像依赖。

训练checkpoint、数据cache与恢复预留资源也会影响放置。

因此调度请求应表达完整资源与拓扑要求。

把这些要求留到作业启动后才检查，会造成昂贵的失败重试。

## 2. 逻辑拓扑与物理拓扑是两张图

逻辑图包含TP、PP、DP、CP和expert groups。

物理图包含GPU、NVLink/NVSwitch、PCIe、NUMA、NIC、交换机和存储。

需要建立显式映射：

```text
logical rank
  → host
  → local process
  → GPU UUID
  → NUMA与PCIe root
  → NIC与rail
  → rack与failure domain
```

local rank在重启后可能改变，因此不能只用local rank追踪坏设备。

GPU UUID与节点身份更适合跨次运行关联。

### 2.1 64卡教学布局

假设8台节点，每台8卡，节点内互联快于节点间。

选择`TP=8, PP=4, DP=2`。

一种自然布局是每个TP组放在一台节点内，4个节点组成一条PP链，两条链作为DP副本。

这种布局可以减少逐层TP通信跨机。

但DP组会连接对应stage的两个节点，PP也跨节点传activation。

实际是否最优仍取决于模型、batch、CP/EP和网络。

## 3. 拓扑选择有两个互相拉扯的目标

紧凑放置可以缩短通信路径。

分散故障域可以减少相关故障同时影响所有副本或checkpoint。

不能只追求其中之一。

例如两个checkpoint副本都放在同一机架，单盘故障容忍提高了，机架断电容忍仍没有提高。

训练进程是否需要跨故障域分布，还应考虑通信代价和恢复策略。

高速本地恢复与跨故障域持久备份通常承担不同职责。

## 4. 成组资源分配与“Gang Scheduling”术语

同步训练希望需要协作的ranks在可用资源满足后共同启动。

否则少量rank先占资源并等待其他rank，可能形成浪费或死锁式排队。

平台通常需要成组准入、超时释放和一致的启动协议。

但不同调度器对“gang scheduling”的用词不同。

本轮核对的Slurm官方Gang Scheduling页面主要描述多个作业共享资源并交替suspend/resume的时间片机制。

它不能直接等同于机器学习平台常说的“整组Pod同时准入”。

[Slurm官方说明](https://slurm.schedmd.com/gang_scheduling.html)应按其具体语义阅读，不能凭相同名称复制配置。

### 4.1 对训练真正要验收的能力

| 能力 | 需要验证的问题 |
|---|---|
| 成组准入 | 是否要等齐必要资源再启动 |
| 拓扑约束 | 是否真正满足通信域要求 |
| 启动失败释放 | 部分rank失败后资源是否回收 |
| 抢占通知 | 是否留出安全保存窗口 |
| 重启身份 | 新旧job/rank/GPU映射可否关联 |
| Reserve容量 | 故障时是否能快速替换 |

选择Slurm、Kubernetes或内部调度器后，均需在实际版本与插件组合下验证这些行为。

本文不提供脱离集群配置的通用生产部署命令。

## 5. 节点健康是生命周期，不是一次开机测试

```mermaid
flowchart LR
  A[准入检查] --> B[Burn in]
  B --> C[可调度]
  C --> D[异常候选]
  D --> E[隔离诊断]
  E --> F[修复与再认证]
  F --> C
```

准入包括驱动、固件、GPU、内存、网络和存储配置。

burn-in应覆盖目标工作负载的主要路径。

异常后不应只重启作业再把同一设备马上重新分配。

quarantine需要与调度器资源池联动。

修复后再认证也要留下版本与诊断结果。

### 5.1 隔离粒度

单GPU、整节点、NIC、机架可能是不同故障粒度。

如果问题来自节点级PCIe或电源，只隔离一张卡可能不够。

如果只是一个局部设备问题，整机长期隔离又可能浪费容量。

粒度应由证据和平台能力决定。

## 6. 四层可观测性

| 层次 | 指标例子 | 关联对象 |
|---|---|---|
| 模型与数值 | loss、grad norm、logit、router分布 | source、layer、step |
| 运行时 | forward/backward、optimizer、data wait | rank、stage、microbatch |
| 通信 | collective类型、字节、开始结束 | group、peer、op序号 |
| 平台 | 时钟、温度、ECC、NIC、存储延迟 | GPU UUID、host、rack |

任何一层单独存在都不够。

GPU遥测能看到降频，但不知道它发生在哪个Transformer layer。

训练日志知道loss spike，但不知道同一时间是否有设备错误或数据读失败。

需要统一时间、身份和运行版本。

## 7. 标签设计比多采几个指标更重要

建议稳定低基数标签：

```text
job_id
run_attempt
code_commit
model_config_hash
host
GPU_UUID
parallel_role
stage
metric_phase
```

sample ID、tensor key、完整error traceback等高基数信息更适合日志或trace。

把每个sample ID都做Prometheus label，会制造巨大时序数量。

关键做法是用trace ID或事件ID连接metrics与详细日志。

### 7.1 跨rank时间对齐

wall clock用于跨主机关联，应维护时钟同步并记录误差范围。

进程内阶段耗时优先使用单调时钟。

GPU事件时间与CPU wall clock是不同时间域，profiler应提供映射或清晰边界。

不能直接把不同主机未经校准的日志时间差当作通信延迟。

## 8. DCGM Exporter能做什么

本轮核对的官方文档说明DCGM Exporter把选定GPU遥测字段暴露为Prometheus格式。

它需要与设备、驱动及DCGM版本组合兼容。

Exporter与DCGM自身也有独立版本号，应保存经过测试的配对信息。

基础exporter不会自动理解你的sample ID、PP stage或optimizer step。

这些语义应由训练程序与调度元数据补充。

[官方安装与兼容性入口](https://docs.nvidia.com/datacenter/dcgm/latest/installation/install-dcgm-exporter.html)是动态文档；实际部署应固定镜像或包版本。

## 9. 仪表盘应该回答因果问题

第一屏不必堆满所有GPU利用率曲线。

它应该回答：

1. 当前有效token/s是否下降？
2. 下降对应哪个阶段？
3. 哪些同角色rank异常？
4. 是否与数据、checkpoint或平台事件同时发生？
5. 当前状态是否仍在推进，还是进入恢复？

### 9.1 推荐的时间线组合

```text
全局step与有效token/s
最慢rank及阶段
data queue与H2D wait
grad RS与param AG暴露时间
checkpoint staging/write/finalize
GPU clocks、NIC与存储事件
restart/quarantine/attempt变化
```

观察时保留P50、P95、P99和最大值。

平均值适合总量，尾部适合同步系统瓶颈。

## 10. RPO与RTO先定义再测量

RPO描述故障时允许损失多少已做但未持久提交的工作。

可以用时间、optimizer updates或有效token表达。

RTO描述从故障发生到恢复约定服务水平所需时间。

对于训练，RTO终点最好是恢复有效训练并通过canary，而不只是进程启动。

### 10.1 RPO手算

假设每300秒选取一次快照，异步写入与发布需要60秒。

若故障发生在最新快照尚未发布时，可恢复版本可能仍是前一份。

在理想固定周期下，最坏的durable状态年龄接近：

$$
300+60=360秒.
$$

因此“每5分钟调用save”不自动等于“最多丢5分钟”。

应监控最新durable checkpoint的年龄，而不是最近save调用的年龄。

### 10.2 换成token损失

有效吞吐为200万token/s时，360秒对应：

$$
2\times10^6\times360=720\times10^6
$$

即7.2亿token的潜在回退工作。

这不是训练质量永久丢失，而是需要重新计算的工作量。

## 11. Goodput的完整手算

设观察窗口为6小时，即21600秒。

纯训练时吞吐为200万有效token/s。

窗口内：

```text
checkpoint可见开销 600s
故障恢复开销        300s
需要重跑的失效工作  180s
```

假设三项互不重叠，并且其余时间都达到稳定速率。

真正留下的有效工作时间为：

$$
21600-600-300-180=20520s.
$$

保留的有效token为：

$$
20520\times2\times10^6=41.04\;B.
$$

goodput为：

$$
41.04\times10^9/21600=1.9\times10^6\;token/s.
$$

相对纯训练吞吐为95%。

如果报告只取两个checkpoint之间的最快几十步，就会漏掉这5%成本。

### 11.1 避免重复扣除

若恢复时间已经包含重跑180秒，就不能再扣一次失效工作。

如果async保存成本以吞吐下降表示，也不能再把全部后台写入时长作为停机时间扣除。

指标必须使用清楚且互斥的计时口径。

## 12. Reserve资源的成本与收益

预留节点可以缩短排队与替换时间。

但预留资源即使空闲也占容量预算。

假设64个active节点加2个reserve节点。

按全部分配容量计，预留比例为$2/66\approx3.03\%$。

是否值得取决于故障频率、节省RTO、机会成本和所需SLA。

不能只报告恢复提速而不报告reserve容量。

也不能因为有reserve就省略checkpoint，因为运行态仍可能需要恢复。

## 13. 故障演练必须有明确实验边界

以下是隔离测试作业的设计清单，不是对当前运行中集群执行的操作。

每次演练先固定：

```text
代码与镜像
模型与数据版本
目标拓扑
checkpoint格式
故障注入点
期望退出与恢复动作
最大重试次数
通过标准
恢复与清理责任
```

演练目标是验证协议，不是尽可能制造破坏。

先从可控软件故障和小规模状态开始，再进入目标规模。

## 14. 演练一：进程退出

注入点：在一个已知step、尚未发布新checkpoint时，让隔离作业的一个rank退出。

预期：其余rank不会永久等待；旧运行态被清理；恢复器只选已发布版本。

需要证据：

- 故障发生与检测时间。
- 各rank退出或abort时间。
- 选中的checkpoint ID及durable时间。
- 恢复后的sample IDs与optimizer计数。
- canary结果与恢复吞吐时间。

通过标准不能仅写“job重新Running”。

应确认没有从不完整checkpoint恢复，也没有跳过未提交数据。

## 15. 演练二：保存中断

分别在staging、shard写入、metadata finalize之前以及发布之后中断隔离保存流程。

预期：发布前的失败产物不能被恢复器当作最新完整版本。

发布后的版本应通过结构与内容校验。

每个注入点都要重复测试，因为时间窗口与并发顺序会影响结果。

不要直接破坏唯一训练checkpoint；使用可丢弃测试目录与已知完整基线。

### 15.1 必查反例

人为保留tracker却删除测试shard，验证loader会拒绝并回退或明确失败。

人为制造错误hash，验证内容校验确实执行。

只让目录存在的测试无法覆盖这些情况。

## 16. 演练三：慢节点与数据长尾

先人为增加隔离rank的计算等待，再增加其数据输入等待。

比较监控是否把两者归入正确阶段。

再用相同工作量的peer baseline检查误报。

若所有异常都被统一标为“NCCL慢”，说明阶段关联还不够。

还应测试正常的长样本或MoE负载变化，确保不会被误判为坏设备。

## 17. 演练四：数值与恢复语义

用受控的软件注入制造一个明确的NaN或验证拒绝。

观察rerun的fatal/nonfatal分支是否符合配置。

检查重放是否使用相同microbatches与随机状态。

随后用固定小batch比较不中断与恢复路径的一次更新。

若改变DP，还要比较全局样本并集以及明确接受的数值容差。

软件注入验证的是检测与恢复协议，不证明真实硬件SDC检测率。

## 18. 可运行的指标计算

```python
window = 6 * 3600
rate = 2_000_000
save_overhead = 600
recovery = 300
lost_work = 180
useful_seconds = window - save_overhead - recovery - lost_work
retained_tokens = useful_seconds * rate
goodput = retained_tokens / window
assert goodput == 1_900_000
print("retained billion tokens", retained_tokens / 1e9)
print("goodput", goodput)
print("efficiency", goodput / rate)

interval, publish_lag = 300, 60
worst_durable_age = interval + publish_lag
print("RPO seconds under stated assumptions", worst_durable_age)
print("potential replay tokens", worst_durable_age * rate)
```

该程序检查指标口径，不执行故障注入或访问任何集群。

实际报表应使用观测事件计算并注明重叠时间处理规则。

## 19. 故障证据包

每次失败保留一个可索引证据包：

```text
run与attempt身份
失败前后配置hash
rank到GPU/host映射
最早异常时间与完整错误链
前后若干step的阶段trace
checkpoint与sample游标
GPU/NIC/存储遥测片段
恢复动作与节点隔离结果
canary与最终验收
```

证据包不应无差别保存敏感数据正文或凭据。

通常sample ID、内容摘要和受控定位入口已足够支持工程调查。

同时保存日志保留周期与访问边界，避免下一次故障时证据已被清理。

## 20. 自测与详细答案

### 题1：64卡数量满足，为什么作业仍可能不适合启动？

因为通信域、CPU、主机内存、NIC和存储需求可能不满足。

逻辑并行组必须映射到合适物理资源。

启动前应验证实际映射，而不只检查GPU总数。

### 题2：每300秒save一次，RPO为什么可能大于300秒？

异步保存需要时间才成为durable版本。

新版本未发布时只能回退到更旧版本。

应测最新可恢复状态年龄。

### 题3：进程重启完成是不是RTO终点？

取决于事先定义，但对训练通常不够。

加载、warmup、canary和恢复有效吞吐仍需时间。

RTO终点应反映真正恢复的服务水平。

### 题4：为什么不能把每个sample ID作为指标label？

这会产生高基数时序，增加监控存储与查询成本。

sample级信息适合日志或trace，通过事件ID关联低基数metrics。

### 题5：reserve节点是否总能提高整体效率？

它减少恢复等待，却消耗预留容量。

应比较故障频率、节省RTO、机会成本与SLA。

只看一次恢复速度会忽略长期资源成本。

### 题6：软件NaN注入通过是否证明能发现真实SDC？

不能，它只验证指定异常信号到恢复动作的路径。

真实SDC可能产生有限且隐蔽的错误。

需要额外的工作负载覆盖、冗余与硬件诊断证据。
