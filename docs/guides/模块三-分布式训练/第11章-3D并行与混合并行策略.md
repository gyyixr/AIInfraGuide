## 本章概述

前面各章分别说明一种并行策略切分什么。本章把它们放到同一个训练步骤里：给定模型、GPU 数、通信拓扑和全局 batch，怎样定义进程组，怎样估算每卡状态和关键路径，怎样判断一项优化真的有效，以及中断后能恢复什么。

设计目标不是把所有并行开关打开。每增加一种切分，都增加一种通信、布局或一致性约束；先建立正确的参数和数据归属，再比较吞吐。

本章也修正三种常见误解：TP 可以跨节点，但性能取决于实际互联；DP 并不总是每步只有一次集合通信；EP 也不能无条件再乘到已经包含相关设备的 DP 网格上。

## 11.1 多维并行拓扑与 Rank 编排

第一篇用 8 卡 `TP=2, PP=2, DP=2` 完整列出 rank 坐标、TP/DP/PP 组，并加入 CP 与 MoE 网格。

| 问题 | 应产出的证据 |
|---|---|
| rank 代表什么 | 全局 rank、local rank、节点和设备映射 |
| TP 怎样分组 | 同 pipeline stage、同数据副本的层内协作组 |
| DP 怎样分组 | 相同逻辑参数位置的数据副本组 |
| PP 怎样分组 | 同一数据副本沿网络深度的 stage 链 |
| CP 计入什么 | 序列切片、共享权重以及梯度归约域 |
| EP 与 DP 怎样共存 | dense 与 expert 两套网格的等式和映射 |

再比较 64 卡两套方案：`TP8×PP4×DP2` 和 `TP4×PP8×DP2`。两者使用同样数量的设备，但通信域、激活状态和流水线空泡不同，不能只比较一个乘积。

### 学完本篇应能做的事

- 从 rank 公式列出所有通信组，并检查每个 rank 的成员身份。
- 根据实际节点映射判断哪些组跨机。
- 正确计算全局 batch，避免把 TP、PP、CP 当成独立样本副本。
- 解释专家 TP 与 Attention TP 不同的时候，为什么需要重新组织布局。
- 对照固定 Megatron `parallel_state.py` 阅读实际 group 构造。

## 11.2 训练性能建模与可靠恢复

第二篇把配置变成可计算的资源账本。

| 账本 | 内容 |
|---|---|
| 常驻状态 | 参数、梯度、master weights、优化器状态各自的字节与副本数 |
| 峰值状态 | 激活、临时 workspace、通信 buffer、预取和聚合参数 |
| 每步数据 | 全局样本/有效 token、microbatch 数、数据并行度 |
| 时间 | 算子、暴露通信、流水线空泡、输入和保存的关键路径 |
| 性能指标 | token/s、GPU 秒、MFU 的公式与计时边界 |
| 恢复状态 | 模型、optimizer、RNG、数据游标、拓扑与分片 manifest |

把“装得下”和“跑得快”分别验收：显存下限不是实际峰值，通信字节下界不是 wall time，能够加载权重也不是精确恢复训练。

## 与本地实验的对应关系

本仓库 `labs/distributed/` 提供数值与 CPU/Gloo 实验。它可以验证集合通信输出、全局有效样本归一化、梯度累积、裁剪和优化器更新等机制。

CPU 实验不会生成真实 GPU/NCCL 性能结论。单进程内存状态恢复也不会验证磁盘分片、断电持久性、跨机器事务或改变并行度后的完全可复现性。

阅读本章时应把下面四层分开：

1. 纸笔计算：对公式、单位、坐标和假设负责。
2. CPU 数值实验：对有限输入上的输出与更新负责。
3. 单机/多机后端实验：需要真实硬件、拓扑和依赖记录。
4. 长周期训练：还需要质量、故障、恢复和持续成本证据。

## 建议的设计流程

先写出模型状态表和批次定义，再列候选 `(TP,PP,DP,CP)`，排除不可整除、超预算和布局不支持的组合。

对可行组合，用同一 global batch 和有效 token 口径估算空泡、通信和激活。随后执行一个固定的小步骤，比较 loss、梯度和参数变化，而不是直接跑长训练看吞吐。

数学一致性通过后，再分阶段计时、增加数据规模和并行度。每次只改变一个主要维度，保留前后有效配置与测量条件。

最后执行恢复实验，确认保存与重启不会把优化器步数、数据位置和权重版本拆散。

## 本章验收

- 能画出 8 卡例子的三个通信组集合，并解释每种通信处理的逻辑对象。
- 能说明 `world_size=TP×PP×DP×CP` 的适用假设和 EP 的特殊关系。
- 能逐项计算一个假设混合精度布局的每卡静态状态，而不是死记 16 字节。
- 能用关键路径解释“kernel 加速了但整个 step 几乎没变”。
- 能区分 MFU、GPU utilization 与实际训练 token 吞吐。
- 能列出 checkpoint 必须共同提交的状态，并设计连续跑/恢复跑对照。

## 自测提示

**TP=8、PP=4、DP=2 是否自动规定哪些 rank 同组？** 没有，还需要 rank 顺序、CP/专家网格、节点分配和框架约定。

**如果理论静态显存是 20 GB，24 GB GPU 是否一定能运行？** 不一定；激活、临时聚合、通信 buffer、碎片及其他进程仍占空间。

**训练快 20% 是否一定更省成本？** 不一定，需要同时比较 GPU 数量、实际有效工作量、验证质量和恢复损耗。
