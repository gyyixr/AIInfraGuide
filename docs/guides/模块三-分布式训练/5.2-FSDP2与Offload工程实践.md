## 1. 从算法名称走到实际对象

上一节回答了哪些状态可以分片。本节继续追问：模型里的哪组参数一起聚合，优化器究竟拿到什么对象，前向结束后哪个 buffer 还活着，CPU 卸载省下的显存由谁支付代价。

**版本说明**：API 组织按 2026-10-30 阅读的 PyTorch FSDP2 官方教程核对，页面标注 PyTorch 2.15。下面的 GPU 脚本是可审阅的最小示范，本章没有执行多 GPU FSDP2。实际运行应记录安装版本，并先检查 import 和参数签名。

不要把 `torch.distributed.fsdp.FullyShardedDataParallel` 包装器的 FSDP1 示例，直接改一个类名就称为 FSDP2。两者的参数表示与配置方式不同。

## 2. fully_shard 改变了什么

FSDP2 通过 `fully_shard(module)` 为模块安装参数生命周期管理，并将分片状态表示为 `DTensor`。

假设一个权重的全局形状是 `[8,4]`，在两个 rank 上沿第 0 维分片：

```text
逻辑参数 W：全局 shape [8,4]
rank 0：local shard shape [4,4]，对应全局行 0..3
rank 1：local shard shape [4,4]，对应全局行 4..7
```

`DTensor` 除了本地数据，还携带 device mesh 与 placement 信息，因此能够表达“这 4 行属于一份 8 行参数”。

一个普通 `[4,4]` 张量本身不包含这种全局语义。把所有分片都简单变成本地 tensor，再交给不了解布局的代码，可能丢失必要的通信和归约规则。

### 2.1 参数、计算副本和优化器

一个典型 mixed-precision 设计如下：

| 时刻/对象 | 表示 | 可能的 dtype |
|---|---|---|
| 常驻参数 shard | DTensor | FP32 |
| 聚合后的计算参数 | 当前参数组的完整 tensor | BF16 |
| 归约中的梯度 | 通信 buffer | FP32 |
| 更新梯度与 Adam moments | 分片状态 | FP32 |

这时不能套用“BF16 参数 2 Bytes + 独立 FP32 master 4 Bytes”的账本再重复计数。FP32 shard 本身可承担更新精度，BF16 完整副本是计算阶段的临时量。

在实际代码中打印 dtype 和本地形状，比从 `bf16=True` 推断所有状态更可靠。

## 3. 为什么要先分 block，再处理根模块

如果只给整个 70B 模型调用一次 `fully_shard`，一次前向可能需要聚合非常大的参数组。虽然平时参数已经分片，活动峰值仍可能放不下。

更常见的结构是：

```python
for block in model.blocks:
    fully_shard(block, mesh=mesh)
fully_shard(model, mesh=mesh)
```

内层 block 先拥有自己的参数组；根模块再管理尚未归入子组的参数，如 embedding 或输出层。不能把同一个参数重复作为两个独立拥有对象更新。

### 3.1 粒度选得太大

假设每个 block 的完整参数为 0.8 GB：

- 每 8 个 block 为一个组，完整活动组约 6.4 GB。
- 每 1 个 block 为一个组，完整活动组约 0.8 GB。

在其他状态相同时，较小组显著降低临时聚合量。

### 3.2 粒度选得太小

若一个 block 被切成几十个很小参数组：

- collective 启动与 CPU 调度次数增加。
- 小消息更容易受延迟而非带宽限制。
- 下一组计算很短，通信难以被隐藏。
- 频繁分配或元数据处理可能成为瓶颈。

所以“越细越省”不能单独决定最终配置。应寻找能满足显存且拥有足够计算窗口的粒度。

## 4. 前向后是否 reshard

`reshard_after_forward=True` 表示前向后恢复分片驻留，反向需要时重新聚合。

`False` 可以保留前向得到的完整参数到反向阶段，省去相应的再次聚合，但增加从前向到反向之间的显存驻留。

| 选择 | 主要收益 | 主要代价 |
|---|---|---|
| 前向后 reshard | 释放完整参数 | 反向再次 AllGather |
| 前向后保留 | 少一次聚合 | 更多完整参数同时驻留 |

这与 ZeRO-2/3 在“参数什么时候完整驻留”方面有对应关系，但不是所有状态与默认设置都一一相同。

根模块、共享参数和特殊执行路径可能有额外策略，分析时以实际 FSDP 参数组和 trace 为准。

## 5. 一个完整但未在本章执行的 GPU 骨架

保存到独立实验目录的 `fsdp2_example.py`，在具备对应 PyTorch 与至少两张可用 GPU 的环境中运行。它训练小 MLP，只用于观察参数状态，不是大模型性能基准。

```python
import os
import torch
import torch.distributed as dist
from torch import nn
from torch.distributed.device_mesh import init_device_mesh
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy


class TinyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.blocks = nn.ModuleList([
            nn.Sequential(nn.Linear(128, 256), nn.GELU(), nn.Linear(256, 128))
            for _ in range(2)
        ])
        self.head = nn.Linear(128, 8)

    def forward(self, x):
        for block in self.blocks:
            x = x + block(x)
        return self.head(x)


def main():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    dist.init_process_group("nccl")
    device = torch.device("cuda", local_rank)
    mesh = init_device_mesh("cuda", (dist.get_world_size(),))

    # 各 rank 先使用相同初始化；输入随机流稍后再分开。
    torch.manual_seed(123)
    model = TinyModel()
    policy = MixedPrecisionPolicy(
        param_dtype=torch.bfloat16,
        reduce_dtype=torch.float32,
    )
    for block in model.blocks:
        fully_shard(block, mesh=mesh, mp_policy=policy,
                    reshard_after_forward=True)
    fully_shard(model, mesh=mesh, mp_policy=policy)
    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)

    torch.manual_seed(1000 + dist.get_rank())
    for step in range(3):
        x = torch.randn(4, 16, 128, device=device)
        target = torch.randn(4, 16, 8, device=device)
        optimizer.zero_grad(set_to_none=True)
        prediction = model(x)
        loss = (prediction.float() - target).square().mean()
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        if dist.get_rank() == 0:
            print(step, float(loss.detach()))

    # 所有 rank 都参与必要通信，避免把集体操作放到 rank 0 分支里。
    dist.destroy_process_group()


if __name__ == "__main__":
    main()
```

启动方式：

```bash
torchrun --standalone --nproc_per_node=2 fsdp2_example.py
```

本章没有替读者安装或验证上述 GPU 环境。仓库配套 CPU 实验与这里的真实参数分片是不同证据层次。

### 5.1 为什么 optimizer 放在 fully_shard 之后

优化器应持有最终用于训练的参数表示。如果先构造优化器，再替换或重建参数对象，优化器可能仍引用旧对象，状态初始化也可能与分片布局不符。

小模型测试应直接检查：模型更新后参数是否变化、优化器是否管理全部可训练参数、moments 的本地形状是否符合分片布局。

### 5.2 日志只打印 rank 0，不代表只让 rank 0 做所有工作

`print` 通常可以只在 rank 0 执行。需要 collective 的参数聚合、梯度范数计算、分布式状态保存则必须由规定的参与者共同调用。

这是分布式脚本里最容易从“省日志”误推成“省参与者”的地方。

## 6. Prefetch 是用显存换等待时间

假设 block $i$ 的计算耗时 8 ms，下一组 AllGather 为 5 ms。如果两者能并行，下一组到达时计算已准备好，5 ms 传输可能基本被隐藏。

如果计算只有 2 ms，则可能仍暴露约 3 ms 等待。这个差值只是理想估计，还要考虑共享链路、不同 stream 依赖和 CPU 发起速度。

预取两个 block，可以更早启动通信，但也使更多完整参数同时驻留。

```text
没有预取：AG_i → Compute_i → AG_i+1 → Compute_i+1
有预取：          Compute_i ──────────────
                  AG_i+1 ───────
```

不要只看 `NCCL time` 是否变短；通信量可能完全没变，变的是它是否暴露在关键路径上。

官方教程提供隐式与显式预取接口。开始时先使用默认执行路径，抓到明确等待后再调整显式顺序，以免手工预取顺序与模型真实控制流不一致。

## 7. 梯度累积不能照抄 DDP 的 no_sync

FSDP2 的梯度同步控制由 `FSDPModule` 接口承担，官方迁移说明将 FSDP1 的 `no_sync()` 对应到 `set_requires_gradient_sync` 一类控制。

但仅控制是否同步，还不能推出内存和数学语义：

1. 本轮是否保留完整梯度？
2. 是否还进行参数 reshard？
3. 最后一个 microbatch 是否恢复同步？
4. loss 是否按全局样本/token 分母归一化？
5. 所有 rank 的累积次数是否一致？

对不等长 token batch，各 microbatch 的局部均值再平均通常不等于全局 token 平均。这里的分母问题与 FSDP 无关，却会在增加并行度后被放大。

## 8. Offload 搬走的是哪些状态

经典 ZeRO-Offload 将优化器相关状态与更新计算移到 CPU，GPU 仍执行主要的模型前向和反向。

这不等于把 Transformer 的反向传播整体搬到 CPU。GPU 生成梯度后，梯度和更新结果需要跨 PCIe 传输。

ZeRO-Infinity 进一步利用 CPU 与 NVMe 层次，并通过分块预取和计算/I/O 重叠管理超大状态。它扩展容量，但没有消除物理带宽和主机计算成本。

### 8.1 CPU 卸载带宽手算

假设某个更新分片需要把 2 GB 梯度送到 CPU，并把 1 GB 更新后的计算权重送回 GPU；测得有效带宽为 20 GB/s。

若两个方向严格串行：

$$
T_{copy}\ge\frac{2+1}{20}=0.15\text{ s}.
$$

若链路、DMA 和实现允许充分双向重叠，理想下界可更接近 $\max(2/20,1/20)=0.1$ s，但还没算 CPU optimizer 时间。

不能看到 PCIe 标称双向带宽就直接把单向数据量除以该数值。测量需明确方向和重叠条件。

### 8.2 NVMe 容量不是 HBM 带宽

若一轮需要从存储读取 16 GB 状态，实际有效读取带宽为 4 GB/s，单读下界已是 4 s。

容量足够仅说明状态放得下；若计算窗口无法隐藏这 4 s，GPU 就会等待。顺序读写、buffer 复用、队列深度和多个 rank 争用同一磁盘都会影响实际值。

这些数字为教学假设，不能用于给任何 SSD 或训练框架打性能分数。

## 9. DeepSpeed 配置应怎样阅读

以下是 **ZeRO 部分的配置片段**，不是包含模型和数据的完整启动配置：

```json
{
  "zero_optimization": {
    "stage": 3,
    "offload_optimizer": {"device": "cpu", "pin_memory": true},
    "offload_param": {"device": "cpu", "pin_memory": true},
    "overlap_comm": true,
    "reduce_bucket_size": 100000000,
    "stage3_prefetch_bucket_size": 50000000
  }
}
```

核对配置时区分 optimizer offload 与 parameter offload。只设置前者，不能推断所有模型参数也已离开 GPU。

DeepSpeed 的相关 bucket 字段按**元素数**描述；如果元素用 BF16，1 亿个元素约为 200 MB，而 FP32 则约为 400 MB。单位不明时，不要直接把数字当作 Bytes。

`pin_memory=true` 也会消耗主机锁页内存。多个 rank 大量 pin 住 buffer，可能使整机内存压力增大。

## 10. Checkpoint 保存的是逻辑状态

FSDP2 的分片参数和 optimizer state 可由 DTensor/DCP 路径保存与恢复。关键区别是：

- 分片 checkpoint 保留各 rank 拥有部分及元数据。
- full state dict 需要聚合；构造过程可能产生显存或主机内存峰值。
- 只保存模型权重不等于可继续训练，还缺 optimizer、scheduler、RNG 和数据进度。
- 改变 world size 后的重分片需要后端明确支持，并不保证未来采样和归约逐 bit 相同。

`state_dict()` 返回不意味着所有保存工作已经持久完成；异步 checkpoint 的 staging 与落盘完成也要区分。

## 11. 排障顺序与验收

| 现象 | 先查什么 | 常见误判 |
|---|---|---|
| 初始化就 OOM | CPU/GPU 完整模型是否先被构造多份 | 认为分片后小就不关心初始化峰值 |
| 第一层前向 OOM | root 包裹粒度、完整聚合组 | 只减优化器状态 |
| 反向峰值高 | 预取、重计算、梯度累积 buffer | 只调生成 batch |
| GPU 间歇空转 | AllGather 是否卡在下一层前 | 把所有空转称为网络差 |
| 开 Offload 后主机 OOM | RAM、锁页、rank 数和预取深度 | 以为省 GPU 内存等于省总内存 |
| 恢复后 loss 跳变 | optimizer、数据游标、RNG、精度 | 只比较权重文件大小 |

最小验收应包括单卡参考更新与分片更新的误差、参数 shard 形状、优化器状态大小、阶段显存峰值，以及保存后恢复下一步的对照。

## 12. 自测与参考答案

**1. 参数从 CPU 初始化后，为什么仍需核对初始化是否一致？**

同一逻辑参数必须从相同值切出各 shard。不同 seed 或错误的分片初始化会拼成未定义的新模型。

**2. 保留前向完整参数是否总比再次聚合更好？**

不是。它用显存换通信，若挤掉更有效的 batch 或导致 OOM，总吞吐可能更差。

**3. Offload 后反向矩阵乘法在哪里执行？**

经典 ZeRO-Offload 的主要前向/反向仍在 GPU；被移动的是相关状态和 optimizer 更新计算，具体扩展需看实现。

**4. 为什么本节 GPU 脚本的存在不等于多卡已验证？**

静态 API 核对、脚本语法和真实运行是三种证据。需要具体运行环境、输出与数值对照才能报告多卡验证。
