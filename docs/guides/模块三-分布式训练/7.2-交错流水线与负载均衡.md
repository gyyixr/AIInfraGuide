## 1. 更细的流水线能省等待，也会制造新成本

上一节中，一个物理设备只负责一段连续层。交错流水线让一个设备负责多个较小、逻辑上不相邻的模型块，在这些块之间切换 microbatch 的计算。

它没有增加 GPU 数，也没有减少模型数学计算量。它改变的是任务颗粒度和可调度顺序，使填充与排空期间可能出现更多可执行工作。

先分清：

- **物理 stage**：通常映射到一组真实设备。
- **虚拟 stage / model chunk**：分配给某个物理 stage 的一段模型。
- **microbatch**：一次更新中的数据片段。

虚拟 stage 不等于更多数据并行副本。

## 2. 64 层、4 个物理 stage、每卡 2 个 chunk

设 $P=4,v=2$，共有 $Pv=8$ 个逻辑 chunk，每个 8 层。一个常见映射是：

| 设备 | 第一个 chunk | 第二个 chunk | 总层数 |
|---|---|---|---:|
| GPU 0 | 逻辑 chunk 0，层 0—7 | chunk 4，层 32—39 | 16 |
| GPU 1 | chunk 1，层 8—15 | chunk 5，层 40—47 | 16 |
| GPU 2 | chunk 2，层 16—23 | chunk 6，层 48—55 | 16 |
| GPU 3 | chunk 3，层 24—31 | chunk 7，层 56—63 | 16 |

一个 microbatch 的前向仍必须按逻辑层顺序走：

```text
GPU0/chunk0 → GPU1/chunk1 → GPU2/chunk2 → GPU3/chunk3
→ GPU0/chunk4 → GPU1/chunk5 → GPU2/chunk6 → GPU3/chunk7
```

注意 chunk 3 到 chunk 4 会从最后一个物理设备回到第一个。网络调度必须包含这条边，不能只数相邻编号设备的第一次传输。

## 3. 理想收益公式从哪里来

记非交错方案中每个物理 stage 对一条 microbatch 的总前向和反向时间为 $t_f+t_b$。

若一个设备的层被均匀切成 $v$ 个 chunk，则一个 chunk 的时间近似缩小为原来的 $1/v$。理想交错调度可以把部分填充/排空气泡缩短到这个粒度。

在负载平衡、调度可行、通信完全忽略的近似模型中：

$$
T_{interleave}\approx M(t_f+t_b)
+\frac{P-1}{v}(t_f+t_b).
$$

对应 bubble fraction：

$$
f_{bubble}\approx\frac{P-1}{Mv+P-1}.
$$

这里的 $Mv$ 是代数整理后的分母项，不表示训练 batch 被放大了 $v$ 倍，也不表示每个 microbatch 只需计算一个 chunk。

### 3.1 为什么要写近似而不是保证

上述公式没有包含：

- microbatch 与 chunk 的实际分组限制。
- 不同层、embedding、loss 的不均匀时间。
- 虚拟边界新增的通信和 buffer。
- 设备对多个 ready 任务的选择顺序。
- 重计算和激活卸载的额外依赖。

小 $M$ 时甚至可能无法进入理想稳态。应把公式当作收益上界的起点，再检查实际 schedule。

## 4. 用上一节数字比较

取 $P=4,M=8,t_f+t_b=6$ ms：

```text
非交错理想时间 = (8+3) × 6 = 66 ms
v=2 交错近似时间 = 8 × 6 + 3 × 6/2 = 57 ms
理论节省 = 9 ms
理想加速 = 66/57 ≈ 1.158 倍
```

如果新增的**暴露通信与调度时间**超过 9 ms，交错就可能得不偿失。

关键是“暴露”：新增总通信工作量不一定全部延长关键路径。如果它被其他 chunk 的计算覆盖，影响可能较小。

## 5. 消息数量不是一句“乘 v”就够了

连续非交错的 $P$ 段模型有 $P-1$ 条逻辑边界；上述交错布局有 $Pv-1$ 条逻辑边界。

每个 microbatch 的每条边界至少需要一次前向激活传输和一次反向输入梯度传输。因此忽略其他消息：

$$
N_{msg}^{plain}=2M(P-1),
\qquad N_{msg}^{interleave}=2M(Pv-1).
$$

取 $P=4,v=2$，比例为 $7/3$，不是严格的 2。某些实现会聚合、合并或重叠 P2P 调用，设备端实际调用次数还需查 trace。

### 5.1 传输量的数值例子

设边界激活为 BF16 `[b=2,s=2048,h=4096]`：

$$
A=bsh\times2=32\text{ MiB}.
$$

若反向边界梯度也是相同大小，$M=8,P=4$：

| 方案 | 逻辑消息数 | 全 PP 组累计发送量 |
|---|---:|---:|
| 非交错 | $2\times8\times3=48$ | 1536 MiB，即 1.5 GiB |
| 两个 chunk | $2\times8\times7=112$ | 3584 MiB，即 3.5 GiB |

这是所有边界累计的发送字节，**不是每张卡的发送量**，也不是某一条链路必然承担的总量。

不同边界可能并行传输，因此不能把全组字节总量除以一条链路带宽，直接宣称得到整步通信时间。

### 5.2 单消息的延迟下界

如果某条链路实测有效带宽为 25 GiB/s，则 32 MiB 消息仅数据传输下界为：

$$
32/(25\times1024)\text{ s}=1.25\text{ ms}.
$$

实际还要加发起延迟、排队、依赖和可能的数据重排。对于很小的 microbatch，固定延迟更容易主导。

## 6. 激活内存不会自动保持“每卡 P 份”

一个物理设备拥有多个 chunk，就有多个前向到反向的生命周期。各 chunk 的在途 microbatch 数可能不同。

应按 chunk 分项计算：

$$
M_{act,r}\approx\sum_{c\in\mathcal C(r)}
N_{live,r,c} A_{r,c}+M_{P2P\ buffers,r}.
$$

虽然每个 chunk 更小，但数量更多、调度间隔更长，某些状态会同时驻留。不能仅把非交错公式中的 $P$ 份激活原样复制过来。

此外应分别记录：输入激活、保存的算子中间值、发送/接收 buffer、重计算边界、梯度暂存。真实峰值可能在不同阶段发生。

## 7. 等层数不等于等工作量

以下是一个教学负载表：8 个顺序层的单 microbatch 计算成本为 `[1,1,1,1,2,2,2,2]` ms，第一 stage 还负责 2 ms embedding，最后 stage 还负责 3 ms loss/head。

按每卡两层划分：

| stage | 层计算 | 额外工作 | 合计 |
|---|---:|---:|---:|
| 0 | 1+1 | 2 | 4 ms |
| 1 | 1+1 | 0 | 2 ms |
| 2 | 2+2 | 0 | 4 ms |
| 3 | 2+2 | 3 | 7 ms |

其他 stage 会频繁等最慢的 stage 3。把“每卡两层”视为均衡，会错过主要瓶颈。

### 7.1 不等层数的改进

一种连续划分是：

```text
stage 0：层 0,1,2 + embedding → 5 ms
stage 1：层 3,4             → 3 ms
stage 2：层 5,6             → 4 ms
stage 3：层 7 + loss        → 5 ms
```

最慢成本从 7 ms 降到 5 ms。长流水线稳态的瓶颈处理率可能改善到约 $7/5=1.4$ 倍，但有限 microbatch 的整步加速还受填充、排空和通信影响。

参数量与激活占用也会随层分配改变，必须同时检查内存约束，不能只追求时间均衡。

## 8. 用枚举法理解分割优化

对于这八层，连续切成四段只需枚举三个切点。下面代码只优化计算成本，不模拟通信：

```python
from itertools import combinations

cost = [1, 1, 1, 1, 2, 2, 2, 2]
best = None
for cuts in combinations(range(1, len(cost)), 3):
    boundaries = (0,) + cuts + (len(cost),)
    loads = [sum(cost[boundaries[i]:boundaries[i+1]])
             for i in range(4)]
    loads[0] += 2
    loads[-1] += 3
    candidate = (max(loads), cuts, loads)
    if best is None or candidate[0] < best[0]:
        best = candidate
assert best[0] == 5
print("max ms, cuts, loads:", best)
```

大模型可用动态规划或搜索，但输入成本必须来自目标形状、精度和后端的测量。拿单层 FLOPs 代替所有阶段时间，可能漏掉词表 softmax、MoE 路由或通信的真实开销。

## 9. P2P 通信要记录哪些契约

每条跨 stage 消息至少包含以下逻辑约定：

| 契约 | 典型错误 |
|---|---|
| microbatch ID 与 chunk ID | 把上一批激活交给下一批反向 |
| shape、dtype、布局 | 发送 BF16，接收按 FP32 解读 |
| 所属 PP/TP/CP 组 | 使用错误 global rank |
| buffer 生命周期 | send 未完成就覆写源 tensor |
| 完成事件与 stream 依赖 | CPU 调用返回后就消费尚未到达的数据 |
| 动态长度协议 | 某 rank 依据不同 padding shape 分配接收区 |

异步 P2P 可以隐藏传输，但必须在真正消费数据前建立依赖。Python API 返回不等于设备端传输完成，更不等于下游计算已经完成。

## 10. 与 TP、SP、DP 组合时重新量化消息

如果 PP 边界携带的是 TP 复制激活，所有 TP rank 都发送完整 tensor，可能造成冗余传输。

有些方案先按特征或序列分片传输，到下一 stage 再恢复布局。这样单个消息更小，但增加布局转换或改变通信组。

因此上面的 $A=bshd_a$ 不是所有混合并行配置的固定消息大小。每次都先写出边界的 global/local shape 和 placement。

DP 梯度同步也会与 PP 反向交叠。若逐 microbatch 都同步 DP，会增加通信；若延迟到最后，又需考虑梯度 buffer 和同步尾部。

## 11. 同步 1F1B、异步更新与权重版本

“1F1B”描述任务交替形式，不独自决定更新语义。

- 同步 flush：整批累积完成后更新，所有 microbatch 使用一致权重版本。
- 某些异步流水线：不同 microbatch 可能使用不同版本，需要权重版本保存或明确的陈旧梯度算法。

因此不能看到一张交替 F/B 图，就断言它等价于普通同步 SGD，也不能反过来认为所有 1F1B 都需要 weight stashing。

每个实验应记录 optimizer step 边界，以及同一 microbatch 的 forward/backward 所对应版本。

## 12. Zero Bubble 的思路与条件

反向常可拆成输入梯度计算和权重梯度计算。上游 stage 必须等待输入梯度，但某些权重梯度计算可以稍后执行。

这提供一种填空闲时隙的机会：优先发送关键路径上的输入梯度，把暂时不影响上游推进的权重梯度任务延后。

但延后会保留更多激活或中间量，也增加调度依赖。所谓“零气泡”通常依赖计算时间比例、足够显存、可拆分算子和特定调度条件，不意味着所有真实任务都有 100% 利用率。

阅读新调度算法时，可统一问：

1. 哪些依赖被拆开了？
2. 哪些状态因此必须活得更久？
3. 通信、优化器和同步尾部是否仍有空闲？
4. 与基线相比是否保持相同 batch、资源和数值目标？

## 13. 对照 Megatron 源码阅读

本节核对固定快照 `7d6895ac6a3ee9e16c53f573f363d2a52b88bf94` 的 `schedules.py`：

```text
get_forward_backward_func
  → 无流水线的执行函数
  → forward_backward_pipelining_without_interleaving
  → forward_backward_pipelining_with_interleaving
```

非交错路径可找到按当前 stage 位置计算 warmup、执行稳态、再 cooldown 的逻辑。交错路径还管理 model chunk、microbatch 分组与 P2P 调度。

实际可用调度受模型配置、虚拟 stage 数和 microbatch 分组约束。不同版本会放宽或改变可整除条件，不应把旧版本“必须 M 能被 P 整除”的经验写成算法定义。

源码阅读建议先画出一个 microbatch 的 chunk 流，再对照其激活队列的入队、出队和反向消费；不要只读最外层 for 循环。

## 14. 一次可复核的调优过程

先固定模型、序列分布、全局 batch、精度、优化器与硬件，依次比较：

| 实验 | 只改变什么 | 记录 |
|---|---|---|
| A | 基础 1F1B | 每 stage F/B/P2P 时间、显存 |
| B | 连续层边界 | 最慢 stage 与头尾特殊层开销 |
| C | microbatch 数 | 计算效率、bubble、全局分母 |
| D | virtual chunks | 新增消息、暴露通信、激活峰值 |
| E | 重计算/卸载 | 额外计算或 I/O 是否换得更优 batch |

先验证一次更新的数值一致性，再测预热后的稳态吞吐。将 warmup、checkpoint、数据加载和 optimizer 等完整成本单独列出，避免只截取最好看的中间几个时隙。

## 15. 自测与参考答案

**1. P=4、v=2 时是否等于模型在 8 张 GPU 上？**

不是，仍是 4 个物理 stage；每个设备负责两个逻辑 chunk。

**2. 为什么消息数不一定严格翻两倍？**

逻辑边界从 $P-1$ 变成 $Pv-1$，还要看融合和实际映射。P=4、v=2 时原始边界比为 7/3。

**3. 理想时间从 66 ms 降到 57 ms，实测却 70 ms，先看什么？**

看新增的暴露 P2P、调度延迟、负载失衡及激活压力；不是先否定公式，也不是假定公式已经包含这些成本。

**4. 为什么最后一个 stage 可能需要更少 Transformer 层？**

它还可能负责大词表输出、loss、评估或其他额外工作。应按实际执行时间和内存划分，而非只按层数。

**5. 延后权重梯度为什么可能增加显存？**

后续计算还要使用的激活与中间量必须继续保存，缩短关键路径不代表缩短所有数据生命周期。
