## 1. MoE 到底改变了哪一层

普通 Transformer 的 FFN 对所有 token 使用同一组参数；MoE 层拥有多个 FFN 专家，Router 为每个 token 选出其中少数几个，再将专家结果加权相加。

设输入隐藏状态 $x_t\in\mathbb R^H$，共有 $E$ 个专家，每个 token 选择 $K$ 个。一个简化形式为：

$$
p_t=\operatorname{softmax}(W_r x_t),\qquad
\mathcal S_t=\operatorname{TopK}(p_t),
$$

$$
y_t=\sum_{e\in\mathcal S_t}g_{t,e}F_e(x_t).
$$

其中 $W_r\in\mathbb R^{E\times H}$，$F_e$ 是第 $e$ 个专家。本文取选中分数重新归一化：

$$
g_{t,e}=\frac{p_{t,e}}{\sum_{j\in\mathcal S_t}p_{t,j}}.
$$

实际模型可能使用 sigmoid score、选择前后不同的归一化、shared expert 或额外缩放。公式里的 gate 约定必须先固定，才能比较输出。

### 1.1 参数规模与激活计算分别计算

若一个专家是两层 FFN，忽略 bias，参数量约为 $2HI$，其中 $I$ 是专家中间维度。共有 $E$ 个专家时专家参数约为 $2EHI$，每 token 仅使用其中 $K$ 份。

但这不代表整个模型参数或 FLOPs 分别恰好增加 $E$ 倍和 $K$ 倍：Attention、Router、Embedding、共享专家及非 MoE 层仍然存在。门控 FFN 也可能是三组投影，需要另算。

稀疏激活主要降低“每 token 使用的专家参数”，不会自动删除未选中专家的权重和优化器状态。

## 2. EP、ETP、专家数据并行先分清

| 名称 | 分的是什么 | 同组设备是否持有相同专家 |
|---|---|---|
| Expert Parallel，EP | 专家集合 | 通常持有不同全局专家 ID |
| Expert Tensor Parallel，ETP | 一个专家内部的矩阵维度 | 同一专家的不同参数分片 |
| Expert Data Parallel，EDP | 处理数据的副本 | 对应相同专家和相同逻辑参数分片 |
| 普通 dense DP | 稠密层的数据副本 | 持有同一稠密层参数或对应分片 |

EP 的核心问题是“把输入送去找专家”。ETP 的核心问题是“一个专家的一次矩阵乘法由谁共同完成”。EDP 的核心问题是“同一个专家的多份训练结果如何合并”。

下文先取 ETP=1、EDP=1，只保留两个 EP 设备，以免混入额外通信。

## 3. 一个六 token、四专家的完整例子

设设备 0 最初拥有 $t_0,t_1,t_2$，设备 1 拥有 $t_3,t_4,t_5$。专家放置如下：

| 设备 | 本地专家 |
|---|---|
| 0 | $e_0,e_1$ |
| 1 | $e_2,e_3$ |

固定 Top-2 路由与归一化 gate：

| token | 初始设备 | 第一条分支 | 第二条分支 |
|---|---:|---|---|
| $t_0$ | 0 | $e_0,0.75$ | $e_2,0.25$ |
| $t_1$ | 0 | $e_1,0.60$ | $e_2,0.40$ |
| $t_2$ | 0 | $e_2,0.70$ | $e_3,0.30$ |
| $t_3$ | 1 | $e_0,0.50$ | $e_3,0.50$ |
| $t_4$ | 1 | $e_1,0.80$ | $e_3,0.20$ |
| $t_5$ | 1 | $e_0,0.40$ | $e_2,0.60$ |

共有 $N K=6\times2=12$ 条逻辑分配。每条分配必须知道原 token ID、目标专家、gate 和原设备，否则无法在 combine 时回到正确位置。

### 3.1 按专家统计输入行数

| 专家 | token 列表 | 输入矩阵形状 |
|---|---|---|
| $e_0$ | $t_0,t_3,t_5$ | $[3,H]$ |
| $e_1$ | $t_1,t_4$ | $[2,H]$ |
| $e_2$ | $t_0,t_1,t_2,t_5$ | $[4,H]$ |
| $e_3$ | $t_2,t_3,t_4$ | $[3,H]$ |

专家权重 shape 可以相同，但每次 GEMM 的行数不同。这正是 MoE 动态 shape 与负载不均衡的来源。

## 4. Dispatch 不是单独的一次通信调用

一个常见实现可拆成：

```mermaid
flowchart LR
    A["原 token 顺序"] --> B["Router: 专家与 gate"]
    B --> C["按目标设备整理发送 buffer"]
    C --> D["All-to-All 交换"]
    D --> E["按本地专家再排列"]
    E --> F["Grouped Expert GEMM"]
    F --> G["反向排列并返回原设备"]
    G --> H["按原 token 加权归并"]
```

真实 dispatcher 可能融合多个步骤，也可能在目标设备内共享 token 副本；这里先采用最容易核对的“每条专家分配单独一行”布局。

### 4.1 源设备整理发送 buffer

设备 0 有六条分配，其中：

- 发给设备 0：$t_0\to e_0,t_1\to e_1$，共 2 行。
- 发给设备 1：$t_0\to e_2,t_1\to e_2,t_2\to e_2,t_2\to e_3$，共 4 行。

设备 1 同样统计：

- 发给设备 0：$t_3\to e_0,t_4\to e_1,t_5\to e_0$，共 3 行。
- 发给设备 1：$t_3\to e_3,t_4\to e_3,t_5\to e_2$，共 3 行。

因此按目标 rank 排列的 split 为：

```text
rank 0 send_splits = [2, 4]
rank 1 send_splits = [3, 3]
```

### 4.2 目标设备的接收 split

接收计数是发送矩阵的转置：

```text
rank 0 recv_splits = [2, 3]  # 分别来自 rank 0、rank 1
rank 1 recv_splits = [4, 3]
```

设备 0 最终收到 5 行，设备 1 收到 7 行。两个 rank 的 buffer 大小不同，这不违反 All-to-All 语义；需要使用支持明确 split 的调用和一致元数据。

交换完成后，来自不同源设备的相同专家 token 往往还不连续，所以还要做一次本地 permutation，把 $e_0$ 的三行和 $e_1$ 的两行分别组织成 GEMM 输入。

### 4.3 逻辑分配数不等于网络流量

例子中跨设备的逻辑分配为 $4+3=7$ 条。但 $t_2$ 的两条分支都前往设备 1，一种优化实现可以只传一份 $x_{t_2}$，到达后供两个专家使用。

此时跨设备输入副本可能从 7 份降到 6 份，同时需要额外的索引关系。不能把某一种 dispatcher 的裸 payload 公式当成所有实现的固定通信量。

## 5. Expert 算完以后怎样回到原 token

为了看清 combine，暂时将专家替换为标量函数：

$$
x_{t_i}=i+1,\qquad F_e(x)=x+10e.
$$

它不是实际 FFN，只用来核对路由、gate 与恢复顺序。

| token | 第一分支结果 | 第二分支结果 | 加权输出 |
|---|---|---|---:|
| $t_0$ | $0.75\times1$ | $0.25\times21$ | 6 |
| $t_1$ | $0.60\times12$ | $0.40\times22$ | 16 |
| $t_2$ | $0.70\times23$ | $0.30\times33$ | 26 |
| $t_3$ | $0.50\times4$ | $0.50\times34$ | 19 |
| $t_4$ | $0.80\times15$ | $0.20\times35$ | 19 |
| $t_5$ | $0.40\times6$ | $0.60\times26$ | 18 |

combine 的数学含义是对同一 token 的分支求和，不是对专家输出简单平均。若前面已在专家输出上乘过 gate，归并时不能再乘一次。

一些实现将 gate 乘法移动到融合 kernel 或专家激活内部；只要保持同一数学计算图，位置可以不同，但检查时必须知道 gate 到底乘了几次。

## 6. 可运行的标准库路由模拟

以下程序模拟逻辑分配和归并，不启动多进程或集合通信：

```python
from collections import defaultdict

routes = [
    [(0, 0.75), (2, 0.25)],
    [(1, 0.60), (2, 0.40)],
    [(2, 0.70), (3, 0.30)],
    [(0, 0.50), (3, 0.50)],
    [(1, 0.80), (3, 0.20)],
    [(0, 0.40), (2, 0.60)],
]
owner = [0, 0, 0, 1, 1, 1]
expert_device = [0, 0, 1, 1]
send_counts = [[0, 0], [0, 0]]
expert_inputs = defaultdict(list)
for token, branches in enumerate(routes):
    assert abs(sum(g for _, g in branches) - 1.0) < 1e-12
    for expert, gate in branches:
        source = owner[token]
        target = expert_device[expert]
        send_counts[source][target] += 1
        expert_inputs[expert].append((token, gate, token + 1.0))

outputs = [0.0] * len(routes)
for expert, assignments in expert_inputs.items():
    for token, gate, x in assignments:
        expert_output = x + 10 * expert
        outputs[token] += gate * expert_output

assert send_counts == [[2, 4], [3, 3]]
assert [len(expert_inputs[e]) for e in range(4)] == [3, 2, 4, 3]
assert all(abs(a-b) < 1e-12 for a, b in zip(outputs, [6, 16, 26, 19, 19, 18]))
print(send_counts, outputs)
```

可把 `expert_inputs` 内部顺序打乱再归并，只要保留原 token ID，结果应相同。若结果随排序改变很多，优先检查索引和 gate；浮点求和顺序只应产生相应精度范围内的舍入差异。

## 7. Backward 沿哪条路线走

记下游梯度为 $\bar y_t=\partial L/\partial y_t$，专家输出为 $z_{t,e}=F_e(x_t)$。固定已经选中的分支时：

$$
\frac{\partial L}{\partial z_{t,e}}=g_{t,e}\bar y_t,
\qquad
\frac{\partial L}{\partial g_{t,e}}=\langle\bar y_t,z_{t,e}\rangle.
$$

所以反向同样需要把每条分支的输出梯度送回负责专家的设备，计算专家权重梯度与输入梯度，然后把输入梯度按原 token 聚合。

$$
\frac{\partial L}{\partial x_t}
=\sum_{e\in\mathcal S_t}g_{t,e}J_{F_e}(x_t)^T\bar y_t
+\text{经 Router gate 返回的梯度}.
$$

第二项容易漏掉：gate 也是输入和 Router 参数的函数。Top-k 索引本身是不连续的，常见实现不对索引选择求普通导数，但选中 score 的数值路径仍可参与反向；某些归一化定义还会涉及未选中 logits。

### 7.1 为什么要区分激活通信和参数同步

EP dispatch/combine 搬的是 token 激活及其梯度。它们不会自动把同一个专家在其他数据副本上的权重梯度求平均。

若 EDP>1，专家参数梯度还要在**相同全局专家、相同逻辑分片**的副本组内归约。把所有 EP rank 的不同专家梯度直接 AllReduce，会把不同模型参数混在一起。

## 8. 容量不足时，数学目标也可能改变

令 capacity factor 为 $c$，一个常用教学配额是：

$$
C=\left\lceil c\frac{NK}{E}\right\rceil.
$$

本例 $N=6,K=2,E=4,c=1$，得到每专家 $C=3$。虽然总槽位 $EC=12$ 等于总分配数，$e_2$ 仍需要 4 行，因此会溢出一条；与此同时 $e_1$ 只有 2 行。

如果按示意顺序丢弃 $t_5\to e_2$：

- 不重新归一化 gate：$y_{t_5}=0.4\times6=2.4$。
- 将剩余 gate 归一化为 1：$y_{t_5}=6$。
- 不丢分支、动态扩容：$y_{t_5}=18$，与原始例子一致。

这些结果不同，说明 drop 策略不是纯粹的通信优化。实际模型还可能保留 residual 或 shared expert 路径，不能将“丢一条专家分支”直接解释成“整条 token 从网络消失”。

### 8.1 从 CPU 模拟迁移到真实后端时怎样验收

先固定同一组 token、路由索引与 gate，对单设备参考实现和分布式实现比较：

1. 每个全局专家实际接收的原 token ID 集合。
2. dispatch 前后各 rank 的 split 矩阵及转置关系。
3. combine 后恢复顺序的输出与最大绝对误差。
4. 输入梯度、Router 梯度和每个全局专家权重梯度。
5. 有无丢分支、padding、重复乘 gate 和遗漏输入梯度。

只比较最终输出还不够：某些错误的 backward 可能在前向完全正常。若使用 dropout，参考实现还必须对齐随机状态；若路由是随机或受数值扰动影响，先冻结路由再测计算和通信本身。

先验证 ETP=1 的简单布局，再增加专家内部 TP、CP、重计算和融合后端。每次扩展只引入一类新的布局变换，定位会更清晰。

## 10. 自测与参考答案

**1. 本例共有多少条逻辑专家分配、多少条跨设备分配？**

答案：12 条逻辑分配，其中 7 条跨设备。若同一 token 发往同一设备的多专家分支复用输入，跨设备输入副本可进一步减少。

**2. `send_splits=[2,4]` 是否意味着 rank 0 最终收到六行？**

答案：不是。它描述发送目标；rank 0 的接收 split 是 `[2,3]`，收到五行。

**3. 为什么 combine 不能只执行一次 unpermute 而不求和？**

答案：Top-k 把一个原 token 展开为多条分支，恢复原序号后还需要累加同一 token 的加权结果。

**4. EP 的 rank 0 和 rank 1 能否直接同步所有专家梯度？**

答案：只有它们持有同一个逻辑参数的副本或按明确算法处理分片时才有对应归约。本文两台设备持有不同专家，不能把不同专家梯度混合。

**5. Drop 后为什么要重新验证模型输出？**

答案：丢分支和 gate 重归一化都会改变函数值和梯度。通信数量正确不代表与 dropless 参考目标等价。
