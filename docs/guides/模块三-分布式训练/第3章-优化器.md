## 本章概述

优化器决定梯度怎样改变参数，也决定要长期保存多少状态。分布式训练还把一个问题放大了：同样叫“平均 loss”，不同 rank、不同 microbatch、不同长度的数据究竟获得什么权重？

本章从 SGD、AdamW 的更新与状态出发，再推导梯度累积和 DDP 归约。目标是能够沿着一轮真实训练，解释 loss、梯度、裁剪、动量、参数和计数器的每一次变化。

## 状态账本必须绑定实现

设参数个数为 $P$。如果工作参数、梯度都是 BF16，另有 FP32 master weights 与两份 FP32 Adam moments，则静态状态为：

$$
M=(2+2+4+4+4)P=16P\text{ bytes}.
$$

若梯度存为 FP32，按相同其他假设计为 $18P$。若原始参数本身保持 FP32 并使用 autocast，则它们可直接作为高精度更新对象，不必自动额外复制 master weights。

普通 PyTorch 直接将参数转成 BF16，也不意味着 Adam 会自动创建 FP32 moments。应在第一次 `optimizer.step()` 后查看实际状态 dtype，因为许多状态是延迟创建的。

“优化器相关量占 75%”来自把 master weights 与 moments 一起计算为 $12P$、总量为 $16P$ 的特定账本，不是所有实现都相同。

## 一个有效 batch 的数据路径

```text
各 DP 副本的数据分片
  → 多个 microbatch 的前向与反向
  → 梯度累积与所需通信
  → 恢复正确全局均值尺度
  → unscale（若使用 loss scaling）与全局 norm clip
  → optimizer.step
  → scheduler / step 计数 / checkpoint 边界
```

每个箭头都可能改变语义。遗漏累积除数、误用总 world size、在 microbatch 内提前更新参数或重复 weight decay，都可能使“能跑”的脚本训练另一个目标。

## 最重要的两个数例

### 不等分片的均值

rank 0 的有效 loss 为 `[1]`，rank 1 为 `[3,3,3]`。局部均值的平均为 2，全局有效元素均值为 2.5。正确日志和梯度都需要保留总和与总数。

### 累积后裁剪

两个梯度贡献 `(3,0)` 和 `(0,4)`，总 norm 为 5。按阈值 2 一次裁剪得到 `(1.2,1.6)`；各 microbatch 分别裁剪再相加得到 `(2,2)`。二者方向和大小都不同。

## 动手验收

配套两进程 CPU/Gloo 实验使用每 rank 有效数 3 和 5，比较：

- DDP `no_sync` 累积的梯度与单进程全局 loss 梯度。
- 三步 AdamW 后的参数与 moments。
- 只平均局部均值时的错误幅度。
- model 与 optimizer 内存状态恢复后的连续更新。

运行入口见第 4.3 节及 `labs/distributed/README.md`。它验证一个小型 float64 模型的正确性，不代表完整 Transformer 或多 GPU 混合精度训练已实测。

## 学习验收与答案要点

1. **AdamW 为什么要保存两个 moments？** 分别追踪梯度及平方梯度的移动统计；实际 dtype 和初始化时机需查实现。
2. **有效 batch 为什么不能总乘 world size？** TP/PP/CP rank 协同处理同一数据；独立样本数取决于 DP 副本数。
3. **什么时候 `loss/K` 足够？** 各 microbatch 的有效元素数相等、局部 loss 为同口径均值，且通信缩放与所定义目标一致。
4. **为什么小步累积后只 step 一次？** 保持同一参数处的梯度和同一优化器更新次数；多次 step 会改变动量、衰减和梯度计算位置。
5. **只保存权重能否精确续跑 Adam？** 不能，还需 moments、step、scheduler、数据进度和相关随机状态；若保存于累积中途，还需累积窗口状态。
