## 1. 先问谁拥有状态，再问用了什么通信

DDP 中每个数据并行 rank 都有相同参数、相同优化器状态，处理不同数据后同步梯度。重复副本方便计算，但也占用了大量显存。

ZeRO 将“谁计算某个层”和“谁长期保存某段状态”分开：每个数据并行 rank 仍处理自己的样本，但不必长期保存所有状态。

例如一本四章的工作手册，可以让四个人各负责维护一章，需要读全文时再交换。交换带来开销，却减少每个人平时保管的内容。

这不是把一个矩阵乘法拆给四人计算。后者是第 6 章的张量并行。ZeRO/FSDP 的一次层计算通常仍需要该 rank 的完整层参数，只是参数在计算前后可以聚合和释放。

### 1.1 固定本节口径

设 $\Psi$ 为参数个数，$D$ 为 **ZeRO 数据分片组大小**。模型还使用 TP/PP 时，$\Psi$ 应替换为这个模型分片所管理的参数量，不能直接拿全模型参数乘除世界总卡数。

定义：

| 符号 | 含义 | 教学数值 |
|---|---|---:|
| $b_p$ | 每个计算参数的字节数 | 2，BF16 |
| $b_g$ | 每个保留梯度的字节数 | 2，BF16 |
| $b_o$ | 每参数优化器相关状态字节数 | 12，FP32 主权重及两个 moment |
| $P$ | 一份计算权重的总字节数 | $b_p\Psi$ |
| $G$ | 一份归约梯度的总字节数 | $b_g\Psi$ |
| $O$ | 一份优化器相关状态字节数 | $b_o\Psi$ |

这里的 16 Bytes/参数是一种**明确指定的实现模型**，不是 BF16 训练的普遍常数。若保留 FP32 梯度，账本变成 18 Bytes/参数；若 FP32 参数本身兼作更新主副本，应避免重复计数。

## 2. 先用四个参数走通一次更新

为了只看所有权，先使用 SGD。两个 rank 都从参数向量开始：

```text
θ = [10, 20, 30, 40]
rank 0 本地梯度 = [1, 3, 5, 7]
rank 1 本地梯度 = [3, 5, 7, 9]
全局平均梯度 = [2, 4, 6, 8]
```

将更新责任分成两段：

```text
rank 0 负责参数索引 [0, 1]
rank 1 负责参数索引 [2, 3]
```

ReduceScatter 若使用 SUM，得到：

```text
rank 0 收到 [1+3, 3+5] = [4, 8]
rank 1 收到 [5+7, 7+9] = [12, 16]
```

再除以 $D=2$，得到拥有者需要的平均梯度 `[2,4]` 和 `[6,8]`。实际后端可能融合除法或采用约定的归约方式，必须保证只平均一次。

取学习率 $\eta=0.1$：

```text
rank 0 更新自己的参数 → [9.8, 19.6]
rank 1 更新自己的参数 → [29.4, 39.2]
```

AllGather 新参数分片之后，双方得到：

```text
θ_new = [9.8, 19.6, 29.4, 39.2]
```

这和 DDP 先 AllReduce 全部梯度、再各自更新完整参数的数学结果相同。但每个 rank 只需维护自己拥有参数的优化器状态。

若使用 Adam，拥有者还更新对应位置的 $m,v$ 和主权重。**没有必要为不属于自己的参数再保存相同的 Adam moments。**

## 3. ZeRO-1：首先分片优化器相关状态

ZeRO-1 长期保留完整计算参数和梯度，分片优化器状态：

$$
M_1=P+G+\frac{O}{D}.
$$

在指定的 2+2+12 Bytes 账本下：

$$
M_1=4\Psi+\frac{12\Psi}{D}.
$$

直观上，先拿走最大且不直接参与前向的大块冗余。即使每卡仍能看见完整模型，也不需要每卡维护完整优化器历史。

### 3.1 为什么不能只凭 stage 编号写死通信序列

一种容易理解但可能多余的实现是：

```text
AllReduce 完整梯度 → 各拥有者更新自己的参数段 → AllGather 新参数
```

更节省通信的组织可以利用：

```text
梯度归约到拥有者 → 分片更新 → 参数分片同步
```

前面的四参数例子就是后者。实际实现还会使用 bucket、融合归约、广播或不同的梯度驻留策略。

**ZeRO stage 主要描述哪些状态被分片，不是一个不可改变的 collective 指令清单。** 分析代码时，应分别记录长期驻留、瞬时 buffer、通信调用和释放时机。

## 4. ZeRO-2：梯度也只留拥有的那部分

ZeRO-2 在 ZeRO-1 基础上进一步分片梯度：

$$
M_2=P+\frac{G+O}{D}
=2\Psi+\frac{14\Psi}{D}.
$$

每个 rank 仍保存完整计算参数。反向生成的梯度可以按 bucket 归约到拥有者，处理完的非拥有部分释放。

```mermaid
flowchart LR
    A["每个 rank：不同数据、完整参数计算"] --> B["局部梯度 bucket"]
    B --> C["ReduceScatter 到拥有者"]
    C --> D["分片梯度和优化器更新"]
    D --> E["同步更新后的参数分片"]
```

### 4.1 稳态梯度分片不表示从未出现过完整形状

单个算子的反向可能先生成临时梯度。通信 bucket、融合 kernel、累积策略决定何时把它归约、何时释放。

因此，看到 OOM 时不能只用 $G/D$ 判断“梯度肯定放得下”。应查反向峰值是否同时包含多个未归约 bucket，以及梯度累积是否延迟了释放。

### 4.2 累积多个 microbatch

如果每个 microbatch 都执行 ReduceScatter，再在拥有者上累积 shard，可以降低常驻梯度，但增加通信次数。

如果先积累完整梯度，到最后再归约，通信次数较少，却可能恢复完整梯度驻留。具体实现可能采用混合策略。

所以 `gradient_accumulation_steps` 与“不同步”选项不仅改变时间，也可能改变峰值显存。

## 5. ZeRO-3：计算参数也按需聚合

ZeRO-3 的长期模型状态进一步变成：

$$
M_3=\frac{P+G+O}{D}=\frac{16\Psi}{D}.
$$

典型的一层生命周期是：

```text
前向前：AllGather 该层参数
前向中：本 rank 用完整层参数处理自己的数据
前向后：按策略释放完整参数，留下 shard
反向前：若已释放，重新 AllGather
反向中：计算局部参数梯度
反向后：ReduceScatter 梯度，释放临时完整参数
```

“按层”也可以是按 block 或用户定义的参数组。粒度大，通信调用少但聚合峰值大；粒度小，峰值低但更多小消息和调度开销。

### 5.1 为什么 $16\Psi/D$ 只是下限

更实用的峰值分解为：

$$
M_{peak}\approx M_{shard}+M_{active\ params}+M_{prefetch}
+M_{activation}+M_{comm}+M_{workspace}.
$$

其中 $M_{active\ params}$ 只应计算相对已计入 shard 的额外驻留，避免双算。若暂时不清楚内存是否复用，用完整活动组大小做保守上界，并标明这不是精确分配器模型。

此外还有 allocator 保留内存、CUDA context、通信库和图缓存。分片能解决长期状态过大，但不能保证所有算子的瞬时工作集都能装下。

## 6. 7B、8 rank 的静态账本

取 $\Psi=7\times10^9,D=8$，采用上述 16 Bytes 账本，以下统一用十进制 GB：

| 策略 | 每 rank 公式 | 每 rank 静态字节数 |
|---|---|---:|
| DDP | $P+G+O$ | 112 GB |
| ZeRO-1 | $P+G+O/8$ | 38.5 GB |
| ZeRO-2 | $P+(G+O)/8$ | 26.25 GB |
| ZeRO-3 | $(P+G+O)/8$ | 14 GB |

例如 ZeRO-2 的计算是：

$$
14+\frac{14+84}{8}=26.25\text{ GB}.
$$

不要直接把 14 GB 当作一张 16 GiB 显卡可训练 7B 的证明：激活、聚合参数、临时空间还没有计入；GB 与 GiB 也不同，$1\text{ GiB}=2^{30}$ Bytes。

### 6.1 一个活动参数组的附加量

若一次聚合 5 亿个 BF16 参数，完整组大小为 1 GB，8 卡每卡原本拥有 0.125 GB shard。

若 shard 与完整 buffer 同时存在，保守计入完整 1 GB；若实现只增配缺失部分，额外量接近 0.875 GB。再预取一组，可能还需类似量级。

这解释了为什么减小 wrapping 单元或 prefetch 深度，有时比再减一个训练样本更能解决 FSDP/ZeRO-3 的加载峰值。

## 7. 通信量必须写明单位和方向

记 $c=(D-1)/D$。在理想 ring 算法下：

| 操作 | 每 rank 发送字节 | 每 rank 接收字节 |
|---|---:|---:|
| AllReduce 一个完整 $G$ 字节梯度 | $2cG$ | $2cG$ |
| ReduceScatter 一个完整 $G$ 字节梯度 | $cG$ | $cG$ |
| AllGather 成完整 $P$ 字节参数 | $cP$ | $cP$ |

表中的发送和接收不能再不加说明地合并。若链路带宽是单方向有效带宽，使用发送量估算；如果报告收发合计，数字会翻倍，但不能据此也把耗时翻倍。

### 7.1 一个简化的整步对比

在每步一次梯度归约、参数和梯度均为同一精度、无额外重复收集的假设下：

$$
V_{DDP}=2cG.
$$

用拥有者归约加参数同步组织 ZeRO-1/2：

$$
V_{1,2}\approx cG+cP.
$$

参数前向和反向各聚合一次的 ZeRO-3：

$$
V_3\approx 2cP+cG.
$$

当 $P=G$ 时，前两者发送量相同，ZeRO-3 为 DDP 的 1.5 倍。这是常见“多 50%”的来源，而不是无条件定律。

### 7.2 改成 FP32 梯度，比例立刻变化

若参数为 BF16、通信梯度为 FP32，则 $P=2\Psi,G=4\Psi$：

$$
V_{DDP}=8c\Psi,\qquad V_3=8c\Psi.
$$

这个简化模型下两者字节量相同，但调用次数、时序和能否隐藏仍不同。因此即使“字节一样”，速度也不会自动相同。

## 8. 7B 的通信下界与暴露时间

继续使用 $D=8,P=G=14$ GB：

```text
DDP 每 rank 发送：2 × 7/8 × 14 = 24.5 GB
ZeRO-3 每 rank 发送：3 × 7/8 × 14 = 36.75 GB
```

假设有效单向带宽为 50 GB/s，忽略延迟和竞争：

$$
T_{DDP,wire}\ge0.49\text{ s},\qquad T_{3,wire}\ge0.735\text{ s}.
$$

这些是**传输工作量下界**，不是实测 step time。若通信能与计算重叠，关键路径只暴露一部分；若许多小 AllGather 串行卡在层前，又可能同时受延迟影响。

一个更接近调优的问题是：

> 哪次聚合来不及完成，使下一层计算必须等待？

这需要时间线，而不是只看一整步的 NCCL 总耗时。

## 9. CPU 可运行的账本核对

以下程序只进行算术，没有模拟物理分片或通信：

```python
psi, d = 7_000_000_000, 8
p, g, o = 2 * psi, 2 * psi, 12 * psi
memory = {
    "ddp": p + g + o,
    "zero1": p + g + o / d,
    "zero2": p + (g + o) / d,
    "zero3": (p + g + o) / d,
}
assert [x / 1e9 for x in memory.values()] == [112, 38.5, 26.25, 14]
c = (d - 1) / d
print({k: v / 1e9 for k, v in memory.items()})
print("send GB", {"ddp": 2*c*g/1e9, "zero3": c*(2*p+g)/1e9})
```

## 10. 自测与参考答案

**1. 16 GB 状态经 8 路分片后，显存峰值是否一定是 2 GB？**

不是。2 GB 是特定状态的理想长期分片量，还要加入活动参数、激活与临时空间。

**2. ZeRO-1 是否必然比 DDP 多一次完整 AllGather 通信？**

不能只凭 stage 判断。高效拥有者归约和参数同步可替代完整梯度 AllReduce 的后半阶段，具体需读实现。

**3. TP=4、DP=8 时能否把 ZeRO 分母写为 32？**

不能直接写。先确定 TP rank 上所持参数分片，再在对应的 8 路数据分片组内分析状态所有权。

**4. 为什么 ZeRO-3 比 DDP 多 50% 的说法需要精度假设？**

因为两者分别传参数和梯度，参数字节宽度不一定等于归约梯度字节宽度。
