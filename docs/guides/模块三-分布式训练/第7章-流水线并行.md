## 本章要解决的问题

PP 按层切开模型，让不同 stage 合作完成一条样本的前向和反向。这样可以减少每个设备持有的层数，但设备会受层间依赖限制，产生空闲。

调度需要同时考虑时间与状态：哪个任务现在可以执行，它依赖哪条激活或梯度，完成后哪些保存数据可以释放。

本章将模型分层、任务调度和 optimizer 更新语义分开讨论，避免只看一张时间线就假定数学目标一致。

前置要求是反向传播、梯度累积和点对点通信。建议先用两个 stage、四个 microbatch 把所有依赖画清楚。

## 1. 不要混淆 batch 与 stage

设 microbatch 样本数为 $b$，一次更新有 $M$ 个 microbatch，DP 副本数为 $D$：

$$
B_{global}=bMD.
$$

PP 和 TP rank 合作处理同一数据，不继续放大全局 batch。增加 $M$ 时若固定 $b$，会改变优化统计；若固定全局 batch，则需要减小 $b$。

## 2. GPipe 的气泡从填充和排空产生

在各 stage 平衡、通信忽略的模型中，每个 stage 单 microbatch 的前后向时间为 $t_f,t_b$：

$$
T=(M+P-1)(t_f+t_b),
\qquad
f_{bubble}=\frac{P-1}{M+P-1}.
$$

这是空闲时间占可用时间的比例。若以有效计算时间为分母，则气泡开销比为 $(P-1)/M$，两者不能混用。

P=4、M=8 时，前者为 27.27%，后者为 37.5%。这些是理想计算，不是实测 GPU 利用率。

## 3. 同步 1F1B 首先缩短激活生命周期

GPipe 先完成全部前向，再执行反向；1F1B 在 warmup 后交替执行前向和反向，尽早消费保存状态。

在第 7.1 节的 P=2、M=4、每个任务等长例子中，两者都使用 10 个时隙，利用率均为 80%。

但 GPipe 各 stage 峰值保存四份前向状态，1F1B 的典型峰值分别为两份与一份。因此 1F1B 的内存收益可以进一步支持更好的实际配置。

不能把这个例子推广成所有 stage 永远保存 P 份状态；份数依 stage 位置、调度、异步 buffer 与重计算而变。

## 4. 交错让一个设备拥有多个 model chunk

P=4、每设备 v=2 个 chunk 时，逻辑模型共有 8 段，但物理 stage 仍只有四个。

在理想平衡近似下，额外填充/排空时间可能缩小到原来的 $1/v$，于是：

$$
f_{bubble}\approx\frac{P-1}{Mv+P-1}.
$$

这不是把训练 batch 乘 v。实际还要支付更多边界消息、调度和激活驻留成本，并满足实现的 microbatch 分组约束。

## 5. 消息和负载要一起算

连续 P 段有 P−1 条逻辑边界，上述交错布局有 Pv−1 条。因此总消息数量不一定严格乘 v。

每个边界应记录实际 global/local shape、dtype、PP/TP/CP 组及 buffer 生命周期，才能计算字节量和完成依赖。

等层数也不等于等时间：embedding、词表输出、loss、MoE 和不同序列形状都可能使头尾 stage 特别慢。瓶颈 stage 决定稳态处理率。

## 6. 梯度与版本是正确性的地基

同步 flush 调度在本次 batch 的所有反向和必要同步完成后再更新参数。前向与对应反向必须遵守一致权重语义。

某些异步流水线使用不同版本和 weight stashing，需要单独分析；“1F1B”这个名字本身不决定是否同步更新。

有效 token 数不等时，microbatch loss 缩放还必须对齐全局分母，避免重复除以 M 或简单平均局部均值。

## 动手实验

1. 手画 P=2、M=4 的 GPipe 与 1F1B 时间表。
2. 用第 7.1 节的纯 Python 检查器验证每条依赖和激活存活数。
3. 将 P=4、M=8 的气泡换成两种分母，解释数值区别。
4. 计算 v=2 后新增的边界消息与理想可节省时间。
5. 对 8 层不等时长模型枚举切点，同时检查显存限制。

这些实验验证时序和算术，不模拟 NCCL 传输、真实 CUDA stream 或 GPU 算子效率。真实优化仍需固定工作负载抓取时间线。

## 学习验收与答案

**为什么 M 很大也可能慢？** 固定全局 batch 时 microbatch 过小，会降低计算效率并放大启动开销。

**为什么交错时间公式不能直接预测实测吞吐？** 它忽略新增通信、分组限制、负载不均和状态驻留。

**为什么异步 send 返回后不能立即覆写 buffer？** 发送可能仍在设备端进行，需要遵守通信完成和 stream 依赖契约。

**如何判断一个优化成立？** 先验证数值与全局 batch 一致，再比较稳态及端到端时间、显存峰值和资源成本。
