## 1. 迁移的是一次完整更新

一个Transformer可以在不同加速器上计算相同的数学函数。
这不意味着同一份二进制、kernel、collective或checkpoint可以直接互换。

一次训练更新至少经过：

```text
全局样本与mask
  → 框架图与autograd
  → compiler与kernel lowering
  → 本地tensor layout
  → collective与归约
  → optimizer更新
  → 持久状态与下一批数据
```

迁移验收需要让这条链闭合。
只比较一个GEMM的峰值，没有回答模型算子、数值、恢复和维护成本。

本篇扩写综述第8.3、8.8、11.5节，官方资料核对日期为2026-11-07。
未安装云SDK，未修改GPU配置，也未运行跨厂商训练。

## 2. 先区分四种任务

| 任务 | 边界 | 主要难点 |
|---|---|---|
| 同一代码迁到另一平台 | 整个作业换后端 | kernel、编译、数值、checkpoint |
| 同厂商不同代际混合 | 一个作业内设备能力不同 | 负载、dtype交集、拓扑 |
| 不同厂商参与同一次同步更新 | 跨runtime通信与共同训练协议 | collective互操作、ABI、状态一致性 |
| 不同平台承担不同服务角色 | 通过明确消息或模型版本协作 | 数据协议、版本、延迟与陈旧性 |

例如在平台A训练、平台B做离线评估，是第四类。
它不要求两种设备共享同一个GPU communicator。

把训练整体迁到AMD成功，也不能作为AMD与NVIDIA混在同一个TP group已成功的证据。
后者多出通信和运行时互操作边界。

## 4. 三套软件栈分别负责什么

| 层 | AMD | TPU常见JAX路径 | AWS Trainium |
|---|---|---|---|
| 框架 | ROCm构建的PyTorch/JAX等 | JAX及其训练库 | TorchNeuron；历史XLA/NxD路径 |
| 编译与运行时 | HIP-Clang、HIP runtime等 | JAX tracing、XLA、设备runtime | Neuron compiler与runtime |
| 专用算子 | hipBLASLt、Composable Kernel等 | XLA生成算子、Pallas等 | 编译算子、NKI kernels |
| 分布式表达 | process groups/框架分片 | global arrays、mesh、sharding | c10d/DTensor等或历史NxD |
| 通信 | RCCL及网络后端 | XLA collective与ICI/DCN映射 | Neuron collective与相应互联 |

表中相同一行表示职责相近，不表示API、对象或二进制相同。
模型层可以共享算法，后端层仍要分别建立能力矩阵。

## 5. AMD：HIPIFY解决的是哪一部分

HIP提供接近CUDA的C++ runtime与kernel编程接口。
HIPIFY可以转换许多CUDA API、类型和名称。
AMD官方仍建议分段移植并逐步验证，不能把文本转换结果当作完整性能移植。[HIP移植指南](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_porting_guide.html)

需要单独检查：

- 内联PTX、CUDA专用库与架构指令有没有对应实现。
- warp大小、lane mask与shuffle是否写死了32。
- shared memory/LDS布局与bank访问是否仍合理。
- vector load的对齐、尾部mask和原子精度是否一致。
- stream、event、异步allocator与graph生命周期是否保持原协议。

不能简单把所有32替换为64。
AMD不同架构的warpSize可能不同，官方要求按目标架构和设备属性处理。
程序中一个64位mask也不自动使原32-lane归约树变成正确实现。

### 5.1 PyTorch里的cuda名称不一定表示NVIDIA设备

PyTorch的HIP构建复用`torch.cuda`及`device='cuda'`等Python接口。
应结合`torch.version.hip`、`torch.version.cuda`与实际设备信息识别构建。
不能因代码里出现`.cuda()`就判定它无法在ROCm上运行，也不能因接口名称相同就认定底层kernel相同。[PyTorch 2.15 HIP语义](https://docs.pytorch.org/docs/2.15/notes/hip.html)

这也是区分Python接口兼容与设备二进制兼容的具体例子。

## 6. AMD：从GEMM descriptor读到实际算法

hipBLASLt的核心不是只调用一个matmul名称。
需要明确A/B/C/D的layout、转置、leading dimension、compute dtype、epilogue与workspace。

建议沿官方API顺序阅读：

```text
hipblasLtMatmulDescCreate
  → hipblasLtMatrixLayoutCreate
  → descriptor与preference属性
  → hipblasLtMatmulAlgoGetHeuristic
  → hipblasLtMatmul
```

heuristic返回候选算法及相关信息，不能把候选首项当所有shape的性能证明。
同一线性层的forward、dgrad、wgrad通常有不同M/N/K与转置组合。
要把这三类shape分别纳入测试。[hipBLASLt API](https://rocm.docs.amd.com/projects/hipBLASLt/en/latest/reference/api-reference.html)

Composable Kernel从tile、tensor coordinate transformation和数据分布表达kernel。
移植自定义kernel时应重新审计tile到thread/warp/block的映射，而非复制CUDA线程配置。
可从`tile_distribution_encoding`、`make_static_tile_distribution`、`make_tile_window`阅读布局入口。[CK Tile](https://rocm.docs.amd.com/projects/composable_kernel/en/develop/conceptual/ck_tile/index.html)

CK的develop文档属于开发分支资料，不能用它证明某个已安装release具有所有接口。

## 7. AMD：RCCL与接口兼容的边界

RCCL提供面向AMD GPU的多GPU、多节点collectives，利用相应设备与网络拓扑。
官方列出了AllReduce、AllGather、ReduceScatter、AllToAll及P2P等原语。[RCCL介绍](https://rocm.docs.amd.com/projects/rccl/en/latest/what-is-rccl.html)

某些接口采用熟悉的NCCL风格名称，有利于框架适配。
但名称或网络plugin接口相似，不证明NCCL与RCCL能直接把不同厂商设备加入同一原生communicator。

要额外证明的条件包括：

1. 两侧runtime能够识别对方提供的buffer和设备内存句柄。
2. communicator/bootstrap及rank协议互通。
3. transport能够访问对应内存，且生命周期和完成语义匹配。
4. dtype、reduction与collective顺序有一致定义。

这些是跨厂商集成应提供的证据要求，不是RCCL API列表已经作出的承诺。

## 8. TPU：global array不等于每个host拥有全量数据

JAX可以把一个逻辑global array分布在多设备、多进程上。
`Mesh`描述设备轴，`NamedSharding`和`PartitionSpec`描述tensor维度怎样对应这些轴。

例如全局X为`[batch=8, hidden=16]`，mesh为data2×model2。
`PartitionSpec('data', None)`把batch切两份，hidden在model轴复制。
每个设备的可见分片为`[4,16]`，但四台设备的元素数相加含复制。

若W为`[16,32]`，按输出维分在model轴，每device持有`[16,16]`。
XW的本地输出为`[4,16]`，整体表达的是不同batch与不同输出特征。
下一层是否需要AllGather或AllReduce，要由其输入布局和收缩维度决定。

实际阅读入口是`jax.sharding.Mesh/NamedSharding/PartitionSpec`、`jax.jit`的输入输出sharding以及`jax.distributed.initialize`。
多进程必须按共同执行协议参与，不是每个host随意执行自己的global program。[JAX分布式数组](https://docs.jax.dev/en/latest/201/sharding.html)、[多控制器JAX](https://docs.jax.dev/en/latest/multi_process.html)

## 9. GSPMD、Shardy与自动插入通信

GSPMD把带sharding信息的全局计算转为各设备的局部计算与collectives。
它解释了“写全局tensor表达式，为何执行时出现通信”。

OpenXLA的Shardy文档介绍新的sharding传播系统，并明确对照此前的GSPMD路径。
因此不能把GSPMD写成所有未来JAX版本唯一固定的默认实现。[Shardy JAX指南](https://openxla.org/shardy/getting_started_jax)

不管使用哪个具体pass，验收问题相同：

- 关键tensor最终按什么维度shard、replicate或产生partial结果？
- layout变化插入了哪些AllGather/ReduceScatter/AllToAll？
- 是否因约束不兼容，把中间tensor临时复制到每台设备？
- 自定义kernel的输入输出sharding是否传播正确？

`jax.jit(...).lower(...)`及编译IR是阅读入口。
仅看到Python层的PartitionSpec不足以推断最终所有通信。

## 10. TPU：ICI与DCN是不同成本域

Google的Multislice文档把slice内部ICI与slice之间DCN分开。
所述路径中跨slice数据经过host及数据中心网络，通信由XLA生成。
同一通信原语落在两个域上，延迟与带宽代价可能不同。[TPU Multislice](https://docs.cloud.google.com/tpu/docs/multislice-introduction)

工程起点通常是把高频细粒度通信尽可能留在快域，再评估较粗粒度的跨域同步。
这是一条代价模型原则，不是“任何TP都绝不能跨DCN”的平台定律。

部署接口也要区分版本。
上面Cloud TPU API页面已提示其维护范围，新的部署应另读对应GKE路径，不能照抄旧创建命令。[GKE Multislice](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/tpu-multislice)

一个可靠的mesh记录应同时包含逻辑轴、物理slice、host、device，以及通信跨越哪一层网络。
只保存一个形如`(8,16)`的mesh shape无法完整复现实验。

## 11. TPU：Pallas的片上内存不能当CUDA shared memory直接替换

Pallas TPU文档区分大容量HBM与较小、较快的VMEM。
kernel通过Refs访问相应memory space，并以搬入、计算、搬出的流水组织tile。[Pallas TPU入门](https://docs.jax.dev/en/latest/pallas/tpu/quickstart.html)

从CUDA迁入一个attention kernel时，应重新设计：

```text
HBM中的Q/K/V layout
  → 进入VMEM的tile与双buffer
  → matrix/vector计算与归约
  → 在线softmax状态
  → 输出写回与跨设备边界
```

不同TPU代际的tile限制和内存容量还需查目标硬件文档。
不能因两个平台都有片上存储，就套用相同tile、线程或warp数量。

## 12. Trainium：先选清楚新旧PyTorch路径

Neuron 2.33.0版本化文档明确区分：

| 路径 | 本篇口径 |
|---|---|
| TorchNeuron native PyTorch | `neuron` device、eager、torch.compile与标准分布式API |
| 历史torch-neuronx XLA | 老XLA训练路径，为已有工作负载保留 |
| NxDT/XLA时代分布式训练 | 该版本文档标维护状态，相关项目已归档 |

两个产品仍使用`torch-neuronx`包名，但API与版本谱系不同。
不能把旧`xla` device初始化片段与新`neuron` backend混成一个作业。[Neuron 2.33训练路径](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.33.0/training/index.html)

本轮读取的2.33 release notes将TorchNeuron标为public beta，适用Trn2/Trn3。
PyTorch包与torch-neuronx版本家族必须配套。
该release的`torch.compile`支持范围强调static shapes；不能由新API存在推断任意dynamic graph已支持。[TorchNeuron 2.33发布说明](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.33.0/release-notes/components/torchneuron.html)

## 13. Trainium：分布式API相同，不代表限制相同

原生路径可从`init_process_group(backend='neuron')`、`init_device_mesh('neuron', ...)`和FSDP2/DTensor入口阅读。
逻辑分片单位需要按实际NeuronCore配置核对，不能把chip、core与GPU rank混称。

Neuron 2.33的分布式指南给出通信stream与HostCC路径，同时列出具体限制：
该HostCC路径支持的collective集合有限，equal-split AllToAll不能直接假定自动fallback。
所以MoE存在AllToAll接口，不等于在所有stream和overlap路径都能使用。[Neuron分布式指南](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.33.0/torch/guides/torch-distributed.html)

迁移时要按操作逐项记录：

```text
device/backend
group与rank身份
collective种类和split
输入contiguous/stride
当前stream与完成依赖
是否在compiled region中
```

`torchrun`负责启动与rendezvous。
它不负责把CUDA、HIP、TPU与Neuron设备内存转成彼此可直接使用的buffer。
即使所有进程成功加入同一控制面，也不能证明训练数据面已互通。

## 14. Trainium：NKI明确表达存储与计算布局

Neuron 2.33 NKI文档的入口包括：

```text
@nki.jit
nki.language.ndarray
nki.language.sbuf / psum / shared_hbm
nki.isa.dma_copy
nki.isa中的计算指令
nki.collectives
```

HBM、SBUF与PSUM承担不同存储职责。
SBUF/PSUM的dim0对应partition维；跨partition的布局变化通常需要实际搬运，不能随意当作零成本view。
dtype、shape、stride、buffer位置和编译期参数都会影响kernel合约。[NKI 2.33语言指南](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.33.0/nki/get-started/nki-language-guide.html)

GPU上一个“只是reshape”的中间表示，迁入后可能不能保持相同物理解释。
应该先确定数学索引，再设计目标设备tile与搬运，最后比较数值和时延。

NKI kernel接入PyTorch训练还需要对应autograd/自定义算子合约。
只写forward kernel没有自动补全backward。[NKI与torch-neuronx集成](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/guides/how-to-work-with-nki.html)

## 15. 两种“layout”都要迁移

第一种是跨设备布局：谁拥有哪个全局tensor片段。
第二种是设备内部布局：tile、stride、packing、scale与片上存储怎样组织。

例如W全局为`[4096,8192]`。
跨设备TP2按输出维切分，每rank的逻辑weight是`[4096,4096]`。
该片段仍可能在设备内部转置、分块、打包或量化。

checkpoint最好保存可解释的逻辑坐标与必要格式信息。
把后端专用packed weight直接当普通二维数组，会在shape相同情况下读错元素。

DTensor或NamedSharding能表达第一层布局的一部分。
它们不会自动证明每个自定义kernel的第二层布局已经兼容。

### 15.1 ABI、kernel二进制与数据协议分别核对

Python扩展的`.so`还依赖所链接的框架、C++ ABI、编译器和运行时库。
同名Python函数不保证另一平台可以加载原来的扩展二进制。
设备代码又有独立目标：CUDA cubin、AMD目标代码和Neuron可执行产物不能当同一种机器码使用。

可迁移的数学源码需要重新编译或lowering到目标设备，并验证相应依赖。
显式消息桥接则应规定tensor逻辑shape、元素编码、byte order、scale格式、长度与所有权。
一段进程内指针值不具备跨runtime、跨机器自动可访问的含义。

跨平台接入至少要分别回答“能加载扩展”“能解释数据”“能执行kernel”“能同步完成”四个问题。

## 16. 算子与dtype能力必须覆盖反向

迁移前为目标模型建立实际shape矩阵：

| 算子族 | 除forward外还需核对 |
|---|---|
| GQA/MLA attention | dQ/dK/dV、causal/packed、位置偏移 |
| SwiGLU/Grouped GEMM | dgrad/wgrad、空expert、尾部padding |
| norm/softmax/CE | 稳定归约、累加dtype、全局词表分母 |
| quantized linear | scale方向、更新周期、转置布局、饱和 |
| collective | reduction dtype、SUM/AVG、异步完成 |
| optimizer | master/moments精度、小更新、epsilon和step |

支持BF16输入不等于内部全部以BF16累加。
“FP8”也不是一个唯一编码和recipe，移植时要记录格式、scale粒度和每个算子的实际dtype。
同名dtype的可用算子范围、特殊值处理与性能可能随设备及版本改变。

先用高精度小tensor oracle，再比较实际dtype的forward、grad、one-step和短程收敛。
误差容差要依据路径与任务设定，不能用一个宽松allclose包住所有阶段。

## 17. 手算一：快慢设备不应简单平均局部loss

以下是纯教学模型，不指定厂商性能。
两设备处理相同长度样本的速度为8与4 samples/s，一步共96条。
每步额外同步时间假设固定为1秒。

均分48/48时，计算耗时分别6和12秒，step为13秒。
按速度分64/32时，两侧计算都为8秒，step为9秒。
该简化模型加速为13/9≈1.444。

但是新的局部batch不同，若两侧局部平均梯度分别为2和5：

$$
g=\frac{64\cdot2+32\cdot5}{96}=3.
$$

等权平均得到3.5，改变了全局目标。
若使用会除以rank数R的平均归约，各rank的局部mean应先乘`R*n_r/N`。
变长数据应换成有效目标token数，而不是样本数。

```python
rates = [8, 4]
equal = [48, 48]
balanced = [64, 32]
step = lambda counts: max(n/r for n, r in zip(counts, rates)) + 1
assert step(equal) == 13 and step(balanced) == 9
means = [2.0, 5.0]
N, R = sum(balanced), len(balanced)
global_mean = sum(n*g for n, g in zip(balanced, means)) / N
ddp_style = sum((R*n/N)*g for n, g in zip(balanced, means)) / R
assert global_mean == ddp_style == 3.0
assert sum(means)/R == 3.5
print("ideal step seconds", step(equal), step(balanced), "gradient", global_mean)
```

实际速度可能依赖batch、长度和kernel shape，通信也不是固定1秒。
这个oracle验证负载与归一化逻辑，不证明跨厂商collective存在。

## 18. 手算二：跨runtime桥接的字节账本

假设两套设备runtime只能通过显式host staging交换256MiB tensor。
D2H与H2D各32GiB/s，网络25GiB/s；忽略协议与序列化开销。

串行路径为：

$$
T=\frac{256}{32\cdot1024}
+\frac{256}{25\cdot1024}
+\frac{256}{32\cdot1024}
=0.025625\ \mathrm{s}.
$$

即25.625ms；只计算网络会得到10ms。
这不是对任何现成平台真实链路的测量。

若切成8块、每块32MiB，理想三段流水可在首块完成后按最慢段节拍推进：

$$
T_{pipe}=t_{D2H}+t_{net}+t_{H2D}+7\max(t_{D2H},t_{net},t_{H2D}).
$$

```python
size_mib, chunk_mib = 256, 32
bandwidths = [32, 25, 32]  # GiB/s，纯教学假设
serial_s = sum(size_mib / (b*1024) for b in bandwidths)
stage_s = [chunk_mib / (b*1024) for b in bandwidths]
chunks = size_mib // chunk_mib
pipeline_s = sum(stage_s) + (chunks-1)*max(stage_s)
assert abs(serial_s*1000 - 25.625) < 1e-10
assert abs(pipeline_s*1000 - 11.953125) < 1e-10
assert pipeline_s < serial_s
print("serial/pipeline lower bounds ms", serial_s*1000, pipeline_s*1000)
```

真实流水要有独立copy/network资源、足够buffer及正确event依赖。
NUMA、CPU序列化、PCIe争用和双向梯度还会增加成本。
不能因为CPU模型允许重叠，就声称已有实现能达到这个下界。

## 19. 编译缓存也是训练状态之外的成本

设平台A冷编译120秒、稳态0.08秒/step；B冷编译20秒、稳态0.10秒/step。
两者总时间相等的步数满足：

$$
120+0.08N=20+0.10N\Rightarrow N=5000.
$$

短于5000步的实验，A的稳态更快也可能总耗时更长。
出现多个长度桶、不同sharding或编译选项时，应统计实际cache miss次数。

这个例子解释编译摊销，不比较具体厂商。
性能报告应分冷启动、预热、稳态、恢复后重编译和完整任务时间。
编译产物还绑定代码、目标架构和版本，不能作为通用跨平台checkpoint。

## 20. 数据与RNG要跨过框架边界

无论在哪个平台，global batch应对应同一组逻辑样本和有效目标。
tokenizer、packing、attention mask、position、label shift及样本游标必须一并迁移。

JAX常用显式PRNG key及split表达随机性；其他框架可能使用可变generator状态。
只复制整数seed不能保证生成同一dropout mask。[JAX随机数](https://docs.jax.dev/en/latest/random-numbers.html)

迁移应明确承诺层级：

1. 同平台同环境的逐位恢复。
2. 新平台上的数值容差等价。
3. 相同数据目标与统计收敛质量。

跨平台浮点归约顺序和RNG实现可能不同。
不能在未建立跨后端随机数协议时承诺第一级。
也不能以“允许非逐位一致”为理由跳过样本覆盖与梯度尺度检查。

## 21. Checkpoint不是一份能torch.load的权重文件

迁移状态至少包括逻辑参数、optimizer master/moments、step、scheduler、数据游标、RNG及量化状态。
还应记录tied weights、QKV排列、expert ID、全局shape/offset和来源dtype。

Neuron **2.32.0历史NxD API**提供具体反例：其load文档要求与保存时相同model-parallel degree；使用ZeRO-1时还要求相同DP degree。
`use_xser`的格式也不能直接当普通PyTorch load格式。
这说明“有save/load API”不等于任意拓扑可重分片。[NxD 2.32训练API](https://awsdocs-neuron.readthedocs-hosted.com/en/v2.32.0/libraries/neuronx-distributed/api-reference-guide-training.html)

该限制属于明确历史路径，不能套到2.33原生TorchNeuron所有checkpoint方案上。
同样，JAX数组的global sharding描述也不自动转换PyTorch optimizer param-group schema。

应把权重warm start与完整resume分开验收。
如果只迁模型权重，应明确fresh optimizer/RNG与新的训练进度，而不是保留旧iteration制造连续恢复表象。

## 22. CPU oracle：重布局时moments跟随逻辑坐标

以下4×4矩阵从两份row shards变成四份column shards。
每种状态都按相同逻辑坐标转换，模拟weight、Adam m和v。

```python
def reshard_rows_to_columns(row_shards):
    full = [row for shard in row_shards for row in shard]
    assert len(full) == 4 and all(len(row) == 4 for row in full)
    return [[[full[i][j]] for i in range(4)] for j in range(4)]

states = {
    "weight": [[4*i+j for j in range(4)] for i in range(4)],
    "m": [[(4*i+j)/10 for j in range(4)] for i in range(4)],
    "v": [[(4*i+j)**2/100 for j in range(4)] for i in range(4)],
}
for name, full in states.items():
    columns = reshard_rows_to_columns([full[:2], full[2:]])
    reconstructed = [[columns[j][i][0] for j in range(4)] for i in range(4)]
    assert reconstructed == full, name
assert reshard_rows_to_columns([states["weight"][:2], states["weight"][2:]])[1] == [[1],[5],[9],[13]]
print("weight/m/v global-coordinate reshard: PASS")
```

它验证逻辑坐标，不解析真实DCP、Orbax或NxD checkpoint格式。
真实转换还要处理padding、fused参数、量化scale、缺失键、replica与文件提交协议。

## 23. 迁移路线与适用条件

| 路线 | 适合的起点 | 必须承担的成本 |
|---|---|---|
| 单平台完整迁移 | 目标后端覆盖主要算子 | 数值、编译、性能与恢复全链验收 |
| 平台分别承载独立DP作业 | 数据任务可独立分配 | 不能随意把独立模型更新当同步DP |
| 同一次更新跨平台DP | 已有显式梯度桥接协议 | 加权分母、一致skip、吞吐与故障域 |
| 跨平台PP | stage边界可序列化且开销可接受 | 双向activation/grad、权重版本、stage平衡 |
| 跨平台TP/CP/EP | 已证明细粒度通信与kernel协作 | 高频collective、layout与延迟约束 |

表中是设计空间，不是任何框架已默认提供的功能列表。
通常应先让每个平台内部形成可运行、可恢复的基线，再评估跨域边界。

某rank发现non-finite而跳过update时，同一同步模型的其他rank也必须形成一致决定。
异构执行不能破坏optimizer更新原子性。
重试、进程退出与checkpoint版本也需要共同协议，不能由各runtime独自推进。

## 25. 故障定位与六道自测

| 现象 | 优先证据 |
|---|---|
| 能import但算子失败 | 首个缺失op、dtype、shape、backend |
| 单设备正确、多设备漂移 | 全局分母、group、layout与归约dtype |
| 迁移后持续重编译 | shape、静态参数、sharding与cache身份 |
| 混合设备step极慢 | slowest rank、桥接copy、跨域collective |
| 权重可加载但下一步发散 | moments、参数排列、RNG/data与scheduler |
| 某平台更快但成本更高 | 冷编译、恢复、goodput与time-to-quality |

**题1：HIPIFY成功后能直接声称CUDA kernel已经高效迁移吗？**

不能。它解决部分源码转换，warp/layout、架构指令、尾部与实际kernel效率仍要验证。
应先证明输出和梯度，再观察目标设备的瓶颈。

**题2：两套库都有AllReduce，为什么不能直接混入同一group？**

名字只说明数学原语。communicator、buffer注册、runtime、transport和完成协议还需互操作实现。
torchrun启动成功不提供这些证明。

**题3：设备按64/32样本分工，局部mean梯度2和5应如何合并？**

按有效样本权重得到3，不能等权平均为3.5。
使用rank平均归约时，先按R*n_r/N修正局部mean；变长目标改用有效token数。

**题4：GSPMD能自动插通信，为什么还需要看IR？**

自动生成不保证拓扑最优，也不保证自定义op传播了期望布局。
要检查实际shard、临时复制和跨快慢网络域的collectives。

**题5：Neuron包也叫torch-neuronx，旧XLA示例能与原生neuron混用吗？**

不能凭包名混用。2.33明确把两条路径分开，API、版本谱系和运行约束不同。
应先选定路径，再核对对应训练与checkpoint文档。

**题6：weight、m、v重布局成功是否已经证明跨平台resume正确？**

没有。还需数据游标、scheduler、随机状态、量化状态与下一步更新验收。
应声明逐位、容差还是统计续训目标，并保存真实运行证据。
