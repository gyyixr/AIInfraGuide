## 1. TorchTitan 在训练栈中的位置

TorchTitan把PyTorch原生分布式能力组织成可阅读、可修改的大模型训练实现。
它连接模型定义、并行布局、数据、优化器、检查点与观测。
FSDP2、DTensor、DeviceMesh、pipelining和DCP是其依赖的运行时能力，不是TorchTitan自行重写的全部基础设施。
学习它的价值是看这些接口如何共享模型与状态契约。

本节核对官方仓库固定快照：

```text
repository: pytorch/torchtitan
commit: 6d9a92994be7942d82374592a5ebb42109648622
commit date: 2026-11-06 UTC
reading date: 2026-11-07
```

这是一份可重查的开发分支快照，不是稳定版本推荐。
官方README要求近期PyTorch nightly，并区分模型存在、debug配置与verified recipes。
本节没有安装TorchTitan，也没有运行GPU训练。
源码结论与下文CPU oracle分别标注。

### 1.1 一个重要的版本变化

此快照使用Python函数返回完整`Trainer.Config`作为recipe。
模型分片使用声明式`ShardingConfig`/`SpmdType`与相应桥接。
不能直接照搬旧教程的TOML配置、旧目录或运行时`parallelize_module`计划。
“同为TorchTitan”不代表配置和模型扩展接口没有变化。

## 2. 四层职责

| 层 | 此快照的代表入口 | 职责 |
|---|---|---|
| Recipe | `torchtitan_recipes`、`ConfigLoader` | 选择模型、布局与优化组合 |
| Trainer | `torchtitan/trainer.py` | 数据迭代、累积、验证、训练循环 |
| TrainingEngine | `torchtitan/training_engine.py` | 模型执行、optimizer、checkpoint生命周期 |
| 原生运行时 | FSDP2/DTensor/DCP等 | 分片、通信、状态序列化与执行 |

这个分层允许同一模型被不同训练任务使用。
但每种组合仍需检查capability与数值测试。
Recipe可以导入，不代表目标GPU、依赖与拓扑已经兼容。

## 3. 从启动到模型构造

固定`train.py:21—66`的主链是：

```text
ConfigLoader.load
  → config.build
  → Trainer
  → TrainingEngine
  → distributed runtime and meshes
  → model/optimizer/checkpointer initialization
  → load checkpoint
  → train loop
```

异常退出与正常退出都需要关闭trainer资源。
正常路径还销毁process group。
这是运行时生命周期，不只是模型forward脚本。

### 3.1 Meta 构造与真正分配

`TrainingEngine._initialize_model`在`torch.device("meta")`及SPMD上下文中构造模型。
Meta tensor描述shape、dtype和结构，尚未为完整数据分配真实存储。
然后根据PP或非PP路径应用并行转换。
最后`to_empty`分配目标设备存储，并调用权重初始化。

```text
architecture/config
  → meta model
  → layout / pipeline / FSDP transformation
  → materialize local storage
  → initialize or restore weights
```

先构造完整GPU模型再分片，可能在分片前就OOM。
Meta路径的意义是避免把“逻辑完整模型”误当作“每rank先完整驻留”。
但初始化函数、buffer与state-dict adapter必须支持这个顺序。

## 4. DeviceMesh 不只是几个数字

此快照`ParallelismContext._validate`验证：

$$
W=DP_{replicate}\times DP_{shard}\times CP\times TP\times PP.
$$

`dp_shard=-1`由world与其他维度推导，最后仍检查乘积一致。
EP不是额外乘在这个式子后面。
源码要求EP整除`dp_shard × cp × tp`的sparse region，再构造另一套专家视图。

三种视图在固定代码注释中明确区分：

```text
storage: [pp, dp_replicate, dp_shard, cp, tp]
dense:   [pp, dp, cp, tp]
sparse:  [pp, dp_replicate, edp_shard, ep]
```

其中数据加载用的`dp`折叠replicate与shard轴。
Loss统计还可能使用包含CP的视图。
不能拿任意group大小重复乘global batch。

## 5. 数例一：32卡如何记账

设DP replicate=2、DP shard=4、TP=2、PP=2、CP=1。
物理world为32，独立数据副本度为8。
若EP=4，它在已有sparse region中重分，不把world扩成128。

| 项目 | 结果 |
|---|---:|
| 物理GPU数 | 2×4×2×2=32 |
| 数据副本度 | 2×4=8 |
| 每TP/PP逻辑模型部分 | 全模型的约1/4，忽略不均衡 |
| FSDP存储分片度 | 此例为4，复制轴不再除一次 |

若教学模型总参数8B，假设模型状态合计18 bytes/param：

$$
M_{state/rank}\approx\frac{8\times10^9\times18}{TP\times PP\times DP_{shard}}
=9\times10^9bytes\approx8.38GiB.
$$

18B/param仅是显式假设，非TorchTitan默认内存承诺。
实际param/master/grad/moment dtype、optimizer和FSDP保留策略需要重新计算。
还必须加activation、临时all-gather、workspace、graph和通信buffer。
Dense与expert参数若使用不同分片域，应分别建账。

## 6. TP 与 FSDP2 是不同时间尺度的布局

TP决定算子执行时每rank负责哪些features/heads。
FSDP2决定参数等状态平时如何分片，并在计算前后进行所需gather/reshard。
一个TP shard内部仍可沿DP shard轴做FSDP。
这不是把同一个矩阵任意切两次后就结束。

以PyTorch Linear权重`[out_features,in_features]`为例：

- Column分片通常切输出维，即weight dim0。
- Row分片切输入维，即weight dim1。
- Row局部partial output还需要对应求和/布局转换。
- FSDP的存储分片与这些执行布局通过桥接组合。

此快照`decoder_sharding.py`把column的weight声明为`S(0)`、row为`S(1)`。
这是PyTorch权重方向，与数学`Y=XW`的行列命名要区分。
模型代码不该直接凭local tensor形状猜全局语义。

## 7. 模型扩展的真实接口

官方模型指南要求单设备语义清晰的模型类与嵌套Config。
结构参数、初始化、分片声明和state-dict adapter各有责任。

| 文件/能力 | 要检查 |
|---|---|
| `model.py` | forward语义、参数/非参数状态 |
| `flavors.py` | 结构变体、context与parallelism输入 |
| `sharding.py` | 每个边界的state/input/output布局 |
| `state_dict_adapter.py` | 外部权重命名、layout和精度 |
| optional pipeline | stage切分与通信边界 |

改变sequence或expert parallelism时，可能需要重建模型配置中的声明式布局。
仅修改recipe最后一个degree，不一定更新已经生成的model config。
固定官方配置指南明确提醒这一点。

## 8. 一次训练更新怎样经过 Trainer

`Trainer`按DP world/rank构建dataloader。
每个optimizer step组织gradient accumulation groups，每组又可以包含PP microbatches。
它汇总有效loss/routing token计数，再调用engine前反向和优化器。

```text
fetch microbatch groups
  → collect valid loss-token counts
  → forward_backward
  → optim_step
  → increment completed updates
  → checkpoint / validation / metrics
```

固定源码的token预算关系是：

$$
N_{step}=T_{micro,DP}\times M_{PP}\times A_{grad}\times D_{data}.
$$

这里$M_{PP}$是每组PP microbatch数量，不是PP stage数。
CP/TP复制或切分同一数学工作，不重复增加独立数据token。
变长packing还需使用实际loss mask计数，不能把padding全当有效目标。

## 9. 数例二：global tokens 与累积步数

延续32卡布局，数据副本度D=8。
设每DP rank每microbatch有2048 token，每组4个PP microbatch，累积2组。
则一个更新处理：

$$
2048\times4\times2\times8=131072\ tokens.
$$

如果目标更新token数不是`2048×4×8`的整数倍，固定Trainer会拒绝不一致配置。
把PP stage数2再乘进去，会错误得到262144。
如果其中10%为不参与loss的padding，实际有效目标数仍需从mask计数获得。

以下只用标准库，验证两个资源账本：

```python
from math import prod

degrees = dict(dp_replicate=2, dp_shard=4, cp=1, tp=2, pp=2)
world = prod(degrees.values())
data_degree = degrees["dp_replicate"] * degrees["dp_shard"]
sparse_region = degrees["dp_shard"] * degrees["cp"] * degrees["tp"]
ep = 4
assert world == 32 and data_degree == 8
assert sparse_region % ep == 0

state_bytes = 8_000_000_000 * 18 / (
    degrees["tp"] * degrees["pp"] * degrees["dp_shard"]
)
tokens = 2048 * 4 * 2 * data_degree
assert state_bytes == 9_000_000_000
assert tokens == 131072
print("world", world, "state_GiB", round(state_bytes/2**30, 3))
print("tokens_per_update", tokens)
```

CPU计算不能证明模型真的fit或能训练多快。
实际capacity先按每rank峰值验证，再比较有效tokens/s和质量。

## 10. DCP：完整恢复与权重导出分开

固定engine把model、optimizers、LR schedulers、可选EMA与extra states交给checkpointer。
`Trainer`明确把dataloader作为额外状态登记。
Engine自身`state_dict`保存completed step与ntokens_seen。
这比只保存模型参数更接近可恢复训练状态。

固定checkpointer文档区分：

```text
step-N: full resumable checkpoint
exports/step-N: model-only export
```

Model-only export不能当作完整训练resume。
自动恢复会优先考虑目录里已有的完整step checkpoint；显式初始权重路径可能因此被忽略。
切换run目录时需要核对实际load日志，而不是只看传入路径。

### 10.1 异步保存不等于参数立即可变

`TrainingEngine.optim_step`在更新前调用checkpointer的staging等待入口。
其目的之一是避免下一次更新覆盖仍被复制的状态。
DCP异步模式还区分staging future与save future。
CPU副本就绪、后台写出完成、metadata可恢复是不同完成事件。

恢复时也要拒绝不完整目录，而不是见到step-N名称就加载。
固定`base.py`对缺少完成metadata的checkpoint明确报错。

## 11. RNG 与数据恢复：不作超过证据的承诺

固定engine初始化会设置determinism与按mesh轴区分的seed。
已读默认checkpointer注册链明确包含model/optimizer/LR/EMA/train_state/dataloader。
本节没有据此证明任意Python、CUDA或自定义模块RNG都被自动保存。
因此不宣称所有配置或跨拓扑resume逐bit连续。

新增随机模块时，应核对其RNG是否属于model state、独立Stateful或可重建的counter协议。
数据恢复也要包含packing、shuffle、mixture和已消费游标的实际loader状态。
改变DP或数据集版本后，需验证全局样本语义而不只验证参数shape。

下面的CPU oracle演示“参数、游标、随机流一起恢复”的必要性，不复刻TorchTitan实现。

```python
import random
from copy import deepcopy

def run(state, count):
    rng = random.Random()
    rng.setstate(state["rng"])
    for _ in range(count):
        noise = rng.random()
        gradient = state["cursor"] * 0.01 + noise
        state["weight"] -= 0.1 * gradient
        state["cursor"] += 1
        state["step"] += 1
    state["rng"] = rng.getstate()
    return state

seed = random.Random(7)
initial = dict(weight=1.0, cursor=0, step=0, rng=seed.getstate())
continuous = run(deepcopy(initial), 10)
checkpoint = run(deepcopy(initial), 4)
resumed = run(deepcopy(checkpoint), 6)
assert continuous == resumed

bad = deepcopy(checkpoint)
bad["rng"] = initial["rng"]
bad = run(bad, 6)
assert bad["weight"] != continuous["weight"]
print("complete state resumes; resetting RNG changes trajectory")
```

## 12. Compile、remat 与实际集成边界

普通engine向模型并行化路径传入regional `local_compile`配置。
实验GraphTrainer可采用不同的whole-step编译契约。
Activation rematerialization、FSDP与CUDA Graph的顺序影响保存张量和地址生命周期。
不能把`compile=True`理解为整个step已经是一张可重复图。

完整实验应记录：

- 首次编译、steady-state和cache失效成本。
- Actual kernels、graph hit和shape变化。
- FSDP gather可见尾部与计算slowdown。
- Remat保存/重算张量和峰值内存。
- Checkpoint staging与更新之间的等待。
- Loss/梯度质量与固定输入的数值差异。

README的某一verified recipe并不承诺所有model×precision×parallelism组合。
AMD优化fork与上游CUDA路径也不能仅凭PyTorch设备抽象视为性能等价。
RTX3090上运行debug模型若可行，仍不能验证Hopper/Blackwell或多机特性。

## 13. 启动与源码阅读路径

固定README给出的debug入口形状是：

```bash
NGPU=1 ./run_train.sh
```

完整模型选择采用`MODULE`和`CONFIG`指定Python recipe，例如：

```bash
MODULE=torchtitan_recipes.models.llama3 CONFIG=llama3_8b ./run_train.sh
```

这些命令需在固定checkout、依赖与tokenizer准备好后运行；本节未执行。
首次实验应先打印完整配置，再核对world与recipe的并行乘积。
不要将旧`--section.option`形式套入此快照：固定配置指南明确不暴露通用此类覆盖。

推荐阅读顺序：

1. `config/README.md`与实际recipe：确定运行身份。
2. `train.py`→`trainer.py`：确定数据与更新边界。
3. `training_engine.py`：模型/optimizer/checkpointer初始化。
4. `parallelism_context.py`：物理world到不同mesh视图。
5. `decoder_sharding.py`与模型flavor：tensor布局契约。
6. `checkpointer/base.py`、`dcp.py`：恢复选择、完成与异步所有权。

## 14. 六道追问与答案

### Q1：TorchTitan只是FSDP2示例吗？

它把模型、并行、数据、优化器、检查点和观测组织成训练平台。
FSDP2只是其中一个基础能力。
每种模型与特性组合仍需独立验证。

### Q2：EP为什么没有再次乘进world公式？

此快照在已有sparse region中重构专家分组。
EP须整除相应区域，复用已有物理rank。
直接外乘会重复记账。

### Q3：Meta初始化省掉了哪些峰值？

它避免每rank先分配完整真实参数再分片的峰值。
后续materialize仍需本地参数、buffer和临时空间。
初始化与adapter不支持该顺序时仍会出错。

### Q4：FSDP2是否消除所有参数通信？

没有。
计算前需要相应权重视图，gather/reshard与梯度归并仍存在。
收益来自状态分片与可组合时序，实际通信由布局决定。

### Q5：已有checkpoint为何没有加载指定初始权重？

固定恢复规则优先已有完整step checkpoint。
应看load日志和run目录，区分resume与模型初始化。
Model-only export不能恢复optimizer和数据进度。

### Q6：固定seed能否证明resume完全复现？

不能。
要核对随机流当前状态、数据游标、packing、模型/优化器以及并行路径。
固定初始化seed只解决起点，不等于恢复中间状态。
