## 1. 同一张GPU为什么有多种通信身份

rank0可能同时属于一个TP组、一个DP×CP组、一条PP链和一个expert通信组。
这些group搬运不同数学对象，成员数相同也不能互换。

例如两个rank各持不同的矩阵列分片。
把它们误当DP副本，对相同下标的weight grad做SUM，可能成功返回却更新了错误参数。

因此process group既是运行时对象，也是模型布局的依赖。
组件需要明确声明“我消费哪一类group”，不能在深处任意使用WORLD。

本篇冻结`48a887fecd01674346f724dcf44f417f455989f0`。
2026-11-07读取固定git对象核对，不使用当前HEAD的实现替代。
这里动态hybrid CP的限制不代表其他release或其他框架的永久限制。

## 2. ProcessGroupCollection实际存什么

它是携带已有process groups的稀疏dataclass。
它本身不负责自动选择最优拓扑，也不因赋值创建NCCL communicator。

| 字段 | 数学/运行域 | 常见消费者 |
|---|---|---|
| tp | tensor parallel | 并行linear、SP |
| pp | pipeline parallel | activation/gradient P2P |
| cp | context parallel | attention上下文通信、MTP roll |
| dp | 独立数据副本 | 数据进度和部分控制逻辑 |
| dp_cp | DP与CP联合权重复制域 | dense grad归约 |
| tp_cp | TP与CP联合域 | 特定布局转换 |
| tp_dp_cp | TP、DP、CP联合域 | 部分FP8统计 |
| ep | expert集合分片 | dispatch/combine |
| expt_tp | 单个expert矩阵分片 | expert linear |
| expt_dp | 相同expert shard副本 | expert grad与state |
| embd、pos_embd | 共享embedding相关stage | 特殊梯度同步 |
| intra_dp_cp、inter_dist_opt | optimizer实例的分层通信域 | partial DistOpt |

`dp_cp_ag`与`expt_dp_ag`还允许为参数AG提供独立通信域。
字段名不能代替成员校验：应该打印每个group对应的global rank列表。

## 3. 稀疏字段与构造校验

字段声明使用`init=False`，但类实现了自己的`__init__(**kwargs)`。
因此既能先构造再赋值，也能把已知字段作为关键字传入。

未知字段立即抛ValueError。
没有传入的字段不一定存在，不能默认它已经被自动补成正确group。

`repr`只列出存在的字段及size，并区分None和group列表。
它适合快速检查依赖，但不会证明组成员正确或collective顺序一致。

```text
组件收到pg_collection
  → 检查required字段是否存在
  → 检查None是否被该路径允许
  → 核对size与global ranks
  → 按组件自己的layout调用collective
```

“字段存在”与“字段可用”不同。
例如某些helper允许显式None表示没有额外optimizer实例通信。
另一些组件则必须拿到真实TP/CP group。

## 4. 最小required set从消费者反推

普通TP linear需要TP语义，不应顺手要求整个训练job的所有group。
MTP block默认legacy适配只请求`cp`和`tp`。
MoE还需要EP、expert TP/DP及组合域。

迁移一个插件时可以逐层建立下表：

| 操作 | 输入布局 | 必须使用的依赖 |
|---|---|---|
| column dgrad归约 | 同一输入的部分梯度 | tp |
| dense grad同步 | 同一参数、不同样本或context贡献 | dp_cp |
| expert grad同步 | 同一expert shard的副本 | expt_dp |
| MTP左移边界 | 同一序列的zigzag切片 | cp |
| PP收发 | 相邻逻辑stage | pp |

然后把最小集合传给组件。
缺字段应在构造阶段失败，避免第一个collective才卡住。

但不能给每个消费者套同一份万能validator。
固定optimizer helper要求dp，并根据实际CP、expert配置决定fallback是否允许。
它还处理Gloo control groups与partial optimizer instances，规则比一个TP层更复杂。

## 5. Legacy适配做了什么

`ProcessGroupCollection.use_mpu_process_groups(required_pgs=[...])`读取旧`parallel_state` getter。
它先验证请求字段名，再只调用相应getter，返回一个collection。

不传required_pgs时会请求全部已知字段。
对只需要TP的组件，这会增加不必要的初始化前提。

适配器是渐进迁移工具：

```text
训练入口仍初始化legacy parallel_state
  → 适配为显式collection
  → 新组件接收collection
  → 组件内部逐步移除global getter
```

它不自动删除旧全局状态，也不保证被调用的第三方模块已经完成迁移。
源码审查要继续搜索组件内部的WORLD和`parallel_state.get_*`。

少量job级控制决策可以有意使用WORLD。
例如全job一致退出与健康判断。
应记录理由，而不是机械认为每一次WORLD出现都是错误。

## 6. 一个最小依赖验证示例

下面是标准库教学模型，不是Megatron API的替代实现。
它验证字段名、required集合和成员身份；真实PG仍要由分布式启动器创建。

```python
ALLOWED = {"tp", "pp", "cp", "dp", "dp_cp", "ep", "expt_tp", "expt_dp"}

def validate_pgs(pgs, required, rank):
    unknown = set(pgs) - ALLOWED
    missing = set(required) - set(pgs)
    if unknown or missing:
        raise ValueError(("unknown", unknown, "missing", missing))
    for name in required:
        members = pgs[name]
        if members is None or rank not in members or len(set(members)) != len(members):
            raise ValueError(("invalid members", name))
    return True

assert validate_pgs({"tp": (0, 1), "cp": (0, 2)}, {"tp", "cp"}, 0)
for bad in ({"tp": (0, 1)}, {"tp": (0, 1), "cp": (2, 3)}):
    try:
        validate_pgs(bad, {"tp", "cp"}, 0)
    except ValueError:
        pass
    else:
        raise AssertionError("invalid collection passed")
print("required fields and rank membership: PASS")
```

此例无法识别“合法成员但数学含义用错”的group。
例如把dp_cp字段填成另一个包含rank0的错误组，还需要独立拓扑reference验证。

## 7. RankGenerator把rank当多维坐标

给定按变化快慢排列的轴大小s_0,...,s_(n-1)。
轴j的stride为之前轴大小的乘积：

$$
a_0=1,\quad a_j=\prod_{i<j}s_i,
\qquad r=offset+\sum_j x_ja_j.
$$

反解时先减offset，再按stride整除和取模。
mask选择哪些坐标允许变化，其余坐标固定，就得到一个通信组。

例如mask选择`dp-cp`，不是把DP列表与CP列表简单连接。
它枚举这两个维度的笛卡尔积。

固定RankGenerator补齐order中遗漏且size=1的维度。
如果遗漏的是size>1的维度，构造报错。
不同order可能得到不同global rank成员，不能只检查组size。

## 8. 同一个generator为何不允许EP和CP同时大于1

构造器明确断言`ep==1 or cp==1`。
这限制的是一次rank坐标分解，不是整个训练job的所有计算阶段。

初始化实际创建两套视图：

$$
W=TP\cdot CP\cdot DP\cdot PP,
$$

$$
W=ETP\cdot EP\cdot EDP\cdot PP.
$$

dense generator固定EP=1。
expert generator固定CP=1，使用ETP替代其中的TP维度。
两者描述相同的W张卡。

若把两个等式的所有维度再相乘，会重复计算设备。
Parallel Folding正是让不同子图选择不同分解。

## 9. 数例一：32张卡的双视图

dense取TP2、CP2、DP4、PP2。
order为`tp-cp-ep-dp-pp`，其中EP=1。

$$
r=t+2c+4d+16p.
$$

| 组的第一例 | global ranks |
|---|---|
| TP | [0,1] |
| CP | [0,2] |
| DP | [0,4,8,12] |
| DP×CP | [0,2,4,6,8,10,12,14] |
| PP | [0,16] |

expert改用ETP1、EP4、EDP4、PP2，CP固定1。

$$
r=e+4d_e+16p.
$$

第一EP组为[0,1,2,3]，第一EDP组为[0,4,8,12]。
PP组仍是[0,16]。

rank3在dense视图是t1,c1,d0,p0。
同一rank在expert视图是e3,d_e0,p0。
从attention进入expert子图时，不能沿用dense TP身份猜expert权重布局。

## 10. 两套PP组为什么必须相同

同一条pipeline要把dense与expert层按同一深度边界连接。
如果两种视图把PP邻居定义成不同设备，模型构造与传输就失去共同协议。

冻结初始化会比较两个generator生成的完整PP rank列表。
它还限制非pp-last order下的数据并行度关系。

因此两套乘积都等于W只是必要条件。
还必须满足PP组一致、shape整除、模块支持和物理放置要求。

将TP放NVLink域是常见起点，但global rank连续不自动意味着物理相邻。
需要额外记录rank→host→local GPU→NIC映射。

## 11. 可运行CPU oracle：生成正交组

这个程序没有导入Megatron，避免把被验证实现同时当reference。
它用坐标枚举验证组覆盖、32卡双视图和rank反解。

```python
from collections import defaultdict
from itertools import product
from math import prod

def groups(sizes, varying, offset=0):
    names = list(sizes)
    dims = list(sizes.values())
    assert len(set(names)) == len(names) and all(n > 0 for n in dims)
    assert set(varying) <= set(names)
    strides = [prod(dims[:j]) for j in range(len(dims))]
    result = defaultdict(list)
    for coord in product(*(range(n) for n in dims)):
        rank = offset + sum(x*s for x, s in zip(coord, strides))
        decoded = tuple((rank-offset)//s % n for s, n in zip(strides, dims))
        assert decoded == coord
        key = tuple(x for name, x in zip(names, coord) if name not in varying)
        result[key].append(rank)
    output = sorted(sorted(v) for v in result.values())
    assert sorted(r for g in output for r in g) == list(range(offset, offset+prod(dims)))
    assert all(len(g) == prod(sizes[n] for n in varying) for g in output)
    return output

dense = dict(tp=2, cp=2, ep=1, dp=4, pp=2)
expert = dict(tp=1, cp=1, ep=4, dp=4, pp=2)
assert groups(dense, {"tp"})[0] == [0, 1]
assert groups(dense, {"cp"})[0] == [0, 2]
assert groups(dense, {"dp", "cp"})[0] == list(range(0, 16, 2))
assert groups(expert, {"ep"})[0] == [0, 1, 2, 3]
assert groups(dense, {"pp"}) == groups(expert, {"pp"})
assert groups(dense, {"pp"}, offset=32)[0] == [32, 48]
print("orthogonal groups, rank inverse and folded PP agreement: PASS")
```

CPU集合相等不代表真实group创建无死锁。
实际创建必须遵守后端要求的参与者、顺序和资源生命周期。

本轮还从冻结git对象提取`generate_masked_orthogonal_rank_groups`纯函数，与这个独立枚举器交叉比较。
三轴大小各取1/2/3，遍历6种order与8种mask，共1296种组合全部一致。
这个结果验证rank代数，不包含PyTorch进程创建或NCCL运行。

## 12. Group创建顺序也属于协议

固定代码优先创建DP×CP相关组，并说明SHARP的collective次序约束。
数学上嵌套的groups不意味着可以任意交错创建或执行。

同样的成员可以属于不同communicator。
一个communicator上尚未完成的操作，可能影响另一个communicator的进度和stream依赖。

建议启动时输出统一清单：

```text
group名称与实例ID
global rank列表及本rank局部编号
backend与timeout
创建序号
对应tensor layout与典型collective
```

不要仅在故障rank打印自己的组。
需要比较所有参与者是否对同一字段和创建序号给出相同解释。

## 13. MultiModule怎样容纳不同grid

`MultiModuleProcessGroupCollection`保存`module_name → ProcessGroupCollection`。
还用`language_model_module_name`标识哪个模块是语言模型。

例如同rank同时运行encoder和LLM，可以给它们不同TP/CP/DP视图。
一个只运行encoder的rank可以把语言模型名称设为None。

冻结构造拒绝空module_pgs。
如果给了语言模型名，却没有对应collection，也立即报错。
无LLM时调用`get_language_model_cp_size()`会失败，而不是猜一个全局CP值。

```text
rank0: encoder grid A + LLM grid B
rank1: encoder grid A + LLM grid B
rank2: 仅LLM grid B
```

这是多模块成员关系示意，不是一份可直接运行的拓扑配置。
colocated和disjoint grids还需要明确跨grid通信、桥接tensor布局及schedule支持。
collection只是记录依赖，不会自动完成encoder→LLM数据重排。

## 14. 两种容易混淆的“hybrid CP”

第一种是固定分层通信，例如节点内A2A、节点间P2P。
它把固定CP域拆成适配物理网络的层级。
`hcp`字段可以携带层级group列表。

第二种是本篇`hybrid_cp_schedule.py`里的动态变长调度。
它根据sequence workload，从DP×CP资源域为不同样本安排不同CP size。

前者改变通信分层，后者改变样本的资源分配与执行时序。
两个名称相似，不能把前者的支持矩阵直接用于后者。

普通SP又是第三个概念：它复用TP域切activation布局。
不能把SP、固定CP和动态hybrid CP当成可随意互换的开关。

## 15. 动态CP的2幂资源公式

固定`BalancedCPScheduler.gpus_needed`使用每rank最大长度Lmax。
对于长度S的非空样本：

$$
c(S)=\max\left(1,2^{\lceil\log_2(S/L_{max})\rceil}\right).
$$

资源度数取1、2、4、8等，以匹配可用hybrid CP组大小。
它是最低所需CP的估算；调度器还可能为填充空闲资源扩大CP。

相对工作量估计为：

$$
w(S,c)=S^2/c.
$$

代码注释明确它不是精确FLOPs计算器。
它省略线性层、causal半三角常数、通信、kernel效率、padding等成本。

因此可用来排序和平衡，不能把w除以GPU峰值就当真实step time。

## 16. 数例二：相同token数不等于相同工作量

设Lmax=2048，可用资源总数为8。

| S | 最小c(S) | 每rank sequence量 | 相对w=S²/c |
|---:|---:|---:|---:|
| 1024 | 1 | 1024 | 1,048,576 |
| 2048 | 1 | 2048 | 4,194,304 |
| 4096 | 2 | 2048 | 8,388,608 |
| 8192 | 4 | 2048 | 16,777,216 |

后面三行每rank都约2048 tokens，但attention work相差4倍。
原因是每个query看到的全局上下文长度仍不同。

如果让8192样本用8个rank，其w变成8,388,608，与4096/CP2的估计相同。
代价是占用更多rank并改变通信，因此不能只按workload表宣布吞吐改善。

在8个rank中同时放8192/CP4、4096/CP2、两个2048/CP1，设备数刚好填满。
它们预计完成时间仍不均衡，长样本组会拖住下一轮协作。

这个例子只说明资源可行性与负载矛盾，不声称是冻结scheduler实际返回的最优分组。

## 17. 可运行CPU oracle：资源估算和边界

整数实现避免浮点log2在边界附近的精度问题。
它等价实现上述非空整数长度的2幂向上取整。

```python
def cp_needed(seq_len, max_per_rank):
    assert seq_len > 0 and max_per_rank > 0
    required = (seq_len + max_per_rank - 1) // max_per_rank
    return 1 << (required - 1).bit_length()

lengths = [1024, 2048, 4096, 8192]
degrees = [cp_needed(s, 2048) for s in lengths]
assert degrees == [1, 1, 2, 4]
assert cp_needed(2049, 2048) == 2
assert cp_needed(4097, 2048) == 4
work = [s*s//c for s, c in zip(lengths, degrees)]
assert work == [1048576, 4194304, 8388608, 16777216]
assert 8192**2 // 8 == 4096**2 // 2
assert cp_needed(32769, 2048) > 8  # 当前8-rank域不可直接承载
print("CP degree and relative workload:", list(zip(lengths, degrees, work)))
```

它不复刻`next_hdp_group`的bucket平衡、样本裁剪与资源复用算法。
完整调度还需检查每个样本ID、每轮资源归属及最终microbatch计数。

## 18. Scheduler的真实控制流

`get_groups_and_subsamples`先按长度排序，然后反复调用`next_hdp_group`。
内部按工作量组织bucket，尝试新资源或把样本交给较轻的已有资源组。
还会修剪、重新分配样本，以减少空闲GPU和长尾。

输出必须保留sample ID与长度的对应关系。
否则负载表正确也可能把错误label交给正确shape的计算。

训练schedule取得整个global batch的调度描述。
TP首rank取得数据，相关计数和metadata通过既定通信传播。
每rank可执行不同数量的subsamples，但控制面必须对group边界达成一致。

## 19. Barrier为何不能随意删除

一个group表示无需全域barrier就能共同执行的一段样本计划。
切换group时，参与同一sequence的rank集合可能改变。

快rank若提前进入下一集合，可能等待还在旧集合上的partner。
如果多个重叠集合的操作次序形成循环等待，会死锁。
单纯“有一个rank等得更久”本身不等于死锁，关键是依赖图有没有环。

固定实现每个非最后group末尾在DP×CP域barrier。
它保证进入新分组前，旧计划中的所有参与者已到达共同边界。

不要把barrier看成只用于测量的多余同步。
删除它之前必须证明新协议保持collective顺序和参与者一致。
把异步调用换成isend也不能自动消除逻辑依赖环。

## 20. 最后一个subsample与梯度同步

前面的group和subsamples位于`no_sync_func()`内。
最后group的最后subsample退出no_sync后执行，允许最终梯度同步。

这里的“最后”是调度后本rank实际执行计划中的位置。
不能把固定长度训练的microbatch下标直接套过来。

schedule累计有效token数，后续用一致的目标分母完成梯度归一。
若简单平均每rank loss，而各rank负责的有效token数量不同，会改变目标函数。

验收要同时核对sample ID并集、token count和grad。
只检查所有GPU都繁忙，无法发现样本重复或归一化错误。

## 21. 冻结动态hybrid CP的配置gate

`arguments.py`在hybrid_context_parallel开启时检查：

| 配置 | 固定限制 |
|---|---|
| pipeline_model_parallel_size | 不允许大于1 |
| enable_cuda_graph | 不允许开启 |
| use_megatron_fsdp | 不允许开启 |
| dataloader_type | 必须为single |
| calculate_per_token_loss | 必须开启 |

这些限制来自具体参数校验分支，不能只引用一张通用CP能力表。
MLA对非空local_cp_size的拒绝是另一道模型gate，见13.5。

已有组的大小、序列切分和packed metadata还必须可兼容。
一个S需要CP32、资源域却只有8张卡时，估算公式本身不会创造额外资源。
应在进入长训练前识别不可行输入或采用明确的替代策略。

## 22. 故障定位清单

| 症状 | 优先定位 | 反例/观测 |
|---|---|---|
| 构造缺字段 | required集合与legacy适配 | 移除cp字段应尽早失败 |
| group size正确但loss错 | global成员及tensor身份 | dense/expert视图交叉比对 |
| multi-module取错CP | language_model_module_name | 无LLM rank不可读取LLM CP |
| 动态CP切换后hang | group序号、partner、barrier | 所有rank第一处分叉 |
| token均匀但负载不均 | S²/c与实际attention work | 每样本长度、每rank时间 |
| 恢复后样本错 | sample ID、计划版本、游标 | 下一global batch并集 |

配置审计与真实NCCL测试应分开。
前者拒绝已知不合法组合；后者验证后端、stream和物理网络上的实际行为。

## 23. 六道自测与答案

**题1：ProcessGroupCollection会自动初始化NCCL吗？**

不会。它承载已构造group，并由consumer执行校验。
初始化顺序、成员、backend与销毁生命周期仍需外层管理。

**题2：缺cp字段时能总用dp代替吗？**

不能。CP处理同序列的切片，DP表示独立样本副本。
即便size相同，通信对象与梯度语义仍可能不同。

**题3：RankGenerator禁止EP和CP同时大于1，为什么整个job可以同时用？**

因为dense和expert分别用两套generator解释同一设备集合。
两套视图仍须满足PP组一致等额外条件。

**题4：S8192、Lmax2048为什么最少CP4，work却比S2048/CP1高4倍？**

每rank token数相同，但每个query需要处理更长的全局上下文。
按S²/c估计分别为16,777,216与4,194,304。

**题5：PG字段都传入后，就算完成legacy迁移吗？**

不算。深层模块可能仍读取global getter，绕过传入依赖。
需要用两套不同grid测试，并审查实际collective消费的group。

**题6：动态CP的barrier降低利用率，能直接删吗？**

不能。它是group成员变化的共同边界。
若要移除，必须设计并验证等效依赖协议，证明不存在跨集合循环等待。
