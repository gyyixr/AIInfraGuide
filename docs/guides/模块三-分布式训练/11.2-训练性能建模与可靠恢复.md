## 1. 设计并行方案需要三张账本

一套配置能启动，不代表它高效；一套配置速度快，也不代表训练目标和恢复状态正确。应把三个问题分开验收：

1. **正确性账本**：样本、梯度、参数副本和更新是否对应同一个目标。
2. **资源账本**：哪些状态在什么时候驻留，哪些通信暴露在关键路径上。
3. **恢复账本**：中断后能够恢复哪些状态，继续训练是否仍处理正确的数据。

本文所有 GB、毫秒和吞吐示例都是明确假设下的教学计算。除最后列明的仓库 CPU/Gloo 实验外，不将任何数值称作本机多 GPU 或生产训练测量。

## 2. 不再直接套用“每参数 16 字节”

设模型总参数量为 $\Psi$，先假设均匀 TP/PP 分割，某 rank 的逻辑模型分片为：

$$
Q=\frac{\Psi}{TP\times PP}.
$$

Embedding、输出层、共享参数和不均匀 stage 会使真实分片不完全平均，所以上式是第一轮估算。

本节选择以下具体混合精度布局：

| 状态 | 每参数字节 | 是否另有副本 |
|---|---:|---|
| BF16 工作权重 | 2 | 与 FP32 master 分开 |
| FP32 梯度累积缓冲 | 4 | 只计这份持久梯度，不另加一份持久 BF16 梯度 |
| FP32 master weights | 4 | 用于优化器更新 |
| Adam 一阶动量 | 4 | 与参数一一对应 |
| Adam 二阶动量 | 4 | 与参数一一对应 |

因此不分片时静态状态为 $18Q$ 字节。若梯度是 BF16、没有独立 master 或状态使用不同精度，公式都会改变。

普通 PyTorch FP32 参数配合 autocast，参数本身就承担高精度更新状态；不能再无条件加一份 FP32 master。显式将参数转 BF16 也不会自动保证 Adam moments 为 FP32。

## 3. 四种状态分片的手算比较

设 `Ψ=32B, TP=4, PP=4, DP=4`，共 64 个 rank，$Q=2\times10^9$。

仍使用上一节的精度布局，忽略 padding、临时聚合与激活：

| 分片策略 | 每 rank 静态状态公式 | 本例十进制 GB |
|---|---|---:|
| 全部状态复制 | $(2+4+12)Q$ | 36 |
| 只分 optimizer/master | $(2+4)Q+12Q/DP$ | 18 |
| 再分梯度 | $2Q+(4+12)Q/DP$ | 12 |
| 参数、梯度、optimizer 全分 | $18Q/DP$ | 9 |

这里把 master 与两个 moments 合记为 12 字节。表格描述**状态布局**，不绑定某个框架恰好使用哪条通信算法。

### 3.1 9 GB 不是 ZeRO-3/FSDP 的峰值

全分片后，用到某层时仍可能聚合完整参数；前后向需要激活，通信需要 buffer，优化器可能还有临时 workspace。

更合理的表达是：

$$
M_{peak}=\max_t\big[
M_{persistent}(t)+M_{activation}(t)+M_{parameter\ cache}(t)
+M_{workspace}(t)+M_{communication}(t)
\big].
$$

分别把每一项的独立最大值相加是保守上界，未必是实际峰值，因为它们可能发生在不同时间。

### 3.2 一次具体的驻留时刻

假设某时刻同时驻留：静态状态 18 GB、激活 12 GB、workspace 3 GB、通信 buffer 2 GB、额外预取参数 2 GB，总计 37 GB。

如果预算为 40 GB，看起来只剩 3 GB 余量；但碎片、分配器保留、其他 CUDA 库与下一次临时分配还没充分覆盖。不能只看平均 allocated 就判断不会 OOM。

应按加载、前向、反向、optimizer step、参数同步和 checkpoint 分阶段记录峰值，找到真正限制 microbatch 的阶段。

## 4. 让三个候选方案使用同样的训练任务

现在比较同一个 32B 稠密模型、64 GPU、global batch=512、每副本 microbatch=4。只分 optimizer/master，精度布局同上：

| 方案 | TP | PP | DP | 每 rank 模型分片 $Q$ | 静态状态 | 每 step microbatch 数 $m$ |
|---|---:|---:|---:|---:|---:|---:|
| A | 8 | 4 | 2 | 1B | 12 GB | 64 |
| B | 4 | 4 | 4 | 2B | 18 GB | 32 |
| C | 4 | 8 | 2 | 1B | 12 GB | 64 |

$m=B_{global}/(bDP)$，不能让每个候选都使用同一个 $m$ 后还声称 global batch 不变。

在均衡 stage、忽略通信的简单流水线模型中：

$$
f_{bubble}\approx\frac{PP-1}{m+PP-1}.
$$

A、B、C 分别约为 4.48%、8.57%、9.86%。这只能帮助筛选候选，不能直接判定 A 最优：A 的 TP 更大、矩阵分片更小，层内通信与算子效率可能更差。

### 4.1 可运行的账本程序

```python
model_parameters = 32_000_000_000
world_size = 64
global_batch = 512
micro_batch = 4

for name, tp, pp, dp in [("A", 8, 4, 2), ("B", 4, 4, 4), ("C", 4, 8, 2)]:
    assert tp * pp * dp == world_size
    assert global_batch % (micro_batch * dp) == 0
    q = model_parameters / (tp * pp)
    static_bytes = (2 + 4) * q + 12 * q / dp
    microbatches = global_batch // (micro_batch * dp)
    bubble = (pp - 1) / (microbatches + pp - 1)
    print(name, static_bytes / 1e9, microbatches, round(bubble, 6))
```

预期输出：

```text
A 12.0 64 0.044776
B 18.0 32 0.085714
C 12.0 64 0.098592
```

它只检查静态公式和假设空泡，没有模拟真实 schedule、激活峰值、重叠或 GPU 执行。

## 5. 通信量应先定义 dtype 和发送口径

以另一条明确的基线为例：某 DP 组有 4 个 rank，每个 rank 有 2B 个本地模型参数，对应 8 GB FP32 梯度，使用 ring AllReduce。

每 rank 的发送 payload 近似为：

$$
V_{send}=2\frac{DP-1}{DP}M_{grad}
=2\times\frac34\times8=12\text{ GB}.
$$

如果假设瓶颈有效单向带宽为 50 GB/s，纯带宽时间下界为 0.24 秒。还需计入延迟、消息分桶和实际网络路径。

这不是在说所有“只分 optimizer”实现都必须走一次完整 AllReduce。采用 ReduceScatter 梯度与 AllGather 更新后权重的实现，需要分别用梯度和参数字节数计算，不能沿用同一公式。

### 5.1 通信总时长不等于暴露通信时长

设 trace 中累计通信 kernel 时间为 6 秒，其中 4 秒与独立计算重叠，关键路径上只暴露 2 秒。把 6 秒全部加到 GPU 计算时间上，会重复计时。

反过来，不同 stream 时间重叠也不保证无成本：通信可能占用 SM、显存带宽或网络资源，导致原来的计算变慢。

性能模型应把通信分成“可隐藏部分”和“依赖链上无法隐藏的部分”，并用完整步骤的墙钟时间校准。

## 6. TP、PP、DP 三类暴露位置不同

| 通信类型 | 常见依赖位置 | 优化时要确认 |
|---|---|---|
| TP collective | 当前层某个算子前后 | 是否阻塞下一 GEMM、tensor 是否可分块 |
| PP 点对点 | stage 边界 | downstream 是否已就绪、buffer 是否可复用 |
| DDP 梯度 bucket | 对应参数梯度 ready 后 | 能否被剩余 backward 覆盖 |
| 参数分片 AllGather | 当前层计算前 | 预取是否足够早、是否增加峰值 |
| EP dispatch/combine | 专家计算两侧 | 远端 token 何时就绪、路由是否不均衡 |

不能预先断言哪一种一定最大。大参数短序列可能受到梯度同步限制；长序列可能被 Attention 和 CP 主导；MoE 还会受到动态专家负载影响。

一个最小 trace 应同时包含 CPU 与 GPU 事件，并标出 step、microbatch、pipeline stage、通信组和 tensor 大小。

## 7. 吞吐和 MFU 要共享同一计时边界

先定义有效 token 吞吐：

$$
\mathrm{tokens/s}=\frac{\text{统计窗口内实际计入训练目标的 token 数}}{\text{该窗口端到端秒数}}.
$$

输入 token、非 padding token、loss mask 有效 token 可以是不同数值。记录时应明确到底用哪个，不能通过增加 padding 把吞吐做高。

### 7.1 一个稠密模型的 MFU 教学计算

对参数相关矩阵乘法占主导的稠密模型，常用每 token 训练计算量近似 $6\Psi$。设上述 32B 模型每步有 $512\times4096=2{,}097{,}152$ 个有效 token，假设一步 16 秒：

$$
\mathrm{tokens/s}=131{,}072.
$$

再假设每 GPU 的对应精度**稠密**峰值为 $10^{15}$ FLOP/s，64 GPU 的模型 FLOPs 利用率估计为：

$$
\mathrm{MFU}\approx
\frac{6\times32\times10^9\times131{,}072}
{64\times10^{15}}
\approx39.32\%.
$$

这是人为给定峰值和耗时的计算示例，没有对应某款设备的本地测量。

### 7.2 什么时候不能直接使用 $6\Psi$

- 极长序列时，Attention 中随序列长度增长的部分不能忽略。
- MoE 不能直接用全部未激活专家参数乘 token 数。
- Embedding、输出词表、非标准结构与不同前后向算子需要具体计算。
- 重计算增加实际执行 FLOPs，但 MFU 的模型工作量口径通常不把重复工作当成新的有效训练量。

因此 MFU 与实际硬件 FLOPs 利用率、监控工具中的 GPU utilization 不是同一个指标。只有模型 FLOPs 公式、精度峰值和计时窗口一致时，跨实验比较才有意义。

## 8. 正确计时比多报一个小数位更重要

GPU kernel 异步执行，host 端 `time.time()` 包围一次 Python 函数可能只测到提交时间。可以使用设备事件测指定 stream 工作，也可以在合适同步边界测完整 wall time。

分布式步骤还需要考虑最慢 rank。平均 rank 时间可能掩盖真正决定步长的尾部；最好同时保留 max、p50 与分布。

稳态测量应包含 warm-up 后多个步骤；是否计入数据等待、eval、checkpoint 和日志必须写清。生产有效吞吐通常还需把周期性保存与故障损耗计入长期窗口。

### 8.1 用 Amdahl 定律判断优化上限

如果某 kernel 仅占原步骤 20%，将它加速两倍，理想端到端加速为：

$$
S=\frac1{0.8+0.2/2}\approx1.111.
$$

最多约 11.1% 的提升，不能把 kernel 的 2× 当作训练的 2×。如果该 kernel 原本已被通信隐藏，端到端收益还可能更小。

## 9. Checkpoint 首先是一个一致的训练时刻

一次可恢复训练的状态通常包括：

| 状态 | 缺失后可能发生什么 |
|---|---|
| 参数与必要 master weights | 权重不完整或精度更新路径改变 |
| optimizer moments 与 step | 后续更新不再等于连续训练 |
| scheduler / loss scaler | 学习率或溢出处理进度改变 |
| CPU/CUDA/并行 RNG 状态 | dropout、采样、数据顺序改变 |
| sampler / 数据游标 / consumed tokens | 重复或跳过数据 |
| TP/PP/DP/CP/EP 布局与模型元数据 | 无法解释每个 shard 的逻辑含义 |
| MoE 路由 bias 等额外状态 | 恢复后专家负载改变 |

如果在梯度累积中间保存，还要记录已经累积的梯度和 microbatch 位置，或者明确只支持在完整 optimizer step 边界保存。

保存参数在 step 100、optimizer 在 step 101、数据游标在 step 102 的组合，通常不是任何一次真实训练状态。

## 10. 分片写完与提交成功分开

下面是**协议设计示意，不是某个 DCP API 的逐行实现**：

```text
1. 在所有参与者上确定一致 step 与快照范围
2. 将要保存的可变状态隔离到一致的 staging 视图
3. 各 rank 写自己的临时 shards
4. 收集完成状态、大小与必要校验信息
5. 发布完整 manifest / committed marker
6. 只有新 checkpoint 可恢复后，才按策略清理旧版本
```

不能只看 rank 0 打印了“save done”。所用 API 可能要求多个 rank 共同参与，失败进程也可能没有写完必要 shard。

[PyTorch DCP 教程](https://docs.pytorch.org/tutorials/recipes/distributed_checkpoint_recipe.html) 展示了分布式状态保存/加载的协作方式；其 API 和返回值应按实际安装版本确认。

### 10.1 异步保存的两个完成边界

异步保存可分为：训练状态变成稳定 staging 副本，以及该副本写入存储。训练何时可以继续修改原 buffer、checkpoint 何时可用于恢复，是不同的问题。

不要在 API 返回后就假定磁盘文件已完整，也不要让后台写入线程持续读取正在被 optimizer 修改的张量。[异步 DCP 教程](https://docs.pytorch.org/tutorials/recipes/distributed_async_checkpoint_recipe.html) 应与所用版本一起阅读。

同时限制在途快照数量，否则 CPU/pinned memory 和存储队列可能持续膨胀。

## 11. 改变并行度后，恢复承诺也要改变

从 `TP=4, PP=4, DP=4` 改成其他布局，需要把参数和 optimizer 状态映射到新的逻辑分片。文件名叫 `rank_3` 不足以描述其中数据属于哪层、哪一段矩阵、哪个全局专家。

恢复器需要全局 tensor 名称、shape、分片 offset、dtype 和拓扑等元数据。MoE 还要区分本地 expert index 与全局 expert ID。

即使参数与 optimizer 成功重分片，rank 数量、归约顺序、RNG 分配和 sampler 布局的变化仍可能改变后续浮点结果与样本序列。

应区分四层承诺：可以加载、单步数值接近、统计效果可复现、逐 bit 续跑一致。后者的条件最严格，不能由前者自动推出。

## 12. 从小实验建立恢复信心

最小对照是：

```text
A：初始化 → step1 → step2 → step3 → 记录状态
B：初始化 → step1 → 保存 → 新对象/新进程恢复 → step2 → step3
```

比较每步的输入 ID、mask、loss、梯度、参数、optimizer moments、步数和数据游标。只比较最后的 loss 可能漏掉大部分状态错误。

本仓库提供真实两进程 CPU/Gloo 实验：

```bash
# 使用已经安装 PyTorch 的解释器，在仓库根目录执行。
python -m torch.distributed.run --standalone --nproc-per-node=2 \
  labs/distributed/ddp_lab.py \
  --output labs/distributed/results/latest-ddp.json
```

该实验使用不同 rank 有效样本数 3 和 5，验证全局归一化、`no_sync` 累积、统一梯度裁剪和三步 AdamW 更新对单进程 oracle 的一致性，并验证一份内存中的 model+optimizer 状态恢复。

它还实际执行 AllReduce、AllGather、ReduceScatter 与 All-to-All 的小输入检查。这里验证的是 CPU/Gloo 数值和控制流，不是 GPU/NCCL 吞吐、FSDP 分片峰值或磁盘分布式 checkpoint 事务。

## 14. 自测与参考答案

**1. 本节为什么是18字节而不是16字节？** 使用了 BF16 工作权重2字节、FP32累积梯度4字节，以及 master/m/v 三份FP32状态共12字节。精度布局不同，结果就不同。

**2. B方案的DP从4换为2，global batch和microbatch都不变，m如何变化？** 从32增至64；若不调整，实际global batch会改变。

**3. DCP能读取参数，是否证明精确恢复训练？** 不能。还要恢复optimizer、RNG、数据位置及额外状态，并检查执行布局与确定性条件。

**4. 单进程恢复oracle与连续训练一致，证明了什么？** 证明所测小模型的状态恢复和更新语义；没有证明多rank分片写入、崩溃一致性或硬件性能。

**5. 选择最终配置的顺序是什么？** 先验证目标与分组正确，再满足峰值预算，之后用同一工作量测关键路径，最后验证保存与恢复。
