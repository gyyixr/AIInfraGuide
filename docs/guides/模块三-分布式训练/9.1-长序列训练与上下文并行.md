序列从 8K 增加到 32K，并不只是“batch 里多四倍 token”。对于 dense Attention，QK 和 PV 计算可以增加到十六倍。单纯降低 batch 只能减少序列条数，无法继续切开已经只有一条的超长样本。

上下文并行把同一个样本的序列工作分给多个 rank，再用通信补齐局部计算需要的远端信息。它改变数据布局，不应改变模型允许看到的上下文或训练目标。

## 1. 先定义一个可核对的长序列

本节主要使用以下教学配置：

| 变量 | 含义 | 数值 |
|---|---|---:|
| $B$ | 序列数 | 1 |
| $S$ | 序列长度 | 32768 |
| $H_q$ | Query heads | 32 |
| $H_{kv}$ | KV heads | 8 |
| $d$ | 每 head 维度 | 128 |
| $H=H_qd$ | 隐藏宽度 | 4096 |
| $w$ | QKV 存储字节 | 2，BF16 |
| $C$ | CP degree | 4 |

所有 MiB/GiB 用 $2^{20}/2^{30}$ 字节；FLOPs 以一次乘加算两次操作。以下是形状与复杂度计算，不是任何 GPU 的性能测量。

## 2. 哪部分真的按平方增长

### 2.1 朴素 score 矩阵

如果显式保存每个 query head 的全部注意力分数：

$$
S_{attn}\in\mathbb R^{B\times H_q\times S\times S}.
$$

假设它以 BF16 存储，大小为：

$$
M_{score}=B H_q S^2 w
=1\times32\times32768^2\times2
=64\text{ GiB}.
$$

这还只是一层的一份 score，不包括 softmax 输出、反向或其他激活。若内部以 FP32 物化，字节数再翻倍。

### 2.2 QKV 和输出是另一条曲线

$$
M_Q=B S H_q d w=256\text{ MiB},
$$

$$
M_K=M_V=B S H_{kv}d w=64\text{ MiB}.
$$

所以 QKV 共 384 MiB，Attention 输出与 Q 同规模，为 256 MiB。这些随序列长度线性增长。

GQA 的 KV heads 少于 Q heads，减少了 K/V 相关存储和通信，但并没有把每个 query head 对全序列的注意力需求消除。

### 2.3 FlashAttention 消除了哪一项

FlashAttention 通过分块和在线归一化避免把完整 $S\times S$ score 长期写到 HBM。它仍要保留输入、输出或其他反向所需统计量，因此显存不是零，但不必承担上面的 64 GiB 矩阵。

所以应该分别描述：

- 朴素 attention 中间矩阵可能平方增长。
- 使用 fused memory-efficient attention 后，主要保存激活通常按序列线性增长。
- 精确 dense attention 的 QK/PV **计算**仍是平方量级。

### 2.4 用纯 Python 核对单位

下面只核对形状算术，不分配相应的大 tensor：

```python
B, S, Hq, Hkv, d, width = 1, 32768, 32, 8, 128, 2
MiB, GiB = 2**20, 2**30
q = B * S * Hq * d * width
kv = 2 * B * S * Hkv * d * width
score = B * Hq * S * S * width
assert q / MiB == 256
assert kv / MiB == 128
assert score / GiB == 64
C = 4
assert ((C-1) / C * kv) / MiB == 96
assert ((C-1) / C**2 * (2*q + kv)) / MiB == 120
```

显式写出单位还能避免把 32 MiB 当成 32 MB 计算网络耗时。容量、字节量和带宽应先换到一致单位，再比较。

## 3. 计算量也手算一遍

忽略投影、softmax 和其他逐元素操作，非因果 Attention 前向的两个矩阵乘大致为：

$$
F_{attn}\approx4B H_q S^2d=4B S^2H.
$$

代入配置：

$$
F_{attn}\approx4\times32768^2\times4096
\approx17.59\times10^{12}\text{ FLOPs}.
$$

这是一层前向约 17.59 TFLOPs。因果 attention 若 kernel 能跳过被 mask 的上三角，主矩阵乘工作约减半，实际效率还取决于分块和边界。

当 $S$ 翻倍时，QKV 字节量翻倍，dense Attention 主计算翻四倍。分析长上下文瓶颈时，必须分别画出这两条曲线。

## 4. SP、CP 与数据并行

### 4.1 DP 处理不同样本

DP=4 可以让四个副本各处理不同序列。但当一条序列在单卡上都放不下时，把 batch 从 4 降到 1 后，继续增加 DP 无法自动切开这一条序列。

### 4.2 本文的 SP 特指 Megatron TP 配套方案

第 6 章介绍的 SP 让部分非 Attention 区域激活沿序列分片，并与 TP 的通信/布局转换结合。它不应简单等同于“每张卡独立做本地片段 Attention”。

### 4.3 CP 在更完整的序列计算路径中分配 token

CP rank 保留本地 token 的工作，Attention 阶段通过 KV 通信或布局转换访问远端上下文。线性层和逐 token 操作可以在局部序列上执行。

不同论文也把 Ulysses 等方法称作 sequence parallelism，因此比较实现时要写出形状和通信组，避免只按 SP/CP 名字推断机制。

## 5. Ring 风格：局部 Q，流动 KV

把序列分成 $C=4$ 块，每块 8192 token。每 rank 初始拥有：

```text
Q_local: [1, 8192, 32, 128]
K_local: [1, 8192,  8, 128]
V_local: [1, 8192,  8, 128]
```

本地 Q 为 64 MiB，K/V 各 16 MiB。每个 rank 让自己的 Q 依次处理四个 KV 块，将分块结果正确合并。

每 rank 做的是“$S/C$ 个 query 对全局 $S$ 个 key”，总计算约为单卡完整 Attention 的 $1/C$，不是 $1/C^2$。

### 5.1 前向每 rank 的发送量

完整 KV 大小为：

$$
M_{KV}=2B S H_{kv}d w=128\text{ MiB}.
$$

每块为 $M_{KV}/C=32$ MiB。若每个 rank 向邻居发送 $C-1$ 次，前向每 rank 发送量为：

$$
V_{ring,send}=\frac{C-1}{C}M_{KV}=96\text{ MiB}.
$$

每 rank 接收量同为 96 MiB。本节报告的是**发送字节**，不把发和收相加后再与同一单向带宽比较。

这个计数假设标准完整环传；causal 跳块、压缩、拓扑路由以及 backward 的额外数据另算。KV 双缓冲可以隐藏部分通信，也会占额外显存。

## 6. AllGather 风格：先取完整 KV

另一条简单路线是每 rank 保留局部 Q，先 AllGather 所有 K/V，再计算本地 query 行。

优点是容易建立数学基线，通信后可使用完整 KV；代价是每 rank 某个阶段会持有完整 KV，削弱了流式 Ring 方案的存储优势。

使用带宽优化 ring AllGather 时，逻辑发送量可以与前面的 KV 环传量相近，但“字节一样”不表示性能一样：

- AllGather 的完成等待和后续计算顺序不同。
- 完整 KV 的驻留峰值更大。
- 可用 attention kernel 和反向布局不同。
- 实际 collective 可能采用别的算法或拓扑映射。

通信原语名称不能直接替代时间线。

## 7. Ulysses 风格：序列分片换成 heads 分片

Ulysses 在 Attention 前使用 All-to-All 重排：

```text
每 rank: 局部序列 × 全部 heads
              ↓ All-to-All
每 rank: 完整序列 × 一部分 heads
              ↓ 本地 Attention
每 rank: 完整序列 × 一部分 output heads
              ↓ All-to-All
每 rank: 局部序列 × 全部 output heads
```

本例 $H_q=32,H_{kv}=8,C=4$，Attention 内部每 rank 得到：

```text
Q: [1, 32768, 8, 128]
K: [1, 32768, 2, 128]
V: [1, 32768, 2, 128]
```

一条完整序列只由部分 heads 计算，因此每 rank 工作量仍约是全量的 $1/C$。

### 7.1 为什么 GQA 的 KV heads 也重要

在直接均匀 head 分片方案中，heads 必须能按 CP 组划分。若只有 2 个 KV heads，却要求 4 个 rank 各拿独立的 KV head 子集，就无法原样划分。

有些实现会复制 KV、使用不同分组或结合 Ring，但那是额外设计，具有不同的显存和通信代价。不能只检查 Q heads 足够多就认定任意 GQA 模型支持任意 Ulysses degree。

### 7.2 每 rank 前向发送量

假设直接均匀 All-to-All，自己持有的 $1/C$ 部分不走网络，忽略布局拷贝和协议开销：

$$
V_{a2a,send}=\frac{C-1}{C^2}(M_Q+M_K+M_V+M_O).
$$

本例括号内为 $256+64+64+256=640$ MiB，所以：

$$
V_{a2a,send}=\frac3{16}\times640=120\text{ MiB}.
$$

其中进入 Attention 的 QKV 重排为 72 MiB，返回输出为 48 MiB。这只是相同假设下的逻辑发送量；不能据此直接断言比 Ring 的 96 MiB 慢。

### 7.3 “通信不随序列增长”的准确条件

固定 $C$、heads 和 batch 时，公式仍正比于 $S$。当 $S$ 与 $C$ 按比例增长，$S/C$ 近似固定，特定每 rank 通信量才体现出弱缩放优势。

[Ulysses 原论文](https://arxiv.org/abs/2309.14509) 的这类分析不能脱离“长度与设备数同时增长”的条件引用。

## 8. CP 怎样与 TP/PP/DP 组合

考虑正交的 dense 模型布局：

$$
N=D\times P\times T\times C.
$$

若 $D=2,P=2,T=2,C=4$，总共 32 个 rank。一个 DP 副本中的 $2\times2\times4$ 个 rank 共同处理其样本，而不是每个 rank 各读一份互不相关的数据。

有效全局样本数应按 DP 副本、每副本 microbatch 和累积次数计算。CP 把同一条序列拆成四份，不能额外把样本数乘四。

同一个参数 shard 可能在多个 CP 成员上复制，各自负责不同 token 的贡献。最终参数梯度需要按后端定义的归约组汇总。框架可能将 CP 与 DP 的相关归约合并；不要在框架已处理后再手工 AllReduce 一遍。

## 9. 长短不等时，loss 分母怎样处理

假设两个 CP rank 的有效监督 token 数分别为 3 和 5，其局部 token 梯度均值分别为 2 和 -1。全局 token mean 应为：

$$
g=\frac{3\times2+5\times(-1)}{3+5}=0.125.
$$

简单平均两个局部均值得到 0.5，已经是另一个目标。

正确实现可以先保留局部损失和，再结合全局有效 token 数归一化。若后端的梯度 collective 默认平均，还需要考虑该平均因子，避免多除一次并行度。

本例只讨论 token 权重；不要把 TP 上重复的 logits、PP 的不同层或已经聚合过的梯度再次作为独立样本计入分母。

## 10. 全局位置、标签与 packed sequence

### 10.1 Position ID 保留逻辑序列位置

S=16、C=4 时，rank 1 连续持有全局 token 4—7。若错误地重新编号为 0—3，远端 query/key 的相对位置关系可能改变，尤其是依赖位置编码的 attention。

位置是否在每篇文档重置由训练协议决定；CP 切分本身不能擅自改变这个协议。长上下文的 RoPE scaling 也应与原模型配置一致。

### 10.2 Next-token 标签跨越分片边界

如果 rank 0 持有输入 token 0—3，那么位置 3 的预测目标可能是 token 4，即下一个 rank 持有的输入。局部切片后再做 `labels = ids[1:]` 会漏掉边界目标。

可靠做法是先在逻辑完整序列上定义 target 与 loss mask，再按相同边界分发；也可以采用明确的边界标签交换协议。最后一个无后继目标的位置按任务约定屏蔽。

### 10.3 Packing 不等于允许文档互相注意

将多篇短文拼进一个 tensor，通常仍需记录 document/sequence 边界，使用 block-diagonal causal 语义或对应 varlen 接口。CP 后必须保留这些全局元数据。

仅按 rank 内局部下三角构造 mask，会同时造成两种错误：屏蔽合法的远端历史，或允许不同文档互相看到。mask 应由逻辑 token 所属序列和全局相对位置决定。

不要为了表达它而无条件物化一个全局 $S\times S$ 布尔矩阵，否则可能把 fused attention 已经省掉的内存又分配回来。

## 11. 工程选型与测量边界

| 需求/约束 | 先考虑的方向 | 必须测的指标 |
|---|---|---|
| 先验证数值正确性 | 单进程分块、低并行度完整 KV 基线 | 输出、loss、grad、mask |
| KV heads 足够且 All-to-All 链路好 | Ulysses 风格布局 | 重排耗时、真实网络流量、head 分片 |
| 需要跨更多设备扩展序列 | Ring 或分层组合 | overlap、因果负载、KV/dKV buffer |
| 长短序列混合 | packing、按长度分桶、适当 CP | 有效 token/s、padding、等待尾部 |
| 与 TP 同时启用 | 检查 TP 后实际 heads 和进程组 | communicator、张量布局、参数归约 |

Megatron Core 0.18.1 配置中分别列出 `sequence_parallel`、`context_parallel_size` 及分层 CP 配置；这说明它们不是一个互换的布尔开关。实际可用的通信模式仍要同时核对 Transformer Engine、attention backend 与模型结构。

## 12. 自测与参考答案

**1. 本例 score 为 64 GiB，是否说明 FlashAttention 也必须分配 64 GiB？** 不是。该数值描述显式物化的矩阵；FlashAttention 的关键就是避免长期物化它。

**2. CP=4 后每 rank 计算量为什么约为 $1/4$ 而不是 $1/16$？** 本地 query 变为四分之一，但每个 query 仍要关注全局 keys。

**3. Ulysses 为何要两次 All-to-All？** 第一次把局部序列/全 heads 转成全序列/局部 heads；第二次把输出还原成后续逐 token 层需要的序列分片布局。

**4. CP rank 增多，global batch 是否随之增大？** 不必。它们通常协作同一批逻辑序列；独立数据副本数由 DP 等数据调度决定。

**5. S=16、C=4，rank 0 的最后一个输入位置预测谁？** 在普通 next-token 目标中预测全局 token 4。必须保存这个跨 shard 的标签关系。
