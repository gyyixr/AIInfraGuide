## 本章解决的问题

模型看到的不是硬盘上的文档集合，而是经过一系列变换后、按照确定顺序进入优化器的有效 token。

例如，同一份 100 GB 文本经过两种去重规则，可能得到不同语言比例；再按文档等概率采样，会进一步偏向短文档。

即使训练配置中的混合权重没有改变，最终参与 loss 的 token 比例也可能变化。

因此本章以“样本身份”为主线。文档从哪里来、为什么被保留、怎样切成样本、在哪个更新中被消费，必须能够连接起来。

## 状态与不变量

| 阶段 | 必须记录的对象 | 验收问题 |
|---|---|---|
| 原始对象 | 内容哈希、来源、处理版本 | 能追溯与重新处理 |
| 规范化文档 | 文档 ID、去重簇、质量标签 | 不把同主题误当重复 |
| token 文档 | tokenizer hash、token 数、EOD 规则 | 词表与模型一致 |
| 逻辑样本 | 源、document span、offset、sample ID | 跨文档 packing 可解释 |
| rank 视图 | DP rank、全局游标、microbatch | 并集覆盖正确 |
| 已提交进度 | optimizer step、consumed samples/tokens | 恢复无不可解释重复遗漏 |

每一行都需要明确读写边界。

只记录最终配置，无法解释训练过程中的状态变化。

只记录运行日志，也无法在底层数据或代码发生变化后重新构造同一任务。

因此应保存不可变版本、运行状态和观测证据三类信息。

## 建议的学习顺序

第一篇推导 MinHash/LSH 与幂次采样，用三个数据源手算目标 token 配比及重复 epoch。

第二篇采用短整数序列，逐层展开三个索引、`S+1` 到 tokens/labels 的移位、文档边界和 sampler 的 DP 切分。

第三篇把 800 万 token/s 换算为 I/O 与 CPU 服务需求，说明平均带宽足够仍可能让同步训练等待。

代码示例优先使用标准 Python 来暴露算法，不依赖真实训练集、云凭据或多 GPU。

## 学完应能完成的任务

- 从一次异常 loss 反查 source、文档范围、tokenizer 和训练消费记录。
- 区分文档比例、样本比例、非 padding token 比例和 loss 权重。
- 解释同一个 EOD token 为何不能自动决定 attention、position 和 label 的全部语义。
- 按三索引手算样本，并说明 sample_index 为什么需要末尾哨兵。
- 用全局样本并集检查 DP 变化后的覆盖，而不是比较某个 rank 的局部序列。
- 拆开 queue wait、文件读、变换、collate、pinned copy 和 GPU wait。

## 从教程到实验的三步

1. 在纸上完成文中的小例子，写出期望输出。
2. 用CPU算法或固定shape检查验证索引、坐标和计数。
3. 在目标硬件与依赖下补全分布式正确性、性能和故障实验。

第三步应记录commit、容器、依赖、GPU、互联和数据版本。

增加GPU数量之前，先证明单步状态与恢复逻辑一致。

性能测量应有预热、计时边界、有效工作量和长尾分布。

任何跨拓扑变化都应重新检查数据映射、RNG与归约顺序。

## 本章交付物建议

- 一份带版本的配置与状态清单。
- 一组可以手算的小输入和期望输出。
- 一张源码入口到消费者的调用图。
- 一份按阶段保存的计数、摘要或时间戳。
- 一份正常路径与失败路径的验收记录。

这些产物帮助判断一次改动改变的是算法、布局、运行时还是平台。

它们也让恢复和迁移的限制可以被复核，而不依赖口头经验。
