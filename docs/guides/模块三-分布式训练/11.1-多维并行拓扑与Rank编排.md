## 1. 并行度乘起来正确，只是第一步

`TP=2, PP=2, DP=2` 使用八张卡，但它还没有告诉我们：rank 0 要和谁同步梯度，激活发给谁，哪两个 rank 共同计算同一层矩阵。

设计分布式训练时，需要回答三个不同问题：

- **逻辑切分**：数据、网络层、矩阵、序列各分给谁。
- **通信组**：哪个集合中的 rank 要参与同一个操作。
- **物理放置**：这些 rank 实际位于哪台机器、哪个 GPU、哪条 NIC 后面。

global rank 是通信命名空间中的编号，不是硬件拓扑本身。只有启动器和设备绑定建立映射后，才能判断“相邻 rank 是否走 NVLink”。

## 2. 明确本文的坐标约定

先不使用 CP、MoE 或其他额外轴。记：

- $T$：TP 大小。
- $P$：PP stage 数。
- $D$：DP 副本数。
- $(t,p,d)$：一个 rank 在三维网格中的坐标。

本文选择 TP 变化最快、DP 次之、PP 最慢：

$$
r=t+T(d+Dp),\qquad W=TPD.
$$

反向解码为：

$$
t=r\bmod T,\quad
 d=\left\lfloor\frac rT\right\rfloor\bmod D,\quad
 p=\left\lfloor\frac r{TD}\right\rfloor.
$$

这是一种明确的教学排列，不是所有框架不可更改的约定。改变 rank 顺序可以保持数学分组结构，却改变跨节点流量。

## 3. 八卡例子：把所有 rank 列出来

取 $T=P=D=2$：

| global rank | TP 坐标 $t$ | PP 坐标 $p$ | DP 坐标 $d$ | 解释 |
|---:|---:|---:|---:|---|
| 0 | 0 | 0 | 0 | 数据副本 0、stage 0、矩阵 shard 0 |
| 1 | 1 | 0 | 0 | 数据副本 0、stage 0、矩阵 shard 1 |
| 2 | 0 | 0 | 1 | 数据副本 1、stage 0、矩阵 shard 0 |
| 3 | 1 | 0 | 1 | 数据副本 1、stage 0、矩阵 shard 1 |
| 4 | 0 | 1 | 0 | 数据副本 0、stage 1、矩阵 shard 0 |
| 5 | 1 | 1 | 0 | 数据副本 0、stage 1、矩阵 shard 1 |
| 6 | 0 | 1 | 1 | 数据副本 1、stage 1、矩阵 shard 0 |
| 7 | 1 | 1 | 1 | 数据副本 1、stage 1、矩阵 shard 1 |

### 3.1 TP 组：固定数据副本与 stage

改变 $t$，固定 $(d,p)$：

```text
[0,1]  [2,3]  [4,5]  [6,7]
```

这些设备共同完成相同数据上的一部分层计算，持有该层不同矩阵 shard。它们不会因为有两张卡就自动看到两倍独立样本。

### 3.2 DP 组：固定逻辑参数位置

改变 $d$，固定 $(t,p)$：

```text
[0,2]  [1,3]  [4,6]  [5,7]
```

例如 rank 0 和 2 持有相同 stage、相同 TP shard 的参数副本，对不同数据计算梯度，再合并更新。

如果 rank 0 和 1 直接把各自不同 TP shard 的梯度按位置 AllReduce，就会把不同参数混合。通信 primitive 运行成功，也不能证明分组语义正确。

### 3.3 PP 组：沿网络深度连接

改变 $p$，固定 $(t,d)$：

```text
[0,4]  [1,5]  [2,6]  [3,7]
```

这些组为激活和反向梯度的阶段间传递提供通信关系。具体发送的是完整隐藏状态还是某种 shard，由 TP/SP 与流水线布局协议决定，不能只根据 PP 组成员推断 tensor shape。

## 4. 用标准库生成并核验分组

```python
from collections import defaultdict

T, P, D = 2, 2, 2
coords = {}
for p in range(P):
    for d in range(D):
        for t in range(T):
            rank = t + T * (d + D * p)
            coords[rank] = (t, p, d)


def groups_for(axis):
    groups = defaultdict(list)
    for rank, coordinate in sorted(coords.items()):
        fixed = tuple(v for i, v in enumerate(coordinate) if i != axis)
        groups[fixed].append(rank)
    return list(groups.values())


tp_groups = groups_for(0)
pp_groups = groups_for(1)
dp_groups = groups_for(2)
assert tp_groups == [[0, 1], [2, 3], [4, 5], [6, 7]]
assert pp_groups == [[0, 4], [1, 5], [2, 6], [3, 7]]
assert dp_groups == [[0, 2], [1, 3], [4, 6], [5, 7]]
for group_set in (tp_groups, pp_groups, dp_groups):
    assert sorted(r for group in group_set for r in group) == list(range(8))
print("TP", tp_groups, "PP", pp_groups, "DP", dp_groups)
```

这个程序验证坐标和分组集合，不创建 process group，也不验证 NCCL 通信性能。

## 5. 实际创建组时还有执行顺序

如果使用 `torch.distributed.new_group`，必须遵守所用版本的全局参与和创建顺序要求。下面是**需要由八进程启动器调用的结构片段**，本节不将它标为已运行：

```python
# tp_groups / pp_groups / dp_groups 来自上面的确定性生成器。
# dist.init_process_group(...) 和设备绑定应已完成。
for group_set in (tp_groups, pp_groups, dp_groups):
    for ranks in group_set:
        group = dist.new_group(ranks=ranks)
        if dist.get_rank() in ranks:
            local_groups[tuple(ranks)] = group
```

这里让所有进程按相同顺序走完整个创建列表，即使某进程不是当前组成员。具体优化选项与后端例外应查 [PyTorch process group 文档](https://docs.pytorch.org/docs/stable/distributed.html#torch.distributed.new_group)。

常见错误是每个 rank 只按自己的局部顺序创建所属组，或某些 rank 因数据为空跳过后续 collective。结果可能是死锁，而非明显的 shape 异常。

## 6. Global batch 由独立数据副本决定

设每个 DP 副本一次 microbatch 包含 $b$ 条序列，每次 optimizer step 消费 $m$ 个 microbatch，则：

$$
B_{global}=b\,m\,D.
$$

八卡例子取 $b=2,m=4,D=2$，得到全局 batch 为 16 条，而不是乘全部 8 张卡得到 64 条。

TP rank 处理同一样本的矩阵分片，PP stage 处理同一样本的不同层，它们不是新增样本副本。

如果每条序列长度相同为 $S$，理论输入 token 数为 $B_{global}S$；packing、padding、loss mask 和可变长度则要求直接数有效 token，不能仅用最大长度相乘。

## 7. 加入 CP：序列被切了，权重没有因此消失

常见稠密网格在不启用其他轴时写为：

$$
W=T\,C\,D\,P.
$$

本文扩展 rank 顺序为：

$$
r=t+T\left(c+C(d+Dp)\right).
$$

CP 组内的 rank 处理同一批序列的不同 token 区间；它们需要交换 Attention 所需数据，通常也共享同一逻辑权重。因此参数梯度最终还要覆盖这些序列切片的贡献。

在 Megatron 的一种组织方式中，权重梯度的归约组包含 DP 与 CP，即固定 TP/PP 后跨 `dp-cp` 的相关 rank 组合。**“权重副本组扩大”不等于“独立样本数扩大”**。

### 7.1 十六卡例子

取 `TP=2, CP=2, DP=2, PP=2`。第一个 PP stage 的 rank 0—7：

| 分组 | 成员 |
|---|---|
| TP | `[0,1] [2,3] [4,5] [6,7]` |
| CP | `[0,2] [1,3] [4,6] [5,7]` |
| DP | `[0,4] [1,5] [2,6] [3,7]` |
| DP×CP 权重副本域 | `[0,2,4,6] [1,3,5,7]` |

后一个 PP stage 的对应组给每个 rank 加 8。PP 组则连接相同局部坐标，例如 `[0,8]`。

## 8. EP 不能无条件再乘一次

MoE 层可能用与 Attention 层不同的并行网格。以下等式限定没有启用额外权重重物化轴、没有其他特殊布局：

$$
W=TP\times CP\times DP\times PP
=ETP\times EP\times EDP\times PP.
$$

这里 EDP 是专家权重的数据副本数；第二个等式描述专家阶段的布局，并不是在第一个网格上再买一组 GPU。

### 8.1 最容易理解的特例

当 `CP=1`、`ETP=TP` 时，可写成：

$$
DP=EP\times EDP.
$$

例如 `W=16, TP=2, PP=2`，稠密 DP 为 4。若专家 EP 为 2、ETP 仍为 2，则专家 EDP 为 2。

此时将 world size 写成 `TP×PP×DP×EP=32` 就重复计算了 EP 已占用的设备。

### 8.2 Parallel Folding 的含义

前面十六卡例子的 Attention 布局是 `TP2×CP2×DP2×PP2`；可以考虑专家布局 `ETP2×EP4×EDP1×PP2`，总设备仍为 16。

在第一个 stage，专家 EP 组可对应 `[0,2,4,6]` 和 `[1,3,5,7]`。它们共同覆盖四个专家分区，而不是四份相同专家权重。

Attention 和专家层的 token/权重布局不同，因此两者之间需要 dispatcher 和必要的布局转换。[MoE Parallel Folding 论文](https://arxiv.org/abs/2504.14960) 研究的正是这种按层采用不同网格的方式。

并不是任意满足乘积等式的组合都能运行。模型维度整除、group 顺序、SP、后端支持和参数布局还有额外约束。

## 9. 固定 Megatron 源码里的两个网格

静态核对快照：`NVIDIA/Megatron-LM@7d6895ac6a3ee9e16c53f573f363d2a52b88bf94`，核对日期 2026-10-30。

在 [`parallel_state.py`](https://github.com/NVIDIA/Megatron-LM/blob/7d6895ac6a3ee9e16c53f573f363d2a52b88bf94/megatron/core/parallel_state.py) 中，阅读顺序建议为：

1. `initialize_model_parallel()` 读取 world size 和并行参数。
2. 检查 dense 模型维度是否能整除 world size，得到 data parallel size。
3. 建立用于 token/weight 组织的 rank generator。
4. 用 expert TP、EP、PP 等重新计算 expert data parallel size。
5. 创建专家 rank generator，并检查两种布局的 PP 组一致性。
6. 创建具体 process group，区分 `dp`、`dp-cp`、`ep`、`expt_tp` 等职责。

该快照还包含 GTP/EGTP 等额外配置轴。本节将这些额外轴保持为 1，因此没有把完整源码所有组合压缩成一个永远适用的公式。若启用它们，必须重新按源码的实际约束建账。

## 10. 把逻辑组放进八节点集群

现在有八节点，每节点八 GPU，假设 global rank 0—7 在节点 0，8—15 在节点 1，以此类推。

### 10.1 方案 A：TP8、PP4、DP2

沿用 $r=t+T(d+Dp)$：

- 每个 TP 组正好占一台节点。
- rank $t$ 与 rank $t+8$ 是 stage 0 的一个 DP 组。
- 数据副本 0 的 PP 链跨节点 0、2、4、6。
- 数据副本 1 的 PP 链跨节点 1、3、5、7。

TP 通信留在节点内；DP 与 PP 通信走节点间。是否真正有高带宽 GPU 互联，仍要由拓扑检查确认。

### 10.2 方案 B：TP4、PP8、DP2

每个 stage 的两份 TP4 副本恰好放在同一节点：

- 节点内有两组 TP4。
- 同 stage 的 DP 组也可留在节点内。
- PP 链依次跨节点 0—7。

它减少了 TP 度数，但增加 PP stage 数。模型分片数 `TP×PP` 在两方案中都为 32，不代表激活、通信和空泡相同。

### 10.3 同一 global batch 下算一次空泡

设全局 batch 为 256，每副本 microbatch 为 4，DP=2，则 $m=256/(4\times2)=32$。

在均衡 stage、简单同步调度、忽略通信的近似下，空泡比例为：

$$
f_{bubble}\approx\frac{P-1}{m+P-1}.
$$

方案 A 为 $3/35\approx8.57\%$，方案 B 为 $7/39\approx17.95\%$。这只比较该简化模型的流水线空泡；B 的算子效率或通信可能更好，仍需完整时间账本。

## 11. 不要给通信量排一个永久顺序

“TP 最频繁，所以通信量永远最大”并不成立。TP 量取决于层数和激活形状，DP 取决于参数/梯度大小和同步时机，CP 取决于序列及 Attention，EP 取决于路由与 Top-k。

更可靠的比较表应写成：

| 维度 | 需要记录的量 | 影响暴露时间的条件 |
|---|---|---|
| TP | 每层 collective 的 tensor shape、次数 | 延迟、带宽、与 GEMM 的依赖 |
| PP | 每 microbatch 的激活/梯度边界 | stage 平衡、microbatch 数、P2P 重叠 |
| DP/分片 DP | 梯度与参数 bucket 的 bytes | bucket ready 时间、`no_sync`、预取 |
| CP | Q/K/V 或相关状态交换 | 序列长度、causal 布局、Attention 算法 |
| EP | 每设备路由 split 与 payload | 热点专家、节点流量、permutation |

TP 可以跨节点，代价是否可接受由网络和模型决定。DP 可能有多个梯度 bucket；分片 DP 还会在前后向中聚合参数，不能概括成“每步只通信一次”。

## 12. 自测与参考答案

**1. 八卡例子 rank 5 的坐标和三个组是什么？** 坐标为 `(t=1,p=1,d=0)`；TP `[4,5]`，DP `[5,7]`，PP `[1,5]`。

**2. 十六卡 CP 例子若 b=2、m=4，全局 batch 是多少？** DP=2，因此是16条序列。CP=2切序列，不能再把独立样本数乘2。

**3. CP=1、ETP=TP=2、PP=2、world size=16、EP=2 时 EDP 是多少？** `EDP=16/(2×2×2)=2`，dense DP=4。

**4. 两个方案 TP×PP 都为32，为什么性能可以不同？** 层内与层间通信位置、单层 GEMM 分片、激活驻留、空泡及物理链路都不同。

**5. 分组计算正确之后，还需要什么验证？** 检查实际设备映射、集体调用顺序、shape 与 dtype；再对固定输入比较 loss、梯度和更新，最后才测性能。
