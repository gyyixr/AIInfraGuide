## 1. TP 为什么还剩下完整复制的激活

基础 TP 将 Attention head 和 MLP 中间特征切开，但一个 Row Parallel 层完成 AllReduce 后，每个 rank 又拿到了完整的 `[b,s,h]` 输出。

接下来的 LayerNorm/RMSNorm、dropout、残差连接通常按 token 工作，不需要知道其他 token 的数值。让所有 TP rank 在相同 token 上重复计算并保存这些激活，会留下冗余。

Megatron 风格 Sequence Parallelism（本节简称 SP）利用这一点：在这些区域将 token 位置分片，进入需要完整 token 布局的 TP 计算区时再聚合。

它与第 9 章 Context Parallelism（CP）有关联，但不相同。这里的 SP **依附于 TP 组和算子布局**，没有自动把完整 Attention 的序列计算切成独立上下文块。

## 2. 先固定轴：序列维不是永远等于 dim=0

本节统一用 `[b,s,h]`：batch、sequence、hidden，序列维为 1。

Megatron 某些路径使用 `[s,b,h]`，序列维为 0。两者说的都是“沿 token 位置切”，不能不看 shape 就照抄 `Shard(0)` 或 `dim=0`。

取 $b=1,s=4,h=2,K=2$：

```text
完整 X = [[[1,10], [2,20], [3,30], [4,40]]]
rank 0 持有 token 0,1 → shape [1,2,2]
rank 1 持有 token 2,3 → shape [1,2,2]
```

每个 token 的两个 hidden 特征仍完整，因此本地能够计算该 token 的 RMSNorm。

如果同时把 hidden 轴也切开，归一化就不能只看本地片段，需要另一个归约设计。不同分片维度对应不同算法，不应混用。

## 3. 为什么归一化可以局部执行

RMSNorm 对一个 token 的隐藏向量 $x\in\mathbb R^h$ 计算：

$$
y_j=x_j\frac{\gamma_j}{\sqrt{\frac1h\sum_{k=1}^{h}x_k^2+\epsilon}}.
$$

求和发生在 hidden 维。SP 保留某些 token 的完整 hidden 向量，所以每个 rank 能独立计算自己 token 的归一化。

LayerNorm 还计算 hidden 均值，条件相同。残差加法是对应元素相加，也可以保持相同 token shard 直接完成。

### 3.1 归一化参数仍可能被复制

$\gamma\in\mathbb R^h$ 是所有 token 共用的参数，通常在 TP/SP 组内复制。不同 rank 处理不同 token，产生的是 $d\gamma$ 的部分贡献。

要恢复逻辑全序列的参数梯度，需要将这些 token 分片贡献求和。它与 MLP 内部互不重叠的权重 shard 不同。

是否由框架的特殊参数标记、DTensor 规则或单独 bucket 完成，取决于实现。**不要把 norm 参数从额外梯度归约中漏掉。**

## 4. 一对 MLP 的 SP 前向

基础 TP 的边界是：

```text
复制 X → Column → 局部激活 → Row 部分和 → AllReduce → 复制 Y
```

加入 SP 后可改成：

```text
序列分片 X
  → 本地 Norm
  → AllGather 序列，得到完整输入
  → Column 特征分片
  → 本地激活
  → Row 完整形状的部分和
  → ReduceScatter：先求和，再只保留自己的序列片段
  → 本地残差，得到序列分片 Y
```

关键不是对 AllReduce 的结果再调用一个独立 scatter，而是将“求和并分发结果分片”组织成 ReduceScatter，避免每卡都长期持有完整归约结果。

## 5. ReduceScatter 的具体数值

假设两个 rank 的 Row Parallel 部分输出分别为：

```text
rank 0 partial = [1, 2, 3, 4]
rank 1 partial = [10, 20, 30, 40]
```

逻辑完整输出为 `[11,22,33,44]`。ReduceScatter SUM 的输出：

```text
rank 0 → [11,22]
rank 1 → [33,44]
```

这一步不应再除以 TP 组大小。各 rank 原来计算的是同一矩阵结果的不同部分贡献，不是不同样本梯度的平均。

后续需要完整序列时，AllGather 得到 `[11,22,33,44]`。它只拼接已归约好的片段，不再求和。

把这两步与 DP 的“平均样本梯度”混在一起，会引入额外的 $1/K$ 缩放。

## 6. 反向也需要布局配对

一个简单的前反向对应关系是：

| 前向布局变换 | 反向需要的布局变换 |
|---|---|
| AllGather 序列 shard，供不同 TP 特征分支使用 | 将各分支输入梯度求和并 ReduceScatter 回原序列 shard |
| ReduceScatter 部分输出到序列 shard | AllGather 输出梯度，供各输入特征分支计算 |

必须结合“各分支是否产生不同梯度贡献”理解，而不是只记 `AllGather.backward = ReduceScatter` 这句口诀；若复制语义或目标函数不同，所需求和规则也会不同。

在本节 MLP 布局中：

```text
dY 的序列 shard
  → AllGather
  → Row backward，本地得到中间特征梯度
  → Column backward，得到完整输入梯度的部分和
  → ReduceScatter
  → 本地 Norm backward
```

这条链路解释了为什么 SP 不只是一种前向优化。自定义实现若只切前向 tensor，而反向布局仍按完整复制处理，会产生错误梯度或 shape 不匹配。

## 7. “通信量不变”成立需要哪些条件

设完整激活为 $A$ Bytes，$c=(K-1)/K$。理想 ring 下：

$$
V_{AR}=2cA,\qquad V_{RS}=cA,\qquad V_{AG}=cA.
$$

因此一个 AllReduce 与一个 ReduceScatter 加一个 AllGather 的理想每 rank 发送字节相同：

$$
V_{AR}=V_{RS}+V_{AG}.
$$

但实际执行时间未必相同：

- collective 调用位置和数量不同。
- 某些布局转换可融合，有些需要额外拷贝。
- 输入为非连续 tensor 时可能产生 packing buffer。
- 预取和计算重叠窗口不同。
- LayerNorm 等复制参数还可能需要额外小梯度归约。

所以正确表述是：**在相同张量大小和理想通信算法下，核心激活变换可保持近似字节量；实际关键路径需要测量。**

## 8. 激活显存到底能省多少

对某个原来在所有 rank 复制的 `[b,s,h]` 激活，SP 可将长期保存量由 $bshd_a$ 变成约 $bshd_a/K$。

取 $b=2,s=8192,h=4096,d_a=2,K=8$：

$$
A=2\times8192\times4096\times2=128\text{ MiB}.
$$

分片后每 rank 约 16 MiB，单个此类 tensor 减少约 112 MiB。

如果同一时刻需要保存 20 个这样的 tensor，差额可达到约 2240 MiB。但不能把“20 个”直接当成 Transformer 实际激活个数；框架可能融合、重计算或释放其中一部分。

### 8.1 为什么不能声称总激活一定减少到 1/K

总激活还包括：

- TP 已按特征分片的 MLP 中间值。
- Attention 所需 Q/K/V 与具体后端保存量。
- 聚合中的完整输入与通信 buffer。
- 未使用 SP 的 embedding、loss 或特殊模块。
- 重计算策略保留的边界状态。

SP 主要消除原有复制区域的冗余，**总模型激活缩放必须分项计算**。

## 9. SP 与 CP 的边界

以 4 个 token、2 个 TP rank 为例：

| 问题 | Megatron 风格 SP | CP 的关注点 |
|---|---|---|
| 非 Attention 区域的 token | 可以分片 | 通常也分片 |
| 进入 TP Attention 前 | 某些路径聚合完整序列 | 保持 Q/序列分块并交换所需 KV |
| 一个 rank 是否仍处理完整序列的部分 heads | 常见情况是 | 由 CP 算法决定，通常分散上下文工作 |
| 主要瓶颈 | 复制激活、norm/dropout 冗余 | 超长序列 Attention 的存储与计算 |

两者可以组合，但进程组、layout 和通信语义必须分别说明。看到配置字段叫 `sequence_parallel`，不能据此断言 Attention 的完整序列已按 CP 切开。

## 10. PyTorch 原生 TP 的布局表达

PyTorch TP 用 `parallelize_module` 和 ParallelStyle 表达权重及输入输出布局。以下是**模块片段**，假设模型已经定义了 `ffn.w1`、`ffn.w2`：

```python
from torch.distributed.device_mesh import init_device_mesh
from torch.distributed.tensor.parallel import (
    ColwiseParallel, RowwiseParallel, parallelize_module,
)

# 进程组、device 绑定、相同模型初始化应已完成。
tp_mesh = init_device_mesh("cuda", (tp_size,))
parallelize_module(
    model,
    tp_mesh,
    {
        "ffn.w1": ColwiseParallel(),
        "ffn.w2": RowwiseParallel(),
    },
)
```

两个类名中的 row/column 描述的是数学线性层布局语义。不要因为 `nn.Linear.weight` 的实际存储转置，就在使用官方 style 时再次手工交换它们。

### 10.1 加入 SP 的方案片段

以下沿 `[b,s,h]` 的 dim=1 分片；需要模型结构与计划键完全匹配：

```python
from torch.distributed.tensor import Shard, Replicate
from torch.distributed.tensor.parallel import (
    SequenceParallel, PrepareModuleInput,
)

sp_plan = {
    "norm": SequenceParallel(sequence_dim=1),
    "ffn": PrepareModuleInput(
        input_layouts=Shard(1),
        desired_input_layouts=Replicate(),
    ),
    "ffn.w1": ColwiseParallel(),
    "ffn.w2": RowwiseParallel(output_layouts=Shard(1)),
}
# parallelize_module(model, tp_mesh, sp_plan)
```

这不是任意 Transformer 的完整训练程序：还缺 embedding、attention、残差、输出/loss 的布局，以及具体实现对 local tensor/DTensor 返回值的选择。

特别是 `view`/`reshape`：普通本地 tensor 只知道 local head 数；DTensor 知道全局 shape。保留哪个表示，会影响后续形状计算。

## 11. GQA/MQA 对 head 切分的限制

假设模型有 32 个 query heads、4 个 KV heads，TP=8。Query 可以每 rank 分到 4 个 head，但 4 个 KV head 无法按整数均分成 8 份非空 shard。

可能的实现选择包括：

- 降低 TP 度。
- 在若干 rank 间复制某些 KV heads。
- 使用支持该布局的专用分组或映射。

不能默认“每个 TP rank 复制全部 KV heads”；具体复制因子与 head 映射由实现决定。

还需区分训练激活和生成 KV cache。相同 head 布局约束在两者中都可能出现，但内存生命周期与累计序列长度不同。

## 12. Dropout 与随机流

SP 改变 token 在不同 rank 上的位置；TP 改变中间特征的持有者。若所有 rank 简单重置同一随机 seed，可能导致不应相同的 dropout mask 被复制。

可复现实现需要按逻辑 tensor 位置和并行维度管理随机流，或者使用框架提供的 RNG tracker。不同并行布局下要求逐 bit 相同更难，不能只比较 `seed=123`。

数学等价检查初期可先禁用 dropout，确认前向、梯度和一次更新；再单独检查有随机算子的行为。

## 13. 分层验收，不只看 loss 会下降

| 层次 | 固定输入 | 要比较什么 |
|---|---|---|
| 本地数学 | 同一矩阵和权重 | 完整算子与分片重组的前向 |
| 反向 | 同一上游梯度 | 参数 shard 和输入梯度 |
| 真实通信 | 两个或更多进程 | collective 输出、shape、组成员 |
| 训练 | 同一全局 batch 与优化器 | 一步参数变化与参考误差 |
| 性能 | 固定硬件、精度、形状 | 显存峰值、暴露通信与吞吐 |

仓库 `labs/distributed/mechanics_lab.py` 提供逻辑 TP 前反向和 Ring 通信算例；另有真实 CPU/Gloo 进程实验。CPU/Gloo 能检查数据和参与者语义，不能证明 NCCL 性能、FSDP2 GPU 分片或 SP 加速已验证。

## 14. 自测与参考答案

**1. SP 下 RMSNorm 为什么可本地计算？**

因为每个本地 token 保留完整 hidden 维；归一化归约发生在 hidden 轴，不需要其他 token。

**2. ReduceScatter 部分激活时为什么通常不除以 TP 大小？**

这里是在求同一算子的不同特征贡献之和，不是在平均不同数据样本的梯度。

**3. SP 是否让所有激活都按 TP 度缩小？**

不是。只有适用布局的复制区域按序列分片；其他参数、激活、聚合 buffer 和 attention 状态应分别计账。

**4. Norm 参数在各 rank 复制，为什么梯度还要跨 SP 组汇总？**

各 rank 处理的是不同 token，同一 norm 参数收到不同 token 的梯度贡献，必须恢复逻辑整体的求和。

**5. 把一层接到下一层时最少要记录什么？**

全局 shape、本地 shape、被分片的维度、placement、是否为部分和、进程组和 dtype。
