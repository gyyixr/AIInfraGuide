## 本章要解决的问题

当单层矩阵或中间激活过大时，只分片优化器并不能拆开这次计算。TP 让多个 rank 合作计算同一个层，代价是层内的数据交换。

基础 TP 仍会在一些边界复制完整激活。SP 利用 norm、dropout、残差的 token 局部性，减少这些复制区域的长期保存量。

本章最重要的区分是：**一个本地 tensor 是全局 tensor 的 shard，还是完整输出的部分和？** 前者通常拼接，后者需要归约。

## 1. 固定数学与存储约定

本章数学表达为 $Y=XW$，其中 $W$ shape 为 `[输入维, 输出维]`。PyTorch `nn.Linear.weight` 存储轴相反，实际切 tensor 时要对应转换。

| 方案 | 切什么 | 本地输出含义 |
|---|---|---|
| Column Parallel | 输出特征轴 | 不同输出特征的 shard |
| Row Parallel | 输入特征轴，输入同步切分 | 相同输出索引的部分和 |

Column 后接逐元素激活，再接 Row，可以让中间特征一直保持分片，不必先收集又切开。

## 2. 前反向的通信位置

基础 TP 配对的规则为：

```text
Column 前向：输入已复制时，本地 matmul 即可
Column 反向：不同特征分支的 dX 需要求和
Row 前向：不同输入特征的部分输出需要求和
Row 反向：各自生成对应输入特征 shard 的梯度
```

所以不能写成“前向 AllReduce 原位对应反向 AllReduce”。必须跟踪逻辑值、复制语义和损失来源，避免反向多乘一个 TP 组大小。

## 3. 一个贯穿全章的矩阵结果

第 6.1 节使用输入 `[1,2]`，第一层中间结果 `[1,2,4,1]`，两张逻辑卡分别产生部分输出 `[1,2]` 与 `[6,3]`。

归约后输出为 `[7,5]`。给定上游梯度 `[1,-1]`，各卡输入梯度贡献为 `[1,-1]` 与 `[-3,3]`，总输入梯度为 `[-2,2]`。

这组数值同时检查列/行切分、ReLU、权重梯度及归约方向。只验证输出一致不足以证明 TP 反向正确。

## 4. Transformer 如何映射

Attention 的 Q/K/V 投影和 MLP 第一层通常采用输出特征切分；Attention 输出投影和 MLP 第二层组合各分片贡献。

SwiGLU 的 gate/up 两路必须使用一致特征范围。Row Parallel 的完整输出 bias 也不能在每个部分和里重复加一次。

GQA/MQA 下 KV head 数可能小于 TP 度，需要核对复制或分组策略；不能假定所有模型和 TP 配置都能均匀切分。

## 5. SP 用序列分片替换部分复制区域

典型 MLP 边界为：

```text
序列 shard → 本地 Norm → AllGather 序列
→ TP 线性计算 → ReduceScatter 输出 → 序列 shard
```

Norm 参数通常仍复制，而不同序列 shard 产生不同 token 贡献，因此它们的参数梯度需要相应汇总。

核心激活传输的理想字节量可与原 AllReduce 接近，但调用数、布局转换和重叠位置改变，实际耗时仍需测量。

## 6. SP 不能替代 CP 的全部工作

SP 主要减少非 TP 区域的激活复制；常见路径在 Attention 内仍处理完整序列的部分 heads。

CP 则针对超长上下文，把 Attention 的序列工作分散并交换所需 KV。两者可组合，但进程组、布局和通信各有自己的定义。

同样，SP 只使适用区域接近 $1/K$ 保存量，不能直接推出全模型激活也缩小到 $1/K$。

## 7. 带宽约束是经济性，不是合法性

TP 通信频繁，通常优先放在高带宽、低延迟域。但 TP 可以跨节点，也可以使用 PCIe 或其他网络；关键是切分后的计算效率和暴露通信是否值得。

当矩阵太窄、head 不足或通信延迟占主导时，继续增大 TP 可能降低吞吐。应同时检查显存、GEMM 效率和端到端时间。

## 动手与验收

1. 独立算出两层 MLP 的完整与分片前向。
2. 写出所有权重 shard 梯度和需要归约的输入梯度。
3. 对一个张量记录 global/local shape、placement、group、dtype。
4. 将 Row 输出 AllReduce 改为 ReduceScatter，跟踪后续 AllGather 和反向。
5. 检查 norm 参数、bias 和随机流有没有遗漏的同步语义。

`labs/distributed/mechanics_lab.py` 提供逻辑 TP 检查。CPU/Gloo 实验可检查 collective 数据流；真实 GPU TP/SP 的正确性与吞吐需要另外运行。

## 自测与答案

**Column 输出为何不一定需要立即 AllGather？** 下一层 Row 可以直接消费对应特征 shard。

**为什么不能对所有 TP 参数梯度求平均？** 不同 rank 通常持有不同逻辑参数元素；需要同步的是同一参数的对应副本或明确的部分贡献。

**SP 的序列维是不是永远 dim=0？** 不是；`[s,b,h]` 与 `[b,s,h]` 使用不同轴，必须先看 shape。
