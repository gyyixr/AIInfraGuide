## 本章概述

并行策略把同一个训练任务拆给不同 rank，而集合通信把局部结果重新组合。本章先解释输入输出语义，再把 Ring 展开到每轮的具体数字，最后讨论实际通信为何会慢、怎样正确计时。

重点不是记住“某种并行使用某个 API”，而是回答：每个 rank 初始拿着什么，结束时应该拿着什么，谁参与计算，谁只转发，以及比较带宽时使用了哪一种字节口径。

## 先建立语义表

| 操作 | 计算或搬运 | 输出归属 |
|---|---|---|
| Broadcast | 复制 root 的数据 | 所有参与 rank |
| Reduce(sum) | 对相同索引求和 | 指定 root |
| AllReduce(sum) | 对相同索引求和 | 所有参与 rank |
| AllGather | 按 rank 顺序拼接 | 所有参与 rank |
| ReduceScatter(sum) | 求和后分片 | 每个 rank 获得对应片段 |
| All-to-All | 源与目的之间交换不同分块 | 按通信契约重新分布 |

AllReduce 的 SUM 不等于平均。平均需要明确除以对应通信组大小；DDP 的梯度平均属于框架约定，不能将它推成每个 collective 的默认语义。

## 一个最小的手算目标

两个 rank 的输入为 `[0,1]` 和 `[10,11]`：

- AllReduce(sum)：两者都得到 `[10,12]`。
- ReduceScatter(sum)：rank 0 得到 `10`，rank 1 得到 `12`。
- All-to-All：rank 0 得到 `[0,10]`，rank 1 得到 `[1,11]`。

后两个操作输入相同，输出却完全不同：一个有归约，一个只有数据重排。后续 ZeRO 的梯度分片和 MoE 的 token 路由就是这两种机制的典型用法。

## 通信账本的共同约定

用 $M$ 表示完整通信张量的字节数，$N$ 表示组大小。理想 Ring 每 rank 的发送量：

$$
V_{AR}=2\frac{N-1}{N}M,\qquad
V_{RS}=V_{AG}=\frac{N-1}{N}M.
$$

其中 AllGather 的 $M$ 指聚合后完整数组，ReduceScatter 的 $M$ 指归约前完整数组。每 rank 接收量相同，发送加接收再乘二。真实数据宽度应来自通信 dtype，不直接拿参数个数当字节数。

每 rank 发送量随 $N$ 增加趋于上界，不意味着延迟、全网流量和跨机瓶颈不变。第 2.2 节用完整的延迟项与带宽项解释这个差别。

## 实验层次

1. **数学模拟**：标准库脚本逐轮记录 Ring 消息和结果，检查各阶段是否加法或复制。

3. **GPU/NCCL 扩展**：在自己的多 GPU 环境固定拓扑、版本、dtype、输入量和计时边界，再测吞吐。

## 学习验收与答案要点

- **能判断操作语义**：ReduceScatter 对同索引相加，All-to-All 只路由数据。
- **能手算 Ring**：先用三轮积累四个输入的和，再用三轮分发，AG 阶段不再次累加。
- **能区分带宽口径**：注明输入字节、发送/接收、algbw/busbw、GB/GiB。
- **能说明异步边界**：host 返回、入队、stream 依赖和设备完成是不同事件。
- **能定位 collective hang**：先找所有 rank 最早的异常，再查参与者、shape 和调用顺序。
