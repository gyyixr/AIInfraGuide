## 1. MaxText 不只是把 PyTorch 换成 JAX

MaxText是面向TPU/GPU的大模型参考训练与模型库。
它把JAX变换和XLA编译、Flax模型状态、Optax优化、Grain数据与Orbax检查点组合起来。
理解它需要同时追踪全局数组、设备分片和可编译训练函数。
不能只把PyTorch process group的名字逐一翻译成JAX参数。

本节固定官方仓库快照：

## 2. 生态组件各负责什么

| 组件 | 职责 | 不能自动保证 |
|---|---|---|
| JAX | grad/jit、数组与分片接口 | 任意Python副作用可编译 |
| XLA/SPMD编译 | 生成分区执行与通信 | 自动得到最优拓扑映射 |
| Flax NNX | 模型图与变量状态 | 所有状态都可遗漏后重建 |
| Optax/NNX Optimizer | 更新规则与优化器状态 | 只恢复参数就连续训练 |
| Grain | 数据处理与可保存迭代状态 | 任意数据源都支持相同恢复 |
| Orbax | 分布式检查点与恢复 | save返回即后台耐久完成 |

MaxText提供组合方式、模型实现与配置，具体能力仍是矩阵。
“支持GPU”和“某个TPU专用attention kernel能在GPU运行”不同。
版本、hardware、attention、packing与CP配置可能触发显式限制。

## 3. 三层布局：物理、逻辑、张量

物理mesh描述设备及命名轴，如data、fsdp、tensor、context。
逻辑轴给模型维度语义，如activation_batch、heads、embed。
规则把逻辑轴映射到物理mesh轴，再得到张量的PartitionSpec。

```text
devices and topology
  → named device mesh
  → logical-axis rules
  → tensor PartitionSpec / NamedSharding
  → compiler sharding propagation and collectives
```

此固定`base.yml`还包含stage、expert、tensor_sequence、diloco等轴。
不是每个轴都在每个任务中大于1。
应该检查已解析配置和实际mesh，而不是把所有参数名都乘起来。

### 3.1 NamedSharding 的含义

可将它理解为“某个mesh加某个tensor的分区说明”。
`PartitionSpec("fsdp", "tensor")`表示二维tensor的两个维度分别按这两个轴切分。
Mesh中未用于此tensor的轴，通常表现为该tensor的复制维度。
全局shape与本进程可访问的local shards是两种视角。

`None`表示该tensor维度不按相应mesh轴切分，不代表整个tensor在全部设备上复制。
若另一个维度已经分片，tensor仍然是分布式数组。
多host程序也不能把只在本机的device count当成全局mesh大小。

## 4. 数例一：8设备的输入与权重布局

取mesh `data=2, fsdp=2, tensor=2`，共8设备。
权重全局shape为`W[4096,8192]`，BF16每元素2字节。
它的全局逻辑容量是64MiB。

若教学存储布局为：

```text
W: PartitionSpec("fsdp", "tensor")
X[B,S,H]: PartitionSpec(("data","fsdp"), None, None)
```

则每设备W shard为`[2048,4096]`，容量16MiB。
Data轴未用于W，所以集群中有两份等价权重副本，总物理权重128MiB。
这与“64MiB除以8=8MiB每卡”不同。

若全局X为`[8,1024,4096]`，batch按data×fsdp四路切，则本地X为`[2,1024,4096]`。
Tensor轴的两设备共同处理同一数据片，不能算作两份独立样本。
计算Y=XW时，W的驻留K分片与X的batch分片还需布局转换或参数materialization。
具体插入AG/RS/其他通信应查编译后的HLO，不由这张表保证。

## 5. 从线性层推通信

设数学权重方向为 $W[H,F]$。
输出F按tensor切分时，每rank可计算一部分输出features。
输入H按tensor切分时，各rank产生同shape的partial output，需要求和或保留合法partial布局。

$$
Y=\sum_r X_rW_r.
$$

这与PyTorch Linear存储`[F,H]`的维度编号相反。
跨框架迁移时先固定数学方向，再谈row/column parallel。
NamedSharding表达布局，并不让数据依赖消失。

固定`logical_to_spec`按规则优先级映射，避免同一mesh轴被不合法重复分配到多个tensor维度。
未被规则分配的维度保留未切分状态。
模型作者仍需检查attention、vocab与MoE的具体logical axes。

## 6. ICI/DCN 与物理分层

MaxText配置区分ICI和DCN并行度，用于表达较快域内与较慢跨域网络。
在TPU语境中常对应slice内互联与slice间网络。
GPU上必须按实际NVLink域、主机与NIC拓扑解释，不能把TPU物理结构原封不动搬过去。

常见初始思路是让高频TP通信留在高速域，跨慢域更多使用数据复制或较低频同步。
但这需要真实message形状、memory与batch约束。
编译器知道逻辑mesh，并不一定了解用户期望的全部机架/拥塞成本。
应保存设备排序、mesh shape和communication profile。

### 6.1 Auto 与 explicit 分片模式

此快照`base.yml`提供`shard_mode: auto/explicit`。
两者在约束传播、collective优化及可支持组合上有差异。
不能从“更explicit”推断一定更快，约束也可能阻碍某些融合。
应对比HLO、实际collective、内存和端到端step。

## 7. 当前 NNX 初始化链

`train_loop`调用`train_utils.setup_train_loop`，返回mesh、model、optimizer相关状态、iterator和checkpointer。
实际setup中的关键步骤包括：

```text
config.init_weights_seed
  → mesh from config
  → create_nnx_abstract_model
  → learning-rate schedule / optimizer transformation
  → nnx.Optimizer and TrainStateNNX
  → Orbax checkpointer
  → data iterator / loader
  → initialize or restore sharded training state
```

抽象模型保留shape和GraphDef，可用于规划，而不等于已有设备数组。
固定代码在相同slice的elastic retry中可能复用mesh和抽象模型。
Replica resize后重新编译或重建的条件仍需分别核对。

## 8. 一次 train step 的实际行为

当前`train_step`先`nnx.merge`恢复结构与状态视图。
普通路径拆出可训练参数、自定义梯度状态和其余状态，再用`jax.value_and_grad`计算loss及梯度。
梯度累积则进入单独函数，不是简单重复调用完整optimizer update。

```text
GraphDef + State + batch
  → merge / differentiate
  → gradients and auxiliary state
  → clipping / optional host-device transfer
  → apply_gradients
  → updated model + optimizer + persistent state
  → metrics
```

优化器更新由`TrainStateNNX.apply_gradients`转给NNX Optimizer。
它同时更新参数、optimizer state和step。
MoE溢出/skip-step等路径还有回滚或重放条件，不能只根据Python循环次数计有效更新。

### 8.1 RNG 不再照抄旧 dropout 参数教程

此固定NNX `train_step`明确丢弃兼容签名中的`dropout_rng`参数。
常规NNX路径的随机状态由模型持久变量承载；DiLoCo外层另有传入step key的路径。
因此不能概括“所有MaxText step都对同一个外部key做fold_in”。
读随机性时要追实际变量类型、状态转换和checkpoint保存，而不是只找函数参数名。

## 9. 数例二：分片后的 loss 不能平均各卡均值

四个数据片的有效token数为`[4,4,1,1]`。
各片loss总和为`[8,12,10,20]`。
正确全局token平均是：

$$
L=\frac{8+12+10+20}{4+4+1+1}=5.
$$

若先求各片均值再等权平均，得到：

$$
(2+3+10+20)/4=8.75.
$$

不等长packing、不同mask或多目标任务尤其容易触发这个问题。
固定MaxText loss/metrics路径携带`xent_sum`和`total_weights`等量，阅读时必须追到实际归一化边界。
设备分片只是执行安排，不应改变数学目标的权重。

下面同时验证布局容量与加权loss，均不依赖JAX：

```python
from math import prod

mesh = {"data":2,"fsdp":2,"tensor":2}
assert prod(mesh.values()) == 8
weight_shape = (4096,8192)
local_weight = (weight_shape[0]//mesh["fsdp"],
                weight_shape[1]//mesh["tensor"])
global_bytes = prod(weight_shape)*2
local_bytes = prod(local_weight)*2
assert global_bytes == 64*2**20
assert local_bytes == 16*2**20
assert local_bytes*8 == global_bytes*mesh["data"]

batch,seq,hidden = 8,1024,4096
local_batch = batch//(mesh["data"]*mesh["fsdp"])
assert local_batch == 2
counts = [4,4,1,1]
sums = [8,12,10,20]
correct = sum(sums)/sum(counts)
wrong = sum(s/n for s,n in zip(sums,counts))/len(counts)
assert correct == 5 and wrong == 8.75
print("local W",local_weight,"local X",(local_batch,seq,hidden))
print("global weighted loss",correct,"incorrect rank mean",wrong)
```

本例所有shape均整除。
真实非整除情况需检查padding、错误或placement调整策略，不能由此oracle推定支持。

## 10. JIT 签名与 memory donation

固定`train_utils.jit_train_step`为函数设置`in_shardings`、`out_shardings`、静态参数与`donate_argnums`。
其中donation允许编译器复用输入state的存储，减少峰值和复制。
它同时意味着调用方不能假设旧state数组仍可安全继续使用。

```text
old state ──donated──▶ compiled update
                         │
                         └──▶ new state
```

用于日志、检查点或回滚的旧状态若需要存活，应走支持的快照/复制协议。
不能在donation后持有旧数组引用并假设数据未变。
这与PyTorch view/allocator的术语不同，但同样是ownership问题。

## 11. 编译缓存与第三个成本数例

JAX首次调用可能发生trace、lowering、compile与autotune。
Persistent cache能在兼容调用间复用可执行物，但不是保存模型参数。
官方说明cache身份涉及计算、jaxlib、XLA flags与设备配置等条件。
同shape不保证跨硬件、拓扑或版本命中。

假设一项布局优化额外编译120秒，每step节省1ms。
需要约120000步才能摊平这笔额外编译成本。
若作业只跑10000步，即使steady-state快，总wall time仍可能更长。

```python
compile_extra = 120.0
saved_per_step = 0.001
break_even = compile_extra/saved_per_step
assert break_even == 120000

def total(steps, step_seconds, compile_seconds):
    return steps*step_seconds+compile_seconds

short_old = total(10000,0.050,0)
short_new = total(10000,0.049,120)
long_old = total(200000,0.050,0)
long_new = total(200000,0.049,120)
assert short_new > short_old
assert long_new < long_old
print("break_even_steps",int(break_even))
print("short_job",short_old,short_new,"long_job",long_old,long_new)
```

这是假设成本的CPU计算，不是MaxText benchmark。
实际要分别记录cold compile、warm-up、steady-state与重启cache命中。
共享cache还需可控写权限，不能让不可信主体写入被执行的编译产物。

## 12. Orbax v1 与完整恢复

此固定代码的标准checkpointer是`ocp.training.Checkpointer`。
`base.yml`明确区分已有run的完整resume、`load_parameters_path`和`load_full_state_path`。
后两者互斥，已有run checkpoint有自己的优先级。
因此“传了新模型路径却恢复旧run”可能是规则生效，而非权重转换错误。

`TrainStateNNX`同时持有model与optimizer。
为了兼容历史磁盘布局，保存转换保留params/step/opt_state结构，并把NNX持久非参数状态放入`nnx_aux`。
固定`train_state_nnx.py`明确包括rngs/dropout等不能丢掉的状态。
不应只提取params后宣称得到完整resume。
实际转换还区分持久变量与可重建的cache/intermediate。
旧checkpoint若缺少相应aux状态，兼容恢复可能保留新初始化值；模型改变后不再存在的aux也会被过滤并记录。
因此“成功load权重”仍不证明随机轨迹或数据语义完全连续。

### 12.1 数据迭代器的实际边界

固定`save_checkpoint`标准路径总会组织`items`状态。
只有满足Grain等对应条件时，代码额外把iterator保存为`iter`。
不能由“框架支持dataloader checkpoint”推断任意HF/TFDS/custom loader恢复完全相同。
改变数据源、DP或packing策略后应独立验证样本游标。

### 12.2 异步返回与耐久完成

固定save路径区分设备工作完成、阻塞D2H staging和后台写出。
`save_checkpointables_async`返回后，后台错误可能在下一次save/wait才显现。
最终保存或preemption处理需要等待完成。
只有能真实restore的状态才可用作恢复承诺。

## 14. 硬件、版本与性能反例

TPU ICI/DCN经验不自动适用于GPU的NVLink/NIC拓扑。
固定setup对GPU的某些attention+packing+CP组合有显式限制。
Pallas、cuDNN/TE或其他kernel路径也有独立硬件和dtype条件。
模型配置存在不代表所有kernel组合都有相同成熟度。

更强的sharding约束可能增加redistribution或阻碍fusion。
更大的fsdp度可以省常驻状态，却让频繁gather主导step。
同一mesh上warm cache更快，也不能外推到频繁重编译的短作业。
官方MFU数字需连同有效token、FLOPs公式、精度和设备解释。

## 15. 六道追问与答案

### Q1：NamedSharding的数组shape是本地shape吗？

JAX分布式数组保留全局shape语义，设备上持有相应local shards。
应区分全局容量、addressable shards与未分片轴的复制。
本节8设备例子因此不是简单全参数除以8。

### Q2：声明layout后是否无需关心通信？

仍需检查相邻算子的输入输出布局是否兼容。
编译器可能插入AG、RS、A2A或其他重分布。
实际HLO和profile决定成本，不只看PartitionSpec。

### Q3：为什么不能平均各rank的loss均值？

有效token数可能不同。
应按目标定义汇总loss分子与有效权重分母。
等权平均rank均值会改变数学目标。

### Q4：当前NNX路径是否每步都消费外部dropout_rng？

此固定常规train_step明确未使用该兼容参数。
应追模型持久随机变量和NNX状态，特殊DiLoCo路径另看。
旧Linen示例不能直接作为当前答案。

### Q5：完整checkpoint和编译cache能互相替代吗？

不能。
前者保存模型/optimizer/随机与数据进度，后者保存执行产物。
二者失效条件、权限和恢复作用都不同。

### Q6：主分支能读，为什么仍不直接推荐生产？

官方README明确提示main不是生产稳定承诺。
本节固定commit用于源码可复核；部署还需release/容器、依赖、目标模型和硬件验证。
静态能力与运行可靠性是两层证据。
