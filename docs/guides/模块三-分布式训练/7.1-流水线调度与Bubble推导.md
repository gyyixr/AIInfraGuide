## 1. 切开模型后，GPU 不会自动忙起来

把 24 层模型分到四个设备，每个设备六层，解决了“每卡存多少层”的问题。但一条样本必须先经过 stage 0，再经过 1、2、3，反向梯度再按相反方向返回。

如果每次只处理一个 microbatch，其他 stage 大量时间都在等依赖。流水线调度的目的，是让不同 stage 同时处理不同 microbatch。

先分清三件事：

- **模型切分**：哪些层由哪个 stage 计算。
- **调度**：每个 stage 在什么时刻执行哪个 microbatch 的前向或反向。
- **更新语义**：何时执行 optimizer step，各次计算用哪份权重。

改变调度不应在没有说明的情况下改变优化目标。

## 2. 本节符号和理想假设

| 符号 | 含义 |
|---|---|
| $P$ | 流水线 stage 数 |
| $M$ | 一次 optimizer step 的 microbatch 数 |
| $b$ | 每个 microbatch 的样本数 |
| $D$ | 数据并行副本数 |
| $t_f,t_b$ | 一个 stage 对一个 microbatch 的前向、反向时间 |
| $F_{r,m}$ | stage $r$ 对 microbatch $m$ 的前向 |
| $B_{r,m}$ | 对应反向 |

先假设各 stage 同速、同一设备一次只执行一个任务、通信耗时忽略、权重在整次 step 内固定。

这些假设是为了导出可手算基准；真实系统会有通信、长短序列、重计算和负载不均，后面再逐项加入。

### 2.1 全局 batch 不乘 PP

在各 microbatch 大小相同的情况下：

$$
B_{global}=bMD.
$$

例如 $b=4,M=8,D=2$，全局 batch 是 64。即使 PP=4、TP=2，也不是再乘 8；这些 rank 合作计算同一批数据。

## 3. 三种不可违反的依赖

一次正确的同步流水线至少满足：

1. $F_{r,m}$ 等待 $F_{r-1,m}$ 输出的激活。
2. $B_{r,m}$ 等待自己前向保存/可重算的状态，并等待 $B_{r+1,m}$ 的输入梯度。
3. optimizer step 等待本次 batch 所需的梯度累积和同步完成。

最后一个 stage 的反向由 loss 梯度启动，第一个 stage 的反向结束后，这个 microbatch 才完成全模型反向。

只要调度图违反第一、第二条，结果就不是“性能差一点”，而是数据尚未准备好或梯度配错。

## 4. GPipe：先把所有 microbatch 向前送

GPipe 的同步 fill-drain 组织可概括为：

```text
填充并执行全部 microbatch 前向
→ 反向依次返回
→ 累积梯度完成后统一更新
```

单独看前向：第一个 microbatch 需要 $P$ 个 stage 时间，之后每隔一个 stage 时间就有下一条完成。

所以：

$$
T_f=(M+P-1)t_f.
$$

反向同理：

$$
T_b=(M+P-1)t_b.
$$

在上述理想假设下，整步时间为：

$$
T_{pipe}=(M+P-1)(t_f+t_b).
$$

其中每个设备真正执行的有效计算时间为 $M(t_f+t_b)$。

## 5. Bubble 分母究竟是什么

如果用“设备可用时间中没有计算的比例”定义 bubble fraction：

$$
f_{bubble}=1-\frac{M(t_f+t_b)}{(M+P-1)(t_f+t_b)}
=\frac{P-1}{M+P-1}.
$$

利用率为：

$$
U=\frac{M}{M+P-1}.
$$

另一种资料可能报告“额外气泡时间相对有效时间的比值”：

$$
r_{bubble}=\frac{P-1}{M}.
$$

两者数值不同，只是分母不同。讨论“气泡 20%”时必须说清定义。

### 5.1 数值代入

取 $P=4,M=8,t_f=2$ ms、$t_b=4$ ms：

```text
理想流水线总时间 = (8+4-1) × 6 = 66 ms
每卡有效计算 = 8 × 6 = 48 ms
每卡空闲时间 = 18 ms
bubble fraction = 18/66 = 27.27%
额外时间/有效时间 = 18/48 = 37.5%
```

如果比较“同一总计算量在单设备串行执行”的 192 ms，则理想加速为 $192/66\approx2.91$，而不是四倍。

这仍未包含模型装载、通信、优化器和数据处理。

## 6. 逐时隙画一张 GPipe 表

下面使用更小的 $P=2,M=4$，每个 F/B 都耗时 1 个时隙，通信为 0。`F0` 表示 microbatch 0 的前向，`B3` 表示 microbatch 3 的反向。

| 时隙 | stage 0 | stage 1 |
|---:|---|---|
| 1 | F0 | 空闲 |
| 2 | F1 | F0 |
| 3 | F2 | F1 |
| 4 | F3 | F2 |
| 5 | 空闲 | F3 |
| 6 | 空闲 | B3 |
| 7 | B3 | B2 |
| 8 | B2 | B1 |
| 9 | B1 | B0 |
| 10 | B0 | 空闲 |

每个 stage 执行 8 个任务，总时长 10，利用率 80%，bubble 为 20%。

在 stage 0 完成 F3 后，四个 microbatch 的激活都还没被对应反向消费，峰值至少涉及四份需要保存的前向状态。

“至少涉及”不等于存下所有中间激活：重计算可以改变每一份的大小，但仍要保留必要的边界和元数据。

## 7. 同步 1F1B：尽早消费激活

1F1B 表示进入稳态后交替做一次前向、一次反向。一般先有 warmup，最后再 cooldown。

同步 flush 版本仍在整次 batch 结束后统一更新，不要求在 microbatch 之间改变权重。

同样使用 $P=2,M=4,F=B=1$，一种合法时间线为：

| 时隙 | stage 0 | stage 1 |
|---:|---|---|
| 1 | F0 | 空闲 |
| 2 | F1 | F0 |
| 3 | 空闲 | B0 |
| 4 | B0 | F1 |
| 5 | F2 | B1 |
| 6 | B1 | F2 |
| 7 | F3 | B2 |
| 8 | B2 | F3 |
| 9 | 空闲 | B3 |
| 10 | B3 | 空闲 |

总时长仍为 10，各 stage 都执行 8 个任务，理想利用率没有改变。

但是 stage 0 最多保留 F0、F1 两份未完成反向的状态，stage 1 基本只保留一份。**1F1B 的首要优势是激活生命周期缩短，不是自动把同一模型下的 bubble 消掉。**

## 8. 激活存活量按 stage 计算

对简单、平衡、非交错同步 1F1B，stage $r$ 通常先 warmup：

$$
w_r=\min(M,P-r-1).
$$

开始反向之前还会进入一次前向，因此常见峰值量级为：

$$
N_{live,r}\lesssim\min(M,P-r).
$$

例如 $P=4,M=8$，典型的各 stage 峰值份数约为 `[4,3,2,1]`，而不是每个 stage 都固定保存 4 份。

实际实现的发送 buffer、输出缓存、异步反向拆分和重计算会改变峰值。上式是调度层的保存份数模型，不是显存分配器的精确公式。

### 8.1 GPipe 与 1F1B 的显存比较

记 stage $r$ 每个 microbatch 需要保存的激活为 $A_r$：

$$
M_{act,r}^{GPipe}\approx M A_r,
\qquad
M_{act,r}^{1F1B}\approx N_{live,r}A_r.
$$

如果 $M=32,P=4$，第一 stage 从约 32 份降到约 4 份，会带来明显空间；后端是否把这个空间转成更大的 microbatch，是另一个调优步骤。

## 9. 增大 M 的收益和代价

从公式看，$M$ 越大 bubble 越小。但必须说明固定了什么。

### 9.1 固定 microbatch 大小 b

增大 $M$ 会增大全局 batch $bMD$，改变优化器更新频率和训练统计。它不只是系统优化。

GPipe 的激活份数也随 $M$ 增长，可能增加内存压力。

### 9.2 固定全局 batch

若全局 batch 和 DP 不变，增大 $M$ 需要减小 $b$。单个 microbatch 的激活通常也随 $b$ 缩小。

因此不能机械地说“GPipe 的 $M$ 翻倍，激活显存一定翻倍”：若同时 $b$ 减半，主要激活总量可能近似不变，但调度元数据和小批效率会变化。

### 9.3 很小的 microbatch 为什么也慢

- GEMM 形状更小，计算效率下降。
- 每个 microbatch 都要触发消息和 kernel 启动。
- CPU 调度开销相对放大。
- padding、变长输入和 stage 不均可能更难隐藏。

所以合理目标是端到端 tokens/s 和目标质量下的成本，不是单独把解析式中的 bubble 调到最小。

## 10. 梯度累积与 loss 分母

若各 microbatch 样本数相同，且每个 microbatch loss 已做样本平均，可以将每个 loss 除以 $M$ 后 backward，或采用等价的最终梯度缩放。

若每个 microbatch 有效 token 数不同，则应按全局有效 token 总数归一化，而不是对 $M$ 个局部均值做简单平均。

流水线框架可能自带 microbatch loss 缩放选项。先核对实现，再决定用户代码是否需要除以 $M$；重复缩放会让梯度小 $M$ 倍。

### 10.1 什么时候 optimizer.step

同步 GPipe/1F1B 的简单规则是：

```text
清零梯度
→ M 个 microbatch 按调度完成前向和反向
→ 必要的 DP 梯度同步/缩放/裁剪
→ optimizer.step
```

不能只因为 stage 3 已完成某个 microbatch，就提前更新它的权重，而其他 microbatch 还在使用旧权重。这样会引入版本不一致，需要另一套有说明的算法。

## 11. 用程序验证时间线的依赖

下面是纯 Python 检查器。它不模拟 GPU，只验证上面两张表的任务依赖和激活存活数：

```python
def audit(rows, stages=2, microbatches=4):
    done, live, peak = set(), [0]*stages, [0]*stages
    for row in rows:
        pending = []
        for rank, task in enumerate(row):
            if task == "-":
                continue
            kind, batch = task[0], int(task[1:])
            key = (rank, kind, batch)
            assert key not in done
            if kind == "F":
                assert rank == 0 or (rank-1, "F", batch) in done
                live[rank] += 1
                peak[rank] = max(peak[rank], live[rank])
            else:
                assert (rank, "F", batch) in done
                assert rank == stages-1 or (rank+1, "B", batch) in done
                live[rank] -= 1
            pending.append(key)
        done.update(pending)  # 同时隙任务只能在下一时隙被消费
    assert live == [0]*stages
    assert len(done) == 2*stages*microbatches
    return peak


gpipe = [
    ("F0","-"), ("F1","F0"), ("F2","F1"), ("F3","F2"),
    ("-","F3"), ("-","B3"), ("B3","B2"), ("B2","B1"),
    ("B1","B0"), ("B0","-"),
]
one_f_one_b = [
    ("F0","-"), ("F1","F0"), ("-","B0"), ("B0","F1"),
    ("F2","B1"), ("B1","F2"), ("F3","B2"), ("B2","F3"),
    ("-","B3"), ("B3","-"),
]
assert audit(gpipe) == [4,4]
assert audit(one_f_one_b) == [2,1]
```

## 12. 自测与参考答案

**1. 为什么 PP=4 不让全局 batch 再乘 4？**

四个 stage 是一个模型副本的不同层，合作处理相同 microbatch，不是四份独立数据副本。

**2. P=4、M=1 时 bubble fraction 是多少？**

在平衡、无通信模型下为 $3/4$。增加 microbatch 才能让不同 stage 获得同时工作的机会。

**3. 1F1B 是否必然比 GPipe 有更小的解析 bubble？**

在本节理想同步模型中不必；主要差异是激活更早释放，进而可能支持更优的实际 batch 和调度。

**4. 为什么 F/B 权重版本必须匹配？**

反向应是对应前向函数的导数。如果中间更新参数而没有权重版本管理，就不再计算同一个函数的梯度。

**5. “M 越大越好”的反例是什么？**

固定全局 batch 时，过多 microbatch 会使每个 batch 太小，GEMM 和启动效率变差；固定 b 时还改变训练统计与显存。
