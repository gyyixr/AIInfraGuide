## 1. 先选抽象层，再比较功能

训练框架可以是可组合的模型库、分布式执行器、完整训练器，或统一启动多后端的工具集。

这些对象不能只按“支持多少并行缩写”排名。

一个入口负责启动Megatron，不意味着它重新实现了Megatron的checkpoint。

一个库能导出Hugging Face权重，也不意味着它能完整导出optimizer、RNG和数据游标。

本篇逐项拆开六个框架，并把它们放进同一个可验证任务合同。

TorchTitan与MaxText分别见17.1和17.2。

## 3. Nanotron：显式并行与可读训练主链

### 3.1 对象与入口

Nanotron面向Transformer预训练，强调较直接的并行接口。

固定入口`run_train.py`读取YAML或Python配置，构造`DistributedTrainer`，建立dataloader，再调用`trainer.train`。

```text
run_train.py
  → DistributedTrainer(config_file)
  → get_dataloader(trainer, ...)
  → trainer.train(dataloader)
```

它适合沿训练迭代阅读参数、数据和并行状态的归属。

### 3.2 并行与功能边界

固定README列出DP+TP+PP、MoE EP、AFAB/1F1B、ZeRO-1、FP32梯度累积和参数共享。

同时把FP8、ZeRO-3、torch.compile、Ring Attention、interleaved 1F1B列在roadmap。

代码中出现CP相关group，不足以把README中未完成的Ring能力直接升级为已验证功能。

应以具体模型路径、配置与测试共同确认。

### 3.3 数据与恢复

入口读取data stage metadata，包括已消费样本和每数据目录的token进度。

固定代码对阶段起点和某些sequence变化路径有显式检查。

`serialize/main.py`分开调用权重、optimizer、scheduler和metadata保存。

它还检查tied参数与对应状态同步。

不要因为使用safetensors就假设任意TP/PP改变都能完整续训。

### 3.4 适用与验收

若目标是学习显式3D并行、修改训练主链或做可控研究，值得从其小Llama配置阅读。

迁移时先验证同拓扑下一batch、一次update和tied权重。

再测试目标并行组合、数据stage变化和外部存储恢复。

本篇不把官方8×H100 tiny示例时长移植到读者设备。

## 4. OLMo-core：模型、TrainModule与Trainer组合

### 4.1 对象与入口

OLMo-core提供模型和训练构件，官方配方位于`src/scripts/official/`。

本轮阅读`src/examples/llm/train.py`，其核心组装链为：

```text
model_config.build(init_device="meta")
  → train_module_config.build(model)
  → dataset_config.build()
  → data_loader_config.build(..., dp_process_group)
  → trainer_config.build(train_module, data_loader)
  → trainer.fit()
```

TrainModule承接模型、optimizer及并行执行；Trainer组织数据、回调、保存与评估。

### 4.2 Batch单位是token

该例`global_batch_size=256*1024`与`rank_microbatch_size=16*1024`明确以token为单位。

不能把它们解释为26万条样本或每卡1.6万条序列。

示例FSDP参数计算dtype为BF16、归约dtype为FP32，并开启模型compile。

这只证明示例配置选择，不表示所有后端组合默认相同。

### 4.3 Checkpoint与导出

训练器先尝试恢复save folder，再考虑load_path。

`load_trainer_state`决定是否恢复包括dataloader在内的训练器状态，且仅在相容数据上才有意义。

checkpoint模块区分临时目录、同步、异步和存储路径。

2026-10-23的MaxText转换提交明确只转换模型权重，不转换optimizer状态。

因此weights round-trip正确与完整跨框架resume是两种验收。

### 4.4 适用与验证

希望复核开放训练配方、模块化模型实现或在PyTorch组件上构建新训练流程时，可从其官方脚本与TrainModule阅读。

需要记录可选Flash/Ring/TE、torchao、grouped GEMM依赖。

镜像中包含依赖，不代表自动包含所需版本的OLMo-core代码。

恢复验收应检查配置、模型、optimizer和data loader的共同状态。

## 5. Colossal-AI：Booster与Plugin拥有不同职责

### 5.1 对象与入口

Colossal-AI不是只有一条统一Trainer主循环。

Booster把模型、optimizer、criterion、dataloader与scheduler交给所选plugin包装。

典型调用关系：

```text
Plugin配置
  → Booster(plugin=...)
  → booster.boost(model, optimizer, criterion, dataloader, scheduler)
  → booster.backward 或 pipeline执行入口
  → optimizer.step
```

### 5.2 为什么返回对象必须重新接收

boost可能改变模型包装、参数组、optimizer状态与数据分片。

后续继续使用旧optimizer或旧model引用，可能绕过所需协议。

固定Booster源码还允许plugin控制device、precision和checkpoint I/O。

此时外层同名参数可能被忽略并发出警告。

### 5.3 并行组织

HybridParallelPlugin建立TP、PP、SP与DP相关group，并把ShardConfig交给模型改写组件。

固定实现包含不同SP模式，梯度同步还需处理共享参数与TP复制参数。

Gemini、LowLevelZero与HybridParallel是不同plugin路线，不能把各自全部能力相加称为任一plugin都支持。

模型policy能否改写某个Hugging Face架构，也是独立条件。

### 5.4 恢复与适用

Booster依据plugin取得CheckpointIO；hybrid模型需要相容的分片格式和参数映射。

适合在现有模型上试验多种并行与内存策略，但应逐plugin验证目标模型。

最小验收包括boost前后逻辑参数身份、forward/grad/update、共享参数和checkpoint round-trip。

README中的历史性能案例不构成当前所有模型与设备的速度承诺。

## 6. InternEvo：训练入口与全局并行上下文

### 6.1 实际主链

固定`train.py`先调用`initialize_distributed_env`建立全局配置与并行状态。

随后：

```text
create_model
  → build_train_loader_with_data_type
  → build_valid_loader_with_data_type
  → TrainerBuilder(model, loaders, ...)
  → trainer.fit
```

模型、数据与optimizer构造不是一个无条件可替换的独立函数。

`gpc`全局上下文决定不少后续行为。

### 6.2 并行命名需要还原含义

README列出1F1B、FSDP、Megatron TP/SP、Flash-Attn SP与Intern Sequence Parallel。

其中“MTP”在该项目某些表格指Megatron Tensor Parallel，不等于多token预测。

不同sequence方案的参数与激活布局需要从其并行实现读取，不能只按缩写对照Megatron CP。

### 6.3 选择性恢复

`checkpoint_manager.py`按content mask选择model、optimizer、scheduler和sampler。

只加载模型权重时，与加载train context和数据状态的路径不同。

sampler是否支持恢复还会检查实际sampler或dataset类型。

代码里有保存/加载方法，不意味着所有自定义dataloader状态都自动可恢复。

### 6.4 适用与验证

若工作围绕InternLM配置、该框架的并行实现或已有训练资产，可沿其TrainerBuilder与checkpoint manager深入。

本轮默认develop提交日期较早，但不能仅据提交年龄推断项目已归档；API显示未归档。

使用NPU等路径需另核对目标工具链与模型，不把README一项支持扩展到所有组合。

迁移首先比较global batch、loss分母、sampler游标和optimizer状态。

## 7. FlagScale：统一编排不等于统一底层实现

### 7.1 仓库与架构变更

原`FlagOpen/FlagScale`在本轮访问重定向到`flagos-ai/FlagScale`。

固定README说明v1.0.0以后进行明显重构，硬件适配移入相应plugin仓库。

旧版工作流需要区分`main-legacy`，不能把旧教程直接套到新入口。

### 7.2 当前入口

根`run.py`是兼容wrapper，建议入口是`flagscale run`或`python -m flagscale.run`。

当前主链为配置解析、task/action验证、runner选择，再执行相应后端。

```text
flagscale.run
  → task/action检查
  → runner与backend
  → 配置转成后端参数
  → launcher/监控/实际训练入口
```

### 7.3 训练后端与插件身份

MegatronBackend会更新训练配置并生成Megatron参数，还组织rendezvous和诊断信息。

Megatron-LM-FL、TransformerEngine-FL、verl-FL、vLLM插件属于不同后端适配关系。

本轮getting-started中的示例固定了各plugin与上游版本对应，并非所有上游最新版随意互换。

FlagCX、设备插件和训练后端也应独立记录版本。

### 7.4 恢复与适用

统一启动器可以管理进程、健康检查和重启，但真正模型/optimizer恢复能力仍取决于后端格式与入口。

适合需要统一多任务、多后端配置与部署接口的团队。

验收时保留最终展开的backend命令、环境、实际group与checkpoint格式。

不能只检查外层YAML合法或runner启动成功。

## 8. LLM Foundry：Composer训练与数据配方

### 8.1 维护状态先说明

本轮官方仓库API显示LLM Foundry已归档，固定主分支提交为2026-03-25。

它仍可作为既有训练资产与配方源码研究对象。

新项目采用时要明确依赖维护、修复与升级责任，不能沿用旧综述将其默认描述为持续快速更新。

### 8.2 真正训练入口

`scripts/train/train.py`是薄wrapper，调用`train_from_yaml`。

实际`llmfoundry/command_utils/train.py`构建tokenizer、loader、模型、optimizer、scheduler与callbacks，再构造Composer Trainer。

```text
YAML及CLI overrides
  → build_dataloader / build_composer_model
  → optimizer / scheduler / callbacks
  → Composer Trainer
  → trainer.fit
```

### 8.3 数据与并行

数据准备可以转换为StreamingDataset/MDS等相关输入格式，训练与评估由配方组织。

固定入口把FSDP与TP配置交给Composer parallelism_config。

它也显式传递device microbatch、precision和按token累积等字段。

不同模型与Composer版本能否组合，要从最终配置与依赖确认。

### 8.4 保存、导出与适用

Trainer参数区分save/load weights-only、autoresume、ignore keys及sharded planner。

HF导出callback与完整Composer训练checkpoint不是同一恢复对象。

适合审阅既有MPT/HF模型配方、流式数据与Composer训练闭环。

若要新硬件或新版本兼容，需承担归档代码的集成验证；旧AMD beta安装段落不能当作当前ROCm兼容矩阵。

## 9. 同一个batch字段，单位可能不同

跨框架迁移最容易悄悄改变训练目标的不是类名，而是batch与schedule单位。

假设global batch为262144有效token，序列长4096、DP=4，每rank microbatch为16384token。

全局每步序列数为64，每rank每microbatch为4条。

累积次数为：

$$
M=262144/(16384\times4)=4.
$$

如果把262144误读为样本数，会扩大4096倍目标工作量。

若存在padding或action mask，还要用有效token重新换算。

### 9.1 可执行oracle一

```python
global_tokens = 262_144
sequence_length = 4_096
rank_micro_tokens = 16_384
dp = 4
assert global_tokens % (rank_micro_tokens*dp) == 0
microbatches = global_tokens//(rank_micro_tokens*dp)
sequences = global_tokens//sequence_length
local_sequences = rank_micro_tokens//sequence_length
assert (microbatches, sequences, local_sequences) == (4,64,4)
print(microbatches, sequences, local_sequences)
```

这只是单位核对，不是OLMo-core或其他框架的完整训练运行。

## 10. 跨框架状态转换必须有语义标签

至少分三类交付：

| 类型 | 必须说明 |
|---|---|
| weights-only | 模型参数、必要buffer与模型配置 |
| warm start | 权重加载，新optimizer/RNG/数据阶段 |
| full resume | model、optimizer、scheduler、RNG、数据进度共同恢复 |

tensor名字匹配只是必要条件。

QKV打包、SwiGLU gate/up顺序、tied权重、norm位置与position配置都可能改变函数。

### 10.1 一个转换验收数例

源参数由两段`[0,1,2]`和`[3,4,5]`保存。

目标希望三段`[0,1]`、`[2,3]`、`[4,5]`。

若m/v也按同一逻辑坐标转换，可以继续验证更新。

如果只有权重，最多证明weights migration，不能给missing moments随意补零后称精确resume。

## 11. 可执行oracle二：恢复合约检查

```python
required_full = {"model", "optimizer", "scheduler", "rng", "data_cursor"}
weights_export = {"model", "model_config"}
training_checkpoint = required_full | {"model_config", "format_version"}

def missing_for_resume(fields):
    return sorted(required_full-set(fields))

assert missing_for_resume(weights_export) == ["data_cursor", "optimizer", "rng", "scheduler"]
assert missing_for_resume(training_checkpoint) == []
source_shards = [[0,1,2],[3,4,5]]
logical = [v for shard in source_shards for v in shard]
target_shards = [logical[i:i+2] for i in range(0,len(logical),2)]
assert target_shards == [[0,1],[2,3],[4,5]]
print("weights export missing", missing_for_resume(weights_export))
```

字段齐全也不证明内容正确；还需检查版本、schema、实际下一batch与一次update。

## 12. 用共同合同比较框架

先给每个候选相同的模型、tokenizer、mask、数据与有效token预算。

随后比较：

```text
模型构造与custom op侵入成本
并行组合与真实group
峰值状态、临时聚合与offload
数据与随机流恢复
checkpoint发布与重分片
低精度和graph支持矩阵
质量、goodput与维护成本
```

没有支持证据的功能标unknown，不填一个乐观的“支持”。

## 13. 最小迁移阶梯

1. 固定小batch，比较logits与loss。
2. 比较关键逻辑参数的grad。
3. 比较一次optimizer update。
4. 连续多步，检查moments与schedule。
5. 同拓扑checkpoint恢复，比较下一batch。
6. 再改并行拓扑或后端，每次只改变主要因素。

最终文本相似不能替代这些数值验收。

任务质量与长期收敛还需独立对照。

## 14. 故障定位

| 症状 | 先查 |
|---|---|
| 切框架后学习率进度差 |step/sample/token单位 |
| 模型加载成功而loss错 |QKV/GLU/norm/position映射 |
| 只在boost后不更新 |是否仍引用旧optimizer/model |
| resume读了旧数据 |trainer-state与sampler实际加载分支 |
| 外层平台声称支持但kernel失败 |后端plugin、设备与dtype组合 |
| 导出后无法续训 |weights-only与训练状态混淆 |
| 旧安装脚本失效 |归档状态、分支、插件版本与API迁移 |

## 15. 自测与详细答案

### 题1：Nanotron README写roadmap能否直接当已实现能力？

不能，必须核对具体代码路径与测试。

某个group或配置字段存在，也不证明端到端算法已支持。

### 题2：OLMo-core的global_batch_size为何不能直接复制成另一框架样本数？

本例单位是token。

应按sequence长度、DP与microbatch换算，并处理mask与padding。

### 题3：Booster为什么可能忽略外层precision参数？

plugin可以声明自己控制precision或device。

有效配置由完整包装链决定，不能只看最外层构造参数。

### 题4：FlagScale支持多芯片是否意味着所有backend都支持同一组合？

不是，硬件适配与功能位于不同plugin和后端。

应检查最终实际加载的实现及版本矩阵。

### 题5：LLM Foundry归档是否意味着源码不再有学习价值？

不是，它仍可解释Composer、数据与配方设计。

但新集成需要明确维护责任，不能假定上游会修复后续兼容问题。

### 题6：权重转换round-trip逐位相同是否证明完整resume？

不证明，optimizer、scheduler、RNG和数据游标可能未转换。

必须单独检查训练状态及下一次更新。
