## 📖 本章概述

一个训练任务能完成第一步，只说明主要代码路径被触发。真正可靠的任务还要能回答：中途退出后从哪里继续、哪些样本已经影响了参数、哪些副本持有哪一版本，以及指标异常时最先检查哪一段数据。

本章将可靠性拆成“状态一致”和“证据完整”。前者让训练可恢复，后者让故障可解释。

## 📑 章节结构

### 9.1 Checkpoint 与可复现训练

- 区分推理权重导出、训练 checkpoint 和包含采样系统的恢复点。
- 保存 actor/critic 参数、optimizer、scheduler、随机状态、数据游标和采样配置。
- 用一个崩溃窗口解释数据重复消费与数据丢失如何发生。
- 设计所有 shard 完成后才提交 manifest 的保存流程。
- 解释异步 staging、持久化完成和下一次参数修改的关系。
- 用“连续跑”与“保存后重启”对照，分别验收严格数值恢复和统计恢复。

### 9.2 RL 训练故障定位实战

- 将 OOM 按模型加载、生成、打分、反向、优化器、同步六个阶段分类。
- 区分首先失败的 rank 与最后报 timeout 的 rank。
- 使用固定 token 回放核对 tokenizer、shift、mask、精度和权重版本。
- 分析零优势组、KL 爆炸、entropy 下降、长度增长和奖励投机。
- 将 trace 中的慢阶段与可执行修复联系起来，并保留回退基线。

## 🔍 一次训练需要保留的最小证据

| 证据 | 解决的问题 |
|---|---|
| 展开的配置与软件版本 | 到底运行了哪套目标和后端 |
| tokenizer、模板和数据 fingerprint | 输入是否发生漂移 |
| sample/group ID、行为版本、结束原因 | 轨迹能否追溯 |
| 训练、采样、同步、保存事件 | 故障发生在哪个阶段 |
| 有效 token、奖励组成和优势统计 | loss 对应的信号是否正确 |
| 每个 rank 的首个异常 | 避免把后续通信超时当根因 |
| 完整 checkpoint manifest | 保存是否形成一致恢复点 |

## 🎯 本章学习目标

- 能解释为什么只有 `model.safetensors` 无法保证训练续跑等价。
- 能指出 actor 已更新、队列已 ack、checkpoint 未完成之间的崩溃窗口。
- 能设计一个最小恢复对照实验，并给出明确验收指标。
- 能根据 OOM 所在阶段调整对应资源，而不是随意减所有 batch。
- 能用逐 token 的固定回放定位概率差异。
- 能区分奖励函数故障、优化数值故障、数据问题和通信问题。

## 🧪 学习练习

训练从 checkpoint 100 恢复，但队列记录显示样本 1001—1100 已消费；实际上 checkpoint 100 的参数还没有使用这批样本。直接跳到样本 1101 会发生什么？

**参考答案**：这 100 条样本会被跳过，训练状态与数据进度不一致。如果反过来加载已经使用该批样本的参数，却把队列退回更早位置，则可能重复更新。需要把模型状态与消费进度绑定到同一提交点，或明确采用允许重复/丢弃的恢复策略。

## 📚 阅读边界

本章展示的是恢复协议与故障诊断方法。单机 toy 实验可以检查数学和局部状态恢复，不能证明跨节点存储持久性、任务调度器故障恢复或完整生产环境 exactly-once 语义。实际承诺必须由相应故障注入实验验证。
