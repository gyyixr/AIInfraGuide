RL 的 loss 不像普通分类交叉熵那样容易解释。采样策略、奖励分布、优势归一化和裁剪都在变化，因此“loss 更小”本身不是质量结论。需要将任务结果、优化状态与系统成本放在同一张记录表里。

本文中的时间和质量数字均为手算示例。评估真实系统时，必须补充模型、硬件、框架版本、采样参数、数据集和计时边界。

## 1. 建立独立于训练奖励的验证协议

一个最小协议至少固定：

| 项目 | 示例记录内容 |
|---|---|
| 输入集合 | prompt IDs、题目家族、数据版本、是否含训练近重复 |
| 模型状态 | checkpoint ID、adapter、tokenizer、模板 |
| 采样规则 | temperature、top-p/top-k、seed、候选数 |
| 预算 | 最大回答长度、最大轮数、工具调用预算 |
| 判定规则 | verifier 版本、测试集、judge 配置 |
| 失败规则 | 截断、格式错误、环境异常如何计入分母 |

对比前后 checkpoint 时，保持协议相同。若一个模型每题允许 8 个候选，另一个只有 1 个，分数差异不能直接归因于训练。

训练 verifier 可以与评估 verifier 使用同类机制，但最终评估必须有独立题目、保留测试或独立复核。反复按验证集挑模型，也会逐渐消耗验证集独立性；最终测试应在选择完成后使用。

## 2. pass@1 与 pass@k

pass@1 关注一次生成成功的概率。pass@k 关注在 $k$ 次候选中至少存在一个正确答案的概率，常用于可自动验证的代码或数学任务。

若题目 $i$ 在固定采样规则下单次成功率为 $p_i$，且候选独立同分布：

$$
\operatorname{pass@k}_i=1-(1-p_i)^k.
$$

注意它只要求候选集合里**存在**正确答案，通常假设有判定正确性的 oracle；不代表部署系统知道应该选择哪一个。

### 2.1 从有限样本估计

实际不知道 $p_i$，但可以生成 $n\ge k$ 个候选，其中 $c$ 个正确。在这 $n$ 个样本中等概率选出 $k$ 个，全部失败的组合数为 $\binom{n-c}{k}$，总组合数为 $\binom nk$，因此：

$$
\widehat{\operatorname{pass@k}}
=1-\frac{\binom{n-c}{k}}{\binom nk}.
$$

若 $n-c<k$，失败组合不可能，估计值为 1。对每道题计算后再对题目求平均，这是 [HumanEval 论文](https://arxiv.org/abs/2107.03374) 使用的估计思路。

### 2.2 手算 $n=5,c=2,k=2$

共有 $\binom52=10$ 种两候选组合，失败候选有 3 个，完全失败组合为 $\binom32=3$，所以：

$$
\widehat{\operatorname{pass@2}}=1-3/10=0.7.
$$

而直接代入经验成功率 $c/n=0.4$ 得到 $1-(1-0.4)^2=0.64$，两者并不相同。组合估计处理了从有限候选中抽样的结构。

### 2.3 可运行的数值实现

```python
import math

def pass_at_k(n: int, c: int, k: int) -> float:
    if not (0 <= c <= n and 1 <= k <= n):
        raise ValueError("要求 0 <= c <= n 且 1 <= k <= n")
    if n - c < k:
        return 1.0
    failure = math.prod((n - c - j) / (n - j) for j in range(k))
    return 1.0 - failure

assert abs(pass_at_k(5, 2, 2) - 0.7) < 1e-12
assert pass_at_k(5, 0, 2) == 0.0
assert pass_at_k(5, 5, 2) == 1.0
```

相同 seed 下复制同一个候选十次，不等于十次独立采样。去重后再改变分母，也不是上述原始评估协议；可以报告多样性，但不要悄悄重定义 pass@k。

## 3. 平均分掩盖了什么

假设验证集包含 90 道简单题、10 道难题。一个模型简单题从 80/90 提升到 90/90，难题从 5/10 降到 0/10，总准确率仍从 85% 变成 90%。

总分改善是真实的，但不能声称困难推理能力改善。应至少按领域、难度、长度、工具类型、数据来源分桶，同时保留各桶样本数。

### 3.1 不确定性与重复评测

在近似独立的二元题目上，成功率 $\hat p$ 的标准误粗略为：

$$
\operatorname{SE}\approx\sqrt{\frac{\hat p(1-\hat p)}{N}}.
$$

例如 $N=100,\hat p=0.6$，标准误约 $0.049$。1 个百分点的差异很可能不能支持强结论。

重复候选属于同一题目，不应当成更多独立题目。对比两个模型时可按题目进行配对 bootstrap；题目有家族相关性时，还需按家族聚类抽样。置信区间方法与抽样单位必须写清。

## 4. KL 指标先说明是哪两个分布

RL 流水线里至少存在当前 Actor、采样时的行为策略、冻结 Reference。以下量各有不同用途：

| 量 | 对比对象 | 用途 |
|---|---|---|
| Actor–Reference KL | 当前策略与固定参考 | 衡量偏离参考程度 |
| Actor–Behavior ratio | 当前策略与生成轨迹的策略 | 重要性采样、PPO 更新幅度 |
| Train–Inference logprob 差 | 同权重、不同执行引擎 | 发现模板、数值与采样实现不一致 |

同一字段叫 `approx_kl` 不意味着同一数学定义。应记录公式、采样分布、token mask、求和/平均与符号。

### 4.1 单样本 log-ratio 可以为负

令动作来自当前 $p$，则：

$$
D_{\rm KL}(p\|q)=\mathbb E_{a\sim p}[\log p(a)-\log q(a)].
$$

完整期望非负，但单个采样 token 的 log-ratio 可以为负，有限 batch 的均值也可能为负。若数据来自旧策略，且没有正确校正，它甚至不是当前 $p$ 下同一个期望。

不要为了“保证 KL 非负”直接对每个 log-ratio 取绝对值；这样改了统计量。非负估计器也有自己的采样假设与梯度处理方式，必须单独说明。

### 4.2 总序列 KL 与每 token KL

每 token 平均差为 0.02，不代表每条回答差也为 0.02。若有效回答长 100 token，其 log-ratio 总和可能约为 2；长度变化会影响序列总量。

因此需同时观察每 token 统计与长度，不能只用一个总序列指标判断训练稳定性。

## 5. entropy、clip fraction 与梯度

### 5.1 entropy 不是文本多样性的全部

给定状态 $s$，完整词表熵为：

$$
H(\pi(\cdot\mid s))=-\sum_v\pi(v\mid s)\log\pi(v\mid s).
$$

完整熵需要所有词汇概率；单个采样 token 的 $-\log p(a)$ 是其随机估计，且必须说明采样分布。高熵可能表示探索，也可能表示失去确定性；低熵可能表示熟练，也可能表示模式坍缩。

结合去重率、长度、领域质量与回答文本判断。只调 entropy bonus 把曲线拉高，并不能保证有效探索。

### 5.2 clip fraction 的分母

PPO 常记录概率比 $\rho_t$ 超出 $[1-\epsilon,1+\epsilon]$ 的有效 token 比例。但“超出范围”与“该 token 的 surrogate 梯度实际被 clip 截断”不完全相同，后者还依赖 advantage 符号。

应该明确日志采用哪种定义，且分母只包含有效动作 token。否则 padding 多的 batch 会呈现虚假的低裁剪比例。

### 5.3 梯度范数和更新次数

梯度裁剪前范数反映优化压力；裁剪后范数几乎固定在阈值以内，单看它可能掩盖异常。应记录非有限梯度、跳过的更新、实际 optimizer step 数和学习率。

梯度范数也受归约尺度影响：token sum 与 token mean、有效 batch、梯度累积数改变后，不应直接比较绝对大小。

## 6. 质量与系统吞吐放到一起

设一个训练周期耗时 100 秒：生成 60 秒、打分 15 秒、更新 20 秒、同步 5 秒。若打分加速一倍，总时间变成 92.5 秒，端到端加速为：

$$
S=100/92.5\approx1.081.
$$

局部加速 2 倍，只带来约 8.1% 的端到端改善。若阶段重叠，还需根据真正的关键路径计算，不能把各阶段计时简单相加。

### 6.1 有效吞吐

```text
原始生成 token/s = 所有生成 token / 端到端时间
有效训练 token/s = 实际进入 loss 的动作 token / 端到端时间
```

若 100,000 个生成 token 中 30,000 来自被剔除轨迹、20,000 是 tool observation，实际有效动作 token 只有 50,000。原始生成吞吐无法代表学习效率。

进一步比较应记录“达到固定验证质量所需 GPU 小时”，并限制评估预算。这比单步速度更接近训练任务的真实目标。

### 6.2 长尾与策略滞后

平均生成时延相同，p95/p99 可能完全不同。同步收集一整批时，最慢样本决定等待时间；多轮任务的工具尾延迟会放大这个问题。

异步系统应记录采样版本、当前训练版本和轨迹年龄。一个版本差可能包含多个 optimizer steps，因此同时记录步数差或时间差。过旧样本带来的统计偏移不能仅靠更高吞吐抵消。

## 7. 一张实际可用的故障定位表

| 现象组合 | 可能原因 | 优先检查 |
|---|---|---|
| reward 升，固定验证降 | 奖励漏洞或验证污染 | 高分样本、verifier、split |
| KL 暴涨，clip 高 | 学习率/更新轮次大、old logprob 错 | ratio 初始值、版本、mask |
| entropy 快速降，回答重复 | 探索不足或数据单一 | 分组成功率、去重率、样本覆盖 |
| reward 不动，adv 全零 | 组内全对/全错、评分退化 | 每 prompt 奖励直方图 |
| 吞吐降，GPU 利用率低 | 工具/打分/输入阻塞 | 阶段时间与队列深度 |
| 同权重 ratio 初始偏离 1 | 模板、温度、精度或 token 错位 | 固定 token 的逐位置 logprob |
| 长度涨，总 KL 涨而 token KL 稳 | 序列长度变化 | 长度分桶与截断率 |
| 单卡好，多卡指标漂移 | 不正确的跨卡加权 | 有效 token 数与归约分母 |

先用极小 batch 固定 token 输入，再逐步打开采样、异步和分布式。每次只改变一个因素，才容易把数学问题与系统问题分开。

## 🎯 自测与参考答案

**1. 生成 5 个候选，2 个正确，pass@2 的组合估计是多少？**

$1-\binom32/\binom52=0.7$。

**2. 某个 token 的 Actor–Reference log-ratio 为负，是否说明 KL 实现一定错误？**

不是。单样本 log-ratio 可为负；要检查采样分布、定义和完整期望的统计性质。

**3. 格式失败样本被过滤后准确率变高，能否声称模型质量提高？**

需要同时报告过滤前成功率、格式通过率和有效样本比例。改变评测分母会改变问题。

**4. 每秒生成 token 翻倍，但达到同样验证准确率更慢，优化成功了吗？**

对端到端训练目标没有成功。可能存在样本陈旧、有效比例下降、奖励变化或更新不稳定，应按达到目标质量的总成本比较。
