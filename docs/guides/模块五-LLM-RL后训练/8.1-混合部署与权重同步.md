训练后得到的新参数并不会自动出现在采样引擎里。训练端和推理端可能使用不同模型类、参数命名、并行布局和数值格式。两端之间的同步，既是大张量传输，也是一次模型状态发布。

## 1. 三种部署方式分别在优化什么

| 方式 | GPU 使用方式 | 主要收益 | 主要成本 |
|---|---|---|---|
| 同卡分时 | 训练与生成轮流占用同一组 GPU | 阶段内可使用全部卡 | 状态装卸和阶段等待 |
| 部分共卡 | 一部分角色共享设备，另一部分独立 | 可按瓶颈分配资源 | 调度与显存重叠复杂 |
| 完全分离 | 训练池和采样池各自常驻 | 可流水并行，布局独立 | 权重跨池传输、版本延迟 |

同卡不代表同一份物理参数始终共用。训练库与推理引擎可能仍持有不同副本。同卡也不代表可以同时执行所有阶段；如果两个角色都按“我独占整卡”分配显存，系统依然会 OOM。

决定部署方式前，先画出每个阶段的同时驻留集合，再考虑是否能重叠。

## 2. 算清楚静态显存的口径

用参数量 `P=7×10^9` 的模型做教学计算，以下 GB 均为十进制 `10^9` Bytes。

假设一种明确的混合精度训练实现：

| 状态 | dtype | 每参数字节 | 7B 规模 |
|---|---|---:|---:|
| 工作参数 | BF16 | 2 | 14 GB |
| 梯度 | BF16 | 2 | 14 GB |
| 主权重 | FP32 | 4 | 28 GB |
| Adam 一阶矩 | FP32 | 4 | 28 GB |
| Adam 二阶矩 | FP32 | 4 | 28 GB |
| 合计 | — | 16 | 112 GB |

这是**指定状态布局下的估算**。有些实现以 FP32 参数配合 autocast，没有独立 BF16 常驻副本；有些保留 FP32 梯度累积，状态会变化。不能仅因模型参数是 BF16，就断言 Adam 状态一定是 FP32 或静态开销必为 16 Bytes/参数。

现在加上 RL 的其他角色：

- 一个独立 BF16 reference 副本增加约 14 GB 参数。
- 一个独立 BF16 rollout 副本再增加约 14 GB 参数。
- 若有同等规模 critic，还要按其真实训练状态另算；它不只是一个很小的 value head。
- 规则奖励可以主要消耗 CPU；神经奖励模型则有自己的权重和激活。

这些数字不能不分时间地机械相加。分时部署关心各阶段峰值，分离部署关心各 GPU 池各自的峰值。

### 2.1 分片后的均值不是峰值

理想完全分片时，112 GB 在 8 rank 上的平均份额为 14 GB/rank，但至少还要加：

1. 激活与反向临时张量。
2. AllGather 后短暂存在的完整参数或参数 bucket。
3. 通信 buffer、优化器临时量和框架缓存。
4. 推理引擎尚未释放的权重、KV cache 与 CUDA graph 内存。

“112/8 小于显存”只能说明平均静态份额可能放下，不能证明整个训练步骤放得下。

## 3. KV cache 的一次手算

对普通存储格式的 decoder attention，未分片 KV cache 近似为：

$$
M_{KV}=2\times L_{layer}\times H_{KV}\times d_{head}
\times b_{elem}\times T_{cached}\times N_{active}.
$$

最前面的 2 对应 K 和 V。假设：

- 32 层，8 个 KV heads，head dimension 128。
- BF16，每元素 2 Bytes。
- 16 条活动序列，每条缓存 4096 个 token，包含 prompt 和已生成回答。

代入：

$$
M_{KV}=2\times32\times8\times128\times2\times4096\times16
=8\,589\,934\,592\ \mathrm{Bytes}=8\ \mathrm{GiB}.
$$

每条序列约 512 MiB。把并发从 16 加到 32，KV 部分也近似翻倍。

若 KV heads 能均匀切到 TP=4，可得到约 2 GiB/rank 的这一项；当 TP 与 KV heads 不匹配、实现复制部分 KV heads、使用 MLA 或其他 cache 格式时，不能套用这个除法。Paged allocation 还涉及块粒度和未使用余量。

这解释了为什么“模型参数只占 14 GB”，并不能推导出“24 GB 卡还能随便开长序列高并发”。

## 4. 训练权重与推理权重不是同一种文件布局

FSDP 可能按 flatten 后参数范围分片；Megatron 可能按 TP 维度切矩阵、按 PP 切层、按 EP 放专家。推理引擎则按自己的模块定义和 TP 规则加载权重。

转换至少包含四种可能工作：

| 转换 | 示例 | 校验点 |
|---|---|---|
| 名称映射 | 训练层名映射到推理层名 | 不漏参数、不把层号错位 |
| 拼接/拆分 | 独立 Q/K/V 与 fused QKV | Q/K/V 顺序、GQA heads 布局 |
| 分片重排 | 训练 TP=4 → 推理 TP=2 | 全局 shape 与每片范围 |
| dtype/量化 | BF16 → 推理量化权重 | scale、zero point、校准/重算策略 |

### 4.1 一个矩阵重分片例子

设某权重全局形状 `[8, 4]`，沿第 0 维分片：

```text
训练 TP=4：rank 0 行0..1，rank 1 行2..3，rank 2 行4..5，rank 3 行6..7
推理 TP=2：rank 0 行0..3，rank 1 行4..7
```

推理 rank 0 需要合并训练 rank 0 和 1 的两片；推理 rank 1 需要合并后两片。简单地把“相同 rank 编号”的 buffer 复制过去是不对的。

现实中的 fused QKV、tied embeddings、MoE expert packing 更复杂，应该由与模型结构匹配的 converter/bridge 完成。

## 5. 一次 7B 权重同步需要多久

只同步 BF16 策略参数，数据量下限为：

$$
S=P\times2=14\ \mathrm{GB}.
$$

注意这里不应同步 Adam 动量或梯度到 rollout，因为采样不需要这些状态。

假设实际可用的端到端有效带宽为 `25 GB/s`，单份完整模型穿过该瓶颈链路的纯传输下界：

$$
T_{wire}\ge \frac{14}{25}=0.56\ \mathrm{s}.
$$

实际同步耗时还包括：

$$
T_{sync}=T_{prepare}+T_{reshard}+T_{wire}+T_{load}+T_{confirm}.
$$

这几个阶段可能部分重叠，因此这是一种分解口径，严格相加只适用于串行情形。有效带宽也不能拿厂商双向标称聚合数字直接代入。

### 5.1 多副本和 bucket 的影响

如果一个发送端按顺序把完整 14 GB 各发给 4 个独立副本，它的出口数据会接近 56 GB。树形广播或节点内复用可以改变网络瓶颈，但不会让接收端无需取得对应参数。

采用 256 MiB bucket 时，14 GB 约分成 53 个 bucket：

- 大 bucket：调用次数少，但临时内存与等待更大。
- 小 bucket：便于边转换边发送，但小包和调度开销增多。
- 同步峰值：旧权重、新权重、临时重排 buffer 可能短暂同时存在。

如果为了减少同步频率，每 4 次训练更新才发布一次，需要同时记录延迟版本和样本分布变化；它不是只改变通信量的纯系统开关。

## 6. Sleep / offload 改变的是驻留状态

vLLM 官方 [Sleep Mode](https://docs.vllm.ai/en/latest/features/sleep_mode/) 文档区分权重卸载、丢弃 KV cache 和选择性唤醒。在核对的文档中，level 1 可将权重备份到 CPU 并释放 KV；level 2 可丢弃权重和 KV，用于随后重载权重。实际能力及保留选项以版本为准。

从训练视角理解顺序更重要：

```text
停止采样 → 等待/取消在途请求 → 释放生成阶段内存
→ 训练 → 只恢复权重所需内存 → 加载新权重
→ 使旧 KV 失效 → 恢复 KV 容量 → 恢复接单
```

把旧参数算出的 KV cache 无条件接到新参数的生成上，会让一次回答混合不同模型状态。若框架支持在途续跑或部分轨迹，必须使用其明确的重算/版本协议。

Offload 的目的在于释放 GPU 内存，代价可能转移到 CPU RAM、PCIe 带宽与装卸时间。主机内存同时存 optimizer 和推理权重时也可能成为瓶颈。

## 7. 策略版本必须在完整加载后发布

以下是**设计示意，不对应具体框架 API**：

```text
prepare v13
  1. 固定 actor 参数快照，生成参数 manifest
  2. 停止向目标推理池派发新请求
  3. drain 在途请求，或按明确规则取消/重算
load v13
  4. 逐 bucket 转换、传输、校验并加载
  5. 各 TP/PP rank 完成设备端工作
commit v13
  6. 每个推理副本确认加载完整且可用
  7. 发布 active_policy_version=13
  8. 恢复接单，轨迹记录 version=13
```

“原子”不是要求 14 GB 在一瞬间复制完成，而是要求请求不能观察到半新半旧的参数状态。可通过暂停接单或双 buffer 切换实现；双 buffer 又会增加显存。

一个副本加载失败时，不能仅把全局版本号加一后继续路由。可以隔离失败副本，或整体回退到仍然有效的版本；具体策略要和负载均衡器、队列一起设计。

## 8. 同步成功怎样验收

仅看 `update_weights()` 返回或打印“done”不够，建议分三层：

| 层次 | 检查 | 能证明什么 |
|---|---|---|
| 结构 | 参数名、全局 shape、dtype、分片范围 | 模型映射没有明显缺失 |
| 数据 | manifest、校验和、抽样参数一致性 | 指定数据确实被传输 |
| 行为 | 固定 token IDs 的 logits/logp 对比 | 转换后模型在选定输入上符合预期 |

对有不同分片布局的参数，不能直接比较每个 rank 的文件 hash。应比较相同逻辑切片或转换后的公共表示。行为对比也需固定 position、mask、kernel 与精度，并设明确误差阈值。

## 9. 自测与参考答案

**题 1：7B BF16 模型只有 14 GB，为何 RL 同卡部署可能超过 100 GB？**

参考答案：14 GB 只算一份权重。训练还可能有梯度、主权重、Adam 状态、激活；RL 还有 rollout/reference/critic 等角色及 KV cache。需按同时驻留阶段计账。

**题 2：训练 TP=4、采样 TP=2，能否只按相同 rank 编号复制？**

参考答案：不能。推理 shard 的逻辑覆盖范围不同，需要合并或切分训练 shards，可能还要映射融合参数。

**题 3：减少同步频率能否无条件提高训练效率？**

参考答案：它减少传输，却增加策略滞后。必须检查样本年龄、ratio 分布、有效样本及验证质量，不能只报告同步秒数下降。

**题 4：为什么旧 KV cache 通常要在权重更新后失效？**

参考答案：其中的 K/V 是旧参数对前缀的计算结果。直接交给新参数续算不再等价于任何一次完整的新策略前向，除非系统有明确的跨版本处理算法。
