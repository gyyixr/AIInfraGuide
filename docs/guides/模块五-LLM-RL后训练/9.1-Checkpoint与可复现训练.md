RL 的 checkpoint 不只是参数文件。它记录“模型已经从哪些经历里学到了什么”，而生成队列、奖励规则和环境状态又决定接下来会学什么。只保存一端，很容易在恢复时出现重复消费或跳过数据。

## 1. 三种保存物分别解决什么问题

| 保存物 | 主要内容 | 用途 |
|---|---|---|
| 推理模型导出 | 参数、模型配置、tokenizer/adapter | 部署和评估 |
| 训练 checkpoint | 参数、optimizer、scheduler、step、随机状态 | 恢复优化过程 |
| RL 一致恢复点 | 训练 checkpoint + 数据/队列/版本/环境协议 | 恢复整个学习循环 |

给部署用的 HF 格式导出并不自动包含 Adam 动量；训练 checkpoint 也不一定保存外部工具环境。必须明确要恢复哪一层。

LoRA 场景除了 adapter 权重，还要固定 base model 的准确版本。只写一个会随时间变化的模型名称，不能唯一确定恢复后的策略。

## 2. 一份 RL 恢复状态清单

| 状态类别 | 典型项目 | 丢失后的后果 |
|---|---|---|
| 模型 | actor、可选 critic、adapter、模型配置 | 策略或价值函数变化 |
| 优化 | Adam moments、master weights、scheduler、scaler | 下一步更新不同 |
| 随机数 | Python、NumPy、CPU/CUDA、各 rank generator | shuffle、dropout、采样序列变化 |
| 数据 | 数据 fingerprint、sampler epoch、cursor、分片规则 | 跳样本或重复样本 |
| 算法 | KL 控制器、reward running stats、归一化状态 | 同一个 reward 产生不同目标 |
| 采样 | 模型版本、temperature/top-p、模板、tokenizer | 行为分布变化 |
| 队列 | 已提交消费集合、未消费轨迹、进行中任务 | 重放、遗失或版本混乱 |
| 环境 | 工具状态、episode ID、终止信息 | 多轮状态无法接续 |

表中项目是否需要持久化取决于任务；关键是对每一项明确“保存、重建、丢弃并重采样”中的一种处理，不能默认它会自己恢复。

### 2.1 为什么 Adam 状态不可随便丢弃

简化忽略 bias correction，Adam 一阶矩更新为：

$$
m_t=\beta_1m_{t-1}+(1-\beta_1)g_t.
$$

设 `β1=0.9, m_(t-1)=0.4, g_t=-0.2`，则：

$$
m_t=0.9\times0.4+0.1\times(-0.2)=0.34.
$$

若恢复时把一阶矩清零，得到 `m_t=-0.02`，连方向都变了。二阶矩、步数和学习率计划也会进一步影响更新。因此“权重相同”并不意味着“下一步相同”。

## 3. 用一个崩溃窗口理解一致性

假设 checkpoint `C100` 表示模型 `θ100`，它已消费数据批次 0—99。接下来发生：

```text
t0: 取出 batch 100
t1: optimizer 更新得到 θ101
t2: 队列标记 batch 100 已消费
t3: 写入 checkpoint C101
t4: 所有文件持久化，提交 C101
```

现在分别在不同位置崩溃：

| 崩溃点 | 可能留下的状态 | 恢复风险 |
|---|---|---|
| t1 前 | θ100，batch 100 尚未提交 | 可以重跑该 batch |
| t2 后、t4 前 | 可恢复模型仍是 θ100，队列已跳过 batch 100 | 数据丢失 |
| 模型 θ101 可见、队列进度未提交 | 模型已使用 batch 100，队列又重放 | 重复更新 |
| t4 后 | θ101 与对应消费进度一起提交 | 可从一致边界继续 |

这不是多加一个 `barrier()` 就自然解决的问题。Barrier 能协调进程到达某处，不能保证存储已经持久化，也不能自动将外部队列 ack 与模型保存组成事务。

### 3.1 “运行完成”与“持久化提交”分开

运行时通知可以释放内存和队列容量；持久化提交则决定失败后哪些更新能被信任。

系统可以采用 at-least-once 重放、允许少量丢弃的统计恢复，或更严格的事务/日志协议。选择哪一种取决于成本和任务要求，但必须记录承诺。不能只因为有 `sample_id` 就宣称训练更新 exactly-once。

## 4. 一个可审计的保存流程

以下是**通用设计示意**，不是现成分布式 checkpoint 库接口：

1. 选定 optimizer step 边界，停止对将要保存状态的并发修改。
2. 固定训练参数、optimizer 和相关算法状态的同一版本快照。
3. 记录与该版本对应的数据消费边界、队列和环境处理策略。
4. 各 rank 写入唯一的临时 snapshot 目录或对象前缀。
5. 等待所有 shard 完成，检查数量、大小和校验信息。
6. 写入 manifest，最后发布 `COMMITTED` 或等价完成标记。
7. 更新“最新可恢复点”指针；旧完整 checkpoint 按保留策略再清理。

本地文件系统的同文件系统 rename 常可提供原子名称替换，但它并不自动等价于掉电持久性。对象存储也不能直接照搬目录 rename；应使用存储支持的条件更新/版本对象和明确提交协议。

## 5. Manifest 应说明恢复语义

下面 JSON 是教学 schema，路径和 hash 是占位符，不是本项目已生成的 checkpoint：

```json
{
  "schema_version": 1,
  "checkpoint_id": "step-000101",
  "status": "committed",
  "optimizer_step": 101,
  "actor_version": 101,
  "rollout_published_version": 100,
  "framework_commit": "<pinned-commit>",
  "model_fingerprint": "<sha256>",
  "tokenizer_fingerprint": "<sha256>",
  "data_fingerprint": "<sha256>",
  "world_size": 8,
  "parallelism": {"dp": 4, "tp": 2, "pp": 1},
  "consumption": {"last_committed_batch": 100},
  "inflight_policy": "discard_and_resample",
  "shards": [
    {"path": "rank-0.pt", "bytes": 12345, "sha256": "<sha256>"}
  ]
}
```

真实 manifest 必须列全所需 shards。`actor_version=101` 而 `rollout_published_version=100` 并不一定是错误：保存时可能尚未发布新权重。恢复时必须选择先同步到 101，或按记录协议处理仍来自 100 的轨迹。

仅有一个 `status: committed` 字符串也不够；只有发布流程和实际文件校验共同满足约束，才构成完成证据。

## 6. 异步保存不是“调用后立刻忘记”

异步 checkpoint 通常把保存分成：

```text
可变训练状态 → 一致的 staging 副本 → 后台写入 → 持久化完成
```

如果后台写入还在读取正在被 optimizer 修改的 buffer，会形成混合步数的坏快照。必须确认 staging 何时与训练状态隔离，再允许下一次修改。

PyTorch 的 [异步 DCP 教程](https://docs.pytorch.org/tutorials/recipes/distributed_async_checkpoint_recipe.html) 区分 staging 与保存完成，并说明异步方案的内存和调用约束。具体返回对象及等待方式随版本变化，应按实际安装版本使用。

此外要限制同时在途的 checkpoint 数。每个快照都可能占用额外 CPU/pinned memory；GPU 利用率提升但主机 OOM，并不是成功优化。

## 7. 改变 GPU 数之后还能恢复吗

如果从 `DP=4, TP=2` 改为 `DP=2, TP=4`：

- 参数 shards 的逻辑范围发生变化。
- optimizer 状态要按同样参数语义重分片。
- RNG 与 sampler 的 rank 分配可能不同。
- 批次组成、归约顺序、浮点舍入和采样顺序可能改变。

支持 reshard 的 checkpoint 工具可以帮助恢复参数和 optimizer，但它不自动恢复完全相同的未来样本序列。PyTorch [Distributed Checkpoint](https://docs.pytorch.org/docs/main/distributed.checkpoint.html) 提供分片状态保存/加载机制；是否支持某个模型与并行组合，还要查看对应版本和后端。

因此要区分“能加载”“数值相近”“训练统计可复现”“逐 bit 相同”四种不同承诺。

## 8. 可复现性分层验收

| 层次 | 固定什么 | 验收方式 |
|---|---|---|
| 数据协议复现 | IDs、token、mask、reward 实现 | 字段和数值逐项比较 |
| 单步数值复现 | 相同参数、输入、随机状态、后端 | loss、grad、参数误差 |
| 严格续跑复现 | 相同环境、执行顺序、所有状态 | 连续跑与恢复跑逐步比较 |
| 统计复现 | 任务、配置、预算、评估协议 | 多随机种子均值与波动 |

PyTorch 官方[随机性说明](https://docs.pytorch.org/docs/stable/notes/randomness.html) 提醒不同版本、平台或执行条件不保证完全一致。对异步采样，动态请求次序和外部环境进一步增加了差异来源。

设置一个 seed 是起点，不是完整证据。至少保存采样器和数据随机状态；若用全局 RNG，异步任务完成顺序改变也会改变后续随机数分配。按 episode/sample 派生独立 seed 可以提高可追踪性，但仍需固定具体生成实现。

## 9. 最小恢复实验怎样设计

先在确定性、小数据、短轨迹条件下做以下对照：

```text
路径 A：初始化 → 更新1 → 更新2 → 更新3 → 保存结果A
路径 B：初始化 → 更新1 → 保存 → 退出
                   → 新进程加载 → 更新2 → 更新3 → 保存结果B
```

比较内容应包括：

1. 每一步输入的 sample/group ID 与有效 action mask。
2. reward、advantages、旧概率和 loss。
3. optimizer step、学习率、Adam moments。
4. 参数最大绝对误差、相对误差或 hash。
5. 待消费队列和下一批数据游标。

再扩展故障注入：写一半 shard 时退出、权重同步一半时退出、reward 超时时退出、队列 ack 前后退出。测试必须限定在专用实验任务中，不能通过终止共享机器的所有 Python 进程制造故障。

## 10. 多轮环境如何恢复

对一个运行了一半的浏览器或代码 Agent，恢复模型并不意味着恢复环境。必须选择：

- **环境可快照**：保存并恢复容器/文件/工具状态，校验 episode 身份。
- **可确定性重放**：保留 action 和 observation，重放时验证结果一致。
- **丢弃在途 episode**：明确重新采样，记录浪费与分布影响。

工具调用有外部副作用时，重试还需要幂等键或业务层确认。仅重放文本日志并不能证明外部世界回到了同一状态。

## 11. 自测与参考答案

**题 1：`θ101` 已在 GPU 上，checkpoint 仍是 `θ100`，能否永久删除 batch 100？**

参考答案：若要从 `θ100` 恢复且不丢失更新，就不能仅凭运行时完成删除唯一可重放数据。需要一致提交、日志或明确允许丢弃的恢复约定。

**题 2：只有模型权重和 seed 能否完全恢复 Adam 训练？**

参考答案：不能。还缺 optimizer moments、步数、scheduler 和相关随机状态；随机 seed 不等于当前 RNG 状态。

**题 3：异步保存 API 返回，是否已经可删除上一个 checkpoint？**

参考答案：不一定。要等待持久化完成并验证新恢复点提交成功，才能按保留策略删除旧版本。

**题 4：更换 world size 后 loss 轨迹略有差异，就能断言 checkpoint 错了吗？**

参考答案：不能。批次、归约顺序和随机流可能改变。应先检查状态和数据协议，再按声明的数值/统计容差验收。
