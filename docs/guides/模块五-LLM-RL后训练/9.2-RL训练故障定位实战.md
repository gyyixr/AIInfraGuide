RL 排障最困难的地方，是同一个表象可能来自完全不同的层。例如 reward 下降可能是权重没同步、模板变了、评估集泄漏被修复，或策略更新太激进。先修改学习率，往往会让问题更难解释。

本节按“固定证据—定位阶段—提出假设—最小验证—回到整轮”的顺序排查。

## 1. 第一个动作：保存发生问题的最小上下文

至少保留：

```text
代码 commit、依赖版本、模型和 tokenizer fingerprint
展开配置、随机 seed、GPU 拓扑、进程与 rank 对应
optimizer step、rollout version、sample/group ID
input token IDs、action mask、结束原因
reward 分项、old/current/reference/behavior logp
每个 rank 的最早错误、阶段计时和显存峰值
```

对于真实业务数据，应按数据管理要求保存可用于复现的最小样本。这里不需要全量倾倒所有用户文本；常见 shift、mask、版本问题用一两个固定例子就能查清。

## 2. OOM 必须先问“在哪个阶段”

| 阶段 | 常见占用 | 优先动作 |
|---|---|---|
| 加载模型 | 参数、临时反序列化副本 | 核对重复副本、dtype、加载分片策略 |
| 生成 | KV、图缓存、并发请求 | 降并发/长度预算，确认 cache 实际容量 |
| reference/reward 打分 | 完整序列激活、logits | 缩小评分微批，确认 inference/no-grad 路径 |
| actor 反向 | 激活、梯度、临时 workspace | 缩训练 microbatch、重计算、变长 batch |
| optimizer step | moments、master weights、临时 buffer | 查状态初始化与优化器实现、分片/offload |
| 权重同步 | old/new 权重、reshard bucket | 调整释放顺序、bucket、选择性唤醒 |

`gpu_memory_utilization` 一类采样配置主要影响推理引擎预算，不能修复训练端 optimizer state 超限。降低训练 microbatch 也不一定影响生成阶段的 KV 峰值。

### 2.1 一个按阶段定位的案例

假设某卡可用预算 24 GiB，某次同步前实测：

| 驻留项 | 示例占用 |
|---|---:|
| 推理权重 | 13 GiB |
| KV 与其他生成状态 | 6 GiB |
| 同步重排临时量 | 即将申请 7 GiB |

合计达到 26 GiB，失败点是同步临时分配。把下一轮生成并发从 16 减到 8，如果当前 KV 仍未释放，对这次同步可能没有帮助。

更直接的验证是确认同步前释放哪些状态、是否能先释放 KV、是否能缩小转换 bucket，再测峰值。这里的数字是教学案例，必须用实际 profiler/日志确认每项来源。

### 2.2 不能把 reserved 当作全部泄漏

PyTorch caching allocator 的 allocated 与 reserved 含义不同；推理引擎或 NCCL 也可能使用非 PyTorch 管理的显存。进程显存、框架统计和实际峰值应联合看。

反复调用 `empty_cache()` 不是通用修复：它不能释放仍被张量引用的内存，也不能纠正阶段内本来就超预算的状态。先找增长的对象与生命周期。

## 3. NCCL timeout 经常只是后果

一个 rank 因 OOM 退出后，其他 rank 可能卡在 AllReduce，最后只剩通信超时。若只读 rank 0 最后的日志，很容易把 GPU 内存错误当成网络故障。

排查顺序：

1. 按时间收集所有 rank 的**第一个异常**。
2. 确认 rank/world size/device 绑定及进程是否都存活。
3. 检查各 rank 是否走相同 collective 顺序和 shape。
4. 再检查网络、拓扑、共享内存和驱动环境。
5. 在同一环境单独运行小规模通信基线，隔离模型和奖励流程。

为专用复现任务设置以下环境变量可增加日志；这段只展示设置，不启动或修改当前任务：

```bash
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,COLL,NET
export TORCH_DISTRIBUTED_DEBUG=DETAIL
```

NCCL 的[环境变量文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/env.html) 和[排障入口](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting.html) 提供各版本支持范围。不要把为定位问题临时关闭某种通信路径的开关永久留在性能基线里。

### 3.1 RL 特有的 rank 分歧

某 rank 在过滤后没有有效样本，直接 `return`；其他 rank 仍进入 backward 和 collective，就可能永久等待。修复重点是全局协调空 batch 和所有 rank 的控制流，而不是单纯加长 timeout。

另一个例子：只有 rank 0 执行需要全体参与的参数聚合或 checkpoint，其他 rank 不进入对应调用。遵守后端规定的参与者集合，比“只有 rank 0 保存”的习惯更重要。

## 4. 固定 token 回放是概率问题的地基

当初始 PPO ratio 明显偏离 1，先暂停更新，使用同一权重版本和**同一串 token ID**在训练端、推理端打分。

逐层对齐：

| 项目 | 检查方式 |
|---|---|
| 模型 | checkpoint revision、adapter、权重版本 |
| 输入 | 逐 token ID 比较，不能只比 decode 后文本 |
| 模板 | BOS/EOS、assistant prefix、thinking 标记 |
| 位置 | padding side、position IDs、packing 边界 |
| 目标 | causal shift、action mask、EOS/截断约定 |
| 分布 | 温度、top-k/top-p、logp 定义 |
| 数值 | dtype、量化、kernel、并行切分 |

如果先重新生成两个回答再比较 log probability，输入动作和历史都变了，这个实验无法隔离后端差异。

## 5. 用 P=3、R=2 找出一个 off-by-one

输入为：

```text
索引:        0   1   2   3   4
input_ids:  p0  p1  p2  y0  y1
```

自回归模型在索引 2 的 logits 预测 `y0`，在索引 3 的 logits 预测 `y1`。因此 response 长度为 2 时，应取：

```python
# 形状示意：假设 prompt 为等宽 P，完整序列宽 P + R。
# logits: [N, P + R, V]，input_ids: [N, P + R]
response_logits = logits[:, P - 1:P + R - 1, :]
response_ids = input_ids[:, P:P + R]
logp = response_logits.float().log_softmax(-1)
selected_logp = logp.gather(-1, response_ids.unsqueeze(-1)).squeeze(-1)
```

这段展示 causal shift 关系，假设等宽 prompt 且尚未做 packing；真实变长实现还要结合每条样本位置索引。完整 `[N,R,V]` 的 FP32 log-softmax 可能占大量显存，生产实现需用其优化后的分块/融合路径。

若误取 `logits[:, P:P+R]`，实际给 `y0` 使用的是已经看到 `y0` 的位置，损失就不是正确的 next-token 目标。

### 5.1 Mask 的三个常见错误

1. 使用 `token_id != pad_id` 推断有效位置，但 pad 与 EOS 共用 ID。
2. 将工具 observation 计入 actor loss，模型被训练去“生成环境返回”。
3. 截断样本的 mask、reward 和 bootstrap 约定不一致。

建议保存一个可打印表：每行是 `position/token_id/role/attention_mask/action_mask/logp/reward/advantage`，人工核对一个完整样本，再看大 batch 汇总。

## 6. 零优势不是单纯的数值故障

对规则奖励 `[1,1,1,1]` 或 `[0,0,0,0]`，组均值居中后策略梯度优势全为零。加入 epsilon 只避免除零，不会凭空制造学习信号。

| 现象 | 可能解释 | 下一步检查 |
|---|---|---|
| 全对组越来越多 | 当前题目已过于简单 | 独立验证难度分布、课程或采样策略 |
| 全错组越来越多 | 任务过难或奖励器故障 | 人工检查回答与 verifier 输入 |
| 所有组突然同分 | parser/template/标签错 | 对固定正反例运行奖励单元检查 |
| 优势非零但更新为零 | mask、detach、学习率或梯度问题 | 有效 token、grad norm、参数差 |

零优势组的 policy-gradient 部分可能没有信号，但 KL、entropy 或其他辅助项仍可能产生梯度。诊断日志应分别报告各 loss 分项。

过滤同分组可以增加有信号数据比例，却改变接受样本分布和生成成本。必须记录过滤率与补采规则，不能只展示过滤后的平均 reward。

## 7. KL、ratio 与 NaN 怎样顺着链路查

### 7.1 先确认指标定义

`mean(log p - log q)` 在有限采样上可能为负；它是否估计某个 KL，还依赖样本来自哪个分布。单 token 的 log ratio 为负也完全正常。

同时，“reference KL”“当前对 old 的更新距离”“rollout 与训练不一致”是三类不同指标。必须写清分子、分母和采样分布，再解释异常。

### 7.2 排查顺序

1. 在更新前比较旧概率与行为概率，判断不一致是否早已存在。
2. 检查有效 mask、分母 token 数和优势分布。
3. 检查 logits/logp 是否有限，极小概率是否引起 ratio 溢出。
4. 查看梯度范数、学习率、更新次数和 loss 缩放。
5. 检查 dtype 边界、Adam 状态、混合精度和量化转换。
6. 最后尝试调整 clip、KL 系数、学习率和 epoch，并做单变量对照。

盲目对所有 ratio 做很小阈值的 clamp，可能让日志稳定却隐藏错误 shift 或概率字段混用。先定位产生异常的第一层，再讨论稳定性超参数。

## 8. 奖励上升但能力下降的案例

假设训练奖励由“最终答案正确 + 格式奖励”构成。某次改动后：

| 指标 | 之前 | 之后 |
|---|---:|---:|
| 总训练 reward | 0.45 | 0.70 |
| 独立验证正确率 | 42% | 30% |
| 格式奖励均值 | 0.05 | 0.40 |
| 响应长度中位数 | 300 | 1200 |

这组教学数据提示模型可能在利用格式评分或反复输出答案标记。应先打印 reward 分项和成功/失败样本，验证 parser 是否只看最后一个片段、是否允许重复标记加分。

修复应对齐任务目标：限制格式项贡献、改进验证器、明确多答案解析规则，并在未用于调试奖励的独立数据上重新评估。不能仅因训练 reward 上升就认定方法有效。

## 9. 性能异常也要先看端到端时间线

一轮假设耗时：

```text
生成 45 s | reward 30 s | logp 8 s | train 12 s | sync 5 s
总计 100 s
```

把 actor 训练优化一倍，只能节省 6 秒，总加速 `100/94≈1.06×`。如果 reward 阶段是在单线程依次执行 30 个独立任务，优化那里可能更有收益。

但阶段可能重叠，不能把分散 worker 上的全部耗时相加当 wall time。应看关键路径和等待关系，并在 GPU 异步执行下使用正确事件或同步边界计时。

建议 trace span 至少带 `step, sample_id, group_id, role, policy_version`，这样才能从某条长尾轨迹追到 reward 服务、队列和训练 batch。

## 10. 把修复变成有结论的小实验

一份有效的排障记录应包含：

- **症状**：第几个阶段、哪个 rank、哪些指标先变化。
- **假设**：例如“同步前 KV 未释放导致峰值超限”。
- **实验**：固定模型和 batch，只改变相关释放时序。
- **证据**：峰值显存、阶段耗时、参数与概率校验结果。
- **结论**：假设被支持或排除，仍存在哪些不确定项。

修复后先重跑最小复现，再跑一轮完整训练和一次评估。若涉及恢复状态，还应重复保存/加载对照；若涉及组或 mask，还要复算已知手算样本。

## 11. 自测与参考答案

**题 1：日志最后是 NCCL timeout，为什么先找所有 rank 的首个错误？**

参考答案：某 rank 可能先 OOM 或数据异常退出，其他 rank 只是等待它参加 collective。Timeout 是后果，增加超时时间不会修复根因。

**题 2：prompt 长 3、response 长 2，预测两个 response token 应用哪些 logits 位置？**

参考答案：位置 2 和 3。它们分别在看到完整 prompt、看到 prompt+y0 后预测 y0、y1。

**题 3：组内 reward 全为 1，epsilon 能否让 GRPO 产生非零优势？**

参考答案：不能。中心化分子已经为 0；epsilon 仅避免除零。要检查题目难度或采样/奖励分布，而不是增大 epsilon 找信号。

**题 4：更新前 ratio 就明显偏离 1，第一步应该降学习率吗？**

参考答案：优先固定回放，核对版本、输入、mask、概率定义和数值路径。更新尚未发生，学习率不是这部分差异的来源。
