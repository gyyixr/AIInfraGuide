## 📖 本章概述

前面各章解释了损失函数，现在把它们放进真正的系统。一次 RL 更新既包含自回归推理，也包含完整序列前向、反向、奖励计算和模型同步。这几种工作负载的最佳执行方式不同，因此一个训练任务常常同时使用训练框架、推理引擎和进程编排框架。

本章先用一个固定 batch 追踪数据，再阅读三个开源框架的职责划分。目标是拿到一份配置后，能回答“哪些角色实际启用、在哪些 GPU 上、传什么张量、什么时刻才能进入下一步”。

## 📑 章节结构

### 7.1 角色编排与端到端数据流

从 2 个 prompt、每题 3 个回答开始，追踪 6 条轨迹：

1. **生成**：rollout engine 持有策略版本，返回 token、长度、结束原因和行为 log probability。
2. **打分**：规则验证器或奖励模型评价相同回答；reference 和 critic 只在目标需要时执行。
3. **构造目标**：明确 response mask、组标识、优势、returns 以及旧策略概率。
4. **更新**：训练后端沿自己的 DP/TP/PP 拓扑切分 batch，计算当前 log probability 与梯度。
5. **发布**：将新策略权重同步到 rollout engine，完成版本确认后才放行新一轮请求。

这一过程中，Ray RPC 是调用边界，NCCL collective 是张量通信协议，HTTP 是服务请求接口。它们可能同时出现在同一个任务中，但不能互相替代。

### 7.2 verl、ROLL 与 slime 框架实践

本节采用 **2026-10-29 阅读时固定的源码快照**，不把滚动更新的 README 当作所有版本的承诺。

| 框架 | 阅读切入点 | 重点问题 |
|---|---|---|
| verl | Hydra 配置、TaskRunner、V1 trainer | 控制流如何组合 worker、agent loop 与数据传输 |
| ROLL | RLVRConfig、RLVRPipeline、角色 strategy | actor_train、actor_infer 和多域奖励怎样协作 |
| slime | train.py、RolloutManager、Megatron backend | 生成扩展如何接入训练与权重更新循环 |

三个框架都能表达“采样—打分—训练”，区别应落到任务扩展点、部署方式、模型支持、可靠性和测量结果，而不能只根据某个项目的性能口号作选择。

## 🎯 本章学习目标

- 能画出一次 PPO 和一次无 critic 的 GRPO 训练链路，并指出哪些角色是可选项。
- 能根据 `B=2, G=3, R=4` 写出 rollout 与训练目标的张量形状。
- 能区分 rollout 行为概率、训练端旧概率、当前概率和 reference 概率。
- 能从实际配置计算全局 batch，而不把 GPU 总数误当 DP 大小。
- 能沿源码定位入口、生成、优势计算、更新、权重同步和保存点。
- 能解释“异步推理 API”与“允许过期策略样本的异步训练”为什么是两个概念。

## 🧪 学习练习

在纸上设计一个 8 GPU 任务：训练使用 `TP=2, PP=1, DP=4`；采样也使用这 8 张卡，每个推理副本 `TP=2`。给每一个阶段标注角色、显存和必须等待的事件。

**参考答案要点**：训练端 4 个 DP 组分别处理数据；推理阶段可以是 4 个 TP=2 副本。两种逻辑布局数量相似不意味着权重布局相同。共卡执行应先结束使用旧权重的请求，再让出显存、执行训练和同步、确认所有推理副本版本一致，最后恢复采样。

## 📚 阅读边界

本章的张量和时间例子是教学构造。框架部分是固定源码的静态阅读，没有在本项目中安装或执行三个框架的多 GPU 训练。第 10 章的本地小实验用于核对算法数值；生产框架是否能运行，还需要匹配模型、驱动、依赖版本和设备拓扑。
