选 RL 框架之前，先问清楚自己的任务：训练什么模型、用什么奖励、是否需要多轮工具、允许多大的策略延迟、有哪些 GPU。仅仅比较“支持 PPO/GRPO”远远不够，这两个名字没有描述执行布局和数据协议。

本节提供一条可复核的阅读路径。它是**官方源码静态核对与集成实验设计**，没有在本项目中安装三个框架或运行其多卡训练。

## 1. 先固定证据版本

以下快照在 2026-10-29 核对。链接固定 commit，后续版本可能改名、迁移或改变默认值。

| 项目 | 仓库与快照 | 核对重点 |
|---|---|---|
| verl | `verl-project/verl`，`a08ea02a784d7d4982b1d81df36d188a476192bb` | `main_ppo.py`、V1 入口、训练和 rollout 配置 |
| ROLL | `alibaba/ROLL`，`d3506ea9e280ae720fb74df9f82db6efac1c72d5` | RLVR pipeline、Megatron RLVR 示例配置 |
| slime | `THUDM/slime`，`540ea919e45b8b929198abce008a103be9cfc779` | `train.py`、Qwen3 示例参数 |

verl 的旧地址 `volcengine/verl` 在核对时重定向到 `verl-project/verl`。阅读时优先跟随实际仓库和固定链接，避免把旧教程中的路径当作当前目录。

比较结论只覆盖这里核实的路径。某框架未在表中写某项能力，不等于它不支持该能力。

## 2. 三个框架放进同一张职责表

| 关注点 | verl | ROLL | slime |
|---|---|---|---|
| 本节入口 | Hydra 配置的 `main_ppo.py` | `RLVRPipeline.run()` | `train.py` |
| 控制组织 | TaskRunner 选择 trainer，连接 worker 与 agent loop | pipeline 调度多个角色 cluster 和采样 scheduler | driver 串起 rollout manager 与 training model |
| 训练执行 | 由配置选训练后端；本节不假定单一后端 | 示例为 Megatron strategy | 本节示例为 Megatron |
| 采样执行 | rollout 配置选择引擎与执行方式 | 示例为 vLLM strategy | 本节示例为 SGLang |
| 可优先学习的扩展点 | trainer、agent loop、reward、worker 配置 | domain、reward worker、strategy、pipeline | generation、reward、rollout manager |
| 首要核对 | V0/V1、trainer mode、最终 Hydra 配置 | 继承配置、设备映射、按域采样与过滤 | 参数数组、模型格式、生成回调协议 |

这张表描述已查看的结构，不是速度排名。比较性能必须统一模型、回答长度、batch、奖励成本、GPU 数、精度以及达到目标质量的标准。

## 3. verl：先识别 V1 入口和最终配置

固定快照中的 [`main_ppo.py`](https://github.com/verl-project/verl/blob/a08ea02a784d7d4982b1d81df36d188a476192bb/verl/trainer/main_ppo.py) 先校验配置，再按 `trainer.use_v1` 选择 TaskRunner；V1 路径初始化数据传输组件与 trainer，并创建 agent loop manager，最后交给 trainer 的 `fit`。

学习时按下面次序读，而不是一开始陷入单个 loss 函数：

```text
Hydra defaults + 用户覆盖
    → 配置校验与角色需求判断
    → Ray TaskRunner
    → V1 trainer 的模式选择
    → worker / engine / data transfer 初始化
    → agent loop 产出轨迹
    → trainer 执行评分、优势与更新
```

### 3.1 两个 async 不应混淆

[`ppo_trainer.yaml`](https://github.com/verl-project/verl/blob/a08ea02a784d7d4982b1d81df36d188a476192bb/verl/trainer/config/ppo_trainer.yaml) 的快照默认 `trainer.use_v1: true`、`trainer.v1.trainer_mode: sync`。与此同时，[rollout 配置](https://github.com/verl-project/verl/blob/a08ea02a784d7d4982b1d81df36d188a476192bb/verl/trainer/config/rollout/rollout.yaml) 的 `mode` 为 `async`。

这不矛盾：一个表示训练循环怎样等待 batch 和更新权重，另一个表示推理引擎的调用方式。异步请求接口可以被同步 RL 训练循环使用。

### 3.2 最小语义配置阅读练习

下列是**字段关系片段，不是可直接启动的完整配置**；仍缺模型、数据路径、设备和环境参数：

```yaml
algorithm:
  adv_estimator: grpo
  norm_adv_by_std_in_grpo: true
actor_rollout_ref:
  rollout:
    n: 4
    temperature: 1.0
trainer:
  use_v1: true
  v1:
    trainer_mode: sync
```

读这几个字段应得出：每个 prompt 请求 4 个回答；优势按 GRPO 路径解释；组内标准差归一化打开；训练循环选择同步 V1。**不能据此推断**是否启用 reference KL、是否使用 LoRA、GPU 数和 micro batch 大小。

检查 PPO/GRPO 配置时至少记录：

| 语义 | 需要查的配置或日志 |
|---|---|
| prompt batch | 数据 batch 大小及过滤后实际数量 |
| 组大小 | rollout 的 `n` 和组完整性 |
| actor 更新 | minibatch、microbatch、累积与 epoch |
| 比率分母 | rollout log probability 还是训练端重算的 old log probability |
| KL 路径 | reward penalty、显式 loss 是否同时启用 |
| 模型布局 | FSDP/Megatron 参数、rollout TP、设备共享情况 |

这些是语义清单；不同版本的字段位置不完全一样，必须在同一 commit 的 config schema 里查证。

## 4. ROLL：从 role 配置追踪 pipeline

核对的 [`RLVRPipeline`](https://github.com/alibaba/ROLL/blob/d3506ea9e280ae720fb74df9f82db6efac1c72d5/roll/pipeline/rlvr/rlvr_pipeline.py) 将采样、参考概率、旧概率、优势和 actor 更新连接起来。具体调用是否执行受配置分支控制。

阅读骨架可以按下面的链路建立：

```text
RLVRConfig
  → actor_train / actor_infer / reference / rewards
  → cluster + strategy + scheduler
  → model_update
  → 按 domain 采样并收集轨迹
  → 可选 reference 和 old log probability
  → 按 domain 构造奖励与优势
  → train_step
```

### 4.1 先看实际示例，别猜算法

固定的 [Qwen2.5-7B Megatron 示例](https://github.com/alibaba/ROLL/blob/d3506ea9e280ae720fb74df9f82db6efac1c72d5/examples/qwen2.5-7B-rlvr_megatron/rlvr_config.yaml) 中，`rollout_batch_size=64`、`num_return_sequences_in_group=8`，但 `adv_estimator` 写的是 `reinforce`。不能因为“每题 8 个回答”就把整个配置叫标准 GRPO。

先不考虑过滤与重采样，候选轨迹数是：

$$
64\times8=512.
$$

真实进入 actor 的数量还受长度、难度、分域采样等条件影响。日志应同时记录候选数、接受数和接受率，才能解释每轮耗时和样本效率。

### 4.2 设备映射比名称更重要

该示例 `num_gpus_per_node=8`，却给 `actor_train.device_mapping` 使用 `0..15`，给 `actor_infer` 使用 `0..11`。这说明它不是一份可以直接套用到单张消费卡的教程配置。

逐项审阅：

1. 设备编号属于哪个资源池，实际总卡数是多少？
2. 训练与推理集合是否交叠，交叠时由谁完成 offload/onload？
3. Megatron 的 TP、PP、EP 如何决定 DP？
4. Reward worker 是 CPU 规则、沙箱还是另一个 GPU 模型？
5. 推理引擎的显存预算是否与共驻留角色冲突？

示例中还包含部署环境相关的数据目录与输出目录。实践时应先把这些字段改成自己可访问的输入与输出，再验证配置；不能把原作者机器路径当作公共数据服务。

### 4.3 哪些字段最容易误读

| 字段类别 | 常见误读 | 应怎样确认 |
|---|---|---|
| `ppo_epochs` | 写在配置里就一定是 PPO 算法 | 继续看实际 policy loss 和 advantage 分支 |
| `adv_estimator` | 决定全部训练目标 | 还要看 clipping、KL、mask、权重 |
| `reference` | 有配置块就一定执行 | 查启用条件、LoRA 分支和具体目标 |
| `device_mapping` | 等于一个普通 rank 列表 | 核对 cluster 的设备分配语义 |
| `reward_type` | 只影响显示方式 | 查看归一化、过滤及优势输入 |

## 5. slime：追踪 generate、train 和 update_weights

在固定 [`train.py`](https://github.com/THUDM/slime/blob/540ea919e45b8b929198abce008a103be9cfc779/train.py) 中，可以找到一个直接的学习骨架：初始化训练模型后先向 rollout 推送权重，然后在循环中生成数据、训练、通知消费完成、按需保存，再更新 rollout 权重。

```text
create_rollout_manager / create_training_models
  → 初始 update_weights
  → training_ready
  → generate(rollout_id)
  → actor / 可选 critic 训练
  → training_completed
  → 按策略 checkpoint
  → pause admission + update_weights + resume
```

源码将运行时消费完成与持久化 checkpoint 区分开。前者释放队列容量，不自动保证模型、优化器和数据进度已一起落盘。这一点直接关系到第 9 章的恢复协议。

### 5.1 用 batch 参数做第一轮验算

固定 [Qwen3-4B 示例脚本](https://github.com/THUDM/slime/blob/540ea919e45b8b929198abce008a103be9cfc779/scripts/run-qwen3-4B.sh) 中可看到：

- `--rollout-batch-size 32`：prompt 数。
- `--n-samples-per-prompt 8`：每题候选数。
- `--global-batch-size 256`：训练 batch 参数。

在无过滤、一次恰好消费完整 rollout 的理想情形下，`32×8=256`，数量能对上。但训练微批、packing、过滤和重新采样仍需查看实现与有效配置。

### 5.2 算法名称不能代替所有开关

该示例不仅指定 `grpo` 优势，还设置了无标准差归一化、逐 token loss、REINFORCE 型 policy loss 和采样校正相关选项。因此更准确的说法是“这份配置的组合目标”，而不是把它等同于论文最初的完整 GRPO 公式。

实践记录必须同时保留：优势估计器、标准差开关、loss 聚合、裁剪/校正、KL 系数和采样分布。后续比较才能说明究竟改了什么。

### 5.3 为什么本文不给一条直接执行该脚本的命令

核对的上游脚本含全局进程清理命令、作者环境路径和很长的响应上限。直接执行会混入与本机不匹配的资源假设。应先复制并审阅自己的启动配置，删除与任务无关的全局清理，再按隔离环境中的设备和数据修改。

这里的实践目标是理解配置并建立验证顺序；完整框架运行需要独立环境，不能由网站构建成功来证明。

## 6. 一个有验收标准的最小集成实验

选任一框架，第一次实验都可按同一序列进行：

| 阶段 | 小规模工作负载 | 验收证据 |
|---|---|---|
| 数据 | 4—16 个短 prompt，确定性规则奖励 | token ID、标签、chat template 可人工检查 |
| 生成 | 每题 2—4 个回答，短响应上限 | 无空组、终止原因和行为概率齐全 |
| 冻结回放 | 同一批 token 训练端只前向 | log probability 差异及 mask 统计 |
| 单次更新 | 一个 optimizer step | 有限梯度、参数变化、更新计数一致 |
| 同步 | 发布一次新权重 | 每个副本确认同一版本，固定输入评分改变 |
| 恢复 | 保存后重启并处理下一小批 | optimizer、global step、数据进度均正确 |

**固定回放不要重新采样回答。** 否则比较的差异同时包含模型执行误差和随机样本差异，无法定位训练/推理不一致。

还应先用只读的 `git rev-parse HEAD`、依赖版本输出和最终配置建立实验记录。安装或运行失败时，保留首次错误和最小复现，不通过随机升级一组依赖掩盖问题。

## 7. 选型问题应落到可验证约束

| 需求 | 要问的问题 |
|---|---|
| 单机教学 | 最小模型的训练与采样是否都能适配显存？依赖是否易复现？ |
| 大模型训练 | 模型结构和权重转换支持是否在所选版本可用？ |
| 多域奖励 | 是否方便按 domain 调度、监控和复核过滤？ |
| Agent RL | 环境异步、工具 mask、取消和续跑协议能否接入？ |
| 异步吞吐 | 版本延迟和校正是否有可观测指标及上界？ |
| 长任务运行 | checkpoint 是否覆盖队列、环境和训练状态？ |

做性能比较时，至少报告“验证质量达到同一目标所需 GPU 小时”；只报告 rollout tokens/s 会掩盖无效样本、失败重试和模型质量变化。

## 8. 自测与参考答案

**题 1：verl 的 rollout 配置写 `async`，是否说明训练在消费旧版本样本？**

参考答案：不能。还要看 trainer mode、队列及权重同步策略。异步引擎接口可以服务同步训练。

**题 2：ROLL 的一轮候选数是 512，训练日志却只有 384 条，首先查什么？**

参考答案：查过滤、重采样、按域配额和组完整性。先对齐 accepted/rejected 数量，再判断 batch 切分是否有误。

**题 3：slime 写 `advantage-estimator=grpo`，能否据此复现论文目标？**

参考答案：还不够。需要核对归一化、policy loss、token/sequence 聚合、KL 和采样校正等选项。

**题 4：某框架示例在作者集群可运行，为什么本机先做固定回放？**

参考答案：本机模型转换、tokenizer、精度和 kernel 可能不同。固定回放能在策略更新前隔离训练/推理一致性问题。
