## 📖 本章概述

优化器只能优化收到的数字。若奖励把“包含正确答案字符串”当成“解决了问题”，模型就可能学会罗列所有候选答案；若把评测服务断线都记作答错，训练就会受到基础设施故障干扰。

本章把奖励与评估当作训练系统的一等组件。前半回答“数字怎么产生”，后半回答“数字变好了，模型是否真的更好”。

## 📑 章节结构

### 5.1 可验证奖励与数据流水线

从原始题目进入系统开始，建立以下链条：

```text
题目与标准 → 去重/分组切分 → 采样轨迹 → 解析回答
→ 调用 verifier → 返回结构化结果 → 组合奖励 → 记录审计字段
```

一个 verifier 不应只返回 `0.0` 或 `1.0`，还应报告原因。例如 `incorrect`、`format_error`、`timeout`、`infrastructure_error` 代表不同事件；其中后两者是否进入训练，必须由任务语义与重试策略决定。

本节覆盖：

- 规则奖励、学习式结果奖励、过程奖励的适用范围。
- 精确数值比较与受限解析，避免文本匹配的捷径。
- 格式奖励、准确性奖励和成本惩罚如何组合。
- 生成代码在隔离执行环境中的资源与权限边界。
- 训练数据、答案、测试集和验证器版本如何形成可追溯记录。

### 5.2 评估指标与训练诊断

把指标分成三个层次：

| 层次 | 回答的问题 | 示例 |
|---|---|---|
| 任务质量 | 学会了什么 | 独立验证准确率、pass@k、分领域表现 |
| 优化状态 | 更新是否正常 | KL、entropy、clip fraction、梯度范数 |
| 系统效率 | 花了多少资源 | 有效 token/s、GPU 小时、打分延迟、版本滞后 |

这些指标必须同时解释。吞吐增加但有效样本比例下降，可能没有带来更多学习；reward 上升而独立评测下降，可能是在利用奖励漏洞。

本节用组合计数推导 pass@k，并手算 $n=5,c=2,k=2$ 的结果为 $0.7$。这比直接把“至少命中一次”当成模型单次成功率更清晰。

## 🧮 一个奖励优先级检查

设正确性 $c\in\{0,1\}$，格式分 $f\in[0,1]$，奖励为 $R=c+0.1f$。正确但格式差的回答奖励至少 1；错误但格式好的回答奖励至多 0.1，因此正确性优先级得到保障。

若再加范围未限制的长度奖励，这个保障可能立即失效。任何附加项都应先写清上下界，再检查总奖励排序。

## 🛠️ 实践产物

1. 一个含输入、输出、评分原因的 verifier 样例集。
2. 至少包含空答案、多个答案、极长输入、超时和服务失败的测试样本。
3. 固定验证 prompt、采样参数和 token 预算的评估配置。
4. 一张同时记录质量、更新状态与端到端成本的结果表。
5. 对最高奖励但人工质量较差样本的逐条复核记录。

## 🎯 自测与参考答案

**问题 1：代码答案超过运行时间限制，是否一律算 0 分？**

若时间限制是题目规范且执行环境健康，可以视为失败；若评测节点异常或队列超时，应作为基础设施事件处理。必须先判断事件来源。

**问题 2：pass@8 高于 pass@1，能否证明单次推理能力更强？**

不能。候选次数和预算不同。需要比较相同预算下的指标，并单独报告 pass@1。

**问题 3：训练 reward 变高时，下一步先看什么？**

查看固定验证集质量、回答长度、格式通过率和抽样文本，再结合 KL、entropy 与系统事件判断原因。
